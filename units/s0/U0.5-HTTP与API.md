**这个单元解决什么问题**

你后面要调的所有东西——Claude、GPT、DeepSeek、飞书、GitHub——本质上都是同一件事：**往一个网址发一个请求，收一个回复**。

## 步骤 1 · 理解一次请求发生了什么

### 这一步在做什么

在写代码之前，先看清楚「网络请求」这个黑盒里面是什么。

### 怎么做

用 `curl` 发一次请求，加 `-v` 看全过程：

```bash
curl -v https://api.github.com/users/torvalds
```

输出分三段，用符号区分：

- `>` 开头的是**你发出去的**
- `<` 开头的是**服务器回来的**
- `*` 开头的是连接过程的说明

### 请求长这样

```
> GET /users/torvalds HTTP/2
> Host: api.github.com
> User-Agent: curl/8.4.0
> Accept: */*
```

| 部分 | 叫什么 | 含义 |
|---|---|---|
| `GET` | 方法 | 我想干什么（取数据） |
| `/users/torvalds` | 路径 | 要哪个资源 |
| `HTTP/2` | 协议版本 | |
| 下面几行 | 请求头（headers） | 附加信息：我是谁、我能接受什么格式 |

### 响应长这样

```
< HTTP/2 200
< content-type: application/json; charset=utf-8
< x-ratelimit-remaining: 59
<
{"login":"torvalds","id":1024025,...}
```

| 部分 | 含义 |
|---|---|
| `200` | **状态码**，表示成功 |
| `content-type` | 返回的是什么格式 |
| 空行之后 | **响应体**（body），真正的数据 |

### 五个方法，够用了

| 方法 | 语义 | 例子 |
|---|---|---|
| `GET` | 取数据，**不应该改变任何东西** | 查用户信息 |
| `POST` | 创建新东西，或者「执行一个动作」 | 发消息、调模型 |
| `PUT` | 整个替换 | 覆盖一份配置 |
| `PATCH` | 局部更新 | 只改用户的昵称 |
| `DELETE` | 删除 | 删一条记录 |

**大模型 API 几乎全部是 POST**，因为你要传一大段内容（prompt）过去，而且每次调用都会产生新的回复。

### 状态码：看第一位数字就够

| 范围 | 含义 | 你该怎么办 |
|---|---|---|
| `2xx` | 成功 | 继续 |
| `3xx` | 重定向 | 跟着新地址走（客户端库通常自动处理） |
| `4xx` | **你错了** | 检查参数、密钥、权限。**重试没用** |
| `5xx` | **服务器错了** | 可以重试 |

需要单独记住的几个：

| 码 | 含义 | 常见原因 |
|---|---|---|
| `400` | 请求格式错 | JSON 写错了、少了必填字段 |
| `401` | 没认证 | 密钥没传、或者传错了 |
| `403` | 认证了但没权限 | 密钥有效但没开通这个能力 |
| `404` | 找不到 | 网址写错了 |
| `429` | **限流** | 调太快了，**要等一下再试** |
| `500`/`502`/`503` | 服务器故障 | 可以重试 |

**`4xx` 和 `5xx` 的区别决定了你要不要重试，这在 S1 写 API 封装时是核心逻辑。**

### 可能卡在哪

**`curl: (6) Could not resolve host`**

域名解析失败。检查网址拼写，检查网络。

**`curl: (60) SSL certificate problem`**

证书问题。可能是你在公司网络里有中间人代理。临时可以加 `-k` 跳过验证（**只在调试时用，生产代码绝不能这样**）。

**返回一大坨 JSON 看不清**

管道给 `jq` 格式化：

```bash
brew install jq
# jq 不带参数就是把整个 JSON 缩进展开，肉眼能看
curl -s https://api.github.com/users/torvalds | jq
# 字段多的时候直接挑你关心的那几个，省得在几百行里翻
curl -s https://api.github.com/users/torvalds | jq '.name, .public_repos'
```

`-s` 是安静模式，不显示进度条。

### 背后的逻辑

**HTTP 是无状态的。**

意思是：服务器不记得你上一次请求是什么。每个请求都必须自带全部信息（包括「我是谁」）。

这就是为什么每次调用都要带认证头，也是为什么大模型 API 每次都要把**完整的对话历史**发过去——服务器根本不记得你们聊过什么。

**理解这一点，你就理解了为什么 token 成本随对话轮数增长。** 第 10 轮对话时，你其实是把前 9 轮全部重发了一遍。S1 学上下文管理、S4 学成本优化，根子都在这里。

## 步骤 2 · 认证：证明你是你

### 这一步在做什么

学会三种主流的「带上身份」的方式。

### 三种方式

**方式一：请求头带 Bearer Token（最常见）**

```bash
curl https://api.example.com/x \
  -H "Authorization: Bearer sk-xxxxx"
```

OpenAI、大多数现代 API 用这个。

**方式二：自定义请求头**

```bash
# 密钥走自定义头 x-api-key，不是 Authorization
# anthropic-version 是必填的，缺了会被拒掉
curl https://api.anthropic.com/v1/messages \
  -H "x-api-key: sk-ant-xxxxx" \
  -H "anthropic-version: 2023-06-01"
```

Anthropic 用这个。

**方式三：OAuth**

用户跳转到授权页面 → 同意 → 拿到 code → 换 token。飞书、GitHub 的用户级授权走这套。**现阶段了解即可，不用手写。**

### 可能卡在哪

**401 Unauthorized**

按顺序排查：

1. 密钥有没有真的传进去（打印出来看看，注意别打印完整密钥）
2. 头的名字对不对（`Authorization` 还是 `x-api-key`）
3. `Bearer ` 后面有没有空格
4. 密钥有没有过期或被删
5. 有没有把测试环境的密钥用在生产环境

**403 Forbidden**

密钥是对的，但这个密钥没有这个权限。去控制台看权限设置。

### 背后的逻辑

为什么认证信息放在**请求头**而不是 URL 里？

因为 URL 会被记录在很多地方：浏览器历史、服务器访问日志、代理日志、Referer 头。**密钥放在 URL 里等于到处泄露。**

请求头不会被这些地方记录（正常配置下），而且 HTTPS 会加密整个请求头。

同理，你在写日志时也要注意：**不要把完整的请求头打进日志。**

## 步骤 3 · 密钥管理

### 这一步在做什么

**本单元最重要的一步。** 建立一个从今天起再也不违反的规矩：密钥绝不出现在代码里。

### 为什么这么严重

GitHub 上有自动扫描机器人，专门找提交上去的密钥。**从你 push 到密钥被盗刷，通常不超过几分钟。**

有人一夜之间被刷掉几万块的云账单，就是这么来的。

### 怎么做

**第一步：建 `.env` 文件**

```bash
cd s0-foundation/csvstats
# 用 <<'EOF' 而不是 <<EOF：加了单引号 shell 就不会展开 $ 和反引号，
# 密钥里带特殊字符时才不会被悄悄改掉
cat > .env <<'EOF'
GITHUB_TOKEN=ghp_xxxxxxxx
DEEPSEEK_API_KEY=sk-xxxxxxxx
EOF
```

**第二步：确认它被 git 忽略**

```bash
git status
```

**`.env` 不应该出现在列表里。** 如果出现了，立刻在 `.gitignore` 里加上 `.env`。

**第三步：代码里这样读**

```bash
uv add python-dotenv
```

```python
import os
from dotenv import load_dotenv

load_dotenv()                                  # 把 .env 里的键值对灌进环境变量

# 走 os.getenv 而不是自己读 .env 文件：本地读 .env、线上读真正的环境变量，
# 两种来源同一份代码都能用
TOKEN = os.getenv("GITHUB_TOKEN")
if not TOKEN:
    # 启动时就报错，否则问题会拖到第一次发请求时才变成一个莫名其妙的 401
    raise RuntimeError("缺少 GITHUB_TOKEN，请检查 .env 文件")
```

**第四步：给别人留个模板**

```bash
# 只写变量名和占位值，不写真实密钥，所以这份文件可以安全地提交
cat > .env.example <<'EOF'
GITHUB_TOKEN=你的_github_token
DEEPSEEK_API_KEY=你的_deepseek_key
EOF
git add .env.example
```

`.env.example` **要提交**，它告诉别人需要配哪些变量，但不含真实值。

### 可能卡在哪

**已经把密钥提交上去了**

**第一优先级是去服务商后台作废这个密钥，重新生成一个。**

删掉提交是次要的——Git 历史里还有，而且可能已经被人克隆走了。作废密钥才是真正解决问题。

**`load_dotenv()` 没读到**

它默认从「当前工作目录」往上找 `.env`。如果你在别的目录运行，可能找不到。显式指定：

```python
from pathlib import Path

# 以「这个源文件的位置」为基准往上找，结果就和你在哪个目录启动程序无关了
load_dotenv(Path(__file__).parent.parent.parent / ".env")
```

**部署到服务器后没有 .env 怎么办**

服务器上用真正的环境变量，或者云平台的密钥管理服务。`os.getenv` 两种都能读——**这就是为什么要用 `os.getenv` 而不是直接读文件**，代码不用改。

### 背后的逻辑

这条原则叫「**配置与代码分离**」，是 12-Factor App 的第三条（你在 S4 会完整学这十二条）。

核心思想：**同一份代码，在开发、测试、生产环境应该完全一样，区别只在配置。** 如果密钥写死在代码里，你就得为每个环境维护一份代码，这是灾难的开始。

## 步骤 4 · 用 Python 发请求

### 这一步在做什么

把 curl 干的事用代码做。

### 怎么做

```bash
uv add httpx
```

```python
import httpx

# GET：公开接口，不用认证也能拿到数据
r = httpx.get("https://api.github.com/users/torvalds")
print(r.status_code)
print(r.json()["name"])

# 带认证和参数
r = httpx.get(
    "https://api.github.com/user/repos",
    headers={"Authorization": f"Bearer {TOKEN}"},   # 密钥来自 .env，别写死在这
    params={"per_page": 10, "sort": "updated"},     # 会被拼成 ?per_page=10&sort=updated
    timeout=10.0,                                   # 必设，否则服务器不回话时程序永远卡住
)
r.raise_for_status()          # 4xx/5xx 时抛异常
data = r.json()

# POST JSON
r = httpx.post(
    "https://api.example.com/items",
    headers={"Authorization": f"Bearer {TOKEN}"},
    json={"name": "测试", "quantity": 3},  # 用 json= 会自动序列化并设 Content-Type
    timeout=30.0,                          # 写操作通常比读慢，超时给宽一点
)
```

**复用连接（调多次时快很多）**：

```python
# Client 会复用底层 TCP 连接，省掉每次请求重新握手和 TLS 协商的开销；
# base_url、headers、timeout 在这里设一次，后面每个请求自动带上
with httpx.Client(
    base_url="https://api.github.com",
    headers={"Authorization": f"Bearer {TOKEN}"},
    timeout=10.0,
) as client:
    r1 = client.get("/users/torvalds")      # 只写路径，会自动拼上 base_url
    r2 = client.get("/users/gvanrossum")    # 这次不用再重建连接
```

### 为什么用 httpx 不用 requests

`requests` 更老更有名，但 `httpx` 有一个决定性优势：**它同时支持同步和异步**，API 几乎一样。

你在 U0.6 之后所有代码都是异步的，到时候只要把 `httpx.get` 换成 `await client.get`，其余不变。用 requests 的话要整个重写。

### 可能卡在哪

**`timeout` 一定要设**

不设的话，服务器不响应时你的程序会永远卡住。**这是生产事故的常见来源。**

大模型 API 的响应可能要几十秒，超时要设得长一些（60 到 300 秒），但绝不能不设。

**`r.json()` 报 JSONDecodeError**

返回的不是 JSON。先看看到底返回了什么：

```python
print(r.status_code)
print(r.text[:500])
```

常见原因：请求出错返回了 HTML 错误页、或者返回的是流式数据。

**中文变成了 `中文`**

那是 JSON 的转义形式，`r.json()` 解析后就是正常中文。只有你自己 `json.dumps` 时要加 `ensure_ascii=False`。

### 背后的逻辑

`r.raise_for_status()` 这个方法值得说一下。默认情况下 httpx **不会**因为 404 或 500 抛异常——它认为「收到响应」就是成功了，状态码是业务层的事。

所以你必须显式检查。两种风格：

```python
# 风格一：让它抛异常
r.raise_for_status()

# 风格二：自己判断
if r.status_code == 429:
    wait_and_retry()     # 限流，等一会儿再来还有机会成功
elif r.status_code >= 400:
    log_error()          # 其余错误重试也没用，记下来交给上层处理
```

**调大模型 API 时你会用风格二**，因为 429（限流）需要重试，而 400（参数错）重试没用。

## 步骤 5 · 重试与退避

### 这一步在做什么

处理真实世界的不稳定：网络抖动、服务器偶发故障、限流。

### 什么该重试，什么不该

| 情况 | 重试？ | 原因 |
|---|---|---|
| 网络超时 | 是 | 可能只是抖动 |
| `429` 限流 | 是，但要**等** | 立刻重试只会继续被限 |
| `500`/`502`/`503` | 是 | 服务器临时故障 |
| `400` 参数错 | **否** | 参数不改，重试一万次也一样 |
| `401`/`403` 认证问题 | **否** | 同上 |
| `404` | **否** | 同上 |

**盲目重试不可重试的错误，只会浪费时间和钱。** 这在调大模型 API 时尤其明显——重试一次就是一次计费。

### 怎么做

```bash
uv add tenacity
```

```python
import httpx
from tenacity import (
    retry, stop_after_attempt, wait_exponential,
    retry_if_exception_type,
)

class RetryableError(Exception):
    """自定义一个异常类型，把「值得重试」和「重试也没用」在类型层面分开。"""


@retry(
    stop=stop_after_attempt(4),                              # 最多 4 次
    wait=wait_exponential(multiplier=1, min=1, max=30),      # 1s 2s 4s 8s...
    retry=retry_if_exception_type(RetryableError),           # 只有这一类异常才重试
    reraise=True,                                            # 次数用尽后抛原始异常，方便排查
)
def call(client: httpx.Client, path: str) -> dict:
    """发一次请求，并把状态码翻译成「该不该重试」。"""
    r = client.get(path)
    # 429 是被限流、5xx 是服务端故障，这两类等一会儿再来通常能成
    if r.status_code == 429 or r.status_code >= 500:
        raise RetryableError(f"{r.status_code}: {r.text[:200]}")
    # 剩下的 4xx 是请求本身写错了，重试多少次结果都一样，直接抛出去
    r.raise_for_status()
    return r.json()
```

### 什么是指数退避

第 1 次失败等 1 秒，第 2 次等 2 秒，第 3 次等 4 秒，翻倍增长。

**为什么不固定等 1 秒？** 因为如果服务器正在过载，所有客户端都每秒重试一次，只会让它更过载。指数退避让压力自动降下来。

**生产级的做法还要加抖动（jitter）**：在等待时间上加一个随机偏移，避免所有客户端在同一时刻一起重试。

### 可能卡在哪

**429 时服务器告诉了你该等多久**

很多 API 在 429 响应里带 `Retry-After` 头，单位是秒。**优先用它**，比你自己算的准：

```python
if r.status_code == 429:
    # 服务器给了 Retry-After 就听它的，没给才用自己的默认值兜底
    retry_after = int(r.headers.get("Retry-After", 5))
    time.sleep(retry_after)
```

**重试把钱花光了**

大模型 API 每次调用都计费。**一定要设最大重试次数**，并且在日志里记录重试发生了几次。S1 会让你加上成本统计。

### 背后的逻辑

这套「重试 + 退避 + 区分错误类型」的模式，是所有分布式系统的基础功课。

它背后的假设是：**网络是不可靠的，远程服务是会挂的，这是常态而不是异常。** 你的代码必须假设每一次网络调用都可能失败。

Agent 的场景把这个问题放大了：一次任务可能调 20 次工具、10 次模型，任何一次失败都可能让整个任务白跑。S4 学的断点续跑，就是为了解决这个问题。
