# U0.4 · Python 工程化（5 小时）

**这个单元解决什么问题**

上个单元你手里是「脚本」——一个文件，自己能跑。这个单元把它变成「项目」——有结构、有依赖声明、别人拿去能跑、以后能维护。

**这一步的价值不在于代码变好看了**，而在于：三个月后你回来看还能看懂，换台电脑能装起来，别人能贡献。这是「写代码的人」和「做软件的人」的分界线。

**这个单元的姿态**：代码由 agent 写，你做三件事——**下指令、验收、读懂**。每一步都给你一段可以直接粘贴给 Claude Code 或 Codex 的指令，一组验收命令和它应该产出的结果，以及两三个你必须能口头回答的问题。**agent 写出来能跑，不等于写对了**。这个单元教你在验收时看出「能跑但方向不对」。

**学完你能做到**：让 agent 建出标准 Python 项目，并且能判断它的依赖管理、模块拆分、类型注解和数据校验是不是合格。

## 步骤 1 · 虚拟环境与 uv（先想清楚再动手）

### 这一步在做什么

解决一个你迟早会撞上的问题：**项目 A 需要某个库的 1.0 版，项目 B 需要 2.0 版，装哪个？**

假设没有虚拟环境，所有库都装在系统 Python 里。某天项目 B 需要升级 requests，你升了，**项目 A 突然跑不了了**。这在真实开发里几乎每周发生一次，行话叫「依赖地狱」。解法是给每个项目一个独立的 Python 环境，互不干扰，这就是**虚拟环境**。

### 让 agent 做

```
在 ~/ai-agent-roadmap/s0-foundation/ 下用 uv 新建一个名为 csvstats 的 Python 项目。
要求：
- 用 `uv init csvstats`，不要手写 pyproject.toml，也不要用 requirements.txt
- 用 `uv add httpx` 加一个依赖
- 完成后运行 `uv run python main.py` 确认能跑
- 把 uv 生成的每个文件是干什么的，用一张表告诉我
- 不要提交 .venv，确认 .gitignore 里有它
```

### 你验收

```bash
cd ~/ai-agent-roadmap/s0-foundation/csvstats
ls -a
uv run python main.py
git status --short
```

应该看到：`pyproject.toml`、`uv.lock`、`.python-version`、`.venv/`、`main.py`；`uv run` 能打出一行 Hello；`git status` 里**没有** `.venv/`。

`pyproject.toml` 里应该有一行 `"httpx>=..."`，`uv.lock` 里应该有精确到小版本的 `httpx==...`。两个文件都要在 `git status` 里出现，**两个都要提交**。

### 你读懂

1. `pyproject.toml` 和 `uv.lock` 分别记录什么？（前者「我想要什么」，如 `httpx>=0.27`；后者「实际装了什么」，精确到每个间接依赖的版本。锁文件保证你、同事、服务器装的是完全一样的东西。）
2. 为什么是 `uv run python` 而不是 `python3`？（`uv run` 自动切进这个项目的虚拟环境。）
3. 如果 agent 给你生成了 `requirements.txt`，你该让它改吗？（该。见下面的坑。）

### 可能卡在哪

**agent 写出来能跑，但方向不对（本单元第一个 vibe coding 坑）**

agent 的训练语料里有海量 2020 年以前的 Python 项目，它很容易给你：

- `requirements.txt` + `pip install`，而不是 `pyproject.toml` + `uv`
- `python3 -m venv .venv && source .venv/bin/activate`，然后让你每次记得激活
- 把依赖直接装进系统 Python

**识别方法**：验收时 `ls` 一眼看根目录。有 `requirements.txt` 没有 `uv.lock`，就是走了老路。**不是它跑不起来，是它把你带进了三个月后会痛的路线。** 让它按指令重做，指令里明确「用 uv，不要 requirements.txt」——这就是为什么上面那段指令要写「不要」。

**`.venv` 被提交进 git 了**

`.venv` 有几百 MB，绝对不能提交。检查 `.gitignore` 里有没有 `.venv/`（仓库里已经有了）。

**已经用 pip 装了一堆东西到系统 Python 里**

现阶段不影响。以后想清理，`pip3 list` 看装了什么，`pip3 uninstall 包名` 卸载。

### 背后的逻辑

**虚拟环境本质上是什么？**

`.venv/` 就是一个普通目录：

```
.venv/
├── bin/python        ← 指向真实 Python 的软链接
└── lib/python3.13/site-packages/    ← 装的库都在这
```

「激活」虚拟环境做的事，只是**把 `.venv/bin` 加到 PATH 最前面**。这样你敲 `python` 时找到的是虚拟环境里那个，它会去自己的 `site-packages` 找库。

又是 PATH。U0.1 学的概念在这里又用上了。**这种「同一个机制反复出现」的感觉，就是你开始入门的标志。**

## 步骤 2 · 把脚本重构成包

### 这一步在做什么

把 U0.3 步骤 9 写的单文件 `s0-foundation/py-basics/csv_stats.py` 拆成有结构的模块。

**先把它和数据搬过来**（当前在 `s0-foundation/csvstats/`）：

```bash
cp ../py-basics/csv_stats.py .
cp ../py-basics/sales.csv ../py-basics/sales_dirty.csv .
python3 csv_stats.py sales.csv        # 先确认搬过来还能跑
```

一个文件写到 300 行以上就没法维护了。拆分的原则是**按职责**：读数据的归读数据，算统计的归算统计，命令行界面归命令行界面。好处很具体：改统计逻辑时不用看读文件的代码；写测试时可以单独测统计函数，不用真的读文件。

### 让 agent 做

```
把当前目录的 csv_stats.py 重构成 src-layout 的 Python 包，结构如下：
src/csvstats/__init__.py、reader.py、stats.py、cli.py，tests/ 先留空。
函数搬运规则：parse_amount 和 read_rows 进 reader.py，summarize 进 stats.py，
write_result 进 reader.py，main 进 cli.py。
要求：
- 不改任何函数的逻辑，只搬家
- summarize 必须保持纯函数：不读文件、不打印、不写盘
- 模块之间用绝对导入（from csvstats.reader import ...），不要用相对导入
- 在 pyproject.toml 里配 [project.scripts]，让 `uv run csvstats sales.csv` 能跑
- 删掉根目录的 csv_stats.py 和 main.py
- 完成后运行 `uv sync && uv run csvstats sales.csv` 和 `uv run csvstats sales_dirty.csv`，
  两次的 stats.json 必须完全一致
```

**U0.3 那四个函数按这张表对号入座**，一个都不用重写：

| U0.3 的函数 | 搬到哪 | 为什么 |
|---|---|---|
| `parse_amount` | `reader.py` | 它是「把文本变成数据」的一部分，属于读取环节 |
| `read_rows` | `reader.py` | 读 CSV |
| `summarize` | `stats.py` | 纯计算，不碰文件——**所以 U0.7 能不读文件就测它** |
| `write_result` | `reader.py` 或新建 `writer.py` | 落盘，属于 IO |
| `main` | `cli.py` | 命令行参数解析和串流程 |

### 你验收

```bash
tree src tests 2>/dev/null || find src tests -type f
uv sync
uv run csvstats sales.csv && cp stats.json a.json
uv run csvstats sales_dirty.csv && diff a.json stats.json && echo "两份完全一致"
grep -n "^from\|^import" src/csvstats/*.py
```

应该看到：四个模块文件；两条命令都跑通且输出「两份完全一致」；import 全是 `from csvstats.xxx import ...` 这种绝对导入，**没有** `from .reader import`。

再打开 `src/csvstats/stats.py` 看一眼：里面**不应该**出现 `open(`、`print(`、`json.dump(`。有就说明 `summarize` 不纯了，让 agent 改。

### 你读懂

对照这段，它是 agent 应该写出来的 `cli.py` 开头和 `pyproject.toml` 关键行：

```python
# src/csvstats/cli.py
# 用「包名.模块名」的绝对导入，而不是 from .reader import：
# 绝对导入在 python -m 和直接跑文件两种方式下表现一致，不容易踩坑
from csvstats.reader import read_rows
from csvstats.stats import summarize
```

```toml
[project.scripts]
# 左边是生成的命令名，右边是「模块路径:函数名」，装包时会据此生成一个可执行入口
csvstats = "csvstats.cli:main"

[tool.hatch.build.targets.wheel]
packages = ["src/csvstats"]            # 关键一行：包在 src/ 下，不在项目根目录
```

1. 为什么 `summarize` 要是纯函数？（给它一个 list 就返回结果，U0.7 测它时不用造文件。）
2. `uv run csvstats` 这个命令是从哪来的？（`[project.scripts]` 那一行，`uv sync` 时生成的。）
3. `__init__.py` 是干嘛的？（标记「这个目录是一个包」，可以是空文件。）

### 可能卡在哪

**agent 把所有东西塞进一个文件，或者拆是拆了但互相 import 成一团**

典型表现：`reader.py` 里 `from csvstats.cli import ...`，形成循环依赖；或者四个文件建了，但 `cli.py` 里还是 150 行什么都干。**识别方法**：`wc -l src/csvstats/*.py`，`cli.py` 应该是最短的那个（只串流程）；`grep import` 的结果里，`stats.py` 不应该 import 任何 csvstats 自己的模块。

**`ModuleNotFoundError: No module named 'csvstats'`**

Python 不知道去 `src/` 下面找。`uv sync` 会把项目本身以可编辑模式装进虚拟环境（软链接，改代码立刻生效）。agent 漏了这步就报这个错。

**agent 用了 `uv run python src/csvstats/cli.py` 这种跑法**

直接跑文件路径，import 会出问题。正确的两种：`uv run csvstats`（配了入口点）或 `uv run python -m csvstats.cli`。

### 背后的逻辑

**为什么代码要放在 `src/` 里？**

这叫 src-layout。flat-layout（包直接放项目根目录）时，你在根目录跑测试，Python 会直接从当前目录找到你的包，**哪怕你根本没装它**。这会掩盖打包配置的问题——本地跑得好好的，别人 `pip install` 之后发现少文件。

src-layout 强制你必须真的装了包才能 import，**测试的是「装好之后的样子」，和用户拿到的一致**。

## 步骤 3 · 类型注解与数据类

### 这一步在做什么

给代码标注「这个变量应该是什么类型」，让工具能提前发现错误；并把「总是一起出现的一组数据」打包成数据类。

Python 不检查类型，所以 `calc_mean("abc")` 要跑到那一行才炸。加上 `def calc_mean(numbers: list[float]) -> float:`，编辑器在你写调用的时候就标红。**注解不影响运行**，它的价值是：编辑器能准确补全、检查器能提前报错、**注解是不会过期的文档**。

**什么时候需要类**：一堆数据总是一起出现 → dataclass 打包；一个函数需要记住上次调用的状态 → 类；就是一段计算逻辑 → **用函数就够了，别硬套类**。

### 让 agent 做

```
给 src/csvstats/ 下所有函数补全类型注解：参数和返回值都要，不返回值的写 -> None。
容器类型要写内部类型（list[float]，不是 list）。可能为 None 的写 X | None，不用 Optional。
用 @dataclass 定义一个 GroupResult(category: str, count: int, mean: float)，
让 summarize 返回 dict[str, GroupResult] 而不是嵌套 dict，write_result 相应调整。
然后 `uv add --dev ty`，运行 `uv run ty check src/`，把报的错改到零。
不许用 Any 或 # type: ignore 来消掉错误。
```

### 你验收

```bash
uv run ty check src/
grep -rn "Any\|type: ignore" src/
grep -n "def " src/csvstats/*.py
```

应该看到：`ty check` 零报错；第二条 grep **没有输出**；第三条里每个 `def` 都带 `->`。

### 你读懂

```python
from dataclasses import dataclass

# 只装数据、没有行为，这种就别手写 __init__ 了
@dataclass
class GroupResult:
    category: str        # 字段顺序就是位置参数的顺序
    count: int
    mean: float

# 函数：参数和返回值都标，这是收益最大的地方
def summarize(rows: list[dict[str, str | float]], group_column: str, value_column: str) -> dict[str, GroupResult]:
    ...
```

1. `@dataclass` 替你生成了什么？（`__init__`、`__repr__`、`__eq__`，不用它这三样要写十几行。）
2. 注解会影响程序运行吗？（不会，运行时完全忽略。它是给编辑器和检查器看的。）
3. 如果 agent 在 dataclass 里写了 `items: list = []`，会怎样？（dataclass 直接报 `ValueError: mutable default`，要改成 `field(default_factory=list)`。这和 U0.3 的可变默认参数是同一个坑。）

### 可能卡在哪

**agent 用 `Any` 或 `# type: ignore` 把检查器「哄」过去（本单元第二个 vibe coding 坑）**

`ty check` 显示零报错，你很满意，但其实 agent 在报错的地方写了 `x: Any` 或行尾加了 `# type: ignore`。**这不是修好了，是把报警器拔了。** 识别方法就是验收里那条 `grep -rn "Any\|type: ignore" src/`，它必须没有输出。同理，如果 agent 把 `pyproject.toml` 里检查器的严格度调低了，也是同一类事。**规则：任何让报错消失但不改代码的操作，都要问它为什么。**

**报一堆错，不知道从哪改起**

从函数签名开始：先给所有参数和返回值加注解，再处理内部变量。错误有依赖关系，改了上游下游可能自动就好了。

**`self` 是什么**

如果 agent 写了普通类，你会看到每个方法第一个参数是 `self`。它指「调用这个方法的那个对象」：你写 `s.process(row)`，Python 实际执行 `StatsCollector.process(s, row)`。属性必须用 `self.` 前缀，否则只是方法内部的临时变量。

### 背后的逻辑

**`@dataclass` 上面那个 `@` 是什么？**

叫**装饰器**：接收函数或类，返回改造后的版本。`@dataclass class A` 完全等价于 `class A; A = dataclass(A)`。你不需要会写，但要能认出它。后面会大量遇到：`@app.get("/")`（FastAPI 路由）、`@pytest.fixture`（测试）。

**为什么 Python 要事后加类型？**

1991 年设计时动态类型被认为是优点。但代码到几万行、几十个人协作时，「这个参数到底该传什么」变成巨大沟通成本，所以 2014 年引入了**可选的**类型注解。关键词是「可选」：你可以渐进式地加——先核心模块，其余以后再说。

## 步骤 4 · Pydantic：数据校验

### 这一步在做什么

**这是本单元最重要的一步，因为它是整个 S1、S2 的基础。**

类型注解只是「提示」，运行时不检查。Pydantic 让类型注解真正生效：**数据进来先校验，不合格直接拒绝。**

你在 S1 会遇到这个场景：大模型返回一段 JSON，它可能少一个字段、把数字写成字符串、自己发明一个枚举值。不校验的话，这些错误会一路传下去，在一个完全不相干的地方崩掉。**Pydantic 让错误在最早的地方暴露，并且告诉你具体哪个字段错了。**

### 让 agent 做

```
`uv add pydantic`，然后在 src/csvstats/models.py 里定义一个 Pydantic 模型 SalesRow，
对应 sales.csv 的一行：order_id: int，category: str（不能为空白），amount: float（>= 0），city: str。
用 Pydantic v2 的写法（field_validator、model_validate），不要用 v1 的 @validator。
让 read_rows 用 SalesRow 校验每一行，校验失败的行记入 skipped，错误信息要包含行号和 Pydantic 给出的字段名。
跑 `uv run csvstats sales_dirty.csv`，三条坏行必须被跳过并报告，stats.json 和干净文件的结果一致。
```

### 你验收

```bash
uv run csvstats sales_dirty.csv
uv run python -c "
from csvstats.models import SalesRow
try:
    SalesRow(order_id=1, category='家电', amount=-5, city='北京')
except Exception as e:
    print(type(e).__name__); print(e)
"
grep -n "@validator\|\.dict()\|parse_obj" src/csvstats/*.py
```

应该看到：三条「第 2x 行」的跳过报告；第二条打印 `ValidationError`，错误信息里有 `amount` 和 `greater than or equal to 0`；第三条 grep **没有输出**（有就是 v1 写法）。

### 你读懂

```python
from pydantic import BaseModel, Field, field_validator

# 继承 BaseModel 之后，类型注解不再只是提示，构造对象时会真的逐个字段检查
class SalesRow(BaseModel):
    order_id: int
    category: str
    amount: float = Field(ge=0)          # ge = 大于等于 0，负数直接拒绝
    city: str

    # 内置规则表达不了的条件写成 field_validator；返回值会替换掉原值
    @field_validator("category")
    @classmethod
    def category_not_blank(cls, v: str) -> str:
        if not v.strip():
            raise ValueError("分类不能是空白")
        return v.strip()
```

1. `SalesRow(amount="1200")` 会报错还是通过？（通过，Pydantic 默认把 `"1200"` 转成 `1200.0`。模型经常把数字写成字符串，这个默认行为省掉一堆 `float()`。）
2. 什么数据该用 Pydantic，什么用 dataclass？（**来自外部**的——用户输入、API 响应、文件、模型输出——用 Pydantic，因为要校验；程序内部造的、你能保证正确的，用 dataclass。）
3. ValidationError 的三行分别是什么？（出错的模型、出错的字段、为什么错以及你传的是什么。**从第二行开始读。**）

### 可能卡在哪

**agent 用了 Pydantic v1 的写法**

网上大量教程还是 v1，agent 也会混用。对照表：

| v1 | v2 |
|---|---|
| `@validator` | `@field_validator` |
| `.dict()` | `.model_dump()` |
| `.json()` | `.model_dump_json()` |
| `parse_obj()` | `model_validate()` |

**你用的是 v2**。验收里那条 grep 就是查这个。

**agent 校验是加了，但校验失败时 `except Exception: pass`**

三条坏行确实被跳过了，但 skipped 里没有任何信息。这是 U0.3 说过的「最糟糕的代码」：错误静默发生。**识别方法**：跑 `sales_dirty.csv` 时必须看到带行号的报告。

### 背后的逻辑

Pydantic 做的事叫「**边界校验**」：在数据进入系统的那一刻检查它，一旦通过，内部代码就可以放心假设数据是干净的。这个思路叫「**Parse, don't validate**」——不要到处写 `if x is None`，而是在入口把不合格的数据挡在外面。

你在 S1 做结构化输出、S2 定义工具参数、U0.6 写 FastAPI 时，用的都是同一个 Pydantic 模型。**它是整个技术栈的粘合剂。**

## 步骤 5 · 日志与代码风格工具

### 这一步在做什么

把 `print` 换成正规的日志，并让工具自动保持代码整洁。

print 做不到：区分重要程度、上线后不删代码就关掉调试输出、知道是哪个模块打的、带时间戳。到 S3 你要把日志和 trace 关联起来，那时 print 完全不够用。

### 让 agent 做

```
1. 把 src/csvstats/ 里所有 print 换成 logging：每个模块顶部 logger = logging.getLogger(__name__)，
   只在 cli.py 的 main 里调一次 logging.basicConfig(level=INFO, format 含时间、级别、模块名)。
   跳过坏行用 logger.warning，文件不存在用 logger.error 然后 raise。
   日志消息用 %s 占位符，不要用 f-string。
2. `uv add --dev ruff`，在 pyproject.toml 配 [tool.ruff]：line-length 88，
   lint 规则选 E、F、I、UP、B。运行 `uv run ruff check --fix src/ && uv run ruff format src/`。
3. 跑 `uv run csvstats sales_dirty.csv`，把输出贴给我看。
```

### 你验收

### 你读懂

```python
import logging

# 每个模块建自己的 logger，__name__ 是当前模块名，
# 这样日志里能看出是谁打的，也能按包名分层控制级别
logger = logging.getLogger(__name__)

def read_rows(path):
    logger.info("开始读取 %s", path)
    try:
        ...
    except FileNotFoundError:
        # 先记日志留下现场，再 raise 把异常继续抛给调用方，千万别 return None 把错误吞掉
        logger.error("文件不存在：%s", path)
        raise
```

1. `basicConfig` 为什么只能在入口调一次？（它只有第一次调用生效；库代码里调会覆盖使用者自己的配置。）
2. `logger.info("x=%s", x)` 比 `logger.info(f"x={x}")` 好在哪？（前者只有真的要输出时才拼字符串，日志量大时差别明显。）
3. `ruff check` 和 `ruff format` 分别干什么？（linter 找可疑写法，formatter 改样子不改逻辑。）

### 可能卡在哪

**配了 logging 但什么都不输出**

`basicConfig` 默认级别是 WARNING，`logger.info()` 不会显示。要 `level=logging.INFO`。

**格式化把代码改了**

这是它的工作。**不要跟格式化工具争论。** 统一风格的价值远大于个人偏好。

**第三方库刷屏**

接大模型 API 后 httpx 会把每个请求细节都打出来。`logging.getLogger("httpx").setLevel(logging.WARNING)` 单独压掉它——这利用的就是下面说的层级树。

### 背后的逻辑

`logging.getLogger(__name__)` 在 `src/csvstats/reader.py` 里拿到的名字是 `"csvstats.reader"`。logging 用点号构建层级树：`csvstats.reader` 是 `csvstats` 的子 logger，所以 `logging.getLogger("csvstats").setLevel(logging.DEBUG)` 一行就能给整个包开 DEBUG。

Ruff 的规则集里，`B` 那组查的是常见 bug 模式，**包括可变默认参数**——U0.3 让你亲手撞的那个坑，从这里开始由工具替你盯着。
