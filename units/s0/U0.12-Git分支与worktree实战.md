# U0.12 · Git 分支与 worktree 实战（8 小时）

**这个单元解决什么问题**

U0.2 教了 add / commit / branch / merge / 解冲突，够你一个人线性地写代码。**但你的实际工作方式不是线性的**——你同时开着 Claude Code、Codex CLI、Codex 桌面端，让它们并行干不同的活。

这种工作方式对 Git 的要求完全不同：**改动要能隔离、方案要能对比、错误要能捞回来、噪音要能整理掉。**

**这个单元补齐 U0.2 没教的那部分，全部围绕「多个 agent 同时改代码」这个真实场景。**

**学完你能做到**：三个 agent 并行互不干扰；让两个 agent 用不同思路做同一件事然后择优合并；agent 把仓库搞乱了能在两分钟内恢复到任意历史状态。

## 步骤 1 · reflog：先学会兜底，再敢放手

### 这一步在做什么

**这是整个单元最重要的一步，而 U0.2 完全没教。**

你敢让 agent 大改代码的前提，是你知道无论它干了什么都能退回去。`reflog` 就是那个保证。

### 它是什么

Git 记录了**你的 HEAD 指针每一次移动**——每次 commit、切分支、merge、rebase、reset，都留下一条记录。

```bash
git reflog
```

输出长这样：

```
a3f21b9 HEAD@{0}: commit: feat: 加日期过滤
7c4e2d1 HEAD@{1}: checkout: moving from main to feat/date-filter
7c4e2d1 HEAD@{2}: reset: moving to HEAD~3        ← 这里做了一次危险操作
9b8a5f3 HEAD@{3}: commit: 加了三个工具
2e1d4c7 HEAD@{4}: commit: 初始化
```

**每一行都是一个你可以回去的时间点。**

### 三种救命场景

**场景一：`git reset --hard` 之后发现搞错了**

```bash
git reset --hard HEAD~3        # 糟糕，三个提交没了
git reflog                     # 找到 reset 之前的那一行
git reset --hard 9b8a5f3       # 回去了
```

**场景二：分支删错了**

```bash
git branch -D feat/important   # 手滑删了，而且没合并过
git reflog                     # 找到那个分支最后的提交哈希
git branch feat/important a3f21b9    # 分支回来了
```

**场景三：agent 做了一堆改动，你想回到它开始之前**

```bash
git reflog | head -20          # 找到 agent 开始工作前的那一行
git reset --hard HEAD@{12}     # 回到那个时刻
```

### 亲手练一遍

**这一步必须做，因为你只有在没压力的时候练过，才会在真出事时想起来。**

```bash
cd ~/ai-agent-roadmap
git switch -c exp/reflog-practice

# 造三个提交
for i in 1 2 3; do
  echo "第 $i 次改动" >> reflog-test.txt
  git add reflog-test.txt && git commit -m "练习提交 $i"
done

git log --oneline -4          # 看到三个提交

# 故意搞砸
git reset --hard HEAD~3       # 三个提交全没了
git log --oneline -2          # 确认没了
cat reflog-test.txt 2>/dev/null || echo "文件也没了"

# 救回来
git reflog                    # 找到 "练习提交 3" 那行的哈希
git reset --hard <那个哈希>
git log --oneline -4          # 三个提交都回来了

# 清理
git switch main
git branch -D exp/reflog-practice
```

### 可能卡在哪

**reflog 里找不到我要的那条**

`git reflog` 默认只显示当前分支的 HEAD 移动。看某个具体分支的：

```bash
git reflog show feat/date-filter
```

**reflog 会保留多久**

默认 90 天（不可达的对象 30 天）。**所以它救得了你昨天的失误，救不了半年前的。**

**reset --hard 之前还没提交的改动能救回来吗**

**不能。** reflog 只记录提交过的状态。**这条要记牢：未提交的改动没有任何安全网。**

所以有一条纪律：**让 agent 大改之前，先 commit 一次**，哪怕是一个 WIP 提交。

### 背后的逻辑

回想 U0.2 讲的：分支只是一个指向提交的指针，提交本身通过父指针串成链。

**`git reset` 只是移动了指针，被「丢弃」的提交对象还在 `.git/objects` 里。** 它们只是暂时没有任何引用指向它们，Git 管这叫「不可达对象」。

reflog 保留了指向它们的引用，所以你能找回来。**直到 `git gc` 把过期的不可达对象真正清理掉。**

**理解这一点，你就理解了 Git 的一个核心特性：默认情况下，提交过的东西极难真正丢失。**

## 步骤 2 · stash：手上有活但要临时切走

### 这一步在做什么

U0.2 的速查表里提了一句 stash，但没练。多 agent 场景下你会频繁用到它。

### 典型场景

Agent A 正在改代码，你手上也改了几个文件还没提交。这时 agent B 报告说有个紧急 bug 要修，你得切到另一个分支。

**直接切会失败**：

```
error: Your local changes would be overwritten by checkout.
```

### 怎么做

```bash
git stash push -m "正在调的日期解析"     # 收起来，带上说明
git switch fix/urgent-bug
# ... 处理紧急问题 ...
git switch feat/date-filter
git stash pop                            # 取回来
```

**常用命令**：

```bash
git stash list                    # 看有哪些暂存
git stash show -p stash@{0}       # 看某个暂存的具体内容
git stash apply stash@{1}         # 取回但不删除记录
git stash drop stash@{0}          # 删掉某个
git stash push -u                 # -u 连未跟踪的新文件一起收
git stash push -- src/api.py      # 只收某个文件
```

### 三个坑

**一、stash 默认不收未跟踪的新文件**

Agent 新建的文件不在 stash 里，切分支后它们还在工作区。**加 `-u`。**

**二、pop 遇到冲突**

`git stash pop` 也可能冲突。解决冲突后，**stash 记录不会自动删除**，要手动 `git stash drop`。

**三、stash 是全局的，不属于任何分支**

在 A 分支 stash，切到 B 分支也能 pop 出来（可能冲突）。**stash 多了会混乱**，养成用 `-m` 加说明的习惯。

### 一条实践建议

**多 agent 场景下，stash 不如「随手提交到临时分支」可靠。**

```bash
git switch -c wip/tmp-$(date +%s)     # 临时分支
git add -A && git commit -m "WIP"
git switch 原分支
```

理由：stash 是一个扁平的栈，没有说明就分不清；临时分支有名字、有历史、能被 reflog 保护。

## 步骤 3 · 远程分支与 fetch

### 这一步在做什么

U0.2 只教了 push 和 pull。多机器、多 agent 场景下你需要理解得更细。

### fetch 和 pull 的区别

```bash
git fetch origin      # 只下载，不改你的工作区
git pull origin main  # 下载 + 自动合并到当前分支
```

**`pull` = `fetch` + `merge`。**

**为什么要知道这个区别**：`pull` 会自动合并，如果有冲突你会突然掉进冲突状态。`fetch` 之后你可以先看看远程改了什么，再决定怎么合。

```bash
git fetch origin
git log --oneline HEAD..origin/main     # 远程有什么我没有的
git log --oneline origin/main..HEAD     # 我有什么远程没有的
git diff HEAD origin/main               # 具体差异
```

**养成习惯：先 fetch 再看，别直接 pull。**

### 远程分支跟踪

```bash
git branch -vv                    # 看本地分支各自跟踪哪个远程分支
git push -u origin feat/xxx       # -u 建立跟踪关系，之后直接 git push 就行
git branch --set-upstream-to=origin/main main    # 事后建立跟踪
```

### 清理已删除的远程分支

PR 合并后 GitHub 通常会删掉远程分支，但你本地还留着引用：

```bash
git fetch --prune                 # 清理本地的过期远程分支引用
git remote prune origin           # 同上
```

**批量清理已合并的本地分支**：

```bash
git branch --merged main | grep -v -E '^\*|main' | xargs -r git branch -d
```

**多 agent 场景下分支会累积得很快，这条命令值得存进 shell alias。**

### force-push 的安全版本

有时你 rebase 或 amend 之后必须强推。**永远不要用 `--force`**：

```bash
git push --force                  # 危险：会无条件覆盖远程
git push --force-with-lease       # 安全：只有远程还是你上次见到的样子才推
```

**`--force-with-lease` 防的是**：你 rebase 期间别人（或另一台机器上的你）往远程推了新东西，用 `--force` 会把它抹掉，用 `--force-with-lease` 会被拒绝并提醒你。

## 步骤 4 · worktree：目录布局与真相

### 这一步在做什么

U0.10 讲了 worktree 的基本用法。这一步讲清楚它的机制，以及你会踩的坑。

### 三种创建方式

```bash
# 一、新建分支并创建 worktree（最常用）
git worktree add ../wt-feat-date -b feat/date-filter

# 二、用已有的本地分支
git worktree add ../wt-review fix/csv-crash

# 三、基于远程分支（比如要 review 别人的 PR）
git fetch origin pull/42/head:pr-42
git worktree add ../wt-pr42 pr-42

# 四、只是想看某个历史提交的代码，不需要分支（detached HEAD）
git worktree add --detach ../wt-old a3f21b9
```

**第三种在 code review 时特别有用**：你可以在一个独立目录里完整地跑别人的分支，而不影响你自己的工作。

### 目录布局

```
~/
├── ai-agent-roadmap/           ← 主工作目录
│   ├── .git/                   ← 真正的仓库数据在这里
│   │   └── worktrees/
│   │       ├── wt-feat-date/   ← 每个 worktree 的元数据
│   │       └── wt-review/
│   └── ...
├── wt-feat-date/
│   ├── .git                    ← 注意：这是一个「文件」，不是目录
│   └── ...
└── wt-review/
    ├── .git
    └── ...
```

**看一眼那个 `.git` 文件**：

```bash
cat ../wt-feat-date/.git
# gitdir: /Users/you/ai-agent-roadmap/.git/worktrees/wt-feat-date
```

**它就是一行指针**，指回主仓库里属于这个 worktree 的元数据目录。

**这解释了三件事**：

一、**为什么 worktree 几乎不占额外空间**——对象数据库（`.git/objects`）是共享的，worktree 只有工作区文件。

二、**为什么在一个 worktree 里提交，另一个立刻能看到那个 commit**——它们写的是同一个对象库。

三、**为什么删除 worktree 目录之后要 `git worktree prune`**——主仓库里的元数据不会自己消失。

### 共享什么，不共享什么

| | 共享 | 独立 |
|---|---|---|
| 提交历史与对象 | ✓ | |
| 分支与标签 | ✓ | |
| 远程配置 | ✓ | |
| stash | ✓ | |
| **仓库级 git config** | ✓ | |
| **hooks**（`.git/hooks`） | ✓ | |
| 工作区文件 | | ✓ |
| **当前检出的分支** | | ✓ |
| **`.gitignore` 里的东西**（.venv、node_modules、.env） | | ✓ |
| index（暂存区） | | ✓ |

**「hooks 共享」这一条值得注意**：你在主仓库配的 pre-commit hook，在所有 worktree 里都生效。这通常是好事。

**「.gitignore 里的东西独立」是最大的坑**——见下一步。

## 步骤 5 · worktree 的四个坑

### 坑一：新 worktree 里没有依赖和密钥

`.venv/`、`node_modules/`、`.env` 都在 `.gitignore` 里，所以不会出现在新 worktree 里。

```bash
cd ../wt-feat-date
uv run pytest         # 报错：找不到模块
cat .env              # 报错：文件不存在
```

**解法：写一个初始化脚本。**

```bash
# ~/bin/wt-new
#!/bin/bash
set -euo pipefail

branch="${1:?用法: wt-new <分支名> [起点]}"
base="${2:-HEAD}"

# 找到主仓库根目录 —— 在任何 worktree 里执行都能定位到
main_repo=$(git rev-parse --path-format=absolute --git-common-dir)
main_repo=$(dirname "$main_repo")

# 分支名里的斜杠转成横线当目录名：feat/date-filter → wt-feat-date-filter
dir="$main_repo/../wt-${branch//\//-}"

if git show-ref --verify --quiet "refs/heads/$branch"; then
  git worktree add "$dir" "$branch"          # 分支已存在，直接检出
else
  git worktree add "$dir" -b "$branch" "$base"   # 新建分支
fi

# 复制被 gitignore 的必需文件
for f in .env .env.local; do
  [ -f "$main_repo/$f" ] && cp "$main_repo/$f" "$dir/$f"
done

# 装依赖
cd "$dir"
[ -f pyproject.toml ] && uv sync
[ -f package.json ] && pnpm install

echo "✓ 已就绪：$dir"
echo "  cd $dir && claude"
```

```bash
chmod +x ~/bin/wt-new
wt-new feat/date-filter
```

**配一个删除脚本**：

```bash
# ~/bin/wt-rm
#!/bin/bash
set -euo pipefail

dir="${1:?用法: wt-rm <worktree 目录>}"
dir=$(cd "$dir" && pwd)                  # 转成绝对路径，避免相对路径歧义

# 主仓库路径：删掉 worktree 之后要回到这里
main_repo=$(git -C "$dir" rev-parse --path-format=absolute --git-common-dir)
main_repo=$(dirname "$main_repo")

# 关键保护：如果你人正站在要删的目录里（或它的子目录里），先退出去。
# 否则删完之后 shell 的 cwd 指向一个不存在的目录，
# 之后每条命令都会报 "Unable to read current working directory"，cd 到存在的目录才能恢复。
case "$PWD/" in
  "$dir"/*) 
    echo "你正在 $dir 里，先切到主仓库"
    cd "$main_repo"
    ;;
esac

branch=$(git -C "$dir" rev-parse --abbrev-ref HEAD 2>/dev/null || echo "")

git -C "$main_repo" worktree remove "$dir" --force
git -C "$main_repo" worktree prune

if [ -n "$branch" ] && [ "$branch" != "HEAD" ]; then
  # -d 只删已合并的分支；未合并时保留并提示，避免误丢工作
  git -C "$main_repo" branch -d "$branch" 2>/dev/null \
    || echo "分支 $branch 未合并，已保留。确认要丢弃就跑：git branch -D $branch"
fi

echo "✓ 已清理：$dir"
echo "  当前目录：$PWD"
```

**注意最后那个 `echo "$PWD"`。** 脚本里的 `cd` 不会影响你的 shell（脚本跑在子进程里），所以如果你原本就在被删的目录里，**脚本结束后你的 shell 仍然卡在那个不存在的目录**。

**要让 `cd` 对当前 shell 生效，得用 `source` 调用**：

```bash
source ~/bin/wt-rm ~/wt-feat-date
```

或者干脆定义成 shell 函数，写进 `~/.zshrc`：

```bash
wt-rm() {
  local dir main_repo branch
  dir=$(cd "$1" && pwd) || return 1
  main_repo=$(git -C "$dir" rev-parse --path-format=absolute --git-common-dir)
  main_repo=$(dirname "$main_repo")
  branch=$(git -C "$dir" rev-parse --abbrev-ref HEAD 2>/dev/null)

  # 函数在当前 shell 里执行，这个 cd 是真的生效的
  case "$PWD/" in "$dir"/*) cd "$main_repo" ;; esac

  git -C "$main_repo" worktree remove "$dir" --force
  git -C "$main_repo" worktree prune
  [ -n "$branch" ] && git -C "$main_repo" branch -d "$branch" 2>/dev/null \
    || echo "分支 $branch 未合并，已保留"
  echo "✓ 已清理，当前在 $PWD"
}
```

**函数版是推荐做法**，因为它能真的把你带出被删的目录。

### 坑二：同一个分支不能被两个 worktree 检出

```
fatal: 'main' is already checked out at '/Users/you/ai-agent-roadmap'
```

**这是设计如此**，防止两个目录同时改同一个分支导致状态错乱。

**如果你只是想看 main 的代码**，用 detached：

```bash
git worktree add --detach ../wt-peek main
```

### 坑三：删了目录但没 prune

```bash
rm -rf ../wt-feat-date        # 直接删目录
git worktree list             # 它还在列表里，标着 prunable
git worktree prune            # 清理掉
```

**养成用 `git worktree remove` 而不是 `rm -rf`。**

### 坑四：人还在里面就把目录删了

**这个坑最要命，因为它会让你的终端完全瘫痪。**

```bash
cd ~/wt-feat-date
git worktree remove ../wt-feat-date     # 或者别的终端把它删了
git status
# fatal: Unable to read current working directory: No such file or directory
```

**之后你敲什么都是这个错**——`git switch`、`git worktree list`、甚至 `git status`，全部失败。因为进程的工作目录指向一个已经不存在的 inode，连「我在哪」都读不到。

**症状特征**：错误信息和你敲的命令完全无关，永远是同一句 `Unable to read current working directory`。

**解法就一条**：

```bash
cd ~/ai-agent-roadmap     # 或者随便一个存在的目录
```

**不需要重开终端**，`cd` 一下就恢复了。

**预防**：用上面的 `wt-rm` 函数版，它会先把你带出去再删。

**另一种触发方式**：你在 worktree A 里干活，另一个终端（或另一个 agent）把 A 删了。这在多 agent 并行时是真实存在的——所以 `wt-status` 巡检脚本值得常跑。

### 坑五：worktree 被锁住

如果 worktree 在一个外接硬盘或网络盘上，Git 可能会锁定它防止误清理：

```bash
git worktree list             # 显示 locked
git worktree unlock ../wt-xxx
git worktree remove ../wt-xxx
```

## 步骤 6 · 三个 agent 并行的完整剧本

### 这一步在做什么

**把前面的东西串成你每天会用的流程。**

### 场景

你同时要做三件事：修一个 bug、加一个功能、试一个重构方案。

### 剧本

```bash
cd ~/ai-agent-roadmap

# 1. 主目录保持在 main，且干净
git switch main && git pull && git status

# 2. 开三个 worktree
wt-new fix/csv-empty-line
wt-new feat/date-filter
wt-new exp/duckdb-backend

# 3. 确认
git worktree list
# /Users/you/ai-agent-roadmap  a3f21b9 [main]
# /Users/you/wt-fix-csv-empty-line  a3f21b9 [fix/csv-empty-line]
# /Users/you/wt-feat-date-filter    a3f21b9 [feat/date-filter]
# /Users/you/wt-exp-duckdb-backend  a3f21b9 [exp/duckdb-backend]
```

**开三个终端标签页，各进一个目录**：

```bash
# 终端 1
cd ~/wt-fix-csv-empty-line && claude

# 终端 2
cd ~/wt-feat-date-filter && claude

# 终端 3
cd ~/wt-exp-duckdb-backend && codex
```

**三个 agent 同时干活，互不干扰。**

### 中途查看全局状态

在主目录：

```bash
# 每个 worktree 各自到了什么状态
git worktree list

# 每个分支相对 main 改了多少
for b in fix/csv-empty-line feat/date-filter exp/duckdb-backend; do
  echo "=== $b"
  git diff --stat main.."$b" | tail -1
done
```

### 收尾

```bash
# 好的合并
cd ~/ai-agent-roadmap
git merge fix/csv-empty-line
uv run pytest                       # 合并后立刻验证

git merge feat/date-filter
uv run pytest

# 实验的丢弃
wt-rm ~/wt-exp-duckdb-backend
git branch -D exp/duckdb-backend    # -D 强制删，因为没合并过

# 清理已合并的
wt-rm ~/wt-fix-csv-empty-line
wt-rm ~/wt-feat-date-filter
git worktree list                   # 只剩主目录
```

### 可能卡在哪

**两个分支改了同一个文件，合并时冲突**

正常。按 U0.2 步骤 5 的方法解决。**降低冲突的办法是任务拆分时就考虑文件边界**——让三个 agent 尽量改不同的模块。

**忘了自己在哪个 worktree**

在 shell 提示符里显示当前分支。装 `starship` 或者在 `.zshrc` 里加：

```bash
# 提示符显示 [当前目录名:分支名]
setopt PROMPT_SUBST
PROMPT='%F{cyan}[${PWD:t}:$(git branch --show-current 2>/dev/null)]%f %~ %# '
```

## 步骤 7 · 让两个 agent 比方案

### 这一步在做什么

**这是 worktree 最有价值的用法，而且只有 worktree 能做到。**

同一个需求，让两个 agent 用不同思路各做一版，然后对比择优。

### 剧本

```bash
# 从同一个起点开两个 worktree
wt-new exp/approach-a
wt-new exp/approach-b
```

**终端 1（Claude Code）**：

```
用「预计算 + 缓存」的思路实现日期范围过滤：
启动时把数据按日期分桶，查询时直接取桶。
实现完跑 pytest 和一次性能测试，把耗时贴给我。
```

**终端 2（Codex）**：

```
用「查询时过滤」的思路实现日期范围过滤：
不做预处理，查询时用索引直接筛。
实现完跑 pytest 和一次性能测试，把耗时贴给我。
```

### 对比

```bash
cd ~/ai-agent-roadmap

# 代码量对比
git diff --stat main..exp/approach-a | tail -1
git diff --stat main..exp/approach-b | tail -1

# 两个方案本身的差异
git diff exp/approach-a..exp/approach-b

# 只看某个文件的两版实现
git diff exp/approach-a..exp/approach-b -- src/csvstats/stats.py

# 并排看某个文件的两个版本
git show exp/approach-a:src/csvstats/stats.py > /tmp/a.py
git show exp/approach-b:src/csvstats/stats.py > /tmp/b.py
diff -y /tmp/a.py /tmp/b.py | less
```

**填一张表**：

| | 方案 A（预计算） | 方案 B（查询时过滤） |
|---|---|---|
| 改动行数 | | |
| 测试是否全过 | | |
| 冷启动耗时 | | |
| 单次查询 P50 | | |
| 内存占用 | | |
| 代码可读性（你的主观判断） | | |

**这张表就是你的技术决策依据。** 而且它可以直接写进作品集——「我实测了两种方案，选了 B，因为……」比「我用了 B 方案」有说服力得多。

### 择优合并 + 取长补短

假设你选了 B，但 A 里有一个测试写得特别好：

```bash
git switch main
git merge exp/approach-b               # 主体用 B

# 从 A 里只捞那一个提交
git log --oneline exp/approach-a       # 找到那个提交的哈希
git cherry-pick a3f21b9                # 只把它摘过来
```

**这就是 cherry-pick 的典型用途：从一个整体被放弃的分支里，捞出局部有价值的东西。**

如果 cherry-pick 冲突：

```bash
# 解决冲突后
git add <文件>
git cherry-pick --continue

# 或者放弃
git cherry-pick --abort
```

## 步骤 8 · 整理 agent 产生的提交噪音

### 这一步在做什么

Agent 干活时提交往往很碎：「修复类型错误」「再修一次」「格式化」「补测试」。合并进 main 之前应该整理成有意义的几个提交。

### 交互式 rebase

```bash
git switch feat/date-filter
git log --oneline main..HEAD
# a3f21b9 补测试
# 8c2e1d4 格式化
# 5f9b3a7 再修一次类型错误
# 2d7c8e1 修复类型错误
# 9a4f6b2 实现日期过滤

git rebase -i main
```

会打开一个编辑器（**注意：在 Claude Code 的终端里交互式命令可能不好用，建议在普通终端里做**）：

```
pick 9a4f6b2 实现日期过滤
squash 2d7c8e1 修复类型错误
squash 5f9b3a7 再修一次类型错误
squash 8c2e1d4 格式化
pick a3f21b9 补测试
```

| 指令 | 作用 |
|---|---|
| `pick` | 保留这个提交 |
| `squash` / `s` | 合并进上一个提交，保留两条信息让你编辑 |
| `fixup` / `f` | 合并进上一个提交，**丢弃**本条信息 |
| `reword` / `r` | 只改提交信息 |
| `drop` / `d` | 删掉这个提交 |
| `edit` / `e` | 停下来让你修改这个提交 |

**上面那五个提交整理成两个**：一个「实现日期过滤」，一个「补测试」。

### rebase 的黄金规则

**永远不要 rebase 已经推送给别人的提交。**

理由：rebase 会重写提交（哈希全变），别人基于旧提交的工作会对不上。

**判断标准很简单**：这个分支只有你在用吗？是的话随便 rebase；已经有人基于它工作了，就用 merge。

**你的场景（个人项目 + agent 分支）几乎总是「只有你在用」，所以可以放心 rebase。**

### rebase 出错了怎么办

```bash
git rebase --abort              # 放弃，回到 rebase 之前
git rebase --continue           # 解决冲突后继续
git rebase --skip               # 跳过当前这个提交
```

**如果 rebase 已经完成但结果不对**——这就是 reflog 派上用场的时候：

```bash
git reflog                      # 找到 rebase 之前的位置
git reset --hard HEAD@{5}
```

### merge 还是 rebase

| | merge | rebase |
|---|---|---|
| 历史 | 保留真实的分叉与合并 | 变成一条直线 |
| 冲突 | 一次性解决 | 可能每个提交都要解一次 |
| 安全性 | 不重写历史 | 重写历史 |
| 适合 | 合并到 main | 整理自己的功能分支 |

**实践建议**：功能分支内部用 rebase 整理，合并到 main 用 merge。

## 步骤 9 · bisect：找出是哪次提交坏的

### 这一步在做什么

Agent 跑了 20 个提交，现在测试挂了，但你不知道是哪一次引入的。

### 怎么做

```bash
git bisect start
git bisect bad                  # 当前是坏的
git bisect good a3f21b9         # 这个已知是好的

# Git 自动切到中间那个提交
uv run pytest                   # 你测一下
git bisect good                 # 或 git bisect bad

# 重复几次，Git 用二分法缩小范围
# 20 个提交只要测 5 次

git bisect reset                # 结束，回到原来的位置
```

### 自动化版本

如果你有一条命令能判断好坏，可以全自动：

```bash
git bisect start HEAD a3f21b9
git bisect run uv run pytest    # 自动跑完，直接告诉你是哪个提交
```

**`git bisect run` 的判断规则**：命令退出码 0 算 good，非 0 算 bad。`pytest` 正好符合。

### 为什么这个命令值钱

**20 个提交手工二分要测 5 次，一个个试要测 20 次。** 而 agent 一晚上能产生几十个提交。

**这是「让 agent 大量提交」这种工作方式的必要配套。**

## 步骤 10 · 分支命名与生命周期规范

### 这一步在做什么

多 agent 并行会让分支快速累积。没有规范三天就乱了。

### 命名规范

写进 `CLAUDE.md` 和 `AGENTS.md`（U0.10 建的那两个文件），让 agent 自己遵守：

```
分支命名：
  unit/U0.3-python-basics      学习单元
  feat/date-range-filter       新功能
  fix/csv-empty-line-crash     修 bug
  exp/duckdb-backend           实验，大概率会丢弃
  refactor/split-stats-module  重构
  docs/update-readme           文档

规则：
- 全小写，单词用横线连接
- 类型前缀必须有
- 名字要能看出改了什么，不要用 fix1、test、tmp
- exp/ 前缀的分支默认可丢弃，不要合并进 main
```

**`exp/` 这个前缀的心理价值被低估了**：它明确标记「这是实验」，让你更敢试激进的方案，也让你更舍得删。

### 生命周期

```
创建 → agent 工作 → 你审阅 → 合并或丢弃 → 删除分支和 worktree
```

**每一步都不要跳过最后一步。**

### 定期清理

写一个巡检脚本：

```bash
# ~/bin/wt-status
#!/bin/bash
echo "=== worktree ==="
git worktree list
echo
echo "=== 已合并进 main 的分支（可删）==="
git branch --merged main | grep -v -E '^\*|main' || echo "  无"
echo
echo "=== 未合并的分支 ==="
git branch --no-merged main | grep -v '^\*' || echo "  无"
echo
echo "=== 每个分支的年龄 ==="
git for-each-ref --sort=committerdate refs/heads/ \
  --format='  %(committerdate:relative)%09%(refname:short)'
```

**每周复盘时跑一次。** 超过两周没动的分支，要么合并要么删掉。

## 一张速查表

```bash
# 兜底

git reset --hard HEAD@{N}           # 回到某个时刻
git branch <名字> <哈希>             # 从哈希恢复分支

# 临时收起
git stash push -u -m "说明"
git stash list / show -p / pop / drop

# 远程
git fetch origin
git log --oneline HEAD..origin/main # 远程有什么我没有
git push --force-with-lease         # 安全的强推
git fetch --prune                   # 清理过期远程引用

# worktree
git worktree add ../dir -b <新分支>
git worktree add ../dir <已有分支>
git worktree add --detach ../dir <提交>
git worktree list / remove / prune / unlock

# 对比
git diff --stat main..<分支>
git diff <分支A>..<分支B> -- <文件>
git show <分支>:<文件>

# 整理
git rebase -i main                  # squash/fixup/reword/drop
git cherry-pick <哈希>
git rebase --abort / --continue

# 定位

git bisect reset

# 清理
git branch --merged main | grep -v -E '^\*|main' | xargs -r git branch -d
```
