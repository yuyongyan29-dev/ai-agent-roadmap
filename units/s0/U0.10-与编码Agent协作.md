# U0.10 · 与编码 Agent 协作（含 Git 分支与 worktree）（12 小时）

**这个单元解决什么问题**

你已经在用 Claude Code 和 Codex 了。但「用过」和「有一套稳定的工作流」是两回事。

**没有工作流的样子**：一个会话里问了五件不相干的事，上下文塞满了；改坏了不知道怎么退回去；跑了两个小时不知道它到底改了什么；想同时做两件事只能等。

**这个单元建立的是接下来 23 周你每天都会用的工作方式。** 它同时解决三个问题：**上下文怎么管、改动怎么隔离、结果怎么验证。**

**必读**（两篇官方文档，各读一遍）：

- [Claude Code 最佳实践](https://code.claude.com/docs/en/best-practices)
- [Codex 最佳实践](https://learn.chatgpt.com/guides/best-practices)

**学完你能做到**：一个真实需求，从提出到合并 PR，全程可复现；同时跑三个 agent 互不干扰；改坏了两分钟内退回去。

## 步骤 1 · 三个入口的定位

### 这一步在做什么

你手上有三个入口，搞清楚各自适合什么，别混着用。

### 对照表

| 入口 | 强在哪 | 适合 |
|---|---|---|
| **Claude Code CLI** | 在终端里，能直接跑命令、看输出、连着你的项目环境 | **主力**。写代码、调试、跑测试、提 PR |
| **Codex CLI** | 同上 | 换个模型视角。做 review、做第二意见 |
| **Codex 桌面端** | 有可视化的 diff 面板、MCP 服务器的图形管理 | **看改动**。大 diff 用它比在终端里翻好得多 |

### 一个实用的分工

```
主力开发    → Claude Code CLI（终端）
              ↓ 产出 diff
看 diff     → Codex 桌面端（可视化审阅）
              ↓ 发现问题
交叉 review → Codex CLI（换个模型，不带写代码时的偏见）
```

**「换个模型做 review」这一条值得单独说。** 写代码的那个会话对自己写的东西有偏好，很难挑出自己的毛病。**换一个模型、换一个干净的上下文，只看 diff，挑出来的问题明显更多。**

### 可能卡在哪

**三个都开着，不知道用哪个**

**定一个默认**：日常用 Claude Code CLI，只有在「diff 大到终端里看不清」和「需要第二意见」时才切换。

**不要在两个工具里同时改同一个文件。** 会互相覆盖。要并行必须用 worktree（步骤 7）。

### 背后的逻辑

这三个入口共享同一个底层模式：**agentic loop**（U2.1 你会亲手实现一遍）——读文件、跑命令、看结果、决定下一步。

区别只在于「界面」和「模型」。理解这一点，你就不会觉得换工具要重新学。

## 步骤 2 · 写项目说明文件

### 这一步在做什么

**这是投入产出比最高的一步。** 一个文件，让 agent 每次会话都知道你的项目怎么跑、有什么规矩。

### 两个文件，两个工具

| 工具 | 文件 | 位置 |
|---|---|---|
| Claude Code | `CLAUDE.md` | 项目根目录（也可以放 `~/.claude/CLAUDE.md` 当全局默认） |
| Codex | `AGENTS.md` | 项目根目录、`.codex/AGENTS.md`、或 `~/.codex/AGENTS.md` 当全局 |

**Codex 的三层结构**：全局（`~/.codex/AGENTS.md`）→ 仓库（`.codex/AGENTS.md`）→ 子目录，下层覆盖上层。

### 怎么做

**先让它自己生成，再改**：

```bash
cd ~/Desktop/AI-Agent-学习计划
claude
# 在会话里输入：
/init
```

Codex 里同样是 `/init`。

**生成的只是起点，必须改。** 官方文档的说法是「生成的版本是一个起点，不是完成的规格」。

### 该写什么，不该写什么

| ✅ 该写 | ❌ 不该写 |
|---|---|
| agent 猜不到的命令（`uv run pytest`、`pnpm dev:weapp`） | 读代码就能知道的东西 |
| 和默认不同的代码风格 | 语言的标准约定 |
| 测试怎么跑、用哪个 runner | 详细的 API 文档（放链接） |
| 仓库规矩（分支命名、PR 约定） | 经常变的信息 |
| 项目特有的架构决策 | 长篇解释和教程 |
| 环境的坑（必须的环境变量） | 逐个文件的说明 |
| 不明显的行为 | 「写干净的代码」这种废话 |

**检验每一行的标准**：**「删掉这行会让 agent 犯错吗？」不会就删掉。**

### 你的仓库现在就该写的

```markdown
# CLAUDE.md

## 这是什么
26 周 AI Agent 学习计划的代码仓库。每个阶段一个独立的 uv 项目。

## 命令
- 跑测试：`uv run pytest`（在对应的阶段目录下）
- 代码检查：`uv run ruff check . && uv run ruff format .`
- 类型检查：`uv run ty check src/`
- 起服务：`uv run uvicorn csvstats.api:app --reload`
- 全套环境：`docker compose up`

## 规矩
- 每个学习单元一个分支：`unit/U0.3-python基础`
- 密钥只在 .env，绝不进代码
- 提交前必须跑 ruff 和 pytest

## 重要：这是学习仓库
S0 和 S1 阶段的代码我要自己写。你只能解释和 review，不要直接替我写实现。
如果我让你写，先提醒我这条规则。
```

**最后那一段很关键。** 它把你的学习纪律写进了 agent 的上下文，让工具帮你守规矩。

### 可能卡在哪

**写太长了，agent 反而不听**

这是官方文档明确警告的失败模式：**文件太长，重要的规则会淹没在噪音里。**

信号：**你明明写了规则但它一直不遵守。** 这时不是加更多字，而是删。

**某一条它总是忽略**

给那一条单独加 `IMPORTANT:`。**但只加一条**——如果十条都标重点，就没有重点了。

**用 `/context` 确认它加载了**

在会话里跑 `/context`，看 CLAUDE.md 在不在加载的内容里。

## 步骤 3 · 权限与沙箱

### 这一步在做什么

在「每步都要点批准」和「随便它干什么」之间找一个安全又不烦的位置。

### 为什么重要

Anthropic 那篇《[Beyond permission prompts](https://www.anthropic.com/engineering/claude-code-sandboxing)》（2025-10-20）说清了问题：**不停点批准会拖慢开发，而且会导致「批准疲劳」——你会变得不看就点。**

他们的解法是操作系统级的沙箱：限制文件系统和网络的边界，在边界内让它自由跑。**数据是能减少 84% 的权限提示。**

**这和你 S4 的 U4.4 是同一个思路**：不要靠人逐个判断，要靠机制划边界。

### Claude Code 怎么配

```
/permissions        # 把你信任的命令加进白名单
/sandbox            # 开启操作系统级沙箱
```

**建议加进白名单的**（这些是只读或者可逆的）：

```
Bash(uv run pytest*)   # 跑测试，失败了也只是退出码非零，不改仓库
Bash(uv run ruff*)     # 格式化最多改本地文件，git 能退回
Bash(git status)       # 下面三条都是只读，看状态不改历史
Bash(git diff*)
Bash(git log*)
Read                   # 读文件/搜索类工具无副作用，逐次批准纯粹是浪费
Grep
Glob
```

**绝不要加进白名单的**：

```
Bash(rm -rf*)          ← 删除不可逆，git 也救不回未提交的东西
Bash(git push*)        ← 推送是外部动作，每次都该确认
Bash(gh pr merge*)     ← 合并影响别人的分支，必须人来点
任何涉及生产环境的命令   ← 后果超出你的工作目录，不属于沙箱能兜住的范围
```

### Codex 怎么配

Codex 有 **sandbox（沙箱边界）** 和 **approval policy（什么时候停下来问）** 两个概念。

官方建议：**`workspace-write` 是大多数人该用的设置**——足够干活，同时防住「agent 改了它被指向的项目之外的东西」这类事故。

配置在 `config.toml` 或桌面端的 Settings → Configuration。

**原则**：默认收紧，只在明确需要时对特定仓库放开。

### 可能卡在哪

**沙箱开了之后有些操作失败**

看它报什么边界被挡了。如果是合理需求，把那个路径或域名加进允许列表；如果不合理，说明它想干的事本来就不该干。

**白名单加了但还是问**

命令的匹配是按前缀的，检查你写的模式对不对。`Bash(uv run pytest*)` 匹配 `uv run pytest tests/` 但不匹配 `uv run  pytest`（两个空格）。

### 背后的逻辑

**这一步的本质是把「信任」从「逐次判断」变成「一次性划边界」。**

你信任的不是「这一次它不会删库」，而是「即使它想删，沙箱也不让它删到项目外面」。

**这个思维在 S4 和 S6 会反复出现。** 最小权限、执行前钩子、容器沙箱，都是同一件事的不同层次。

## 步骤 4 · 核心工作流：探索 → 计划 → 实现 → 提交

### 这一步在做什么

**这是官方推荐的四阶段工作流，也是你后面 23 周的默认节奏。**

### 为什么不直接让它写

**直接让它写代码，容易解决错误的问题。** 它会基于自己的猜测动手，你看到结果时已经晚了。

**先探索、再计划，把「理解需求」和「写代码」分开。**

### 四个阶段

**阶段一：探索（不改任何东西）**

进入 plan mode：**按 `Shift+Tab` 直到状态栏显示 `⏸ plan mode on`**，或者启动时加参数：

```bash
claude --permission-mode plan
```

（Codex 里是 `/plan`。）

在这个模式下它只读不写。让它先搞清楚现状：

```
读一下 s0-foundation/csvstats/src/ 下的全部代码，
说明现在的模块划分、每个模块的职责、以及数据是怎么流动的。
```

**阶段二：计划**

```
我要给这个服务加一个「按日期范围过滤」的功能。
需要改哪些文件？会影响现有的哪些行为？测试要怎么补？
写一个实施计划。
```

**按 `Ctrl+G` 可以把计划拉到你的编辑器里直接改**，改完再让它执行。

**阶段三：实现**

`Shift+Tab` 退出 plan mode，然后：

```
按你的计划实现。写完跑 uv run pytest，有失败就修到全绿。
```

**阶段四：提交**

```
用清晰的提交信息 commit，然后开一个 PR
```

### 什么时候跳过计划阶段

官方文档说得很清楚：**计划模式有开销。**

| 情况 | 要不要计划 |
|---|---|
| 改个错别字、加一行日志、重命名变量 | **不要**，直接说 |
| **你能用一句话描述这个 diff** | **不要** |
| 不确定该怎么做 | 要 |
| 改动跨多个文件 | 要 |
| 你不熟悉要改的这块代码 | 要 |

### 可能卡在哪

**它跳过计划直接开始改**

确认你真的在 plan mode（状态栏有提示）。或者在 prompt 里明说「先不要改代码，只给方案」。

**计划写得很空泛**

你的需求描述太模糊。**给它具体的文件、具体的场景、具体的约束。**

对比：

```
差：「优化一下性能」
好：「/uploads/{id}/stats 这个接口在数据超过一万行时要 8 秒。
     看 src/csvstats/stats.py 里的实现，找出瓶颈，给一个不改接口签名的优化方案。」
```

## 步骤 5 · 给它一个能自己跑的验证

### 这一步在做什么

**这是官方文档里最重要的一条，也是最多人没做的一条。**

### 问题

**agent 在「看起来做完了」的时候就停。** 如果没有它能自己跑的检查，「看起来做完了」就是唯一的信号——**而你就成了那个验证的人，每个错误都要等你发现。**

### 解法

**给它一个能返回通过/失败的东西**，循环就能自己闭合：它做，它跑检查，它读结果，不通过就继续改。

### 什么可以当检查

| 检查 | 适合 |
|---|---|
| **测试套件** | 最通用。`uv run pytest` |
| 构建的退出码 | 前端、编译型语言 |
| Linter | 代码风格 |
| **一个把输出和标准答案 diff 的脚本** | 数据处理类 |
| **浏览器截图和设计稿对比** | 界面 |

### 三种写法，从弱到强

**一、在同一句 prompt 里要求它验证**

```
写一个 validate_email 函数。
测试用例：user@example.com 是 true，invalid 是 false，user@.com 是 false。
实现完跑一遍测试。
```

**二、把验证写进任务描述，要求它给证据**

```
修复这个 bug。修完之后：
1. 跑 uv run pytest，把输出贴给我
2. 说明你改了什么、为什么这样改能解决问题
```

**要求它展示证据，而不是声称成功。** 看证据比你自己重跑一遍快。

**三、用钩子做成硬性门禁**

配置一个 Stop hook，它会在每次回合结束前跑你的脚本，不通过就不让结束。

**这三种的取舍**：第一种今天就能用；第三种能让你走开之后它自己跑对。

### 可能卡在哪

**它说测试通过了，但我跑发现没有**

**这就是为什么要它贴输出。** 让它把 `pytest` 的实际输出贴出来，而不是只说「测试通过」。

**没有测试怎么办**

**那就先让它写测试。** 这正好是 U0.7 要学的东西。

```
先给现有的 stats.py 写测试，覆盖正常情况和两个边界情况。
测试写完跑一遍确认全绿，然后我们再改功能。
```

### 背后的逻辑

**这一条决定了「你盯着看的会话」和「你可以走开的会话」的区别。**

没有检查，你必须全程盯着。有了检查，它能自己迭代到对为止。

**这个模式你在 S2 会再次遇到**（U2.1 的错误回填给模型）和 **S3**（评估集就是一个大号的检查）。**底层是同一件事：让系统能自己判断对错。**

## 步骤 6 · 上下文管理

### 这一步在做什么

**这是所有最佳实践背后的那一个约束：上下文窗口填得很快，而且填满之前性能就开始下降。**

**这和 U1.5 你会学的上下文工程是同一个问题**，只不过现在你是使用者，S1 之后你是设计者。

### 五个手段

**一、`/clear`：不相干的任务之间清空**

**最常用也最有效。**

失败模式叫「大杂烩会话」：你开始做一件事，中间问了个不相干的问题，然后回到第一件事。**上下文里全是无关信息。**

**规矩：换任务就 `/clear`。**

**二、纠正超过两次就 `/clear` 重来**

官方文档的原话：**如果你在同一个问题上纠正了它两次以上，上下文里已经堆满了失败的尝试。**

**这时不要继续纠正。** `/clear`，然后写一个更好的初始 prompt，把你刚学到的东西写进去。

**一个干净的会话加一个更好的 prompt，几乎总是胜过一个长会话加一堆纠正。**

**三、用 subagent 做调研**

调研会读大量文件，全部进你的上下文。**用 subagent，它在独立的上下文里读，只把结论报回来。**

```
用 subagent 调研一下我们的 csvstats 项目里，
CSV 解析的错误处理是怎么做的，有哪些地方可以复用。
```

**四、`/compact` 压缩**

上下文快满时自动触发，也可以手动带指令：

```
/compact 重点保留 API 的改动和测试命令
```

**五、`Esc Esc` 或 `/rewind` 回到之前的检查点**

**每条 prompt 都会创建一个检查点。** 可以只回退对话、只回退代码、或者两者都回退。

**这意味着你可以让它试一个有风险的做法**，不行就回退。

**注意：检查点只跟踪它通过文件编辑工具做的改动，Bash 命令做的改动不在内。所以它不能替代 git。**

### 可能卡在哪

**不知道什么时候该 clear**

三个信号：

1. 换了一个不相干的任务
2. 同一个问题纠正了两次还不对
3. 它开始「忘记」你前面说过的要求

**清了之后要重新解释一遍背景，很烦**

**这正是 CLAUDE.md 的价值**——项目级的背景写在那里，每次会话自动加载，不用重复说。

如果是任务级的背景，写进一个 `SPEC.md`，`/clear` 之后 `@SPEC.md` 引用它。

## 步骤 7 · Git 分支纪律

### 这一步在做什么

**让 agent 的每一次改动都是可隔离、可审阅、可丢弃的。**

### 核心规矩：一个任务一个分支

**永远不要让 agent 直接在 main 上改。**

```bash
git switch -c unit/U0.3-csv统计
# 让 agent 干活
# 审阅、测试
git switch main
git merge unit/U0.3-csv统计
git branch -d unit/U0.3-csv统计
```

**这条规矩的价值**：

| 场景 | 有分支 | 没分支 |
|---|---|---|
| 它改坏了 | `git switch main`，分支一删了事 | 要一个个 revert |
| 改到一半要做别的 | 切分支，回来再切回去 | 只能 stash 或者硬着头皮 |
| 想对比两种方案 | 两个分支各做一个 | 做不了 |
| 想看它到底改了什么 | `git diff main...分支` 一目了然 | 混在一堆改动里 |

### 分支命名约定

写进 CLAUDE.md，让它自己遵守：

```
分支命名：
- 学习单元：unit/U0.3-python基础
- 功能：feat/日期范围过滤
- 修复：fix/csv空行崩溃
- 实验：exp/试试用duckdb
```

**`exp/` 前缀的意义**：明确标记「这是实验，大概率会丢弃」，心理上更敢试。

### 审阅 diff 的正确方式

**agent 说「我改好了」之后，你必须自己看一遍。**

```bash
git diff main...HEAD              # 看这个分支相对 main 的全部改动
git diff main...HEAD --stat       # 先看改了哪些文件、各多少行
git diff main...HEAD -- src/      # 只看某个目录
```

**审阅的顺序**：

1. **先看 `--stat`**。文件数和行数对不对？有没有它不该碰的文件？
2. **再看你最关心的文件**
3. **最后扫一遍其余的**

**如果 diff 大到看不完**，两个办法：切到 Codex 桌面端的可视化 diff 面板；或者让另一个会话帮你 review（步骤 9）。

### 可能卡在哪

**忘了切分支，直接在 main 上改了**

还没提交的话：

```bash
git switch -c unit/xxx        # 带着未提交的改动切到新分支
```

已经提交了的话：

```bash
git branch unit/xxx           # 在当前位置建个分支
git switch main
git reset --hard origin/main  # 把 main 退回去（注意：会丢弃 main 上的改动）
git switch unit/xxx           # 改动都在这个分支上
```

**`reset --hard` 会丢东西，用之前确认改动确实已经在新分支上了。**

**分支太多，乱了**

定期清理：

```bash
git branch --merged main | grep -v main | xargs git branch -d
```

这会删掉所有已经合并进 main 的分支。

## 步骤 8 · Git worktree：并行跑多个 agent

> **这一步是概览。完整的实操、脚本、四个坑、以及「让两个 agent 比方案」的剧本，在 [U0.12 · Git 分支与 worktree 实战](U0.12-Git分支与worktree实战.md)。**
> 先在这里建立概念，U0.12 里动手练透。

### 这一步在做什么

**这是本单元最有价值的一个技能。**

### 问题

你想同时做三件事：修一个 bug、写一个新功能、重构一个模块。

**用分支不行**——一个工作目录同时只能在一个分支上。切分支会把工作区的文件全换掉，另一个 agent 正在改的东西就没了。

**开三个终端也不行**——它们看到的是同一个目录。

### 解法：worktree

**一个仓库，多个工作目录，各自在不同的分支上。**

```
~/Desktop/AI-Agent-学习计划/          ← 主工作目录，在 main 上
~/Desktop/wt-fix-csv/                 ← worktree 1，在 fix/csv空行 上
~/Desktop/wt-feat-date/               ← worktree 2，在 feat/日期过滤 上
```

**三个目录共享同一份 git 历史，但文件互不影响。** 你可以在三个终端里各跑一个 agent。

### 完整命令

**创建**（同时新建分支）：

```bash
cd ~/Desktop/AI-Agent-学习计划
# -b 表示「顺手建这个分支」，省掉先 branch 再 checkout 两步
# 路径写 ../ 是让 worktree 落在仓库外面，避免被 git 当成仓库内的未跟踪文件
git worktree add ../wt-fix-csv -b fix/csv空行
git worktree add ../wt-feat-date -b feat/日期过滤
```

**查看**：

```bash
git worktree list
# /Users/yanyan/Desktop/AI-Agent-学习计划  a3f21b9 [main]
# /Users/yanyan/Desktop/wt-fix-csv         a3f21b9 [fix/csv空行]
# /Users/yanyan/Desktop/wt-feat-date       a3f21b9 [feat/日期过滤]
```

**进去干活**：

```bash
cd ../wt-fix-csv
claude                          # 在这个 worktree 里起一个 agent
```

**合并回来**：

```bash
cd ~/Desktop/AI-Agent-学习计划
git merge fix/csv空行
```

**清理**：

```bash
git worktree remove ../wt-fix-csv
git branch -d fix/csv空行
```

**如果目录已经手动删了**：

```bash
git worktree prune               # 清理失效的 worktree 记录
```

### 三个必须知道的坑

**一、每个 worktree 要单独装依赖**

`.venv/` 和 `node_modules/` 在 `.gitignore` 里，所以新 worktree 里没有。

```bash
cd ../wt-fix-csv
uv sync                          # 必须重新装
```

**二、`.env` 不会被复制**

同样因为它在 `.gitignore` 里。手动拷：

```bash
cp ~/Desktop/AI-Agent-学习计划/.env ../wt-fix-csv/.env
```

**建议在 CLAUDE.md 里写一条「新建 worktree 后必须做的两件事」，或者写一个脚本。**

**三、同一个分支不能被两个 worktree 同时检出**

```
fatal: 'main' is already checked out at '/Users/yanyan/Desktop/AI-Agent-学习计划'
```

每个 worktree 必须在不同的分支上。

### 写一个脚本省事

```bash
# ~/bin/wt-new
#!/bin/bash
# 任何一步失败就立刻退出，避免依赖没装好还继续往下跑
set -e

branch_name=$1
[ -z "$branch_name" ] && { echo "用法: wt-new 分支名"; exit 1; }

# 不管在仓库的哪个子目录里调用，都定位到仓库根目录
repo_root=$(git rev-parse --show-toplevel)
# 分支名里的 / 换成 -，否则 wt-fix/csv 会被当成多层目录
worktree_path="$repo_root/../wt-${branch_name//\//-}"

git worktree add "$worktree_path" -b "$branch_name"
# .env 在 .gitignore 里，新 worktree 拿不到，手动拷一份；主目录没有 .env 时不算失败
cp "$repo_root/.env" "$worktree_path/.env" 2>/dev/null || true
cd "$worktree_path"
# 依赖同样不跟随 git，是 Python 项目就重新装一遍
[ -f pyproject.toml ] && uv sync
echo "已就绪：$worktree_path"
```

```bash
chmod +x ~/bin/wt-new
# 单引号防止 $HOME 现在就被展开，要的是每次开 shell 时再解析
echo 'export PATH="$HOME/bin:$PATH"' >> ~/.zshrc && source ~/.zshrc
wt-new fix/csv空行
```

### 什么时候该用 worktree

| 场景 | 用吗 |
|---|---|
| **同时做两三件不相干的事** | **用** |
| **想让两个 agent 用不同方案做同一件事，然后对比** | **用**，这是最有价值的用法 |
| **长时间跑的任务（重构、迁移），同时想做别的** | **用** |
| 一次只做一件事 | 不用，分支就够 |
| 快速看一眼另一个分支的代码 | 不用，`git show 分支:文件` 就行 |

### 背后的逻辑

**worktree 之所以可行，是因为 git 的分支只是一个指针**（U0.2 学过）。

仓库的对象数据库（`.git/objects`）是共享的，worktree 只是「用不同的指针检出一份工作区」。所以：

- 新建一个 worktree 几乎不占额外空间（只有工作区的文件）
- 在一个 worktree 里提交，另一个立刻能看到那个 commit
- 但工作区的文件完全独立

**这正是并行 agent 需要的隔离级别**：共享历史，隔离改动。

## 步骤 9 · 双会话：写和审分开

### 这一步在做什么

**用一个干净上下文的会话来审阅另一个会话的产出。**

### 为什么有效

**写代码的那个会话对自己的产出有偏见。** 它记得自己为什么这么写，倾向于认为这样是对的。

**一个新的会话只看到 diff 和你给的标准，不知道产生这个改动的推理过程**，所以它是按结果评判的。

### 怎么做

**Writer / Reviewer 模式**：

| 会话 A（写） | 会话 B（审） |
|---|---|
| `实现日期范围过滤功能` | |
| | `审阅 @src/csvstats/stats.py 的日期过滤实现。看边界情况、时区处理、和现有代码的一致性。只报影响正确性的问题，不要报风格偏好。` |
| `这是 review 意见：[贴 B 的输出]。处理这些问题。` | |

**跨工具更好**：会话 A 用 Claude Code，会话 B 用 Codex CLI。**不同的模型，盲区不一样。**

### 用 subagent 做同样的事

不想开两个窗口的话，让它自己派一个 subagent：

```
用 subagent 审阅刚才的 diff，对照 PLAN.md 检查：
每个需求都实现了吗、列出的边界情况有测试吗、有没有改到范围外的东西。
只报缺口，不报风格。
```

**subagent 在独立上下文里跑**，效果接近另开一个会话，而且它的发现会直接回到当前会话，不用你手工搬运。

### 一个重要的提醒

**被要求「找缺口」的审阅者通常总能报出一些，即使代码本身没问题——因为那是它被要求做的事。**

**追着每一条改会导致过度工程**：多余的抽象层、防御性代码、为不可能发生的情况写的测试。

**做法**：让审阅者只标记「影响正确性或明确需求」的问题，其余当作可选。

### 可能卡在哪

**两个会话的意见冲突**

**你来判断。** 这正是你的价值所在。**不要让两个 agent 互相说服，那会无限循环。**

## 步骤 10 · 完整实操：一个需求从提出到合并

### 这一步在做什么

**把前面九步串成一次完整的、可复现的流程。这是本单元的核心产出。**

### 需求

给 U0.6 做的 csvstats 服务加一个功能：**统计接口支持按日期范围过滤**。

### 完整流程（照着做一遍）

**第 1 步：建 worktree**

```bash
cd ~/Desktop/AI-Agent-学习计划
# 新工作目录 + 新分支一步到位，主目录仍停在 main，不受影响
git worktree add ../wt-feat-date -b feat/日期范围过滤
cd ../wt-feat-date
# .env 和 .venv 都在 .gitignore 里，不会跟着 worktree 过来，得手动补
cp ~/Desktop/AI-Agent-学习计划/.env . 2>/dev/null || true
cd s0-foundation/csvstats && uv sync
```

**验证**：`git worktree list` 能看到两个目录；`uv run pytest` 能跑。

**第 2 步：进 plan mode 探索**

```bash
claude --permission-mode plan
```

```
读一下 src/csvstats/ 下的全部代码。
说明：模块划分、数据流、现在的统计接口接受哪些参数、有哪些测试。
```

**验证**：它的描述和你自己看到的一致。**不一致说明它读错了或者你理解错了，先对齐再往下。**

**第 3 步：让它出计划**

```
我要给 GET /uploads/{id}/stats 加两个可选查询参数：start_date 和 end_date，
格式 YYYY-MM-DD，用来过滤参与统计的行。

要求：
- 不传时行为和现在完全一样
- 传了非法格式返回 422
- start_date 晚于 end_date 时返回 422 并说明原因
- 过滤后没有数据时返回空统计而不是报错

需要改哪些文件？测试要补哪些？写一个实施计划。
```

按 `Ctrl+G` 把计划拉到编辑器里看一遍，**改掉你不认同的部分**。

**验证**：计划里点名了具体的文件和函数，不是「修改统计模块」这种空话。

**第 4 步：让它先写测试**

`Shift+Tab` 退出 plan mode。

```
先按计划写测试，覆盖计划里列的四种情况。
测试写完跑一遍，确认它们现在是失败的（因为功能还没实现）。
把 pytest 的输出贴给我。
```

**验证**：你看到 4 个测试，全部 FAILED。**这一步很关键**——它证明测试真的在测你要的东西。如果测试一开始就通过，说明它测错了。

**第 5 步：实现**

```
现在实现功能，让这些测试通过。
实现完跑 uv run pytest 和 uv run ruff check .，都通过再告诉我。
把两个命令的输出都贴给我。
```

**验证**：看它贴的输出，不是看它说「都通过了」。

**第 6 步：自己审 diff**

```bash
git diff main...HEAD --stat
```

问自己三个问题：

1. 改的文件数对吗？有没有它不该碰的？
2. 行数合理吗？一个小功能改了 500 行说明有问题
3. 有没有新增依赖？

然后细看：

```bash
git diff main...HEAD -- src/
```

**如果 diff 大到看不清，打开 Codex 桌面端看可视化 diff。**

**第 7 步：交叉 review**

另开一个终端，用 Codex：

```bash
cd ~/Desktop/wt-feat-date
codex
```

```
审阅 git diff main...HEAD 的改动。
这是一个给 CSV 统计接口加日期范围过滤的功能。
检查：边界情况、日期解析的健壮性、和现有代码风格的一致性、有没有引入不必要的复杂度。
只报影响正确性的问题，不报风格偏好。
```

**第 8 步：处理 review 意见**

回到 Claude Code 会话：

```
另一个模型 review 出了这些问题：
[贴 Codex 的输出]

逐条判断哪些是真问题，哪些是过度担心。真问题修掉，
过度担心的说明理由。修完重新跑测试。
```

**注意「逐条判断」这个要求**——不要让它无脑照单全改。

**第 9 步：提交**

```
用清晰的提交信息 commit。格式：feat: 简短描述，正文说明改了什么和为什么。
```

**自己检查一遍提交信息**，不合适就改：

```bash
git commit --amend
```

**第 10 步：开 PR**

```
push 到远程并开一个 PR，描述里说明：解决什么问题、怎么实现的、怎么验证的。
```

**第 11 步：合并**

```bash
cd ~/Desktop/AI-Agent-学习计划
git switch main
git pull                         # 先同步远程，否则合并的是过时的 main
git merge feat/日期范围过滤
uv run pytest                    # 合并后再跑一次：分支上全绿不代表和 main 合起来也全绿
git push
```

**第 12 步：清理**

```bash
git worktree remove ../wt-feat-date
git branch -d feat/日期范围过滤    # 小写 -d 只删已合并的分支，没合并会拦下来
git worktree list                # 确认只剩主目录
```

## 步骤 11 · 什么不能交给 agent

### 这一步在做什么

**划清界线。这条界线会随着你的能力变化，但现在必须严格。**

### S0 和 S1 阶段的规矩

**这两个阶段的代码，你必须每一行都能口头解释。**

| 能让它做 | 不能让它做 |
|---|---|
| **解释报错** | 直接给改好的代码 |
| **解释某段代码在干什么** | 替你写实现 |
| 说明某个概念的原理 | |
| **review 你写的代码，指出不地道的地方** | |
| 给方向和思路 | |
| 写测试（你先写实现） | |
| 生成样板代码（配置文件、目录结构） | |

**把这条规矩写进 CLAUDE.md**（步骤 2 已经写了），让工具帮你守。

### S2 之后可以放开

**因为那时你有判断力了。** 但有三件事永远是你的：

**一、架构决策。** 用不用多 Agent、选哪个框架、工具怎么切分——**这些是面试要问的，也是 agent 给不了正确答案的**（它不知道你的约束）。

**二、取舍的理由。** 你可以让它实现，但「为什么这样做而不是那样」必须是你的判断。

**三、验证标准。** 什么算做对了，只能你定。

### 一个实用的自检

**每次 agent 写完一段代码，问自己**：

> 如果现在断网，这段代码报错了，我能不能自己修？

**答不上来就说明你没看懂**，回去让它解释，直到你能答上来。

每个学习单元开始时：`wt-new unit/Ux.x-单元名`，写 SPEC，plan mode 探索，实现，自审，交叉 review，合并，清理。
