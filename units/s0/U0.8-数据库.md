# U0.8 · 数据库（6 小时）

**这个单元解决什么问题**

现在你的服务重启一次，数据就没了。数据库让数据活下来，而且查得快、不会写坏。

**为什么选 Postgres 而不是别的**：S2 做 RAG 检索时，装一个 `pgvector` 扩展它就能当向量数据库用；做全文检索它也自带。你现在学的这一套，到 S2 直接复用，不用再学一套新东西。

**学完你能做到**：写 SQL 查数据、用 Python 操作数据库、理解索引和事务、会做数据库结构变更。

## 步骤 1 · 把数据库跑起来

### 这一步在做什么

在你的电脑上启动一个 Postgres 服务。

### 怎么做

```bash
brew install postgresql@17
brew services start postgresql@17
```

`brew services start` 的意思是「让它开机自启，一直在后台跑」。

**把命令加进 PATH**（brew 装的带版本号的包默认不加）：

```bash
echo 'export PATH="/opt/homebrew/opt/postgresql@17/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
```

建一个属于这个项目的数据库：

```bash
createdb csvstats
psql csvstats
```

进入 `psql` 后提示符变成 `csvstats=#`，你现在在数据库里了。

几个 psql 的内置命令（**都以反斜杠开头，不是 SQL**）：

```
\l               列出所有数据库
\dt              列出当前数据库的所有表
\d table_name    查看表结构（列、类型、索引、外键）
\q               退出
```

### 可能卡在哪

**`command not found: createdb`**

PATH 没配好。检查：

```bash
ls /opt/homebrew/opt/postgresql@17/bin/
```

有东西的话就是 PATH 问题，重新执行上面那两行。

**`could not connect to server`**

服务没启动。

```bash
brew services list          # 看状态
brew services restart postgresql@17
```

**`database "yanyan" does not exist`**

psql 默认连一个和你用户名同名的数据库。指定数据库名：`psql csvstats`，或者先 `createdb yanyan`。

**不想装本地服务，能不能用 Docker**

能，而且下个单元就会这么做。现阶段先装本地的，因为直接用 psql 练 SQL 更方便。

### 背后的逻辑

Postgres 是**客户端-服务器**架构：一个服务进程一直跑着管理数据，你用客户端（psql、或者你的 Python 程序）连上去发命令。

这和 SQLite 不同——SQLite 就是一个文件，没有服务进程。SQLite 适合单机小应用，Postgres 适合需要多个程序同时访问、需要并发控制的场景。

**你的 Agent 服务会有多个请求同时读写，所以需要 Postgres 这种。**

## 步骤 2 · SQL 基础

### 这一步在做什么

学会用 SQL 这门语言跟数据库对话。

### 建表

```sql
-- 一次上传对应一行：文件名、上传时间、这个文件有多少行
CREATE TABLE uploads (
    id          SERIAL PRIMARY KEY,
    filename    TEXT NOT NULL,
    -- 用带时区的类型，服务器和客户端不在同一时区时才不会错
    uploaded_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    row_count   INTEGER NOT NULL DEFAULT 0
);

-- CSV 里的每一行数据，通过 upload_id 挂在某次上传下面
CREATE TABLE rows (
    id         SERIAL PRIMARY KEY,
    -- 外键 + 级联删除：删掉一次上传，它的数据行自动清干净，不留孤儿数据
    upload_id  INTEGER NOT NULL REFERENCES uploads(id) ON DELETE CASCADE,
    category   TEXT NOT NULL,
    -- 金额用 NUMERIC 而不是 float，float 存 0.1 会有误差，累加会越差越多
    amount     NUMERIC(12, 2) NOT NULL
);
```

逐个解释这些关键字：

| 关键字 | 含义 |
|---|---|
| `SERIAL` | 自增整数，插入时不用管，数据库自动给 1、2、3 |
| `PRIMARY KEY` | 主键，唯一标识一行，自动建索引 |
| `NOT NULL` | 这一列不能为空 |
| `DEFAULT now()` | 不给值时用当前时间 |
| `REFERENCES uploads(id)` | **外键**，这一列的值必须在 uploads 表的 id 里存在 |
| `ON DELETE CASCADE` | 删除 uploads 的一行时，自动删掉所有引用它的 rows |
| `TIMESTAMPTZ` | 带时区的时间戳。**永远用这个，不要用 TIMESTAMP** |
| `NUMERIC(12,2)` | 精确小数，12 位总长度、2 位小数。**钱和精确数值用它，不要用 float** |

### 增删改查

```sql
-- 插入
INSERT INTO uploads (filename, row_count) VALUES ('a.csv', 100);
-- RETURNING 让插入和取自增 id 一次完成，不用再补一句 SELECT
INSERT INTO uploads (filename) VALUES ('b.csv') RETURNING id;

-- 查询
SELECT * FROM uploads;
SELECT id, filename FROM uploads WHERE row_count > 50;
-- 分页/取最新都靠 ORDER BY + LIMIT，不写 ORDER BY 时返回顺序是不保证的
SELECT * FROM uploads ORDER BY uploaded_at DESC LIMIT 10;

-- 更新
-- UPDATE / DELETE 一定要带 WHERE，漏掉就是全表操作
UPDATE uploads SET row_count = 200 WHERE id = 1;

-- 删除
DELETE FROM uploads WHERE id = 1;
```

### 分组统计

**这正好是 csvstats 在做的事，用 SQL 一句话就完成了**：

```sql
-- AS 起的别名就是结果集的列名，后面的 ORDER BY 可以直接用它
SELECT
    category,
    COUNT(*)     AS item_count,
    AVG(amount)  AS avg_amount,
    SUM(amount)  AS total_amount
FROM rows
WHERE upload_id = 1        -- 分组前先筛行：只算这一次上传的数据
GROUP BY category
HAVING COUNT(*) > 2        -- 分组后再筛组：样本太少的类别没有统计意义
ORDER BY avg_amount DESC;
```

**`WHERE` 和 `HAVING` 的区别**：`WHERE` 在分组**前**过滤原始行，`HAVING` 在分组**后**过滤分组结果。上面这句的意思是「只看 upload_id=1 的行，按 category 分组，只保留数量超过 2 的组」。

### JOIN：把两张表连起来

```sql
-- r / u 是表别名，多表查询时用它给列加前缀，避免同名列分不清
SELECT u.filename, r.category, COUNT(*) AS item_count
FROM rows r
-- ON 后面写的是两张表的连接条件：数据行的 upload_id 对应上传记录的 id
JOIN uploads u ON u.id = r.upload_id
-- SELECT 里没被聚合的列，都必须出现在 GROUP BY 里
GROUP BY u.filename, r.category;
```

四种 JOIN，实际常用两种：

| 类型 | 含义 |
|---|---|
| `INNER JOIN`（就是 `JOIN`） | 只保留两边都匹配上的行 |
| `LEFT JOIN` | 保留左表全部，右表没匹配上的填 NULL |
| `RIGHT JOIN` / `FULL JOIN` | 很少用 |

**判断用哪个**：「我要不要保留那些没有对应记录的行？」要保留就 LEFT JOIN。比如「列出所有上传，以及它们各有多少行（可能是 0 行）」，必须用 LEFT JOIN，否则 0 行的上传会被漏掉。

### 可能卡在哪

**SQL 关键字要大写吗**

不需要，SQL 不区分大小写。但**约定俗成关键字大写**，这样一眼能看出结构。

**忘了写分号**

psql 里必须以 `;` 结尾才会执行。没写的话提示符会变成 `csvstats-#`，表示「还在等你写完」。补一个分号回车即可。

**`NULL` 的比较**

```sql
SELECT * FROM uploads WHERE note = NULL;      -- 永远查不到任何东西！
SELECT * FROM uploads WHERE note IS NULL;     -- 正确
```

**NULL 表示「未知」，而「未知 = 未知」的结果也是未知，不是真。** 这是 SQL 里最反直觉的一点，必须用 `IS NULL` / `IS NOT NULL`。

**中文排序不对**

Postgres 的排序依赖 locale 设置。中文按拼音排序需要指定 collation，现阶段不用纠结。

### 背后的逻辑

**SQL 是声明式语言。**

你写的是「我要什么」，不是「怎么去拿」。数据库的查询优化器会自己决定：先扫哪张表、用不用索引、怎么连接。

这和你写 Python 完全不同——Python 里你要一步步说清楚怎么做。

**这个差别的实际后果是**：同样的查询，数据库可能用完全不同的执行方式，性能差几百倍。所以下一步的「索引」和 `EXPLAIN` 很重要。

## 步骤 3 · 索引

### 先看清索引在做什么

```
没有索引：顺序扫描（Seq Scan）
  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
  │  │  │  │  │  │██│  │  │  │  │   十万行，一行行看过去
  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
   ①  ②  ③  ④  ⑤  ⑥ ← 找到      平均要看一半

有索引：B-tree 逐层缩小范围（Index Scan）
                 ┌─────┐
                 │ m-t │              第 1 步
                 └──┬──┘
            ┌───────┴───────┐
         ┌──▼──┐         ┌──▼──┐      第 2 步
         │ a-f │         │ n-s │
         └──┬──┘         └─────┘
       ┌────┴────┐
    ┌──▼──┐  ┌──▼──┐                  第 3 步 → 命中
    │ cat │  │ dog │
    └─────┘  └─────┘

  数据量翻倍，只多一层。所以十万行和一千万行速度差不多。

  代价：索引本身占空间；每次 INSERT/UPDATE 都要同步更新索引。
        所以不是越多越好。
```



### 这一步在做什么

理解为什么同样一句查询，有时几毫秒，有时几秒。

### 亲手感受一下

先造十万行数据：

```sql
-- INSERT ... SELECT：数据来自查询而不是手写的 VALUES，一句就能造十万行
INSERT INTO rows (upload_id, category, amount)
-- || 是字符串拼接；i % 100 让类别只有 cat0~cat99 一百种，每种约一千行
SELECT 1, 'cat' || (i % 100), (random() * 1000)::numeric(12,2)
-- generate_series 生成 1..100000 的临时序列，专门用来造测试数据
FROM generate_series(1, 100000) AS i;
```

不加索引查一次：

```sql
EXPLAIN ANALYZE SELECT * FROM rows WHERE category = 'cat42';
```

看输出里的 `Seq Scan`（顺序扫描，意思是从头到尾看了一遍）和 `Execution Time`。

加索引再查：

```sql
-- 索引名约定 idx_表名_列名，以后看名字就知道它是给谁建的
CREATE INDEX idx_rows_category ON rows(category);
EXPLAIN ANALYZE SELECT * FROM rows WHERE category = 'cat42';
```

现在应该是 `Index Scan`，时间通常快一到两个数量级。

### 索引是什么

**类比：书的目录。** 没有目录，找某一章要从头翻；有目录，先查目录再直接跳到那一页。

代价也和目录一样：

| 代价 | 说明 |
|---|---|
| 占空间 | 索引本身要存储 |
| **拖慢写入** | 每次 INSERT/UPDATE 都要同步更新索引 |

**所以不是索引越多越好。**

### 什么时候该建索引

| 情况 | 建不建 |
|---|---|
| 经常出现在 `WHERE` 里的列 | 建 |
| 经常用来 `JOIN` 的外键列 | 建 |
| 经常 `ORDER BY` 的列 | 建 |
| 值只有几种的列（比如性别） | **不建**，区分度太低，索引没用 |
| 很少查询但频繁写入的表 | 慎重 |

### 可能卡在哪

**建了索引但没用上**

`EXPLAIN` 显示还是 `Seq Scan`。几个常见原因：

1. **表太小**。几百行的表，全扫比走索引还快，优化器会选择不用索引。这是对的。
2. **在列上用了函数**。`WHERE lower(category) = 'x'` 用不上 `category` 的普通索引，要建函数索引。
3. **类型不匹配**。列是 `TEXT`，你传的是数字。

**`EXPLAIN` 输出看不懂**

先只看两个东西：有没有 `Seq Scan`（可能需要索引）、`Execution Time` 是多少。其余细节以后再学。

### 背后的逻辑

Postgres 默认的索引类型是 **B-tree**（平衡树）。它把值排好序存成树状结构，查找时逐层缩小范围，所以时间复杂度是对数级——**数据量翻倍，查找只多一步**。

这就是为什么十万行和一千万行，索引查找的速度差别不大。

Postgres 还有别的索引类型，其中 **GIN 索引**用于全文检索、**HNSW 索引**用于向量检索——**这两个你在 S2 做 RAG 时会用到**。原理不同，但「用额外的数据结构换查询速度」这个思路是一样的。

## 步骤 4 · 事务

### 这一步在做什么

保证「要么全做，要么全不做」。

### 问题长什么样

转账：从 A 扣 100，给 B 加 100。

```sql
-- 两句各自独立提交：第一句一执行完，钱就真的从 A 账户扣掉了
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
-- 如果程序在这里崩了…
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
```

**100 块凭空消失了。**

### 解法

```sql
-- 开启事务：下面的改动先攒着，别的连接看不到
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
-- 到这一句两个改动才一起对外生效；中间任何一步失败就整体作废
COMMIT;
```

`BEGIN` 到 `COMMIT` 之间的所有操作是一个整体。中途崩溃或者你执行 `ROLLBACK`，所有改动全部撤销，就像从没发生过。

### 什么操作必须放在一个事务里

判断标准：**这几个操作是不是「一件事」的不同部分？** 如果只做一半会导致数据不一致，就必须放在一个事务里。

在你的 Agent 项目里，典型场景是：

- 扣除用户配额 + 记录一次调用
- 保存任务状态 + 写入执行日志
- 创建上传记录 + 插入所有数据行

### 可能卡在哪

**忘了 COMMIT**

psql 里如果你 `BEGIN` 了但没 `COMMIT` 就退出，改动会全部丢失。而且在你的会话没结束前，其他连接看不到你的改动。

**事务里包了太多东西**

事务期间数据库会持有锁，事务越长，其他请求等待越久。**不要在事务里调外部 API**——网络慢的时候整个数据库会被拖住。

**在 Python 里怎么用**

用 ORM 的话通常是这样：

```python
# 进入时 BEGIN，正常退出 COMMIT，中间抛异常自动 ROLLBACK
# 好处是不用自己写 try/except 去补 rollback，漏写一处就会留下半截数据
with session.begin():
    session.add(record_a)
    session.add(record_b)
```

又是 `with`。**你现在应该已经能预测到了。**

### 背后的逻辑

事务保证四个特性，缩写叫 ACID：

| 字母 | 含义 |
|---|---|
| **A** Atomicity 原子性 | 要么全成功，要么全失败 |
| **C** Consistency 一致性 | 约束（外键、非空）始终成立 |
| **I** Isolation 隔离性 | 并发的事务互不干扰 |
| **D** Durability 持久性 | 提交后即使断电也不会丢 |

其中隔离性最复杂，有多个级别，实际开发中默认级别通常够用。**现阶段你只要记住「相关的写操作放一个事务里」就行。**

到 S4 学幂等性和断点续跑时，你会再次遇到这些概念——那时的问题是「调外部 API 没法回滚怎么办」，事务解决不了，需要别的手段。

## 步骤 5 · 用 Python 操作数据库

### 这一步在做什么

不再手敲 SQL，让 Python 代码来读写。

### 怎么做

```bash
uv add sqlmodel psycopg[binary]
```

**SQLModel** 是 FastAPI 作者写的，它把 Pydantic 和 SQLAlchemy 合二为一——**同一个类既是数据库表定义，又是 API 的请求响应模型**。

```python
from datetime import datetime
from sqlmodel import Field, SQLModel, Session, create_engine, select


# table=True 才会真的建表；不写它就只是个普通 Pydantic 模型
class Upload(SQLModel, table=True):
    """一次 CSV 上传，既当数据库表定义，也当 API 的响应模型。"""

    # id 声明成可空，是因为对象刚建出来还没入库，自增 id 由数据库分配
    id: int | None = Field(default=None, primary_key=True)
    filename: str
    # default_factory 传的是函数而不是调用结果，否则所有记录会共用导入那一刻的时间
    uploaded_at: datetime = Field(default_factory=datetime.now)
    row_count: int = 0


# engine 管理连接池，整个进程建一个就够，不要每次请求都新建
engine = create_engine("postgresql+psycopg://localhost/csvstats")
SQLModel.metadata.create_all(engine)      # 按类定义建表（已存在的表不动）


# 写
# Session 是一次会话/一批操作的上下文，用 with 保证结束时一定关闭
with Session(engine) as session:
    u = Upload(filename="a.csv", row_count=100)
    session.add(u)           # 只是放进待提交队列，此时还没落库
    session.commit()         # 提交后数据才真正写入
    session.refresh(u)       # 提交后对象里的字段已过期，refresh 从库里读回自增的 id
    print(u.id)

# 读
with Session(engine) as session:
    # select() 拼出的是查询语句，exec() 才真正发给数据库；.all() 取全部结果
    result = session.exec(
        select(Upload).where(Upload.row_count > 50).order_by(Upload.uploaded_at.desc())
    ).all()
```

### 接进 FastAPI

用 U0.6 学的依赖注入：

```python
from fastapi import Depends
from typing import Annotated

def get_session():
    """每个请求独占一个会话，请求结束后自动关闭，连接还回连接池。"""
    # 用 yield 而不是 return：yield 之后的清理代码会在响应返回后执行
    with Session(engine) as session:
        yield session

# 起个别名，省得每个路由函数都重复写一遍长长的 Annotated
SessionDep = Annotated[Session, Depends(get_session)]


@app.get("/uploads")
def list_uploads(session: SessionDep, limit: int = 10) -> list[Upload]:
    """列出上传记录。limit 有默认值，所以 FastAPI 把它当可选查询参数。"""
    # 一定要带 limit：没有上限的列表接口，数据涨起来会拖垮响应
    return session.exec(select(Upload).limit(limit)).all()
```

### 可能卡在哪

**连接字符串怎么写**

```
postgresql+psycopg://user:password@host:port/database
```

本地开发通常可以省略用户名密码：`postgresql+psycopg://localhost/csvstats`。

**这个字符串要放进 `.env`**，不能写死在代码里（U0.5 的规矩）。

**`create_all` 改了表结构没生效**

`create_all` 只建**不存在**的表，它不会修改已存在的表。改表结构要用迁移工具，见下一步。

**N+1 查询问题**

```python
uploads = session.exec(select(Upload)).all()   # 第 1 次查询：取回所有上传
for u in uploads:
    # u.rows 是懒加载的关联字段，第一次访问才去查库
    print(len(u.rows))        # 每次循环都发一次 SQL！
```

100 个 upload 就是 101 次查询。解法是用 `selectinload` 一次性把关联数据取出来。

**这是 ORM 最经典的性能坑**，遇到「怎么这么慢」时第一个怀疑它。

### 背后的逻辑

**ORM 是什么，为什么用它**

ORM（对象关系映射）在「Python 对象」和「数据库表」之间做翻译。

好处：类型安全、自动补全、不用手写 SQL 字符串、天然防 SQL 注入。

代价：多一层抽象，性能问题不直观（比如上面的 N+1），复杂查询反而比 SQL 难写。

**实践建议**：日常增删改查用 ORM，复杂的分析查询直接写 SQL。SQLModel 支持混用。

## 步骤 6 · 数据库迁移

### 这一步在做什么

解决「我改了表结构，线上已有的数据怎么办」。

### 问题长什么样

你给 `Upload` 加了一个 `note` 字段。本地重建表就行，但线上有几万条真实数据，不能删表重建。

需要的是一个**变更脚本**：「给 uploads 表加一列 note」。而且要能记录哪些变更已经执行过了。

### 怎么做

```bash
uv add alembic
uv run alembic init migrations
```

改 `alembic.ini` 和 `migrations/env.py`，让它知道你的数据库地址和模型定义。

然后每次改模型后：

```bash
uv run alembic revision --autogenerate -m "给 uploads 加 note 字段"
```

它会对比模型和数据库的差异，生成一个迁移文件。**打开看一眼**，确认它生成的 SQL 是你想要的。

执行：

```bash
uv run alembic upgrade head        # 升到最新
uv run alembic downgrade -1        # 回退一步
```

### 可能卡在哪

**autogenerate 生成的东西不对**

它检测不了所有变更（比如改列名会被识别成「删一列加一列」，数据就丢了）。**生成的迁移文件必须人工审阅**，必要时手动改。

**迁移文件要提交进 git 吗**

**必须提交。** 它们和代码是一体的，代码用到新字段，就必须有对应的迁移。

**执行顺序乱了**

Alembic 用 `down_revision` 把迁移串成链。多人协作时可能出现分叉，需要 `alembic merge` 处理。个人项目基本不会遇到。

### 背后的逻辑

数据库迁移的本质是**给数据库结构也做版本控制**。

它和 Git 解决的是同一类问题：记录变更历史、能前进能回退、多人协作时能合并。

**在你的项目里，「代码版本 + 迁移版本」必须是配套的。** 部署时的正确顺序是：先跑迁移，再切新代码。S4 学部署时会具体讲。
