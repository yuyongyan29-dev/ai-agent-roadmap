# U0.7 · 测试（6 小时）

**这个单元解决什么问题**

你现在改代码的方式是：改完，手动跑一遍，看看有没有坏。项目小的时候还行，等到有 20 个功能时，你改一处要手动验 20 处，实际上你不会验——你会祈祷。

测试就是把「手动验一遍」变成「敲一个命令验全部」。

**更重要的是**：这个单元的思维方式，是 S3 学 Agent 评估的直接基础。Agent 的输出不确定，不能用 `assert x == y`，但「先定义什么是对的，再自动验证」这个思路完全一样。

**学完你能做到**：改代码不怕改坏；能把外部依赖假掉，让测试快且稳定。

## 步骤 1 · 第一个测试

### 这一步在做什么

看清楚测试到底是什么——**它就是普通的 Python 函数**，没有任何魔法。

### 怎么做

```bash
uv add --dev pytest pytest-cov
```

建 `tests/test_stats.py`：

```python
from csvstats.stats import 算均值


def test_算均值_正常情况():
    结果 = 算均值([1, 2, 3])
    assert 结果 == 2


def test_算均值_空列表():
    结果 = 算均值([])
    assert 结果 == 0
```

跑：

```bash
uv run pytest
```

输出：

```
tests/test_stats.py ..                    [100%]
2 passed in 0.02s
```

每个点代表一个通过的测试。失败会显示 `F` 并打印详细对比。

### pytest 的三条约定

pytest 靠命名约定找测试，**不遵守就不会被执行**：

| 约定 | 规则 |
|---|---|
| 文件 | `test_*.py` 或 `*_test.py` |
| 函数 | `test_` 开头 |
| 类 | `Test` 开头（不常用） |

### AAA 结构

好的测试都是三段：

```python
def test_统计_按分类分组():
    # Arrange 准备
    数据 = [
        {"分类": "家电", "销量": 10},
        {"分类": "家电", "销量": 20},
        {"分类": "家居", "销量": 5},
    ]

    # Act 执行
    结果 = 统计(数据, 分组列="分类", 数值列="销量")

    # Assert 断言
    assert 结果["家电"]["数量"] == 2
    assert 结果["家电"]["均值"] == 15
    assert 结果["家居"]["数量"] == 1
```

**一个测试只测一件事。** 名字要说清楚测的是什么，`test_1` 这种名字在失败时毫无帮助。

### 可能卡在哪

**`ModuleNotFoundError: No module named 'csvstats'`**

测试文件找不到你的包。解法：确保项目已经装进虚拟环境（`uv sync`），并且用 `uv run pytest` 而不是直接 `pytest`。

**pytest 找不到测试**

- 文件名是不是 `test_` 开头
- 函数名是不是 `test_` 开头
- 有没有跑错目录

用 `uv run pytest -v` 看详细信息，它会列出找到了哪些测试。

**assert 失败看不懂**

pytest 会展示详细对比：

```
E   assert 15.5 == 15
E    +  where 15.5 = 结果['家电']['均值']
```

它把表达式拆开告诉你每部分的实际值。**这是 pytest 比标准库 unittest 好用的主要原因。**

### 背后的逻辑

**测试的真正价值不是「验证代码是对的」。**

新手以为测试是为了证明代码正确。实际上，测试最大的价值是：

1. **让你敢改代码**。有测试兜底，重构时改坏了立刻知道
2. **它是可执行的文档**。想知道一个函数怎么用，看测试比看注释准，因为注释会过期，测试不会
3. **写测试会暴露糟糕的设计**。如果一个函数很难测，通常说明它做的事太多、依赖太杂

第 3 点特别值得记住。**当你觉得「这个函数没法测」时，往往是设计问题，不是测试问题。**

## 步骤 2 · fixture：准备可复用的测试数据

### 这一步在做什么

把多个测试都要用的准备工作抽出来。

### 怎么做

```python
import pytest


@pytest.fixture
def 样本数据():
    return [
        {"分类": "家电", "销量": 10},
        {"分类": "家电", "销量": 20},
        {"分类": "家居", "销量": 5},
    ]


def test_分组数量(样本数据):          # 参数名和 fixture 名一致
    结果 = 统计(样本数据, "分类", "销量")
    assert len(结果) == 2


def test_均值(样本数据):              # 每个测试拿到的是全新的一份
    结果 = 统计(样本数据, "分类", "销量")
    assert 结果["家电"]["均值"] == 15
```

**pytest 看到测试函数的参数名，会自动去找同名的 fixture 并调用它。**

### 带清理的 fixture

```python
@pytest.fixture
def 临时文件(tmp_path):               # tmp_path 是 pytest 内置的 fixture
    路径 = tmp_path / "test.csv"
    路径.write_text("分类,销量\n家电,10\n", encoding="utf-8")
    yield 路径                        # 把它交给测试用
    # yield 之后的代码在测试结束后执行（这里不用清理，tmp_path 会自动删）
```

### 共享 fixture

放进 `tests/conftest.py`，同目录及子目录的所有测试文件都能用，不需要 import。

### 可能卡在哪

**fixture 没被调用**

参数名必须和 fixture 函数名**完全一致**。

**多个测试改了同一份数据互相影响**

默认每个测试都会重新执行一次 fixture，拿到全新的数据。如果你写了 `@pytest.fixture(scope="module")`，那就是所有测试共享同一份——**这是测试互相污染的常见来源**。

**除非有性能理由，否则用默认的 function 作用域。**

### 背后的逻辑

fixture 体现了「测试之间必须相互独立」这条铁律。

**每个测试都应该能单独运行，且顺序无关。** 如果测试 B 依赖测试 A 先跑过，那你就有了隐藏的耦合，某天单独跑 B 时会莫名其妙失败。

这条原则在 S3 做 Agent 评估时同样成立，而且更重要——**每条评估用例必须在隔离的环境里跑**，否则上一条的副作用（写了数据库、改了记忆）会污染下一条。

## 步骤 3 · 参数化：一次测多组输入

### 这一步在做什么

同样的逻辑，多组输入输出，不用复制粘贴测试函数。

### 怎么做

```python
@pytest.mark.parametrize(
    "输入,期望",
    [
        ([1, 2, 3], 2),
        ([10], 10),
        ([], 0),
        ([-1, 1], 0),
    ],
)
def test_算均值(输入, 期望):
    assert 算均值(输入) == 期望
```

跑起来是 4 个独立的测试，某个失败时会告诉你是哪组数据。

**给用例起名字**，失败时更好读：

```python
@pytest.mark.parametrize(
    "输入,期望",
    [
        pytest.param([1, 2, 3], 2, id="普通情况"),
        pytest.param([], 0, id="空列表"),
        pytest.param([-1, 1], 0, id="正负抵消"),
    ],
)
def test_算均值(输入, 期望):
    assert 算均值(输入) == 期望
```

### 测试异常

```python
def test_除零应该报错():
    with pytest.raises(ZeroDivisionError):
        1 / 0


def test_错误信息():
    with pytest.raises(ValueError, match="不能为空"):
        解析("")
```

### 背后的逻辑

参数化的价值是把「测试逻辑」和「测试数据」分开。

**逻辑写一遍，数据可以随便加。** 发现一个新的边界情况，加一行数据就行。

**这个模式在 S3 会变成你的评估集**：评估逻辑（跑 Agent、打分）写一遍，50 条测试数据放在一个 YAML 文件里。发现新的失败 case，往 YAML 里加一条。完全是同一个思路。

## 步骤 4 · Mock：把外部依赖假掉

### 这一步在做什么

**本单元最重要的技能。** 让测试不依赖网络、不依赖真实数据库、不花钱。

### 为什么必须做

假设你的测试要调 GitHub API：

| 问题 | 后果 |
|---|---|
| 需要网络 | 断网就跑不了，CI 里不稳定 |
| 慢 | 每次几百毫秒，100 个测试就是半分钟 |
| 有限流 | 跑多了被封 |
| 结果会变 | 今天返回 5 条，明天 6 条，测试随机失败 |
| **要花钱** | 调大模型 API 的话，每跑一次测试都在烧钱 |

最后一条在 S1 之后会变得极其现实。

### 怎么做

```bash
uv add --dev pytest-httpx
```

```python
import httpx
import pytest
from csvstats.api_client import 取用户


def test_取用户_成功(httpx_mock):
    httpx_mock.add_response(
        url="https://api.github.com/users/torvalds",
        json={"login": "torvalds", "name": "Linus"},
    )

    结果 = 取用户("torvalds")

    assert 结果.名字 == "Linus"


def test_取用户_限流时重试(httpx_mock):
    httpx_mock.add_response(status_code=429)       # 第一次限流
    httpx_mock.add_response(json={"login": "a", "name": "A"})   # 第二次成功

    结果 = 取用户("a")

    assert 结果.名字 == "A"
    assert len(httpx_mock.get_requests()) == 2     # 确认真的重试了
```

**第二个测试尤其有价值**——它验证了你的重试逻辑真的在工作。这种场景在真实环境里很难复现（你没法让 GitHub 按需给你返回 429），但 mock 里一行就搞定。

### 测 FastAPI 接口

```python
from fastapi.testclient import TestClient
from csvstats.api import app

client = TestClient(app)


def test_health():
    r = client.get("/health")
    assert r.status_code == 200
    assert r.json() == {"status": "ok"}


def test_参数校验():
    r = client.get("/items/abc")       # item_id 应该是 int
    assert r.status_code == 422
```

**替换依赖**（用 U0.6 学的依赖注入）：

```python
def 假数据库():
    return {"1": {"名字": "测试"}}

app.dependency_overrides[数据库会话] = 假数据库
```

### 可能卡在哪

**mock 了但真实请求还是发出去了**

检查 mock 的 URL 是不是完全匹配（包括查询参数）。`pytest-httpx` 默认严格匹配。

也可以用 `httpx_mock.add_response()` 不指定 url，匹配所有请求。

**`httpx_mock` 报「未使用的响应」**

你注册了 mock 响应但没被用到。说明代码的请求路径和你想的不一样，**这本身就是一个有价值的发现**。

**该 mock 到什么程度**

原则：**mock 你控制不了的东西**（网络、时间、随机数、外部服务），**不要 mock 你自己的代码**。

如果你发现要 mock 自己的三四个模块才能测一个函数，说明这个函数的依赖太多，该重构了。

### 背后的逻辑

测试分层，各有各的用途：

| 层 | 测什么 | 特点 |
|---|---|---|
| **单元测试** | 单个函数 | 快、多、全 mock |
| **集成测试** | 几个模块协作 | 慢一些、少一些、部分真实 |
| **端到端测试** | 整个系统 | 最慢、最少、全真实 |

常见的建议是金字塔形：单元测试最多，端到端最少。

**在 Agent 项目里这个分层依然成立**，只是最上层变成了「评估」：工具函数用单元测试，工具+模型的编排用集成测试，完整任务用评估集。S3 会展开讲。

## 步骤 5 · 覆盖率

### 这一步在做什么

看看哪些代码从来没被测试碰过。

### 怎么做

```bash
uv run pytest --cov=csvstats --cov-report=term-missing
```

输出：

```
Name                        Stmts   Miss  Cover   Missing
---------------------------------------------------------
src/csvstats/reader.py         45      3    93%   28-30
src/csvstats/stats.py          30      0   100%
src/csvstats/api.py            60     18    70%   45-52, 78-88
---------------------------------------------------------
TOTAL                         135     21    84%
```

`Missing` 列是没被执行到的行号。**去看那几行是什么**——往往是错误处理分支，而错误处理恰恰是最容易写错的地方。

生成 HTML 报告更直观：

```bash
uv run pytest --cov=csvstats --cov-report=html
open htmlcov/index.html
```

红色的行就是没测到的。

### 可能卡在哪

**追求 100% 覆盖率**

**不要。** 覆盖率是一个「找漏洞」的工具，不是一个「要冲的指标」。

覆盖率高不代表测试好——你可以写一个跑遍所有代码但一个 assert 都没有的测试，覆盖率 100%，价值为零。

**70% 到 80% 是一个健康的区间。** 重点看：核心业务逻辑覆盖了吗？错误分支覆盖了吗？

**有些代码就是不好测**

比如 `if __name__ == "__main__":` 里的启动代码。用 `# pragma: no cover` 标记它跳过。

### 背后的逻辑

覆盖率工具的原理是：运行测试时记录每一行有没有被执行过。

所以它只能告诉你「这行**没**被执行」（确定有问题），不能告诉你「这行被执行了所以是对的」（不确定）。

**它是一个负向指标：低覆盖率一定有问题，高覆盖率不一定没问题。**
