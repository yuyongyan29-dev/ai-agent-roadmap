## 步骤 1 · 起一个 Redis 并连上

### 这一步在做什么

在你 U0.9 建好的 compose 里加一个服务，两行的事。

### 怎么做

在 `compose.yaml` 里加：

```yaml
services:
  # ... 已有的 db 服务 ...

  redis:
    image: redis:8-alpine
    ports:
      - "6379:6379"
    # appendonly 开启 AOF 持久化：默认只有 RDB 快照，
    # 崩溃时最多丢一整个快照周期的数据；AOF 每秒刷盘，最多丢 1 秒
    command: redis-server --appendonly yes
    volumes:
      - redisdata:/data
    healthcheck:
      # redis-cli ping 返回 PONG 才算就绪，避免应用先起来连不上
      test: ["CMD", "redis-cli", "ping"]
      interval: 3s
      retries: 20

volumes:
  redisdata:
```

```bash
docker compose up -d redis
docker compose exec redis redis-cli ping    # 应该返回 PONG
```

Python 侧：

```bash
uv add redis
```

```python
import redis.asyncio as redis

# decode_responses=True 让返回值直接是 str 而不是 bytes，
# 省掉每次 .decode()；代价是存二进制数据时要单独开一个不解码的连接
r = redis.from_url("redis://localhost:6379/0", decode_responses=True)

await r.set("hello", "world")
print(await r.get("hello"))    # world
```

**连接串放进 `.env`**（U0.5 的规矩），不要写死。

### 可能卡在哪

**端口 6379 被占**

本机可能装过 Redis。`lsof -i :6379` 看是谁占的，停掉它或者改映射端口。

**连不上但容器在跑**

检查 healthcheck 通过没有：`docker compose ps`。以及确认应用连的是 `localhost`（从宿主机）还是 `redis`（从另一个容器里，U0.9 讲过）。

### 背后的逻辑

**Redis 是内存数据库**：数据主要在内存里，所以快，代价是内存装不下就麻烦，以及断电会丢。

它提供两种持久化：**RDB** 是定期快照，恢复快但可能丢一个周期；**AOF** 是记录每条写命令，丢得少但文件大恢复慢。

**理解这两者的取舍，就理解了 Redis 在你系统里的定位**：它适合放「丢了能重建」的数据（缓存、会话、计数器），不适合放「丢了就没了」的业务数据——那是 U0.8 学的 Postgres 的活。

U4.2 会告诉你一条规矩：**任何丢了会导致不一致的东西，放数据库不放 Redis。** 这个单元学完你就知道那条规矩的依据是什么。

## 步骤 2 · 五种数据结构各用一次

### 这一步在做什么

Redis 不是「一个大字典」。五种结构对应五类不同的问题，用错了性能差很远。

### 五种结构与它们的真实用途

**string · 做工具结果缓存**

```python
import json, hashlib

async def cached_tool_call(tool_name: str, params: dict, ttl: int = 300):
    """只读工具的结果缓存。有副作用的工具绝不能缓存。"""
    # 参数要规范化后再哈希：{"a":1,"b":2} 和 {"b":2,"a":1} 必须命中同一个键
    key = f"tool:{tool_name}:{hashlib.sha256(json.dumps(params, sort_keys=True).encode()).hexdigest()[:16]}"
    hit = await r.get(key)
    if hit is not None:
        return json.loads(hit)
    result = await run_tool(tool_name, params)
    await r.setex(key, ttl, json.dumps(result, ensure_ascii=False))
    return result
```

**hash · 存会话的热数据**

```python
# 会话状态字段多且要单独更新，用 hash 比用 string 存整个 JSON 好：
# 改一个字段不用读出来再写回去，也不会有并发覆盖问题
await r.hset(f"session:{sid}", mapping={"user_id": uid, "turn": 0, "model": "..."})
await r.hincrby(f"session:{sid}", "turn", 1)      # 原子自增，不用读改写
await r.expire(f"session:{sid}", 3600)            # 一小时不活动就过期
```

**zset · 做滑动窗口限流**

```python
async def sliding_window_limit(user_id: str, limit: int, window_sec: int, now_ts: float) -> bool:
    """滑动窗口限流。now_ts 由调用方传入，便于测试时注入固定时间。"""
    key = f"ratelimit:{user_id}"
    # pipeline 把四条命令打包成一次往返，减少网络开销
    async with r.pipeline() as pipe:
        # zset 的 score 存时间戳：先删掉窗口外的旧记录
        pipe.zremrangebyscore(key, 0, now_ts - window_sec)
        pipe.zcard(key)                                  # 数窗口内还剩几条
        pipe.zadd(key, {f"{now_ts}": now_ts})            # 记录本次
        pipe.expire(key, window_sec)
        _, count, _, _ = await pipe.execute()
    return count < limit
```

**为什么用 zset 而不是简单计数器**：固定窗口计数器在窗口边界会有两倍突发（比如 0:59 和 1:01 各打满一个窗口）。zset 按时间戳存每次请求，能做到真正的滑动窗口。

**list · 做轻量队列**

```python
await r.lpush("queue:tasks", json.dumps(task))
# brpop 阻塞等待，比轮询省资源；timeout=5 让 worker 能定期检查退出信号
item = await r.brpop("queue:tasks", timeout=5)
```

**注意**：这只适合「丢了无所谓」的任务。要可靠投递用 U4.3 的 Postgres 队列或消息队列。

**set · 做去重**

```python
# sadd 返回 1 表示是新元素，0 表示已存在——一次操作同时完成判重和记录
is_new = await r.sadd(f"seen:{task_id}", item_id)
if not is_new:
    return "已处理过，跳过"
```

### 可能卡在哪

**不知道该用哪个结构**

一个简单的判断：要按名字取单个值用 string；一个对象有多个字段要分别更新用 hash；要排序或按范围查用 zset；要判「在不在」用 set；要先进先出用 list。

**key 命名很乱**

用冒号分层：`业务:类型:标识`，比如 `tool:search_notes:a3f21b`、`session:abc123`。**这不只是好看**——Redis 的 `SCAN key:*` 能按前缀批量操作，命名乱了就没法管理。

## 步骤 3 · 缓存三兄弟

### 这一步在做什么

**这是面试必问的一组，而且三个问题的成因完全不同。**

### 穿透：查一个根本不存在的东西

**成因**：请求的 key 在缓存和数据库里都没有。缓存永远不命中，每次都打到数据库。如果被恶意构造大量不存在的 key，数据库会被打垮。

**对策：空值也缓存。**

```python
async def get_with_null_cache(key: str, ttl: int = 300, null_ttl: int = 60):
    hit = await r.get(key)
    if hit == "__NULL__":      # 用一个不可能是真实值的哨兵
        return None
    if hit is not None:
        return json.loads(hit)

    value = await query_db(key)
    if value is None:
        # 空结果也缓存，但 TTL 短得多：数据可能马上就被创建出来
        await r.setex(key, null_ttl, "__NULL__")
        return None
    await r.setex(key, ttl, json.dumps(value))
    return value
```

### 击穿：一个热点 key 恰好过期

**成因**：某个 key 访问量极大，它过期的那一瞬间，所有并发请求同时发现缓存没有，一起去查数据库。

**对策：互斥重建，只让一个请求去查库。**

```python
async def get_with_mutex(key: str, ttl: int = 300):
    hit = await r.get(key)
    if hit is not None:
        return json.loads(hit)

    lock_key = f"lock:{key}"
    # nx=True 表示只有键不存在时才设置成功——这就是互斥
    # ex=10 是保险：拿到锁的进程崩了，10 秒后锁自动释放，不会死锁
    got_lock = await r.set(lock_key, "1", nx=True, ex=10)
    if got_lock:
        try:
            value = await query_db(key)
            await r.setex(key, ttl, json.dumps(value))
            return value
        finally:
            await r.delete(lock_key)
    else:
        # 没抢到锁的请求短暂等待后重试读缓存，而不是也去查库
        await asyncio.sleep(0.05)
        return await get_with_mutex(key, ttl)
```

### 雪崩：大量 key 同时过期

**成因**：一批缓存是同一时刻写入的（比如服务启动时预热），TTL 又相同，于是同时失效，数据库瞬间承压。

**对策：TTL 加随机抖动。**

```python
def jittered_ttl(base: int, jitter_ratio: float = 0.2) -> int:
    """给 TTL 加 ±20% 的随机偏移，把过期时间打散开。
    注意随机数种子：生产环境用 random 即可，测试里要能固定。"""
    import random
    delta = int(base * jitter_ratio)
    return base + random.randint(-delta, delta)

await r.setex(key, jittered_ttl(300), value)
```

### 亲手复现三次

**这一步不能只看不做。**

穿透：写一个循环，用 1000 个随机不存在的 key 去查，观察数据库的查询次数。加上空值缓存后再跑一次。

击穿：用 `asyncio.gather` 起 50 个并发请求同一个 key，在请求前手动 `DEL` 掉它。数一下数据库被查了几次。加互斥后再数一次。

雪崩：写入 100 个 TTL 都是 60 秒的 key，等它们过期，观察数据库的 QPS 尖峰。加抖动后再看。

**每次都记录数字。** 这三组前后对比数据直接能进作品集。

### 可能卡在哪

**怎么统计数据库被查了几次**

在 `query_db` 里加一个计数器，或者用 U0.4 学的 logging 记录每次调用。

**互斥版本的递归会不会栈溢出**

理论上会。生产代码要改成循环加最大重试次数。这里用递归是为了读起来清楚。

## 步骤 4 · 分布式锁与它的经典失效

### 这一步在做什么

**U4.2 会讲到「用 Redis 分布式锁」，也会提到它的经典失效场景。这一步让你亲手复现那个失效。**

### 基础版

```python
import uuid

async def acquire_lock(name: str, ttl_ms: int = 10000) -> str | None:
    """获取锁，返回一个唯一 token；拿不到返回 None。
    token 是解锁凭证——没有它，你可能会释放掉别人的锁。"""
    token = uuid.uuid4().hex
    ok = await r.set(f"lock:{name}", token, nx=True, px=ttl_ms)
    return token if ok else None
```

### 释放锁：为什么必须用 Lua

**这是最关键的一处。**

```python
# 错误做法：先查再删，两步之间可能被别人插入
# if await r.get(key) == token:
#     await r.delete(key)          # ← 如果在这两行之间锁过期了、别人拿到了新锁，
#                                  #   你会删掉别人的锁

# 正确做法：用 Lua 脚本，Redis 保证脚本执行的原子性
UNLOCK_SCRIPT = """
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
"""

async def release_lock(name: str, token: str) -> bool:
    """只有持有正确 token 的人才能释放锁。返回是否真的释放了。"""
    result = await r.eval(UNLOCK_SCRIPT, 1, f"lock:{name}", token)
    return result == 1
```

### 复现经典失效

**场景**：进程 A 拿到锁，TTL 10 秒。A 在临界区里遇到了一次 GC 停顿（或者被系统挂起、或者网络抖动），停了 12 秒。锁在第 10 秒过期，进程 B 拿到了锁。第 12 秒 A 醒来，**它以为自己还持有锁**，继续执行临界区——现在 A 和 B 同时在临界区里。

**手工复现**：

```python
async def reproduce_lock_expiry():
    token_a = await acquire_lock("critical", ttl_ms=2000)   # 故意设短
    print("A 拿到锁")

    # 模拟 GC 停顿 / 进程挂起，超过 TTL
    await asyncio.sleep(3)

    token_b = await acquire_lock("critical", ttl_ms=2000)
    print("B 也拿到锁了：", token_b is not None)   # True —— 两个进程同时在临界区

    # A 此时如果直接 delete，会删掉 B 的锁；用 Lua 版本才安全
    released = await release_lock("critical", token_a)
    print("A 尝试释放自己的锁：", released)        # False —— token 对不上，没删成
```

**这个实验说明两件事**：

一、**Lua 释放不是可选的**，它至少防止了「删掉别人的锁」这个更严重的问题。

二、**它防不住「两个进程同时在临界区」**。这是 Redis 分布式锁的固有限制，不是实现 bug。

### 那怎么办

三个方向，按可靠性排序：

**一、锁续期（watchdog）**：后台起一个任务，只要临界区还在执行就定期续 TTL。这是主流客户端库（如 Java 的 Redisson）的做法。**能大幅降低概率，但不能根除。**

**二、让临界区本身幂等**——即使被执行两次结果也一样。**这是 U2.2 和 U4.2 反复强调的那条原则，在这里再次成立。**

**三、真正需要强一致时，别用 Redis 锁，用数据库的行锁**（U4.2 的做法）。它和事务天然一致。

**记住这个结论**：Redis 锁是「大概率互斥」，不是「保证互斥」。**用它的前提是你能接受偶发的重入。**

### 可能卡在哪

**Lua 脚本报错**

`r.eval(script, numkeys, *keys_and_args)` 的参数顺序容易搞错：第二个参数是 key 的个数，然后先传所有 key，再传所有 arg。

## 步骤 5 · 内存与淘汰策略

### 这一步在做什么

Redis 内存装满了会发生什么，由你配的策略决定。选错了会静默丢数据。

### 三个关键配置

```bash
docker compose exec redis redis-cli CONFIG GET maxmemory
docker compose exec redis redis-cli CONFIG GET maxmemory-policy
```

**`maxmemory`**：内存上限。**不设的话 Redis 会一直吃内存直到被系统 OOM killer 杀掉。** 生产环境必须设。

**`maxmemory-policy`**：满了之后怎么办。

| 策略 | 行为 | 什么时候用 |
|---|---|---|
| `noeviction` | 拒绝写入，返回错误 | **当 Redis 存的是不能丢的数据时** |
| `allkeys-lru` | 淘汰最久未使用的 key | **当 Redis 纯当缓存用时** |
| `volatile-lru` | 只淘汰设了 TTL 的 key | 缓存和持久数据混存时 |
| `allkeys-lfu` | 淘汰访问频率最低的 | 热点数据长期稳定时 |

**这个选择直接对应你的架构判断**：如果你的系统里 Redis 只是缓存，选 `allkeys-lru`，丢了自动重建；如果 Redis 里有会话状态这种丢了会影响用户的东西，选 `noeviction` 并且监控内存。

### 过期是怎么发生的

**这里有一个常见误解**：设了 TTL 的 key 不是到点立刻被删。

Redis 用两种机制配合：

**惰性删除**——你访问这个 key 时才检查过期没有，过期了当场删并返回 nil。

**定期删除**——后台任务每隔一段时间随机抽一批设了 TTL 的 key 检查。

**后果是：过期的 key 可能在一段时间内仍然占着内存。** 所以监控内存时要知道，`used_memory` 里可能包含还没被清理的过期数据。

### 观察一次

```bash
docker compose exec redis redis-cli INFO memory | grep -E 'used_memory_human|maxmemory'
docker compose exec redis redis-cli INFO stats | grep -E 'keyspace_hits|keyspace_misses|evicted_keys'
```

**`keyspace_hits` 和 `keyspace_misses` 算出命中率**——这是判断缓存有没有用的核心指标。命中率低于 50% 的缓存，往往是键设计有问题或者 TTL 太短。

## 步骤 6 · 接进你的项目

### 这一步在做什么

把前面五步落到 U0.6 的服务上，并为 S2 到 S4 的用法打好基础。

### 做三件事

**一、给 U0.6 的统计接口加缓存**

同一个 upload_id 加同一组参数的统计结果可以缓存。跑一次前后对比：

| | 无缓存 | 有缓存（命中） |
|---|---|---|
| P50 延迟 | | |
| 数据库查询次数 | | |

**二、给 API 加限流**

用步骤 2 的滑动窗口，按用户或 IP 限制每分钟请求数。测一次：超过限制后返回 429。

**三、写一个 `cache.py` 模块**

把缓存读写、空值缓存、互斥重建、TTL 抖动封装成可复用的函数。**这个模块 S4 的 U4.5 成本治理会直接用**——那里要做工具结果缓存来降本。

### 可能卡在哪

**缓存导致数据不一致**

改了数据但缓存还是旧的。两种解法：写数据时同时删缓存（cache-aside 的标准做法），或者给缓存键加版本号，数据更新时 bump 版本。

**先删缓存还是先写库**

标准答案是**先写库再删缓存**。反过来的话，在「删缓存」和「写库完成」之间的窗口里，如果有读请求进来，会把旧数据重新加载进缓存。
