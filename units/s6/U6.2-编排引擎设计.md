## 步骤 1 · 三种编排模型

### 这一步在做什么

搞清楚三种模型的表达能力和适用场景。

### DAG（有向无环图）

```
    ┌→ 节点B ─┐
节点A          → 节点D
    └→ 节点C ─┘
```

**特点**：步骤固定、可并行、**无环**（不能循环）。

**适合**：数据处理流水线、固定的多步任务。

**不适合**：需要「不满意就重来」的场景。

### 状态机

```
     ┌──────────┐
     ↓          │
[模型] → [工具] ─┘
  │
  └→ [等确认] → [工具]
  │
  └→ [结束]
```

**特点**：节点之间的跳转由条件决定，**可以有环**（循环）。

**适合**：大多数 Agent 场景。**LangGraph 走的就是这条路。**

**这是你要重点实现的。**

### 自由循环

就是 U2.1 的做法：模型自己决定下一步，没有预定义的图。

**特点**：最灵活，最难控制和调试。

**三者的关系**：自由循环可以看成「只有一个节点的状态机，这个节点的下一步由模型决定」。

## 步骤 2 · 设计核心抽象

### 这一步在做什么

**设计先于实现。想清楚有哪些概念，它们之间什么关系。**

### 五个核心概念

```python
from typing import Callable, Awaitable, Any, Annotated, TypedDict
from dataclasses import dataclass, field
from datetime import datetime


# 1. 状态：在节点之间流动的数据。
#    用 Annotated 把「合并策略」贴在字段类型上，而不是写死在引擎里，
#    这样加一个新字段只要声明它怎么合并，引擎代码不用动。
class State(TypedDict):
    messages: Annotated[list, append]   # 合并策略：追加
    current_tool_result: Any            # 合并策略：覆盖（默认）
    confirmed: bool


# 2. 节点：一个函数，接收状态，返回状态的更新（不是完整状态，原因见下一节）
NodeFn = Callable[[State], Awaitable[dict]]


# 3. 边：从哪个节点到哪个节点
@dataclass
class Edge:
    source: str
    target: str | None                 # None 表示这是条件边，目标运行时才算得出来
    condition: Callable[[State], str] | None = None


# 4. 图：节点和边的集合。整个控制流就是这个对象，是数据不是代码
@dataclass
class Graph:
    nodes: dict[str, NodeFn] = field(default_factory=dict)
    edges: list[Edge] = field(default_factory=list)
    entry: str = ""
    # 在这些节点「之前」暂停，等人工输入；对齐 LangGraph 的 interrupt_before 语义
    interrupt_before: set[str] = field(default_factory=set)


# 5. Checkpoint：某一时刻的完整状态。有它才谈得上中断恢复和时间旅行
@dataclass
class Checkpoint:
    run_id: str
    seq: int                           # 单调递增，用来定位「跑到第几步」
    node: str
    state: dict
    created_at: datetime
```

### 关键设计：状态的合并策略

**这是 LangGraph 最巧妙的设计，值得抄。**

节点函数返回的**不是完整的新状态，而是「对状态的更新」**：

```python
async def call_model(state: State) -> dict:
    # 节点只关心自己产出了什么，不用读全量状态再拼一份新的回去
    reply = await llm.chat(state["messages"])
    return {"messages": [reply]}     # 只返回要追加的那一条
```

引擎按每个字段声明的策略合并：

```python
# 每个字段一条合并策略：引擎不需要知道字段的业务含义，只按这张表合
REDUCERS = {
    "messages": lambda old, new: old + new,        # 追加
    "current_tool_result": lambda old, new: new,   # 覆盖
    "count": lambda old, new: old + new,           # 累加
}

def merge_state(old: dict, update: dict) -> dict:
    # 复制而不是原地改：并行分支拿的是同一份状态，就地修改会互相污染
    new = dict(old)
    for k, v in update.items():
        reducer = REDUCERS.get(k, lambda o, n: n)   # 没声明策略的字段默认覆盖
        # 字段第一次出现时没有「旧值」可合，直接写入
        new[k] = reducer(old.get(k), v) if k in old else v
    return new
```

**为什么这个设计重要**：

**并行分支时，两个节点各自返回更新，引擎按策略合并。** 如果节点返回完整状态，并行合并时就不知道该用谁的。

## 步骤 3 · 实现执行器

### 这一步在做什么

写出核心的执行逻辑。

### 单步执行

```python
class Engine:
    def __init__(self, graph: Graph, checkpointer: Checkpointer):
        self.graph = graph
        self.cp = checkpointer

    async def run(self, run_id: str, initial_state: dict | None = None) -> RunResult:
        # 「恢复」和「新建」走同一个入口：调用方不用关心这是第几次跑，
        # 有 checkpoint 就接着跑，没有就从入口开始
        cp = await self.cp.get_latest(run_id)
        if cp:
            state, current = cp.state, cp.node
            logger.info("从 checkpoint 恢复：节点 %s，序号 %d", current, cp.seq)
        else:
            state, current = initial_state or {}, self.graph.entry
            # 先落一个 seq=0 的初始 checkpoint，否则第一个节点跑一半崩了就无从恢复
            await self.cp.save(run_id, 0, current, state)

        seq = cp.seq if cp else 0

        while current is not None:
            # 中断点检查：放在执行「之前」，所以人工可以在节点动手前叫停。
            # approved_* 标记由 resume() 写入，否则恢复后会在同一个点再次中断
            if current in self.graph.interrupt_before and not state.get(f"approved_{current}"):
                await self.cp.save(run_id, seq, current, state, status="interrupted")
                return RunResult(status="interrupted", waiting_node=current, state=state)

            # 执行节点，拿到的是「更新」，按合并策略并回状态
            update = await self._run_node(current, state)
            state = merge_state(state, update)
            seq += 1
            # 每步都存：进程随时可能被 kill，存完这一步才算这一步真的做过
            await self.cp.save(run_id, seq, current, state)

            # 下一步是谁，由边（可能是条件边）决定
            current = self._next_node(current, state)

        return RunResult(status="completed", state=state)

    def _next_node(self, current: str, state: dict) -> str | None:
        for e in self.graph.edges:
            if e.source != current:
                continue
            if e.condition is not None:
                # 条件边：目标在运行时才算出来，所以路由函数只读状态、不改状态
                target = e.condition(state)
                return None if target == "__END__" else target
            return e.target
        # 没有出边就是终点：返回 None 让主循环退出
        return None
```

### 并行分支

```python
async def _run_parallel(self, node_names: list[str], state: dict) -> dict:
    updates = await asyncio.gather(
        # 每个分支拿到同一份状态，各自返回自己的更新，互不可见
        *[self._run_node(n, state) for n in node_names],
        # 不让一个分支的异常取消掉其他分支：异常当成返回值收回来单独处理
        return_exceptions=True,
    )

    merged = {}
    for n, u in zip(node_names, updates):
        if isinstance(u, Exception):
            # 失败也要留在状态里（而不是只打日志），后续节点才能据此决定要不要降级
            logger.error("并行节点 %s 失败：%s", n, u)
            merged = merge_state(merged, {"errors": [f"{n}: {u}"]})
            continue
        merged = merge_state(merged, u)
    return merged
```

**关键点**：

- 每个并行节点拿到的是**同一份状态的副本**，互不干扰
- 结果按合并策略汇总
- **一个失败不影响其他**（`return_exceptions=True`）

### 循环与上限

```python
# 计数存在状态里而不是引擎实例里：恢复时跟着 checkpoint 一起回来，
# 否则重启一次上限就重新算，死循环照样烧钱。双下划线前缀标记它是引擎内部字段
state.setdefault("__node_counts", {})
state["__node_counts"][current] = state["__node_counts"].get(current, 0) + 1
if state["__node_counts"][current] > max_iterations:
    raise LoopLimitExceeded(f"节点 {current} 执行了 {max_iterations} 次")
```

**必须有。** 条件边写错很容易造成死循环。

### 可能卡在哪

**并行节点修改了同一个字段**

合并策略决定结果。**如果两个节点都返回 `{"result": x}`，用「覆盖」策略的话后者赢，而顺序是不确定的。**

**解法**：并行节点要写不同的字段，或者用「追加」策略。**这是设计约束，要在文档里写清楚。**

**恢复时状态不一致**

checkpoint 的存储必须和业务数据在同一个事务里（U4.2 学的）。

## 步骤 4 · Checkpoint 与中断恢复

### 这一步在做什么

**这三样才是框架相比手写循环的真正价值。**

### Checkpointer 接口

```python
# 定成 Protocol 而不是基类：内存实现用来跑测试，Postgres 实现用于生产，两者互不依赖
class Checkpointer(Protocol):
    # status 区分「运行中 / 中断 / 完成」，恢复时靠它判断这个运行能不能续
    async def save(self, run_id: str, seq: int, node: str, state: dict, status: str = "running"): ...
    async def get_latest(self, run_id: str) -> Checkpoint | None: ...
    # 历史全留着，不是只留最新那条——这是时间旅行的前提
    async def get_history(self, run_id: str) -> list[Checkpoint]: ...
```

**`get_history` 的价值**：可以做「时间旅行」——回到任意一个历史 checkpoint 重新跑。**这在调试时极其有用。**

### 中断恢复

```python
async def resume(self, run_id: str, decision: dict | None = None) -> RunResult:
    cp = await self.cp.get_latest(run_id)
    # 先卡状态：对一个正在跑的运行再调一次 resume 会跑出两条并发流
    if cp.status != "interrupted":
        raise ValueError("这个运行不处于中断状态")

    state = cp.state
    if decision:
        # 写入 approved_<节点名>，否则 run() 走到同一个中断点会再停一次；
        # 人工决定本身也存进状态，供后续节点和审计使用
        state = merge_state(state, {
            f"approved_{cp.node}": decision["approved"],
            "human_decision": decision,
        })

    return await self.run(run_id)      # 从 checkpoint 继续
```

**接上 U4.4 的人工确认流程。**

### 流式

```python
async def run_stream(self, run_id: str, initial_state: dict | None = None):
    """跑的同时 yield 事件，让前端能实时看到走到了哪个节点"""
    ...
    while current is not None:
        yield {"type": "node_start", "node": current}
        update = await self._run_node(current, state)
        # 只 yield 摘要而不是完整更新：状态里可能有大段文本或敏感数据，不适合直接推给前端
        yield {"type": "node_end", "node": current, "update": summarize(update)}
        ...
```

builder = GraphBuilder()
