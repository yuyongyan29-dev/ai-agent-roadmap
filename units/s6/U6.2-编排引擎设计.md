## 步骤 1 · 三种编排模型

### 这一步在做什么

搞清楚三种模型的表达能力和适用场景。

### DAG（有向无环图）

```
    ┌→ 节点B ─┐
节点A          → 节点D
    └→ 节点C ─┘
```

**特点**：步骤固定、可并行、**无环**（不能循环）。

**适合**：数据处理流水线、固定的多步任务。

**不适合**：需要「不满意就重来」的场景。

### 状态机

```
     ┌──────────┐
     ↓          │
[模型] → [工具] ─┘
  │
  └→ [等确认] → [工具]
  │
  └→ [结束]
```

**特点**：节点之间的跳转由条件决定，**可以有环**（循环）。

**适合**：大多数 Agent 场景。**LangGraph 走的就是这条路。**

**这是你要重点实现的。**

### 自由循环

就是 U2.1 的做法：模型自己决定下一步，没有预定义的图。

**特点**：最灵活，最难控制和调试。

**三者的关系**：自由循环可以看成「只有一个节点的状态机，这个节点的下一步由模型决定」。

## 步骤 2 · 设计核心抽象

### 这一步在做什么

**设计先于实现。想清楚有哪些概念，它们之间什么关系。**

### 五个核心概念

```python
from typing import Callable, Awaitable, Any
from dataclasses import dataclass, field


# 1. 状态：在节点之间流动的数据
class 状态(TypedDict):
    消息: Annotated[list, 追加]        # 合并策略：追加
    当前工具结果: Any                   # 合并策略：覆盖（默认）
    已确认: bool


# 2. 节点：一个函数，接收状态，返回状态的更新
节点函数 = Callable[[状态], Awaitable[dict]]


# 3. 边：从哪个节点到哪个节点
@dataclass
class 边:
    从: str
    到: str | None                     # None 表示条件边
    条件: Callable[[状态], str] | None = None


# 4. 图：节点和边的集合
@dataclass
class 图:
    节点: dict[str, 节点函数] = field(default_factory=dict)
    边: list[边] = field(default_factory=list)
    入口: str = ""
    中断点: set[str] = field(default_factory=set)     # 在这些节点之前暂停


# 5. Checkpoint：某一时刻的完整状态
@dataclass
class Checkpoint:
    运行id: str
    序号: int
    当前节点: str
    状态: dict
    时间: datetime
```

### 关键设计：状态的合并策略

**这是 LangGraph 最巧妙的设计，值得抄。**

节点函数返回的**不是完整的新状态，而是「对状态的更新」**：

```python
async def 调模型(状态: 状态) -> dict:
    回复 = await llm.对话(状态["消息"])
    return {"消息": [回复]}          # 只返回要追加的那一条
```

引擎按每个字段声明的策略合并：

```python
合并策略 = {
    "消息": lambda 旧, 新: 旧 + 新,        # 追加
    "当前工具结果": lambda 旧, 新: 新,      # 覆盖
    "计数": lambda 旧, 新: 旧 + 新,        # 累加
}

def 合并状态(旧: dict, 更新: dict) -> dict:
    新 = dict(旧)
    for k, v in 更新.items():
        策略 = 合并策略.get(k, lambda 旧, 新: 新)      # 默认覆盖
        新[k] = 策略(旧.get(k), v) if k in 旧 else v
    return 新
```

**为什么这个设计重要**：

**并行分支时，两个节点各自返回更新，引擎按策略合并。** 如果节点返回完整状态，并行合并时就不知道该用谁的。

## 步骤 3 · 实现执行器

### 这一步在做什么

写出核心的执行逻辑。

### 单步执行

```python
class 引擎:
    def __init__(self, 图: 图, checkpointer: Checkpointer):
        self.图 = 图
        self.cp = checkpointer

    async def 跑(self, 运行id: str, 初始状态: dict | None = None) -> 结果:
        # 恢复或初始化
        cp = await self.cp.取最新(运行id)
        if cp:
            状态, 当前 = cp.状态, cp.当前节点
            logger.info("从 checkpoint 恢复：节点 %s，序号 %d", 当前, cp.序号)
        else:
            状态, 当前 = 初始状态 or {}, self.图.入口
            await self.cp.存(运行id, 0, 当前, 状态)

        序号 = cp.序号 if cp else 0

        while 当前 is not None:
            # 中断点检查
            if 当前 in self.图.中断点 and not 状态.get(f"已批准_{当前}"):
                await self.cp.存(运行id, 序号, 当前, 状态, 状态="中断")
                return 结果(状态="中断", 等待节点=当前, 状态数据=状态)

            # 执行节点
            更新 = await self._执行节点(当前, 状态)
            状态 = 合并状态(状态, 更新)
            序号 += 1
            await self.cp.存(运行id, 序号, 当前, 状态)

            # 决定下一个
            当前 = self._下一个(当前, 状态)

        return 结果(状态="完成", 状态数据=状态)

    def _下一个(self, 当前: str, 状态: dict) -> str | None:
        for e in self.图.边:
            if e.从 != 当前:
                continue
            if e.条件 is not None:
                目标 = e.条件(状态)
                return None if 目标 == "__END__" else 目标
            return e.到
        return None
```

### 并行分支

```python
async def _执行并行(self, 节点们: list[str], 状态: dict) -> dict:
    更新们 = await asyncio.gather(
        *[self._执行节点(n, 状态) for n in 节点们],
        return_exceptions=True,
    )

    合并 = {}
    for n, u in zip(节点们, 更新们):
        if isinstance(u, Exception):
            logger.error("并行节点 %s 失败：%s", n, u)
            合并 = 合并状态(合并, {"错误": [f"{n}: {u}"]})
            continue
        合并 = 合并状态(合并, u)
    return 合并
```

**关键点**：

- 每个并行节点拿到的是**同一份状态的副本**，互不干扰
- 结果按合并策略汇总
- **一个失败不影响其他**（`return_exceptions=True`）

### 循环与上限

```python
状态.setdefault("__节点计数", {})
状态["__节点计数"][当前] = 状态["__节点计数"].get(当前, 0) + 1
if 状态["__节点计数"][当前] > 最大迭代:
    raise 循环超限(f"节点 {当前} 执行了 {最大迭代} 次")
```

**必须有。** 条件边写错很容易造成死循环。

### 可能卡在哪

**并行节点修改了同一个字段**

合并策略决定结果。**如果两个节点都返回 `{"结果": x}`，用「覆盖」策略的话后者赢，而顺序是不确定的。**

**解法**：并行节点要写不同的字段，或者用「追加」策略。**这是设计约束，要在文档里写清楚。**

**恢复时状态不一致**

checkpoint 的存储必须和业务数据在同一个事务里（U4.2 学的）。

## 步骤 4 · Checkpoint 与中断恢复

### 这一步在做什么

**这三样才是框架相比手写循环的真正价值。**

### Checkpointer 接口

```python
class Checkpointer(Protocol):
    async def 存(self, 运行id: str, 序号: int, 节点: str, 状态: dict, 状态标记: str = "运行中"): ...
    async def 取最新(self, 运行id: str) -> Checkpoint | None: ...
    async def 取历史(self, 运行id: str) -> list[Checkpoint]: ...
```

**「取历史」的价值**：可以做「时间旅行」——回到任意一个历史 checkpoint 重新跑。**这在调试时极其有用。**

### 中断恢复

```python
async def 恢复(self, 运行id: str, 决定: dict | None = None) -> 结果:
    cp = await self.cp.取最新(运行id)
    if cp.状态标记 != "中断":
        raise ValueError("这个运行不处于中断状态")

    状态 = cp.状态
    if 决定:
        状态 = 合并状态(状态, {f"已批准_{cp.当前节点}": 决定["批准"], "人工决定": 决定})

    return await self.跑(运行id)      # 从 checkpoint 继续
```

**接上 U4.4 的人工确认流程。**

### 流式

```python
async def 跑并流式(self, 运行id: str, 初始状态: dict | None = None):
    """跑的同时 yield 事件"""
    ...
    while 当前 is not None:
        yield {"类型": "节点开始", "节点": 当前}
        更新 = await self._执行节点(当前, 状态)
        yield {"类型": "节点完成", "节点": 当前, "更新": 摘要(更新)}
        ...
```

**接上 U4.3 的事件流和 U5.4 的界面。**

### 定义你的图

```python
图 = 图构建器()
图.加节点("加载记忆", 加载记忆)
图.加节点("调模型", 调模型)
图.加节点("执行工具", 执行工具)

图.设入口("加载记忆")
图.加边("加载记忆", "调模型")

图.加条件边("调模型", lambda s:
    "等确认" if 需要确认(s) else
    "执行工具" if 有工具调用(s) else
    "生成答案")

图.加边("执行工具", "调模型")          # 环
图.加边("等确认", "执行工具")
图.加边("生成答案", "__END__")

图.设中断点({"等确认"})

引擎 = 引擎(图.构建(), PostgresCheckpointer(db))
```

**看这段代码：整个 Agent 的控制流一目了然。** 这就是显式状态图相比隐式循环的价值——**流程是数据，不是藏在代码里的 if-else。**

### 可能卡在哪

**改造成本比想象大**

正常。**先让一个简单场景跑通，再逐步迁移。**

**性能比之前差**

每步都存 checkpoint 会有开销。**但相比模型调用（几秒）可以忽略。** 如果真的成瓶颈，可以隔几步存一次。
