# U6.6 · 作品集、简历与面试准备（21 小时）

**这个单元解决什么问题**

走到这里，你已经有能演示的项目和验收证据。现在把它们整理成陌生人看得懂的作品集、能针对岗位调整的简历，再练习现场解释和调试。

**学完你能做到**：对着作品集能连续讲 40 分钟；30 个高频问题每题都有你自己的答案，其中至少 10 题能引用你项目的真实数据。

**时间分配**：步骤 0 的简历与投递准备 4h，步骤 1–5 的作品集与表达 14h，步骤 6 的独立编码演练 3h。求职材料由 agent 帮你组织，每项经历和数字由你核对。下面示例里的项目数据只演示写法，不能复制成个人业绩。

## 步骤 0 · 把项目证据变成简历和投递材料（4 小时）

### 这一步在做什么

让招聘方快速找到「岗位要求」对应的真实证据。先准备投递材料与记录表，实际投递由你自行决定。

### 怎么做

**第一小时：收集岗位要求和证据。** 从你现在想投的公司官网找三份仍在招聘的 JD，分别偏 Agent 应用、后端工程和产品交付。保存 URL、读取日期和原文要求；找不到某类就记录缺失，不用历史统计代替当前职位。

在 `s6-platform/job-search/evidence.md` 写：

| 岗位原文要求 | 你做过的动作 | 证据位置 | 实测条件与局限 | 状态 |
|---|---|---|---|---|
| 例如：能构建评估体系 | 从失败案例建评估集、校准评分器 | 你自己的报告、提交、截图 | 数据集版本、样本数、模型配置 | 做过 / 练习过 / 没做过 |
| 例如：能排查服务问题 | 找到连接池瓶颈并复测 | U4.8 的前后数据 | 本地 fake 模型，不代表线上吞吐 | |
| 例如：能交付业务功能 | 明确输入、异常与验收 | U1.9 规格及演示反馈 | 原型还是实际用户使用 | |

先填事实，再生成文案。技术范围来自实际贡献，不把「教程要求会做」写成「我已做过」。

**第二小时：写一页中文简历。** 用下面的指令让 agent 起草 `resume-zh.md`：

```text
读取我的 evidence.md、已有里程碑报告和三个岗位的 JD。
先为 Agent 应用方向起草一页中文简历：简介、已有经历、两个重点项目、技能和教育。
只用文件里已有事实，每条项目经历写“为谁解决什么 → 我做的动作 → 如何验证结果”。
量化结果必须指向证据，缺数字就保留待补，不编工作年限、用户数、客户名或收益。
区分工作项目、个人项目、教程练习；说明我在 AI 协作中亲自决定和验收了什么。
另给逐条证据索引，索引不放进正式简历。
```

项目句子的结构可以是：

```text
为【使用者】解决【具体流程】中的【问题】，设计并验收【你的实际工作】；
在【数据版本/规模】上，将【指标】从【实测前值】改为【实测后值】，
代价是【延迟/成本/边界】；结果见【报告或提交】。
```

方括号必须换成自己的事实。没有业务上线就写本地实验或试用，不写「大规模生产」。导出 PDF 后检查是否一页、文字能否选中、链接能否打开。Markdown 一页不等于 PDF 一页。

**第三小时：做岗位变体和英文版。** 保留同一套事实，按三份 JD 调整项目顺序和侧重点：应用岗先讲工具和评估，后端岗先讲幂等、队列、数据库和排障，交付岗先讲规格、演示和用户反馈。给所投岗位准备一页英文版，技术名保留原文，逐句对照中文事实。

```text
按这份目标 JD 调整简历的项目顺序和表述，不增加经历。
给出“修改前 → 修改后 → 对应要求 → 证据”表。
再生成英文版本，保持职责、数字和限制条件完全一致。
发现必需技能没有证据时列为缺口，不塞进技能清单。
```

一页与三类变体是本练习的约束，不是所有雇主的统一规定。Harvard 的[简历指导](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/)强调简明、有针对性地呈现能力与经历；具体格式按目标岗位要求调整。

**第四小时：整理公开入口和投递表。** 用[GitHub 官方说明](https://docs.github.com/en/account-and-profile/tutorials/using-your-github-profile-to-enhance-your-resume)检查个人主页、已有项目 README 和置顶项目。用退出登录的窗口检查演示步骤、限制和复现命令。步骤 1–2 完成后再把 `PORTFOLIO.md` 加到入口，检查新链接；现在不要求已有这份文件。

复制[投递记录模板](../../templates/投递记录模板.md)到 `s6-platform/job-search/applications.md`，先填准备好的三份职位。准备一段沟通草稿：为什么适合、一个证据链接、希望对方了解的具体能力。只填已经实际发生的状态，不把「材料准备好」记成「已投递」。

简历、联系方式、JD 存档和投递表默认保存在个人副本。若你的 fork 公开，在 `.gitignore` 中排除 `s6-platform/job-search/`，公开只展示你愿意分享的项目证据。

### 你验收

随机抽三句简历，能在一分钟内找到原始证据；中英文数字一致；三份岗位变体能解释为什么调了顺序。请一个人读 30 秒，复述你的目标方向和最强证据，记录误解并改一遍。

### 可能卡在哪

**agent 写得很像专家，但你解释不了**：降回你亲自验证的动作。「实现并验证重投不会重复写入」比没测过的「保障高可用」具体。

**没有正式工作经验**：清楚标注个人项目和练习，补齐可复现的结果。不要把录屏、模拟用户或压测请求换算成真实客户量。

### 背后的逻辑

作品集回答「如何做成」，简历帮助对方快速发现相关经历，投递表帮助你区分材料、面试和能力上的卡点。三者共用证据，避免越润色越偏离事实。

## 步骤 1 · 整理作品集

### 这一步在做什么

给六个里程碑各写一页。

### 固定的四段结构

**每一页都用同样的结构，这样别人容易读，你也容易讲。**

```markdown
# M3 · 评估与可观测性体系

## 问题
M2 做完后，我无法回答一个基本问题：改一版 prompt 之后，
它是变好了还是变坏了？我只能凭感觉。
这意味着任何优化都是赌博，任何重构都可能悄悄破坏已有功能。

## 方案
（架构图）

三层验证：
- 确定性逻辑用 pytest（工具函数、解析、权限判断）
- 非确定性逻辑用评估集（模型的判断、规划、生成）
- 全链路 trace 用 Langfuse，属性遵循 OpenTelemetry GenAI 语义约定

（以下数字仅为格式示例，替换成自己的实测证据。）
评估集 52 条，其中 31 条来自使用时的失败。
评分器：6 个代码型 + 1 个校准过的 LLM judge。
CI 分三层跑：PR 跑核心路径子集，合并跑全量，每晚跑深度评估。

## 数据
| 指标 | 数值 |
|---|---|
| 评估集规模 | 52 条（25 典型 / 12 边界 / 10 负例 / 5 回归） |
| 标注一致率 | 90%（10 条双人独立判定） |
| Judge 与人工一致率 | 88%（30 条校准） |
| CI 快速子集耗时 | 4 分 12 秒 |
| CI 单次成本 | ¥0.83 |
| 拦截劣化 PR | 3 次（截图见附录） |

## 取舍
**放弃了「评估工具调用序列」。** 最初我断言「必须先搜索再读详情」，
后来发现模型有时能直接从搜索结果里得到答案，不需要读详情——
这时它被判失败，但它其实做得更好。
改成只评结果，加上两条硬约束的轨迹断言（高危操作必须确认、步数上限）。

**放弃了全量在线评估。** 采样率从 100% 降到 5%，
因为全量评估的成本是业务本身的 1.4 倍。5% 足够看趋势。

**如果重做**：我会更早建评估集。我是在 S3 才开始建，
导致 S2 的很多设计决策只能凭感觉。如果 S2 开始时就有 20 条题，
U2.3 的模式选择和 U2.6 的多 Agent 决策会更有依据。
```

### 「取舍」这一段是区分度最高的

**只讲做了什么的人很多，能讲清楚为什么不做另一种方案的人很少。**

每一页的取舍段要包含：

1. **你放弃了什么**（具体的技术方案）
2. **为什么放弃**（有数据最好）
3. **如果重做会怎么改**（展示反思能力）

### 可能卡在哪

**有些里程碑数据不好看**

**照实写。** 「成本只降了 28%，没达到 40% 的目标，卡在检索质量上——压缩到一定程度后召回率掉太多」比编一个 45% 有说服力得多。

**面试官更在意你怎么分析，而不是数字本身。**

**架构图不会画**

用文字画的 ASCII 图就行，或者用 Mermaid（GitHub 能直接渲染）。**清晰比好看重要。**

## 步骤 2 · 准备总览页

### 这一步在做什么

一页纸讲清楚整个项目。**这是面试官最先看的。**

### 结构

```markdown
# 项目名 · 一句话描述

**是什么**：（两句话）

**在线地址**：https://...
**代码**：https://github.com/...

## 我做了什么
从零构建了一个 Agent 系统，覆盖从原型到生产的完整链路：
Agent 核心（工具、记忆、检索、编排）→ 评估与可观测性 →
生产化（持久化、安全、成本、灰度）→ 产品化（实际完成的 Web / 小程序 / App）→
运行时抽象（配置化的 Agent runtime）

## 关键数据
| | |
|---|---|
| 评估集 | 52 条，judge 与人工一致率 88% |
| 检索质量 | 混合检索 + rerank，召回率@5 从 0.62 提升到 0.89 |
| 成本 | 单任务从 ¥0.315 降到 ¥0.176（-44%），评估分掉 0.01 |
| 可靠性 | kill -9 后能续跑，副作用不重复 |
| 安全 | 10 个提示注入样本，第一轮 6 个成功，修复后全部失效 |

## 技术栈
Python / FastAPI / Postgres+pgvector / Docker / LangGraph /
MCP / Langfuse / TypeScript / Next.js / Taro

## 最想讲的三件事
1. 评估体系（M3）——它让所有后续优化成为可能
2. 成本优化（M4）——用数据驱动的方法降了 44%
3. 我放弃的那些方案——多 Agent、某些成本优化、A2A
```

**「最想讲的三件事」这一段很有用**：它给了面试官一个抓手，也让你能主导话题走向。

## 步骤 3 · 准备系统设计题

### 这一步在做什么

练三道，每道画出架构图并写出关键取舍。

### 题目一：企业客服 Agent 平台

**要求**：多租户、知识库隔离、人工接管、7×24 可用。

**你要覆盖的点**：

| 点 | 你的经验来自 |
|---|---|
| 多租户数据隔离 | U5.5 的三层隔离 + RLS |
| 知识库的切分和检索 | U2.5 |
| 人工接管的时机和交接 | U4.4 的确认流 + U2.6 的 handoff |
| 质量保证 | U3 整个阶段 |
| 成本控制（客服量大） | U4.5 的路由和缓存 |
| 高可用和降级 | U4.8 |

**关键取舍要讲**：什么时候转人工（置信度阈值？关键词？用户主动要求？）；知识库更新后怎么保证不出错（评估集回归）。

### 题目二：长时研究 Agent

**要求**：能跑数小时、可中断、可恢复、成本可控、结果可追溯。

**你要覆盖的点**：

| 点 | 来自 |
|---|---|
| 状态持久化和 checkpoint | U4.2 |
| 异步架构和事件流 | U4.3 |
| 上下文管理（长任务上下文会爆） | U1.5 |
| 多 Agent 的上下文隔离 | U2.6 |
| 成本预算和熔断 | U4.5 |
| 结果的来源追溯 | U2.5 的返回值带来源 |

**关键取舍**：什么时候拆子 Agent（上下文压力 vs 成本翻倍）；中断恢复的粒度（每步存 vs 每 N 步存）。

### 题目三：Agent 的评估与发布流水线

**要求**：从代码提交到上线的完整链路。

**你要覆盖的点**：整个 S3 + U4.6。

**这道题你有完整的实战经验，是你的强项题。**

### 怎么练

**每道题限时 30 分钟**：

1. 5 分钟澄清需求（规模？延迟要求？预算？）
2. 10 分钟画架构
3. 10 分钟讲关键取舍
4. 5 分钟讲怎么验证和演进

**录音听一遍**，找出讲不清楚的地方。

## 步骤 4 · 准备高频问题

### 这一步在做什么

**30 个问题，每题写出你自己的答案，尽量引用真实数据。**

### 八组问题

**检索（5 题）**

1. 怎么提升召回率？
2. 混合检索为什么有效？RRF 相比加权求和好在哪？
3. Rerank 的代价是什么？什么时候不值得？
4. Chunk 策略怎么选？
5. 多跳问题怎么处理？

**幻觉（3 题）**

6. 幻觉的机制是什么？
7. 怎么检测和降低？
8. 怎么让模型承认不知道？

**评估（5 题）**

9. 评估集怎么建？多少条够？
10. LLM judge 怎么校准？有哪些偏见？
11. 怎么防止评估集饱和？
12. 离线分高但线上体验差，怎么办？
13. 怎么评估多步任务？评过程还是评结果？

**上下文（3 题）**

14. 长上下文为什么会衰减？
15. 三种压缩策略怎么选？
16. 上下文中毒怎么处理？

**多 Agent（3 题）**

17. 什么时候该拆？
18. 多 Agent 的成本代价是什么？
19. 上下文隔离的价值是什么？

**成本（4 题）**

20. 怎么定位成本大头？
21. 有哪些降本手段？各降多少？
22. 降本后怎么保证质量不掉？
23. Prompt caching 的前提条件是什么？

**安全（4 题）**

24. 提示注入怎么防？
25. 间接注入为什么更危险？
26. 沙箱怎么设计？防不住什么？
27. 「最小代理权」是什么？和最小权限的区别？

**工程（3 题）**

28. 断点续跑怎么实现？幂等怎么保证？
29. 灰度和回滚怎么做？
30. Trace 怎么设计？为什么用 OTel 语义约定？

### 答案的标准

**每个答案三段**：

1. **原理**（为什么会这样）
2. **做法**（怎么解决）
3. **我的数据**（我的项目里是什么情况）

举例（第 2 题，数字为写法示例，需要换成你自己的报告）：

> **原理**：向量检索能匹配语义相近但用词不同的内容，但对精确匹配（型号、专有名词、数字）很弱，因为这类字符串没有语义。关键词检索正好相反。两者的失败模式不同，所以组合起来整体召回率高于任何单一方法。
>
> **RRF 相比加权求和的好处**：向量相似度和 BM25 分数量纲不同。RRF 使用排名融合，避免直接相加不同量纲的分数，但候选数量、排名常数和权重仍会影响效果，需要用自己的评估集选择。
>
> **我的数据**：在我自己的 50 篇文档、20 组问答对上测，纯向量召回率@5 是 0.62，加上 BM25 用 RRF 融合后是 0.74，再加 rerank 到 0.89。但 rerank 增加了 1.4 秒延迟，占总延迟的 12%。

**至少 10 题要有第三段。**

## 步骤 5 · 讲一遍

### 这一步在做什么

**说出来和写下来是两回事。**

### 怎么做

**第一遍：对着录音讲 40 分钟。**

结构：

| 时间 | 内容 |
|---|---|
| 0-3 分钟 | 项目总览：是什么、为什么做、最终做成什么样 |
| 3-10 分钟 | M2：Agent 核心的设计和关键决策 |
| 10-20 分钟 | **M3：评估体系（重点，讲透）** |
| 20-30 分钟 | M4：生产化的四个方面 |
| 30-35 分钟 | M5、M6：产品化和运行时抽象 |
| 35-40 分钟 | 我放弃的那些方案，和如果重做会怎么改 |

**M3 要讲最久**，因为它是最有区分度的部分。

**第二遍：听录音，标出这些地方**：

- 卡壳的
- 说了一半发现讲不清楚的
- 用了模糊表述（「效果比较好」「性能有提升」）的
- 讲了但没数据支撑的

**第三遍：改完再讲一遍。**

### 一个实用技巧

**准备三个版本的讲法**：

| 时长 | 场景 |
|---|---|
| **1 分钟** | 自我介绍时的项目描述 |
| **5 分钟** | 面试官说「简单介绍一下你的项目」 |
| **40 分钟** | 深入讨论 |

**1 分钟版最难写，也最重要。** 它要在一分钟内让人知道：你做了什么、难点在哪、结果如何。

## 步骤 6 · 三次独立编码与调试演练（3 小时）

### 这一步在做什么

检验没有 coding agent 帮写时，你是否仍能解释控制流、查出错误并修复。它沿用 U2.1 的小循环，不增加一门编程语言。实际面试能否用 AI 按雇主规则确认，不把一次练习当成所有岗位的要求。

### 怎么做

在三个不同时间段各做一次 60 分钟计时练习。提前保存题目和离线 fake 工具，计时后关闭补全和聊天；允许看语言标准库文档。每次保存自己的代码、测试输出和复盘，不看参考实现重写。

| 轮次 | 任务 | 现场必须验证的行为 |
|---|---|---|
| 1 | 用 U2.1 的工具协议重写最小 Agent 循环 | 正常结束、未知工具、参数错误、步数上限；fake 模型无网络 |
| 2 | 让另一个会话提前在干净副本里埋两个 bug，你定位修复 | 一个正常案例和两个失败案例；解释症状、根因、修复证据 |
| 3 | 在首版循环上增加可测试的取消或任务预算，二选一 | 选取消：取消后不执行下一工具；选预算：耗尽后显式退出。所选分支与已有案例均通过 |

每轮建议用 10 分钟读题和复述约束、35 分钟实现或修复、15 分钟测试并解释。故障轮只把源码和失败输入交给你，答案单独保存，结束后再揭晓，不能自己先看答案再声称盲测。

可在第一轮开始前交给 agent 的准备指令：

```text
只准备 U2.1 工具协议的离线题目、fake 模型响应和验收命令，不给实现。
把正常结束、未知工具、无效参数、达到步数上限列为独立用例。
题目放 s6-platform/practice/round1/；我计时完成之后你再审查代码。
验收不能依赖真实密钥，也不能把“没有抛异常”当成成功完成任务。
```

### 你验收

记录每轮是否完成、通过哪些用例、查了什么资料、哪里解释不清楚。未完成就保留失败输出，回到对应单元补练；不要让 agent 补完后算进自己的计时成绩。

### 可能卡在哪

**读代码没问题，写不出来**：缩小到一个分支，先把输入输出讲清楚，再写。需要补练的内容由失败记录决定，不从头刷一遍语法。

### 背后的逻辑

日常开发仍然由 agent 协作完成。有限的独立演练用来确认：工具给出错误实现时，你有能力判断它错在哪里。

## 39 周之后

学习不会在这里结束，但**方式要变**。往后靠三件事保持：

**一、持续维护你的主线项目。**

真实用户的真实反馈，比任何课程都有价值。你已经有了完整的评估和回流闭环（S3），**让它自己转起来**。

**二、每月读三篇一手工程博客。**

[Anthropic Engineering](https://www.anthropic.com/engineering) 是可持续跟进的一手来源。优先读能解释你当前问题的文章，拿自己的项目验证。

**三、参与一个开源项目。**

从给文档提 PR 开始，慢慢到提 issue、修 bug、加功能。**这是从「会用」到「会造」最有效的路径。**

推荐从你用过的项目开始：Dify、LangGraph、smolagents、MCP 的 server 仓库。**你在 S6 读过它们的源码，有基础。**

### 最后

回头看看 `logs/` 里这一路的周复盘。

**从第一周「不知道 PATH 是什么」，到最后一周「能设计一个 Agent 运行时」——这个跨度是真实的，而且每一步都有代码和数据为证。**

这就是这份计划的全部意义：**不是让你知道很多概念，而是让你手上有一个真的能跑、有数据支撑、别人能用的东西。**
