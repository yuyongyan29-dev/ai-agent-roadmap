# U6.5 · Mini Agent Runtime（20 小时）

**这个单元解决什么问题**

**这是你的毕业设计。** 把 26 周学的所有东西整合成一个别人能用的 Agent 运行时。

**验收标准很具体**：一个陌生人照着你的 README，**在不改你任何代码的前提下，只写一个 YAML 就配出一个能跑的新 Agent**，20 分钟内完成。

**这个标准同时考验三样东西**：抽象设计得对不对、文档写得清不清楚、边界处理得周不周全。**这正是真实开源项目的标准。**

---

## 步骤 1 · 想清楚边界

### 这一步在做什么

**在写代码之前，明确「什么是 runtime 的职责，什么是使用者的职责」。**

### 划清楚

| Runtime 负责 | 使用者负责 |
|---|---|
| 编排执行（U6.2 的引擎） | 定义流程的形状 |
| 工具的注册和调用 | **实现具体的工具函数** |
| 模型调用、路由、降级 | 选哪个模型 |
| 记忆的存取 | 决定记什么 |
| 检索管线 | 提供语料 |
| 沙箱 | 决定要不要开 |
| Trace 埋点 | 无需关心（自动） |
| 评估运行 | **提供评估集** |
| 护栏（轮次、成本、超时） | 设定阈值 |

**关键判断：如果一件事所有 Agent 都要做，就归 runtime；如果每个 Agent 不一样，就暴露成配置。**

### 设计原则

**一、约定优于配置。** 大部分参数有合理默认值，配置文件只写你要改的。

**二、渐进式暴露复杂度。** 最简单的 Agent 应该只需要 5 行配置。复杂的需求再往下挖。

**三、逃生舱。** 配置表达不了的，允许写 Python 扩展。**不要把用户逼死在 YAML 里。**

## 步骤 2 · 设计配置格式

### 这一步在做什么

**配置格式是你的产品界面。设计好它，其余是实现。**

### 最简的配置

```yaml
# 没写的部分（工具、记忆、检索、护栏）全部走默认值，所以这几行就够跑
name: 简单助手
prompt: |
  你是一个有帮助的助手。
model: deepseek/deepseek-v4-pro
```

**5 行，能跑起来一个基础 Agent。** 这是入门体验。

### 完整的配置

```yaml
name: 选题助手
description: 帮我找小红书上值得做的家电选题

# 模型：可以是一个字符串，也可以按环节配
# routes 的键是环节名，简单环节走小模型省钱，难的才用 default
model:
  default: claude-sonnet-5
  routes:
    intent_classify: ollama/qwen3:8b
    chunk_compress: deepseek/deepseek-v4-flash
  # fallback 按顺序降级：上一个不可用（限流、超时、报错）才试下一个
  fallback: [deepseek/deepseek-v4-pro, ollama/qwen3:8b]

# Prompt：可以内联，也可以指向文件（带版本）
prompt: prompts/topic_helper/v3.md

# 工具：本地的 + MCP 的
# include 是白名单：一个模块里可能有十几个工具，只挂这个 Agent 用得上的，
# 免得工具描述把上下文撑爆、也免得模型被无关工具带偏
tools:
  local:
    - module: my_tools.notes          # 指向一个 Python 模块
      include: [search_notes, read_detail]
  mcp:
    - name: feishu
      command: uvx
      args: [lark-mcp-server]
      include: [read_base, write_base]

# 记忆
# compress_after 小于 max_turns：留出余量，压缩在撑爆之前就开始
memory:
  short: { max_turns: 20, compress_after: 12 }
  long:
    enabled: true
    types: [preference, constraint, fact]
    retrieval: { top_k: 5 }

# 检索
# candidates 远大于 top_n：先粗召回一批，再由 rerank 精排出最终 5 条
retrieval:
  collection: my_notes
  chunk: { size: 500, overlap: 100, strategy: structural }
  hybrid: true
  rerank: { enabled: true, top_n: 5, candidates: 30 }

# 编排：不写就用默认的 ReAct 循环
graph:
  type: react              # react | plan_execute | custom
  # type: custom
  # module: my_graphs.topic_flow

# 护栏
# confirm_before 列的是工具名：这些工具不可逆，执行前必须停下来等人确认
guardrails:
  max_turns: 15
  max_cost: 2.0
  tool_timeout: 30
  confirm_before: [publish_note, delete_note]
  sandbox: { enabled: true, network: false }

# 上下文预算（U1.5 的产出）
context:
  budget: 24000
  strategy: summarize        # summarize | select | externalize

# 评估
eval:
  dataset: eval/topic_helper.yaml
  baseline: eval/baseline.json
```

### 用 Pydantic 定义并校验

```python
class AgentConfig(BaseModel):
    """一个 Agent 的完整配置。YAML 读进来后由它校验，字段名即 YAML 的键名。"""

    # 只有 name / model / prompt 必填：没有名字没法区分 Agent，没有模型和 prompt 跑不起来
    name: str
    description: str = ""
    # 联合类型让同一个键既能写成 "claude-sonnet-5"，也能写成带 routes 的对象
    model: str | ModelConfig
    prompt: str
    # 下面这些都给了默认实例（而不是 None），所以最简配置里整段不写也能跑，
    # 且实现里可以直接 config.memory.short.max_turns，不必到处判空
    tools: ToolsConfig = ToolsConfig()
    memory: MemoryConfig = MemoryConfig()
    # 检索和评估用 None 表示「这个能力整体关掉」，和「开着但用默认参数」是两回事
    retrieval: RetrievalConfig | None = None
    graph: GraphConfig = GraphConfig()
    guardrails: GuardrailsConfig = GuardrailsConfig()
    context: ContextConfig = ContextConfig()
    eval: EvalConfig | None = None
```

**每个子配置都有默认值**，所以最简配置能跑。

**配置错误要给出清晰的提示**（这是 Pydantic 的强项，U1.3 学过）：

```
配置文件 configs/my_agent.yaml 有错误：
  guardrails.max_cost
    Input should be a valid number [type=float_parsing, input_value='两块']
```

### 工具的动态加载

**这是「不改代码就能配新 Agent」的关键。**

```python
import importlib

def load_local_tools(module_path: str, include: list[str] | None) -> list[Tool]:
    """按配置里的模块路径导入用户写的工具，runtime 自身完全不认识这些函数。

    module_path 是 YAML 里的 tools.local[].module，形如 "my_tools.notes"；
    include 是白名单，None 表示这个模块里的工具全挂上。
    """
    # 运行时才 import：runtime 打包时不可能知道使用者会写哪个模块
    module = importlib.import_module(module_path)

    tools = []
    for name in dir(module):
        obj = getattr(module, name)
        # 认的是 @tool 装饰器盖的戳，不是命名约定——模块里的普通函数、
        # 顺手 import 进来的第三方符号都不会被误当成工具
        if not callable(obj) or not hasattr(obj, "__tool_meta__"):
            continue
        if include and name not in include:
            continue
        tools.append(build_tool_from_function(obj))
    return tools
```

使用者这样写工具：

```python
# my_tools/notes.py
from mini_runtime import tool
from pydantic import BaseModel, Field

class SearchParams(BaseModel):
    """工具参数。这个类会被转成 JSON schema 发给模型，description 就是给模型的说明。"""

    keyword: str = Field(description="搜索关键词")
    # ge/le 会一起进 schema，模型看得到；同时 Pydantic 会真的挡住越界的调用
    limit: int = Field(default=10, ge=1, le=50, description="返回条数")

# 描述里要写「什么时候用」而不只是「这是什么」——模型是靠它决定调不调的
@tool(description="在笔记库搜索。当你需要了解某话题下已有内容时使用。")
async def search_notes(p: SearchParams) -> str:
    # 返回字符串而不是对象：结果要回填进对话，最终都得是模型能读的文本
    ...
```

**一个装饰器 + 一个 Pydantic 模型，就是一个工具。**

### 可能卡在哪

**循环依赖**

各部件之间可能互相引用。**用依赖注入**：runtime 在启动时构造好各部件，注入给需要的地方，而不是让它们互相 import。

**配置项越来越多，实现越来越乱**

每个部件负责解析自己的配置段，不要在一个大函数里处理所有配置。

## 步骤 4 · 命令行界面

### 这一步在做什么

**让人能用起来。**

### 命令设计

```bash
# 初始化一个新 Agent（生成模板）
mini-runtime init my-agent

# 交互式运行
mini-runtime run configs/my-agent.yaml

# 单次执行
mini-runtime run configs/my-agent.yaml --input "帮我找家电选题"

# 起 HTTP 服务
mini-runtime serve configs/my-agent.yaml --port 8000

# 跑评估
mini-runtime eval configs/my-agent.yaml

# 校验配置
mini-runtime validate configs/my-agent.yaml

# 看 trace
mini-runtime trace <run_id>
```

**`init` 命令很重要**：它生成一个可以直接跑的模板，包括示例配置、示例工具、示例评估集。**新用户的第一步体验就靠它。**

### `init` 生成什么

```
my-agent/
├── config.yaml          # 带注释的配置模板
├── prompts/
│   └── main.md
├── tools/
│   └── example.py       # 一个示例工具，带注释
├── eval/
│   └── dataset.yaml     # 3 条示例评估题
├── .env.example
└── README.md            # 「下一步做什么」
```

**让人 `cd my-agent && mini-runtime run config.yaml` 就能跑起来。**

## 步骤 5 · 写文档

### 这一步在做什么

**验收标准是「陌生人 20 分钟配出新 Agent」。文档决定成败。**

### 必须有的四部分

**一、Quickstart（5 分钟见效果）**

```markdown
## 快速开始

1. 安装
   uv add mini-runtime

2. 初始化
   mini-runtime init my-agent && cd my-agent

3. 配密钥
   cp .env.example .env
   # 编辑 .env，填入你的 API key

4. 运行
   mini-runtime run config.yaml

你会看到一个交互式对话界面。试试输入「你好」。
```

**必须是从零到跑起来，不超过 4 步。**

**二、配置参考（每个字段都要有）**

```markdown
### guardrails.max_turns

类型：整数
默认：15
说明：Agent 循环的最大轮次。达到后强制终止并返回已有结果。

设太小：复杂任务做不完。
设太大：出问题时会浪费很多钱。

建议：从 15 开始，看你的 trace 里实际用了多少轮再调整。
```

**每个字段都要写「设太小会怎样、设太大会怎样」**，而不只是「这个字段是什么」。

**三、常见场景的完整示例**

至少三个：

1. 一个只调用 API 的简单 Agent
2. 一个带知识库检索的 Agent
3. 一个有高危操作和人工确认的 Agent

**每个都是可以直接复制运行的完整配置。**

**四、扩展指南**

- 怎么写自定义工具
- 怎么写自定义图
- 怎么接入自定义的模型提供方

### 文档的检验方法

**把 README 给一个不了解你项目的人（或者用一个新的 Claude Code 会话），让他照着做。**

**他卡在哪，就补哪。**

## 步骤 6 · 验收测试

### 这一步在做什么

**真的找人测。**

### 怎么做

**找一个朋友**（或者用一个全新的 AI 会话模拟），给他：

1. 你的 GitHub 仓库地址
2. 一个任务：「配出一个能查天气并给穿衣建议的 Agent」
3. 一个 API key

**不给任何口头解释。**

**记录**：

| 时间 | 他在做什么 | 卡住了吗 |
|---|---|---|
| 0-3 分钟 | 读 README，装依赖 | 否 |
| 3-5 分钟 | `init` 生成模板 | 否 |
| 5-12 分钟 | 写天气工具 | **卡了，不知道工具函数的返回值格式要求** |
| 12-18 分钟 | 改配置 | 否 |
| 18-20 分钟 | 跑起来 | 否 |

**「卡住」的地方就是文档要补的地方。**

### 如果超过 20 分钟

**说明抽象或文档有问题。** 分析卡点，改进，再找一个人测。

**这个迭代过程本身就是最有价值的部分。**
