# U6.4 · A2A 与多 Agent 互操作（10 小时）

**这个单元解决什么问题**

MCP 解决了「Agent 怎么用工具」。**A2A 解决「Agent 之间怎么互相委派任务」。**

**学完你能做到**：两个独立进程的 Agent 通过 A2A 完成一次任务委派，且 trace 能跨 Agent 串联。

**同时你要能诚实回答**：你的项目现在需不需要它。**大概率不需要，但知道它存在、知道什么时候会需要，这本身就是价值。**

---

## 步骤 1 · 理解 A2A 的定位

### 这一步在做什么

搞清楚它和 MCP 的分工。

### 背景

[A2A 协议](https://a2a-protocol.org)最初由 Google 开发，后捐给 Linux 基金会，现由技术指导委员会维护，成员来自 AWS、Cisco、Google、IBM Research、Microsoft、Salesforce、SAP、ServiceNow。协议已发布 v1.0。

### 和 MCP 的分工

```
        ┌─────────┐   A2A（横向：委派任务）   ┌─────────┐
        │ Agent A │ ←──────────────────────→ │ Agent B │
        └────┬────┘                          └────┬────┘
             │ MCP（纵向：调用工具）                 │ MCP
        ┌────▼────┐                          ┌────▼────┐
        │  工具   │                           │  工具   │
        └─────────┘                          └─────────┘
```

**一句话概括**：MCP 给 Agent「手」，A2A 给 Agent「同事」。

**企业架构里两者通常一起用，不是二选一。**

### 什么时候需要 A2A

| 场景 | 需要吗 |
|---|---|
| 你自己写的几个 Agent 在同一个进程里 | **不需要**，直接函数调用 |
| 你自己写的 Agent 在不同服务里 | 可以用，但自己定义接口也行 |
| **要调用别人（别的团队、别的公司）的 Agent** | **需要**，标准化才能互操作 |
| **要让别人调用你的 Agent** | **需要** |

**核心价值是「跨组织边界的互操作」。** 在一个团队内部，标准协议的价值不大。

## 步骤 2 · 三个核心概念

### 这一步在做什么

理解协议的数据模型。

### Agent Card

**Agent 的「名片」**：说明它是谁、能做什么、怎么调用、需要什么认证。

通常放在一个约定的路径上供发现（类似 `robots.txt` 的思路）。

```json
{
  "name": "笔记分析 Agent",
  "description": "分析小红书笔记的互动数据和内容特征",
  "url": "https://your-agent.example.com/a2a",
  "version": "1.0.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "skills": [
    {
      "id": "analyze_engagement",
      "name": "分析互动率",
      "description": "给定一批笔记 id，返回互动率分析",
      "inputModes": ["text"],
      "outputModes": ["text", "data"]
    }
  ],
  "authentication": { "schemes": ["bearer"] }
}
```

**这和 MCP 的工具 schema 是同一个思路**：**先声明能力，再被调用。**

**具体的字段名和结构以 [A2A 规范当前版本](https://a2a-protocol.org) 为准。**

### Task

**一次委派的任务，有完整的生命周期。**

```
submitted → working → input-required → completed
                    ↘ failed
                    ↘ canceled
```

**注意 `input-required` 这个状态**：被委派方可以说「我需要更多信息」，把球踢回来。**这是 A2A 相比简单 RPC 的关键差异**——任务是长期的、有状态的、可以来回交互的。

**你在 U4.2 做的任务状态机，和这个是同一类东西。**

### Message 和 Artifact

- **Message**：交互过程中的消息（提问、补充信息、进度更新）
- **Artifact**：任务的产出物（报告、文件、结构化数据）

**区分的意义**：消息是过程，产出是结果。客户端可以只关心 Artifact。

## 步骤 3 · 跑通官方示例

### 这一步在做什么

**先跑通别人的，再写自己的。**

### 怎么做

去 [a2aproject/A2A](https://github.com/a2aproject/A2A) 仓库找示例代码。

跑通一个最小的 server 和 client：

1. Server 暴露一个 skill
2. Client 发现它的 Agent Card
3. Client 提交一个 task
4. Server 处理并返回结果
5. Client 拿到 Artifact

**重点观察**：

- Agent Card 是怎么被发现的
- 任务状态是怎么流转的
- 流式更新是怎么推的

### 可能卡在哪

**示例跑不起来**

协议还在演进，示例可能和文档版本不一致。**以仓库当前的 README 为准**，注意看版本号。

**看不懂协议细节**

**不用全懂。** 你需要理解的是：Agent Card 声明能力、Task 有生命周期、Message 和 Artifact 分开。**具体的字段名用到时查。**

## 步骤 4 · 实战：拆成两个 Agent

### 这一步在做什么

**把你的项目拆成两个独立进程，用 A2A 连起来。**

### 怎么拆

从你的项目里找一个相对独立的能力，拆出去：

```
主 Agent（选题助手）
    │
    │ A2A 委派：「分析这 20 篇笔记的互动特征」
    ↓
分析 Agent（独立进程，独立部署）
    │ 内部用 MCP 调用数据工具
    ↓
返回 Artifact：分析报告
```

**选什么拆**：

- 有明确的输入输出边界
- 内部逻辑复杂（值得独立）
- 可能被复用（比如分析能力其他地方也用得上）

### 实现

**Server 侧**（分析 Agent）：

```python
# 暴露 Agent Card
@app.get("/.well-known/agent.json")
async def agent_card():
    return {...}

# 处理任务
@app.post("/a2a/tasks")
async def 创建任务(req: A2A请求):
    task_id = 建任务(req)
    asyncio.create_task(处理(task_id))
    return {"id": task_id, "status": {"state": "submitted"}}

@app.get("/a2a/tasks/{task_id}")
async def 查任务(task_id: str):
    return 取任务状态(task_id)
```

**你会发现这和 U4.3 做的异步任务接口几乎一样。** A2A 只是把它标准化了。

**Client 侧**（主 Agent）：把「委派给分析 Agent」实现成一个工具：

```python
工具表.注册(工具(
    名字="委派分析",
    描述="把笔记分析任务委派给专门的分析 Agent。当需要深度的互动数据分析时使用。",
    参数模型=委派参数,
    函数=通过A2A委派,
))
```

**从主 Agent 的角度看，A2A 委派就是一次工具调用。** 这个抽象很自然。

## 步骤 5 · 四个工程问题

### 这一步在做什么

**协议本身简单，工程细节才是难点。**

### 问题一：Trace 怎么跨 Agent 串联

**这是最重要的一个。**

如果主 Agent 和分析 Agent 各自有独立的 trace，你就看不到完整的执行链路。

**解法：传递 trace context。**

```python
# 主 Agent 发起委派时
headers = {
    "traceparent": 当前trace的W3C格式,      # OpenTelemetry 的标准头
}

# 分析 Agent 接收时
parent_context = 从header解析(request.headers.get("traceparent"))
trace = lf.trace(parent=parent_context, ...)
```

**用 W3C Trace Context 标准**（`traceparent` 头），这样任何遵循 OTel 的系统都能串起来。

**这也是 U3.5 强调用标准语义约定的价值体现。**

### 问题二：错误怎么传播

被委派的 Agent 失败了，主 Agent 怎么办？

**三种策略**：

| 策略 | 适合 |
|---|---|
| 把错误当工具返回值回填给模型 | 大多数情况（模型可以换个方式） |
| 重试委派 | 临时性故障 |
| 整个任务失败 | 这个委派是必须的 |

**默认用第一种**（U2.1 的原则：错误回填给模型）。

### 问题三：超时怎么设

**跨 Agent 的调用是长任务**（对方可能跑几分钟）。

**不要用同步等待。** 用 A2A 的任务模型：提交 → 轮询或订阅 → 拿结果。

**主 Agent 的超时要大于被委派方的最大执行时间。**

### 问题四：权限怎么传递而不放大

**这是安全上最关键的一点。**

主 Agent 有权限 A、B、C。它委派任务给分析 Agent。

**分析 Agent 应该拿到什么权限？**

**错误做法**：把主 Agent 的完整凭证传过去。**这会导致权限放大**——分析 Agent 只需要读数据的权限，却拿到了删除的权限。

**正确做法**：签发一个**受众受限、能力受限、时间受限**的临时凭证：

```json
{
  "sub": "user_123",
  "aud": "analysis-agent",           // 只能被分析 Agent 使用
  "scope": ["notes:read"],           // 只有读权限
  "exp": 1234567890,                 // 5 分钟后过期
  "task_id": "t_abc"                 // 绑定到这个任务
}
```

**「受众绑定」（aud）很重要**：即使凭证泄露，也只能对指定的服务使用。

**这就是 U4.4 讲的「最小代理权」在跨 Agent 场景的应用。**

## 步骤 6 · 诚实评估

### 这一步在做什么

**回答：你的项目现在需要 A2A 吗。**

### 判断

问自己三个问题：

1. **我的几个 Agent 是不是在同一个进程/服务里？** 是的话，直接函数调用更简单。
2. **我需要调用别人的 Agent，或让别人调用我的吗？** 不需要的话，自定义接口就够。
3. **我未来 6 个月会有跨组织的 Agent 协作需求吗？** 没有的话，现在做是过度设计。

**大概率你的答案是「现在不需要」。**

**这个结论完全合格。** 写清楚：

> 我实现了 A2A 的 server 和 client，把分析能力拆成了独立 Agent。
> 但在我的实际场景里，这两个 Agent 部署在同一台机器上、由我一个人维护，
> A2A 带来的标准化收益（跨组织互操作）我用不上，
> 反而增加了一层网络调用的延迟（+180ms）和运维复杂度。
>
> **所以生产环境我保留单进程的直接调用，A2A 的实现留在代码里作为未来的扩展点。**
>
> 什么时候会启用：如果分析能力要被其他团队复用，或者要接入别人的 Agent。

**这段话展示的判断力，比「我用了 A2A 协议」有价值得多。**
