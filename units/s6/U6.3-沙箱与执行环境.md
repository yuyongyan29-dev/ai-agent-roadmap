# U6.3 · 沙箱与执行环境（12 小时）

**这个单元解决什么问题**

让 Agent 能安全地执行不可信代码。

**为什么需要**：U2.7 步骤 5 讲的「代码执行模式」能大幅减少工具数量和轮次，但**硬门槛是必须有沙箱**。没有沙箱就让模型执行代码，等于把机器交给它。

**学完你能做到**：一个能执行不可信 Python 代码的沙箱，5 个逃逸尝试全部失败；以及一份诚实的威胁模型。

---

## 步骤 0 · 两个真实案例（重读）

### 这一步在做什么

U4.4 提过这两个 CVE，这里从沙箱设计的角度再看一遍。**它们是本单元的设计依据。**

### CVE-2026-22708（2026-01-14，Cursor 2.3 之前）

Agent 在自动运行加白名单模式下，**某些 shell 内建命令能绕过白名单执行，不需要用户批准。**

**设计教训**：**不要在 shell 命令字符串上做白名单匹配。**

原因：shell 有太多让你防不住的机制——内建命令、别名、变量展开、命令替换、管道、重定向。你写的正则永远会漏掉一种。

**正确做法**：不给 shell，直接执行进程（`execve` 而不是 `sh -c`），或者在真正的执行点（系统调用层）做限制。

### CVE-2025-59532（2025-09-22，Codex CLI 0.2.0–0.38.0）

沙箱配置逻辑的 bug 导致**模型生成的工作目录被当成了沙箱的可写根目录**，包括目标文件夹之外的路径。

**设计教训**：**沙箱的边界绝对不能由被沙箱的东西自己决定。**

模型的输出是不可信输入。用它来配置安全策略，等于让嫌疑人自己写审讯笔录。

### 共同点

**两个都不是「模型作恶」，而是工程实现的边界搞错了。写这两个工具的都是顶尖团队。**

**所以本单元的顺序是**：先写威胁模型，再写代码，最后自己攻击自己。

## 步骤 1 · 写威胁模型

### 这一步在做什么

**在写任何代码之前，先想清楚防谁、防什么、不防什么。**

### 模板

```markdown
# 沙箱威胁模型

## 攻击者能控制什么
1. 模型生成的代码内容（完全控制）
2. 用户输入（完全控制）
3. Agent 读取的外部文档、网页（通过间接注入，完全控制其中的文字）
4. 工具返回的部分内容（如果工具调用外部服务）

## 我要保护什么
| 资产 | 为什么 | 优先级 |
|---|---|---|
| 宿主机文件系统 | 有源码、密钥、其他用户数据 | 最高 |
| 环境变量里的密钥 | 泄露 = 账号被盗刷 | 最高 |
| 内网其他服务 | 数据库、内部 API | 高 |
| 其他用户的数据 | 隐私和合规 | 高 |
| 计算资源 | 被挖矿或耗尽 | 中 |
| 出网能力 | 数据外泄、DDoS 跳板 | 中 |

## 我不防什么（明确列出）
1. 沙箱内的代码浪费自己的 CPU 时间（有超时兜底）
2. 沙箱内的代码打印大量输出（有长度截断）
3. 内核 0day 提权（超出我的能力范围，接受这个风险）
4. 侧信道攻击（同上）

## 我的假设
1. Docker/容器运行时本身没有已知可利用的逃逸漏洞
2. 宿主机的内核是打过补丁的
3. 我不会给沙箱容器 privileged 或挂载 docker.sock

## 如果假设被打破
容器逃逸 → 攻击者拿到宿主机权限 → 全部资产失守。
缓解：宿主机上不放密钥（用外部密钥服务），沙箱跑在独立的机器/VM 上。
```

### 为什么「不防什么」这一段必须写

**因为它划定了你的能力边界，让你不会自欺欺人。**

一个说「我什么都防住了」的沙箱设计，一定是没想清楚的。

**面试时这一段特别加分。** 能说清楚自己防不住什么的人，比声称万无一失的人可信得多。

## 步骤 2 · 容器沙箱

### 这一步在做什么

用 Docker 实现基础隔离。

### 怎么做

```python
import asyncio, json, uuid
from pathlib import Path

async def run_in_sandbox(code: str, timeout_seconds: int = 10, allow_network: bool = False) -> dict:
    """在一次性容器里执行不可信代码，返回截断后的输出。

    默认不给网络：需要出网是例外，必须由调用方显式打开，
    这样「忘了配」的结果是更安全而不是更危险。
    """
    # 每次执行用一个新的随机 id，容器名和工作目录都从它派生，
    # 并发执行之间不会互相覆盖文件、也不会 kill 错容器
    run_id = uuid.uuid4().hex
    # 路径由我的代码拼出来，绝不接受模型给的目录——这就是 CVE-2025-59532 踩的坑
    work_dir = Path(f"/tmp/sandbox/{run_id}")
    work_dir.mkdir(parents=True)
    (work_dir / "main.py").write_text(code, encoding="utf-8")

    args = [
        "docker", "run", "--rm",
        # 显式命名，超时后才有办法精确 kill 这一个容器
        "--name", f"sbx-{run_id}",

        # 网络
        "--network", "none" if not allow_network else "sandbox-net",

        # 资源限制
        "--memory", "256m",
        "--memory-swap", "256m",          # 禁用 swap，否则内存限制形同虚设
        "--cpus", "0.5",
        "--pids-limit", "64",             # 防 fork 炸弹

        # 文件系统
        "--read-only",                                    # 根文件系统只读
        "--tmpfs", "/tmp:rw,noexec,nosuid,size=64m",      # 临时目录，不可执行
        "-v", f"{work_dir}:/work:ro",                     # 代码只读挂载
        "-w", "/work",

        # 权限
        "--user", "65534:65534",          # nobody，非 root
        "--cap-drop", "ALL",              # 丢弃所有 capability
        "--security-opt", "no-new-privileges",

        "python:3.13-slim",
        "python", "main.py",
    ]

    try:
        # create_subprocess_exec 而不是 _shell：参数以列表传入，不经过 shell 解析，
        # 代码里的引号、分号、反引号都不会被当成命令
        p = await asyncio.create_subprocess_exec(
            *args,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
        )
        out, err = await asyncio.wait_for(p.communicate(), timeout=timeout_seconds)
        return {
            "success": p.returncode == 0,
            # 截断长度：沙箱内的代码可以无限打印，不截断会把整段日志和模型上下文撑爆
            "stdout": out.decode(errors="replace")[:8000],
            "stderr": err.decode(errors="replace")[:2000],
            "exit_code": p.returncode,
        }
    except asyncio.TimeoutError:
        # 超时只是 Python 这边不等了，容器还在跑，必须显式 kill，否则留下僵尸容器占资源
        await asyncio.create_subprocess_exec("docker", "kill", f"sbx-{run_id}")
        return {"success": False, "stdout": "", "stderr": f"执行超过 {timeout_seconds} 秒，已终止"}
    finally:
        # 放在 finally 里：无论成功、报错还是超时都要清掉临时目录
        import shutil
        shutil.rmtree(work_dir, ignore_errors=True)
```

### 逐条解释关键参数

| 参数 | 防什么 |
|---|---|
| `--network none` | **出网、访问内网服务** |
| `--memory` + `--memory-swap` | 内存耗尽。**两个都要设**，只设第一个的话会用 swap |
| `--cpus` | CPU 耗尽 |
| `--pids-limit` | **fork 炸弹** |
| `--read-only` | 修改容器内的系统文件 |
| `--tmpfs ... noexec` | **写一个文件然后执行它** |
| `-v ...:ro` | 修改你的代码 |
| `--user 65534` | root 权限。**这一条很关键**，容器默认是 root |
| `--cap-drop ALL` | 各种特权操作 |
| `--rm` | 容器堆积 |

### 三条绝不能做的

**一、不要挂载 `/var/run/docker.sock`。** 挂了等于给了宿主机 root 权限。

**二、不要用 `--privileged`。** 同上。

**三、工作目录的路径不能来自模型输出。** 这就是 CVE-2025-59532 的教训。

### 可能卡在哪

**每次执行都起一个容器，太慢**

冷启动大约几百毫秒。优化：

1. 预热容器池（提前起几个空闲容器待命）
2. 用更轻的运行时

**但先跑通再优化。** 几百毫秒相比模型调用的几秒可以接受。

**需要网络的场景怎么办**

创建一个受限的网络，只允许访问你的代理：

```bash
docker network create --internal sandbox-net
```

然后在这个网络里跑一个正向代理，只放行白名单域名。

**需要装第三方包**

预先构建一个包含常用包的镜像，而不是让沙箱内 `pip install`（那需要网络）。

## 步骤 3 · 能力白名单

### 这一步在做什么

在容器隔离之上，再加一层「这段代码能调用什么」的限制。

### 为什么还需要这一层

容器隔离防的是「代码能碰到什么资源」。**白名单防的是「代码能做什么操作」。**

比如你允许沙箱访问你的数据库（通过受限的代理），但**只允许 SELECT，不允许 DROP TABLE**。这一层容器管不了。

### 怎么做：提供受限的 API

不让沙箱直接连数据库，而是提供一个受限的函数库：

```python
# 注入到沙箱环境里的库
class RestrictedDataAPI:
    """沙箱内的代码只能通过这个接口访问数据。

    这个类里没有数据库连接对象，也没有连接字符串——
    沙箱拿到的只是几个方法，即使代码被完全控制，能做的也就是这几件事。
    """

    async def search_notes(self, keyword: str, limit: int = 10) -> list[dict]:
        # 真正的查询在宿主机执行，这里只把参数通过 IPC 转发出去；
        # 权限校验、SQL 拼接、结果过滤全部发生在沙箱之外
        return await _call_host("search_notes", {"keyword": keyword, "limit": limit})

    # 刻意不提供 execute_sql 之类的方法：暴露一个能跑任意 SQL 的口子，
    # 前面所有限制就都白做了
```

**沙箱内的代码只能调用你暴露的方法。** 它拿不到数据库连接，也就无法执行任意 SQL。

**这个模式的本质：把「能力」而不是「资源」交给沙箱。**

### 关于 shell 命令

**回到 CVE-2026-22708 的教训。**

如果你确实需要让 Agent 执行 shell 命令：

```python
# 错误：在字符串上做白名单
# split()[0] 看到的只是「字面上的第一个词」，`ls; rm -rf /`、`ls $(rm -rf /)`
# 都能通过检查，真正执行的却是别的命令
if command.split()[0] in allowlist:
    subprocess.run(command, shell=True)      # shell=True 是灾难

# 好一些：不给 shell，直接执行进程
# shlex.split 按 shell 的引号规则切成参数列表，但不做变量展开和命令替换；
# shell=False 时这个列表直接进 execve，管道、分号、反引号都只是普通字符
command_parts = shlex.split(command)
if command_parts[0] not in allowlist:
    return reject()
subprocess.run(command_parts, shell=False)   # 不经过 shell

# 最好：根本不提供「执行任意命令」的能力
# 而是为每个具体需求提供一个专门的工具
```

**最后一种是最安全的。** 「执行任意 shell 命令」这个能力本身就很难安全化。

### 可能卡在哪

**沙箱内怎么和宿主通信**

三种方式：

1. **通过挂载的文件**：沙箱写请求文件，宿主轮询处理，写回响应文件
2. **通过 stdin/stdout**：宿主和沙箱进程用管道通信
3. **通过受限网络里的 HTTP 服务**

**第 2 种最简单**，适合起步。

## 步骤 4 · 了解更强的隔离

### 这一步在做什么

**知道容器不是隔离的终点，以及什么时候需要更强的。**

### 容器的隔离强度

容器共享宿主机内核（U0.9 讲过）。**这意味着内核漏洞可能导致逃逸。**

对于「防误操作」，容器足够。**对于「防蓄意攻击」，容器是有风险的。**

### 两种更强的方案

**gVisor**：在容器和内核之间加一层用户态的系统调用拦截层。容器的系统调用不直接到宿主内核，而是被 gVisor 处理。

- **优点**：大幅减少内核攻击面
- **代价**：性能损失（某些工作负载明显），部分系统调用不支持

**Firecracker 微虚拟机**：为每个沙箱起一个极简的虚拟机，有独立的内核。

- **优点**：隔离强度接近传统虚拟机
- **代价**：启动稍慢（百毫秒级），资源开销更大

**很多云厂商的 Serverless 和沙箱服务底层用的就是 Firecracker。**

### 你现在该怎么做

**理解它们解决什么问题就够，不用实现。**

**在威胁模型里写清楚**：

```markdown
## 隔离强度选择
当前使用容器隔离。
接受的风险：内核 0day 可能导致逃逸。
缓解措施：宿主机上不放密钥；沙箱跑在独立机器上；定期打内核补丁。
如果未来处理不可信的多租户负载，需要升级到 gVisor 或微虚拟机。
```

## 步骤 5 · 自己攻击自己

### 这一步在做什么

**验证。不测试的沙箱等于没有沙箱。**

### 五个逃逸尝试

**尝试 1：读宿主机文件**

```python
# /etc/passwd 读到的应该是容器镜像自带的那份，不是宿主机的
print(open("/etc/passwd").read())
# /proc/1/environ 是最常见的密钥泄露路径：进程环境变量里往往有 API key
print(open("/proc/1/environ").read())
# 列根目录，确认看到的是容器的文件系统而不是宿主机挂进来的东西
import os; print(os.listdir("/"))
```

**期望**：只能看到容器内的文件系统，读不到宿主机的东西，环境变量里没有密钥。

**尝试 2：访问网络**

```python
import socket, urllib.request
# 出网测试：加 timeout，否则网络被禁时这行会挂很久，看不出是被拦还是卡住
print(urllib.request.urlopen("http://example.com", timeout=3).read()[:100])
# 内网测试比出网更重要：172.17.0.1 是 docker 默认网桥的宿主机地址，
# 5432 是 Postgres——真实事故里数据在内网被拖走的比直接出网的多
s = socket.create_connection(("172.17.0.1", 5432), timeout=3)
```

**期望**：全部失败（`--network none`）。

**尝试 3：耗尽资源**

```python
# 内存：一次要 10GB，远超 --memory 256m，应该被 OOM killer 干掉而不是拖垮宿主机
x = bytearray(10 ** 10)

# CPU + 时间：死循环烧满一个核，靠 --cpus 限流、靠 wait_for 超时终止
while True: pass

# fork 炸弹：不停 fork，没有 --pids-limit 的话会把宿主机的进程表占满
import os
while True: os.fork()
```

**期望**：分别被内存限制、超时、pids-limit 挡住，**且不影响宿主机**。

**注意：跑 fork 炸弹时观察宿主机的负载**，确认真的被限制住了。

**尝试 4：写文件并执行**

```python
# 根文件系统只读，但 /tmp 是可写的 tmpfs，所以写入这一步预期会成功
open("/tmp/x.sh", "w").write("#!/bin/sh\necho pwned")
import os, subprocess
# 加执行位也会成功——chmod 改的是 inode 权限，和挂载选项是两回事
os.chmod("/tmp/x.sh", 0o755)
# 真正该失败的是这一步：noexec 让内核拒绝从这个挂载点加载可执行文件
subprocess.run(["/tmp/x.sh"])
```

**期望**：失败（`/tmp` 挂载了 `noexec`）。

**尝试 5：提权**

```python
import os
# 先确认起点：--user 65534 生效的话这里是 nobody，不是 root
print(os.getuid())              # 应该是 65534，不是 0
# 再试着提回 root：cap-drop ALL 拿掉了 CAP_SETUID，这里应该抛 PermissionError
os.setuid(0)                    # 应该失败
```

**期望**：uid 非 0，setuid 失败（`no-new-privileges` + `cap-drop ALL`）。

### 记录

```markdown
| 尝试 | 内容 | 结果 | 被哪一层挡住 |
|---|---|---|---|
| 1 读宿主文件 | ... | ✓ 失败 | 容器文件系统隔离 |
| 2 访问网络 | ... | ✓ 失败 | --network none |
| 3a 耗内存 | ... | ✓ 被 kill | --memory 256m |
| 3b 死循环 | ... | ✓ 超时终止 | asyncio timeout |
| 3c fork 炸弹 | ... | ✓ 失败 | --pids-limit 64 |
| 4 写并执行 | ... | ✓ 失败 | tmpfs noexec |
| 5 提权 | ... | ✓ 失败 | --user + cap-drop |
```
