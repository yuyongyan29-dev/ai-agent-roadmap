# U6.1 · 拆解主流 Agent 平台（10 小时）

**这个单元解决什么问题**

你已经做出了一个 Agent。现在看看「Agent 平台」是什么——**它让不会写代码的人也能配出 Agent。**

理解它的构成，你才知道自己的项目要平台化的话缺什么，也才知道大厂在做什么。

**学完你能做到**：一份平台对比文档，说清各家的编排抽象差异，以及你的项目平台化最先要补的三个能力。

---

## 步骤 1 · 动手用，不要只看文章

### 这一步在做什么

**每个平台都真的搭一个 Agent，不要只看介绍。**

### 选三个

| 平台 | 为什么选它 |
|---|---|
| **[Dify](https://github.com/langgenius/dify)** | **开源，可以本地部署然后读源码。这是最有价值的一个** |
| **Coze**（字节） | 看它的工作流编排和多渠道发布 |
| **一个企业级平台**（腾讯、阿里的） | 看它们怎么对接企业内部系统和权限 |

### 部署 Dify 到本地

```bash
git clone https://github.com/langgenius/dify.git
cd dify/docker
# 官方只给 .env.example，必须复制一份出来；端口冲突和内存参数都改这个文件
cp .env.example .env
# Dify 是多容器组合（API、worker、web、数据库、向量库），所以用 compose 一次拉起而不是单个 docker run
docker compose up -d
```

（具体步骤以仓库当前的 README 为准。）

**在每个平台上搭同一个东西**：一个能检索知识库并回答问题的 Agent。**这样才能公平对比。**

### 可能卡在哪

**Dify 部署失败**

看 `docker compose logs`。常见原因：端口冲突（改 `.env` 里的端口）、内存不够（Dify 组件较多，建议至少 8GB）。

**没有企业版账号**

看公开的文档和演示视频。**重点是理解它的产品形态，不是必须亲手用。**

## 步骤 2 · 六个维度对比

### 这一步在做什么

**结构化地观察，而不是凭印象。**

### 每个平台回答同样六个问题

**一、编排是怎么表达的？**

| 形态 | 特点 |
|---|---|
| **拖拽 DAG** | 直观，非技术人员能用，但表达能力有限（循环、复杂条件难画） |
| **状态机** | 表达能力强，但概念门槛高 |
| **代码** | 最灵活，但只有开发者能用 |
| **自然语言配置** | 门槛最低，但不可控 |

**记录每家用的是哪种，以及它们怎么处理「循环」和「条件分支」。**

**二、工具怎么接入？**

- 有插件市场吗？
- 支持 MCP 吗？
- 能自定义 HTTP 调用吗？
- 工具的参数怎么配置？

**三、知识库怎么做？**

**这一项对你特别有价值**，因为你在 U2.5 亲手做过 RAG。

看它们：

- 切分策略暴露了哪些参数？
- 用什么 embedding 模型？能换吗？
- 支持混合检索吗？有 rerank 吗？
- 检索质量怎么评估？（**大多数平台在这一项上很弱**）

**四、状态和记忆存在哪？**

- 会话历史怎么管理？
- 有长期记忆吗？
- 长对话怎么处理（有没有压缩）？

**五、怎么发布和分发？**

- 能发布成 API 吗？
- 能嵌入网页吗？
- 能发布到微信、飞书、钉钉这些渠道吗？

**六、可观测性和评估提供了什么？**

- 能看到完整的执行 trace 吗？
- 有没有内置的评估能力？
- 成本和延迟能看到吗？

**这一项通常是各家最弱的。** 你做完 S3 之后，会发现自己的评估体系比很多商业平台还完整。

### 输出对比表

```markdown
| 维度 | Dify | Coze | 企业平台 X | 我的项目 |
|---|---|---|---|---|
| 编排形态 | 拖拽 DAG + 代码节点 | 拖拽工作流 | ... | 代码（LangGraph） |
| 循环怎么表达 | 迭代节点 | ... | ... | 状态机的边 |
| 工具接入 | 插件 + HTTP + MCP | 插件市场 | ... | 本地 + MCP |
| 检索可配参数 | chunk 大小、重叠、top_k | ... | ... | 全部可配 |
| 支持 rerank | 是 | ... | ... | 是 |
| 检索质量评估 | **无** | **无** | ... | **有（20 组评测集）** |
| 长期记忆 | ... | ... | ... | 有（U2.4） |
| Trace | 有基础的 | ... | ... | 完整（OTel 语义） |
| 内置评估 | **弱** | **无** | ... | **完整（S3）** |
```

**把「我的项目」这一列加上，你会发现一个有意思的事实：你在评估和可观测性上比很多平台强。**

## 步骤 3 · 读 Dify 源码

### 这一步在做什么

**看清楚一个完整平台的真实结构。**

### 重点看四处

**一、工作流引擎在哪、怎么实现的**

找到执行工作流的核心代码，看它：

- 节点是怎么定义和注册的
- 怎么决定下一个执行哪个节点
- 状态在节点之间怎么传递
- 怎么处理并行和条件分支

**和你 U2.1 手写的循环对比，看它多了什么。**

**二、工具系统**

- 工具的抽象是什么（一个接口？一个基类？）
- 参数 schema 怎么生成
- 内置工具、自定义工具、MCP 工具怎么统一

**三、知识库的实现**

- 切分在哪一层做
- 检索管线是怎么组装的
- 有没有做 rerank

**对比你 U2.5 的实现。**

**四、多租户和权限**

- 数据怎么按租户隔离（是不是用了你 U5.5 学的 RLS？）
- 权限模型是什么

### 可能卡在哪

**代码太多读不完**

**不要读完。** 带着上面四个问题，用搜索定位到相关的目录和文件，只读那部分。

**用你的 IDE 的「跳转到定义」功能**，从一个入口顺着调用链读下去。

**看不懂某段代码**

用 Claude Code 问：「解释这个文件在整个系统里的作用，它的调用者是谁，它调用了什么」。

**这正是 AI 辅助阅读代码的最佳场景。**

## 步骤 4 · 总结平台的部件清单

### 这一步在做什么

把观察变成一个可复用的认知框架。

### 一个 Agent 平台的部件

```
┌─────────────────────────────────────────┐
│ 面向用户的层                              │
│ · 配置界面（拖拽编排 / 表单 / 代码编辑器）   │
│ · 调试和预览                              │
│ · 发布和渠道管理                          │
├─────────────────────────────────────────┤
│ 运行时                                   │
│ · 编排引擎（节点、边、状态、并行、循环）      │
│ · 工具系统（注册表、schema、执行器、MCP）    │
│ · 模型抽象层（多提供方、路由、降级）          │
│ · 记忆（短期、工作、长期）                  │
│ · 检索（切分、嵌入、混合检索、rerank）       │
│ · 沙箱（代码执行、隔离）                    │
├─────────────────────────────────────────┤
│ 平台能力                                 │
│ · 多租户和权限                            │
│ · 配额和计费                              │
│ · 可观测性（trace、日志、指标）             │
│ · 评估                                   │
│ · 版本管理和发布流程                       │
├─────────────────────────────────────────┤
│ 基础设施                                 │
│ · 任务队列和调度                          │
│ · 存储（关系库、向量库、对象存储）           │
│ · 密钥管理                                │
└─────────────────────────────────────────┘
```

**对照这张图，标出你的项目已经有哪些、缺哪些。**

你会发现：**运行时和平台能力你基本都有了（S2 到 S4 做的），缺的主要是「面向用户的配置层」。**

## 步骤 5 · 回答「我的项目要平台化，最先补什么」

### 这一步在做什么

**把观察落到自己的项目上。**

### 三个候选方向

**方向一：配置化**

现在你的 Agent 是硬编码的。平台化的第一步是**让它能被配置出来**：

```yaml
# 一个 Agent 的全部可变部分都收敛到这份配置里：换 Agent 只改这个文件，不改代码
name: 选题助手                             # 给人看的名字，会出现在界面和 trace 里
prompt: prompts/topic_helper_v3.md         # prompt 单独放文件，才能像代码一样做版本和 diff
tools: [search_notes, analyze_engagement]  # 只写工具名，运行时去注册表里取实现
model: claude-sonnet-5
```

**U6.5 会做这个。**

**方向二：多租户**

现在你的 U5.5 做了用户隔离，但那是「一个应用的多个用户」。

平台化意味着「多个租户，每个租户有自己的 Agent、知识库、工具」。**隔离的维度多了一层。**

**方向三：可视化编排**

让不会写代码的人也能配。**这是工作量最大的一块，而且对个人项目价值最低。**

### 建议

**优先做方向一。** 它成本最低、价值最高，而且是 U6.5 毕业设计的核心。

**方向三除非你的目标就是做一个平台产品，否则不要投入。**

**关键产出**

一段有观点的结论：

> 三个平台的编排抽象差异很大。Dify 用拖拽 DAG 加代码节点，循环用专门的迭代节点表达，表达能力够但复杂逻辑画出来很乱。Coze 更偏产品化，编排简化了但灵活性低。
>
> 我的项目在运行时层面已经比较完整，缺的主要是配置层——现在换一个 Agent 要改代码。
>
> 但有一个反直觉的发现：**我的评估和可观测性比这三个平台都完整**。它们都能看 trace，但都没有「评估集 + 门禁 + 回归」这套东西。这说明「让人能配出 Agent」和「保证 Agent 质量」是两个不同的产品方向，前者是易用性，后者是工程能力。
>
> 平台化最先补：1. 配置化（U6.5 做）2. 工具的动态注册 3. 多租户的资源隔离。
