## 步骤 1 · 理解数据从哪来

### 这一步在做什么

搞清楚整条链路，再动手。

### 链路

```
Agent 后端（S4 的 U4.3）
  │  产生事件写入 task_events 表
  │  通过 SSE 推送：GET /tasks/{id}/events
  ↓
Next.js API 路由（转发层）
  │  加鉴权，转发 SSE 流
  ↓
浏览器
  │  EventSource 或 fetch stream 接收
  ↓
React 状态 → 界面
```

**关键**：你在 U4.3 已经做好了事件流。**这个单元主要是把它接到界面上。**

### 事件类型回顾

```
task_started / turn_started / thinking       # 任务开始 / 轮次开始 / 思考（流式文本片段）
tool_started / tool_finished / tool_failed   # 工具开始 / 工具完成 / 工具失败
confirmation_required                        # 需要人工确认
task_completed / task_failed                 # 任务完成 / 任务失败
```

**每种事件对应界面上的一种展示。**

## 步骤 2 · 转发 SSE

### 这一步在做什么

Next.js 的 API 路由把后端的 SSE 流转发给浏览器。

### 怎么做

```tsx
// src/app/api/tasks/[id]/events/route.ts
export const runtime = "nodejs";        // 不要用 edge，流式行为不一致

export async function GET(
  req: Request,
  { params }: { params: Promise<{ id: string }> },
) {
  const { id } = await params;
  const user = await getCurrentUser();
  if (!user) return new Response("未授权", { status: 401 });

  // 归属校验：任务 id 是连续可猜的，不验证就能订阅别人的任务事件流
  if (!(await taskBelongsToUser(id, user.id))) {
    return new Response("无权限", { status: 403 });
  }

  // 断线重连时浏览器自动带这个头，直接透传给后端做续传，前端不用记进度
  const lastEventId = req.headers.get("last-event-id") ?? "0";

  const upstream = await fetch(
    `${process.env.AGENT_API}/tasks/${id}/events?last_event_id=${lastEventId}`,
    {
      headers: { Authorization: `Bearer ${process.env.AGENT_API_KEY}` },
      signal: req.signal,               // 客户端断开时连带断开上游，否则后端连接一直挂着
    },
  );

  // 直接把上游的 body（ReadableStream）交出去，不 await 不缓存，才是真流式转发
  return new Response(upstream.body, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache, no-transform",
      "Connection": "keep-alive",
      "X-Accel-Buffering": "no",        // 关掉 nginx 缓冲
    },
  });
}
```

### 三个关键点

**一、`signal: req.signal`**。客户端关掉页面时，这个 signal 会被 abort，从而也断开对后端的连接。**不加的话后端连接会一直挂着，浪费资源。**

**二、`X-Accel-Buffering: no`**。很多反向代理会缓冲响应，导致流式变成一次性返回。这个头告诉它别缓冲。

**三、归属校验**。任务 id 是可猜的，必须验证这个任务属于当前用户。

### 可能卡在哪

**流式不生效，一次性全出来了**

按顺序排查：

1. `Content-Type` 是不是 `text/event-stream`
2. 有没有中间层缓冲（加 `X-Accel-Buffering: no`）
3. runtime 是不是 nodejs
4. 后端有没有真的流式发出来（用 `curl -N` 直接测后端）

**用 curl 测后端**是最有效的排查方法：

```bash
# -N 关掉 curl 自己的缓冲，否则看到的「一次性返回」是 curl 造成的假象
curl -N "$AGENT_API/tasks/$ID/events?last_event_id=0"
```

**如果 curl 是流式的，问题在转发层；如果 curl 也是一次性的，问题在后端。**

## 步骤 3 · 前端接收事件

### 这一步在做什么

在 React 里把事件流变成状态。

### 用 EventSource（简单）

```tsx
"use client";
import { useEffect, useState, useRef } from "react";

// id 用后端给的 SSE event id，去重和排序都靠它，不要用数组下标
type TaskEvent = { id: number; type: string; data: any };

function useTaskEvents(taskId: string | null) {
  const [events, setEvents] = useState<TaskEvent[]>([]);
  const [status, setStatus] = useState<"idle" | "running" | "done" | "failed">("idle");
  // 用 ref 存连接，是为了让 useEffect 之外的 stop 也能拿到它
  const esRef = useRef<EventSource | null>(null);

  useEffect(() => {
    if (!taskId) return;

    const es = new EventSource(`/api/tasks/${taskId}/events`);
    esRef.current = es;
    setStatus("running");

    // 柯里化成 handle(type) 是因为 addEventListener 的回调拿不到自己监听的事件名
    const handle = (type: string) => (e: MessageEvent) => {
      setEvents(prev => [...prev, { id: Number(e.lastEventId), type, data: JSON.parse(e.data) }]);
    };

    // 这些是中间过程事件，只累积不改任务状态
    ["turn_started", "thinking", "tool_started", "tool_finished", "tool_failed", "confirmation_required"]
      .forEach(t => es.addEventListener(t, handle(t)));

    // 终态事件要主动 close：EventSource 默认会自动重连，不关就会一直重新拉流
    es.addEventListener("task_completed", (e) => {
      handle("task_completed")(e as MessageEvent);
      setStatus("done");
      es.close();
    });

    es.addEventListener("task_failed", (e) => {
      handle("task_failed")(e as MessageEvent);
      setStatus("failed");
      es.close();
    });

    return () => { es.close(); };        // 清理，U5.2 学的
  }, [taskId]);

  // 只 close 是「前端不看了」，后端还在烧钱，必须同时通知后端取消
  const stop = () => {
    esRef.current?.close();
    fetch(`/api/tasks/${taskId}/cancel`, { method: "POST" });
  };

  return { events, status, stop };
}
```

### EventSource 的优点和限制

| 优点 | 限制 |
|---|---|
| **浏览器内置，自动重连** | 只支持 GET |
| **自动带 Last-Event-ID** | **不能自定义请求头**（所以鉴权要靠 cookie） |
| 简单 | 不支持 POST |

**「自动带 Last-Event-ID」是关键优势**：断线重连时浏览器自动把上次收到的 id 发过去，配合你 U4.3 做的续传逻辑，**用户完全感知不到断线**。

**如果需要自定义头或 POST**，改用 `fetch` + `ReadableStream` 手动解析。**先用 EventSource 跑通，有需要再换。**

### 可能卡在哪

**重复连接**

`useEffect` 在开发模式下会执行两次。确保清理函数正确关闭连接。

**事件重复**

断线重连时如果 `last_event_id` 传得不对，会重复收到事件。**在状态更新时按 id 去重**：

```tsx
setEvents(prev => {
  // 返回原数组（而不是新数组）能顺便省掉一次重渲染
  if (prev.some(e => e.id === newEvent.id)) return prev;
  return [...prev, newEvent];
});
```

## 步骤 4 · 渲染执行过程

### 这一步在做什么

**这一步决定了你的界面是「Agent 产品」还是「聊天框」。**

### 要显示什么

```
┌─────────────────────────────────────┐
│ 用户：帮我看看这周家电类目值得做的选题   │
├─────────────────────────────────────┤
│                                     │
│  ⚙️ 正在搜索「家电 选题」…              │
│  ✓ 找到 23 条笔记（0.4 秒）            │
│                                     │
│  ⚙️ 正在读取 3 篇高赞笔记的详情…         │
│  ✓ 完成（1.2 秒）                     │
│                                     │
│  ⚙️ 正在分析互动数据…                   │
│  ✓ 完成                              │
│                                     │
│  💭 基于这些数据，我发现…（流式文本）      │
│                                     │
└─────────────────────────────────────┘
```

### 三条设计原则

**一、工具调用要说人话**

```tsx
// 差
工具：search_notes(keyword="家电 选题", limit=50)

// 好
正在搜索「家电 选题」…
```

**在事件的数据里带上给人看的描述**，而不是让前端去解析原始参数。

**二、完成的步骤要折叠但可展开**

任务跑到第 8 步时，前 7 步的详情占了太多空间。**默认折叠成一行摘要，点击展开看详情。**

**三、区分「进行中」和「已完成」**

用不同的图标和颜色。进行中的可以有动画（转圈或呼吸效果）。

### 组件结构

```tsx
function ExecutionTimeline({ events }: { events: TaskEvent[] }) {
  // 界面要的是「步骤」不是「事件」：把 tool_started 和 tool_finished 按 call_id 配成一条
  const steps = groupIntoSteps(events);

  return (
    <div className="space-y-2">
      {steps.map(s => (
        <StepRow key={s.id} step={s} />
      ))}
    </div>
  );
}

function StepRow({ step }: { step: Step }) {
  // 折叠状态放在每一行自己身上，展开一行不会引起整个列表重渲染
  const [expanded, setExpanded] = useState(false);

  return (
    <div className="border-l-2 pl-3 py-1"
         // 用左边框的颜色区分进行中和已完成，比额外加一块背景更不打扰
         style={{ borderColor: step.status === "running" ? "#3b82f6" : "#d1d5db" }}>
      <button onClick={() => setExpanded(!expanded)} className="flex items-center gap-2 w-full text-left">
        <span>{step.status === "running" ? "⚙️" : step.status === "failed" ? "❌" : "✓"}</span>
        {/* description 取自事件里的 summary，是后端写好的人话，前端不解析原始参数 */}
        <span className="flex-1">{step.description}</span>
        {step.duration && <span className="text-xs text-gray-500">{step.duration}s</span>}
      </button>
      {expanded && (
        // 详情是原始参数和返回，只在展开时给排查问题的人看
        <pre className="mt-2 text-xs bg-gray-50 dark:bg-gray-800 p-2 rounded overflow-x-auto">
          {JSON.stringify(step.detail, null, 2)}
        </pre>
      )}
    </div>
  );
}
```

### 可能卡在哪

**事件顺序乱了**

按事件 id 排序，不要依赖到达顺序。

**`tool_started` 和 `tool_finished` 怎么配对**

在事件数据里带一个 `call_id`，前端按它配对。**在后端产生事件时就带上。**

## 步骤 5 · 人工确认界面

### 这一步在做什么

把 U4.4 的确认流程接到界面上。

### 流程

```
收到 confirmation_required 事件
    ↓
显示确认卡片：操作摘要 + 影响范围 + 批准/拒绝按钮
    ↓
用户点击
    ↓
调用 /api/tasks/{id}/resume 带上决定
    ↓
后端继续执行，继续推事件
```

### 卡片设计

```tsx
function ConfirmCard({ confirmation, taskId }: { confirmation: ConfirmRequest; taskId: string }) {
  // 提交中就锁住两个按钮，否则用户连点会往 resume 发多次决定
  const [submitting, setSubmitting] = useState(false);

  // reason 只在拒绝时填：U4.4 里它会被回填给模型，让模型换个做法
  const decide = async (approved: boolean, reason?: string) => {
    setSubmitting(true);
    await fetch(`/api/tasks/${taskId}/resume`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      // 请求体的键用后端（Python）的 snake_case，跟 API 契约保持一致
      body: JSON.stringify({ confirmation_id: confirmation.id, approved, reason }),
    });
  };

  return (
    <div className="border-2 border-amber-400 rounded-lg p-4 bg-amber-50 dark:bg-amber-950">
      <div className="font-semibold mb-2">⚠️ 需要你确认</div>
      {/* summary 取自 confirmation_required 事件的 action，是一句人话，不是工具参数 */}
      <div className="mb-3">{confirmation.summary}</div>

      {/* 影响范围可能几十条，默认收起，用 details 免掉一个额外状态 */}
      {confirmation.affectedItems && (
        <details className="mb-3 text-sm">
          <summary className="cursor-pointer">查看受影响的内容（{confirmation.affectedItems.length} 项）</summary>
          <ul className="mt-2 space-y-1">
            {confirmation.affectedItems.map((x, i) => <li key={i}>· {x}</li>)}
          </ul>
        </details>
      )}

      <div className="flex gap-2">
        <button onClick={() => decide(true)} disabled={submitting}
                className="px-4 py-2 bg-amber-600 text-white rounded disabled:opacity-50">
          批准
        </button>
        <button onClick={() => decide(false, "用户拒绝")} disabled={submitting}
                className="px-4 py-2 border rounded disabled:opacity-50">
          拒绝
        </button>
      </div>
    </div>
  );
}
```

### 三个要点

**一、显示「影响范围」而不是原始参数。** U4.4 讲过：用户看不懂 `ids=[201,205,...]`。

**二、按钮要有 disabled 状态。** 防止重复点击。

**三、拒绝时可以让用户填理由。** 这个理由会回填给模型（U4.4 的设计），让它调整策略。

## 步骤 6 · 打磨细节

### 这一步在做什么

让它像个成品。

### 清单

**Markdown 渲染**

```bash
pnpm add react-markdown remark-gfm
```

模型输出经常带 Markdown（列表、加粗、表格）。不渲染的话用户看到的是一堆 `**` 和 `|`。

**代码块高亮**：如果你的场景会输出代码，加一个高亮库。

**自动滚动**（U5.2 学的），但要加一个判断：**用户手动往上滚时不要强制拉回底部。**

```tsx
// 是否自动滚由「用户当前在哪」决定，而不是由「有没有新内容」决定
const [autoScroll, setAutoScroll] = useState(true);

const handleScroll = (e) => {
  const { scrollTop, scrollHeight, clientHeight } = e.currentTarget;
  // 留 50px 容差：滚动条很难精确停在底部，严格判等会让自动滚动随机失效
  setAutoScroll(scrollHeight - scrollTop - clientHeight < 50);
};
```

**这个细节很影响体验。** 用户想回看前面的内容时，界面一直把他拽到底部会很烦。

**复制按钮**、**重新生成**、**停止**。

**错误提示**：区分「模型出错」「网络断了」「配额用完了」，给不同的提示和操作建议。
