# U5.5 · 认证与数据（10 小时）

**这个单元解决什么问题**

现在你的应用只有一个用户（你）。加上认证之后，多个人可以各自使用，数据互不可见。

**这一单元的重点不是「怎么接登录」，而是「怎么保证数据不串」。** 后者才是真正会出事故的地方。

**学完你能做到**：两个账号各自登录，会话历史互不可见，越权测试失败。

---

## 步骤 1 · 选认证方案

### 这一步在做什么

选一个，跑通，不纠结。

### 选项

| 方案 | 适合 | 说明 |
|---|---|---|
| **Auth.js**（原 NextAuth） | 开源、自托管、免费 | 配置稍多，但完全可控 |
| **Clerk** | 省事、体验好 | 海外服务，国内访问可能慢 |
| **手机号验证码** | 国内产品的标配 | 需要接短信服务，有成本 |
| **微信登录** | 国内、要接小程序 | 和 U5.6 的小程序能打通 |

### 建议

**练手阶段用 Auth.js + GitHub/Google 登录**，最快跑通，零成本。

**如果你的项目最终要接小程序（U5.6），提前考虑微信登录**，这样 Web 和小程序能用同一套账号。

### 核心概念

不管用哪个方案，都是这三步：

```
1. 用户证明身份（密码、验证码、第三方授权）
2. 服务端签发一个凭证（session cookie 或 JWT）
3. 后续请求带上凭证，服务端验证
```

### 可能卡在哪

**session 还是 JWT**

| | Session（服务端存） | JWT（自包含） |
|---|---|---|
| 撤销 | **容易**（删记录即可） | **难**（要维护黑名单） |
| 扩展 | 需要共享存储 | 无状态，易扩展 |
| 大小 | cookie 里只有一个 id | cookie 里是完整 token |

**对你的项目，session 更简单也更安全。** 「能立刻撤销」这个特性在出事时很重要。

## 步骤 2 · 数据隔离（最重要的一步）

### 三层防御

```
  用户 A 的请求
      │
  ┌───▼─────────────────────────────────────┐
  │ 第 3 层：接口层归属校验                    │
  │ if session.user_id !== user.id: 403     │  按 id 访问时挡住
  └───┬─────────────────────────────────────┘
      │
  ┌───▼─────────────────────────────────────┐
  │ 第 1 层：应用层过滤                        │
  │ WHERE user_id = $1                      │  正常路径
  │ ⚠ 人会忘。写一百个查询总有一个漏           │
  └───┬─────────────────────────────────────┘
      │
  ┌───▼─────────────────────────────────────┐
  │ 第 2 层：数据库行级安全（RLS）  ★ 兜底      │
  │ POLICY USING (user_id = current_setting) │
  │ 即使你写了 SELECT * FROM sessions         │  忘记过滤也挡住
  │ 也只能查到自己的行                         │
  └───┬─────────────────────────────────────┘
      │
      ▼  只返回 A 的数据

  ⚠ RLS 最常见的失效原因：应用用的是超级用户账号。
     超级用户会绕过 RLS，让这一层形同虚设。
```



### 这一步在做什么

**这是本单元真正的重点。认证解决「你是谁」，隔离解决「你能看什么」。**

### 三层防御

**第一层：应用层过滤**

每个查询都带用户过滤：

```typescript
// 每个查询都自己带上 user_id 过滤：这是正常路径，但完全依赖写查询的人记得加
const sessions = await db.query(
  "SELECT * FROM sessions WHERE user_id = $1 ORDER BY updated_at DESC",
  [user.id],
);
```

**问题**：人会忘。写一百个查询，总有一个忘了加 `WHERE user_id = ?`。

**第二层：行级安全（RLS）——数据库层兜底**

**这一层是关键。它让「忘记加过滤」这个错误在数据库层被挡住。**

```sql
-- 开启后这张表上的所有查询都会被策略过一遍；不开启的话策略写了也没用
ALTER TABLE sessions ENABLE ROW LEVEL SECURITY;

-- FOR ALL 表示 SELECT/INSERT/UPDATE/DELETE 都受这条策略约束，
-- 只写 FOR SELECT 的话，别人仍然能改到不属于自己的行
CREATE POLICY user_isolation ON sessions
  FOR ALL
  -- current_setting 读的是连接/事务上的运行时变量，由应用层在每次请求开头写入；
  -- 第二个参数 true 表示变量没设置时返回 NULL 而不是报错
  USING (user_id = current_setting('app.current_user_id', true));
```

应用层在每个事务开头设置当前用户：

```typescript
// 把当前用户写进事务级变量，RLS 策略读的就是它
await db.query("SELECT set_config('app.current_user_id', $1, true)", [user.id]);
// 之后这个事务里的所有查询都自动带上过滤
```

**`true` 参数表示「只在当前事务内有效」**，事务结束自动清除，不会污染连接池里的其他请求。

**效果**：即使你写了 `SELECT * FROM sessions`（忘了加过滤），也只能查到自己的数据。

**第三层：接口层归属校验**

对于「按 id 访问」的接口，显式校验：

```typescript
// 按 id 直接取，绕过了列表查询里的 user_id 过滤，所以必须在这里补一次归属校验
const session = await getSession(sessionId);
if (session.user_id !== user.id) {
  // 必须用严格比较 !==：宽松的 != 会先做类型转换，null / undefined 这类空值会被判成相等，直接放行
  return new Response("无权限", { status: 403 });      // 不是 404
}
```

### 为什么返回 403 而不是 404

**有争议，两种做法各有道理**：

- **403「无权限」**：诚实，但泄露了「这个 id 存在」的信息
- **404「不存在」**：不泄露信息，但用户可能困惑

**对于可枚举的 id（自增整数），用 404 更安全。对于随机 UUID，403 无所谓。**

**建议：id 用 UUID，返回 403。** UUID 猜不出来，不存在枚举风险。

### 可能卡在哪

**RLS 配了但不生效**

按顺序检查：

1. 表上开了 `ENABLE ROW LEVEL SECURITY` 吗
2. 应用用的数据库账号是不是超级用户（**超级用户会绕过 RLS**）
3. `set_config` 是不是在同一个事务/连接里执行的

**第 2 点最常见**：本地开发时用 postgres 超级用户，RLS 形同虚设。**建一个普通用户给应用用。**

**连接池导致 user_id 串了**

这是最危险的 bug。**用 `set_config(..., true)` 的事务作用域版本**，或者确保每个请求用完连接就归还并清除设置。

**写一个测试专门验证这一点。**

## 步骤 3 · 会话管理

### 这一步在做什么

让用户能管理自己的对话历史。

### 数据结构

```sql
-- 会话表：一行 = 一次对话。id 用 UUID 而不是自增整数，别人猜不出来，没有枚举风险
CREATE TABLE sessions (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     TEXT NOT NULL,
    title       TEXT NOT NULL DEFAULT '新对话',
    created_at  TIMESTAMPTZ DEFAULT now(),
    updated_at  TIMESTAMPTZ DEFAULT now(),
    archived    BOOLEAN DEFAULT false     -- 软删除标记，不真的删行
);

-- 列表页永远是「某个用户 + 未归档 + 按更新时间倒序」，索引照着这个形状建；
-- 加 WHERE NOT archived 做成部分索引，归档的行不占索引空间
CREATE INDEX ON sessions (user_id, updated_at DESC) WHERE NOT archived;

CREATE TABLE messages (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    -- 删会话时消息一起删，避免留下查不到归属的孤儿行
    session_id  UUID NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    role        TEXT NOT NULL,           -- user / assistant / tool
    content     TEXT NOT NULL,
    task_id     TEXT,                    -- 关联到 U4.3 的任务
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- 按会话取消息总是要按时间排，这个复合索引让「查一个会话的全部消息」一次走完
CREATE INDEX ON messages (session_id, created_at);
```

### 功能清单

- [ ] 列表（分页，最近的在前）
- [ ] 新建
- [ ] 继续之前的对话
- [ ] 重命名
- [ ] 删除（软删除，用 `archived` 字段）
- [ ] 搜索（按标题或内容）

### 自动生成标题

用户第一条消息发出后，用一次便宜的调用生成标题：

```typescript
// 只喂第一条用户消息就够了：标题要的是主题，不是摘要，喂全量历史纯属浪费 token
const title = await chatWithSmallModel(
  // 「只输出标题本身」这句不能省，否则模型会加上「这个对话的主题是……」
  "用不超过 15 个字概括这个对话的主题，只输出标题本身：\n" + firstMessage,
);
```

**用小模型**（U1.7 测过，这类任务够用）。

### 可能卡在哪

**为什么软删除**

用户可能误删。软删除让你能恢复，也保留了审计线索。

**真正的物理删除**留给「用户主动要求清空所有数据」的场景，那时要连 trace 里的数据一起删（数据合规要求）。

**搜索怎么做**

先用 `ILIKE '%关键词%'` 跑通。数据量大了再上全文检索（U2.5 学的）。

## 步骤 4 · 用量限制

### 这一步在做什么

接上 U4.5 的配额系统，防止单个用户烧光你的预算。

### 前端要做的

**一、显示剩余额度**

```tsx
<div className="text-sm text-gray-500">
  {/* toFixed(2) 把金额固定到两位小数，否则浮点余额会显示成 3.9000000000000004 */}
  今日剩余：{remainingCalls} 次 / ¥{remainingBudget.toFixed(2)}
</div>
```

**二、超限时给出明确提示**

```tsx
// 靠服务端返回的错误码分支，不要去匹配错误文案——文案一改前端就失效了
if (error.type === "quota_exceeded") {
  return <div>今日额度已用完，明天 0 点重置。</div>;
}
```

**不要只显示「请求失败」。** 用户不知道发生了什么。

**三、提交前预检查**

```typescript
// 提交前先问一次配额：额度早就用完了还让请求发出去，用户要等一个来回才看到失败
const quota = await fetchQuota();
if (quota.remaining <= 0) {
  showToast("今日额度已用完");
  return;                     // 不要发请求
}
```

**这样能避免用户点了半天发现不能用。**

### 可能卡在哪

**配额检查的时机**

服务端必须在任务开始前检查（U4.5 讲过）。**前端的检查只是体验优化，不能替代服务端检查。**

**任何只在前端做的校验都是装饰品。**

## 步骤 5 · 越权测试

### 这一步在做什么

**验证你的隔离真的有效。这一步不能省。**

### 测试清单

准备两个账号 A 和 B。用 A 登录，尝试访问 B 的数据。

| 测试 | 怎么测 | 期望 |
|---|---|---|
| **直接改 URL** | 用 A 的身份访问 `/chat/{B的会话id}` | 403 或 404 |
| **改 API 参数** | 用 A 的 cookie 调 `GET /api/sessions/{B的id}` | 403 |
| **改 Server Action 参数** | 用 A 的身份调 `deleteSession({B的会话id})` | 抛权限错误 |
| **订阅别人的任务** | 用 A 的身份订阅 `/api/tasks/{B的任务id}/events` | 403 |
| **列表接口** | 用 A 的身份调 `GET /api/sessions` | 只返回 A 的 |
| **RLS 兜底** | 故意写一个不带 `WHERE user_id` 的查询 | 仍然只返回 A 的 |

**最后一条是验证 RLS 的关键。** 临时写一个测试接口，故意不加过滤，看能不能查到别人的数据。

### 怎么测

用 curl 加上 A 的 cookie：

```bash
# 先登录拿到 cookie
curl -c cookies.txt -X POST http://localhost:3000/api/auth/... 

# 带着 A 的 cookie 去请求 B 的资源，期望被拒；这里必须用 -b 读 cookie，
# 用 -c 只会把响应里的 cookie 写回文件，请求本身仍然是未登录的
curl -b cookies.txt "http://localhost:3000/api/sessions/$B_SESSION_ID"
```

### 记录结果

```markdown

| 测试 | 结果 | 备注 |
|---|---|---|
| 直接改 URL | ✓ 403 | |
| 改 API 参数 | ✓ 403 | |
| 改 Server Action 参数 | **✗ 成功了！** | 忘了加归属校验，已修复 commit abc123 |
| 订阅别人的任务 | ✓ 403 | |
| 列表接口 | ✓ 只返回自己的 | |
```

**第一次做，通常会发现至少一个漏洞。** 这就是这个测试的价值。
