# U5.0 · 三端技术栈怎么选（4 小时）

**这个单元解决什么问题**

你的 Agent 后端已经上线（S4）。现在要给它一个用户能碰到的界面，摆在面前的是三条路：网页、微信小程序、手机 App。**一个人不可能同时做三端，先做哪个、用什么做，是一个业务决定，不是技术偏好。** 这个单元让你在写第一行界面代码之前把这个决定做掉，并且能说清楚理由。

**学完你能做到**：给出你自己项目的三端选型表，写明先做哪端、第二端什么时候做、哪些代码能复用，每一条都有依据。

---

## 步骤 1 · 三端各自是什么，成本差在哪

### 这一步在做什么

先把三条路的**真实成本**摆出来。大多数人选错不是因为技术，是因为低估了上线环节的成本。

### 三端对照

| | Web（Next.js） | 微信小程序（Taro） | App（Expo / React Native） |
|---|---|---|---|
| **用户怎么打开** | 一个链接，任何设备 | 微信内搜索、扫码、分享卡片 | 应用商店下载安装 |
| **适合的场景** | 需要被搜索到、需要分享链接、桌面端使用、B 端后台 | 用户在微信里、需要微信登录/支付/分享裂变、轻量高频 | 需要推送通知、后台运行、相机/定位等系统能力、用户愿意装 |
| **从零到能用** | 最快。本阶段 U5.2–U5.5 做完就是 | 中等。多一套审核流程和微信的能力限制 | 最慢。多两个商店、两套证书、一次审核周期 |
| **上线前置条件** | 域名；国内服务器需 ICP 备案 | 小程序账号、类目审核、企业主体才有支付 | iOS 开发者账号（年费）、Android 各商店账号、国内商店多要求软著 |
| **改一版发出去** | 推一次 git，几分钟 | 提交审核，通常 1–7 天 | 商店审核，iOS 通常 1–3 天；Expo 的 OTA 更新可以绕过部分场景 |
| **能复用的 S5 代码** | 全部 | React 组件逻辑、类型、API 层可复用；布局和组件要按 Taro 重写 | React 组件逻辑、类型、API 层可复用；布局用 RN 组件重写 |
| **和 Agent 的流式输出** | 原生支持 SSE | 小程序 `request` 不支持 SSE，要用分块传输或 WebSocket，见 U5.6 | 支持，需注意后台时的连接管理 |

### 两个你会在招聘和别人的项目里反复遇到的名字

**uni-app**：DCloud 出品、Vue 语法的小程序 / App 跨端框架，**国内小程序开发里最常见的选择**，插件市场和现成模板最多。本计划选 Taro 只有一个理由——复用 S5 前面学的 React。如果你的起点是 Vue，把「Next.js + Taro」整体换成「Nuxt + uni-app」是自洽的，后端和部署部分不用动。看到 uni-app 的 JD 或项目不要陌生，它和 Taro 解决的是同一个问题。

**Cloudflare Pages / Workers**：海外个人开发者最省钱的一套托管，免费额度大、R2 对象存储出站流量免费。**但国内访问 Cloudflare 网络不稳定**，Next.js 上去还要走 OpenNext 适配层。用户在海外可以选，用户在国内它不是选项。Web 部署的三条正式路径在 U5.7。

每一层还有什么可选、什么时候该换，见 [`docs/选型地图.md`](../../docs/选型地图.md)。

### 国内的现实

这几条是国内独有的，海外教程不会写：

- **ICP 备案**：服务器在中国大陆就必须备案，工信部规定的审核上限是 20 个工作日，实际多在 1–2 周。服务器在境外（含香港）不用备案，但国内访问速度和稳定性要自己测。以 [工信部备案系统](https://beian.miit.gov.cn) 和你云厂商的备案入口为准。
- **小程序类目**：注册后要选服务类目，某些类目（教育、医疗、金融、内容资讯）需要资质文件。**AI 对话类产品在 2024 年后审核明显收紧**，很多被归到需要备案的「生成式 AI」范畴。注册前先在 [微信公众平台](https://mp.weixin.qq.com) 的类目说明里查你的产品属于哪类、要什么资质。个人主体不能开通微信支付。
- **软著**：华为、小米、OPPO、vivo 等国内 Android 商店上架基本都要求软件著作权登记证书。在 [中国版权保护中心](https://www.ccopyright.com.cn) 申请本身免费，官方审核周期以官网公示为准（历史上是 30 个工作日左右），代办加急另收费。
- **Android 多商店**：国内没有统一的 Google Play，主流是华为、小米、OPPO、vivo、应用宝五家，各自审核。Expo 能一次产出 APK/AAB，但上架要一家一家提交。
- **iOS 开发者账号**：Apple Developer Program 年费官网长期标价 99 美元，以 [developer.apple.com/programs](https://developer.apple.com/programs/) 当前为准。Google Play 开发者账号是一次性 25 美元，以 [Play Console 帮助](https://support.google.com/googleplay/android-developer/answer/6112435) 为准。

**核实日期 2026-09-10。** 这些价格和周期都会变，动手前打开链接再看一眼。

### 背后的逻辑

三端的技术难度差别其实不大，都是 React。**差别在「发出去」这一步的摩擦力**：Web 几乎没有，小程序有一道审核门，App 有商店、证书、软著三道门。摩擦力决定迭代速度，迭代速度决定你能多快拿到真实用户反馈——而反馈是 S3 评估集唯一正确的增长来源。**所以默认答案是先做 Web，除非你的用户明确不在 Web 上。**

## 步骤 2 · 让 agent 帮你出对比表，你核对事实

### 这一步在做什么

上面的表是通用版。你要的是**针对你自己 Agent 场景**的版本。这一步让 agent 出初稿，你来核对。

### 怎么做

**让 agent 做**。在 Claude Code 或 Codex 里，先让它读你 U1.8 写的 `PROJECT.md`，然后给这段指令：

```
读完 PROJECT.md 之后，帮我做三端选型分析。我的 Agent 是给 PROJECT.md 里描述的用户用的。

请输出一张表，行是 Web / 微信小程序 / App 三端，列是：
1. 我的目标用户在这一端的可达性（他们平时在哪、怎么会打开我的产品）
2. 我的核心流程在这一端有没有能力限制（流式输出、长任务、文件上传、通知）
3. 上线需要的账号、资质、审核环节，逐条列出
4. 从现在到第一个真实用户能用，预估工作量（按天）
5. 这一端做完后，第二端能复用多少

要求：
- 每一条涉及费用、周期、政策的事实，附官方来源链接。查不到官方来源就写「待核实」，不要编。
- 最后给一个推荐顺序和理由，理由必须回到我的用户是谁，不要泛泛说「Web 最快」。
- 不要写代码。
```

**你验收**。拿到表之后逐条做三件事：

1. **点开每一个来源链接**。打不开、或者链接内容和它说的对不上，这一条整行打问号。agent 在政策类事实上最容易编，这是它的高发区。
2. **把「待核实」的条目自己查一遍**。查的入口就是步骤 1 里那几个官网。
3. **对照步骤 1 的表看有没有漏**。最常漏的是：小程序 SSE 限制、国内 Android 多商店、ICP 备案。

**你读懂**。在笔记里回答：agent 给的推荐顺序和你直觉一样吗？如果不一样，是它错了还是你原来想错了？

### 可能卡在哪

**agent 给出的费用和周期数字看起来很具体，但没来源**

具体不等于可靠。要求它补来源，补不出来就按「待核实」处理。**这个动作本身就是 S3 教的「不信没来源的数字」在选型环节的应用。**

**agent 推荐做 App，理由是「体验更好」**

「体验更好」不是理由，「我的用户需要推送通知才会回来」才是。让它把理由落到 PROJECT.md 里的具体用户行为上，落不到就是没理由。

**PROJECT.md 里没写清楚用户在哪**

那是 U1.8 欠的债，现在补：去问三个目标用户「你平时在哪看到这类东西、会在哪用」，把答案写回 PROJECT.md。选型不能建立在猜测上。

## 步骤 3 · 做决定，写下来

### 这一步在做什么

填一张一页纸的决定表，放进仓库。**这张表是你后面 S5 六周的路线图，也是面试时「你为什么这么选」的答案。**

### 怎么做

在 `s5-frontend/DECISION.md` 里填这张表（自己填，不要让 agent 填——它不知道你的用户，你知道）：

```markdown
# 三端选型决定（YYYY-MM-DD）

## 我的用户在哪
（一两句话，来自 PROJECT.md 和你问过的三个人）

## 第一端：____
- 为什么是它：
- 上线前要办的事（账号 / 资质 / 备案），每件预计几天：
- 我的核心流程在这一端的限制，以及打算怎么绕：

## 第二端：____（预计在第一端拿到 __ 个真实用户后开始）
- 为什么是它，为什么不是现在：
- 从第一端能复用什么：

## 暂时不做：____
- 触发条件（什么情况下重新考虑）：

## 我核对过的事实（附来源和日期）
- 
```

### 判断标准

| 你的情况 | 先做 |
|---|---|
| 用户会从搜索、群聊链接、公众号文章进来；或有桌面端使用场景 | Web |
| 用户主要在微信里，产品是轻量高频操作，需要微信分享裂变或微信支付 | 小程序（但 Web 也要有一个最简版，用于分享给微信外的人和给面试官看） |
| 产品离不开推送通知、后台运行或相机/定位；用户已经愿意为此装一个 App | App |
| 说不清用户在哪 | 先别选，回去问用户 |

**绝大多数学习者的正确答案是 Web 先做，小程序第二，App 看情况。** 本阶段的单元顺序就是按这个排的：U5.1–U5.5 做 Web，U5.6 做小程序，U5.8 做 App，U5.7 统一上线。如果你的决定不是这个顺序，把 U5.6 和 U5.8 的顺序对调即可，其他不变。

### 背后的逻辑

**选型表的价值不在结论，在「我核对过的事实」那一栏。** 六个月后政策变了、你的用户变了，你能回来看当初的判断建立在哪些事实上，哪些已经不成立。没有这一栏的决定只是一个偏好，有了它才是一个可以被复盘的决策。这也是招聘方问「你为什么选 X」时想听到的东西：不是 X 有多好，而是你当时知道什么、怎么权衡的。

## 完成判据

**产出**：`s5-frontend/DECISION.md`

- [ ] agent 出的对比表里，每一条费用、周期、政策事实的来源链接你都点开核对过，对不上的已标出
- [ ] `DECISION.md` 填完，第一端、第二端、暂不做的都有理由，理由落到具体用户行为上
- [ ] 「上线前要办的事」列出来了，并且**今天就去注册需要排队的那些账号**（小程序账号、iOS 开发者账号、备案）——这些环节的等待时间比你写代码的时间长
- [ ] 如果第一端不是 Web，写清楚 Web 最简版什么时候补

**理解检查**（笔记里回答）

1. 三端里，把一版改动发到用户手上的最短路径各是什么？分别要过几道门？
2. 小程序里做 Agent 流式输出为什么比 Web 麻烦？
3. 国内 Android 上架比海外多了哪两件事？
4. agent 给的选型分析里，你抓到了哪一条没来源或来源对不上的事实？
5. 你的第二端为什么不是现在做？什么信号出现时开始？
