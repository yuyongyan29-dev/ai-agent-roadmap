# U3.7 · 评估进 CI（12 小时）

**这个单元解决什么问题**

现在你的评估要手动跑。人会忘、会偷懒、会在赶时间时跳过。

**这个单元把评估变成一道自动的门禁：改坏了，合并不进去。**

**做完这一步，你的项目就从「个人作品」变成了「工程产物」。**

**学完你能做到**：提一个把 prompt 改差的 PR，CI 自动拦下来并指出是哪几条题退化了。

---

## 步骤 1 · 第一个 GitHub Actions

### 这一步在做什么

先跑通最简单的：PR 时自动跑 pytest。

### 怎么做

建 `.github/workflows/test.yml`：

```yaml
name: 测试

on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 装 uv
        uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true

      - name: 装依赖
        run: uv sync --frozen

      - name: 代码检查
        run: |
          uv run ruff check .
          uv run ruff format --check .

      - name: 单元测试
        run: uv run pytest -v --cov
```

提一个 PR，看它跑起来。

### 可能卡在哪

**`uv sync --frozen` 失败**

`uv.lock` 没提交，或者和 `pyproject.toml` 不一致。本地跑一次 `uv sync` 然后提交 lock 文件。

**测试需要数据库**

用 GitHub Actions 的 service 容器：

```yaml
    services:
      postgres:
        image: pgvector/pgvector:pg17
        env:
          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-retries 10
        ports:
          - 5432:5432
```

**测试要调模型 API**

**不应该。** U0.7 学的 mock 在这里发挥作用——单元测试必须全部 mock 掉外部调用。**真实调用留给评估（下一步）。**

### 背后的逻辑

CI（持续集成）的核心思想是：**每一次改动都自动验证，问题在最小的范围内被发现。**

对比没有 CI 的情况：你改了十个地方，一起提交，出问题了不知道是哪个改动导致的。

**这个思想在评估上同样成立**，只是验证的对象从「代码逻辑」变成了「模型行为」。

## 步骤 2 · 分层跑评估

### 这一步在做什么

**评估很贵很慢，不能每次 PR 都跑全量。**

### 三层策略

| 时机 | 跑什么 | 目标耗时 | 目标成本 |
|---|---|---|---|
| **每次 PR** | 标了 `核心路径` 的子集（约 15 条），只用代码型评分器 | < 5 分钟 | < ¥1 |
| **合并到 main** | 全量（50 条），代码型 + LLM judge | < 20 分钟 | < ¥5 |
| **每晚定时** | 全量 + 成对比较 + 成本延迟报告 | 不限 | < ¥20 |

### 怎么实现

```yaml
name: 评估

on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: "0 18 * * *"        # UTC 18:00 = 北京时间凌晨 2:00

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5

      - run: uv sync --frozen

      - name: 决定跑什么
        id: 范围
        run: |
          if [ "${{ github.event_name }}" = "pull_request" ]; then
            echo "args=--tags 核心路径 --no-judge" >> $GITHUB_OUTPUT
          elif [ "${{ github.event_name }}" = "schedule" ]; then
            echo "args=--all --judge --pairwise --report-cost" >> $GITHUB_OUTPUT
          else
            echo "args=--all --judge" >> $GITHUB_OUTPUT
          fi

      - name: 跑评估
        env:
          DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}
          LANGFUSE_PUBLIC_KEY: ${{ secrets.LANGFUSE_PUBLIC_KEY }}
          LANGFUSE_SECRET_KEY: ${{ secrets.LANGFUSE_SECRET_KEY }}
          LANGFUSE_HOST: ${{ secrets.LANGFUSE_HOST }}
        run: |
          uv run python -m s3_eval.runner ${{ steps.范围.outputs.args }} \
            --baseline s3-eval/baseline.json \
            --output eval-report.md \
            --json eval-result.json

      - name: 上传报告
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: eval-report
          path: |
            eval-report.md
            eval-result.json
```

### 可能卡在哪

**PR 的评估还是太慢**

再缩小子集。**10 条核心路径的题，只用规则评分，两三分钟就该跑完。**

**定时任务的 cron 时区**

GitHub Actions 用 UTC。北京时间减 8 小时。

**自托管的 Langfuse 在 CI 里连不上**

CI 跑在 GitHub 的机器上，连不到你本地的 Langfuse。三个选择：

1. CI 里不上报 trace（加个开关）
2. 把 Langfuse 部署到公网可访问的地方
3. CI 里也起一个临时的 Langfuse（service 容器）

**最简单是第 1 种**，CI 的评估结果存在 artifact 里就够了。

## 步骤 3 · 设门禁

### 这一步在做什么

**分数掉了就不让合并。**

### 基线机制

在仓库里存一个 `s3-eval/baseline.json`：

```json
{
  "更新时间": "2026-11-20T10:00:00Z",
  "commit": "a3f21b9",
  "全量通过率": 0.76,
  "核心路径通过率": 0.92,
  "按题": {
    "EVAL-001": {"通过": true, "得分": 1.0},
    "EVAL-002": {"通过": true, "得分": 1.0},
    "EVAL-031": {"通过": false, "得分": 0.67}
  }
}
```

**门禁规则**：

```python
def 检查门禁(本次: dict, 基线: dict) -> tuple[bool, list[str]]:
    问题 = []

    # 规则 1：核心路径通过率不能低于基线
    if 本次["核心路径通过率"] < 基线["核心路径通过率"] - 0.02:      # 留 2% 容差
        问题.append(
            f"核心路径通过率从 {基线['核心路径通过率']:.0%} "
            f"降到 {本次['核心路径通过率']:.0%}"
        )

    # 规则 2：任何原本通过的题都不能变失败
    for id, 基线项 in 基线["按题"].items():
        if 基线项["通过"] and not 本次["按题"].get(id, {}).get("通过"):
            问题.append(f"{id} 原本通过，现在失败")

    return len(问题) == 0, 问题
```

**规则 2 比规则 1 更严格也更有用。** 总通过率可能因为「修好 A 但改坏 B」而保持不变，规则 2 能抓到这种情况。

### 为什么要留容差

因为 LLM 有随机性。**同样的代码跑两次，分数可能差一两个百分点。**

**2% 是一个起点**，你可以先测一下：同样的 commit 连续跑 5 次，看分数的波动范围，容差设成波动范围的上限。

### 基线什么时候更新

**只在合并到 main 之后自动更新**：

```yaml
      - name: 更新基线
        if: github.ref == 'refs/heads/main' && success()
        run: |
          cp eval-result.json s3-eval/baseline.json
          git config user.name "eval-bot"
          git config user.email "bot@localhost"
          git add s3-eval/baseline.json
          git commit -m "chore: 更新评估基线 [skip ci]"
          git push
```

**`[skip ci]` 很重要**，否则这次提交会触发新的 CI，无限循环。

### 可能卡在哪

**门禁太严，正常改动也被拦**

先观察一段时间再开启强制拦截。**建议流程**：

1. 第一周：只报告，不拦截
2. 观察波动范围，调整容差
3. 第二周开始强制拦截

**修改评估集本身导致基线失效**

改评估集时，基线里那些题的记录也要相应处理。**建议**：改评估集的 PR 单独提，合并后立刻重跑一次更新基线。

**紧急情况需要跳过门禁**

留一个逃生口：PR 标题带 `[skip-eval]` 或者打特定 label 时跳过。**但要在报告里明确标出「本次跳过了评估门禁」。**

## 步骤 4 · 结果贴回 PR

### 这一步在做什么

**让人在 PR 页面上直接看到影响，不用点进 CI 日志。**

### 怎么做

```yaml
      - name: 贴评论
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const body = fs.readFileSync('eval-report.md', 'utf8');
            const {data: comments} = await github.rest.issues.listComments({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.issue.number,
            });
            const 旧的 = comments.find(c =>
              c.user.type === 'Bot' && c.body.includes('<!-- eval-report -->')
            );
            const 内容 = '<!-- eval-report -->\n' + body;
            if (旧的) {
              await github.rest.issues.updateComment({
                owner: context.repo.owner, repo: context.repo.repo,
                comment_id: 旧的.id, body: 内容,
              });
            } else {
              await github.rest.issues.createComment({
                owner: context.repo.owner, repo: context.repo.repo,
                issue_number: context.issue.number, body: 内容,
              });
            }
```

**注意是「更新已有评论」而不是每次新增。** 否则一个 PR 改十次会有十条评论。

### 评论内容

```markdown
<!-- eval-report -->
## 评估结果 ❌

| 指标 | 本次 | 基线 | 变化 |
|---|---|---|---|
| 核心路径 | 12/15 (80%) | 14/15 (93%) | **-13%** ⚠️ |
| 成本 | ¥0.82 | ¥0.79 | +4% |
| 耗时 | 3m12s | 3m05s | +4% |

### ⚠️ 退化的题目（2 条）
- **EVAL-007** [核心路径] 原本通过，现在失败
  失败原因：不包含 · 输出里出现了禁词「家居」
  [查看 trace](链接)
- **EVAL-013** [核心路径] 原本通过，现在失败
  失败原因：轨迹 · 未调用「搜索笔记」工具

### 新通过的题目（0 条）

**门禁未通过。** 请修复退化的题目，或说明为什么这些退化是可接受的。
```

**「查看 trace」的链接**：如果 CI 上报了 trace 到公网可访问的 Langfuse，这个链接能直接跳过去看执行细节。**这是排查效率的关键。**

## 步骤 5 · 做一次验证演练

### 这一步在做什么

**证明你的门禁真的有用。**

### 怎么做

1. 开一个分支
2. **故意把 prompt 改差**。比如删掉「只回答家电类目相关的内容」这条约束
3. 提 PR
4. 等 CI 跑完
5. **确认它红灯，并且评论里准确指出了是哪几条题退化了**
6. 截图

### 如果没拦住

说明：

- 你改的那条约束没有对应的评估题（**评估集有盲区，去补**）
- 或者容差设太宽了
- 或者门禁规则有 bug

**每一种都是有价值的发现，修完再试一次。**

### 这个截图的价值

**这是 S3 最有说服力的作品集素材。**

面试时被问「你怎么保证 Agent 的质量」，你直接打开这张截图：一个改坏 prompt 的 PR，CI 自动拦下来，并且精确指出是哪两条评估题退化了、失败原因是什么。

**这比讲一万句「我很重视质量」都有用。**

## 步骤 6 · 密钥和成本管理

### 这一步在做什么

CI 里要调真实 API，涉及密钥和花钱。

### 密钥

存进 GitHub 仓库的 Settings → Secrets and variables → Actions。

**注意**：

- **fork 来的 PR 拿不到 secrets**（这是安全设计）。个人项目不受影响
- 定期轮换
- **给 CI 用单独的密钥**，和你本地开发的分开，这样出问题能单独作废

### 控制成本

**一、给 CI 的密钥设独立预算**。大多数厂商支持在控制台给某个 key 设上限。

**二、评估运行器里加总成本上限**：

```python
if 累计成本 > 上限:
    logger.error("评估成本超限，中止")
    sys.exit(2)
```

**三、并发控制**。CI 里也要用 Semaphore，别把限流撞了。

**四、监控趋势**。每次评估的成本记进报告，**如果发现成本在涨，说明上下文在膨胀**，该查了。

### 可能卡在哪

**CI 跑一次要几块钱，一天几十次 PR**

用分层策略（步骤 2）。PR 只跑 15 条规则评分，成本应该在几毛钱。

**忘了设上限，某次跑飞了**

**先设上限再开 CI。** 这个顺序不能反。

## 完成判据

**产出**：`.github/workflows/test.yml`、`.github/workflows/eval.yml`、`s3-eval/baseline.json`

**动手部分**

- [ ] pytest + ruff 在 PR 时自动跑
- [ ] **评估分三层**：PR 跑核心路径子集、main 跑全量、每晚跑深度
- [ ] PR 的评估在 5 分钟内完成，成本 1 元以内
- [ ] 基线机制，**合并到 main 后自动更新**（带 `[skip ci]`）
- [ ] 门禁两条规则：整体通过率不降、**原本通过的题不能变失败**
- [ ] 容差经过实测（同 commit 跑 5 次看波动）
- [ ] 结果贴回 PR 评论，**更新而不是新增**
- [ ] 评论里有退化题目的明细和失败原因
- [ ] CI 密钥独立、有预算上限、评估运行器有成本熔断

**关键验证：拦截演练**

提一个故意改差 prompt 的 PR，**确认 CI 红灯并准确指出退化的题目**。

**截图存进 README。** 这是你作品集里最有说服力的一张图。
