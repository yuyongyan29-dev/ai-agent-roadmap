# U3.8 · 成本与延迟看板（12 小时）

**这个单元解决什么问题**

回答两个问题：**「上周钱花在哪」和「哪一步最慢」。**

这两个答案是 S4 优化的直接输入。**没有它们，S4 的优化就是瞎猜。**

**学完你能做到**：一个能回答上述问题的看板；一份指出前三大成本项和前三大耗时项的分析报告。

---

## 步骤 1 · 想清楚要看什么

### 这一步在做什么

**先定问题，再建看板。** 反过来做的话，你会做出一堆漂亮但没人看的图表。

### 你真正需要回答的问题

| 问题 | 需要什么数据 |
|---|---|
| 一次任务平均花多少钱？最贵的呢？ | 按 trace 聚合成本，看均值和 P95 |
| **钱花在哪个环节？** | 按 span 类型/工具名聚合成本 |
| 输入 token 和输出 token 各占多少成本？ | 分别统计 |
| **哪一步最慢？** | 按 span 类型聚合耗时 |
| 用户感知的延迟是多少？ | 首 token 延迟的 P50/P95 |
| 平均要几轮？有没有失控的？ | 按 trace 统计轮次分布 |
| **哪个工具最不靠谱？** | 按工具聚合失败率 |
| 成本在涨还是在降？ | 按天的趋势 |

**这八个问题就是你的看板需求。** 不要做超出这些的图表。

---

## 步骤 2 · 从 trace 聚合数据

### 这一步在做什么

U3.5 已经把数据都记进 trace 了，现在把它们汇总出来。

### 两种做法

**做法一：用 Langfuse 自带的看板**

Langfuse 有内置的 Dashboard，能看总成本、按模型拆分、按 tag 拆分、延迟分布。

**先用它。** 大部分问题它能回答，零开发成本。

**做法二：自己查数据库做定制视图**

Langfuse 自托管时数据在你自己的 Postgres 里，可以直接查。

```sql
-- 按天的成本和任务量
SELECT
    date_trunc('day', t.timestamp) AS 日期,
    count(DISTINCT t.id)           AS 任务数,
    sum(o.calculated_total_cost)   AS 总成本,
    avg(o.calculated_total_cost)   AS 单任务均价,
    percentile_cont(0.95) WITHIN GROUP (ORDER BY o.calculated_total_cost) AS P95
FROM traces t
JOIN observations o ON o.trace_id = t.id
WHERE t.timestamp > now() - interval '30 days'
GROUP BY 1
ORDER BY 1;
```

**具体的表名和字段以你部署的 Langfuse 版本为准**，先用 `\dt` 看有哪些表。

### 关键：按维度拆分

**总数没有信息量，拆分才有。**

必须能按这几个维度切：

| 维度 | 从哪来 | 用来回答 |
|---|---|---|
| 时间 | trace 时间戳 | 趋势 |
| 任务类型 | trace 的 tag | 哪类任务贵 |
| 模型 | generation 的 model 字段 | 哪个模型花的多 |
| **环节**（span 名） | span 的 name | **哪一步贵/慢** |
| 工具 | 工具 span 的 name | 哪个工具慢/失败多 |
| prompt 版本 | trace 的 metadata | 版本间对比 |
| 用户 | trace 的 user_id | 有没有异常用户 |

**「环节」这个维度最重要，也最容易被忽略。**

### 可能卡在哪

**Langfuse 的成本算得不准**

它依赖内置的价格表，可能滞后或者不包含国内模型。

**解法**：在埋点时自己传 `cost_details`（U3.5 已经这么做了），用你 `models.yaml` 里维护的价格。

**数据量大了查询很慢**

给常用的查询字段加索引（U0.8 学的）。或者定期把明细聚合成日表。

## 步骤 3 · 做成本拆解分析

### 这一步在做什么

**本单元最重要的产出。**

### 分析步骤

**第一步：总览**

```
统计区间：2026-11-01 到 2026-11-30
总任务数：312
总成本：¥98.4
单任务均价：¥0.315
P50：¥0.21   P95：¥0.87   P99：¥2.31
```

**注意看 P95 和均值的差距。** 如果 P95 是均值的 3 倍以上，说明有一批异常昂贵的任务，**去找它们**。

**第二步：按环节拆**

```
| 环节 | 成本 | 占比 | 调用次数 | 单次均价 |
|---|---|---|---|---|
| 检索后总结 | ¥71.2 | 72% | 312 | ¥0.228 |
| 意图分类 | ¥12.1 | 12% | 312 | ¥0.039 |
| 工具选择 | ¥9.8 | 10% | 891 | ¥0.011 |
| 最终生成 | ¥5.3 | 5% | 312 | ¥0.017 |
```

**「检索后总结」占 72%——这就是你的优化目标。**

**第三步：拆到 token 级**

对最贵的那个环节，看它的输入输出构成：

```
检索后总结环节：
  输入平均 8420 tokens，成本占该环节的 81%
  输出平均 340 tokens，成本占 19%

  输入的构成（用 U1.5 的分析工具）：
    检索结果   6200 tokens (74%)   ← 问题在这
    对话历史   1400 tokens (17%)
    系统提示    620 tokens (7%)
    工具定义    200 tokens (2%)
```

**结论**：成本大头是检索结果太长。**优化方向明确了**：减少 top_k、压缩片段、或者先摘要再总结。

**第四步：找异常值**

```sql
SELECT t.id, t.name, sum(o.calculated_total_cost) AS 成本
FROM traces t JOIN observations o ON o.trace_id = t.id
GROUP BY t.id, t.name
ORDER BY 成本 DESC
LIMIT 10;
```

打开最贵的那几条 trace，看它们为什么贵。**常见原因**：

- 检索命中了一篇超长文档
- 模型陷入了重复循环（调了同一个工具 8 次）
- 上下文压缩没触发（阈值设得太高）

### 你大概率会发现的三件事

**一、输入 token 是成本大头。** 不是「模型生成得多所以贵」，而是上下文太长。

**二、成本高度集中。** 通常一两个环节占了 70% 以上。

**三、异常值贡献了很大比例。** 前 5% 最贵的任务可能占了 20% 的成本。

**这三个发现直接决定 S4 的优化优先级。**

## 步骤 4 · 做延迟分析

### 这一步在做什么

同样的方法，换成延迟。

### 关键区分：两个延迟指标

| 指标 | 含义 | 影响什么 |
|---|---|---|
| **首 token 延迟（TTFT）** | 用户开始看到内容 | **用户感知的「快慢」** |
| 总耗时 | 任务完成 | 用户要等多久才能拿到结果 |

**两个都要看，但 TTFT 更影响体验**（U1.6 讲过）。

### 按环节拆

```
| 环节 | 平均耗时 | P95 | 占总耗时 |
|---|---|---|---|
| 模型调用（3 轮合计） | 7.3s | 18.2s | 61% |
| 检索 | 2.1s | 4.8s | 18% |
|   ├─ 向量召回 | 0.4s | | |
|   ├─ 关键词召回 | 0.3s | | |
|   └─ rerank | 1.4s | | ← 检索里最慢的 |
| 其他工具 | 1.8s | 6.1s | 15% |
| 本地处理 | 0.7s | 1.2s | 6% |
```

**这张表能告诉你**：优化 rerank 能省多少、减少一轮模型调用能省多少。

### 找慢的原因

对 P95 的那些慢任务，打开 trace 看：

- 是模型本身慢（输出长？模型选得贵？）
- 是轮次多（本该 3 轮用了 8 轮）
- 是某个工具卡（外部 API 慢）
- 是串行了本可以并行的操作

**最后一条经常有优化空间**：两个互不依赖的工具调用，可以并行。

## 步骤 5 · 工具健康度

### 这一步在做什么

看每个工具的表现，找出问题工具。

### 表格

```
| 工具 | 调用次数 | 失败率 | 平均耗时 | P95 耗时 | 平均返回长度 |
|---|---|---|---|---|---|
| 搜索笔记 | 891 | 2.1% | 0.42s | 1.1s | 1240 字符 |
| 读笔记详情 | 412 | 0.5% | 0.31s | 0.8s | 3800 字符 ⚠️ |
| 算互动率 | 203 | 12.3% ⚠️ | 0.08s | 0.2s | 90 字符 |
| 存草稿 | 88 | 0.0% | 0.15s | 0.3s | 45 字符 |
```

**两个值得关注的信号**：

**`算互动率` 失败率 12.3%** —— 太高了。去看失败的 trace，是参数传错（描述不清楚）还是工具本身有 bug。

**`读笔记详情` 平均返回 3800 字符** —— 太长了。它每次调用往上下文里塞 3800 字符，调 3 次就是一万多。**这就是成本大头的来源之一。**

### 可能卡在哪

**失败率高但看不出原因**

按失败类型再细分：参数校验失败 / 外部 API 报错 / 超时 / 业务错误。**不同类型的处理方式完全不同。**

**返回长度怎么统计**

在 U3.5 的埋点里已经记了工具的 output（截断到 2000）。**如果要统计真实长度，单独记一个 `output_length` 字段，不要靠截断后的长度算。**

## 步骤 6 · 设告警线

### 这一步在做什么

从「事后分析」变成「事中发现」。

### 三条起步告警

**不要一开始设太多。告警太多等于没有告警。**

| 告警 | 阈值怎么定 | 为什么 |
|---|---|---|
| 单次任务成本超限 | 现状 P99 的 1.5 倍 | 抓失控的个例 |
| 日成本超限 | 你的预算 / 30 | 防止总量失控 |
| 错误率超限 | 现状的 3 倍 | 抓系统性故障 |

**阈值必须基于你的实际数据定**，不要拍脑袋。你已经有一个月的数据了，用它。

### 实现

先做最简单的：一个定时任务，查数据，超阈值就发飞书机器人消息。

```python
async def 检查告警():
    今日成本 = await 查今日成本()
    if 今日成本 > 日预算:
        await 发飞书消息(f"⚠️ 今日成本 ¥{今日成本:.2f} 超过预算 ¥{日预算}")

    近1小时错误率 = await 查错误率(小时=1)
    if 近1小时错误率 > 错误率阈值:
        await 发飞书消息(f"⚠️ 近 1 小时错误率 {近1小时错误率:.1%}")
```

**S4 会把它做得更完整**（分级、抑制、值班）。现在能到手机就行。

**关键产出：一份指出优化优先级的报告**

```markdown
# 成本与延迟分析 2026-11

## 前三大成本项
1. **检索后总结环节 ¥71.2（72%）**
   根因：检索结果平均 6200 tokens 进入上下文
   优化方向：top_k 从 5 降到 3 + 片段压缩，预计省 40%

2. 意图分类 ¥12.1（12%）
   根因：用了和主流程一样的贵模型
   优化方向：换本地小模型（U1.7 测过通过率 18/20），预计省 90%

3. 工具选择 ¥9.8（10%）
   根因：工具定义 200 tokens × 891 次调用
   优化方向：暂不动，占比不高

## 前三大耗时项
1. **模型调用 7.3s（61%）**
   其中第 2 轮最慢（3.4s），因为上下文最长
2. **rerank 1.4s**
   优化方向：候选从 50 降到 30，或换本地 reranker
3. 串行的工具调用
   优化方向：搜索和读记忆可以并行，省约 0.4s

## 异常值分析
最贵的 5 次任务平均 ¥2.31（是中位数的 11 倍）
共同原因：检索命中了超长文档（>20000 字符），全文进了上下文
优化方向：给检索结果加长度上限

## S4 优化优先级
1. 压缩检索结果（成本降 40%，改动小）
2. 意图分类换本地模型（成本降 12%，需要重测 prompt）
3. 给检索结果加长度上限（消除异常值）
4. 并行化独立的工具调用（延迟降 5%）
```

**这份报告是 S4 的 U4.5 的直接输入。**

## M3 里程碑

**这是 S3 的终点。也是整个 26 周里最有价值的一份产出。**

### 验收清单

- [ ] **30 条以上评估集**，含正负例，有标注规范，一致率超过 90%
- [ ] 至少 6 种代码型评分器，含副作用验证和轨迹断言
- [ ] LLM judge 校准过，**与人工一致率超过 85%**，三种偏见都测过
- [ ] Langfuse 里能看到完整调用树，属性遵循 OTel GenAI 约定
- [ ] **线上失败到评估集的闭环走通过至少 3 次**，有完整记录
- [ ] **CI 门禁生效**，有「拦住劣化 PR」的截图
- [ ] 成本与延迟分析报告，指出前三大问题和优化优先级

### 为什么这一份最值钱

会做 Agent demo 的人很多。**能证明自己的 Agent 好在哪、坏在哪、这次改动是变好还是变坏的人很少。**

面试里被问「你怎么保证质量」，你有三样东西可以直接拿出来：

1. CI 拦截劣化 PR 的截图
2. 一次完整闭环的记录（真实失败 → 评估题 → 修复 → 回归）
3. Judge 校准报告（一致率、混淆矩阵、偏见测试）

**这三样东西展示的是工程能力，不是使用工具的能力。**
