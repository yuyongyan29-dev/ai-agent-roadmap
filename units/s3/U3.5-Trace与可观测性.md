# U3.5 · Trace 与可观测性（16 小时）

**这个单元解决什么问题**

评估告诉你「哪几题失败了」，trace 告诉你「为什么失败」。

没有 trace 时，排查一个失败要靠翻日志、猜、加 print、重跑。有 trace 时，你能沿调用树查到哪一轮、哪个工具、哪段上下文开始偏离预期；定位耗时要通过本单元的盲测自己量。

**学完你能做到**：看到运行的调用树、输入输出、耗时和模型用量；能把质量下降区分为模型决策、prompt、工具处理、外部 API、语料五层问题。

**时间安排**：原有埋点、评估关联与排查练习 12 小时；新增跨层故障归因盲测 4 小时。这是练习安排，不是完成速度承诺。

## 步骤 1 · 理解 trace 的结构

### 这一步在做什么

搞清楚要记录什么、怎么组织。

### 三个核心概念

| 概念 | 是什么 | 在你的 Agent 里对应 |
|---|---|---|
| **Trace** | 一次完整的请求 | 用户的一次任务 |
| **Span** | trace 里的一个操作 | 一轮循环、一次工具调用 |
| **嵌套** | span 之间的父子关系 | 工具调用是那一轮的子 span |

### 你的 Agent 的 trace 应该长这样

```
Trace: 任务「帮我找家电选题」
├── Span: 加载记忆                       12ms
├── Span: 第 1 轮
│   ├── Generation: 模型调用             1.8s  输入 2340 / 输出 87 tokens  ¥0.003
│   └── Span: 工具 搜索笔记               420ms
│       └── Span: 检索                    380ms
│           ├── Span: 向量召回            180ms  返回 50 条
│           ├── Span: 关键词召回          90ms   返回 50 条
│           └── Span: rerank              110ms  返回 5 条
├── Span: 第 2 轮
│   ├── Generation: 模型调用             2.1s   输入 5120 / 输出 340 tokens  ¥0.008
│   └── Span: 工具 读笔记详情             310ms
└── Span: 第 3 轮
    └── Generation: 模型调用             3.4s   输入 8900 / 输出 620 tokens  ¥0.015
```

**看这棵树你能立刻回答**：

- 总共几轮
- 哪一步最慢（检索还是模型）
- 上下文怎么增长的（2340 → 5120 → 8900）
- 钱花在哪一轮

### 每种 span 要记什么

| span 类型 | 必记字段 |
|---|---|
| **Generation**（模型调用） | 模型名、完整输入消息、输出、输入/输出 token、费用、耗时、结束原因、采样参数 |
| **工具调用** | 工具名、参数、返回值（截断）、耗时、是否报错 |
| **检索** | 查询、召回数量、返回的文档 id、各阶段耗时 |
| **Trace 根节点** | 用户 id、会话 id、任务类型、**prompt 版本、代码版本**、最终结果、总成本 |

**「prompt 版本、代码版本」这两个标签特别重要。** 没有它们，你无法回答「这个问题是哪个版本引入的」。

## 步骤 2 · 部署 Langfuse

### 这一步在做什么

起一个自托管的可观测性平台。

### 怎么做

沿用 Langfuse 做本地追踪，但部署文件从[官方 Docker Compose 文档](https://langfuse.com/self-hosting/deployment/docker-compose)取得，记录使用的 commit 和镜像版本。不要复制「一个 Langfuse + 一个 Postgres」再配 `latest`：这不是当前完整部署方案。自托管仍会消耗机器和存储资源。

给 coding agent 的任务：

> 在 `~/ai-agent-roadmap/s3-eval/tracing/langfuse/` 准备官方 Compose 的固定版本，说明所有服务及用途，生成本地密钥；将对外端口绑定到回环地址，与业务服务分开。检查配置后启动，提交一条 smoke trace，给我界面截图、trace ID、Compose commit、镜像版本和 SDK 版本。不要把密钥写入提交。

这是要在你机器上执行的部署任务；本次教程核验机器的 Docker daemon 未运行，**没有验证平台启动、接收数据或界面**。先完成步骤 3 的内存导出验证，具备 Docker 环境后再补平台验收，不能把前者勾成后者。

### 可能卡在哪

**Docker CLI 存在，但服务起不来**

先检查 Docker daemon 是否运行，再看官方 Compose 中各服务的日志和健康检查。CLI 能打印版本不代表 daemon 可连接。

**3000 端口冲突或 key 无效**

更换主机端口后同步实例 URL；确认 `.env` 的 public key、secret key、`LANGFUSE_BASE_URL` 属于同一个项目和实例。短脚本结束前 flush；页面仍无数据时分别验证认证和导出错误。

### 背后的逻辑

官方部署文件和 SDK 可能分别升级，固定两者版本才能重现。平台是否可用，与埋点父子关系是否正确，是两项独立验收。

## 步骤 3 · 埋点

### 这一步在做什么

把 trace 数据发出去。

### 怎么做

埋点仍放在 U1.2 的 `llm_kit`、Agent 循环和工具执行边界。先跑仓库提供的短示例，它使用真实 Langfuse SDK 和内存 exporter，不调用模型，也不连接远端平台。

```bash
cd ~/ai-agent-roadmap
python3 -m venv .venv
.venv/bin/python -m pip install 'langfuse==4.15.2'
.venv/bin/python examples/production-labs/tracing_smoke.py
```

本次实际输出（2026-09-10，Python 3.14.6 / Langfuse 4.15.2）：

```text
spans=4 one_trace=True parent_links=True
export=in-memory model=mock remote_ingestion=not-tested
```

查看 `examples/production-labs/tracing_smoke.py`。重点是 `start_as_current_observation(as_type="span" / "generation")` 的嵌套上下文；上下文退出时结束 span，子调用继承当前父节点。完整实现不到 50 行。

让 coding agent 按这个任务接入你的 Agent：

> 保留现有模型和工具行为。在一次任务根 span 内创建每轮 span，再在调用模型与工具时创建子 observation。用实际发给模型的脱敏 messages、工具声明和实际返回结果埋点；记录真实 usage，提供方没有给的值标记 unknown，不用估算值冒充。成功和异常都结束 span；在短脚本退出时 flush。把 mock 的内存 exporter 换成从环境变量初始化的 Langfuse 客户端，跑一条成功、一条异常，核验父子结构、trace ID 和平台接收。

[官方 Instrumentation 文档](https://langfuse.com/docs/observability/sdk/instrumentation)是上下文 API 的依据；旧教程中的 `lf.trace()` / `lf.generation()` 不应和本例 SDK 混用。

### 盲测前必须补齐的字段

| 层 | 除耗时外还必须看到 |
|---|---|
| 模型决策 | 实际 messages、可用工具定义、选择的工具和参数、模型版本、结束原因 |
| Prompt | 渲染后的约束、prompt 版本和哈希；不是只有模板文件名 |
| 工具处理 | 原始响应引用和哈希、原始长度、传给模型的长度、`truncated`、截断策略版本 |
| 外部 API | 请求 ID、HTTP 状态、业务状态、实际来源、fallback 标记、数据新鲜度 |
| 语料 | 文档 ID、来源、版本、更新时间、召回片段和选中片段 |

完整原文放在受控的本地文件或对象存储，trace 放脱敏预览和可读取的引用。**只记录前 2000 字符却没有长度、截断标记或原文引用，会让工具截断问题无法定位。**

### 用 OpenTelemetry 语义约定命名

**这一条决定你以后能不能换平台。**

OpenTelemetry 定义了一套 GenAI 的标准属性名：

| 属性 | 含义 |
|---|---|
| `gen_ai.provider.name` | 提供方（anthropic / openai / ...） |
| `gen_ai.request.model` | 请求的模型 |
| `gen_ai.request.temperature` | 采样参数 |
| `gen_ai.usage.input_tokens` | 输入 token |
| `gen_ai.usage.output_tokens` | 输出 token |
| `gen_ai.response.finish_reasons` | 结束原因 |

**用标准命名的好处**：迁移时可以保留通用属性含义；平台特有的评分、费用、查询和导出接口仍需适配。

**具体的属性名以 [OpenTelemetry 的 GenAI 语义约定](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/) 当前版本为准**，这个规范还在演进。

### 可能卡在哪

**trace 里看不到数据**

Langfuse 的 SDK 是异步批量上报的。程序退出前要 flush：

```python
lf.flush()
```

**在短脚本里特别容易忘。**

**输入输出太大，把 trace 撑爆了**

限制预览长度，把完整原文放到受控存储，并记录原文长度、交给模型的长度、截断标记和引用。排查时要区分「trace 的显示截断」和「模型真的没收到后半段」。

**敏感信息进了 trace**

**这是个真实风险。** trace 里会有完整的 prompt 和用户输入。

处理：

- 上报前做脱敏（手机号、身份证、密钥模式匹配后打码）
- Langfuse 自托管，数据不出你的机器
- 设置数据保留期，定期清理

**埋点代码把业务代码搞乱了**

用装饰器或上下文管理器封装：

```python
# 埋点收进装饰器，业务函数体里就只剩业务逻辑
@observe(name="tool")
async def run_tool(name, arguments): ...
```

## 步骤 4 · 把评估分数关联到 trace

### 这一步在做什么

**让「哪题失败了」和「为什么失败」在同一个地方能看到。**

### 怎么做

评估任务建立自己的根 observation，记录 `eval_id`、`dataset_version` 和 `eval` 标签，取到该根节点的 trace ID 后，以这个 ID 关联评分。[官方 scores API](https://langfuse.com/docs/evaluation/evaluation-methods/scores-via-sdk) 支持这种显式关联。

下面是接入片段，`trace_id`、`score`、`reason` 取自你的实际评估结果，不是独立程序：

```python
lf.create_score(
    trace_id=trace_id,
    name="overall",
    value=float(score),
    data_type="NUMERIC",
    comment=reason,
)
lf.flush()
```

在界面筛选失败题目，点开对应 trace，确认它的输入、数据集版本和运行 ID 与评估记录相同。上报分数成功但关联错了 trace，仍然算失败；本次内存 smoke 不验证评分上报。

### 可能卡在哪

**评估的 trace 和生产的 trace 混在一起**

用 tag 区分（`eval` vs `prod`），或者用 Langfuse 的不同项目。

## 步骤 5 · 练习一次真实排查

### 这一步在做什么

**验证你的 trace 真的能用。**

### 怎么做

1. **故意制造一个 bug**。选一个不太明显的：
   - 让某个工具在特定条件下返回错误数据
   - 让上下文压缩丢掉关键信息
   - 让 prompt 里少一句关键约束

2. **跑评估，看到失败**

3. **只用 Langfuse 界面**（不看代码、不加 print、不重跑）找出问题在哪

4. **记录你花了多久**

### 如果找不到

说明你的 trace 缺信息。常见的缺失：

| 缺什么 | 后果 |
|---|---|
| 完整的输入消息 | 看不到实际发给模型的 prompt 长什么样 |
| 工具的原始返回 | 不知道工具给了什么 |
| 上下文压缩前后的对比 | 不知道丢了什么 |
| 中间状态 | 不知道记忆里有什么 |

**补上，再试一次。**

### 背后的逻辑

**可观测性的检验标准是「能不能回答你没预料到的问题」。**

日志只能回答你写日志时想到的问题。**结构化的 trace 能回答你当时没想到的问题**——因为它记录的是完整的结构和上下文，而不是几行你选定的文本。

**这就是为什么值得花时间做好埋点。**

## 步骤 6 · 跨层故障归因盲测（新增 4 小时）

### 这一步在做什么

前一步是熟悉工具；这一步检验你面对未知故障时，能否从证据定位，避免一见答错就改 prompt。五类故障是这次练习的覆盖范围，不是所有系统故障的完整分类。

### 怎么做

**先把出题和诊断分开。** 找同伴，或新开一个不继承诊断过程的 coding agent 会话当出题者。出题者独立准备故障；你和诊断会话只看输入、失败结果及 trace。不要让同一个会话先埋故障再「猜」答案。

把下面的任务交给出题会话：

> 在隔离的实验副本里准备五个独立案例，每例只注入一层故障：①模型错误选择工具，②prompt 缺少必要约束，③工具处理截断掉关键内容，④外部 API 返回 HTTP 200 但静默降级为旧数据，⑤检索语料含过期或错误数据。案例顺序随机，使用无含义编号。保留正常对照、可复现输入和失败断言，每例跑通并生成真实 trace；模型选择工具可以用明确标记的响应 fixture 稳定复现，其余链路仍要真实执行。不给诊断者看 fixture 实现。私下保存故障答案、补丁和完整版本映射；公开材料不要出现故障名、故障分支名或泄露答案的 commit 描述。只把五份失败结果及 trace ID/导出文件交给我。封存答案直到我提交五条诊断。若做不到独立出题，明确写“已知故障演练”，不能声称完成盲测。

每例只从 trace 开始：先确认最终错误，再逆向检查传给最终模型的材料；沿模型决策 → prompt → 工具处理 → 外部 API → 语料找**最早出现错误的证据**。这不是机械地按顺序归罪：模型收到完整正确的约束和工具说明，却选错工具，才支持模型决策层；约束原本就没传进去，先查 prompt。

独立提交下面记录后再揭晓答案。不要填预设的“30 秒定位成功”：时间从你打开案例开始，用计时器实际记录。

| 案例 ID | 开始/提交时间与耗时 | 看过的 span/字段路径 | 初步层级 | 证据与排除依据 | 还缺什么信息 | 揭晓后是否一致 |
|---|---|---|---|---|---|---|
| 随机编号 | 自己测量 | `root → turn → tool` 等实际路径 | 五层之一或证据不足 | 写看到的值和原文引用 | 不足就写不足 | 提交后填写 |

最后只修一层，重跑失败用例和正常对照；保存“修复前 trace → 修改 → 修复后 trace”的链路，把五类归因入口带到 U4.8 Runbook。4 小时可以分给字段检查、独立出题、逐例诊断、揭晓复盘；没走完就记录未完成部分，不为了凑时长把猜测写成结论。

### 可能卡在哪

**两层看起来都像原因**：写出一条能区分它们的证据。例如外部 API 正确、工具输出少了末尾条款，支持工具截断；原始响应就用了旧数据，则继续查 API 来源和语料版本。

**工具返回 200，所以排除了工具链**：HTTP 成功不说明业务内容完整或新鲜；查看 `degraded`、来源、更新时间、业务状态和原始数据。

**trace 没有关键材料**：提交“证据不足，需要字段 X”，由出题者补齐再计时重测。诚实的缺证据结论优于碰巧猜中。

### 背后的逻辑

定位是收集证据、提出可区分的假设，再用最小修复验证。盲测检验的是这条推理路径；修复后单次通过仍不能证明模型错误永远消失，随机模型需要在固定评估条件下复测。
