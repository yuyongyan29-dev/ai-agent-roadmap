# U3.5 · Trace 与可观测性（12 小时）

**这个单元解决什么问题**

评估告诉你「哪几题失败了」，trace 告诉你「为什么失败」。

没有 trace 时，排查一个失败要靠翻日志、猜、加 print、重跑。**有 trace 时，30 秒内定位到是哪一轮、哪个工具、哪段上下文出的问题。**

**学完你能做到**：任何一次运行都能看到完整的调用树，每个节点有输入输出、token、耗时、成本。

---

## 步骤 1 · 理解 trace 的结构

### 这一步在做什么

搞清楚要记录什么、怎么组织。

### 三个核心概念

| 概念 | 是什么 | 在你的 Agent 里对应 |
|---|---|---|
| **Trace** | 一次完整的请求 | 用户的一次任务 |
| **Span** | trace 里的一个操作 | 一轮循环、一次工具调用 |
| **嵌套** | span 之间的父子关系 | 工具调用是那一轮的子 span |

### 你的 Agent 的 trace 应该长这样

```
Trace: 任务「帮我找家电选题」
├── Span: 加载记忆                       12ms
├── Span: 第 1 轮
│   ├── Generation: 模型调用             1.8s  输入 2340 / 输出 87 tokens  ¥0.003
│   └── Span: 工具 搜索笔记               420ms
│       └── Span: 检索                    380ms
│           ├── Span: 向量召回            180ms  返回 50 条
│           ├── Span: 关键词召回          90ms   返回 50 条
│           └── Span: rerank              110ms  返回 5 条
├── Span: 第 2 轮
│   ├── Generation: 模型调用             2.1s   输入 5120 / 输出 340 tokens  ¥0.008
│   └── Span: 工具 读笔记详情             310ms
└── Span: 第 3 轮
    └── Generation: 模型调用             3.4s   输入 8900 / 输出 620 tokens  ¥0.015
```

**看这棵树你能立刻回答**：

- 总共几轮
- 哪一步最慢（检索还是模型）
- 上下文怎么增长的（2340 → 5120 → 8900）
- 钱花在哪一轮

### 每种 span 要记什么

| span 类型 | 必记字段 |
|---|---|
| **Generation**（模型调用） | 模型名、完整输入消息、输出、输入/输出 token、费用、耗时、结束原因、采样参数 |
| **工具调用** | 工具名、参数、返回值（截断）、耗时、是否报错 |
| **检索** | 查询、召回数量、返回的文档 id、各阶段耗时 |
| **Trace 根节点** | 用户 id、会话 id、任务类型、**prompt 版本、代码版本**、最终结果、总成本 |

**「prompt 版本、代码版本」这两个标签特别重要。** 没有它们，你无法回答「这个问题是哪个版本引入的」。

## 步骤 2 · 部署 Langfuse

### 这一步在做什么

起一个自托管的可观测性平台。

### 为什么选 Langfuse

开源、可自部署、trace 和评估和成本分析在一个地方。对个人学习者是最优解——数据在自己手里，不限量，不花钱。

（生产团队常见的另外几个是 LangSmith、Braintrust、Arize Phoenix。原理相通。）

### 怎么做

加进你 U0.9 建的 `compose.yaml`：

```yaml
services:
  # Langfuse 单独用一个 Postgres：它的写入量远大于业务库，混在一起既拖慢查询也不好单独备份
  langfuse-db:
    image: postgres:17
    environment:
      POSTGRES_USER: langfuse
      POSTGRES_PASSWORD: langfuse
      POSTGRES_DB: langfuse
    volumes:
      # 挂命名卷，容器重建时历史 trace 不丢
      - langfuse_pgdata:/var/lib/postgresql/data
    healthcheck:
      # 有 healthcheck，下面的 langfuse 才能等到数据库真正可连；否则它会因连不上库反复重启
      test: ["CMD-SHELL", "pg_isready -U langfuse"]
      interval: 3s
      retries: 20

  langfuse:
    image: langfuse/langfuse:latest
    depends_on:
      langfuse-db:
        # 等的是 healthy 而不是「容器已启动」，这是启动失败最常见的坑
        condition: service_healthy
    environment:
      # 主机名用 compose 里的服务名 langfuse-db，走容器网络而不是 localhost
      DATABASE_URL: postgresql://langfuse:langfuse@langfuse-db:5432/langfuse
      NEXTAUTH_URL: http://localhost:3000
      # 下面三个是密钥，必须自己生成；ENCRYPTION_KEY 用来加密库里存的 API key，改了会解不开旧数据
      NEXTAUTH_SECRET: 换成一个随机字符串
      SALT: 换成另一个随机字符串
      ENCRYPTION_KEY: 换成 64 位十六进制
    ports:
      - "3000:3000"

volumes:
  langfuse_pgdata:
```

**具体的环境变量以 [Langfuse 官方自托管文档](https://langfuse.com/docs/deployment/self-host) 为准**，版本更新会有变化。

```bash
docker compose up -d langfuse
```

打开 http://localhost:3000，注册一个账号，建一个项目，拿到 public key 和 secret key，存进 `.env`。

### 可能卡在哪

**容器起不来**

`docker compose logs langfuse` 看日志。常见原因：数据库没就绪（healthcheck 没配好）、必填的环境变量缺失。

**端口 3000 被占用**

改映射：`"3001:3000"`。

**为什么要单独一个数据库**

Langfuse 会写大量数据，和你的业务库混在一起不好管理和备份。**生产环境更要分开。**

## 步骤 3 · 埋点

### 这一步在做什么

把 trace 数据发出去。

### 在哪里埋

**回到 S1**：你在 U1.2 封装了 `llm_kit`，U1.6 给它加了成本统计。**埋点就加在同一个地方。**

```python
from langfuse import Langfuse

lf = Langfuse()          # 从环境变量读 key


class LLM:
    async def chat(self, messages, model=None, trace=None, **kw):
        """在已有的 LLM 封装里就地埋点：调用方一行不改，所有模型调用自动进 trace。

        trace 是父节点（通常是某一轮的 span）。不传就挂到全局客户端下，
        这样在脚本里单独调一次模型也能留下记录。
        """
        span = (trace or lf).generation(
            name="llm-call",
            model=model or self.default_model,
            input=messages,          # 存完整消息列表，排查时才看得到真正发给模型的 prompt
            model_parameters={"temperature": kw.get("temperature")},
        )
        try:
            r = await self._do_call(messages, model, **kw)
            span.end(
                output=r.text,
                # token 和费用交给 Langfuse 聚合，才能按 trace、用户、时间维度算成本
                usage_details={
                    "input": r.usage.input_tokens,
                    "output": r.usage.output_tokens,
                },
                cost_details={"total": r.usage.cost},
                # 结束原因用来区分「模型自己说完了」和「被 max_tokens 截断」，输出异常时第一个看它
                metadata={"finish_reason": r.finish_reason},
            )
            return r
        except Exception as e:
            # 失败的调用也要落 trace 再抛出去，否则最需要排查的那次反而没有记录
            span.end(level="ERROR", status_message=str(e))
            raise
```

**Agent 循环里**：

```python
async def run(self, user_input: str, user_id: str) -> RunResult:
    # 根节点带上 prompt 版本和代码版本，出问题时才能回答「这是哪个版本引入的」
    trace = lf.trace(
        name="agent-run",
        user_id=user_id,
        input=user_input,
        tags=[self.task_type],
        metadata={
            "prompt_version": self.prompt_version,
            "code_version": os.getenv("GIT_SHA", "dev"),
            "model": self.default_model,
        },
    )

    for turn in range(1, max_turns + 1):
        # 每轮开一个 span，模型调用和工具调用都挂在它下面，trace 树的层级就和循环结构一一对应
        turn_span = trace.span(name=f"turn-{turn}")
        reply = await self.llm.chat(history, trace=turn_span)

        for tc in tool_calls:
            # 参数进 input、返回进 output，才能判断「是模型传错了参数」还是「工具返回了错数据」
            tool_span = turn_span.span(name=f"tool:{tc.name}", input=tc.arguments)
            result = await self._run_one_tool(tc)
            tool_span.end(output=result[:2000])      # 截断，避免存太大

        turn_span.end()

    # 总费用和实际轮次回填到根节点，列表页不用点进去就能筛出「贵的」和「跑太多轮的」
    trace.update(output=final_answer, metadata={"total_cost": total_cost, "turns": turn})
    return ...
```

### 用 OpenTelemetry 语义约定命名

**这一条决定你以后能不能换平台。**

OpenTelemetry 定义了一套 GenAI 的标准属性名：

| 属性 | 含义 |
|---|---|
| `gen_ai.system` | 提供方（anthropic / openai / ...） |
| `gen_ai.request.model` | 请求的模型 |
| `gen_ai.request.temperature` | 采样参数 |
| `gen_ai.usage.input_tokens` | 输入 token |
| `gen_ai.usage.output_tokens` | 输出 token |
| `gen_ai.response.finish_reasons` | 结束原因 |

**用标准命名的好处**：以后想从 Langfuse 换到别的平台，或者接进公司统一的 APM 系统，埋点不用重写。

**具体的属性名以 [OpenTelemetry 的 GenAI 语义约定](https://opentelemetry.io/docs/specs/semconv/gen-ai/) 当前版本为准**，这个规范还在演进。

### 可能卡在哪

**trace 里看不到数据**

Langfuse 的 SDK 是异步批量上报的。程序退出前要 flush：

```python
lf.flush()
```

**在短脚本里特别容易忘。**

**输入输出太大，把 trace 撑爆了**

截断。工具返回值只存前 2000 字符，完整内容存到别处（对象存储或文件），trace 里放一个引用。

**敏感信息进了 trace**

**这是个真实风险。** trace 里会有完整的 prompt 和用户输入。

处理：

- 上报前做脱敏（手机号、身份证、密钥模式匹配后打码）
- Langfuse 自托管，数据不出你的机器
- 设置数据保留期，定期清理

**埋点代码把业务代码搞乱了**

用装饰器或上下文管理器封装：

```python
# 埋点收进装饰器，业务函数体里就只剩业务逻辑
@observe("tool")
async def run_tool(name, arguments): ...
```

## 步骤 4 · 把评估分数关联到 trace

### 这一步在做什么

**让「哪题失败了」和「为什么失败」在同一个地方能看到。**

### 怎么做

评估运行时，给每题的 trace 打上分数：

```python
async def run_one_case(case, agent_factory):
    # eval 标签把评估流量和生产流量分开；数据集版本让「换了题库之后分数变了」能对得上
    trace = lf.trace(
        name="eval-run",
        tags=["eval", *case["tags"]],
        metadata={"eval_id": case["id"], "dataset_version": dataset_version},
    )

    # 把 trace 传进 Agent，这一题的模型调用和工具调用都会挂到同一棵树上
    r = await agent.run(case["input"], trace=trace)

    # 评分后附上：每条标准单独打一个分，判定理由放进 comment，
    # 之后在界面上筛出不及格的那条，点开就是对应的执行树
    for criterion, passed, reason in details:
        trace.score(name=criterion, value=1.0 if passed else 0.0, comment=reason)

    trace.score(name="overall", value=score)
    return ...
```

**这样在 Langfuse 里你可以**：

- 筛出所有失败的评估运行
- 点进去直接看完整的执行树
- 对比通过和失败的运行有什么不同

**这个闭环让排查效率提升一个数量级。**

### 可能卡在哪

**评估的 trace 和生产的 trace 混在一起**

用 tag 区分（`eval` vs `prod`），或者用 Langfuse 的不同项目。

## 步骤 5 · 练习一次真实排查

### 这一步在做什么

**验证你的 trace 真的能用。**

### 怎么做

1. **故意制造一个 bug**。选一个不太明显的：
   - 让某个工具在特定条件下返回错误数据
   - 让上下文压缩丢掉关键信息
   - 让 prompt 里少一句关键约束

2. **跑评估，看到失败**

3. **只用 Langfuse 界面**（不看代码、不加 print、不重跑）找出问题在哪

4. **记录你花了多久**

### 如果找不到

说明你的 trace 缺信息。常见的缺失：

| 缺什么 | 后果 |
|---|---|
| 完整的输入消息 | 看不到实际发给模型的 prompt 长什么样 |
| 工具的原始返回 | 不知道工具给了什么 |
| 上下文压缩前后的对比 | 不知道丢了什么 |
| 中间状态 | 不知道记忆里有什么 |

**补上，再试一次。**

### 背后的逻辑

**可观测性的检验标准是「能不能回答你没预料到的问题」。**

日志只能回答你写日志时想到的问题。**结构化的 trace 能回答你当时没想到的问题**——因为它记录的是完整的结构和上下文，而不是几行你选定的文本。

**这就是为什么值得花时间做好埋点。**
