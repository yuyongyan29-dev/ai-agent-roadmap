# U3.4 · 模型型评分器（LLM-as-judge）（10 小时）

**这个单元解决什么问题**

有些东西规则判不了：答案是否引用了正确的数据、推理是否有逻辑漏洞、语气是否符合要求。

这时用另一个模型来当裁判。**但它不可靠，这个单元的一半篇幅是教你怎么发现和缓解它的不可靠。**

**必读文章的定位**：模型型评分器「灵活、能处理细微差别」，配合评分标准、自然语言断言、成对比较使用。**它是三类评分器之一，不是替代品。**

**学完你能做到**：一个和你人工判断一致率超过 85% 的 judge；知道它的三种偏见并测过。

---

## 步骤 1 · 写评分 prompt

### 这一步在做什么

judge 的质量 80% 取决于评分 prompt。

### 三个必备要素

**一、明确的评分维度**

不要问「这个答案好不好」，要拆成具体的维度：

```
维度：
1. 数据准确性——引用的数字是否来自工具返回，有没有编造
2. 完整性——是否回答了用户问的全部内容
3. 可追溯性——是否标明了数据来源和时间范围
4. 约束遵守——是否违反了用户设定的限制
```

**二、每档分数的具体描述**

不要只写「1 到 5 分」，要写清楚 3 分和 4 分的区别：

```
数据准确性：
5 = 所有数字都能在工具返回里找到对应，无任何编造
4 = 所有数字有依据，但有个别表述不够精确（如「约 1000」实际是 1023）
3 = 主要数字有依据，但有 1 处无法追溯的细节
2 = 有多处无法追溯的数据
1 = 存在明显编造的数据
```

**这种描述让 judge 有明确的锚点**，而不是凭感觉给分。

**三、要求先给理由再给分**

```
对每个维度，先写出你的判断依据（引用具体的原文），再给分。
```

**顺序很重要。** 回想 U1.1 的自回归原理：先写理由，分数才是基于理由推出来的；先给分，理由就变成了事后合理化。

### 用结构化输出

```python
class 维度评分(BaseModel):
    维度: str
    理由: str = Field(description="判断依据，必须引用被评内容里的具体原文")
    得分: int = Field(ge=1, le=5)


class 评分结果(BaseModel):
    各维度: list[维度评分]
    总体通过: bool
    关键问题: str | None = Field(default=None, description="如果不通过，最主要的问题是什么")
```

复用 U1.3 的结构化输出能力。

### 可能卡在哪

**judge 总是给 4 分**

分数分布集中是常见问题。三个改进：

1. 在 prompt 里明确要求「不要回避极端分数，符合标准就给 5，不符合就给 1」
2. 给几个不同分数的例子（few-shot）
3. **改用成对比较**（见步骤 2）

**judge 看不懂任务**

它需要足够的上下文：用户的原始问题、参考答案、工具返回的原始数据。**只给它最终输出，它没法判断数据准不准。**

## 步骤 2 · 绝对打分 vs 成对比较

### 这一步在做什么

理解两种模式的差异，知道各自适合什么。

### 绝对打分

给一个输出，打 1 到 5 分。

| 优点 | 缺点 |
|---|---|
| 简单 | **分数漂移严重**：同一个输出，今天 4 分明天 3 分 |
| 可以设阈值当门禁 | 分布集中，区分度低 |
| 单次调用 | 不同批次之间不可比 |

### 成对比较

给 A 和 B 两个输出，判断哪个更好。

| 优点 | 缺点 |
|---|---|
| **明显更稳定** | 需要两个版本才能比 |
| 区分度高 | 不能给绝对分数 |
| | 调用次数翻倍 |

**为什么成对比较更稳定？** 因为「哪个更好」是相对判断，不需要模型在心里维持一个绝对的标准。人也是这样——让你给一篇文章打分很难，让你说 A 和 B 哪篇好就容易得多。

### 各用在哪

| 场景 | 用哪个 |
|---|---|
| CI 门禁（需要绝对阈值） | 绝对打分 |
| **对比两个 prompt 版本** | **成对比较** |
| 对比两个模型 | 成对比较 |
| 长期追踪质量趋势 | 绝对打分（但要注意漂移） |

**实践建议**：**主要用成对比较做版本对比，绝对打分只用于粗筛「明显不合格」。**

### 可能卡在哪

**成对比较怎么算总分**

跑 N 条题，统计 A 赢多少、B 赢多少、平局多少。

```
A 版 vs B 版（50 条题）：
A 更好：31    B 更好：14    平局：5
```

**这个结论比「A 版 4.2 分，B 版 4.0 分」有说服力得多。**

## 步骤 3 · 测 judge 的三种偏见

### 这一步在做什么

**这一步大多数人跳过，然后被坑。**

### 偏见一：位置偏见

成对比较时，模型可能倾向于选第一个（或第二个）。

**怎么测**：

```python
async def 测位置偏见(题目对: list[tuple[str, str]]) -> dict:
    正序赢A = 0
    反序赢A = 0
    for A, B in 题目对:
        r1 = await 成对比较(A, B)       # A 在前
        r2 = await 成对比较(B, A)       # B 在前
        if r1 == "第一个更好": 正序赢A += 1
        if r2 == "第二个更好": 反序赢A += 1
    return {
        "正序时 A 胜率": 正序赢A / len(题目对),
        "反序时 A 胜率": 反序赢A / len(题目对),
        "不一致率": abs(正序赢A - 反序赢A) / len(题目对),
    }
```

**如果两个胜率差很多，说明有位置偏见。**

**缓解**：每对都比两次（交换位置），取一致的结论；不一致的算平局。**代价是调用翻倍。**

### 偏见二：长度偏见

模型可能觉得长答案更好。

**怎么测**：把你的评估结果按输出长度分组，看得分和长度的相关性。

```python
短的平均分 = 平均([r.得分 for r in 结果 if len(r.输出) < 200])
长的平均分 = 平均([r.得分 for r in 结果 if len(r.输出) > 800])
```

**如果长的明显高，可能有长度偏见。**

**缓解**：在评分 prompt 里明确「简洁不是缺点，冗余是缺点」；或者在维度里加一条「简洁性」。

### 偏见三：自我偏好

用 A 模型评 A 模型自己生成的内容，可能给分偏高。

**怎么测**：用两个不同的模型分别当 judge，评同一批输出，看结论一致吗。

**缓解**：**judge 用和被评者不同的模型。** 这是最简单有效的做法。

### 可能卡在哪

**测偏见的成本很高**

每种偏见测 20 条就够看出趋势。总共 60 次调用，不贵。

**发现有偏见但没法完全消除**

正常。**目标不是消除，是知道它存在并在解读分数时考虑进去。**

比如你知道 judge 有长度偏见，那当一个版本分数高但输出明显更长时，你就该多留个心眼。

### 背后的逻辑

**judge 也是一个模型，它有模型的所有问题**：不确定、有偏见、会被 prompt 影响、会幻觉。

把它当成「一个不太可靠但很便宜的标注员」，而不是「客观的裁判」。

**这个心态决定了你会不会去校准它。**

## 步骤 4 · 用人工校准

### 这一步在做什么

**必读文章把人工评分定位为「校准的黄金标准」。** 这一步就是做校准。

### 怎么做

**第一步：你自己人工判 30 条**

从评估集里抽 30 条（要覆盖不同难度和标签），你自己按标注规范判定通过或不通过。**记录下来，不要看 judge 的结果。**

**第二步：跑 judge**

同样 30 条，让 judge 判。

**第三步：算一致率**

```python
一致 = sum(1 for i in range(30) if 人工[i] == judge[i])
print(f"一致率 {一致}/30 = {一致/30:.1%}")
```

**第四步：分析不一致的**

对每一条不一致的，判断是谁错了：

| 情况 | 处理 |
|---|---|
| judge 错了 | 改评分 prompt |
| **我错了** | 改标注规范（说明我的标准本身不清楚） |
| 题目本身有歧义 | 改题或删题 |

**第二种情况比你想的更常见。** judge 有时会指出你没注意到的问题。

**第五步：改完重跑，直到一致率超过 85%**

### 混淆矩阵更有信息量

不只看一致率，看四个格子：

| | judge 判通过 | judge 判不通过 |
|---|---|---|
| **人工判通过** | 真通过 | **假阴性**（judge 太严） |
| **人工判不通过** | **假阳性**（judge 太松） | 真不通过 |

**假阳性更危险**：judge 说通过但实际有问题，你会漏掉真实缺陷。

**如果假阳性多，就把评分 prompt 改严。**

### 可能卡在哪

**一致率一直上不去**

按顺序检查：

1. 评分维度是不是太主观（「是否有洞察力」这种没法客观判）
2. judge 有没有拿到足够的信息（工具返回的原始数据给它了吗）
3. 分档描述是不是不够具体
4. 是不是题目本身有歧义

**人工判 30 条太累**

确实累，但这是必要投入。**分两天做，每天 15 条。** 而且这个过程本身会让你对系统的理解深一层。

### 背后的逻辑

校准的本质是**建立 judge 和人的信任关系**。

没有校准的 judge，它的分数是一个你不知道意味着什么的数字。校准过的 judge，你知道「它说通过，有 85% 的概率我也会说通过」。

**这个 85% 就是你解读它的分数时的置信度。**

## 步骤 5 · 工程化

### 这一步在做什么

把 judge 变成可靠的基础设施。

### 必须处理的

**一、judge 自己会失败**

返回格式错误、调用超时、被限流。**用 U1.3 的自动修复和 U1.2 的重试。**

**二、judge 有成本**

50 条题 × 每条 1 次 judge 调用，加上成对比较要 2 次，成本不低。

**优化**：

- 先跑代码型评分器，**只对通过了代码型的才跑 judge**（省掉明显失败的）
- 用批处理（U1.6 学的），省一半
- judge 用便宜的模型（先测一致率，够用就行）

**三、judge 的版本要记录**

judge 的 prompt 改了，分数就不可比了。**judge prompt 也要进版本管理**（U1.4 学的），报告里记录用的哪版。

**四、缓存**

同样的输入 + 同样的 judge 版本 = 同样的结果，可以缓存。**评估反复跑时能省很多。**

### 可能卡在哪

**judge 用哪个模型**

先用中等模型测一致率。**如果中等模型就能达到 85%，没必要用最贵的。**

不同 judge 模型的一致率对比也做一下：

| judge 模型 | 与人工一致率 | 每次成本 |
|---|---|---|
| 强模型 | | |
| 中等模型 | | |
| 小模型 | | |

**这张表能帮你选出性价比最高的。**
