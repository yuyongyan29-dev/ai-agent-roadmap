# U3.1 · 评估的思维框架（4 小时）

**这个单元解决什么问题**

在写任何评估代码之前，先想清楚三件事：**什么该测、用什么方式测、测出来的数字意味着什么。**

想不清楚就动手，你会做出一堆看着很忙但没有信号的评估——分数天天变，但你不知道是代码变了还是运气变了。

**必读，在本单元之前读完**：Anthropic《[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)》（2026-01-09）。**整个 S3 的方法论建立在它之上。**

---

## 步骤 1 · 理解为什么传统测试不够

### 这一步在做什么

搞清楚 pytest 在哪里失效，在哪里依然有效。

### 传统测试的前提假设

```python
assert 加(1, 2) == 3
```

这行代码成立，依赖一个假设：**相同输入永远产生相同输出。**

LLM 打破了这个假设：

- 同样的 prompt 跑两次，输出措辞不同
- 即使 `temperature=0` 也不保证完全一致（U1.1 讲过）
- 模型版本更新，行为会变
- 同样意思的回答可以有无数种表达

### 但这不代表不能测

**关键认知：失效的是「逐字比对」，不是「验证」本身。**

你依然可以断言：

| 能断言的 | 例子 |
|---|---|
| 结构 | 返回的是合法 JSON，包含这 5 个字段 |
| 包含关系 | 答案里必须提到「三个月」这个时间 |
| 不包含 | 答案里不能出现其他用户的姓名 |
| 数值范围 | 算出的均值在 100 到 200 之间 |
| **副作用** | **数据库里确实新增了那条记录** |
| 行为约束 | 调用删除工具前一定请求了确认 |
| 相对比较 | 新版本的得分不低于旧版本 |

**「副作用」那一条最可靠。** 如果任务是「创建一条记录」，你不用管它怎么描述这件事，直接去数据库查记录在不在。

## 步骤 2 · 划清边界：什么用测试，什么用评估

### 这一步在做什么

**这是本单元最有价值的一步。** 很多人把整个 Agent 当黑盒去评估，其实一大半代码可以用普通测试覆盖。

### 怎么做

把你的项目拆成模块，逐个归类：

| 模块 | 是否确定性 | 用什么验证 |
|---|---|---|
| 工具函数内部逻辑（解析、计算、格式化） | **确定** | pytest |
| 数据库读写 | **确定** | pytest |
| 权限判断 | **确定** | pytest |
| 检索的召回（给定查询，返回哪些片段） | **确定** | pytest 或检索评测 |
| 上下文组装（给定输入，拼出什么 prompt） | **确定** | pytest |
| 重试逻辑 | **确定** | pytest + mock |
| **模型选哪个工具** | 不确定 | **评估** |
| **模型填的参数对不对** | 不确定 | **评估** |
| **最终答案的质量** | 不确定 | **评估** |
| **多步任务的完成度** | 不确定 | **评估** |

### 为什么这个划分重要

三个理由：

**一、确定性部分必须 100% 可靠。** 如果你的日期解析函数有 bug，模型再聪明也救不了。**这部分用 pytest，要求全绿。**

**二、评估很贵。** 每跑一次评估要调很多次模型。把能用 pytest 覆盖的挪出去，评估集就能更聚焦、跑得更快更便宜。

**三、定位问题更快。** 评估挂了，如果确定性部分有测试保护，你就知道问题一定在模型层，不用大海捞针。

### 可能卡在哪

**有些模块介于两者之间**

比如「上下文压缩」——压缩逻辑是确定的（给定输入，压出什么是固定的），但「压缩后模型还能不能答对」是不确定的。

**拆开测**：压缩逻辑用 pytest（验证保留了哪些消息），压缩后的效果用评估。

**检索算不算确定性**

给定查询和索引，返回哪些片段是确定的（假设 embedding 模型固定）。**所以可以用 pytest 风格的断言**：「查询 X 应该召回文档 doc_012」。

**这就是你 U2.5 建的那 20 组评测集**——它本质上是一种确定性测试。

## 步骤 3 · 理解评估的三个层次

### 这一步在做什么

知道你在测哪一层，以及每层能发现什么问题。

### 三层

**组件级：单个环节对不对**

- 意图分类是否正确
- 检索是否召回了正确文档
- 抽取的字段是否准确
- 工具参数是否合法

**特点**：快、便宜、定位准确。**能告诉你「哪里坏了」。**

**轨迹级：过程是否合理**

- 是否调用了不该调的工具
- 步数是否失控（本该 3 步用了 12 步）
- 是否在没确认的情况下执行了高危操作
- 是否陷入了重复循环

**特点**：能发现「结果对了但过程有问题」的情况。**这类问题在生产环境会变成事故。**

**端到端：最终结果对不对**

- 用户的需求被满足了吗
- 答案准确吗
- 格式符合要求吗

**特点**：最贴近用户体验，但**出问题时不知道是哪一步的锅**。

### 三层的关系

**必读文章里的建议是：优先评结果，而不是评具体的工具调用序列。**

原因是：如果你断言「必须先调 A 再调 B」，模型找到了一条更好的路径（直接调 C 就完成了）反而会被判失败。**这会惩罚模型的创造性，也会让你的评估集在换模型后大面积失效。**

**但轨迹级评估在两种情况下必须有**：

1. **安全约束**：「执行删除前必须请求确认」——这不是效率问题，是硬约束
2. **成本约束**：「步数不能超过 15」——防止成本失控

**所以正确的做法是**：端到端评结果，轨迹级只评硬约束。

### 背后的逻辑

三层对应软件测试里的单元、集成、端到端，**金字塔形状也一样**：组件级最多、端到端最少。

原因也一样：**越底层越快越便宜越准确，越上层越贴近真实但越难定位。**

**实践建议**：新发现一个问题时，先在端到端层加一条用例（证明问题存在），修复后再在组件级加一条（防止回归）。

## 步骤 4 · 理解评估的局限

### 这一步在做什么

在开始建评估之前，先知道它不能做什么。**这能防止你过度信任分数。**

### 局限一：评估集会饱和

必读文章里的说法：**当分数接近 100% 时，评估集就不再提供信号了。**

因为它测不出更细的差别——所有版本都满分，你无法比较。

**应对**：定期加入新的、更难的用例。**分数从 95% 掉到 85% 不是坏事**，说明你加进了有区分度的题目。

### 局限二：分数高不代表体验好

评估集只覆盖你想到的场景。真实用户会用你没想到的方式使用它。

**应对**：U3.6 会做「线上失败回流」，让真实场景持续进入评估集。

### 局限三：评分器本身会错

规则评分器可能判断标准太死；LLM judge 有偏见且不稳定。

**应对**：必读文章的原话——**「在有人真正深入细节之前，我们不会把评估分数当真。」** U3.4 会教你怎么校准 judge，U3.6 会要求你定期读原始记录。

### 局限四：评估有成本

50 条用例，每条跑一次完整任务，可能要几十块钱和十几分钟。

**应对**：分层跑。U3.7 会教你 PR 跑快速子集、合并跑全量、每晚跑深度评估。

### 背后的逻辑

**评估不是「证明系统是对的」，而是「在系统变坏时告诉你」。**

这个定位很重要。你不需要一个能证明完美的评估体系，你需要一个能**捕捉退化**的安全网。

从这个角度看，**评估集的价值不在于覆盖率有多高，而在于它能不能可靠地捕捉到你在意的那些失败模式。**

## 完成判据

**产出**：`s3-eval/SCOPE.md`

内容是一张表，覆盖你项目的**全部模块**：

| 模块 | 确定性？ | 验证方式 | 评估层次 | 理由 |
|---|---|---|---|---|
| 日期解析工具 | 是 | pytest | - | 输入输出固定 |
| 检索召回 | 是 | 检索评测集 | 组件级 | 索引固定时结果确定 |
| 意图分类 | 否 | 评估 | 组件级 | 模型判断 |
| 工具选择 | 否 | 评估 | 轨迹级 | 只评硬约束，不评顺序 |
| 最终答案 | 否 | 评估 | 端到端 | 质量判断 |
| ... | | | | |

**要求**：

- [ ] 覆盖你项目的全部模块，不能有遗漏
- [ ] 每一行都有理由，不能有「不适用」这种敷衍答案
- [ ] **确定性的部分列出来还缺哪些 pytest 测试**（这是你接下来要补的）

**理解检查**（笔记里回答）

1. LLM 打破了传统测试的什么假设？失效的是「验证」本身吗？
2. 哪七类断言依然可用？其中最可靠的是哪一类，为什么？
3. 为什么要把确定性部分从评估里挪出去用 pytest？（三个理由）
4. 为什么「评结果」优先于「评工具调用序列」？什么情况下必须评轨迹？
5. 评估集饱和是什么意思？分数从 95% 掉到 85% 一定是坏事吗？
