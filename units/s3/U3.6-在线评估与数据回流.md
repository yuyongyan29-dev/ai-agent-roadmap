# U3.6 · 在线评估与数据回流（10 小时）

**这个单元解决什么问题**

离线评估集是你想到的场景。**真实用户会用你想不到的方式用它。**

这个单元建立一个闭环：**线上的失败自动变成评估集的新题目。这是评估集唯一正确的增长方式。**

**学完你能做到**：走通「线上失败 → 人工确认 → 进 golden set → 修复 → 回归验证」的完整闭环，至少 3 次。

---

## 步骤 1 · 采集用户信号

### 这一步在做什么

知道用户对结果满不满意。**这比任何自动指标都真实。**

### 两类信号

**显式信号**：用户主动给的

| 信号 | 怎么采 | 可靠性 |
|---|---|---|
| 点赞/点踩 | 界面上加按钮 | 高，但**采集率低**（大多数人不点） |
| 打分 | 1-5 星 | 高，采集率更低 |
| 文字反馈 | 输入框 | 最有价值，采集率最低 |

**隐式信号**：从行为推断

| 信号 | 含义 | 怎么采 |
|---|---|---|
| **立刻重试** | 结果不满意 | 检测同一会话内相似输入的重复 |
| **中途放弃** | 太慢或者跑偏了 | 检测未完成就关闭的会话 |
| **手动修改结果** | 部分可用 | 如果界面允许编辑，记录编辑量 |
| **复制走了** | 满意 | 检测复制事件 |
| 长时间停留后无动作 | 在读，可能在判断 | 记录停留时长 |

**隐式信号的采集率是 100%**，这是它最大的优势。**但含义模糊**——「重试」可能是不满意，也可能是想问别的。

### 怎么做

在 U3.5 的 trace 上附加：

```python
async def 记录反馈(trace_id: str, 类型: str, 值: float, 说明: str = ""):
    lf.score(
        trace_id=trace_id,
        name=f"feedback:{类型}",
        value=值,
        comment=说明,
    )
```

前端调用（S5 会做）：

```python
@app.post("/feedback")
async def 反馈(trace_id: str, 好评: bool, 说明: str = ""):
    await 记录反馈(trace_id, "explicit", 1.0 if 好评 else 0.0, 说明)
```

隐式的在后端检测：

```python
async def 检测重试(会话id: str, 新输入: str) -> bool:
    上一次 = await 取上一次输入(会话id)
    if 上一次 and 相似度(上一次, 新输入) > 0.8:
        await 记录反馈(上一次的trace_id, "implicit_retry", 0.0)
        return True
    return False
```

### 可能卡在哪

**只有我一个用户**

**你就是用户。** 用的时候诚实地点赞点踩，不要因为「这是我自己写的」就宽容。

**实际上一个人的真实反馈，比十个人敷衍的反馈有价值。**

**隐式信号误判**

比如用户重试是因为想问别的，不是因为不满意。

**处理**：隐式信号只用于「筛选出可能有问题的 case 供人工检查」，**不直接当作负反馈用于统计。**

## 步骤 2 · 线上采样评估

### 这一步在做什么

不等用户反馈，主动对线上流量打分。

### 怎么做

对线上 trace 采样（比如 5%），异步跑 U3.4 的 judge：

```python
async def 在线评估任务():
    """后台任务，定期跑"""
    while True:
        待评的 = await 取未评分的trace(限制=50, 采样率=0.05)
        for t in 待评的:
            try:
                评分 = await judge评分(
                    输入=t.input,
                    输出=t.output,
                    工具返回=t.取工具span的返回(),
                )
                lf.score(trace_id=t.id, name="online_judge", value=评分.总分)
                if 评分.总分 < 0.6:
                    await 进收件箱(t.id, 原因="judge 低分", 详情=评分.关键问题)
            except Exception:
                logger.exception("在线评估失败 trace=%s", t.id)
        await asyncio.sleep(300)
```

**三个要点**：

**一、必须异步。** 绝对不能阻塞用户请求。用户等结果时不该再等一次 judge 调用。

**二、采样，不要全量。** 全量评估的成本可能比业务本身还高。5% 到 10% 通常够看趋势。

**三、失败不影响业务。** 在线评估挂了，业务照常跑。用 try/except 包住。

### 可能卡在哪

**成本太高**

降采样率，或者用便宜的 judge 模型（U3.4 测过一致率了）。

**judge 在线上和离线表现不一致**

因为线上的输入分布和评估集不同。**这本身就是一个发现**——说明你的评估集不够代表真实分布，该补充了。

### 背后的逻辑

在线评估和离线评估的分工：

| | 离线评估 | 在线评估 |
|---|---|---|
| 数据 | 固定的评估集 | 真实流量 |
| 时机 | 每次改动 | 持续 |
| 作用 | **防止退化** | **发现新问题** |
| 成本 | 可控 | 随流量增长 |

**两者互补，不能互相替代。**

## 步骤 3 · 建失败收件箱

### 这一步在做什么

把所有「可能有问题」的运行集中到一个地方，等你处理。

### 什么该进收件箱

| 来源 | 触发条件 |
|---|---|
| 显式负反馈 | 用户点踩或低分 |
| 隐式信号 | 立刻重试、中途放弃 |
| 在线 judge | 分数低于阈值 |
| **异常** | 报错、超时、超轮次、超预算 |
| **护栏触发** | 触发了任何一个护栏 |

### 数据结构

```sql
CREATE TABLE 失败收件箱 (
    id          SERIAL PRIMARY KEY,
    trace_id    TEXT NOT NULL,
    来源        TEXT NOT NULL,          -- 用户负反馈 / judge低分 / 异常 / ...
    详情        TEXT,
    创建时间     TIMESTAMPTZ DEFAULT now(),
    状态        TEXT DEFAULT '待处理',   -- 待处理 / 已确认是问题 / 误报 / 已转评估集
    处理备注     TEXT,
    评估条目id   TEXT                    -- 转成评估题之后填
);
```

### 处理流程

**每周固定时间**（比如周日复盘时）清一次收件箱：

1. 打开 Langfuse，看 trace
2. 判断：真的是问题吗？
3. 是 → **写成评估题**（用 U3.2 的格式），状态改「已转评估集」
4. 不是 → 状态改「误报」，写清楚为什么

### 可能卡在哪

**收件箱堆积**

说明系统问题很多，或者触发条件太宽。

**优先处理**：先看「异常」和「用户显式负反馈」，这两类最确定。

**判断不了是不是问题**

**这说明你的成功标准不清楚。** 回到 `PROJECT.md` 看你当初定的成功标准，如果那里也没写清楚，现在补上。

### 背后的逻辑

收件箱的价值是**把「发现问题」和「处理问题」解耦**。

发现是自动的、持续的、廉价的。处理是人工的、批量的、需要判断的。

**如果没有收件箱**，你要么实时处理每个告警（累死），要么什么都不处理（问题堆积）。

## 步骤 4 · 走通完整闭环

### 这一步在做什么

**本单元的核心。至少走通 3 次真实的完整流程。**

### 完整闭环的六步

```
1. 线上失败发生
   ↓
2. 进收件箱（自动）
   ↓
3. 你人工看 trace，确认是真问题
   ↓
4. 写成评估题，加进 golden.yaml
   ↓
5. 跑一次评估，确认这条题现在是失败的     ← 关键的一步
   ↓
6. 修复，再跑评估，确认这条题通过了
```

### 第 5 步为什么关键

**先确认题目能复现问题，再去修。**

如果你写完题跑一下发现它居然通过了，说明：

- 你的题没有准确复现那个失败（前置状态不对？输入不完整？）
- 或者问题是间歇性的

**这两种情况都要先解决，否则你的「修复」是在修一个不存在的问题。**

### 记录格式

对每次闭环，在 `s3-eval/dataset/CHANGELOG.md` 里记：

```markdown
## 2026-11-20 · EVAL-051

**来源**：2026-11-18 我自己使用时点了踩
**trace**：http://localhost:3000/trace/abc123
**问题**：用户问「上个月的数据」，Agent 用了本月的数据，且没说明时间范围
**根因**：日期解析工具对「上个月」的处理有 off-by-one，而且工具返回值没带时间范围

**评估题**：EVAL-051，判定标准包括
  - 包含「10 月」（上个月）
  - 不包含「11 月」
  - 输出必须标明数据的时间范围

**验证**：加题后跑评估，EVAL-051 失败 ✓（确认能复现）
**修复**：commit a3f21b9，修了日期解析 + 工具返回值加时间范围
**回归**：修复后 EVAL-051 通过 ✓，其余 50 题无退化 ✓
```

**这份记录本身就是很好的作品集素材。** 它展示了完整的工程闭环。

### 可能卡在哪

**没有足够的真实失败**

用得不够多。**这一步没有捷径**，必须真的把 Agent 用起来。

如果实在凑不够 3 次，**可以放宽到「你手工测试时发现的问题」**，但要在记录里标明来源。

**修复一个问题引入了新问题**

**这正是评估集存在的意义**——它会告诉你。回归跑的时候如果其他题挂了，说明修复方式有问题。

### 背后的逻辑

**这个闭环建立的是一条纪律：修任何 bug 之前，先给它写一条评估题。**

这条纪律的价值是**防止同一个 bug 复发**。没有它，你修了一个问题，三个月后重构时又引入了同样的问题，而且没人发现。

**顺序不能反。** 先修再补题的话，你补出来的题往往是「刚好能被你的修复通过」的题——那不是评估，那是自我证明。

## 步骤 5 · 定期读原始记录

### 这一步在做什么

U3.3 讲过这条，这里再强调一次，因为它在线上更重要。

### 怎么做

**每周随机抽 10 条线上 trace**（不管评分高低），完整读一遍。

关注：

- 用户实际是怎么用的（可能和你设计的完全不同）
- 有没有评分器和 judge 都没发现的问题
- 有没有你从没想到的使用场景

### 你会发现的事

第一次做这件事的人，**通常会发现用户的使用方式和自己的设计假设有很大出入。**

比如你设计的是「输入一个话题，返回选题」，但用户实际输入的是一大段乱糟糟的想法，期望它自己理清楚。

**这类发现无法通过任何自动指标得到。**

### 背后的逻辑

**必读文章的原话**：「在有人真正深入细节之前，我们不会把评估分数当真。」

自动化能告诉你「分数是多少」，**只有人能告诉你「这个分数意味着什么」。**
