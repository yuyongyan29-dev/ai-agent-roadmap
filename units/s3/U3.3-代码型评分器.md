# U3.3 · 代码型评分器（8 小时）

**这个单元解决什么问题**

把 U3.2 写的判定标准变成能自动执行的代码。

**必读文章的建议是三类评分器互补**：代码型（确定、快、便宜）、模型型（灵活、能处理细微差别）、人工（校准的黄金标准）。

**这一单元做第一类。原则很简单：能用规则判的，绝不用模型判。**

**学完你能做到**：一条命令跑完整个评估集，输出带失败明细的报告。

---

## 步骤 1 · 六种基础评分器

### 这一步在做什么

实现最常用的几种，覆盖你评估集里 80% 的判定标准。

### 一、精确匹配 / 包含

```python
def 包含(输出: str, 关键词: list[str], 全部: bool = True) -> tuple[bool, str]:
    命中 = [k for k in 关键词 if k in 输出]
    缺失 = [k for k in 关键词 if k not in 输出]
    通过 = (len(缺失) == 0) if 全部 else (len(命中) > 0)
    return 通过, f"命中 {命中}，缺失 {缺失}"


def 不包含(输出: str, 禁词: list[str]) -> tuple[bool, str]:
    违规 = [k for k in 禁词 if k in 输出]
    return len(违规) == 0, f"出现了禁词 {违规}" if 违规 else "无违规"
```

**注意返回值是 `(通过, 理由)` 的元组。** 理由字段很关键——**评估失败时你需要知道为什么**，而不是只看到一个 False。

### 二、结构校验

```python
from pydantic import BaseModel, ValidationError

def schema校验(输出: str, 模型类: type[BaseModel]) -> tuple[bool, str]:
    try:
        模型类.model_validate_json(剥壳(输出))
        return True, "结构合法"
    except ValidationError as e:
        return False, f"结构不合法：{e}"
```

复用 U1.3 的剥壳和 Pydantic 模型。

### 三、数值容差

```python
def 数值接近(输出值: float, 期望: float, 容差: float = 0.01) -> tuple[bool, str]:
    差 = abs(输出值 - 期望)
    通过 = 差 <= 容差
    return 通过, f"实际 {输出值}，期望 {期望}，差 {差:.4f}（容差 {容差}）"
```

**从自由文本里提数字**要小心，用正则加上下文约束，别抓错。

### 四、集合比较（检索类任务必用）

```python
def 召回评分(召回: list[str], 应召回: list[str], 必须: list[str]) -> tuple[bool, str]:
    召回集 = set(召回)
    命中 = 召回集 & set(应召回)
    必须命中 = set(必须) <= 召回集

    precision = len(命中) / len(召回集) if 召回集 else 0
    recall = len(命中) / len(应召回) if 应召回 else 0

    return 必须命中, f"precision={precision:.2f} recall={recall:.2f} 必须项{'全中' if 必须命中 else '有缺失'}"
```

**直接接你 U2.5 的检索评测集。**

### 五、轨迹断言（只测硬约束）

```python
def 调用过(轨迹: list[dict], 工具名: str) -> tuple[bool, str]:
    调用过的 = [t["名字"] for t in 轨迹 if t["类型"] == "工具调用"]
    return 工具名 in 调用过的, f"实际调用了 {调用过的}"


def 确认先于执行(轨迹: list[dict], 高危工具: str) -> tuple[bool, str]:
    """高危工具执行前必须有确认动作"""
    for i, t in enumerate(轨迹):
        if t.get("名字") == 高危工具:
            之前 = 轨迹[:i]
            if not any(x.get("类型") == "人工确认" for x in 之前):
                return False, f"第 {i} 步执行了 {高危工具}，但之前没有确认动作"
    return True, "高危操作都经过确认"


def 步数上限(轨迹: list[dict], 上限: int) -> tuple[bool, str]:
    步数 = len([t for t in 轨迹 if t["类型"] == "模型调用"])
    return 步数 <= 上限, f"用了 {步数} 步（上限 {上限}）"
```

**记住 U3.1 的原则**：轨迹只断言硬约束（安全、成本），**不要断言具体顺序**。

### 六、副作用验证（最可靠）

```python
async def 数据库有记录(条件: dict, 期望数量: int = 1) -> tuple[bool, str]:
    实际 = await 查数量(条件)
    return 实际 == 期望数量, f"符合 {条件} 的记录有 {实际} 条，期望 {期望数量}"


async def 文件存在且内容匹配(路径: str, 必须包含: list[str]) -> tuple[bool, str]:
    p = Path(路径)
    if not p.exists():
        return False, f"文件 {路径} 不存在"
    内容 = p.read_text(encoding="utf-8")
    缺失 = [k for k in 必须包含 if k not in 内容]
    return len(缺失) == 0, f"缺失内容 {缺失}" if 缺失 else "内容符合"
```

**必读文章特别提到「验证结果」（outcome verification）这类评分器。** 它最可靠，因为它不管模型怎么描述，直接查真实世界的状态。

**能用这类的时候优先用它。**

### 可能卡在哪

**关键词匹配太死板**

「三个月」和「3 个月」是一回事，但字符串匹配判不通过。

三个改进：

1. 预处理：统一全半角、统一数字写法
2. 用正则而不是固定字符串：`r"[3三]\s*个?月"`
3. 提供同义词列表：`["三个月", "3个月", "90天"]` 命中任一即可

**从自由文本提结构化值很难**

**更好的做法是让 Agent 直接输出结构化结果**（U1.3 学的），评估时直接读字段，不用从文本里抠。

**如果你的 Agent 现在只输出文本，考虑改成「文本 + 结构化摘要」双输出。** 这对 S5 前端也有好处。

### 背后的逻辑

代码型评分器的价值是**确定性**：同样的输出，永远得到同样的分数。

这意味着：

- 分数变化一定是系统变了，不是评分器抖动
- 可以在 CI 里当门禁（U3.7）
- 零成本，可以随便跑

**LLM judge 做不到这三点。** 所以原则是：**能用规则的绝不用模型。**

## 步骤 2 · 写评估运行器

### 这一步在做什么

把「读题 → 跑 Agent → 评分 → 出报告」串起来。

### 骨架

```python
@dataclass
class 单题结果:
    id: str
    通过: bool
    得分: float                  # 0 到 1，支持部分分
    评分明细: list[tuple[str, bool, str]]     # (标准名, 是否通过, 理由)
    输出: str
    轨迹: list[dict]
    耗时: float
    成本: float
    异常: str | None = None


async def 跑一题(题: dict, agent工厂) -> 单题结果:
    # 1. 隔离环境
    async with 隔离环境(题.get("前置状态")) as 环境:
        agent = agent工厂(环境)
        开始 = time.perf_counter()
        try:
            r = await asyncio.wait_for(agent.跑(题["输入"]), timeout=300)
        except Exception as e:
            return 单题结果(题["id"], False, 0.0, [], "", [], time.perf_counter()-开始, 0, str(e))

    # 2. 逐条判定
    明细 = []
    for 标准 in 题["判定标准"]:
        通过, 理由 = await 执行标准(标准, r)
        明细.append((标准["类型"], 通过, 理由))

    通过数 = sum(1 for _, p, _ in 明细 if p)
    return 单题结果(
        id=题["id"],
        通过=(通过数 == len(明细)),
        得分=通过数 / len(明细),
        评分明细=明细,
        输出=r.答案 or "",
        轨迹=r.轨迹,
        耗时=time.perf_counter() - 开始,
        成本=r.总费用,
    )
```

### 关键：环境隔离

**必读文章明确要求：构建隔离的环境，防止试次之间共享状态。**

如果第 1 题往数据库写了数据，第 2 题读到了，评估结果就不可信了。

三种隔离方式：

| 方式 | 做法 | 适合 |
|---|---|---|
| **事务回滚** | 每题开一个事务，结束时 ROLLBACK | 只涉及数据库 |
| **独立 schema** | 每题用一个临时 schema | 数据库 + 需要看最终状态 |
| **容器** | 每题起一个容器 | 涉及文件系统、外部服务 |

**推荐从事务回滚开始**，最简单，覆盖大部分场景。

```python
@asynccontextmanager
async def 隔离环境(前置: dict | None):
    async with engine.begin() as conn:
        if 前置 and 前置.get("数据库"):
            await conn.execute(text(Path(前置["数据库"]).read_text()))
        try:
            yield 环境(conn)
        finally:
            await conn.rollback()          # 无论如何都回滚
```

### 并发控制

```python
async def 跑全部(题目: list[dict], 并发: int = 3) -> list[单题结果]:
    信号量 = asyncio.Semaphore(并发)

    async def 一个(题):
        async with 信号量:
            return await 跑一题(题, agent工厂)

    return await asyncio.gather(*[一个(t) for t in 题目])
```

**并发数不要太高**：会撞模型 API 限流，而且如果隔离方式是容器，资源开销大。

### 可能卡在哪

**某一题卡死了，整个评估挂起**

加超时（上面代码里的 `asyncio.wait_for`）。超时算失败，记录下来。

**评估跑一次太久**

分层跑（U3.7）。或者对慢的题单独标记，日常只跑快的。

**外部依赖不稳定导致评估结果波动**

评估时把不稳定的外部服务 mock 掉（U0.7 学的技能）。**但要注意**：mock 掉之后你测的就不是真实链路了。

**折中方案**：核心路径的题用真实服务，其余用 mock。

## 步骤 3 · 报告输出

### 这一步在做什么

让评估结果一眼能看懂，而不是一堆数字。

### 报告要包含什么

```markdown
# 评估报告 2026-11-12 14:23

**配置**：模型 claude-sonnet-5 / prompt v4 / 代码 a3f21b9

## 总览
| 指标 | 本次 | 上次 | 变化 |
|---|---|---|---|
| 通过率 | 38/50 (76%) | 35/50 (70%) | **+6%** |
| 平均得分 | 0.84 | 0.79 | +0.05 |
| 总成本 | ¥3.21 | ¥3.05 | +5% |
| 平均耗时 | 12.3s | 11.8s | +4% |

## 按标签
| 标签 | 通过率 |
|---|---|
| 核心路径 | 23/25 (92%) |
| 边界 | 7/10 (70%) |
| 负例 | 5/10 (50%) |
| 回归 | 3/5 (60%) |

## 相比上次的变化
### 新通过（4 条）
- EVAL-012 边界 · 之前缺失关键词「时间范围」
- ...

### 新失败（1 条）⚠️
- EVAL-031 回归 · 之前通过，现在轨迹断言失败：执行删除前没有确认

## 全部失败明细
### EVAL-031 [回归] 得分 0.67
**输入**：把过期的草稿清理掉
**失败的标准**：轨迹 · 第 4 步执行了 删除草稿，但之前没有确认动作
**输出**：已为你清理了 12 条过期草稿。
**轨迹**：搜索草稿 → 筛选 → 删除草稿(×12) → 汇总
**原始记录**：runs/2026-11-12/EVAL-031.json
```

### 三个必须有的部分

**一、和上次对比。** 单次的绝对分数意义不大，**变化才有信号。**

**二、按标签拆分。** 总分 76% 可能掩盖了「负例只有 50%」这个严重问题。

**三、新失败要突出。** 「本来通过现在失败」是最需要立刻关注的信号。

### 可能卡在哪

**怎么存「上次的结果」**

存成 JSON 放在 `s3-eval/runs/` 下，按时间命名。同时维护一个 `baseline.json` 记录当前基线（U3.7 会用它做 CI 门禁）。

**报告太长看不完**

分层：终端里打印总览和新失败，完整明细写进文件。

## 步骤 4 · 定期读原始记录

### 这一步在做什么

**必读文章特别强调的一条：定期阅读原始记录，验证评分器确实在评你以为它在评的东西。**

### 为什么必须做

举一个真实会发生的情况：

你的评分器检查「输出包含『点赞』这个词」。某次改动后通过率突然从 70% 涨到 95%。

你很高兴。但读原始记录会发现：模型现在每次都在结尾加一句「以上数据包含点赞、收藏等指标」——**它学会了应付你的评分器，但答案质量并没有提升。**

**这叫「评分器被钻空子」，而且非常常见。**

### 怎么做

**建立一个习惯**：每次跑完全量评估，**随机抽 5 条通过的题**，人工读一遍原始输出和轨迹。

问自己：

- 它是真的做对了，还是碰巧满足了我的规则？
- 它的过程合理吗？
- 有没有我的评分器没覆盖到的问题？

**发现问题就改评分器或加新标准。**

### 可能卡在哪

**读起来很费劲**

用 U2.1 写的回放功能，把轨迹渲染成人能读的格式。

**没时间读**

**这一步不能省。** 必读文章的原话是：**「在有人真正深入细节之前，我们不会把评估分数当真。」**

每次 5 条，十分钟。这十分钟能防止你在一个假象上优化几周。
