# U3.3 · 代码型评分器（8 小时）

**这个单元解决什么问题**

把 U3.2 写的判定标准变成能自动执行的代码。

**必读文章的建议是三类评分器互补**：代码型（确定、快、便宜）、模型型（灵活、能处理细微差别）、人工（校准的黄金标准）。

**这一单元做第一类。原则很简单：能用规则判的，绝不用模型判。**

**学完你能做到**：一条命令跑完整个评估集，输出带失败明细的报告。

## 步骤 1 · 六种基础评分器

### 这一步在做什么

实现最常用的几种，覆盖你评估集里 80% 的判定标准。

### 一、精确匹配 / 包含

```python
def contains(output: str, keywords: list[str], require_all: bool = True) -> tuple[bool, str]:
    """检查输出是否命中关键词。require_all=True 表示全部命中才算过，False 表示命中任意一个即可。"""
    hits = [k for k in keywords if k in output]
    missing = [k for k in keywords if k not in output]
    passed = (len(missing) == 0) if require_all else (len(hits) > 0)
    # 理由里同时给出命中和缺失，失败时不用回头翻原始输出就知道差在哪
    return passed, f"命中 {hits}，缺失 {missing}"


def not_contains(output: str, banned: list[str]) -> tuple[bool, str]:
    """负向检查：输出里不能出现禁词（比如内部字段名、道歉套话、越权承诺）。"""
    violations = [k for k in banned if k in output]
    return len(violations) == 0, f"出现了禁词 {violations}" if violations else "无违规"
```

**注意返回值是 `(passed, reason)` 的元组。** 理由字段很关键——**评估失败时你需要知道为什么**，而不是只看到一个 False。

### 二、结构校验

```python
from pydantic import BaseModel, ValidationError

def validate_schema(output: str, model_cls: type[BaseModel]) -> tuple[bool, str]:
    """用 Pydantic 判断输出是否符合约定结构，model_cls 是这道题期望的 schema。"""
    try:
        # 先 strip_fence 剥掉 markdown 代码块外壳：模型经常在 JSON 外面裹一层说明文字
        model_cls.model_validate_json(strip_fence(output))
        return True, "结构合法"
    except ValidationError as e:
        # 把 Pydantic 的报错原样带回去，它已经指明了是哪个字段不合法
        return False, f"结构不合法：{e}"
```

复用 U1.3 的剥壳和 Pydantic 模型。

### 三、数值容差

```python
def numeric_close(actual: float, expected: float, tolerance: float = 0.01) -> tuple[bool, str]:
    """数值不做相等判断：浮点计算和口径差异会让完全相等几乎不可能，只要落在容差内就算过。"""
    diff = abs(actual - expected)
    passed = diff <= tolerance
    # 理由里把实际差值打出来，方便判断是算错了还是容差定得太紧
    return passed, f"实际 {actual}，期望 {expected}，差 {diff:.4f}（容差 {tolerance}）"
```

**从自由文本里提数字**要小心，用正则加上下文约束，别抓错。

### 四、集合比较（检索类任务必用）

```python
def recall_score(
    retrieved: list[str], expected: list[str], required: list[str]
) -> tuple[bool, str]:
    """检索类任务评分。expected 是理想召回集，required 是漏一个就算错的必须项。"""
    retrieved_set = set(retrieved)
    hits = retrieved_set & set(expected)
    # 通过与否只看必须项是否全中：precision/recall 是连续值，卡阈值容易变成噪声
    all_required_hit = set(required) <= retrieved_set

    # 空集时直接给 0，避免除零
    precision = len(hits) / len(retrieved_set) if retrieved_set else 0
    recall = len(hits) / len(expected) if expected else 0

    # 两个指标仍然算出来放进理由里，用来观察趋势（召回变多了还是变准了）
    return all_required_hit, f"precision={precision:.2f} recall={recall:.2f} 必须项{'全中' if all_required_hit else '有缺失'}"
```

**直接接你 U2.5 的检索评测集。**

### 五、轨迹断言（只测硬约束）

```python
def called_tool(trace: list[dict], tool_name: str) -> tuple[bool, str]:
    """断言某个工具被调用过。只问「有没有」，不问「第几步」——顺序不是硬约束。"""
    called = [step["name"] for step in trace if step["type"] == "tool_call"]
    return tool_name in called, f"实际调用了 {called}"


def confirm_before_execute(trace: list[dict], risky_tool: str) -> tuple[bool, str]:
    """高危工具执行前必须有确认动作。这是安全约束，任何一次违反都算失败。"""
    for i, step in enumerate(trace):
        if step.get("name") == risky_tool:
            # 只看这次调用之前的轨迹：确认必须发生在执行前，事后补确认无效
            before = trace[:i]
            if not any(x.get("type") == "human_confirm" for x in before):
                return False, f"第 {i} 步执行了 {risky_tool}，但之前没有确认动作"
    return True, "高危操作都经过确认"


def max_steps(trace: list[dict], limit: int) -> tuple[bool, str]:
    """成本约束：只数模型调用次数，工具调用不花模型的钱，也不体现循环失控。"""
    steps = len([step for step in trace if step["type"] == "model_call"])
    return steps <= limit, f"用了 {steps} 步（上限 {limit}）"
```

**记住 U3.1 的原则**：轨迹只断言硬约束（安全、成本），**不要断言具体顺序**。

### 六、副作用验证（最可靠）

```python
async def db_has_records(where: dict, expected_count: int = 1) -> tuple[bool, str]:
    """不看模型怎么说，直接查库：它声称写入了，就必须真的写进去了。"""
    actual = await count_rows(where)
    return actual == expected_count, f"符合 {where} 的记录有 {actual} 条，期望 {expected_count}"


async def file_exists_with_content(path: str, must_contain: list[str]) -> tuple[bool, str]:
    """验证文件产物：先判存在，再判内容，两种失败给不同理由，方便定位。"""
    p = Path(path)
    if not p.exists():
        # 文件都没生成，就没必要再比内容了
        return False, f"文件 {path} 不存在"
    content = p.read_text(encoding="utf-8")
    missing = [k for k in must_contain if k not in content]
    return len(missing) == 0, f"缺失内容 {missing}" if missing else "内容符合"
```

**必读文章特别提到「验证结果」（outcome verification）这类评分器。** 它最可靠，因为它不管模型怎么描述，直接查真实世界的状态。

**能用这类的时候优先用它。**

### 可能卡在哪

**关键词匹配太死板**

「三个月」和「3 个月」是一回事，但字符串匹配判不通过。

三个改进：

1. 预处理：统一全半角、统一数字写法
2. 用正则而不是固定字符串：`r"[3三]\s*个?月"`
3. 提供同义词列表：`["三个月", "3个月", "90天"]` 命中任一即可

**从自由文本提结构化值很难**

**更好的做法是让 Agent 直接输出结构化结果**（U1.3 学的），评估时直接读字段，不用从文本里抠。

**如果你的 Agent 现在只输出文本，考虑改成「文本 + 结构化摘要」双输出。** 这对 S5 前端也有好处。

### 背后的逻辑

代码型评分器的价值是**确定性**：同样的输出，永远得到同样的分数。

这意味着：

- 分数变化一定是系统变了，不是评分器抖动
- 可以在 CI 里当门禁（U3.7）
- 零成本，可以随便跑

**LLM judge 做不到这三点。** 所以原则是：**能用规则的绝不用模型。**

## 步骤 2 · 写评估运行器

### 这一步在做什么

把「读题 → 跑 Agent → 评分 → 出报告」串起来。

### 骨架

```python
@dataclass
class CaseResult:
    """单题的完整结果。除了分数，还留下输出、轨迹、成本，用来事后人工复查。"""
    id: str
    passed: bool
    score: float                             # 0 到 1，支持部分分
    details: list[tuple[str, bool, str]]     # (标准名, 是否通过, 理由)
    output: str
    trace: list[dict]
    duration: float
    cost: float
    error: str | None = None


async def run_case(case: dict, agent_factory) -> CaseResult:
    # 1. 每题跑在独立环境里，退出上下文时自动清理，题目之间不共享状态
    async with isolated_env(case.get("setup_state")) as env:
        agent = agent_factory(env)
        started = time.perf_counter()
        try:
            # 超时是必须的：一题卡死不能拖垮整轮评估，超时按失败记
            r = await asyncio.wait_for(agent.run(case["input"]), timeout=300)
        except Exception as e:
            # 异常不往上抛，转成一条失败结果，让剩下的题继续跑完
            return CaseResult(
                case["id"], False, 0.0, [], "", [], time.perf_counter() - started, 0, str(e)
            )

    # 2. 逐条判定：每条标准单独记理由，失败时能直接看出是哪一条没过
    details = []
    for criterion in case["criteria"]:
        passed, reason = await run_criterion(criterion, r)
        details.append((criterion["type"], passed, reason))

    passed_count = sum(1 for _, p, _ in details if p)
    return CaseResult(
        id=case["id"],
        # 全过才算这题通过；score 记部分分，用来观察「离通过还差多少」
        passed=(passed_count == len(details)),
        score=passed_count / len(details),
        details=details,
        output=r.answer or "",
        trace=r.trace,
        duration=time.perf_counter() - started,
        cost=r.total_cost,
    )
```

### 关键：环境隔离

**必读文章明确要求：构建隔离的环境，防止试次之间共享状态。**

如果第 1 题往数据库写了数据，第 2 题读到了，评估结果就不可信了。

三种隔离方式：

| 方式 | 做法 | 适合 |
|---|---|---|
| **事务回滚** | 每题开一个事务，结束时 ROLLBACK | 只涉及数据库 |
| **独立 schema** | 每题用一个临时 schema | 数据库 + 需要看最终状态 |
| **容器** | 每题起一个容器 | 涉及文件系统、外部服务 |

**推荐从事务回滚开始**，最简单，覆盖大部分场景。

```python
@asynccontextmanager
async def isolated_env(setup: dict | None):
    """整题包在一个事务里跑，结束时回滚，写进去的数据不会被下一题看见。"""
    async with engine.begin() as conn:
        if setup and setup.get("db"):
            # 前置数据用 SQL 文件灌进来；因为最后要回滚，不需要写对应的清理脚本
            await conn.execute(text(Path(setup["db"]).read_text()))
        try:
            yield Env(conn)
        finally:
            # 放在 finally 里：题目跑挂了也要回滚，否则脏数据会污染后面所有题
            await conn.rollback()          # 无论如何都回滚
```

### 并发控制

```python
async def run_all(cases: list[dict], concurrency: int = 3) -> list[CaseResult]:
    """并发跑整个评估集。用信号量而不是直接 gather，避免一次性打满模型 API。"""
    semaphore = asyncio.Semaphore(concurrency)

    async def run_one(case):
        # 信号量在协程内部获取，gather 一次性创建所有任务但同时在跑的只有 concurrency 个
        async with semaphore:
            return await run_case(case, agent_factory)

    return await asyncio.gather(*[run_one(c) for c in cases])
```

**并发数不要太高**：会撞模型 API 限流，而且如果隔离方式是容器，资源开销大。

### 可能卡在哪

**某一题卡死了，整个评估挂起**

加超时（上面代码里的 `asyncio.wait_for`）。超时算失败，记录下来。

**评估跑一次太久**

分层跑（U3.7）。或者对慢的题单独标记，日常只跑快的。

**外部依赖不稳定导致评估结果波动**

评估时把不稳定的外部服务 mock 掉（U0.7 学的技能）。**但要注意**：mock 掉之后你测的就不是真实链路了。

**折中方案**：核心路径的题用真实服务，其余用 mock。

## 步骤 3 · 报告输出

### 这一步在做什么

让评估结果一眼能看懂，而不是一堆数字。

### 报告要包含什么

```markdown
# 评估报告 2026-11-12 14:23

**配置**：模型 claude-sonnet-5 / prompt v4 / 代码 a3f21b9

## 总览
| 指标 | 本次 | 上次 | 变化 |
|---|---|---|---|
| 通过率 | 38/50 (76%) | 35/50 (70%) | **+6%** |
| 平均得分 | 0.84 | 0.79 | +0.05 |
| 总成本 | ¥3.21 | ¥3.05 | +5% |
| 平均耗时 | 12.3s | 11.8s | +4% |

## 按标签
| 标签 | 通过率 |
|---|---|
| 核心路径 | 23/25 (92%) |
| 边界 | 7/10 (70%) |
| 负例 | 5/10 (50%) |
| 回归 | 3/5 (60%) |

## 相比上次的变化
### 新通过（4 条）
- EVAL-012 边界 · 之前缺失关键词「时间范围」
- ...

### 新失败（1 条）⚠️
- EVAL-031 回归 · 之前通过，现在轨迹断言失败：执行删除前没有确认

## 全部失败明细
### EVAL-031 [回归] 得分 0.67
**输入**：把过期的草稿清理掉
**失败的标准**：轨迹 · 第 4 步执行了 删除草稿，但之前没有确认动作
**输出**：已为你清理了 12 条过期草稿。
**轨迹**：搜索草稿 → 筛选 → 删除草稿(×12) → 汇总
**原始记录**：runs/2026-11-12/EVAL-031.json
```

### 三个必须有的部分

**一、和上次对比。** 单次的绝对分数意义不大，**变化才有信号。**

**二、按标签拆分。** 总分 76% 可能掩盖了「负例只有 50%」这个严重问题。

**三、新失败要突出。** 「本来通过现在失败」是最需要立刻关注的信号。

### 可能卡在哪

**怎么存「上次的结果」**

存成 JSON 放在 `s3-eval/runs/` 下，按时间命名。同时维护一个 `baseline.json` 记录当前基线（U3.7 会用它做 CI 门禁）。

**报告太长看不完**

分层：终端里打印总览和新失败，完整明细写进文件。

## 步骤 4 · 定期读原始记录

### 这一步在做什么

**必读文章特别强调的一条：定期阅读原始记录，验证评分器确实在评你以为它在评的东西。**

### 为什么必须做

举一个真实会发生的情况：

你的评分器检查「输出包含『点赞』这个词」。某次改动后通过率突然从 70% 涨到 95%。

你很高兴。但读原始记录会发现：模型现在每次都在结尾加一句「以上数据包含点赞、收藏等指标」——**它学会了应付你的评分器，但答案质量并没有提升。**

**这叫「评分器被钻空子」，而且非常常见。**

### 怎么做

**建立一个习惯**：每次跑完全量评估，**随机抽 5 条通过的题**，人工读一遍原始输出和轨迹。

问自己：

- 它是真的做对了，还是碰巧满足了我的规则？
- 它的过程合理吗？
- 有没有我的评分器没覆盖到的问题？

**发现问题就改评分器或加新标准。**

### 可能卡在哪

**读起来很费劲**

用 U2.1 写的回放功能，把轨迹渲染成人能读的格式。

**没时间读**

**这一步不能省。** 必读文章的原话是：**「在有人真正深入细节之前，我们不会把评估分数当真。」**

每次 5 条，十分钟。这十分钟能防止你在一个假象上优化几周。
