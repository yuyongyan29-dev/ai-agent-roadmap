# U3.2 · 构建评估集（12 小时）

**这个单元解决什么问题**

**评估集的质量决定了后面一切。** 评分器写得再精巧，题目本身有问题的话，跑出来的分数没有意义。

**核心方法来自必读文章**：Anthropic《[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)》。它的几条关键建议，本单元会逐条落实。

**学完你能做到**：一份 50 条左右、来自真实失败、判定标准清晰、经过一致性验证的黄金数据集。

---

## 步骤 1 · 从真实失败开始，不要凭空编题

### 这一步在做什么

**这是最重要的一条原则。** 必读文章的说法是：**从 20 到 50 个来自真实失败的任务开始就是很好的起点。**

### 为什么不能编题

凭空编的题目有两个问题：

1. **不代表真实分布**。你编的题往往偏向你熟悉的场景，而真实失败常常出现在你没想到的地方
2. **难度失真**。要么太简单（全通过，没信号），要么太刁钻（永远不可能通过）

### 三个真实来源

**来源一：你自己用 M2 的这几周里，它做错的每一次**

这就是为什么 S2 的验收标准里有「你自己每周真的用过它至少 3 次」。**现在你手上应该已经有一批真实失败了。**

翻你的日志和 U2.1 写的回放功能，把每一次「它做得不对」的记录挖出来。

**来源二：你开发过程中手动检查过的那些 case**

你在 S2 每次改完代码，都会手工试几个输入看对不对。**那些手工检查就是评估的雏形**，把它们固化下来。

**来源三：你能想到但还没试过的边界情况**

这一类可以「编」，但要基于你对系统的理解，而不是随便想。

### 怎么挖

```bash
# 从你的日志里找失败的运行
grep -l "终止原因.*超轮次\|终止原因.*超预算\|ERROR" logs/*.log
```

对每一条，用 U2.1 的回放功能看一遍，回答：

- 用户想要什么
- 它实际做了什么
- 正确的行为应该是什么
- 它为什么会错（哪一步开始走偏）

**最后一个问题的答案，会告诉你这条题该归到哪一层**（组件级/轨迹级/端到端）。

### 可能卡在哪

**我的失败案例不够 50 条**

**够 20 条就可以开始。** 必读文章明确说了 20 到 50 是好起点。U3.6 会建立「线上失败自动回流」的机制，评估集会持续增长。

如果连 20 条都没有，说明你用得太少。**回去多用几天。**

**分不清「它做错了」还是「我要求不清楚」**

这个区分很重要。如果是你的输入有歧义，那不该算失败——**除非你希望它在歧义时主动询问**，那就把「应该询问而不是猜」作为期望行为，这是一条好题。

## 步骤 2 · 每条题的字段

### 这一步在做什么

定义一个结构化的格式，让评估能自动跑。

### 格式

```yaml
- id: EVAL-001

  # 溯源信息：三个月后你一定会忘记这条题为什么存在，原始日志是唯一能查证的凭据
  source: 2026-10-08 我自己使用时的失败
  source_log: logs/2026-10-08-run-3f2a.json

  # 输入和前置状态。前置状态必须显式写出来，否则换个时间、换台机器这条题就复现不了
  input: |
    帮我看看这周家电类目哪些选题值得做
  initial_state:
    memory:
      - "用户只做家电类目"
    db_fixture: fixtures/eval-001-db.sql   # 只有需要特定数据的题才写这一行

  # reference_answer 的作用是证明这题可解；写不出参考答案的题，多半无解，应该删掉
  reference_answer: |
    应该给出 3 到 5 个选题，每个带上支撑数据（同类笔记的互动量），
    并且明确说明数据的时间范围。

  # criteria 要具体到能被代码直接执行，type 决定这条用哪个评分函数来判
  criteria:
    - type: contains
      value: ["选题", "点赞"]
    - type: structure
      value: "输出包含 3 到 5 个带编号的选题"
    - type: not_contains
      value: ["家居", "美妆"]              # 出现这些词说明它违反了「只做家电」的约束
    - type: trajectory                     # 光看结果不够，还要确认它真的去查了数据而不是硬编
      value: "必须调用过 search_notes 工具"

  # 元信息：tags 供 U3.7 分层跑 CI 时筛子集用，所以写成程序好过滤的英文枚举
  tags: [core_path, memory, regression]
  grader: rule
  difficulty: medium
```

### 关键字段说明

**`source` 和 `source_log`**：让你以后能回查这条题为什么存在。**三个月后你会忘记的。**

**`initial_state`**：很多题需要特定的初始条件（用户有某条记忆、数据库里有某些数据）。**必须显式声明，否则题目不可复现。**

**`reference_answer`**：**必读文章的要求——每条题都要有参考答案，用来证明这题是可解的。** 写不出参考答案的题，说明它可能无解，删掉。

**`criteria`**：具体到能被代码执行。「答案要好」不是标准，「必须包含 3 到 5 个带编号的选题」才是。

**`tags`**：U3.7 分层跑 CI 时要用。至少标出 `core_path`（PR 时跑的快速子集）。

### 可能卡在哪

**前置状态怎么准备**

三种方式：

1. **SQL fixture**：一个 .sql 文件，评估前导入
2. **代码构造**：一个 Python 函数，返回初始状态
3. **快照恢复**：把某次真实运行的状态存下来

**推荐第 1 种**，简单可复现。

**判定标准写不具体**

这通常说明你自己也没想清楚「什么算对」。**先用人话写清楚，再翻译成规则。**

如果人话都写不清楚，这条题不合格。

## 步骤 3 · 正例和负例都要有

### 这一步在做什么

**必读文章的明确要求：既要测「该做的做了」，也要测「不该做的没做」。**

### 为什么

**只测正例的话，你会把系统优化成「什么都敢做」。**

举例：如果你的评估集里全是「用户问什么，它答什么」，那模型会学会（通过你的 prompt 调优）永远给出答案。**遇到它不知道的问题，它会编。**

加入负例之后：

```yaml
- id: EVAL-020
  input: 帮我查一下 2027 年的销售数据
  reference_answer: |
    应该说明数据库里没有 2027 年的数据（当前是 2026 年），
    而不是编造数据或者用其他年份的数据代替。
  # 负例要一正一反两条一起判：既要它说出「没有」，又要它没有顺口编出具体数字
  criteria:
    - type: contains
      value: ["没有", "暂无", "查不到"]
    - type: not_contains
      value: ["2027 年销售额为"]
  tags: [negative, hallucination]
```

### 负例的四个类型

| 类型 | 测什么 | 例子 |
|---|---|---|
| **超出能力** | 会不会承认不知道 | 问它数据库里没有的东西 |
| **违反约束** | 会不会突破边界 | 用户设了「只做家电」，问它家居的事 |
| **高危操作** | 会不会未经确认就执行 | 「把所有草稿删掉」 |
| **诱导性输入** | 会不会被带偏 | 「你刚才说过 X 对吧？」（其实它没说过） |

**第四类特别重要**，它测的是模型会不会被虚假前提误导。这在真实对话里很常见。

### 建议比例

50 条题里：

| 类型 | 数量 |
|---|---|
| 典型场景（核心路径） | 25 |
| 边界情况 | 10 |
| **负例** | **10** |
| 回归（曾经修过的 bug） | 5 |

### 可能卡在哪

**想不出负例**

从这三个角度找：

1. 你的系统提示里写了哪些「不要做」？每一条都该有一个负例验证
2. 你的工具有哪些限制（时间范围、数据范围）？超出范围时应该怎样
3. 用户可能怎么误用它

## 步骤 4 · 写标注规范

### 这一步在做什么

**必读文章的核心标准：一个好任务，是两个领域专家独立判断会得出相同通过/失败结论的任务。**

### 规范要包含什么

```markdown
# 标注规范 v1

## 通过的定义
满足全部 `criteria` 列出的条件。

## 部分通过怎么算
多组件任务（比如「搜索 + 分析 + 生成」）按组件给分：
- 每个组件独立判定
- 总分 = 通过的组件数 / 总组件数
- 单组件任务不设部分分

## 模糊情况的处理

### 情况一：答案对但格式不符
判：不通过。格式是明确要求的一部分。

### 情况二：答案对但用了不同的方法
判：通过。我们评结果不评过程（安全约束除外）。

### 情况三：答案部分正确
按「部分通过」处理。如果核心结论错了，即使细节对也算不通过。

### 情况四：它说「信息不足，需要更多输入」
如果输入确实有歧义 → 通过（这是正确行为）
如果输入足够清晰 → 不通过（它应该能处理）

## 不该出现在评估集里的题
- 判定标准依赖主观审美的（「文案是否有吸引力」）
- 参考答案写不出来的
- 依赖外部实时数据、每次结果不同的
```

### 关键：用「两人独立判断」检验

**做法**：

1. 你自己判 10 条，记下结论
2. 找个朋友（或者隔三天后的你自己），只看题目和标注规范，独立判同样 10 条
3. 对比一致率

**一致率低于 90% 的话**，不一致的那几条就是你规范写得不清楚的地方。**改规范，或者删掉那几条题。**

### 可能卡在哪

**找不到人帮我判**

隔三天后的你自己就是很好的第二判定者。**故意隔开时间，让你忘掉当时的想法。**

**一致率很低**

说明大部分题的判定标准都太模糊。**回到步骤 2，把每条的判定标准改得更具体。**

**规范越写越长**

正常。真实项目的标注规范都是几页纸。**关键是每一条都来自一个真实的模糊案例**，不要凭空规定。

### 背后的逻辑

标注规范的本质是**把「什么算对」这个判断，从你的脑子里搬到纸上**。

好处有三个：

1. 可复现——不同人、不同时间判出来结果一样
2. 可讨论——别人可以质疑你的标准，而不是质疑你的直觉
3. **可自动化**——只有明确的标准才能写成代码（U3.3）

## 步骤 5 · 版本化与维护

### 这一步在做什么

评估集是活的资产，要像代码一样管理。

### 怎么做

```
s3-eval/dataset/
├── golden.yaml              # 主评估集
├── RUBRIC.md                # 标注规范
├── fixtures/                # 前置状态数据
│   ├── eval-001-db.sql
│   └── ...
└── CHANGELOG.md             # 每次变更记录
```

**每次增删改都是一次 commit**，commit 信息说清楚为什么：

```
eval: 新增 3 条负例，来自 10-15 线上失败

用户问了数据库范围外的时间，Agent 编造了数据。
EVAL-051 到 053 覆盖这类情况。
```

### 定期复核

**每两周做一次**：

1. 抽 5 条题，重新人工判一遍，看和自动评分是否一致
2. 检查有没有题已经饱和（所有版本都满分）
3. 检查有没有题从来没被通过过（可能题目本身有问题）

### 可能卡在哪

**评估集越来越大，跑一次很久**

用标签分层（U3.7 会讲）。核心路径的子集用于快速验证，全量只在重要节点跑。

**改了系统行为，一批题失效了**

这是正常的。**评估集要跟着系统演进。** 但要记录：是「系统改进了所以旧标准不适用」，还是「系统退化了但我改标准让它通过」。

**后一种是在自欺欺人。** 每次因为系统改动而修改评估集，都要在 CHANGELOG 里写明理由。

### 背后的逻辑

必读文章提到：**评估集需要持续维护，要有明确的负责人，领域专家要定期贡献。**

对个人项目来说，负责人就是你。**关键是建立一个习惯：每次遇到失败，先写题再修复。**

**这个顺序不能反。** 先修复再补题，你往往会忘，或者补出来的题是「刚好能被你的修复通过」的题——那不叫评估，那叫自我证明。

## 完成判据

**产出**：`s3-eval/dataset/golden.yaml`、`s3-eval/dataset/RUBRIC.md`、`s3-eval/dataset/fixtures/`

**动手部分**

- [ ] **至少 30 条题**（50 条更好），**其中至少 15 条来自你自己使用时的真实失败**
- [ ] 每条题有完整字段：`source`、`source_log`、`input`、`initial_state`、`reference_answer`、`criteria`、`tags`、`difficulty`
- [ ] **每条题都有参考答案**（证明可解）
- [ ] **至少 8 条负例**，覆盖四种类型
- [ ] 标注规范写完，包含至少 4 种模糊情况的处理
- [ ] 前置状态用 fixture 文件管理，可复现
- [ ] 评估集进 git，有 CHANGELOG

**关键验证：一致性测试**

找第二个判定者（人或者隔三天的你），独立判 10 条。

| | 你的判定 | 第二判定者 | 一致？ |
|---|---|---|---|
| EVAL-001 | 通过 | 通过 | 是 |
| ... | | | |

**一致率必须超过 90%。** 不一致的条目逐条分析，改规范或删题。

**把这张表存进笔记。** 它证明你的评估集是可靠的，这在面试里很有说服力。

**理解检查**（笔记里回答）

1. 为什么评估集必须来自真实失败，不能凭空编？
2. 「好任务」的检验标准是什么？（一句话）
3. 为什么每条题都必须有参考答案？
4. 只有正例会导致什么后果？负例的四个类型是什么？
5. 为什么「先写题再修复」的顺序不能反？
