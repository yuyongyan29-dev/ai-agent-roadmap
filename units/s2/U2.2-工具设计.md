# U2.2 · 工具设计（8 小时）

**这个单元解决什么问题**

**Agent 失败的很大一部分原因不是模型笨，是工具设计得烂。**

工具描述含糊 → 模型不知道什么时候该用它。参数设计不好 → 模型传错。返回值太长 → 污染上下文。返回值太短 → 模型不知道下一步做什么。

**必读**：Anthropic《[Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents)》（2025-09-11）。

**学完你能做到**：用数据证明某个描述写法把工具调用准确率提高了多少。

---

## 步骤 1 · 工具描述：说清楚「什么时候用」

### 这一步在做什么

理解一件反直觉的事：**描述工具「做什么」不如描述「什么时候该用它」。**

### 对比

```python
# 弱：只说做什么
描述="搜索笔记库"

# 强：说什么时候用
描述=(
    "在小红书笔记库里按关键词搜索。"
    "当你需要了解某个话题下已有哪些内容、竞品在做什么、"
    "或者验证一个选题是否已经被做过时使用。"
    "返回笔记标题、点赞数、发布时间和链接。"
    "注意：只覆盖过去 90 天的数据，更早的内容查不到。"
)
```

强的那版包含四类信息：

| 信息 | 作用 |
|---|---|
| 做什么 | 基本功能 |
| **什么时候用** | **帮模型在多个工具间做选择** |
| 返回什么 | 让模型知道能得到什么，决定要不要调 |
| **限制是什么** | **避免模型误用后得到空结果又不知道为什么** |

### 加一句「什么时候不该用」

```python
描述=(
    "...（上面的内容）..."
    "不要用它来查某一篇笔记的详情——那用「读笔记详情」工具。"
)
```

**当你有多个功能相近的工具时，这一句的效果非常明显。**

### 做这个实验

选一个工具，写两版描述（弱版和强版）。构造 20 个用户输入，其中：

- 10 个应该调用这个工具
- 10 个不应该（应该调别的工具或者不调）

两版各跑一遍，统计：

| 描述版本 | 该调时调了 | 不该调时没调 | 总准确率 |
|---|---|---|---|
| 弱版 | /10 | /10 | /20 |
| 强版 | /10 | /10 | /20 |

**这组数据是本单元的核心产出。**

### 可能卡在哪

**描述写多长合适**

回想 U1.5：工具定义可能占上下文的 20% 到 40%。**每个字都要付费，而且每一轮都重发。**

经验值：2 到 4 句话。超过 5 句就该考虑是不是这个工具做的事太多，该拆开。

**模型总是调错工具**

按顺序检查：

1. 两个工具的描述是不是太像？加「不要用它来…」区分
2. 工具名是不是不够自解释？
3. 工具是不是太多？（见步骤 5）

### 背后的逻辑

从模型的视角想这件事：它看到的是一份工具清单，要在其中选一个。**这本质上是一个分类任务。**

分类任务的准确率取决于类别之间的**区分度**。所以你的目标不是「把每个工具描述得完美」，而是「让任意两个工具之间的边界清晰」。

**这就是为什么「什么时候不该用」比「做什么」更有效**——它直接划边界。

## 步骤 2 · 参数设计

### 这一步在做什么

让模型少传错参数。

### 五条规则

**一、能用枚举就别用自由字符串**

```python
# 弱
排序方式: str = Field(description="排序方式")

# 强
from enum import Enum
class 排序(str, Enum):
    最新 = "latest"
    最热 = "hottest"
    相关度 = "relevance"

排序方式: 排序 = Field(default=排序.相关度, description="排序方式")
```

枚举会进入 JSON schema，模型只能选其中之一。**从机制上排除了瞎编。**

**二、必填参数越少越好**

每个必填参数都是一个出错机会。能给默认值的都给。

**三、参数名要自解释**

`start_date` 比 `d1` 好。模型看不到你的文档，只能看名字和描述。

**四、格式要求写在描述里，并给例子**

```python
开始日期: str = Field(
    description="开始日期，格式 YYYY-MM-DD，例如 2026-09-01。不要用其他格式。"
)
```

更好的做法是**用类型约束而不是描述**：

```python
from datetime import date
开始日期: date        # Pydantic 会校验，schema 里也会标明 format: date
```

**五、避免深层嵌套**

超过两层的嵌套结构，模型出错率明显上升。**能拍平就拍平**，或者拆成多个工具。

### 可能卡在哪

**模型总是漏传某个必填参数**

三个可能：

1. 这个参数从用户输入里得不到（模型无中生有不了）→ 给默认值或改成可选
2. 描述不清楚 → 补充说明和例子
3. 参数太多了 → 拆分工具

**日期类参数总是出错**

日期是最容易出错的一类。三个改进：

1. 用 `date` 类型而不是 `str`
2. 提供相对表述的支持：加一个 `最近N天: int` 参数，比让模型自己算日期可靠得多
3. **在工具内部做容错解析**：接受多种格式，内部统一

**第 2 条特别值得记住**：**让模型做它擅长的（理解意图），别让它做它不擅长的（算日期）。**

### 背后的逻辑

模型填参数的过程，和它生成任何文本一样，是在「猜最可能的内容」。

**你的每一个约束都在缩小它的猜测空间**：枚举把无限的字符串缩到 3 个选项，类型把任意文本缩到合法日期，默认值把「必须猜」变成「可以不猜」。

**设计原则：把出错的可能性从机制上消除，而不是靠描述去请求。**

## 步骤 3 · 返回值设计

### 这一步在做什么

**这是最被低估、也最影响效果的一环。**

### 两个极端都不好

**返回太多**：一个查询返回 500 行数据，全塞进上下文。后果是成本暴涨、上下文被污染、模型抓不住重点。（回想 U1.5 的长度效应实验。）

**返回太少**：只返回「成功」。模型不知道拿到了什么，无法决定下一步。

### 正确的原则

**返回模型做决策需要的信息，而不是全部数据。**

```python
# 差：全量返回
return json.dumps(全部500条, ensure_ascii=False)     # 可能几万 token

# 好：摘要 + 关键项 + 继续获取的线索
return f"""找到 523 条匹配「{关键词}」的笔记（时间范围 2026-06-01 至 2026-09-09）。

按点赞数排序的前 5 条：
1. 冬季家电选购指南 · 12.3k赞 · 2026-08-15 · id=n_8823
2. 我家电器踩过的坑 · 8.1k赞 · 2026-07-22 · id=n_7712
3. ...

统计：平均点赞 340，中位数 89，超过 1k 赞的有 23 条。
高频标签：家电(412) 选购(388) 避坑(201)

需要看某一条的详情，用「读笔记详情」传入 id。
需要看更多结果，本工具传 offset=5。
"""
```

这个返回值里有四种东西：

| 成分 | 作用 |
|---|---|
| **总量和范围** | 让模型知道搜到的多不多、够不够 |
| **前 N 条的关键字段** | 直接可用的信息 |
| **聚合统计** | 帮模型判断整体情况，往往比看单条更有用 |
| **下一步的线索** | 明确告诉模型怎么继续 |

### 错误返回也要设计

```python
# 差
return "Error"
return "500 Internal Server Error"

# 好
return (
    "错误：日期格式不正确。"
    "你传的 start_date 是「2026/09/01」，应为「2026-09-01」。"
    "请修正后重试。"
)

return (
    "查询失败：数据源暂时不可用（超时）。"
    "这是临时故障，可以稍后重试，或者换用「本地缓存搜索」工具。"
)
```

**错误信息要包含：什么错了、为什么错、怎么办。** 这直接决定模型能不能自我修复。

### 可能卡在哪

**不知道返回多少合适**

用数据决定。在 U1.5 学的上下文分析里，看工具返回占了多少。**如果某个工具的返回占了上下文的 30% 以上，就该压缩。**

**摘要要不要用模型生成**

可以，但要算成本。**优先用规则**：截断、取前 N 条、算统计值。规则做不到的（比如把一篇长文压成三句话）再用模型。

**模型需要完整数据怎么办**

用 U1.5 学的「外部化」策略：完整数据存文件，返回值里给路径和摘要，模型需要时用另一个工具去读。

### 背后的逻辑

工具返回值是**唯一进入上下文的外部信息**。它的质量直接决定模型的决策质量。

有一个视角很有用：**把工具返回值当成「写给模型看的报告」**，而不是「数据的转储」。

好的报告是：先给结论和概览，再给关键细节，最后说明还能怎么深入。**这正好就是上面那个返回值的结构。**

## 步骤 4 · 幂等与副作用

### 这一步在做什么

保证工具被重复调用时不出乱子。

### 为什么会重复调用

三种情况，都很常见：

1. 模型忘了自己调过，又调一次
2. 网络超时，你的重试逻辑重发了，但其实第一次已经执行成功了
3. S4 的断点续跑：任务从 checkpoint 恢复，可能重放某些步骤

### 分类处理

| 工具类型 | 例子 | 重复调用的后果 | 怎么办 |
|---|---|---|---|
| **只读** | 搜索、查询、读文件 | 无害 | 不用处理 |
| **幂等写** | 「把状态设为已完成」 | 无害（结果一样） | 不用处理 |
| **非幂等写** | 发消息、扣款、创建记录 | **有害** | **必须处理** |

### 非幂等操作的三种处理

**一、加幂等键**

```python
class 发消息参数(BaseModel):
    接收人: str
    内容: str
    幂等键: str = Field(
        description="本次发送的唯一标识。同一条消息重发请用相同的键。"
    )


async def 发消息(p: 发消息参数) -> str:
    if await 已执行过(p.幂等键):
        return f"这条消息（键 {p.幂等键}）已经发送过了，未重复发送。"
    结果 = await 真的发(p.接收人, p.内容)
    await 记录已执行(p.幂等键)
    return 结果
```

**二、设计成两步：先预览，再确认**

```
工具1：生成消息草稿 → 返回草稿 id 和内容
工具2：确认发送(草稿id) → 真的发出
```

**这也顺便实现了人工确认的钩子**（S4 会用到）。

**三、加频率限制**

```python
if await 最近N分钟内发过相同内容(接收人, 内容):
    return "错误：5 分钟内已向该用户发送过相同内容，已阻止重复发送。"
```

### 可能卡在哪

**幂等键让模型自己生成靠谱吗**

不太靠谱。**更好的做法是你的代码生成**：用「任务 id + 步骤序号」或者「参数内容的哈希」。

**外部 API 本身不支持幂等**

那就在你这边记录。执行前先查「这个操作做过没有」，执行后立刻记录。

**注意顺序问题**：如果「执行」和「记录」之间崩溃了，就会漏记。S4 会讲怎么处理这个（先记「意图」再执行，恢复时查证）。

### 背后的逻辑

**幂等性是分布式系统的基本功课**，Agent 只是把它的重要性放大了。

放大的原因是：Agent 的执行路径不确定，重试和恢复更频繁，而且**模型可能做出人不会做的事**（比如连续调用同一个工具三次）。

**设计原则**：假设每个工具都可能被调用多次，然后问「这样会出什么问题」。会出问题的就加保护。

## 步骤 5 · 工具太多怎么办

### 这一步在做什么

处理一个你迟早会遇到的问题。

### 问题

工具超过 15 到 20 个之后，两件事同时发生：

1. **工具定义占的上下文越来越大**（U1.5 已经量化过）
2. **模型选错工具的概率上升**（选项越多，分类越难）

### 三种解法

**解法一：按场景分组，动态加载**

```python
工具组 = {
    "搜索类": ["搜索笔记", "搜索用户", "搜索标签"],
    "分析类": ["算互动率", "对比数据", "找趋势"],
    "输出类": ["生成选题", "存草稿", "导出报表"],
}

# 先用一次便宜的调用判断意图，再只加载相关组
组 = await 判断意图(用户输入)
可用工具 = 工具表.取组(组) + 工具表.取组("通用")
```

**代价**：多一次调用；判断错了会缺工具。

**缓解**：给模型一个「加载更多工具」的元工具，让它自己要。

**解法二：分层工具**

把细粒度的工具合并成粗粒度的，参数里带子操作：

```python
# 之前：3 个工具
搜索笔记 / 搜索用户 / 搜索标签

# 之后：1 个工具
class 搜索参数(BaseModel):
    类型: Literal["笔记", "用户", "标签"]
    关键词: str
```

**代价**：单个工具的描述变复杂；参数校验要按类型分支。

**解法三：代码执行**

不给几十个工具，给一个「执行代码」的工具和一份 API 文档。模型写代码来调用你的能力。

参考 Anthropic《[Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)》（2025-11-04）。

| 优点 | 缺点 |
|---|---|
| 上下文占用极小 | **必须有安全沙箱**（S6 的 U6.3） |
| 模型能组合、循环、条件判断 | 调试更难 |
| 一次调用完成多步 | 模型写的代码可能有 bug |

**这是能力最强但工程要求最高的一种。**

### 可能卡在哪

**我现在只有 5 个工具，需要考虑这个吗**

不需要。**但要知道这个上限的存在**，别无节制地加工具。

每次想加新工具时先问：能不能用现有工具的参数扩展来实现？

**动态加载后模型说「我没有这个工具」**

意图判断错了。加一个兜底：给模型一个「列出所有可用工具」和「加载某组工具」的元工具。

### 背后的逻辑

这个问题的本质是**注意力预算的分配**。

工具定义占的每一个 token，都是从「对话历史」和「检索结果」那里抢来的。**当工具定义占 40% 时，你实际上是在用「模型知道有哪些能力」换「模型知道当前情况」。**

**这就是上下文工程在工具层面的体现。** U1.5 学的原则在这里直接适用。
