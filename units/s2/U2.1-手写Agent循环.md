# U2.1 · 手写 Agent 循环（10 小时）

**这个单元解决什么问题**

**不用任何框架，200 行以内写出一个能用的 Agent。**

这是整个 S2 的地基。跳过它，你后面会一直停留在「调框架的 API」，遇到问题不知道从哪查——因为你不知道框架在替你做什么。

**必读，在动手前读完**：Anthropic《[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)》（2024-12-19）。它定义了五种工作流模式和一种 Agent 模式，核心建议是：**从最简单的方案开始，只在必要时增加复杂度。工作流适合路径确定的任务，Agent 适合需要模型自主决策的开放场景。**

**大多数人做 Agent 的第一个错误，就是本该用工作流的地方用了 Agent。**

**学完你能做到**：写出一个能用 3 个工具完成多步任务的 Agent，并且能逐行解释每一行代码。

## 步骤 1 · 理解 Agent 到底是什么

### 这一步在做什么

在写代码之前，先把「Agent」这个词的神秘感去掉。

### 它就是一个循环

```
while 没完成 and 轮次 < 上限:
    响应 = 调模型(系统提示, 工具定义, 消息历史)

    if 响应里有工具调用:
        for 每个工具调用:
            结果 = 执行工具(名字, 参数)
            把「调用」和「结果」都追加进消息历史
        continue                    # 回到循环开头，再问一次模型
    else:
        return 响应的文本            # 模型觉得可以给答案了
```

**就这样。没有别的了。**

所有 Agent 框架，剥掉抽象之后，核心都是这个循环。它们提供的是：状态持久化、错误恢复、可观测性、并行控制——**但循环本身就是这十几行。**

### 三个关键点

**一、模型不执行工具，模型只是「说」它想调什么。**

模型返回的是一段结构化数据：「我想调用 `搜索`，参数是 `{关键词: "家电"}`」。**真正去执行的是你的代码。**

这一点很多人一开始搞不清。模型没有任何执行能力，它只会生成文本（包括生成「工具调用」这种结构化文本）。

**二、工具的执行结果必须回填进消息历史。**

模型下一轮要看到「我调了搜索，返回了这些内容」，才能决定下一步。

**三、循环的终止条件是模型自己决定的。**

模型不再返回工具调用，而是返回文本时，就是它认为任务完成了。**所以你必须有一个强制上限**，否则遇到模型钻牛角尖就会无限循环。

### 什么时候不该用 Agent

回到必读文章的核心建议。先问自己：**这个任务的执行路径是确定的吗？**

| 场景 | 该用什么 |
|---|---|
| 「先查库存，再算价格，再生成报价单」步骤固定 | **工作流**：写死的 if-else 或函数调用链 |
| 「先分类，然后按类别走不同的处理」分支已知 | **工作流**：Routing 模式 |
| 「查资料，看结果决定要不要再查，直到能回答」 | **Agent** |

**工作流可预测、可测试、便宜。Agent 灵活但不可预测、难调试、贵。**

**在你的项目里，很可能大部分是工作流，只有一小部分需要 Agent。** 这个判断本身就是有价值的工程能力。

## 步骤 2 · 工具注册表

### 这一步在做什么

建一个「工具名 → 函数」的映射，同时能生成给模型看的 schema。

### 怎么做

```python
from typing import Callable, Any
from pydantic import BaseModel


class 工具:
    def __init__(self, 名字: str, 描述: str, 参数模型: type[BaseModel], 函数: Callable):
        self.名字 = 名字
        self.描述 = 描述
        self.参数模型 = 参数模型
        self.函数 = 函数

    def 生成schema(self) -> dict:
        return {
            "type": "function",
            "function": {
                "name": self.名字,
                "description": self.描述,
                "parameters": self.参数模型.model_json_schema(),
            },
        }

    async def 执行(self, 原始参数: str) -> str:
        参数 = self.参数模型.model_validate_json(原始参数)
        结果 = await self.函数(参数)
        return str(结果)


class 工具表:
    def __init__(self):
        self._工具: dict[str, 工具] = {}

    def 注册(self, t: 工具):
        self._工具[t.名字] = t

    def schemas(self) -> list[dict]:
        return [t.生成schema() for t in self._工具.values()]

    def 取(self, 名字: str) -> 工具 | None:
        return self._工具.get(名字)
```

**用 U1.3 学的 Pydantic 定义参数**：

```python
class 搜索参数(BaseModel):
    关键词: str = Field(description="搜索关键词，用空格分隔多个词")
    数量: int = Field(default=10, ge=1, le=50, description="返回条数")


async def 搜索(p: 搜索参数) -> str:
    结果 = await 真的去搜(p.关键词, p.数量)
    return 格式化(结果)


工具表.注册(工具(
    名字="搜索笔记",
    描述="在小红书笔记库里搜索。当你需要了解某个话题下已有哪些内容时使用。",
    参数模型=搜索参数,
    函数=搜索,
))
```

### 可能卡在哪

**JSON schema 生成的格式模型不认**

不同模型对 schema 的要求略有差异。常见问题：

- 有些不支持 `$ref`（Pydantic 嵌套模型会生成引用）。解法是用 `model_json_schema(ref_template=...)` 或者手动展开
- 有些要求 `additionalProperties: False`，有些不支持它

**先固定用一家模型跑通，再考虑兼容。**

**工具名有什么讲究**

用动词短语，说清楚做什么。`搜索笔记` 比 `search` 好，`get_data` 是最差的那种。

**中文工具名可以吗**

可以，模型能处理。但**建议用英文**：有些模型对非 ASCII 的函数名支持不好，而且和主流生态一致。参数描述用中文没问题。

### 背后的逻辑

这个设计的核心是**一份定义三处使用**（U1.3 讲过的同一个思想）：

1. Pydantic 模型 → 生成给模型看的 JSON schema
2. Pydantic 模型 → 校验模型返回的参数
3. Pydantic 模型 → 你函数里的类型提示

**这就是为什么 U0.4 花时间学 Pydantic 是值得的。** 它是整个技术栈的粘合剂。

## 步骤 3 · 写循环

### 这一步在做什么

把步骤 1 的伪代码变成真代码。

### 骨架

```python
import json
import logging
from dataclasses import dataclass, field

logger = logging.getLogger(__name__)


@dataclass
class 护栏:
    最大轮次: int = 15
    单工具超时秒: float = 30.0
    最大总费用: float = 2.0


@dataclass
class 运行结果:
    答案: str | None
    轮次: int
    总费用: float
    终止原因: str            # 正常 / 超轮次 / 超预算 / 出错
    消息历史: list = field(default_factory=list)


class Agent:
    def __init__(self, llm, 工具表, 系统提示: str, 护栏: 护栏 = 护栏()):
        self.llm = llm
        self.工具表 = 工具表
        self.系统提示 = 系统提示
        self.护栏 = 护栏

    async def 跑(self, 用户输入: str) -> 运行结果:
        历史 = [
            {"role": "system", "content": self.系统提示},
            {"role": "user", "content": 用户输入},
        ]
        总费用 = 0.0

        for 轮 in range(1, self.护栏.最大轮次 + 1):
            if 总费用 > self.护栏.最大总费用:
                return 运行结果(None, 轮, 总费用, "超预算", 历史)

            回复 = await self.llm.对话(历史, tools=self.工具表.schemas())
            总费用 += 回复.用量.费用

            工具调用们 = 提取工具调用(回复)

            if not 工具调用们:
                logger.info("第 %d 轮：模型给出最终答案", 轮)
                return 运行结果(回复.文本, 轮, 总费用, "正常", 历史)

            历史.append(回复.原始消息)

            for tc in 工具调用们:
                logger.info("第 %d 轮：调用 %s，参数 %s", 轮, tc.名字, tc.参数[:200])
                结果 = await self._执行一个(tc)
                logger.info("  返回 %d 字符", len(结果))
                历史.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": 结果,
                })

        return 运行结果(None, self.护栏.最大轮次, 总费用, "超轮次", 历史)

    async def _执行一个(self, tc) -> str:
        t = self.工具表.取(tc.名字)
        if t is None:
            return f"错误：不存在名为 {tc.名字} 的工具。可用工具：{列出可用()}"
        try:
            return await asyncio.wait_for(
                t.执行(tc.参数), timeout=self.护栏.单工具超时秒
            )
        except asyncio.TimeoutError:
            return f"错误：工具 {tc.名字} 执行超过 {self.护栏.单工具超时秒} 秒，已中止。"
        except ValidationError as e:
            return f"错误：参数不合法。{e}。请检查参数格式后重试。"
        except Exception as e:
            logger.exception("工具 %s 执行失败", tc.名字)
            return f"错误：工具执行失败：{type(e).__name__}: {e}"
```

### 三个必须有的护栏

**这三样缺一不可，缺了会烧钱。**

| 护栏 | 防什么 |
|---|---|
| **最大轮次** | 模型在两个工具间反复横跳，永远不给答案 |
| **单工具超时** | 某个工具卡死，整个任务挂起 |
| **总费用上限** | 上面两个都没触发，但已经花了几十块 |

**真实发生过的事**：一个没设上限的 Agent 因为某个工具总是返回「未找到」，模型不断换关键词重试，跑了 200 轮，烧掉几百块。

### 错误也要回填给模型

注意 `_执行一个` 里：**所有异常都被转换成了字符串返回，而不是往上抛。**

这是有意的。模型看到「错误：参数不合法，日期格式应为 YYYY-MM-DD」之后，通常能自己改正重试。**如果你直接抛异常终止任务，就浪费了模型的自我修复能力。**

**但错误信息必须可行动**：

```python
# 不好
return "Error: 500"

# 好
return "错误：查询失败。日期格式应为 YYYY-MM-DD，你传的是 2026/1/1。请修正后重试。"
```

**这和 U1.3 的自动修复是同一个模式**：把错误明确地喂回去。

### 可能卡在哪

**各家的工具调用格式不一样**

OpenAI 系：`response.choices[0].message.tool_calls`，每个有 `id`、`function.name`、`function.arguments`（字符串）。

Anthropic：`response.content` 是一个列表，里面混着 `text` 块和 `tool_use` 块。

**建议**：先固定用一家做通，把提取逻辑写成一个函数，之后再加别家。或者直接用 LiteLLM，它统一成 OpenAI 格式。

**模型一次返回多个工具调用**

现代模型支持并行工具调用。你的代码要能处理列表，而不是假设只有一个。

**可以并行执行**（用 `asyncio.gather`），但要注意：有副作用的工具并行执行可能有问题。**保守做法是先串行跑通，再考虑并行。**

**tool_call_id 对不上**

每个工具结果必须带上对应调用的 `id`。漏了或者错了，模型就不知道哪个结果对应哪个调用。

**模型不调用工具，直接编答案**

三个原因：

1. 系统提示没说清楚有工具可用、什么时候该用
2. 工具描述写得不清楚
3. 模型觉得自己知道答案（幻觉）

解法：在系统提示里明确「你必须使用工具获取信息，不要凭记忆回答」。

### 背后的逻辑

**为什么错误要变成字符串回填，而不是抛异常？**

因为 Agent 的本质是「让模型在环境反馈中调整行为」。错误信息就是一种环境反馈。

对比两种设计：

| 设计 | 结果 |
|---|---|
| 出错就抛异常终止 | 任务失败，用户看到崩溃 |
| 出错回填给模型 | 模型看到错误，改正参数重试，任务成功 |

**第二种的成功率高得多。** 这是 Agent 相比传统程序的一个关键优势——它能从错误中恢复。

**但也有例外**：如果错误是系统性的（数据库挂了、密钥失效），让模型重试没有意义，应该直接终止。**你的代码要区分这两类。**

## 步骤 4 · 系统提示怎么写

### 这一步在做什么

写 Agent 的「工作说明书」。

### 骨架

```
你是（角色），负责（任务范围）。

## 你能做什么
（简述能力边界，什么在范围内，什么不在）

## 工作方式
1. 先理解用户要什么，不清楚就问
2. 用工具获取信息，不要凭记忆回答
3. 每一步都基于工具返回的真实数据
4. 信息足够了再给结论

## 重要约束
- 如果工具返回的信息不足以回答，说明缺什么，不要推测
- 引用数据时说明来源和时间
- （其他你项目特有的约束）

## 输出格式
（最终答案应该长什么样）
```

### 三个要点

**一、明确说「用工具，别凭记忆」。** 不说的话模型经常会直接用它的训练知识回答，而那些知识可能过期或者根本是编的。

**二、明确授权它说「不知道」。** 见 U1.1 的幻觉部分。

**三、不要在系统提示里重复工具的描述。** 工具描述已经在 schema 里了，重复只是浪费 token（U1.5 学过工具定义占多少上下文）。

### 可能卡在哪

**系统提示越写越长**

用 U1.4 学的方法：删一条，跑测试，分数不掉就永久删掉。

**模型不遵守某条约束**

三个手段递进：

1. 把这条挪到系统提示的开头或结尾（位置效应）
2. 改成正向表述（「不要 X」→「必须 Y」）
3. **用代码强制**：在 `_执行一个` 里加检查，而不是指望模型自觉

**第 3 条是关键认知**：**能用代码保证的，就不要指望 prompt。** 比如「不能删除超过 10 条记录」，应该在工具里检查，而不是在系统提示里请求。

## 步骤 5 · 日志：你唯一的排查依据

### 这一步在做什么

让每一次运行都能事后复盘。

### 必须记录的

```python
logger.info("=== 任务开始 === 输入：%s", 用户输入[:200])

# 每一轮
logger.info("第 %d 轮 → 模型（历史 %d 条，约 %d tokens）", 轮, len(历史), 估算token)
logger.info("第 %d 轮 ← 模型：%s", 轮, "工具调用" if 有工具 else "最终答案")

# 每次工具调用
logger.info("  调用 %s(%s)", 名字, 参数[:200])
logger.info("  返回 %d 字符：%s", len(结果), 结果[:200])

# 结束
logger.info("=== 任务结束 === %d 轮，¥%.4f，原因：%s", 轮次, 费用, 原因)
```

**关键是截断**。工具返回可能是几千字符，全打出来日志会没法看。截断到 200 字符，同时把完整内容存到别处（文件或数据库）供需要时查。

### 加一个「回放」功能

```python
def 回放(历史: list):
    """把一次运行的消息历史打印成人能读的格式"""
    for m in 历史:
        role = m["role"]
        if role == "tool":
            print(f"[工具返回] {m['content'][:300]}")
        elif m.get("tool_calls"):
            for tc in m["tool_calls"]:
                print(f"[模型想调] {tc['function']['name']}({tc['function']['arguments'][:200]})")
        else:
            print(f"[{role}] {m['content'][:300]}")
        print("-" * 60)
```

**出问题时，回放一遍你就知道它在哪一步走偏了。** 这是最原始但也最有效的调试手段。

### 可能卡在哪

**日志太多看不过来**

分级：INFO 记关键节点，DEBUG 记详细内容。平时用 INFO，排查时开 DEBUG。（U0.4 学的。）

**怎么知道每轮用了多少 token**

用 U1.6 的账本。每轮记录，最后汇总。

### 背后的逻辑

**这一步是 S3 可观测性的雏形。**

S3 你会把这些日志升级成结构化的 trace：每一轮是一个 span，每次工具调用是一个子 span，带上输入输出、token 数、耗时。然后在 Langfuse 里看树形结构。

**但底层要记录的东西是一样的。** 现在用 print 和 logger 建立习惯，S3 只是换个存储和展示方式。
