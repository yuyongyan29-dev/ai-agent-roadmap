# U2.10 · 企业系统集成（4 小时）

**这个单元解决什么问题**

给 Agent 接一个企业系统，困难往往发生在“第一次请求成功”之后：令牌过期、第二页漏了、请求被限流、事件重复到达、程序中途退出。这个单元把这些情况放到一个可重复运行的小实验里。

**学完你能做到**：写清并验证 OAuth 授权与刷新、游标分页、429 退避、Webhook 验签、去重和增量同步的处理方式，再把它们映射到一个真实 SaaS。本页选 **Slack 测试工作区的公开测试频道**，产物接到主线笔记 Agent 的只读资料入口。

**前置**：U0 的 Python/HTTP/SQLite、U2.2 工具设计。准备 Python 3；本地练习不需要 Slack 账号。建议预算：20 + 40 + 40 + 45 + 40 + 55 分钟。

**范围**：前 5 步用纯 Python 模拟器稳定制造故障；第 6 步做 Slack 适配和实连验证。测试工作区、安装权限和 HTTPS 回调若没准备好，先交付本地结果与适配契约，实连项保持未验收。账号审批、外网部署时间另计，不用一张“PASS”截图代替 SaaS 接入证据。

**来源核验日期：2026-09-10**。协议事实以 [Slack OAuth](https://docs.slack.dev/authentication/installing-with-oauth/)、[Token rotation](https://docs.slack.dev/authentication/using-token-rotation/)、[分页](https://docs.slack.dev/apis/web-api/pagination/)、[限流](https://docs.slack.dev/apis/web-api/rate-limits/)、[请求验签](https://docs.slack.dev/authentication/verifying-requests-from-slack/)、[Events API](https://docs.slack.dev/apis/events-api/)为准。

## 步骤 1 · 先跑一次完整故障实验（20 分钟）

### 这一步在做什么

先看到“成功、失败、恢复”各是什么样，再读代码。模拟协议与 Slack 协议明确分开。

### 怎么做

仓库带有两个文件：[`lab.py`](../../examples/saas-integration-lab/lab.py) 是模拟供应商和接入代码，[`verify.py`](../../examples/saas-integration-lab/verify.py) 是故障注入。只使用 Python 标准库，不请求外网。

```bash
cd ~/ai-agent-roadmap
python3 examples/saas-integration-lab/verify.py
```

本仓库实际运行输出：

```text
PASS OAuth state binding, expiry and callback replay
PASS token rotation, opaque pagination and Retry-After=2
PASS restart, transaction rollback, incremental update and tombstone
PASS raw-body signature, replay window, persistent dedup and stale event
PASS webhook inbox and record rollback together
PASS bounded retry without Retry-After
```

`sleep` 被替换为记录等待时长的函数，因此 `Retry-After=2` 表示代码要求等待 2 秒，测试不会真的睡 2 秒。OAuth 的“用户同意”由模拟器代替，授权不是通过真实浏览器发生的。SQLite 临时文件在验证结束后自动清理。

在 `s2-agent/integrations/notes_source/contract.md` 写下数据契约：主线 Agent 最终只需要 `id`、`text`、`source`；租户、版本、删除标记、同步检查点由接入层管理。不要把 OAuth 和重试逻辑散进工具提示词。

### 可能卡在哪

**想直接把模拟器 URL 换成 Slack URL。** 模拟器没有 HTTP 服务，`DemoSaaS` 是进程内的假供应商；`items`、`revision`、`next_cursor` 是教学契约，不是 Slack 返回字段。

### 背后的逻辑

把不稳定因素拆开：先验证接入逻辑能否正确恢复，再用厂商适配器验证真实权限、网络与响应字段。

## 步骤 2 · 完成授权与令牌轮转（40 分钟）

### 这一步在做什么

把“这次授权属于谁”和“过期后怎样继续”变成程序状态，避免只粘贴一个永久令牌。

### 怎么做

在 `lab.py` 找到 `begin_authorization`、`finish_authorization` 和 `request_page`，跟着 `verify.py` 的第一、二段走一遍：

1. 开始授权时产生随机 `state`，绑定当前浏览器会话，并设过期时间。
2. 回调先核对会话、`state` 和有效期，再兑换一次性授权码；成功消费的 state 不能再次使用。
3. 保存 access/refresh token 整对数据。本实验只接一个 `demo-team`；真实系统按安装租户分别存储。
4. 模拟供应商让 access token 失效；客户端只尝试刷新一次，保存新的整对令牌，再请求同一页。
5. 旧 refresh token 再用会失败，转到重新授权，不能无限刷新。

把下面任务交给 coding agent，修改学习项目里的副本：

```text
把 examples/saas-integration-lab 复制到 s2-agent/integrations/lab，先运行 verify.py。
读完授权部分后补一个测试：同一浏览器发起两次授权，旧 state 回来时必须拒绝，最新 state 能成功。
再补一个测试：refresh token 已失效时，不推进同步检查点，返回明确的“需要重新授权”。
不要输出 token 或授权码。保留现有成功输出，把新测试结果写到 integrations/evidence.md。
只修改接入实验，不改主线 Agent 的对话逻辑。
```

真实 Slack 要先为**新建测试 App**启用 token rotation，兑换时使用 `oauth.v2.access`，刷新时传 `grant_type=refresh_token`。按实际 `expires_in` 安排提前刷新，并保存返回的新 refresh token。启用轮转不能关闭，因此不要拿现有生产 App 做实验。[Slack 轮转说明](https://docs.slack.dev/authentication/using-token-rotation/)。

### 可能卡在哪

**刷新成功，重启后却无法访问。** 查是否只改了内存，或只保存 access token 忘了新 refresh token。

**两个 worker 同时刷新。** 教学模拟器是单进程单连接，没有处理并发刷新。真实适配器用每个安装独立的锁或数据库并发控制；刷新失败后先重新读取已保存版本，不能拿旧令牌反复试。

**误以为所有 401 都代表令牌到期。** 实际厂商可能在 HTTP 200 的 JSON 中返回错误；需要按文档区分到期、撤销、缺权限。Slack 的 `ok: false` 也必须检查，不能只看状态码。[Web API 使用方式](https://docs.slack.dev/apis/web-api/)。

### 背后的逻辑

OAuth callback 的 state 与 API access token 解决不同问题。前者将授权结果绑定到发起会话，后者代表已获授权的 API 访问；refresh token 只用于续期。

## 步骤 3 · 把每一页读完，并有界地等待限流（40 分钟）

### 这一步在做什么

证明你不是只读到了第一页，也不会遇到 429 后快速重试到服务失控。

### 怎么做

阅读 `DemoSaaS.page`、`request_page` 和 `sync` 的取数部分。这里故意让 3 条记录分成两页，游标随机生成；客户端只能把游标原样带回去，不能解析成页码。

执行路径是：令牌失效 → 刷新 → 429 → 记录等待 → 请求第一页 → 请求第二页 → 空游标结束。检查点只在完整同步成功后保存。

给 coding agent 的补充任务：

```text
针对 integrations/lab 增加两种假响应：
1. 第一页 items=[] 但 next_cursor 非空，第二页有记录。必须继续。
2. 服务连续返回相同 next_cursor。必须报 cursor cycle，不死循环。
再记录 429 的重试次数和要求等待的时长：有 Retry-After 时按它等待；
没有时使用有上限的指数退避加抖动；总尝试次数有限，耗尽后失败且检查点不变。
测试用 fake sleep，不等待真实分钟数，也不要访问 Slack 人为制造 429。
```

Slack 下一页游标来自 `response_metadata.next_cursor`。少于 `limit` 条甚至空页，都不能单独作为结束信号；按返回游标处理。[Slack 分页](https://docs.slack.dev/apis/web-api/pagination/)。429 的 `Retry-After` 表示重试前需等待的秒数；真实请求要真的等待。[Slack 限流](https://docs.slack.dev/apis/web-api/rate-limits/)。

### 可能卡在哪

**重试一页时新增了重复数据。** 取数可以重试，入库需要稳定主键和 upsert，步骤 5 会处理。

**游标隔天再用失效。** 游标只作为本轮翻页状态，长期恢复使用你的同步检查点。重新开始固定范围的扫描，再依赖幂等写入。

### 背后的逻辑

分页解决“有没有读完”，退避解决“什么时候再读”，重试预算解决“什么时候停止”。三者要分别可观察，不能用无限重试掩盖错误。

## 步骤 4 · 先验原始字节，再处理 Webhook（45 分钟）

### 这一步在做什么

确保事件确实来自预期发送方，并证明重复投递不会重复改业务状态。

### 怎么做

打开 `signature` 与 `receive_webhook`。签名计算采用 Slack 官方的 v0 规则：时间戳和**原始请求体字节**参与 HMAC-SHA256；再用恒定时间比较函数核对签名。时间窗口核验用于拒绝过旧请求。本实验的事件 JSON 是自定义教学格式，真实 Slack envelope 还要单独映射。[Slack 请求验签](https://docs.slack.dev/authentication/verifying-requests-from-slack/)。

先看 `verify.py` 的四个反例：

| 注入变化 | 必须看到的结果 |
|---|---|
| 同一 JSON 尾部添加空格，沿用原签名 | rejected |
| 正确签名，但时间戳超出窗口 | rejected |
| 相同 event_id 发送两次，第二次前重启 | accepted，然后 duplicate |
| 新 event_id 携带旧版本记录 | 可接收事件，但不覆盖新版本内容 |

再交给 coding agent：

```text
将接收函数放到现有 FastAPI 项目的 POST /integrations/slack/events 中。
先 await request.body() 取得原始 bytes，核验 X-Slack-Request-Timestamp 和 X-Slack-Signature，
不要先 request.json() 再 json.dumps()。验签通过后再解析 JSON。
url_verification 返回 challenge；event_callback 用 team_id + event_id 做持久去重。
事件先持久入 inbox，成功后及时返回 2xx；后台 worker 再做耗时业务。
本地测试至少包含 body 改一个字节、过期时间戳、重复事件、插入 inbox 后事务失败再重试。
不要把长时间模型调用放在事件 HTTP 请求里，也不要自动回复 Slack 消息。
```

本单元示例把“插入去重记录 + 更新本地镜像”放在同一个 SQLite 事务里，适合短小的本地操作。接真实 Slack 时按上面要求先持久化 inbox，HTTP 接收完成后再由 worker 处理；Slack 要求尽快回应事件，官方说明了 3 秒响应窗口及重投行为。[Events API](https://docs.slack.dev/apis/events-api/)。

### 可能卡在哪

**本地验签通过，上服务器失败。** 先看框架或代理是否改变了 body、字符编码或压缩处理，再看时间戳与服务器时钟；不要跳过验签“临时修好”。

**重启之后同一个事件又执行了。** 去重记录不能只放进程内 `set`。数据库唯一约束在并发到达时也必须生效。

### 背后的逻辑

签名回答“发送方是否可信”，event_id 去重回答“这次投递是否已处理”。同一个真实事件可能合法地重投，验签通过不代表首次到达。

## 步骤 5 · 增量同步崩一次，再从检查点恢复（40 分钟）

### 这一步在做什么

验证退出、重复读取和事件乱序不会丢记录，也不会让已删除内容重新出现。

### 怎么做

沿 `verify.py` 的同步段阅读：首次同步 3 条；供应商修改 `n1`、给 `n3` 设置删除标记；写入后、更新检查点前故意抛异常。事务回滚后关闭数据库，再打开，重新同步，最后再同步一次。

你需要在实际输出之外解释这些断言：

- 崩溃后 watermark 仍为旧值，本地记录也未部分更新。
- 重启后只读本轮变更；再跑一次没有新变更，不新增重复行。
- 删除以 tombstone 保留版本，旧事件不能把删除前内容覆盖回来。
- Webhook 更新本地记录，但不会把批量同步 watermark 向前推；否则可能跳过尚未补齐的其他记录。

模拟器提供单调 `revision` 和固定上界 `through`；一次取完再事务提交，适合这几个样本。真实系统数据多时分批暂存，只有本轮范围完整落盘后才提交最终检查点；失败就重扫未完成的范围。

### 可能卡在哪

**SaaS 没有 `updated_after` 或 revision。** 不要假造这个参数。以 Slack 为例，`conversations.history` 的 `oldest/latest` 是消息时间范围，不是通用“修改时间”过滤器。新消息可用固定时间窗补拉；旧消息编辑、删除需要事件处理和适当的补偿扫描，线程还需单独考虑。[conversations.history](https://docs.slack.dev/reference/methods/conversations.history/)。

**想把“写数据库一次”推广成“发消息一次”。** 本地事务不能回滚已经成功的外部 API。外部写入要按供应商支持设计幂等键或 outbox 与补偿；本单元只更新本地镜像，不宣称实现跨系统 exactly-once。

### 背后的逻辑

可靠同步通常允许重读，再用稳定身份和版本约束避免重复副作用。检查点代表“此前范围已完整处理”，不能代表“见过一个更晚的事件”。

## 步骤 6 · 接上 Slack 的真实协议（55 分钟）

### 这一步在做什么

把刚验证的逻辑连接到一个真实测试工作区，并记录哪些故障只在本地注入过。

### 怎么做

**先准备一个最小测试对象。** 在 [Slack App 管理页](https://api.slack.com/apps)新建测试 App，选择你有安装权限的测试工作区。在 OAuth & Permissions 中配置 HTTPS 回调地址，只申请公开频道读取所需的 `channels:history`；本练习手动提供频道 ID，不要求枚举频道。让 App 加入你选择的测试频道，手动发两条普通文本测试消息。公开频道权限与可访问范围见 [conversations.history 权限表](https://docs.slack.dev/reference/methods/conversations.history/)。

**建真实适配器，不改教学供应商。** 在 `s2-agent/integrations/slack_adapter.py` 实现以下对应关系：

| 本地概念 | Slack 真实接口或字段 | 适配时必须处理 |
|---|---|---|
| 授权开始 | `https://slack.com/oauth/v2/authorize` | client_id、scope、redirect_uri、state，绑定浏览器会话 |
| 兑换/刷新 | `https://slack.com/api/oauth.v2.access` | form 编码；code 或 refresh_token；client_id/client_secret；检查 ok |
| 列表读取 | `https://slack.com/api/conversations.history` | Bearer token、channel、cursor、时间边界 |
| 下一页 | `response_metadata.next_cursor` | 原样传回；不能拿数组长度判断结束 |
| 消息身份 | workspace/team ID + channel ID + `ts` | 将 ts 保留为字符串，避免浮点精度丢失 |
| 限流 | HTTP 429 + `Retry-After` | 按方法/安装控制请求；等待后重试同一页 |
| 事件身份 | `team_id` + `event_id` | 验签、持久 inbox、唯一约束 |
| 编辑/删除 | `message_changed` / `message_deleted` | 按事件文档取原消息身份，不套用模拟器 revision |

授权流程见 [OAuth 安装](https://docs.slack.dev/authentication/installing-with-oauth/)，事件映射见 [message_changed](https://docs.slack.dev/reference/events/message/message_changed/)和 [message_deleted](https://docs.slack.dev/reference/events/message/message_deleted/)。表格是接入契约，不是可直接发送的完整请求体。

把这个任务交给 coding agent：

```text
在现有 FastAPI 项目实现 Slack 测试工作区的只读资料接入，不新建完整应用。
配置通过环境读取 SLACK_CLIENT_ID、SLACK_CLIENT_SECRET、SLACK_SIGNING_SECRET、
SLACK_REDIRECT_URI、SLACK_TEST_CHANNEL_ID。不要在日志或报告输出凭证。
路由：GET /integrations/slack/install 产生会话绑定 state 并重定向；
GET /integrations/slack/callback 核对 state、处理用户拒绝、服务端兑换 code 后保存安装；
POST /integrations/slack/events 按步骤 4 验签并持久入 inbox。
实现 slack_adapter.py：auth.test 确认安装；conversations.history 全部分页只读同步；
按 expires_in 提前刷新，按安装保存整对令牌；HTTP 非 2xx 和 JSON ok=false 分别处理。
同步用固定 oldest/latest 时间窗、稳定消息主键，完成整窗后提交检查点；
编辑/删除事件按官方字段更新镜像。不要把 Slack ts 直接当完整修改版本协议。
用本地假 HTTP 响应测试两页、429、过期令牌、撤销授权和签名失败。
按步骤 6 的人工清单配合实连，证据只记录状态、条数和脱敏标识；不发送业务消息。
提供实际启动命令和接口测试命令；未配置账号的检查保持未验证，不能静默切换为 mock。
```

**人工实连按顺序做：**

1. 用已有 HTTPS 开发回调地址映射到 FastAPI 服务，把完全相同的 OAuth callback URL 填进 App 设置。浏览器打开你自己的 `/integrations/slack/install`，在 Slack 页面授权，回调完成后确认服务端记录了安装。拒绝授权也应显示可理解的状态。
2. 用刚得到的 token 调 `auth.test`，核对工作区；读取目标频道，确认两条测试消息可定位。分页验证使用本地假两页响应；如真实响应有游标，再记录真实第二页，不能故意刷 API 制造 429。[auth.test](https://docs.slack.dev/reference/methods/auth.test/)。
3. 对新测试 App 启用轮转并按 OAuth 流程重新安装；如果启用前已有长期 token，按官方迁移文档使用 `oauth.v2.exchange`。实际刷新一次，确认新 token 可读同频道；不要在短时间反复刷新。[Token rotation](https://docs.slack.dev/authentication/using-token-rotation/)。
4. 在 Event Subscriptions 配置 HTTPS `/integrations/slack/events`，处理 URL verification，订阅测试公开频道的 `message.channels` 事件；App 应已加入频道。[message.channels](https://docs.slack.dev/reference/events/message.channels/)。
5. 人工修改或删除一条测试消息，确认入库事件更新了对应镜像；保存的脱敏样本用于本地重投，不能绕过验签。重启服务后再检查去重持久性。

### 可能卡在哪

**没有工作区安装权限或回调 HTTPS。** 继续完成本地适配器测试，把缺少的条件写到证据表中；不要宣称“已完整接入”。平台管理步骤可能超过这一节预算，恢复环境后继续人工清单。

**读取普通消息成功，但线程/编辑/删除都没覆盖。** 在 `contract.md` 写清本次只支持的记录类型。只有相应真实事件经过适配器并改变镜像，才能勾选该项；完整线程同步需要 `conversations.replies` 的权限与分页，不能默认算上。

### 背后的逻辑

可以复用的是失败恢复策略；授权字段、业务身份、更新语义、权限与事件格式属于供应商协议，必须由适配层明确转换。

## 验收与证据表

在 `s2-agent/integrations/evidence.md` 填写实际状态。`本地通过`、`Slack 实连通过`、`未验证` 是不同结论：

| 验收项 | 本地故障注入 | Slack 实连 |
|---|---|---|
| OAuth 会话绑定、过期与重放拒绝 | 运行记录 | 授权回调记录 |
| access/refresh token 轮转 | 旧令牌拒绝，检查点不乱动 | 一次真实刷新与后续只读请求 |
| 全部分页、429 有界等待 | 两页、空页、重复游标、重试预算 | 真实分页如有；不主动制造限流 |
| 原始请求体验签与事件去重 | 改字节、过期、重启后重投 | 真实事件签名与持久 inbox |
| 增量、删除与事务恢复 | 崩溃回滚、tombstone、旧事件 | 目标消息新增/编辑/删除对应记录 |
| 接到主线笔记 Agent | 来源有稳定 ID 与可追溯路径 | Agent 能只读检索测试资料 |

本仓库自带示例已运行通过步骤 1 列出的输出；**没有使用真实 Slack 凭证，没有验证工作区权限、公开 HTTPS 回调或厂商实际投递**。你需用自己的实连证据完成右列。

## 你必须懂的 6 个问题

1. state、access token、refresh token 各解决什么问题？分别什么时候失效？
2. 为什么本轮拿到空数组仍可能要继续请求下一页？
3. 把 JSON 解析后重新序列化，为什么可能让验签失败？
4. 为什么“事件已收到”不等于“全部历史数据已同步到这个时间”？
5. 插入去重记录成功、业务处理失败，事务或 inbox worker 应怎样保证可重试？
6. 模拟器的 revision、Slack 的 ts、编辑事件时间各代表什么？哪些不能直接互换？
