# U2.6 · 多 Agent 编排（10 小时）

**这个单元解决什么问题**

「多 Agent 架构」听起来很高级，所以很多人一上来就拆。**这个单元的目标不只是教你怎么拆，更重要的是让你有能力判断该不该拆。**

**必读**：Anthropic《[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)》（2025-06-13）。它讲了 orchestrator 和 subagent 的分工、上下文隔离的价值，以及多 Agent 的真实成本代价。

**学完你能做到**：实现两种多 Agent 模式；**用数据决定你的项目拆不拆**——而且「不拆」是一个完全合格的结论。

## 步骤 1 · 先搞清楚多 Agent 到底解决什么

### 这一步在做什么

多 Agent 的价值只有一个真正的来源，其余都是附带的。

### 核心价值：上下文隔离

假设你的任务是「调研三个竞品并对比」。

**单 Agent 的上下文**：

```
系统提示
工具定义
调研竞品A：搜索 → 20 条结果 → 读详情 → 5 篇长文
调研竞品B：搜索 → 20 条结果 → 读详情 → 5 篇长文
调研竞品C：搜索 → 20 条结果 → 读详情 → 5 篇长文
现在做对比
```

**到最后一步时，上下文里塞满了三轮调研的全部原始过程。** 回想 U1.5 的实验：这么长的上下文，模型的表现会明显下降。

**多 Agent 的上下文**：

```
主 Agent 的上下文：
  系统提示
  「已派三个子任务，返回结果：
   竞品A 摘要（300字）
   竞品B 摘要（300字）
   竞品C 摘要（300字）」
  现在做对比

每个子 Agent 的上下文（独立）：
  系统提示（专注于调研一个竞品）
  搜索 → 结果 → 读详情 → 长文
  产出摘要
```

**主 Agent 只看到三份摘要，干净。子 Agent 各自有充足的空间做深入探索。**

### 第二个价值：并行

三个子 Agent 可以同时跑，总耗时约等于最慢的那个，而不是三个之和。

### 真实的代价

| 代价 | 说明 |
|---|---|
| **Token 成本通常是数倍** | 每个子 Agent 都要重新建立自己的上下文（系统提示、工具定义都要重发） |
| **协调开销** | 主 Agent 要拆任务、派发、汇总，这些都是额外调用 |
| **错误传播** | 一个子 Agent 出错，主 Agent 可能不知道，基于错误结果继续 |
| **调试困难** | 出问题时要在多个执行流里找 |
| **结果冲突** | 两个子 Agent 给出矛盾的结论，谁对 |

### 判断标准

**该拆的信号**：

- 子任务之间**相对独立**（不需要互相看中间过程）
- 单个子任务的**探索过程很长**（会产生大量中间上下文）
- 子任务可以**并行**，且延迟敏感

**不该拆的信号**：

- 子任务之间**紧密耦合**（B 需要 A 的详细过程，不只是结论）
- 每个子任务**很短**（拆分开销大于收益）
- **成本敏感**
- 任务本身就是线性的

### 背后的逻辑

**多 Agent 是上下文工程在架构层面的应用。**

U1.5 讲的是「在一个上下文里怎么取舍」，多 Agent 讲的是「把一个上下文拆成几个」。**底层是同一个问题：注意力预算不够用。**

**理解这一点，你就不会为了「架构高级」而拆。** 拆的唯一理由是上下文装不下或者会被稀释。

## 步骤 2 · Orchestrator-Worker 模式

### 这一步在做什么

实现最常用的一种：主 Agent 拆任务，子 Agent 干活，主 Agent 汇总。

### 怎么做

```python
class SubTask(BaseModel):
    id: str
    # 子 Agent 看不到主 Agent 的上下文，description 是它唯一的信息来源，所以必须自包含
    description: str = Field(description="子 Agent 要完成什么，要自包含")
    required_tools: list[str]
    expected_output: str = Field(description="子 Agent 应该返回什么格式的结果")


class DecompositionResult(BaseModel):
    can_parallelize: bool
    # 卡上限，避免模型把任务拆得太碎：拆分开销会吃掉上下文隔离带来的那点收益
    subtasks: list[SubTask] = Field(max_length=5)


async def orchestrator(user_input: str):
    # 1. 拆任务。能不能并行交给模型判断，不写死——有依赖的任务串行跑才对
    decomposition = await structured_call(DECOMPOSE_PROMPT + user_input, DecompositionResult)
    logger.info("拆成 %d 个子任务，并行=%s", len(decomposition.subtasks), decomposition.can_parallelize)

    # 2. 派发。return_exceptions=True 是关键：一个子任务炸了不会连带取消其他人
    if decomposition.can_parallelize:
        results = await asyncio.gather(*[
            run_subagent(t) for t in decomposition.subtasks
        ], return_exceptions=True)
    else:
        # 串行分支把已完成的结果传给下一个子任务，供有依赖的拆分使用
        results = []
        for t in decomposition.subtasks:
            results.append(await run_subagent(t, prior_results=results))

    # 3. 分离成功和失败。失败项要带上原任务，汇总时才知道到底缺了哪一块
    succeeded = [r for r in results if not isinstance(r, Exception)]
    failed = [(t, r) for t, r in zip(decomposition.subtasks, results) if isinstance(r, Exception)]
    for t, e in failed:
        logger.error("子任务 %s 失败：%s", t.id, e)

    # 4. 汇总时把失败清单一起交给主 Agent，由它决定重试、跳过，还是如实告诉用户
    return await synthesize(user_input, succeeded, failed)


async def run_subagent(t: SubTask, prior_results=None) -> str:
    """跑一个子 Agent：上下文独立、工具受限、护栏比主 Agent 更严。"""
    subagent = Agent(
        llm=llm,
        tool_registry=tool_registry.subset(t.required_tools),      # 只给它需要的工具，省上下文也降低选错工具的概率
        system_prompt=f"你负责一个子任务。{t.description}\n\n产出要求：{t.expected_output}",
        guardrails=Guardrails(max_turns=8, max_total_cost=0.5),    # 三个子 Agent 各跑 15 轮的话总成本会爆
    )
    r = await subagent.run(t.description)
    return r.answer
```

### 四个关键设计点

**一、子任务描述必须自包含。**

子 Agent 看不到主 Agent 的上下文（这正是隔离的意义），所以任务描述里必须包含它需要知道的一切。

**二、只给子 Agent 它需要的工具。**

用 U2.2 学的分组。这既省上下文，又降低它调错工具的概率。

**三、子 Agent 的护栏要更严。**

主 Agent 允许 15 轮，子 Agent 给 8 轮就够。**否则三个子 Agent 各跑 15 轮，总成本会爆。**

**四、必须处理部分失败。**

`return_exceptions=True` 让一个失败不影响其他。汇总时要告诉主 Agent 哪些失败了，让它决定是重试、跳过、还是告诉用户。

### 可能卡在哪

**拆出来的子任务不合理**

在拆分 prompt 里给例子，说明什么样的拆分是好的。限制 `max_length=5` 避免拆得太碎。

**子 Agent 返回的东西格式不一**

在 `expected_output` 里明确格式，或者直接用结构化输出约束子 Agent 的返回。

**成本失控**

给每个子 Agent 设费用上限，并且主 Agent 也要有总预算。**在派发前先估算：子任务数 × 单个上限 ≤ 总预算。**

**并行时限流了**

用 U1.2 学的 Semaphore 控制同时跑的子 Agent 数量。

### 背后的逻辑

这个模式对应人类组织里的「项目经理 + 执行者」。

**它的成立条件和现实中一样**：任务能被清晰拆分、执行者能独立完成、结果能被汇总。

**任何一条不成立，这个模式就会失效**——就像现实中，如果任务拆不清楚，加人只会更慢。

## 步骤 3 · Handoff 模式

### 这一步在做什么

实现另一种：Agent 判断这事该另一个 Agent 管，把控制权交出去。

### 和 Orchestrator 的区别

| | Orchestrator-Worker | Handoff |
|---|---|---|
| 控制权 | 主 Agent 始终持有 | **完全转移** |
| 子 Agent 结束后 | 返回给主 Agent | 直接面对用户，或再转给别人 |
| 适合 | 任务分解 | **领域路由** |

**Handoff 的典型场景是客服**：通用助手判断这是技术问题 → 转给技术 Agent；技术 Agent 判断这需要退款 → 转给售后 Agent。

### 怎么做

把「转交」实现成一个特殊的工具：

```python
class HandoffArgs(BaseModel):
    # 目标用英文标识符，和 agents 字典的键一一对应；中文含义写在 description 里给模型看
    target_agent: Literal["tech_support", "after_sales", "sales"] = Field(
        description="转给谁：tech_support 技术支持 / after_sales 售后处理 / sales 销售咨询"
    )
    reason: str = Field(description="为什么要转交")
    context_summary: str = Field(description="给下一个 Agent 的交接说明，要自包含")


async def handoff(p: HandoffArgs) -> dict:
    # 转交不产出业务结果，只返回一个带哨兵键的信号，由 Agent 循环识别并结束本轮
    return {"__handoff__": p.target_agent, "summary": p.context_summary, "reason": p.reason}
```

在 Agent 循环里检测这个特殊返回：

```python
result = await self._execute_one(tc)
# 命中哨兵键就直接跳出循环：控制权连同交接摘要一起交出去，不再继续本 Agent 的推理
if isinstance(result, dict) and "__handoff__" in result:
    return RunResult(None, turn, total_cost, "handoff", history,
                     handoff_to=result["__handoff__"], summary=result["summary"])
```

外层调度：

```python
async def run_with_handoff(user_input: str, max_handoffs: int = 3):
    """一直跑到某个 Agent 给出答案，或转交次数用完为止。"""
    current = "general"
    agent_input = user_input
    handoff_chain = [current]

    # 用次数上限打断 A 转 B、B 又转回 A 这类互相踢皮球的死循环
    for _ in range(max_handoffs):
        r = await agents[current].run(agent_input)
        if r.stop_reason != "handoff":
            return r, handoff_chain
        current = r.handoff_to
        # 下一个 Agent 只看得到摘要，所以把原始请求一并带上，避免关键信息在交接中丢失
        agent_input = f"[从 {handoff_chain[-1]} 转来]\n{r.summary}\n\n原始请求：{user_input}"
        handoff_chain.append(current)
        logger.info("转交链：%s", " → ".join(handoff_chain))

    # 超限直接抛错，而不是静默返回半成品——转交链本身就是排查线索
    raise RuntimeError(f"转交次数超限：{handoff_chain}")
```

### 三个必须处理的问题

**一、转交次数上限。** 否则 A 转 B、B 转回 A 会无限循环。

**二、交接摘要的质量。** 下一个 Agent 只看到摘要，摘要写得差它就抓瞎。**在参数描述里强调「自包含」。**

**三、转交链要记录。** 出问题时要能看到「用户的请求转了几手」。

### 可能卡在哪

**Agent 太爱转交了**

在每个 Agent 的系统提示里明确它自己的能力范围，并说明「只有确实超出你的范围才转交」。

**转交后信息丢失**

除了摘要，可以把关键的原始信息（用户的第一条输入、关键的工具返回）也传过去。**权衡：传得越多越准，但隔离的价值就越小。**

### 背后的逻辑

Handoff 和 Orchestrator 的本质区别是**控制流的形状**：

- Orchestrator 是**树**：主 → 子 → 回到主
- Handoff 是**链**：A → B → C

**树适合「一件事拆成几部分」，链适合「一件事在不同阶段需要不同专长」。**

你的项目可能两种都需要，也可能一种都不需要。

## 步骤 4 · 做对比实验

### 这一步在做什么

**本单元最重要的一步。用数据回答「该不该拆」。**

### 怎么做

从你的项目里挑一个**复杂的子任务**（多步、会产生大量中间上下文的那种）。

三个版本：

1. **单 Agent**（U2.1/U2.3 已有的）
2. **Orchestrator-Worker**
3. **单 Agent，但加上下文压缩**（U1.5 学的策略）

**第 3 个版本很关键。** 因为多 Agent 的主要价值是上下文隔离，而上下文压缩也能达到类似效果，成本却低得多。**如果压缩就够了，就不需要多 Agent。**

用 10 个任务测：

| 方案 | 成功率 | 总 token | 总成本 | 耗时 | 最大单次上下文 |
|---|---|---|---|---|---|
| 单 Agent | /10 | | ¥ | s | |
| 单 Agent + 上下文压缩 | /10 | | ¥ | s | |
| Orchestrator-Worker | /10 | | ¥ | s | |

### 怎么读这张表

**如果多 Agent 的成功率明显更高**（比如 8/10 vs 5/10），而且成本能接受，那就拆。

**如果差不多**（8/10 vs 7/10），但成本是 3 倍，**那就别拆**。

**如果「单 Agent + 压缩」就达到了多 Agent 的效果**，那压缩是更优解——更便宜、更简单、更好调试。

### 诚实地下结论

**「我测过，不拆更好」是一个完全合格、而且很有说服力的结论。**

面试时这样讲：

> 我实现了 orchestrator-worker，也测了单 Agent 加上下文压缩。在我的场景下，多 Agent 的成功率是 8/10，单 Agent 加压缩是 7/10，但多 Agent 的成本是 3.2 倍、延迟是 1.8 倍。考虑到我的场景对成本敏感、对延迟敏感，我最终选择了单 Agent 加压缩，把多 Agent 的实现保留在代码里，等任务复杂度上升到某个阈值再启用。

**这段话展示的判断力，比「我用了多 Agent 架构」强得多。**

### 可能卡在哪

**测不出差异**

任务可能不够复杂。**多 Agent 的价值只在上下文压力大时才体现。** 找一个真的会产生大量中间内容的任务。

**多 Agent 版本一直失败**

先看子 Agent 单独跑得对不对。**分层排查：先确认每个子 Agent 能独立完成任务，再看拆分和汇总。**

### 背后的逻辑

这个实验的方法论和 U1.4、U2.3 一脉相承：**控制变量、量化对比、看失败细节。**

到这里你应该已经形成了一个习惯：**任何架构决策都要有数据支持。**

**这就是 S3 存在的意义**——把这种手工对比升级成自动化的、可重复的评估体系。你现在每做一次实验都很费劲，S3 之后跑一个命令就行。
