# U2.4 · 记忆系统（10 小时）

**这个单元解决什么问题**

现在你的 Agent 是「金鱼」——每次新会话从零开始，用户上周说过的偏好它完全不知道。

这个单元让它记住东西。但**难点不是「存下来」，而是「记住对的东西、在对的时候想起来、在事实变了时更新」。**

**学完你能做到**：跨会话的记忆；处理事实冲突和时效性；知道什么该记什么不该记。

---

## 步骤 1 · 分清三种记忆

### 这一步在做什么

**很多人把「记忆」当成一个东西，其实是三个，存储和检索方式完全不同。**

### 三种记忆

| 类型 | 是什么 | 存哪 | 生命周期 | 例子 |
|---|---|---|---|---|
| **短期记忆** | 当前会话的消息历史 | 内存 / Redis | 会话结束就没 | 「你刚才说的那个链接」 |
| **工作记忆** | 当前任务的中间状态 | 任务状态表 | 任务结束就没 | 「已完成第 3 步，拿到了 23 条数据」 |
| **长期记忆** | 跨会话的用户事实和偏好 | 数据库 | 长期，需要更新和淘汰 | 「用户只做家电类目」 |

### 为什么必须分开

因为它们的**检索方式**完全不同：

- **短期**：全量带上（或按 U1.5 的策略压缩）
- **工作**：结构化读取，不进上下文，由代码使用
- **长期**：**按当前话题检索相关的几条**，不能全量带

**新手最常犯的错是把长期记忆当短期用**——把所有记忆全塞进系统提示。用户用了三个月之后，记忆库有 500 条，全塞进去就爆了，而且大部分跟当前话题无关，纯属噪音。

### 可能卡在哪

**工作记忆和短期记忆有什么区别**

短期记忆是「对话内容」，工作记忆是「任务进度」。

一个任务可能跨多轮对话（用户中途问了别的），工作记忆记录的是「这个任务做到哪了」，和对话内容是两回事。

**S4 的断点续跑依赖工作记忆。** 现在把它单独存起来，到时候直接能用。

## 步骤 2 · 长期记忆：写什么

### 这一步在做什么

**关键判断：不是所有对话都值得存。**

### 错误做法

把每轮对话都存进记忆库。后果是：记忆库爆炸、检索时全是噪音、成本失控。

### 正确做法：提取式写入

每轮对话后，用一次便宜的调用判断「这里面有值得长期记住的事实吗」：

```python
class MemoryItem(BaseModel):
    """一条长期记忆。字段设计的目的是让每条记忆能被单独检索、单独判断是否还有效。"""

    # 四个类别对应 prompt 里的「偏好 / 事实 / 约束 / 目标」，
    # 用英文值是为了后面检索时按类别过滤（见步骤 3 的分类注入）
    category: Literal["preference", "fact", "constraint", "goal"]
    content: str = Field(description="一句话，自包含，脱离上下文也能理解")
    # confirmed = 用户明说的；inferred = 模型推断的。
    # 分开标记，才能对推断结果采取更保守的用法（比如先向用户确认）
    confidence: Literal["confirmed", "inferred"]
    source: str = Field(description="来自哪次对话")
    # 有时效的信息（截止日期、本季度预算）到期后要停止注入，
    # 没有时效的留空，不要强行编一个日期
    valid_until: date | None = Field(default=None, description="如果这是有时效的信息")


# 提取用的 prompt：正面清单 + 反面清单一起给，
# 只给正面清单模型会把一次性请求也当成偏好记下来
EXTRACTION_PROMPT = """
从下面的对话里提取值得长期记住的信息。只提取：

- 偏好：用户明确表达的喜好、习惯、风格要求
- 事实：关于用户或其业务的稳定事实
- 约束：用户明确的限制条件（预算、时间、不做什么）
- 目标：用户想达成的中长期目标

不要提取：
- 一次性的任务请求
- 可以随时重新查到的信息
- 你的推测（除非标记为推测）
- 寒暄和情绪表达

如果没有值得记的，返回空列表。
"""
```

**「如果没有值得记的，返回空列表」这句话很重要。** 不写的话，模型会觉得「必须提取点什么」，然后编出一堆垃圾。

### 内容必须自包含

```
差：「他更喜欢第二个方案」        ← 脱离上下文没有意义
好：「用户偏好简洁的标题风格，不喜欢用感叹号和夸张词」
```

**检验标准**：三个月后你单独看到这一条，还能理解吗？

### 可能卡在哪

**提取出来的都是废话**

改 prompt，加更多「不要提取」的例子。或者加一个二次筛选：提取后再判断一次「这条真的值得存吗」。

**每轮都调一次模型，成本受不了**

三个优化：

1. 用小模型（U1.7 测过，这类抽取任务小模型够用）
2. 不是每轮都跑，会话结束时统一跑一次
3. 先用规则粗筛（含「我喜欢」「不要」「必须」「预算」等关键词的才送去提取）

### 背后的逻辑

这个设计的核心是**把「记忆」当成一种有成本的资源来管理**，而不是「能存就存」。

类比人的记忆：你不会记住今天早上第三个红绿灯是什么颜色，但你会记住「这条路早高峰堵」。**区别在于「是否对未来的决策有用」。**

**同样的判断标准用在这里**：这条信息会影响未来的决策吗？会才存。

## 步骤 3 · 长期记忆：怎么找回来

### 这一步在做什么

新会话开始时，把相关的记忆捞出来注入上下文。

### 三种检索方式

**方式一：全量注入（记忆少时可用）**

```python
# 记忆很少时不必检索，全量拼进上下文最省事也最不容易漏
if memory_count < 20:
    context += format_all_memories()
```

简单可靠。**但记忆超过 20 条就不行了**，会占太多上下文且稀释注意力。

**方式二：向量检索（记忆多时）**

把每条记忆做 embedding，按当前话题检索最相关的 top-K。

**这需要 U2.5 的检索能力**，可以先跳过，等 U2.5 做完再回来。

**方式三：分类注入（实用的折中）**

```python
# 「约束」和「偏好」类的永远注入（数量少，且总是相关）
always_included = [m for m in memories if m.category in ("constraint", "preference")]

# 「事实」类的数量会随时间涨，只按当前话题捞最相关的几条，
# 全量带上会稀释注意力（U1.5 的同一个问题）
related_facts = search_memories(current_topic, category="fact", top_k=5)
```

**大多数项目用方式三就够了。** 约束和偏好通常只有几条，而且总是相关。

### 可能卡在哪

**注入的记忆模型不用**

在系统提示里明确说明这是什么：

```
## 关于这位用户你已知的信息
（下面是从历史对话中积累的信息，请在回答时考虑它们）
- [约束] 只做家电类目
- [偏好] 标题风格简洁，不用感叹号
```

**加上类型标签**，比一堆无标记的句子有效。

**记忆和用户当前说的矛盾**

**以用户当前说的为准，并更新记忆。** 见下一步。

### 背后的逻辑

检索式记忆和全量记忆的区别，本质上是 U1.5 上下文工程的又一次应用：**在有限的注意力预算里，只放最相关的。**

**这也是为什么记忆条目要「自包含」**——因为它会被单独检索出来，脱离原始上下文。

## 步骤 4 · 处理事实冲突

### 这一步在做什么

用户上周说喜欢 A，这周说喜欢 B。怎么办？

### 错误做法

直接覆盖。问题是：

- 丢失了历史，无法回答「我什么时候改的主意」
- 如果新信息是错的（比如用户说错了），没法回退
- 无法区分「改变了」和「补充了」

### 正确做法：追加 + 版本

```python
class MemoryItem(BaseModel):
    """加上时态字段后的记忆条目：旧记忆不删除，只标记「什么时候被谁取代的」。"""

    id: str
    category: str
    content: str
    created_at: datetime
    superseded_at: datetime | None = None  # 被后续记忆取代时填上，None 表示当前仍有效
    superseded_by: str | None = None       # 指向取代它的那条记忆，用来追溯改动链
    source: str
```

写入新记忆时，先判断它和已有记忆的关系：

```python
async def write_memory(new_item: MemoryItem):
    """写入前先判断新记忆和旧记忆的关系，避免同一件事留下两条互相矛盾的记录。"""

    # 阈值 0.8 只是起点：调高会漏掉该取代的，调低会把不相干的记忆判成冲突，
    # 用自己的数据试出来的值才算数
    related_old_items = await find_similar_memories(new_item.content, threshold=0.8)

    if related_old_items:
        # 关系交给模型判断：supersede（同一维度上不一致）/ extend（新增维度）/ unrelated
        relation = await judge_relation(old=related_old_items, new=new_item)

        if relation == "supersede":
            # 只标记失效，不删除——用户可能回头问「我上个季度的预算是多少」
            for old_item in related_old_items:
                old_item.superseded_at = now()
                old_item.superseded_by = new_item.id
            logger.info("记忆 %s 取代了 %s", new_item.id, [m.id for m in related_old_items])

    # extend 和 unrelated 都直接追加，新旧共存
    await save_memory(new_item)
```

**检索时只返回未失效的**，但历史留着。

### 处理时效性

有些记忆天生有有效期：

```
「项目截止日期是 3 月 1 日」     ← 3 月 2 日就该失效
「这个季度的预算是 5 万」        ← 季度结束就该失效
「我下周要出差」                ← 下周结束就失效
```

在提取时就识别出来并标记 `valid_until`。检索时过滤掉过期的。

**过期的不要直接删**，标记为过期即可，因为用户可能问「我上个季度的预算是多少」。

### 可能卡在哪

**判断「取代还是补充」很难**

给模型明确的判断标准和例子：

```
取代：新信息和旧信息在同一维度上不一致
  旧「只做家电类目」+ 新「现在也做家居了」→ 取代（类目范围变了）

补充：新信息增加了旧信息没有的维度
  旧「只做家电类目」+ 新「预算每月 5000」→ 补充（不同维度）

无关：两条信息没关系
```

**用户没明说改变，但事实上变了**

比如用户一直在问家居相关的问题，但从没说「我现在也做家居了」。

**这属于推断，风险较高。** 保守做法是标记为「推测」类型，并在合适的时候向用户确认。

### 背后的逻辑

这个设计借鉴了数据库的「软删除」和「时态数据」思想：**不删除，只标记失效，保留完整历史。**

好处是：

- 可审计（能回答「这条记忆是什么时候、因为什么改的」）
- 可回退（发现改错了能恢复）
- 可分析（能看出用户的偏好如何演变）

**在 Agent 场景里，可审计性尤其重要。** 当 Agent 做出一个奇怪的决策时，你需要能查出「它当时基于哪些记忆」。

## 步骤 5 · 遗忘机制

### 这一步在做什么

防止记忆库无限膨胀并稀释检索质量。

### 三种淘汰策略

**一、按访问频率**

记录每条记忆被检索命中的次数和最后命中时间。长期不被命中的降权或归档。

```python
async def archive_stale_memories():
    """定期把「长期没被检索命中」的记忆降级为归档，减少检索时的噪音。"""

    # 两个条件要一起用：只看命中次数会误伤刚写入的新记忆，
    # 只看时间会归档掉那些低频但每次都关键的记忆
    candidates = await query_memories(
        last_hit_at__before=now() - timedelta(days=90),
        hit_count__lt=2,
    )
    # 归档不是删除：主检索捞不到时还能去归档区兜底找一遍
    for m in candidates:
        m.status = "archived"
```

**二、按类型的自然生命周期**

| 类型 | 建议保留 |
|---|---|
| 约束、偏好 | 长期（除非被取代） |
| 事实 | 中期，定期复核 |
| 目标 | 达成或过期后归档 |
| 一次性信息 | 本来就不该存 |

**三、合并相似记忆**

```
「用户喜欢简洁的标题」
「用户不喜欢标题里用感叹号」
「用户觉得夸张的形容词很俗」
     ↓ 合并
「用户偏好简洁克制的标题风格：不用感叹号、不用夸张形容词」
```

定期跑一次合并，能显著减少条目数。

### 可能卡在哪

**归档了之后用户提到相关的事怎么办**

归档不是删除。检索时可以设一个「扩展检索」：主检索没找到相关的，再去归档区找一遍。

**合并把不同的意思揉在一起了**

合并是有损的。**建议只合并高度相似的**（向量相似度 0.9 以上），并且保留原始条目的引用。

### 背后的逻辑

**记忆系统的健康度指标是「信噪比」，不是「容量」。**

500 条记忆里 450 条是噪音，比 30 条精准记忆差得多——因为检索会把噪音捞上来，占据上下文并误导模型。

**这和 U1.5 的核心命题是同一个**：不是能塞多少，而是塞什么最有用。
