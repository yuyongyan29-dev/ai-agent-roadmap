## 步骤 1 · 定一个统一的测试任务

### 先看清你在比较什么

```
抽象程度                                        你要付出的
   低  ┌──────────────────────────────┐  控制力最强
   ▲   │ 你手写的循环（U2.1）           │  边界情况全自己处理
   │   │ 200 行，每行你都懂             │  持久化/中断/流式都要自己写
   │   └──────────────────────────────┘
   │   ┌──────────────────────────────┐
   │   │ smolagents                   │  能读完源码
   │   │ 极简，核心几百行               │  但缺持久化
   │   └──────────────────────────────┘
   │   ┌──────────────────────────────┐
   │   │ OpenAI Agents SDK            │  概念少：agent/tool/
   │   │ 抽象轻                        │  handoff/guardrail/session
   │   └──────────────────────────────┘
   │   ┌──────────────────────────────┐
   ▼   │ LangGraph                    │  显式状态图
   高  │ 概念多，但持久化/中断/流式齐全  │  学习成本最高
       └──────────────────────────────┘

框架真正替你做的不是「主循环」（那和你写的差不多），
而是：持久化、中断恢复、流式、可观测性接入、边界情况。
你的测试任务必须覆盖这些，否则比不出差别。
```



### 这一步在做什么

三个框架实现同一件事，才能公平比较。

### 怎么做

从你项目里选一个**真实但不太大**的场景，要求：

- 需要 3 到 5 步
- 用到至少 3 个工具
- **有一个需要人工确认的高危动作**（比如「发布」「删除」）
- 中间会产生较多上下文

**「需要人工确认」这一条很关键**，因为它会暴露各框架在「中断和恢复」上的差异——**这正是生产环境最需要的能力。**

写下这个任务的规格：

```markdown
## 测试任务规格
输入：（用户会说什么）
期望流程：
  1. 调用工具 A 获取...
  2. 基于结果判断...
  3. 调用工具 B...
  4. **请求人工确认**
  5. 确认后调用工具 C 执行
输出：（最终应该返回什么）
必须验证：
  - 中途 kill 进程，重启后能续上
  - 人工确认能正常暂停和恢复
  - 流式能看到中间过程
```

## 步骤 2 · 三个框架各实现一遍

### 这一步在做什么

动手。每实现完一个，立刻记录感受，不要等三个都做完再回忆。

### LangGraph 的核心概念

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Annotated
import operator


class AgentState(TypedDict):
    """整张图共享的状态。Annotated 的第二个参数声明「这个字段被更新时怎么合并」。"""
    messages: Annotated[list, operator.add]   # operator.add 表示列表相加，即追加而不是覆盖
    confirmed: bool                           # 没有 Annotated 的字段默认覆盖


def call_model(state: AgentState) -> dict:
    """调模型的节点。节点返回的是「对状态的更新」，不是完整的新状态。"""
    ...
    return {"messages": [new_message]}        # 只返回增量，框架按上面声明的规则合并


def route_next(state: AgentState) -> str:
    """条件边：读当前状态，决定下一个节点，返回节点名或 END。"""
    if needs_confirmation(state):
        return "await_confirmation"           # 高危动作先停下等人确认，不直接执行
    if has_tool_calls(state):
        return "run_tools"
    return END


graph = StateGraph(AgentState)
graph.add_node("model", call_model)
graph.add_node("run_tools", run_tools)
graph.add_conditional_edges("model", route_next)   # 出边由函数动态决定，构成分支
graph.add_edge("run_tools", "model")               # 工具跑完固定回到模型，形成主循环
graph.set_entry_point("model")

# checkpointer 把每一步的状态落盘，进程被 kill 后能从断点续跑
# interrupt_before 让图在进入 run_tools 之前暂停，人工确认后再恢复执行
app = graph.compile(checkpointer=your_checkpointer, interrupt_before=["run_tools"])
```

**重点体验这三个**：

1. `checkpointer` 怎么让状态持久化
2. `interrupt_before` 怎么实现人工确认
3. `Annotated[list, operator.add]` 这种「状态合并规则」的设计

### OpenAI Agents SDK 的核心概念

```python
from agents import Agent, Runner, function_tool


# @function_tool 直接从函数签名和 docstring 生成给模型看的 schema，
# 所以参数名、类型标注和 docstring 都是写给模型的提示，要写得能让它判断何时调用
@function_tool
def search_notes(keyword: str, limit: int = 10) -> str:
    """在笔记库搜索。..."""
    ...


agent = Agent(
    name="选题助手",                      # 这个名字会出现在 tracing 和 handoff 记录里
    instructions="...",                  # 相当于 system prompt
    tools=[search_notes, read_detail],
)

# Runner 负责跑完整个「模型 → 工具 → 模型」的循环，直到模型不再要求调用工具
result = await Runner.run(agent, "帮我找家电选题")
```

**重点体验**：抽象有多少、自带的 tracing 长什么样、handoff 怎么用。

### Claude Agent SDK 的核心概念

**重点体验**：它对 MCP 的集成有多深、内置的文件和命令行工具怎么用、权限控制怎么做。

### 可能卡在哪

**框架的文档和实际 API 对不上**

这个领域迭代很快，**教程和博客经常过时**。**永远以官方文档的当前版本为准**，并且注意文档页上标的版本号。

**LangGraph 的状态合并搞不懂**

关键理解：节点函数返回的是「对状态的更新」，不是完整的新状态。`Annotated[list, operator.add]` 的意思是「这个字段的更新方式是列表相加」，所以返回 `{"messages": [new_message]}` 会追加而不是覆盖。

不加 `Annotated` 的字段默认是覆盖。

**某个框架实在写不出来**

给自己定个时间盒：每个框架 3 小时。**写不出来就记录「上手难度高」，这本身就是评估结果。**

## 步骤 3 · 六项对比

### 这一步在做什么

**结构化地记录，而不是凭印象。**

### 每个框架回答这六个问题

**一、状态存在哪，怎么持久化？**

- 状态的数据结构是什么
- 存到数据库要写多少代码
- 支持哪些存储后端

**二、能不能从任意一步恢复？**

**实际测试**：跑到第 3 步，`kill -9`，重启，能续上吗？

这是生产环境的硬需求（S4 的 U4.2）。

**三、怎么实现人工确认？**

- 有没有内置的中断机制
- 暂停后状态怎么保存
- 恢复时怎么把用户的决定传进去

**四、流式怎么做？**

- 能流式输出模型的文本吗
- 能流式输出「正在调用某工具」这类事件吗
- 前端拿到的数据结构是什么

**这决定了 S5 前端能做到什么程度。**

**五、工具出错怎么恢复？**

- 异常是往上抛还是回填给模型
- 能不能自定义重试策略
- 有没有降级机制

**六、可观测性怎么接？**

- 有没有内置 tracing
- 能不能接 OpenTelemetry / Langfuse
- 埋点要写多少代码

**这决定了 S3 的工作量。**

### 加上量化指标

| 框架 | 代码行数 | 上手耗时 | 依赖包数量 | 测试任务是否通过 |
|---|---|---|---|---|
| 手写（U2.1） | | - | | |
| LangGraph | | | | |
| OpenAI Agents SDK | | | | |
| Claude Agent SDK | | | | |

**把手写版也列进来。** 你会发现框架省的代码量可能没你想的多，但省的是「持久化、中断、流式」这些难写对的部分。

### 可能卡在哪

**对比维度太多记不过来**

就用上面这六个问题，做成一张表，每个框架填一列。

**某个框架某项做不到**

**记下来「做不到」，这是有价值的信息。** 不要因为做不到就跳过。

## 步骤 4 · 读 smolagents 的源码

### 这一步在做什么

**看清楚框架到底做了什么。**

### 为什么读它

因为它足够小。LangGraph 有几万行，读不完；smolagents 的核心逻辑几百行，一个下午能读透。

### 重点看这几处

1. **主循环在哪**，和你 U2.1 写的有什么不同
2. **工具是怎么注册和序列化成 schema 的**
3. **错误是怎么处理的**——是抛出还是回填
4. **上下文是怎么组装的**——有没有做压缩
5. **它有没有做持久化**（多半没有，这正是它「极简」的代价）

### 你会发现的事

**框架的核心循环和你写的差不多。** 真正的差别在于：

- 边界情况的处理更周全
- 有可插拔的扩展点
- 有配套的生态（工具库、集成、可观测性）

**这个发现很重要**——它让你不再对框架有神秘感，遇到问题敢去读源码而不是只会搜 issue。


### 关于「迁移成本」这一段

**这是最有价值的一段。**

好的架构应该让框架成为可替换的部件。具体做法是：

- **工具的实现不依赖框架**（就是普通的 async 函数）
- **模型调用走你自己的 `llm_kit`**（S1 建的）
- **业务逻辑和编排逻辑分离**

这样换框架时，改的只是编排层那一小部分。

### 一个诚实的可能结论

**「我继续用手写的循环」也是合格的结论**，如果：

- 你的任务不需要复杂的状态管理
- 你自己实现了持久化和中断（S4 会教）
- 你更看重完全的控制权和零依赖

**但你必须能说明白代价**：你要自己维护那些框架已经处理好的边界情况。
