# U2.8 · 框架横评（18 小时）

**这个单元解决什么问题**

你已经手写了 Agent。现在用同一个任务检验框架替你承担了哪些工作：工具调用、状态保存、人工中断、失败恢复与前端事件。选型的结论必须来自可重复的操作和日志。

**学完你能做到**：三个候选各做一个薄适配器，理解主流名称的关系；从中选出两个做恢复与迁移验证，最后把一个接进主线项目。新增名称不意味着每个都重做一遍。

**18 小时怎么用**（教学时间盒）：

| 部分 | 时间 | 交付 |
|---|---:|---|
| 步骤 1：词汇映射与当前状态（新增） | 1.5h | 概念对照、一个官方示例的流程图 |
| 步骤 2：冻结同一任务 | 1h | 业务工具与验收合同 |
| 步骤 3：三个薄适配器 | 7.5h | 每个最多 2.5h 的首轮实现与记录 |
| 步骤 4：恢复、人工中断与迁移（新增） | 4.5h | 两候选的故障记录、一次编排迁移 |
| 步骤 5：六项对比与读源码 | 1.5h | 逐项证据和源码定位 |
| 步骤 6：决定与接入主线 | 2h | 选型记录、主线运行结果 |

编码 Agent 负责适配与运行，你负责冻结任务、审查副作用边界、亲自触发批准/拒绝和核对回执。参考例使用本地回执模拟「发布」，不用真的对外发送内容。

## 步骤 1 · 把名称映射到同一个工程问题（1.5h）

### 这一步在做什么

分清 Agent 框架、编排运行时和带工具/会话/渠道的完整系统。否则会把「现成能力多」误认为「适合嵌入自己的服务」。

### 怎么做

下面是 **2026-09-10 核验的官方状态**。版本写进你项目的依赖锁文件；不按 Star 数量排名。

| 名称 | 在本单元怎样理解 | 对同一任务的映射与来源 |
|---|---|---|
| LangChain / LangGraph | LangChain 提供模型、工具与 Agent 抽象；当前 LangChain Agent 建立在 LangGraph 之上。LangGraph 可独立使用，负责显式图与执行状态 | 搜索→草稿→确认→写回执，对应节点、状态和边；[官方层次说明](https://docs.langchain.com/oss/python/concepts/products)、[LangGraph 概览](https://docs.langchain.com/oss/python/langgraph/overview) |
| OpenAI Agents SDK | Agent、工具、Runner、handoff、session 与 tracing 等能力；已提供内置工具审批及 RunState | `needs_approval` 标记写工具，`interruptions` 获取请求，RunState 保存待批运行；[人工介入](https://openai.github.io/openai-agents-python/human_in_the_loop/)、[RunState](https://openai.github.io/openai-agents-python/ref/run_state/) |
| Claude Agent SDK | 可编程地使用 Claude Code 的 Agent 能力，适合评估已有文件、命令行和 MCP 工作流 | 工具权限控制与会话恢复分别检验；[SDK](https://code.claude.com/docs/en/agent-sdk/overview)、[权限](https://code.claude.com/docs/en/agent-sdk/permissions)、[会话](https://code.claude.com/docs/en/agent-sdk/sessions) |
| CrewAI | Agent / Task / Crew 表达协作；Flow 表达有状态的流程 | 外层 Flow 对应任务状态，Crew 可承担草稿生成；核对 `@persist` 与人工反馈如何保存和恢复；[Flows](https://docs.crewai.com/en/concepts/flows)、[Human Feedback](https://docs.crewai.com/en/learn/human-feedback-in-flows) |
| AutoGen / Microsoft Agent Framework | AutoGen 官方仓库已进入维护模式，建议新用户从 Microsoft Agent Framework 开始 | 读旧代码时识别 Core、AgentChat 和扩展层；新选型看迁移后的对应概念；[AutoGen 官方状态](https://github.com/microsoft/autogen)、[迁移指南](https://learn.microsoft.com/en-us/agent-framework/migration-guide/from-autogen/) |
| OpenClaw | Gateway 连接消息渠道、客户端与节点，属于更完整的运行系统 | 画出渠道请求→Gateway→Agent→工具的路径，判断你的需求是否包含渠道接入；[Gateway 架构](https://docs.openclaw.ai/concepts/architecture) |
| smolagents | 源码阅读候选，观察循环、工具执行和记忆的实现 | 追踪一个工具调用到最终结果；[官方源码](https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py) |

完成两个小产出：

1. 默认实现 LangGraph、OpenAI Agents SDK、Claude Agent SDK 的适配器。若项目明显需要 CrewAI / Microsoft Agent Framework，或某个模型服务不可用，可用其中一个替换第三候选，并在任务规格中写明原因；仍只做三个。
2. 从 CrewAI、AutoGen→Microsoft Agent Framework、OpenClaw 中，挑与你主线最相关的一个官方示例，标出输入、状态归属、工具执行、人工介入、结果输出。另两个在表中写出「本任务需要/不需要哪层能力」；不额外安装整套系统。

**交给编码 Agent 的任务**：

> 读取当前官方概览和已锁定版本，为我们的搜索→草稿→批准→回执任务画概念映射。注明核验日期、对应文档或源码；区分库、运行时和完整系统。不要用旧博客断言某框架不支持人工确认，也不要为表里每个名称另建项目。

**你审、你验**：能说明 LangChain 与 LangGraph 的关系、AutoGen 当前维护状态，以及 OpenClaw 接入会多承担哪些系统职责。

### 可能卡在哪

- **看到 AutoGen 的老教程就选它做新项目**：先读仓库当前维护说明与迁移指南。
- **以为 OpenClaw 是另一个 Python 编排库**：先找到 Gateway 与渠道入口，看你是否需要这层能力。
- **想全试一遍**：用同一任务筛出三个，剩下的留下排除依据；超过时间盒只会减少真正的恢复测试时间。

### 背后的逻辑

名字只是入口，重要的是状态、执行边界和服务集成成本。层次不同的产品可以解决相关问题，但不适合直接比较代码行数或模型得分。

## 步骤 2 · 冻结同一任务和业务工具（1h）

### 这一步在做什么

让三个实现只在编排上不同。工具、输入、错误和验收保持一致，才能知道差异来自哪里。

### 怎么做

复用 U2.1 的场景，或采用下面的最小任务。在 `s2-agent/frameworks/TASK.md` 写好合同：

```text
输入：根据笔记生成一份草稿，审核后保存发布回执。
工具：search_notes、read_note、write_receipt。
流程：检索→读取→草稿→人工批准/拒绝→回执或拒绝结果。
状态：job_id、schema_version、source_ids、draft、draft_hash、approval、status。
批准：绑定 job_id + draft_hash + 动作；草稿变更后旧批准失效。
回执：按业务幂等键保存；同一动作重试只产生一份回执。
成功：有来源、有最终状态；批准产生一份回执，拒绝产生零份。
故障：工具超时、待批进程退出、写回执后响应丢失。
```

工具实现放在不依赖框架的 `domain/`；适配器只做工具 schema、状态转换、事件映射与恢复。模型调用尽量使用同一个提供商/模型和相同参数。某 SDK 约束导致无法对齐时，记录这个混杂因素，模型输出优劣不算框架输赢。

先用固定工具返回值冻结错误案例，再用主线真实数据运行。目录中的 `run_id` 负责追踪一次执行，`job_id` 负责标识同一个业务请求；重试时不能随手生成新 job_id。

**交给编码 Agent 的任务**：

> 从 U2.1 提取这三个业务工具和固定输入，建立 TASK.md 与共享验收。写工具返回同一数据结构，发布先用本地回执模拟。框架包不得进入 domain/。先给我看批准前后允许的状态转移，再写适配器。

**你审、你验**：直接调用工具也能运行；批准前没有回执，业务幂等键不来自模型的自由文本。

### 可能卡在哪

三个实现各自改工具描述、提示词或错误处理，最后对比就失真。先对工具返回值做相同的断言，再允许编排层不同。

### 背后的逻辑

换框架的成本主要取决于业务代码是否被框架类型绑住。先拆边界，后面的迁移才是小改动。

## 步骤 3 · 三个候选各做一个薄适配器（7.5h）

### 这一步在做什么

先让同一任务从输入跑到待批状态，再人工恢复到结束。每个候选首轮最多 2.5h；超过时间盒就保存最小复现及未通过项，把后续深测留给两个可运行候选。

### 怎么做

**LangGraph**：把检索、草稿、确认和执行映射成节点；按更新含义决定状态字段是覆盖还是追加。人工介入使用 `interrupt()` 和 `Command(resume=...)`；保存固定的 `thread_id`，配置落盘 checkpointer。恢复会重新执行包含 interrupt 的节点，节点前半段不能无条件重复写入。[中断文档](https://docs.langchain.com/oss/python/langgraph/interrupts)、[持久化](https://docs.langchain.com/oss/python/langgraph/persistence)（核验：2026-09-10）。

先读并跑下节的完整无密钥示例，再把固定节点换成共享工具与模型。不要把 `interrupt_before` 暂停所有工具的调试示例直接当成批准业务动作的完整实现。

**OpenAI Agents SDK**：用 `Agent`、`Runner` 和函数工具连接共享工具。给写回执工具设置 `needs_approval`，读取 `result.interruptions`，将 `result.to_state()` 得到的 RunState 序列化落盘；在新进程重建相同 Agent/工具后，用当前版本支持的恢复 API 加载状态、批准或拒绝，再交给 Runner。对照官方完整示例实现，不只保存聊天历史。[人工介入与恢复示例](https://openai.github.io/openai-agents-python/human_in_the_loop/)（核验：2026-09-10）。

**Claude Agent SDK**：把共享工具接成 MCP 或 SDK 自定义工具，验证权限决策真正覆盖写回执操作。显式保存并恢复目标 session ID；用独立的业务任务/审批记录判断草稿和动作是否仍有效。会话恢复保存的是上下文，不能由此推导数据库副作用只执行一次。[自定义工具](https://code.claude.com/docs/en/agent-sdk/custom-tools)、[会话恢复](https://code.claude.com/docs/en/agent-sdk/sessions)（核验：2026-09-10）。

若选择替代候选，CrewAI 重点验证 Flow 状态与人工反馈的恢复；Microsoft Agent Framework 重点按官方迁移指南完成同样的工具和状态映射。不要另外扩成多 Agent 项目。

**三者统一输出**：`started`、`tool_started`、`tool_finished`、`approval_required`、`completed` 或 `failed` 等你定义的业务事件。保存原始事件作证据，给前端用的事件通过自己的适配层产生，不让前端直接依赖某框架内部类型。

**交给编码 Agent 的任务**（每次替换候选名）：

> 在 frameworks/<candidate>/ 实现 TASK.md 的同一任务，只写编排适配器，复用 domain/。记录依赖版本、启动命令、待批 payload、批准和拒绝的恢复命令、原始事件与业务事件。禁止在主线业务中引入候选包；不要通过关闭审批让用例通过。模型不可用时记录具体错误和已验证的确定性部分，不把 mock 写成真实运行。

**你审、你验**：三份记录使用同一个任务合同；能看到批准前的具体草稿。每个候选分别标明「已跑通 / 已实现但未验证 / 环境阻塞」，不能用安装成功代替运行成功。

### 可能卡在哪

- **LangGraph 恢复后重复记日志或写数据**：包含 interrupt 的节点会重入；幂等控制放在业务写入层。
- **把 OpenAI session 当成任意步骤恢复**：对话历史与待批 RunState 承担的职责不同；检查究竟保存了什么。
- **Claude 权限回调没有触发**：自动允许的工具可能在回调前已通过。核对权限规则的顺序与实际工具名。[官方权限决策顺序](https://code.claude.com/docs/en/agent-sdk/permissions)（核验：2026-09-10）。
- **版本 API 对不上**：保存依赖锁文件并打开对应的官方示例；记录不兼容处，不反复猜函数名。

### 背后的逻辑

框架替你组织执行和状态，不替你定义业务授权、幂等键或正确答案。把这几层分开，才知道该在什么地方修问题。

## 步骤 4 · 跨进程恢复、人工中断与迁移（4.5h）

### 这一步在做什么

首轮有聊天输出还不够。选两个最符合主线需求的候选，检验它们在退出进程、拒绝批准、重复恢复时的行为；再把同一任务从一个编排层迁到另一个。

### 怎么做

先运行仓库提供的完整 LangGraph 参考程序：

```bash
cd ~/ai-agent-roadmap
uv run examples/framework-recovery/langgraph_smoke.py
```

**你应该看到**（2026-09-10 实跑；`langgraph==1.2.11`、`langgraph-checkpoint-sqlite==3.1.1`）：

```text
PASS pause in process A; approve in process B; effects=1
PASS reject after restart; effects=0
PASS exit after business commit; resume twice; effects=1
```

程序每次操作都启动新进程，用两个 SQLite 文件分别保存 checkpoint 与业务回执；在业务提交后用 `os._exit(70)` 强制结束子进程，再恢复两次。它验证本机进程突然退出后的持久化和幂等行为，不调用模型、不发消息；也不证明远程写入、并发恢复和服务部署已经通过。临时数据库由程序自动清理。

把它变成你两个候选的共享实验。4.5h 建议分成：2h 恢复/批准/拒绝，1h 故障后的副作用核验，1.5h 迁移与回切。

| 实验 | 操作 | 验收目标 |
|---|---|---|
| 待批恢复 | 进程 A 输出待批记录后退出；B 加载相同运行并批准 | 草稿与待批动作不变，写入一份回执 |
| 拒绝恢复 | 另起 job，在 B 中拒绝 | 零回执，终态明确为拒绝 |
| 变更草稿 | 待批期间修改 draft_hash，再提交旧批准 | 旧批准不能执行新草稿，需要新批准 |
| 写后崩溃 | 回执提交后、框架记录完成前终止进程 | 恢复不会产生第二份回执 |
| 重复恢复 | 用同一待批/完成记录重复请求恢复 | 终态一致；业务动作不重复 |
| 超时 | 同一只读工具注入一次超时 | 有限重试或明确失败，错误出现在日志 |
| 编排迁移 | 切换两个候选的适配器，复跑相同固定任务 | domain/ 与验收不变，输出和副作用合同一致 |

**迁移边界**：这里迁移新任务的编排实现，不要求把框架 A 内部 checkpoint 二进制搬到 B。对于尚未结束的旧任务，写清楚采用「旧版本排空」还是「导出业务状态后重新创建待批任务」；后一种必须重新校验草稿、权限和批准版本。不能悄悄重放已完成的写操作。

若远程服务写入成功却连接断开，查询业务回执或使用服务端幂等键；单独保存 framework checkpoint 不能解决这个窗口。不要把表里一项未测写成「框架不支持」。

**交给编码 Agent 的任务**：

> 选两个已运行候选，按上表写进程级故障脚本。每组保存 job_id、退出位置、恢复输入、最终状态和回执数量。先把写后崩溃复现出来，再验证业务幂等修复。完成一次适配器迁移并给出 diff，domain/ 和验收合同不得随之变化。列出不能透明迁移的会话/状态，以及旧任务如何结束。

**你审、你验**：亲自拒绝一次，再重复批准一次；查看业务数据库的真实行数。读迁移 diff，指出哪几处是不可避免的框架依赖。

### 可能卡在哪

- **恢复后从头开始**：保存的是内存状态，或换了 `thread_id` / session ID / 存储目录。
- **恢复输出成功，但写了两次**：checkpoint 与业务存储不是一个事务；修业务幂等后重跑故障窗口。
- **移植时工具全重写了**：框架类型进入业务函数了；先把工具拆回普通函数。
- **迁移不了待批任务**：这是需要交代的发布策略；保留旧执行器排空可以比转换内部状态更稳妥。

### 背后的逻辑

恢复能力由框架、存储和业务工具共同构成。真正要验证的是业务结果和副作用次数，而不只是 Agent 是否还能继续说话。

## 步骤 5 · 六项对比，读一段相关源码（1.5h）

### 这一步在做什么

把实验变成别人能复查的依据，给下一阶段评估、可靠性和全栈界面留下接入契约。

### 怎么做

每个候选用同一张表，值写「原生能力 / 需要适配 / 已实测 / 未验证」，后面挂你的文件路径、日志或官方来源：

| 维度 | 必须回答的问题 | 证据 |
|---|---|---|
| 状态与持久化 | 状态存在哪？进程退出后哪些保留？ | schema、存储配置、重启记录 |
| 失败恢复 | 从哪个已保存边界恢复？写后崩溃如何处理？ | 故障脚本、回执数量 |
| 人工介入 | 批准绑定什么？拒绝、过期与重复批准如何处理？ | 请求/响应与终态 |
| 流式 | 模型文本与工具事件如何给前端？断线后怎样读最终状态？ | 原始事件与业务事件样本 |
| 工具失败 | 超时、重试、取消和错误回填由谁控制？ | 一次注入失败的执行记录 |
| 可观测性 | 如何通过 job_id 找到工具、模型和耗时？ | 本地 trace 或日志位置 |

再记录你实际新增的适配代码量、首轮耗时、依赖数量。跨模型的费用/耗时保留原始记录，明确不能单独归因于框架；不要填教程作者的估算数字。

读 smolagents 的 `agents.py`，从一次运行入口追踪工具执行、错误处理、记忆组装和终止判定。写出与 U2.1 手写循环的三处差异。遇到 `save()` 时看它究竟保存 Agent 配置/代码还是运行中的 checkpoint；同名「保存」不等于同样的恢复语义。[当前官方源码](https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py)（核验：2026-09-10）。

**交给编码 Agent 的任务**：
