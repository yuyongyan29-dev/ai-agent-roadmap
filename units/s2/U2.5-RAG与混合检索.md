# U2.5 · RAG 与混合检索（18 小时）

**这个单元解决什么问题**

模型的知识来自训练数据，是过期的、通用的、不包含你私有内容的。RAG（检索增强生成）解决这个问题：**先从你的资料里找出相关内容，再让模型基于它回答。**

但检索到的资料也可能过期、错位或无权访问。本单元同时检查答案依据、资料生命周期和访问边界。

**必读**：Anthropic《[Introducing Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)》（2024-09-19）。它讲清楚了为什么单纯的向量检索不够，以及给每个片段加上下文说明能带来什么。

**学完你能做到**：搭出可评测的检索管线，接入 PDF、扫描件和表格；验证文档更新、删除、权限；用同一批向量比较 pgvector 与 Qdrant。

**重要提醒**：网上关于 RAG 的各种数字（「混合检索提升 X%」「rerank 提升 Y%」）**大多无法追溯来源，而且别人的语料和你的不一样。这个单元的核心动作就是自己测。**

**18 小时怎么用**（学习时间盒，不是性能承诺）：

| 部分 | 时间 | 必须留下的证据 |
|---|---:|---|
| 步骤 1–2：评测集与切分 | 3h | 冻结的题目、三种切分对比 |
| 步骤 3–4：向量、关键词与融合 | 4h | 同口径的召回结果 |
| 步骤 5–6：重排与接入 Agent | 5h | 延迟、成本、来源引用 |
| 步骤 7：解析与质量抽检（新增） | 2h | PDF / 扫描页 / 表格的原文对照 |
| 步骤 8：文档治理（新增） | 2h | 更新、重复入库、删除、撤权回归 |
| 步骤 9：专用向量库对照（新增） | 2h | 同数据、同权限的 Qdrant 对比 |

**协作方式**：编码 Agent 写适配器和测试，你先确定题目与正确来源，再审查解析产物、过滤条件和实际输出。不要让它同时改检索代码和标准答案。步骤 1–6 的代码是需要接进主线项目的概念片段；步骤 8 提供了可直接运行的完整参考程序。

步骤 1–6 可逐条复制下面的任务交给编码 Agent；每次只改当前变量，运行后由你复核右栏。

| 步骤 | 可复制的 Agent 任务 | 你审、你验 |
|---|---|---|
| 1 | 扫描现有语料，输出稳定 doc_id 和来源清单；根据我确认的 20 题保存评测文件，不自行改答案。 | 逐题确认 must_hit 文档确实包含答案。 |
| 2 | 在现有语料上实现固定、结构、上下文增强三种切分；保存版本、chunk 和同一评测集结果。 | 抽查切分边界、来源，核对新增成本。 |
| 3 | 用选定 embedding 建 pgvector 索引，记录模型、维度与导出向量，按固定题目评文档级 Recall 和 MRR。 | 挑一个命中和一个漏召回，核对真实排名。 |
| 4 | 保留向量路径，加关键词与 RRF；只改变融合设置，输出单路与融合逐题排名。 | 查型号/数字题；确认没有把 chunk 重复算成文档命中。 |
| 5 | 在同一候选集上加 rerank，记录 Recall@50、top-5、延迟与费用；保留退化案例。 | 若没提升，先核对正确文档是否进入候选集。 |
| 6 | 把检索接成工具，返回来源与页码；比较固定检索与 Agent 决策检索的调用次数、答案和费用。 | 实际问一次有答案和一次无答案的问题，核对引用与拒答。 |

## 步骤 1 · 准备语料和评测集

### 这一步在做什么

**先建评测集，再建检索系统。** 顺序不能反——否则你没法知道改动是变好还是变坏。

### 怎么做：准备语料

50 篇以上你项目真实需要的文档。可以是：

- 你的行业资料、竞品笔记、产品文档
- 你自己的笔记、飞书文档
- 公开的领域资料

**必须是真实的。** 用玩具数据测出来的结论在真实数据上不成立。

### 建评测集

准备 20 组「问题 → 正确答案在哪篇文档」：

```yaml
# 评测集是判分依据，先写死再动检索代码；改检索时这个文件不许跟着改
# relevant_docs 只作参考，真正算分只看 must_hit 有没有被召回
- id: R001
  question: 冬季家电选购要注意什么
  relevant_docs: [doc_012, doc_045]   # 可能不止一篇
  must_hit: [doc_012]                 # 判分所需文档集合
  note: doc_012 是最直接的答案来源

- id: R002
  question: 这个品牌的售后政策
  relevant_docs: [doc_007]
  must_hit: [doc_007]
  note: 边界情况，问题里没有品牌名，靠上下文
```

**建评测集的方法**：读你的文档，从中提出问题。或者反过来——想 20 个你真的会问的问题，然后去文档里找答案。

### 两个指标

| 指标 | 含义 | 怎么算 |
|---|---|---|
| **Recall@K** | 每题应召回的文档找回多少 | 每题 `前 K 个唯一 doc_id 与 must_hit 的交集数 / must_hit 数`，再对题目取平均 |
| **MRR** | 正确文档排第几位的倒数的平均 | 排第 1 得 1 分，第 2 得 0.5 分，第 3 得 0.33 分 |

每题 must_hit 必须非空。先将 chunk 排名按 `doc_id` 去重，再评文档级 Recall 和 MRR；`must_hit` 是判分依据，MRR 取第一个命中它的文档排名。仅判断「至少命中一篇」时，指标叫 HitRate@K；每题只有一篇必需文档时，两者才相等。不要把同一文档的多个 chunk 当成多个命中。

**召回率关心「找回多少」，MRR 关心「排得靠前不」。** 两个都要看——排在第 20 位的正确答案，实际上等于没找到，因为你只会把前 5 个给模型。

### 可能卡在哪

**20 组太少**

对早期够用。**关键是难度要有梯度**：一半是直接问答（关键词能匹配上），一半是需要语义理解的（问法和文档用词不同）。

**不知道正确答案在哪篇**

那说明你对自己的语料不熟。**先花时间读一遍**，这个投入是必要的。

### 背后的逻辑

冻结题目与正确来源，让后续实验只改变检索设置；否则系统和答案一起变化，分数就不能说明改动的价值。

## 步骤 2 · 切分

### 这一步在做什么

把长文档切成小片段。切分改变召回粒度，也决定能否准确标注来源。

### 为什么要切

三个原因：

1. embedding 模型有长度上限
2. 检索的粒度要合适——返回一整篇 5000 字的文档，模型还是要自己找
3. 上下文有预算（U1.5）

### 怎么做：三种策略

**策略一：固定长度 + 重叠**

```python
def fixed_split(text: str, size: int = 500, overlap: int = 100) -> list[str]:
    """按固定字符数切分，相邻片段之间保留 overlap 个字符的重叠。"""
    if not 0 <= overlap < size:
        raise ValueError("require 0 <= overlap < size")
    chunks = []
    i = 0
    while i < len(text):
        chunks.append(text[i:i + size])
        # 每次只前进 size - overlap，下一段会往回吃一截：
        # 被切在边界上的关键句至少在其中一段里是完整的
        i += size - overlap
    return chunks
```

**重叠是为了防止关键信息正好被切在边界上。**

优点：简单，任何文本都能用。缺点：会切断句子和语义单元。

**策略二：按结构切**

按 Markdown 的标题层级、HTML 的段落、PDF 的章节切。

```python
def split_by_heading(md: str) -> list[dict]:
    """按 Markdown 标题层级切分，每段带上从顶层一路下来的标题路径。

    标题路径不只是元数据：做 embedding 时把它拼在正文前面，
    片段被单独检索出来时也知道自己属于哪一章。
    """
    # 按 ## 切，每段带上它的标题路径
    ...
    return [{"heading_path": "第3章 > 选购要点", "content": "..."}, ...]
```

**优点：语义完整，而且标题路径本身就是有价值的上下文。** 缺点：只适用于有结构的文档，长度不均。

**策略三：加上下文说明（Contextual Retrieval）**

这是必读文章里的方法。给每个片段前面加一小段说明它在整篇文档里的位置和作用：

```python
# 让模型给每个片段写一句定位说明，专门解决「片段脱离原文后指代不明」
# 结尾强调「只输出这段说明」，否则模型会顺手复述片段内容，把 token 花在无用的地方
context_prompt = """
这是一篇关于「{doc_title}」的文档。
下面这个片段来自其中。请用一到两句话说明这个片段在整篇文档里讲的是什么，
以便它被单独检索出来时能被理解。只输出这段说明。

片段：
{chunk}
"""

# 说明拼在原文前面，整体拿去做 embedding；原文一个字不改，
# 这样最终引用给用户看的仍是原始表述
enriched_chunk = f"{context_note}\n\n{raw_chunk}"
```

**代价**：每个片段要调一次模型（可以用小模型 + 批处理降本，见 U1.6 和 U1.7）。

**收益**：解决了「片段脱离上下文后无法理解」的问题。比如一个片段里写「它的续航是 8 小时」，单独看不知道「它」是什么。

### 实测对比

三种策略各建一份索引，用你的评测集测：

| 切分策略 | 片段数 | 平均长度 | 召回率@5 | MRR |
|---|---|---|---|---|
| 固定 500/100 | | | | |
| 按结构 | | | | |
| 结构 + 上下文说明 | | | | |

### 可能卡在哪

**片段该多长**

没有普适答案，**取决于你的文档和问题类型**。

经验起点：中文 300 到 800 字。问题很具体的（找一个数字）用短片段，问题需要综合理解的用长片段。**用评测集测三个长度，选最好的。**

**PDF 解析出来是乱的**

PDF 是显示格式不是数据格式，解析质量参差不齐。试几个库（`pymupdf`、`pdfplumber`），或者用模型的多模态能力直接读页面图片。

**表格被切碎了**

表格要特殊处理：整个表格作为一个片段，或者转成 Markdown 表格后再切。

### 背后的逻辑

切分的本质是在两个目标间权衡：

- **片段要小**，这样检索精确、上下文省
- **片段要完整**，这样单独看能理解

「加上下文说明」这个方法巧妙在：**它让片段既小又完整**——用一句额外的说明补上了被切掉的语境。

## 步骤 3 · 向量检索

### 这一步在做什么

搭第一条召回路径：按语义相似度找。

### 怎么做

**选 embedding 模型**。中文场景建议：

- BGE 系列（开源，可本地跑）
- 各云厂商的 embedding API（阿里、智谱等）

**存进 Postgres**（U0.8 装的那个）：

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
    id           SERIAL PRIMARY KEY,
    doc_id       TEXT NOT NULL,        -- 指回原文档，返回结果时要靠它标注来源
    heading_path TEXT,
    content      TEXT NOT NULL,
    embedding    vector(1024)          -- 维度看你选的模型
);

-- HNSW 是近似最近邻索引，用一点召回率换查询速度；
-- 算子类必须和检索时用的距离一致，余弦距离配 vector_cosine_ops
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
```

**检索**：

```sql
-- $1 是问题的 embedding；距离换算成相似度只是为了读起来顺
SELECT id, doc_id, content, 1 - (embedding <=> $1) AS similarity
FROM chunks
ORDER BY embedding <=> $1   -- 必须直接按 <=> 排序，套一层算式就用不上 HNSW 索引
LIMIT 50;
```

`<=>` 是余弦距离操作符，越小越相似。

### 可能卡在哪

**`CREATE EXTENSION vector` 报错**

pgvector 扩展没装。用 Docker 的话换镜像：`pgvector/pgvector:pg17`。本地装的话 `brew install pgvector`。

**维度对不上**

`vector(1024)` 里的数字必须和你的 embedding 模型输出维度一致。换模型就要重建表和重新嵌入所有内容。

**批量嵌入很慢**

用批量接口（一次传多条），加并发（U1.2 学的 Semaphore）。记录你自己语料的片段数、总 token 和实际耗时。

**HNSW 索引建得很慢**

数据量大时正常。可以先不建索引（小数据量全表扫也很快），数据稳定后再建。

### 背后的逻辑

**向量检索的原理**：embedding 模型把文本映射成高维空间里的一个点，**语义相近的文本，点的位置也相近。** 检索就是找最近的几个点。

**它的强项**：能匹配语义相近但用词完全不同的内容。「怎么挑洗衣机」能匹配到「洗衣机选购指南」。

**它的弱项**：

- **精确匹配差**。搜一个型号 `XQB80-M1268`，向量检索可能找不到，因为这种字符串没有语义
- **对专有名词、缩写、数字不敏感**
- **无法表达布尔逻辑**（「包含 A 但不包含 B」）

**这些弱项正好是关键词检索的强项。** 所以有了下一步。

## 步骤 4 · 关键词检索与融合

### 这一步在做什么

加第二条召回路径，补上向量检索的短板。

### 怎么做：Postgres 全文检索

下面的 SQL 是配置示意，`chinese` 不是默认自带的配置名；要先安装中文分词扩展并创建对应配置。若采用后面的 Python 分词方案，入库和查询两边都必须用相同的分词词典，并分别使用 `to_tsvector('simple', 已分词正文)` 与 `plainto_tsquery('simple', 已分词问题)`。[PostgreSQL 文档与查询解析](https://www.postgresql.org/docs/current/textsearch-controls.html)（核验：2026-09-10）。

```sql
-- tsvector 是分好词的检索列，和 embedding 并存，构成第二条召回路径
ALTER TABLE chunks ADD COLUMN tsv tsvector;

-- 中文需要分词扩展
UPDATE chunks SET tsv = to_tsvector('chinese', content);
CREATE INDEX ON chunks USING gin(tsv);   -- 全文检索用 GIN，不是向量那套 HNSW

-- 检索
SELECT id, ts_rank(tsv, query) AS score
FROM chunks, to_tsquery('chinese', '家电 & 选购') query
WHERE tsv @@ query                       -- @@ 判断是否匹配，ts_rank 只负责算分
ORDER BY score DESC
LIMIT 50;
```

**中文分词需要额外扩展**（`zhparser` 或 `pg_jieba`），装起来有点麻烦。

**如果卡在这里，先用简化方案跑通流程**：

```python
# 用 jieba 在 Python 侧分词，存成空格分隔的词，用默认的 simple 配置
# 好处是不用装 Postgres 的中文扩展；代价是换词典要重跑一遍全库
import jieba
tokenized = " ".join(jieba.cut(content))
```

或者干脆先用 `LIKE '%关键词%'` 跑通，之后再优化。**不要在这一步卡太久。**

### RRF 融合

两路召回各有一个排序，怎么合并？

**RRF（Reciprocal Rank Fusion）**：不看分数，只看排名。

```python
def rrf(ranked_lists: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """把多路召回的排序结果合成一份总排序。

    只吃排名不吃原始分数，所以向量的余弦相似度和 BM25 分数
    不用归一化就能合并，也不用为两路调权重。
    """
    scores: dict[str, float] = {}
    for ranked in ranked_lists:
        # RRF 的排名从 1 开始；k 是平滑项
        for rank, doc_id in enumerate(ranked, start=1):
            # 同一个 doc 被多路召回就累加，天然奖励「两边都认为相关」的结果
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])
```

**RRF 的好处是不需要归一化两边的分数。** 向量的余弦相似度和 BM25 的分数量纲完全不同，直接加权求和很难调；RRF 只用排名，天然可比。

`k=60` 是常用的默认值，作用是压平高排名的优势，让两路都有发言权。

### 实测对比

| 配置 | 召回率@5 | MRR |
|---|---|---|
| 纯向量 | | |
| 纯关键词 | | |
| RRF 融合 | | |

**在你自己的语料上测。别人的数字对你不成立。**

### 可能卡在哪

**融合之后反而变差了**

可能是某一路质量太差，拖累了整体。分别看两路的单独表现，如果关键词那路召回率只有 20%，考虑降低它的权重或者先改进它。

**RRF 的 k 怎么调**

试 20、60、100 三个值，看哪个在你的评测集上最好。差别通常不大。

### 背后的逻辑

**混合检索的本质是「用两种不同的失败模式互补」。**

向量检索会漏掉精确匹配的内容，关键词检索会漏掉换了说法的内容。合并候选可以补回单一路径的遗漏，但融合后的 top-K 不保证更好；必须用固定评测集检验。

**这个思路在工程里很通用**：多个不完美但失败模式不同的系统组合起来，整体可靠性高于任何单个。

## 步骤 5 · 重排

### 这一步在做什么

召回 50 条，用一个更精确但更慢的模型重新排序，选出最好的 5 条。

### 为什么分两步

**召回**用的是「双塔」模型：问题和文档分别算向量，然后比距离。快，因为文档的向量可以预先算好。但不够精确，因为算文档向量时不知道问题是什么。

**重排**用的是「交叉编码器」：把问题和文档拼在一起送进模型，输出一个相关性分数。**精确得多**，因为模型能看到两者的交互。但慢，因为每个候选都要算一次，没法预计算。

**所以标准做法是：快的召回一批，慢的精排少量。**

### 怎么做

```python
async def rerank(query: str, candidates: list[str], top_n: int = 5) -> list[tuple[str, float]]:
    """用交叉编码器给召回的候选重新打分，只留最相关的 top_n 条。

    candidates 是召回阶段的那 50 条：模型要把问题和每条候选拼起来算一次，
    成本和延迟都跟候选数成正比，所以候选数和 top_n 都要卡住。
    """
    scores = await rerank_api(query=query, documents=candidates)
    ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
    return ranked[:top_n]
```

可选方案：

- 云端 rerank API（阿里、Cohere、Jina 都有）
- 本地跑 BGE-reranker（用 U1.7 学的思路，本地模型在这类任务上够用）

### 实测对比

| 配置 | 召回率@5 | MRR | 平均延迟 | 成本 |
|---|---|---|---|---|
| 纯向量 top-5 | | | | |
| 混合 top-5 | | | | |
| **混合召回 50 → rerank top-5** | | | | |

**注意也要记延迟和成本。** rerank 会增加延迟，你要知道增加了多少、值不值。

### 可能卡在哪

**rerank 之后提升不明显**

可能召回阶段就没把正确答案捞上来。**先看召回率@50**——如果正确答案根本不在这 50 条里，rerank 再强也没用。

**这是个重要的排查顺序：先看召回，再看排序。**

**延迟增加太多**

减少候选数（50 → 20），或者用本地模型，或者只在「召回结果分数接近」时才 rerank。

### 背后的逻辑

「粗排 + 精排」是搜索和推荐系统的经典架构，已经用了几十年。

它解决的是**质量和成本的矛盾**：全部用精确方法算不起，全部用快速方法不够准。**分层就能兼顾。**

**这个思路在 S4 会再次出现**：模型路由也是同一个结构——便宜的模型处理大部分，贵的模型处理筛选出来的少数。

## 步骤 6 · 接进 Agent

### 这一步在做什么

把检索变成一个工具，让 Agent 自己决定什么时候查、查什么。

### 怎么做：两种接法

**方式一：检索是工具（Agentic RAG）**

```python
registry.register(Tool(
    # 工具名会原样发给模型，用英文小写下划线，模型调用更稳
    name="search_knowledge_base",
    # 描述里必须写清楚「什么时候用」，否则模型会跳过工具凭记忆答
    description="在你的资料库里检索相关内容。当你需要基于私有资料回答时使用。"
                "支持自然语言查询。返回最相关的 5 个片段及其来源。",
    params_model=RetrieveParams,
    func=retrieve,
))
```

**模型自己决定查不查、查什么、要不要再查一次。** 更灵活，能多轮迭代地查。

**方式二：检索是前置步骤（传统 RAG）**

```python
# 检索写死在流程里：固定查一次，模型没有「查不查」的选择权
chunks = await retrieve(user_question)
# 资料放在问题前面，先给材料再给任务，模型更容易照着材料答
context = f"参考资料：\n{chunks}\n\n用户问题：{user_question}"
answer = await llm.chat(context)
```

**每次都查，固定流程。** 更快、更省（少一轮），但不灵活。

**建议**：先做方式二跑通，再改成方式一对比。**很多场景方式二就够了**（回想 U2.1：路径确定的用工作流）。

### 返回值设计

用 U2.2 学的原则：

```python
# 返回值是给模型读的：先报总数让它知道还有没捞完，每条挂来源方便引用和验证，
# 末尾提示下一步动作，模型发现结果不够时才知道可以换个说法再查
return f"""检索到 5 个相关片段（共匹配 23 个）：

[1] 来源：《冬季家电选购指南》第 3 节 · 相关度 0.89
{chunk1}

[2] 来源：《用户评测汇总》 · 相关度 0.85
{chunk2}

...

如果这些不够，可以换个说法再检索，或者用「读完整文档」工具查看某个来源的全文。
"""
```

**必须带来源。** 这样模型引用时能标注出处，用户能验证，也降低幻觉。

### 可能卡在哪

**模型不用检索工具，直接凭记忆答**

在系统提示里明确：「涉及产品、政策、数据的问题必须先检索，不要凭记忆回答」。

**模型检索了但不用检索结果**

检查返回值格式是不是清晰。有时是因为片段太多太长，模型抓不住重点。**减少 top_k，或者在返回值开头加一句概括。**

### 背后的逻辑

Agentic RAG 相比传统 RAG 的核心优势是**多轮迭代检索**：

```
第一次检索「冬季家电选购」→ 结果提到了「能效等级」
第二次检索「能效等级 一级 二级 区别」→ 拿到详细解释
综合两次的结果回答
```

本例的固定流程只查一次；也可以用确定性的多步工作流实现多次检索。区别在于是否把下一次检索的决定交给模型。

代价是更多轮次、更高成本、更长延迟。**又是一次取舍，用数据决定。**

## 步骤 7 · 把 PDF、扫描件和表格变成可追溯的片段（2h）

### 这一步在做什么

复用步骤 1 的资料，选一篇原生 PDF、一页扫描件和一张包含表头、单位的表格。先判断解析是否正确，再谈召回。没有扫描件时可把一页自有文档导出为图片作练习，并标明这是构造样本。

### 怎么做

1. 保留原始文件，在 `s2-agent/rag/ingestion/manifest.jsonl` 登记稳定的 `doc_id`、来源 URI、文件散列、文档版本、解析器版本、租户和权限版本。内容散列只用于检测同版本重复内容，不能代替跨版本稳定的 `doc_id`。
2. 用 PyMuPDF 对原生 PDF 提取文本、位置和页码；先逐页查看阅读顺序。对扫描页走 OCR 分支，缓存识别结果，避免每次查询重复 OCR。PyMuPDF 的 OCR 需要额外安装 Tesseract 及对应语言包；`get_textpage_ocr()` 生成的 TextPage 要传给后续提取函数。[文字提取](https://pymupdf.readthedocs.io/en/latest/recipes-text.html)、[OCR](https://pymupdf.readthedocs.io/en/latest/recipes-ocr.html)（核验：2026-09-10）。
3. 表格先保留标题、列名、单位和每行的对应关系，再转 Markdown 或结构化行。大表按行组拆分时，每组重复表头；合并单元格先展开，不把一列所有数字抽成一个片段。原生表格可试 `Page.find_tables()`，扫描表格需要另行抽检 OCR 结果。[官方表格提取说明](https://pymupdf.readthedocs.io/en/latest/recipes-text.html#how-to-extract-table-content-from-documents)（核验：2026-09-10）。
4. 输出统一记录：`doc_id, version, chunk_id, page, heading_path, content, parser_version, content_hash`。人类看到的第一页记为 1；保留字符或区域位置，让答案能跳回原文。
5. 从这三类输入各挑一个「答案是数字、单位或表格交叉项」的问题，冻结到新增解析回归集。把解析出的文字和原页并排查看，记录错误位置及修正；不要把 OCR 猜出的字符当作原文事实。

**交给编码 Agent 的任务**：

> 在现有 rag/ingestion 中增加原生 PDF 与扫描页分流，输出统一 chunk 记录。先展示三类样本的原页→提取结果，再批量入库。空页、扫描页和解析失败必须有不同状态；失败文件不能被当作成功入库。不要重做现有检索、embedding 或评测集。给出一条解析命令、一条重试失败文件的命令以及页码引用证据。

**你审、你验**：选中的三类样本都能反查原文，数值和单位一致；错误页进入待修队列。解析回归通过后，只给变更后的文档重建索引。

### 可能卡在哪

- **提取到文字但双栏顺序错了**：有文字不代表可用。按块和区域检查阅读顺序；只对出问题的版式加规则。
- **整页只有图片，却被记为「空文档」**：明确标记 `needs_ocr`，处理后再进入成功状态。
- **表格数字齐全，答案仍错**：检查列名和单位是否与数据行一起进入 chunk；模型无法从孤立数字补回表头。

### 背后的逻辑

解析质量是检索质量的上限。保留原始文件与位置，让修复能够重放、引用能够核验，也避免换解析器时丢失来源关系。

## 步骤 8 · 更新、删除与权限必须沿整条链路生效（2h）

### 这一步在做什么

把「写入成功一次」升级成能长期维护的知识库。该步骤的案例数是教学验收要求，不是行业统计。

### 怎么做

先运行仓库里的无密钥参考程序：

```bash
cd ~/ai-agent-roadmap
uv run examples/rag-lifecycle/qdrant_smoke.py
```

**你应该看到**（2026-09-10 实跑；`qdrant-client==1.19.0`）：

```text
PASS repeated ingestion: 1 point
PASS tenant, principal and revoked-access filters
PASS staged version invisible; switched version visible
PASS deletion: all team_a versions removed; team_b preserved
PASS local index survives client reopen
```

程序用三维固定向量，验证本地 Qdrant API 的行为；权限目录用内存对象模拟。它不测语义质量、不验证分布式一致性，也不能代替真实语料的检索评测。[Qdrant 本地模式](https://github.com/qdrant/qdrant-client)、[写入与删除](https://qdrant.tech/documentation/manage-data/points/)、[过滤](https://qdrant.tech/documentation/search/filtering/)（核验：2026-09-10）。

把同样的检查接到你的 pgvector 管线：

| 操作 | 实现要点 | 人工验收 |
|---|---|---|
| 重复导入 | 以租户、doc_id、不可变版本、chunk 序号组成稳定键；同版本散列不一致则拒绝 | 同文件导入两次，行数和结果不变 |
| 文档更新 | 先写 v2，核对片段数和索引成功状态，再事务切换权威目录的 active_version | v2 未就绪时只查到 v1；切换后只查到 v2 |
| 解析失败 | 保留失败状态和重试原因，不改变 active_version | 故意损坏一份新版本，旧版仍可查询 |
| 删除 | 权威目录先标记不可读，再清除所有版本的向量、关键词索引和缓存 | 搜旧原句也无法命中；记录物理删除完成状态 |
| 撤销权限 | 从可信身份读取租户、主体和当前授权；两路召回都带相同过滤，读取原文再次鉴权 | 同问题换用户或撤权后，不返回片段、标题、摘要或计数泄漏 |

小规模练习可以像参考程序那样查询明确的 `(doc_id, active_version)` 集合；生产数据较大时需要索引分代或权限可检索索引方案，不能把巨大的授权清单塞进每次请求。这里先解决正确性。

**过滤必须先于片段进入模型上下文**。向量召回、关键词召回、rerank 输入、全文读取都复用同一授权判断。缓存键至少包含身份范围、知识库版本及权限版本；撤权后的旧缓存要失效。不要只在最终回答时让模型「自行隐藏」。

**交给编码 Agent 的任务**：

> 在现有 pgvector 管线补文档目录、不可变版本和幂等 chunk 键，按上表实现五组回归。新版本全部写入并校验后才切换可见版本。tenant_id、principal 只能从服务端身份取得。先做两租户两用户测试，再用真实文档更新、删除、撤权复测；不能删除原评测题来让测试通过。输出每次操作前后的行数、可见版本和检索结果。

**你审、你验**：读实际 SQL / Qdrant filter，确认工具参数不能伪造身份；在原文、索引、缓存三处追踪同一份被删除的文档。权限拒绝用例单独统计，不与「本来有答案却没召回」混算。

### 可能卡在哪

- **删完向量还能搜到**：关键词索引或缓存还存着旧数据；按 doc_id 追踪整条链路。
- **更新时 v1、v2 同时出现**：`is_active` 的多行更新不是天然原子切换。用事务中的版本指针或查询固定索引代际。
- **撤权后偶尔还能读**：查权限缓存、结果缓存与正在运行的请求；返回原文前再校验权威权限。
- **重复内容跨租户被合并**：内容散列可复用 embedding 计算，但不能合并来源关系与访问权限。

### 背后的逻辑

文档是有身份、有版本、有读者范围的业务对象。向量只是它的一份派生索引；权威目录决定什么能读，重建索引不能改变权限或版本语义。

## 步骤 9 · 用 Qdrant 复现同一条检索路径（2h）

### 这一步在做什么

体验一种专用向量库，并回答你的项目是否值得多运维一个组件。本单元只新增 Qdrant；不轮流重做其他向量库。

### 怎么做

1. 导出步骤 3 已有的 `chunk_id + metadata + embedding`，连同 embedding 模型、维度、归一化方式和语料版本写入 `index_manifest.json`。**不重新调用 embedding 模型**。
2. 写一个薄适配器：`upsert_chunks`、`search`、`delete_document`。让 pgvector 与 Qdrant 返回相同的 chunk 结构，保留原有关键词召回、RRF、rerank 和题目。参照步骤 8 程序使用 `query_points`，不要从旧教程复制已变动的调用。
3. 先用 Qdrant 本地模式做功能对照，复跑五组治理回归；用原 20 题输出每题排名。相同向量得分并列时固定次序，评文档指标前去重。
4. 把向量召回切换为 Qdrant，其余设置不变，再测完整混合管线。若要比较服务延迟，将两者都改为本机服务模式，记录 CPU、内存、客户端位置、预热、请求数与并发；只完成本地模式时，性能栏写「未测服务部署」，不做快慢结论。
5. 针对权限过滤较严格的一组题单独检查 Recall。pgvector 的近似索引过滤可能减少候选；先与精确扫描比较，必要时按官方文档调整 iterative scan 等设置，再解释差异。[pgvector 的过滤与迭代扫描](https://github.com/pgvector/pgvector#filtering)（核验：2026-09-10）。

| 对照项 | pgvector | Qdrant | 判定证据 |
|---|---|---|---|
| 同语料向量 Recall@5 / MRR | 自测 | 自测 | 逐题结果与排名 |
| 相同关键词 + RRF + rerank 后结果 | 自测 | 自测 | 除向量库外配置相同 |
| 更新 / 删除 / 撤权 | 通过或失败 | 通过或失败 | 步骤 8 的回归记录 |
| 查询 P50 / P95、入库耗时 | 自测或未测 | 自测或未测 | 说明模式、样本数、机器 |
| 运维与业务数据关联 | 已有 Postgres 如何事务关联 | 额外服务与目录如何同步 | 一次更新失败的处理记录 |

**交给编码 Agent 的任务**：

> 复用现有 chunk 和 embedding 导出，增加 Qdrant 适配器；不改问题、关键词、rerank 或 top-K。用同一授权输入跑两套后端，产出逐题排名、文档级指标和生命周期检查。分开记录本地模式的功能结果与服务模式的性能结果。最后给出继续用 pgvector 或迁到 Qdrant 的证据，以及回切配置。

**你审、你验**：挑一个排名差异最大的题，沿「解析 → chunk → 向量候选 → 过滤 → 融合」解释原因。明确留下一个选型结论；两者结果相近、继续使用已有 Postgres 也是合格结果。

### 可能卡在哪

- **两个库结果完全不同**：先核对模型、维度、归一化、距离函数和是否导入同一批向量；不要先调索引。
- **本地模式比 Postgres 快**：一个是进程内调用，一个跨连接，实验条件不一致。
- **Qdrant 数据删除了，目录还显示正常**：用权威目录的删除状态驱动可重试清理，别把跨存储写入当成单个事务。

### 背后的逻辑

数据库选型不改变 embedding 的语义；它改变的是查询、过滤、持久化和维护方式。先控制变量，才能区分模型问题、数据问题和索引问题。
