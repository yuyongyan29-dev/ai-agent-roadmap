# U2.3 · 规划与反思（8 小时）

**这个单元解决什么问题**

U2.1 写的是最基础的 ReAct 循环：想一步做一步。它灵活，但容易跑偏、步数失控。

这个单元让你实现另外两种模式，并且**用数据决定你的项目该用哪种**。

**学完你能做到**：三种模式各实现一遍；用四项指标的对比表支持你的选择。

---

## 步骤 1 · 三种模式是什么

### 模式一：ReAct（你 U2.1 写的那个）

```
思考 → 行动 → 观察 → 思考 → 行动 → 观察 → ... → 答案
```

模型每一轮都基于当前所有信息决定下一步。

| 优点 | 缺点 |
|---|---|
| 灵活，能适应意外情况 | **容易跑偏**，中途改变目标 |
| 实现简单 | **步数不可控** |
| 每步都能利用最新信息 | 没有全局视野，可能重复劳动 |

### 模式二：Plan-and-Execute

```
先规划：列出完整计划（步骤 1..N）
再执行：逐步执行，每步后检查是否需要调整计划
```

```python
class Plan(BaseModel):
    """规划阶段的产出：先把整条路径定下来，执行阶段只照着走。"""

    goal: str
    steps: list[str]
    expected_output: str


async def plan_execute(user_input: str):
    # 规划只调用一次，用结构化输出拿到可枚举的步骤，步数和成本从这一刻起就能预估
    plan = await make_plan(user_input)
    logger.info("计划：%s", plan.steps)

    results = []
    for i, step in enumerate(plan.steps):
        # 把已完成步骤的结果一起传下去，后一步才能用到前一步的产出
        r = await execute_step(step, previous_results=results)
        results.append(r)

        # 每步后检查是否需要改计划：计划错了会全盘错，这里是整个流程唯一的纠偏点
        if needs_replan(r):
            plan = await replan(plan, results)

    return await summarize(plan, results)
```

| 优点 | 缺点 |
|---|---|
| **步数可控**，能预估成本和时间 | **计划错了全盘错** |
| 有全局视野，不重复劳动 | 多一次规划调用的成本 |
| **计划可以给人看和修改** | 对意外情况适应差 |

**「计划可以给人看」这一点被低估了。** 它让用户能在执行前介入，这是 S4 人工确认机制的天然接口。

### 模式三：Evaluator-Optimizer（反思）

```
生成 → 评价 → 不合格就带着评价重做 → 再评价 → ... → 合格
```

```python
async def reflect_loop(task: str, max_iterations: int = 3):
    """生成 → 评价 → 带着意见重做，直到合格或迭代次数用完。"""

    result = await generate(task)

    for i in range(max_iterations):
        # 评价是另一次独立调用，输出结构化的评分和意见，才能用 passed 直接判断
        review = await evaluate(task, result)
        if review.passed:
            # 连迭代轮数一起返回：做对比实验时要靠它算「多花几倍成本换到多少质量」
            return result, i + 1
        # 重做时必须把上一版和具体意见一起给回去，只说「重写」模型会原地打转
        result = await generate(task, previous_result=result, feedback=review.feedback)

    # 次数用尽仍不合格：返回最后一版而不是报错，由上层决定用不用
    return result, max_iterations
```

| 优点 | 缺点 |
|---|---|
| **质量明显更高** | **成本至少翻倍** |
| 能发现自己的错误 | 延迟明显增加 |
| 评价标准可以很具体 | 评价者和生成者是同一个模型时，容易「自己看不出自己的错」 |

**最后一条要注意**：用同一个模型自评有盲区。**更有效的做法是让评价者用不同的模型，或者给它明确的检查清单而不是「你觉得好不好」。**

## 步骤 2 · 各实现一遍

### 这一步在做什么

三种都写出来，用同一组任务对比。

### 实现要点

**Plan-and-Execute 的关键**

用 U1.3 的结构化输出生成计划：

```python
# 先定义 PlanStep，Plan 才能直接引用它（否则要写成字符串前向引用再 rebuild）
class PlanStep(BaseModel):
    index: int
    description: str = Field(description="这一步具体做什么")
    # 要求每步指明工具，是逼模型写出能执行的步骤而不是「收集信息」这种空话
    required_tools: list[str] = Field(description="这一步可能用到的工具名")
    depends_on: list[int] = Field(default_factory=list, description="依赖哪些前置步骤的结果")


class Plan(BaseModel):
    goal: str = Field(description="用一句话说明最终要达成什么")
    # 限制步数：既控成本，也让模型把粒度定在能执行的层面
    steps: list[PlanStep] = Field(min_length=1, max_length=8)
```

**加上 `depends_on` 字段之后，你就能识别出可以并行的步骤**——没有依赖关系的步骤可以同时跑。这是 S6 编排引擎的雏形。

**Evaluator 的关键**

评价的 prompt 要给**具体的检查清单**，不要问「好不好」：

```python
# 给逐条可判断的清单，而不是问「好不好」：
# 主观提问时模型容易顺着自己的产出说好话，清单把要检查的点固定住，减少自评盲区
evaluator_prompt = """
检查下面的产出是否满足这些要求，逐条判断：

1. 是否引用了工具返回的真实数据（而不是编造）
2. 每个数据是否标明了来源和时间
3. 是否回答了用户的原始问题
4. 是否有明显的逻辑矛盾
5. 格式是否符合要求

对每条给出「通过/不通过」和理由。全部通过才算合格。
不通过的，给出具体的修改建议。
"""
```

**这个清单其实就是 S3 评估用的 rubric 的雏形。**

### 可能卡在哪

**规划出来的步骤很空泛**

「第一步：收集信息」这种没法执行。改进：

1. 在 prompt 里给一个好计划的例子
2. 要求每步指明用哪个工具
3. 限制步数（`max_length=8`），逼它写具体

**规划时模型不知道有哪些工具**

把工具列表（只要名字和一句话描述，不用完整 schema）放进规划的 prompt。

**反思循环里评价永远说不合格**

评价标准太严。检查：清单里有没有做不到的要求；有没有「主观」的判断项（「是否足够有洞察力」这种没法客观判断）。

**反思之后反而变差了**

有可能。**必须记录每次迭代的结果**，对比看是不是真的在改进。如果第 2 轮比第 1 轮差，说明评价意见误导了它。

### 背后的逻辑

三种模式对应人做事的三种方式：

| 模式 | 人的类比 |
|---|---|
| ReAct | 边做边看，走一步算一步 |
| Plan-Execute | 先列清单，再逐条做 |
| Evaluator-Optimizer | 做完自己检查，不满意就改 |

**它们可以组合。** 最常见的组合是：Plan-Execute 定框架，每个步骤内部用 ReAct，最后整体过一遍 Evaluator。

**但组合的成本是叠加的。** 先分别测清楚每种的收益，再决定值不值得组合。

## 步骤 3 · 做对比实验

### 这一步在做什么

**本单元的核心产出。**

### 怎么做

准备 10 个真实任务（从你的项目场景里选，难度有梯度）。三种模式各跑一遍，记录：

| 模式 | 成功率 | 平均轮次 | 平均成本 | 平均耗时 | 失败的是哪几个 |
|---|---|---|---|---|---|
| ReAct | /10 | | ¥ | s | |
| Plan-Execute | /10 | | ¥ | s | |
| Reflexion | /10 | | ¥ | s | |

**「成功」怎么判定**：你先人工定标准（就是 U1.4 学的那套），然后人工判或者用规则判。

### 加一列：稳定性

同一个任务跑 3 次，看结果一致吗：

| 模式 | 3 次结果一致的任务数 |
|---|---|
| ReAct | /10 |
| Plan-Execute | /10 |
| Reflexion | /10 |

**Plan-Execute 通常更稳定**，因为路径被计划约束住了。**这在生产环境里很重要**——用户不希望同一个操作每次结果都不一样。

### 你大概率会发现

| 任务特征 | 哪种更好 |
|---|---|
| 路径清晰、步骤可预见 | **Plan-Execute**（更稳、更省） |
| 需要根据中间结果大幅调整方向 | **ReAct** |
| 对输出质量要求高、能接受成本翻倍 | **Reflexion** |
| 简单任务（1-2 步） | **都不需要，直接一次调用** |

**最后一条很重要。** 如果你的任务只要一两步，加 Agent 循环是纯粹的浪费。

### 可能卡在哪

**三种差别不明显**

可能任务太简单。**加几个更难的任务**（需要 5 步以上、有分支判断的）。

**跑一轮实验成本太高**

30 次任务执行确实不便宜。两个办法：

1. 用便宜的模型做这个实验（定性结论通常一致）
2. 任务数减到 6 个，但保持难度梯度

**Reflexion 的成本高得离谱**

正常。它至少是 2 倍，如果迭代 3 次就是 4 到 6 倍。**这正是你要量化的东西**——知道它贵多少，才能判断值不值。

### 背后的逻辑

这个实验的方法论和 U1.4 的 prompt 对比是一样的：**控制变量、样本量够、看失败细节。**

S3 会把这套方法工程化。现在你做的是「手工版的评估」，S3 做的是「自动化的评估」。**方法论没变，只是变得可重复了。**

## 步骤 4 · 做出你的决定

### 这一步在做什么

从数据得出一个明确的、能讲清楚理由的结论。

### 输出这段结论

模板：

```
我的项目用 __________ 模式。

依据：
- 我的任务特征是 __________（路径是否确定、是否需要中途调整）
- 实验数据显示：__________ 的成功率是 __/10，比 __________ 高 __ 个百分点
- 成本代价是 __________，我认为值得/不值得，因为 __________
- 稳定性方面 __________

放弃 __________ 的原因是 __________。

在 __________ 这个特定环节，我会额外用 __________，因为 __________。
```

### 一个常见的正确答案

**很多项目的最优解是混合**：

```
主流程用 Plan-Execute（我的任务步骤基本固定，成本可控，用户能看到计划）。
每个步骤内部用简单的 ReAct（步骤内部可能需要重试和调整）。
只在「最终报告生成」这一步用 Reflexion（这是用户唯一看到的产出，质量优先）。
```

**这种「分环节采用不同模式」的思路，比全局选一种更实用。**

### 背后的逻辑

回到 U2.1 的必读文章那句话：**从最简单的方案开始，只在必要时增加复杂度。**

具体到这里，复杂度的阶梯是：

```
单次调用 < 工作流（写死的步骤） < ReAct < Plan-Execute < 加 Reflexion < 多 Agent
```

**每上一级都要有数据支持。** 「我觉得多 Agent 更高级」不是理由。

**这个判断力是面试里最容易拉开差距的地方。** 大多数人会说「我用了多 Agent 架构」，能说清楚「我测过，单 Agent 在我的场景下成功率只低 3%，但成本低 60%，所以我没拆」的人很少。
