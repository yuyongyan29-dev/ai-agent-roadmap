# U4.5 · 成本治理（10 小时）

**这个单元解决什么问题**

U3.8 的分析报告已经告诉你钱花在哪了。这个单元把它降下来。

**目标：成本降 40% 以上，评估分下降不超过 2%。**

**这个目标之所以能定，正是因为你有 S3 的评估体系。** 没有它，你不敢做任何优化——因为你不知道会不会把质量搞砸。

**学完你能做到**：一张表，列出每项优化的成本降幅和评估分变化。

---

## 步骤 0 · 建立工作方法

### 这一步在做什么

定一个纪律，贯穿本单元。

### 纪律：每改一项，跑一次评估

```
1. 记录当前基线：成本 ¥X，评估分 Y
2. 做一项优化
3. 跑评估
4. 记录：成本 ¥X'，评估分 Y'
5. 如果 Y' 掉太多，回退或调整
6. 通过就提交，更新基线
```

**一次只改一项。** 同时改三项的话，分数掉了你不知道是哪项的锅。

**这就是 U1.4 和 U2.3 反复练的控制变量法，现在它变成了日常工作方式。**

### 建一张追踪表

```markdown
| 优化项 | 成本前 | 成本后 | 降幅 | 评估分前 | 评估分后 | 变化 | 决定 |
|---|---|---|---|---|---|---|---|
| 基线 | ¥0.315 | - | - | 0.84 | - | - | - |
| 压缩检索结果 | ¥0.315 | ¥0.198 | -37% | 0.84 | 0.83 | -0.01 | **采用** |
| ... | | | | | | | |
```

**这张表就是本单元的核心产出。**

## 步骤 1 · 优先攻击最大的成本项

### 这一步在做什么

按 U3.8 的分析结论，从占比最大的开始。

### 最常见的第一名：上下文太长

U3.8 的典型发现是「输入 token 占成本的 70% 以上，而输入里检索结果又占大头」。

**四个手段，从简单到复杂：**

**手段一：减少 top_k**

```python
# 从 top-5 降到 top-3
```

立刻见效，改一个数字。**跑评估看质量掉多少。**

**如果掉得不多，这是性价比最高的优化。** 因为 rerank 之后的第 4、5 名本来质量就一般。

**手段二：给每个片段加长度上限**

U3.8 可能发现「异常昂贵的任务是因为检索到了超长文档」。

```python
def 截断片段(片段: str, 上限: int = 1500) -> str:
    if len(片段) <= 上限:
        return 片段
    return 片段[:上限] + f"\n...（本片段已截断，原长 {len(片段)} 字符）"
```

**这一项主要消除异常值**，对均值影响不大，但能显著降低 P95 和 P99。

**手段三：先压缩再进上下文**

对检索到的片段做一次压缩：只保留和问题相关的部分。

```python
async def 压缩片段(问题: str, 片段: str) -> str:
    return await 小模型.对话([
        消息.system("从下面的资料里，只提取和问题直接相关的内容，逐字保留原文，不要改写。无关的直接省略。"),
        消息.user(f"问题：{问题}\n\n资料：{片段}"),
    ])
```

**注意「逐字保留原文，不要改写」**——改写会引入新的错误。

**代价**：每个片段一次额外调用。用小模型 + 并发能控制住。**算一下：3 个片段 × 小模型的价格，是不是比省下的 token 便宜。**

**手段四：外部化**

U1.5 学的。长文档存文件，上下文里只放摘要和路径，模型需要时用工具去读。

**收益最大，但要多一轮工具调用。**

### 可能卡在哪

**压缩之后质量掉太多**

看是哪几条评估题掉了。**通常是那些需要完整上下文才能答的题。**

折中：**按问题类型决定压缩强度**。简单查询用激进压缩，复杂分析用宽松压缩。

**改了 top_k 之后召回率不够了**

回到 U2.5 的检索评测集，先确认 top-3 的召回率是多少。如果召回率掉太多，说明不能减，要从别的地方省。

## 步骤 2 · 模型路由

### 这一步在做什么

**让简单的活走便宜的模型。**

### 你已经有数据了

U1.7 测过本地模型的能力边界，U1.2 的 `models.yaml` 有各模型的价格。**现在把它们用起来。**

### 三层路由

```python
async def 选模型(任务类型: str, 复杂度: str) -> str:
    表 = {
        ("意图分类", "任意"): "ollama/qwen3:8b",        # 本地，免费
        ("关键词抽取", "任意"): "ollama/qwen3:8b",
        ("片段压缩", "任意"): "deepseek/deepseek-v4-flash",  # 便宜的云端
        ("工具选择", "简单"): "deepseek/deepseek-v4-pro",
        ("工具选择", "复杂"): "claude-sonnet-5",
        ("最终生成", "任意"): "claude-sonnet-5",         # 用户唯一看到的，质量优先
    }
    return 表.get((任务类型, 复杂度)) or 表.get((任务类型, "任意")) or 默认模型
```

### 复杂度怎么判断

**方式一：规则（优先）**

```python
def 判断复杂度(输入: str, 上下文长度: int) -> str:
    if 上下文长度 > 8000: return "复杂"
    if len(输入) > 200: return "复杂"
    if 任何关键词(输入, ["对比", "分析", "为什么", "如何"]): return "复杂"
    return "简单"
```

**零成本，先用这个。**

**方式二：小模型分类**

规则判不准时，用一次小模型调用来判断。**成本很低，但要确认它比规则准。**

### 必须做的验证

**每个路由决定都要单独验证**：

| 环节 | 原模型 | 新模型 | 评估分变化 | 成本变化 |
|---|---|---|---|---|
| 意图分类 | claude-sonnet-5 | ollama/qwen3:8b | -0.00 | **-100%** |
| 片段压缩 | claude-sonnet-5 | deepseek-flash | -0.01 | -92% |
| 工具选择（简单） | claude-sonnet-5 | deepseek-pro | **-0.04** ⚠️ | -85% |

**上面第三行掉了 0.04，超过了 2% 的容忍线。** 处理方式：

1. 给便宜模型单独写一版更详细的 prompt（U1.4 步骤 5 讲过 prompt 不通用）
2. 或者放弃这个路由

### 可能卡在哪

**换了模型 prompt 就不работает了**

正常。**为便宜的模型单独维护一版 prompt**：

```
prompts/工具选择/
├── v3.md              # 给强模型
└── v3-small.md        # 给小模型，指令更详细，例子更多
```

**降级链**

主模型挂了怎么办？配一个 fallback：

```python
模型链 = ["claude-sonnet-5", "deepseek/deepseek-v4-pro", "ollama/qwen3:8b"]
for m in 模型链:
    try:
        return await llm.对话(消息, 模型=m)
    except (限流, 服务不可用):
        continue
```

**这既是成本手段也是可用性手段。**

## 步骤 3 · 缓存

### 这一步在做什么

不要为同样的事付两次钱。

### 三种缓存

**一、Prompt caching（U1.6 学过）**

**关键是把上下文按「变化频率」排序**，固定的放前面：

```
[固定] 系统提示 + 工具定义 + few-shot 示例    ← 可缓存
[变化] 长期记忆 + 检索结果 + 对话历史 + 当前输入
```

**检查你的实现有没有把变化的东西放前面。** 一个时间戳就能让缓存永远失效。

**二、工具结果缓存**

确定性的、只读的工具，结果可以缓存：

```python
@缓存(ttl=300, 条件=lambda t: t.只读 and t.确定性)
async def 执行工具(名字, 参数): ...
```

**缓存键**：`工具名 + 参数的规范化哈希`。

**注意**：

- 只缓存只读工具，**有副作用的绝不缓存**
- TTL 要短（数据会变）
- **按用户隔离**，否则会串数据

**三、语义缓存（谨慎使用）**

相似的问题复用答案。

**风险很大**：「北京今天天气」和「北京明天天气」语义相似度很高，但答案完全不同。

**建议**：只在明确的场景用（比如 FAQ），并且相似度阈值设得很高（0.95 以上）。

### 可能卡在哪

**prompt cache 一直不命中**

U1.6 的排查清单：前缀是否完全一致、长度是否达到门槛、间隔是否超过有效期。

**打印出实际发送的前 500 个字符，两次调用 diff 一下。** 通常一眼就能看出哪里变了。

**缓存导致数据不一致**

给缓存加版本号，数据更新时 bump 版本，旧缓存自然失效。

## 步骤 4 · 限流与配额

### 这一步在做什么

**防止单个用户或单个失控的任务烧光你的预算。**

### 三层限制

**一、单任务预算**

U2.1 的护栏已经有了。**检查数值是否合理**：设成 P99 的 1.5 倍左右。

**二、用户配额**

```sql
CREATE TABLE 用户配额 (
    用户id      TEXT PRIMARY KEY,
    日限额      NUMERIC(10,2) DEFAULT 5.00,
    月限额      NUMERIC(10,2) DEFAULT 50.00,
    今日已用     NUMERIC(10,4) DEFAULT 0,
    本月已用     NUMERIC(10,4) DEFAULT 0,
    重置日期     DATE
);
```

**检查要在任务开始前做**，而不是结束后：

```python
async def 检查配额(用户id: str, 预估成本: float):
    配额 = await 取配额(用户id)
    if 配额.今日已用 + 预估成本 > 配额.日限额:
        raise 配额不足(f"今日额度剩余 ¥{配额.日限额 - 配额.今日已用:.2f}")
```

**「预估成本」怎么算**：用历史数据的均值，或者按最大轮次 × 单轮均价的保守估计。

**三、全局熔断**

```python
async def 全局检查():
    今日总成本 = await 查今日总成本()
    if 今日总成本 > 全局日预算:
        await 进入降级模式()      # 只服务已有任务，拒绝新任务
        await 发告警("全局预算耗尽，已进入降级模式")
```

### 可能卡在哪

**配额扣减和任务执行的一致性**

任务开始前先「预扣」，结束后按实际用量「结算」（多退少补）。**这两步都要在事务里。**

**用户抱怨配额太少**

配额是保护你自己的。**先设保守，再根据实际使用调整。**

## 步骤 5 · 减少轮次

### 这一步在做什么

**一个容易被忽略但很有效的优化方向。**

### 为什么轮次贵

每一轮都要重发全部上下文（HTTP 无状态，U0.5 讲过）。**而且上下文是递增的**，第 5 轮比第 1 轮贵得多。

**减少一轮，省的不只是一次调用的钱。**

### 三个手段

**一、并行工具调用**

如果模型一次返回多个工具调用，并行执行（U2.1 提过）：

```python
结果们 = await asyncio.gather(*[执行(tc) for tc in 工具调用们])
```

**注意**：有副作用的工具不要并行，或者要确认它们互不冲突。

**二、合并工具**

U2.2 步骤 5 讲的分层工具。如果模型经常连续调用「搜索」再「读详情」，考虑合并成一个「搜索并返回详情」的工具。

**用 trace 数据找出高频的工具调用序列**：

```sql
-- 找出常见的相邻工具调用对
SELECT a.name, b.name, count(*)
FROM spans a JOIN spans b ON b.parent_id = a.parent_id AND b.seq = a.seq + 1
WHERE a.type = 'tool' AND b.type = 'tool'
GROUP BY 1, 2 ORDER BY 3 DESC LIMIT 10;
```

**三、更好的系统提示**

有时轮次多是因为模型不知道该怎么做，在试错。**在系统提示里给出典型的工作流程**，能显著减少探索的轮次。

**这个改动零成本，先试它。**
