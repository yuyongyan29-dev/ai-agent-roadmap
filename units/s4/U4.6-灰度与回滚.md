# U4.6 · 灰度与回滚（10 小时）

**这个单元解决什么问题**

现在你发新版本的方式是：改代码，部署，祈祷。

**灰度让你先用 5% 的流量验证，回滚让你在两分钟内退回去。**

**学完你能做到**：两个版本同时在线，按比例分流，看板上能分别看到各自的表现；一键回滚并演练过。

---

## 步骤 1 · 给一切可变的东西加版本

### 这一步在做什么

**你要能精确回答：这次请求用的是哪个版本的什么。**

### 需要版本化的东西

| 项 | 怎么标识 | 怎么切换 |
|---|---|---|
| **代码** | git commit sha | 部署 |
| **Prompt** | 文件版本号（U1.4 建的） | 改配置，不用发版 |
| **模型选择** | models.yaml 里的配置 | 改配置 |
| **工具集** | 工具注册的配置 | 改配置 |
| **参数**（top_k、温度、轮次上限） | 配置文件 | 改配置 |

**关键设计：把「不用发版就能改的东西」和「必须发版的代码」分开。**

### 打包成「配置版本」

```yaml
# configs/v7.yaml
version: v7
description: 减少 top_k，意图分类换本地模型
# base 指向上一个版本：只写和它不同的部分，加载时合并，避免每个版本都抄一遍全量配置
base: v6

# 三个环节各自引用 prompt 的版本号（U1.4 建的），改 prompt 不用改这里的代码
prompts:
  intent_classify: v2
  tool_select: v4
  final_generate: v3

# 模型是按环节配的，不是全局一个：便宜的活给本地模型，难的活才用大模型
models:
  intent_classify: ollama/qwen3:8b
  tool_select: claude-sonnet-5
  final_generate: claude-sonnet-5

# 所有「改一个数字就会改变行为」的旋钮都收在这里，不散落在代码各处
params:
  top_k: 3
  rerank_candidates: 30
  max_turns: 15
  max_cost: 2.0
  snippet_max_length: 1500

# 工具集也算版本的一部分：少给一个工具，Agent 的行为就完全不同
tools: [search_notes, read_detail, calc_engagement, save_draft, publish]
```

**一个 YAML 文件定义一个完整的行为版本。**

### 加载与记录

```python
class ConfigVersion(BaseModel):
    """一个完整行为版本的定义。

    用 Pydantic 而不是裸 dict，是为了让 CI 能直接校验 YAML 格式——
    配置改错和代码改错一样会把线上搞挂，必须在合并前拦下来。
    """

    version: str
    prompts: dict[str, str]
    models: dict[str, str]
    params: dict
    tools: list[str]


def load_config(version: str) -> ConfigVersion:
    # 文件名就是版本号。model_validate 让格式错误在启动时立刻暴露，
    # 而不是等线上跑到某个分支才发现少了一个键
    return ConfigVersion.model_validate(yaml.safe_load(Path(f"configs/{version}.yaml").read_text()))
```

**每条 trace 都要带上配置版本**（U3.5 已经埋了 metadata，现在把它填对）：

```python
trace = lf.trace(
    metadata={
        # 两个版本号缺一不可：config_version 回答「行为为什么变了」，
        # code_version 回答「是哪次部署引入的」
        "config_version": config.version,
        "code_version": os.getenv("GIT_SHA"),
    },
)
```

**没有这个标签，你无法回答「这个问题是哪个版本引入的」。**

### 可能卡在哪

**配置越来越多，管理麻烦**

用继承：`base: v6` 表示只写和 v6 不同的部分，加载时合并。

**配置改错了导致线上出问题**

配置文件也要进 git、走 review、有 CI 校验（用 Pydantic 模型验证格式）。**它和代码一样重要。**

## 步骤 2 · 按比例分流

### 这一步在做什么

让一部分流量走新版本。

### 关键：同一用户始终看到同一版本

**不能随机分。** 否则同一个用户这次看到 A 版的行为，下次看到 B 版，体验会精神分裂。

**用用户 id 的哈希**：

```python
import hashlib

def pick_version(user_id: str, split_config: dict, experiment: str) -> str:
    """给一个用户选定版本。

    split_config 示例：{"v6": 90, "v7": 10}，即 v6 占 90%、v7 占 10%。
    """
    # 用哈希取模而不是随机数：同一个用户每次都落在同一个桶里，
    # 不会这次看到 v6 的行为、下次看到 v7 的行为。
    # 把 experiment 拌进哈希，是让同一个用户在不同实验里落到不同的组，
    # 否则几个实验会永远绑定同一批人，互相污染结论
    h = int(hashlib.sha256(f"{user_id}:{experiment}".encode()).hexdigest()[:8], 16)
    bucket = h % 100

    # sorted 保证遍历顺序稳定：dict 顺序一变，同样的配置在不同进程里会切出不同结果
    cumulative = 0
    for version, weight in sorted(split_config.items()):
        cumulative += weight
        if bucket < cumulative:
            return version
    # 权重之和不足 100 时的兜底，回落到第一个版本，不要在请求路径上抛异常
    return list(split_config)[0]
```

**加 `experiment` 到哈希里**：这样不同的实验，同一个用户会被分到不同的组，避免实验之间互相干扰。

### 分流配置放哪

**不能写在代码里**（改一次要发版）。放数据库或配置服务：

```sql
-- 分流配置是「数据」不是「代码」：改比例只是一条 UPDATE，秒级生效，不用发版。
-- 自动回滚也是改这张表，所以它必须在数据库里而不是在配置文件里。
CREATE TABLE traffic_split (
    experiment   TEXT PRIMARY KEY,
    config       JSONB NOT NULL,        -- {"v6": 90, "v7": 10}
    status       TEXT DEFAULT '进行中',
    -- 出问题时第一件事是查「谁在什么时候改了比例」，这两列就是为复盘留的
    updated_at   TIMESTAMPTZ DEFAULT now(),
    updated_by   TEXT
);
```

**改分流比例 = 改一行数据，秒级生效。**

### 灰度节奏

```
5% → 观察 1 天 → 20% → 观察 1 天 → 50% → 观察 1 天 → 100%
```

**每一档都要看指标再决定是否推进。**

对个人项目可以快一些，但**不要直接 0% 跳到 100%**。

### 可能卡在哪

**只有我一个用户，怎么灰度**

用「会话」而不是「用户」做分流单位。或者手动切换：这次用 v6，下次用 v7，各跑几次对比。

**更实际的做法**：**用评估集当灰度前的验证**。评估集通过了才上灰度。你的评估集就是你的「模拟用户」。

**新版本的效果需要时间才能看出来**

对，所以要有观察期。**指标要选那些能快速反映问题的**：错误率、延迟、成本立刻能看到；质量分需要在线评估（U3.6）积累一些样本。

## 步骤 3 · 按版本切分看板

### 这一步在做什么

**能同时看到两个版本的表现，才叫灰度。**

### 需要按版本切分的指标

| 指标 | 从哪来 |
|---|---|
| 成功率 / 错误率 | trace 的状态 |
| 在线评分 | U3.6 的采样评估 |
| 用户反馈 | U3.6 的显式和隐式信号 |
| 平均成本 | trace 的 cost |
| P95 延迟 | trace 的耗时 |
| 平均轮次 | trace 的 metadata |

### 对比视图

```
                        v6 (90%)      v7 (10%)     差异
任务数                   1240           138
成功率                   94.2%          95.7%       +1.5%
在线评分                  0.83           0.85       +0.02
用户点踩率                 3.1%           2.2%       -0.9%
平均成本                 ¥0.315         ¥0.176      -44%  ✓
P95 延迟                  18.2s          16.4s      -10%
平均轮次                   4.3            3.9
```

**这就是灰度的价值**：你能在小流量上看到全部这些指标，而不是全量上线后才发现问题。

### 样本量的问题

**138 个样本能说明问题吗？**

看差异大小：

- **成本降 44%** —— 确定，因为这是机制性的改变，不是统计波动
- **成功率 +1.5%** —— 138 个样本上的 1.5% 是 2 个任务，**说明不了任何问题**
- **点踩率 -0.9%** —— 同上

**判断原则**：机制性的改变（成本、延迟）小样本就能看出；概率性的改变（成功率、评分）需要大样本。

**不要在小样本上对概率性指标下结论。**

### 可能卡在哪

**样本量永远不够**

个人项目确实如此。**替代方案**：

1. 主要靠离线评估集判断质量（样本可控、可重复）
2. 灰度主要看「有没有明显的崩溃」（错误率、超时），而不是「质量提升了多少」

**这是个人项目的现实约束，写在文档里，别假装做了严谨的 A/B 实验。**

## 步骤 4 · 自动回滚

### 这一步在做什么

出问题时不用你手动介入。

### 触发条件

```python
async def should_rollback(experiment: str) -> tuple[bool, str]:
    # 对照组和实验组必须取同一个时间窗：不同时段的流量构成不一样，
    # 跨窗对比会把「晚上问题更难」当成「新版本更差」
    control = await get_metrics(experiment, version="control", window="1h")
    treatment = await get_metrics(experiment, version="treatment", window="1h")

    # 最小样本门槛。灰度刚开的几分钟里两三条异常请求就能把错误率顶到 100%，
    # 没这道闸门会天天误回滚
    if treatment.sample_count < 20:
        return False, "样本不足"

    # 硬性条件：任何一条触发就回滚。
    # 阈值都取「明显劣化」（2 倍、1.5 倍）而不是「略差」，给正常波动留出空间
    if treatment.error_rate > control.error_rate * 2:
        return True, f"错误率 {treatment.error_rate:.1%} 是对照组的 2 倍以上"
    if treatment.p95_latency > control.p95_latency * 1.5:
        return True, f"P95 延迟 {treatment.p95_latency:.1f}s 超过对照组 1.5 倍"
    if treatment.avg_cost > control.avg_cost * 1.5:
        return True, "成本超过对照组 1.5 倍"
    # 评分是 0~1 的绝对值，用差值判断比用倍率更直观
    if treatment.online_score < control.online_score - 0.1:
        return True, "在线评分明显低于对照组"

    return False, "正常"
```

**注意都是「明显劣化」的阈值，不是「略差就回滚」。** 否则正常波动会触发误回滚。

### 执行回滚

```python
async def rollback(experiment: str, reason: str):
    # 回滚就是把流量全部拨回对照组版本，一条 UPDATE 的事，不需要重新部署
    await update_traffic_split(experiment, {"control_version": 100})
    # 审计和告警都不能省：自动回滚如果悄无声息，
    # 第二天没人知道线上换过版本，也没人去查真正的原因
    await write_audit(action="自动回滚", detail=reason)
    await send_alert(f"🔴 已自动回滚 {experiment}\n原因：{reason}")
```

**回滚就是改一行数据库记录**，因为分流配置在数据库里（步骤 2 的设计）。

### 回滚必须比发布快

| 操作 | 目标时间 |
|---|---|
| 改配置版本（prompt、参数、模型） | **秒级** |
| 回滚代码 | 分钟级 |

**这就是为什么要把「配置」和「代码」分开** —— 大部分问题改配置就能解决，不用等重新部署。

### 可能卡在哪

**回滚了但问题还在**

说明问题不在新版本。**回滚只是止血，不是治疗。** 回滚后要查真正的原因。

**误回滚**

阈值太敏感，或者样本太少。**加一个最小样本数的门槛**（上面代码里的 20）。

**代码怎么回滚**

用容器镜像的 tag。部署时打上 git sha，回滚就是部署上一个 tag。**保留最近几个版本的镜像。**

## 步骤 5 · 演练

### 这一步在做什么

**回滚流程只有演练过才算数。**

### 演练一：配置回滚

1. 把某个 prompt 改成明显有问题的版本，发布为 v8
2. 灰度 20%
3. 观察指标劣化
4. **触发回滚，记录耗时**
5. 确认流量全部回到 v7

**目标：从发现问题到完成回滚，不超过 2 分钟。**

### 演练二：代码回滚

1. 部署一个有 bug 的版本
2. 回滚到上一个镜像 tag
3. **记录耗时**

**目标：不超过 10 分钟。**

### 演练三：自动回滚

1. 部署一个会大量报错的版本
2. **不要手动干预**
3. 观察自动回滚是否触发
4. 确认收到了告警

### 记录

```markdown

| 演练 | 发现问题 | 完成回滚 | 总耗时 | 结果 |

| 配置回滚 | 14:03 | 14:04 | 1分12秒 | ✓ |
| 代码回滚 | 14:20 | 14:26 | 6分30秒 | ✓ |
```

**「发现的问题」这一段是演练的真正价值。** 不演练的话，这些问题会在真实事故时才暴露。
