# U4.1 · 12-Factor 自查（6 小时）

**这个单元解决什么问题**

用一套成熟的检查表，把你项目里所有「demo 能跑但上不了生产」的硬伤找出来。

**这一单元不写代码，它产出的是后面七个单元的待办清单。**

**必读**：[humanlayer/12-factor-agents](https://github.com/humanlayer/12-factor-agents)（2.6 万 star）。

**重要提醒**：这个仓库最后一次更新是 2025 年 9 月，部分工具和示例已过时。**按原则读，别按代码抄。** 十二条原则本身依然成立。

---

## 步骤 1 · 通读并理解每一条

### 这一步在做什么

先读一遍，理解每条原则在说什么，以及它防的是什么问题。

### 十二条的核心问题

（以仓库当前版本为准，下面是每条要问自己的问题。）

**1. 自然语言到工具调用**
你的系统怎么把用户的话变成结构化的动作？这个转换是可控、可测的吗？

**2. 拥有你的 prompt**
prompt 是不是被框架藏起来了？你能看到实际发出去的完整 prompt 吗？

**3. 拥有你的上下文窗口**
上下文是你显式组装的，还是框架偷偷帮你拼的？你知道每一部分占多少吗？

**4. 工具就是结构化输出**
你有没有把「工具」想得太神秘？它本质上就是模型输出一个结构化对象，你的代码去执行。

**5. 统一执行状态和业务状态**
「跑到第几步」和「业务数据是什么」是分开存的两套东西吗？它们会不会不一致？

**6. 用简单的 API 来启动/暂停/恢复**
能从外部暂停一个跑到一半的任务，之后恢复吗？

**7. 用工具调用来联系人类**
「向用户提问」「请求确认」是不是也实现成了工具？还是硬编码在流程里？

**8. 拥有你的控制流**
循环、分支、重试的逻辑是你写的，还是框架的黑盒？出问题你能改吗？

**9. 把错误压缩进上下文窗口**
错误信息是怎么回填给模型的？会不会把上下文撑爆？重复的错误会不会累积？

**10. 小而专的 Agent**
你的 Agent 是一个什么都管的巨无霸，还是几个职责清晰的小 Agent？

**11. 从任何地方触发，在任何地方交付**
只能从命令行跑，还是能被 API、定时任务、消息事件触发？

**12. 让你的 Agent 成为无状态的 reducer**
给定 (当前状态, 新事件) 能确定地算出 (新状态)？还是依赖内存里的隐藏状态？

### 可能卡在哪

**有几条看不懂**

第 12 条最抽象。它说的是：**把 Agent 想成一个纯函数**。

```
新状态 = Agent(旧状态, 事件)
```

好处是：状态可以存、可以传、可以重放。**任何时候拿到一个状态快照，就能从那里继续跑。** 这是 U4.2 断点续跑的理论基础。

反面例子是：Agent 在内存里存了一堆东西（当前轮次、已调用的工具、缓存），进程一死全没了。

**第 5 条和第 12 条像是重复的**

第 5 条讲「别分成两套」，第 12 条讲「状态要能外部化」。**第 5 条是前提，第 12 条是目标。**

## 步骤 2 · 逐条自查

### 这一步在做什么

**对照你的实际代码**，不是凭印象。

### 自查表格式

```markdown
## 条目 3：拥有你的上下文窗口

**原则说什么**
上下文的组装应该是你显式控制的，而不是框架的黑盒行为。

**我的现状**
用 LangGraph 的 MessagesState，消息是自动累加的。我没有显式控制过。
实际发出去的 prompt 我没看过完整版。

**差距**
1. 不知道每次实际发了多少 token、各部分占比多少
2. 长对话时没有压缩策略生效（U1.5 写的代码在 S2 项目里没接上）
3. 工具定义每轮全量重发，20 个工具约 3000 tokens

**严重程度**
高。这直接导致成本失控（U3.8 的分析显示上下文是成本大头）。

**改进项**
- [ ] 在 llm_kit 里加上下文组装日志，每次打印各部分 token 数
- [ ] 把 U1.5 的压缩策略接进 S2 的 Agent
- [ ] 评估工具分组加载（U2.2 步骤 5 的方案）

**排期**
U4.2 一起做（都涉及状态管理）
```

### 三个要求

**一、每条都要写现状，不能空着。**

**二、不能有「不适用」。** 如果你真的觉得某条不适用，写清楚为什么。大多数「不适用」其实是「我还没想清楚」。

**三、严重程度要分级。** 高/中/低，依据是「不改会出什么后果」。

### 可能卡在哪

**十二条全是「高」**

正常，第一次自查大多数项目都很惨。**按「不改会出什么后果」排序**：

| 后果 | 级别 |
|---|---|
| 会丢数据、会重复扣款、会泄露信息 | 高 |
| 会导致成本失控或体验差 | 中 |
| 影响可维护性 | 低 |

**发现某条我完全没考虑过**

**这就是自查的价值。** 记下来，不要跳过。

## 步骤 3 · 排出优先级清单

### 这一步在做什么

把自查结果变成 U4.2 到 U4.8 的实际待办。

### 怎么排

**按「影响 × 紧急」排，不是按条目顺序。**

| 改进项 | 对应条目 | 严重度 | 在哪个单元做 |
|---|---|---|---|
| 状态外部化，支持断点续跑 | 5, 6, 12 | 高 | U4.2 |
| 非幂等工具加保护 | 5 | 高 | U4.2 |
| 长任务异步化 | 6, 11 | 高 | U4.3 |
| 高危操作人工确认 | 7 | 高 | U4.4 |
| 提示注入防御 | - | 高 | U4.4 |
| 上下文显式控制 + 压缩 | 3 | 中 | U4.5 |
| 错误压缩，防止累积 | 9 | 中 | U4.5 |
| prompt 版本可追溯 | 2 | 中 | U4.6 |
| 支持多种触发方式 | 11 | 低 | U4.7 |
| 拆分巨无霸 Agent | 10 | 低 | 视情况 |

### 关于第 10 条「小而专的 Agent」

**注意这条和 U2.6 的结论可能冲突。**

U2.6 你可能测出「不拆更好」。那 12-factor 的这条怎么办？

**理解上的关键**：这条说的是「Agent 的职责边界要清晰」，不一定是「拆成多个进程」。

一个 Agent 只做一类事、系统提示不超过一页、工具不超过 10 个——**这就已经是「小而专」了**，不需要真的拆成多 Agent 架构。

**如果你的 Agent 有 30 个工具、系统提示三页长、什么都能干，那才是需要拆的信号。**

## 步骤 4 · 补充你自己的检查项

### 这一步在做什么

12-factor 是通用原则，你的项目可能有它没覆盖的问题。

### 常见的额外检查项

| 项 | 问题 |
|---|---|
| **密钥管理** | 密钥有没有轮换机制？泄露了怎么办？ |
| **数据保留** | trace 里的用户数据存多久？怎么删？ |
| **依赖健康** | 外部服务挂了，你的 Agent 怎么表现？ |
| **配额与限流** | 单个用户能不能烧光你的预算？ |
| **可回滚性** | 上一个版本的代码 + 上一个版本的 prompt，能不能一键回去？ |
| **冷启动** | 新环境从零部署要多久？步骤有文档吗？ |

**把和你项目相关的补进自查表。**

## 完成判据

**产出**：`s4-production/12factor_audit.md`

**动手部分**

- [ ] 通读 12-factor-agents 全文
- [ ] **十二条每条都有：原则说什么、我的现状、差距、严重程度、改进项**
- [ ] 没有「不适用」这种敷衍答案
- [ ] 严重程度按「不改会出什么后果」分级
- [ ] 排出优先级清单，每项对应到 U4.2 到 U4.8 的某个单元

**关键验证**：把自查表给一个不了解你项目的人看，**他能不能从这份表理解你的系统现在有哪些风险。**

如果他看不懂，说明你写得太笼统。

**理解检查**（笔记里回答）

1. 第 12 条「无状态 reducer」是什么意思？它和断点续跑有什么关系？
2. 「小而专的 Agent」一定要拆成多个进程吗？判断信号是什么？
3. 你的自查里，哪三条是「高」严重度？各会导致什么后果？
4. 12-factor 没覆盖但你的项目需要的检查项是什么？
5. 为什么这个仓库停更了但原则依然值得读？
