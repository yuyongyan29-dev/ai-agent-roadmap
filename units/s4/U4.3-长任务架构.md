# U4.3 · 长任务架构（12 小时）

**这个单元解决什么问题**

你的 Agent 一个任务可能跑十分钟。现在的做法是：用户发一个 HTTP 请求，然后一直等着。

这有四个问题：**HTTP 连接会超时；用户看不到进度；刷新页面就断了；服务器重启所有正在跑的任务全废。**

**学完你能做到**：任务异步执行，客户端断线重连后能看到断开期间的全部进度。

---

## 步骤 1 · 改成异步接口

### 改造前后的对比

```
改造前（同步）：
  客户端 ──POST /run──▶ 服务器 ├────── 跑 10 分钟 ──────┤ ──▶ 结果
                              ▲
                    HTTP 连接一直占着
                    ✗ 网关超时  ✗ 看不到进度
                    ✗ 刷新就断  ✗ 服务重启全废

改造后（异步）：
  客户端 ──POST /tasks──▶ 建任务，入队 ──▶ 202 + task_id
                                  │
                            ┌─────▼─────┐
                            │  Worker   │ 后台跑
                            │  每步存    │
                            │ checkpoint │──▶ task_events 表
                            └───────────┘         │
  客户端 ──GET /tasks/{id}/events────────────────▶ │ SSE 推送
         （断线后带 last_event_id 重连，补齐中间事件）│
  客户端 ──GET /tasks/{id}──────────────────────▶ 查状态
  客户端 ──POST /tasks/{id}/cancel──────────────▶ 取消
```



### 这一步在做什么

把「一个请求跑完全程」拆成「提交、查询、订阅、取消」四个接口。

### 接口设计

```python
@app.post("/tasks", status_code=202)
async def submit_task(payload: TaskInput, user: CurrentUser) -> TaskResponse:
    """立刻返回 task_id，任务进队列"""
    # 这个函数里绝不能做任何耗时的事：它唯一的职责是把任务落库并入队，
    # 让 HTTP 连接在毫秒级就断开，真正的执行交给 worker
    task_id = generate_id()
    # 建任务时就记下 user_id，后面查状态/订阅事件都靠它做归属校验
    await create_task(task_id, user.id, payload)
    await enqueue(task_id)
    return TaskResponse(task_id=task_id, status="pending")


@app.get("/tasks/{task_id}")
async def get_task_detail(task_id: str, user: CurrentUser) -> TaskDetail:
    """当前状态、已完成的步骤、结果"""
    task = await fetch_task(task_id)
    # task_id 是可猜的字符串，不校验归属就等于任何人都能读别人的任务
    check_ownership(task, user)
    steps = await fetch_steps(task_id)
    return TaskDetail(
        status=task.status,
        current_step=task.current_step,
        steps=steps,
        result=task.result,
    )


@app.get("/tasks/{task_id}/events")
async def subscribe_events(task_id: str, user: CurrentUser, last_event_id: int = 0):
    """SSE 流式推送事件，从 last_event_id 之后开始"""
    # last_event_id 是断线续传的关键：客户端报出它收到的最后一个事件 id，
    # 服务端只补发之后的，既不漏也不重
    ...


@app.post("/tasks/{task_id}/cancel")
async def cancel_task(task_id: str, user: CurrentUser):
    # 取消只是打一个标记，由 worker 在下一个步骤边界自己退出，
    # 不要试图从外部杀掉正在跑的协程，那样 checkpoint 会丢
    ...


@app.post("/tasks/{task_id}/resume")
async def resume_task(task_id: str, user: CurrentUser, decision: HumanDecision | None = None):
    """从 paused 状态恢复，可带上人工确认的结果"""
    # decision 用来把「人批准了/否决了」这个外部输入喂回任务，
    # 没有它的话人工确认环节没法闭环
    ...
```

**`202 Accepted` 这个状态码的语义就是「已接受，还在处理」。** 用它而不是 200。

### 可能卡在哪

**用户希望「就等着拿结果」**

前端可以在提交后自动订阅事件流，体验上和同步一样，但底层是异步的。**S5 会做这个。**

**要不要提供同步接口作为兼容**

可以提供一个「提交并等待，最多 N 秒」的接口，超时就返回 task_id 让客户端去轮询。**但不要让它成为主路径。**

## 步骤 2 · 任务队列

### 这一步在做什么

让任务在后台被 worker 消费。

### 不要一上来就上 Celery

**小项目用 Postgres 当队列就够了**，而且和你的事务天然一致。

```sql
-- 取一个待处理的任务，同时加锁
SELECT * FROM tasks
WHERE status = 'pending'
  -- 锁带 TTL：worker 崩溃后锁会过期，任务能被别人接手，不会永远卡住
  AND (lock_expires_at IS NULL OR lock_expires_at < now())
ORDER BY created_at          -- 先进先出，避免老任务被一直插队
LIMIT 1
FOR UPDATE SKIP LOCKED;      -- 跳过已被别的 worker 锁住的行，而不是排队等它
```

**`SKIP LOCKED` 是关键**：多个 worker 同时查，各自拿到不同的任务，不会互相阻塞。

Worker 循环：

```python
async def worker(worker_id: str):
    # should_stop 是优雅关闭的开关（步骤 5），循环条件放这里意味着
    # 收到停止信号后不再领新任务，但当前这一轮会正常跑完
    while not should_stop:
        task = await claim_pending_task(worker_id)
        if task is None:
            # 队列空时短暂休眠，否则空转会把数据库打满
            await asyncio.sleep(1)
            continue
        try:
            await run_task(task.id)          # U4.2 写的
        except Exception:
            # 捕获所有异常：一个任务炸了不能让整个 worker 进程退出，
            # 否则队列里其他任务全都停摆
            logger.exception("任务 %s 失败", task.id)
            await mark_failed(task.id)
```

### 什么时候需要专门的队列

| 场景 | 需要 |
|---|---|
| 每秒几个任务 | Postgres 够 |
| 每秒几百个任务 | 需要 Redis 或专门的队列 |
| 需要优先级、延迟执行、重试策略 | 用 [ARQ](https://arq-docs.helpmanual.io/)（基于 Redis，轻量）或 Celery |
| 需要跨语言 | 消息队列（RabbitMQ / Kafka） |

**你的项目大概率永远不需要超出 Postgres。**

### 可能卡在哪

**worker 怎么部署**

三种：

1. 和 API 同一个进程，用 `asyncio.create_task` 起一个后台循环。**最简单，适合个人项目**
2. 同一个镜像，不同的启动命令（`uvicorn` vs `python worker.py`）
3. 完全独立的服务

**建议从第 1 种开始**，需要扩展时再拆。

**任务卡死了怎么办**

锁有 TTL（U4.2），过期后别的 worker 会接手。但要小心：**如果任务本身有 bug 导致每次都卡死，会被反复重试。**

加一个重试次数上限：

```sql
ALTER TABLE tasks ADD COLUMN retry_count INTEGER DEFAULT 0;
```

超过 3 次就标记为 failed，不再自动重试。

## 步骤 3 · 事件流与 SSE

### 这一步在做什么

**让用户看到 Agent 在做什么，而不是盯着一个转圈。**

### 事件表

```sql
CREATE TABLE task_events (
    -- 用自增 id 而不是 UUID：SSE 的断线续传要靠「大于某个 id」来定位，
    -- 必须是单调递增且可比较的
    id          BIGSERIAL PRIMARY KEY,
    -- 任务删掉时事件一起删，避免留下查不到归属的孤儿行
    task_id     TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    event_type  TEXT NOT NULL,
    -- 各类事件的字段差别很大，用 JSONB 装载荷，不为每种事件加一列
    payload     JSONB NOT NULL,
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- (task_id, id) 复合索引正好覆盖「某个任务、id 大于游标」这个唯一的查询模式
CREATE INDEX ON task_events (task_id, id);
```

**事件必须持久化，不能只存内存。** 否则客户端断线重连就拿不到断开期间的事件了。

### 事件类型

```python
# 事件类型是前端的渲染依据：每加一种，前端就多一种展示方式。
# 所以类型要粗到能穷举、细到能区分该怎么显示
EVENT_TYPES = [
    "task_started",
    "turn_started",           # {"turn": 3}
    "thinking",               # {"text": "我需要先搜索..."} 流式片段
    "tool_started",           # {"name": "search_notes", "arguments": {...}}
    # summary 是一句人话摘要，不是工具的完整返回值
    "tool_finished",          # {"name": "search_notes", "summary": "找到 23 条", "duration": 0.42}
    "tool_failed",            # {"name": "...", "error": "..."}
    # confirmation_id 让前端知道该把用户的「同意」回传到哪一次确认上
    "confirmation_required",  # {"action": "删除 12 条草稿", "confirmation_id": "c_123"}
    "task_completed",         # {"result": {...}}
    "task_failed",            # {"error": "..."}
]
```

**`tool_finished` 事件里放摘要而不是完整返回值**，否则事件表会很大。

### SSE 接口

```python
from fastapi.responses import StreamingResponse

@app.get("/tasks/{task_id}/events")
async def subscribe_events(task_id: str, user: CurrentUser, last_event_id: int = 0):
    # 归属校验必须在开始推流之前做完：流一旦开始，就没法再返回 403 了
    check_ownership(await fetch_task(task_id), user)

    async def event_stream():
        # cursor 从客户端报上来的位置起步，重连时就能补齐断开期间的事件
        cursor = last_event_id
        idle_ticks = 0
        while True:
            # 限制 100 条：客户端断开很久时可能积压大量事件，一次全查会撑爆内存
            events = await fetch_events(task_id, after_id=cursor, limit=100)
            for e in events:
                cursor = e.id
                # id 行让浏览器 EventSource 记住位置；ensure_ascii=False 保证中文不被转义成 \uXXXX
                yield f"id: {e.id}\nevent: {e.event_type}\ndata: {json.dumps(e.payload, ensure_ascii=False)}\n\n"
                idle_ticks = 0

            # 终态检查放在发完事件之后，保证最后一批事件不会因为提前 return 而丢掉
            task = await fetch_task(task_id)
            if task.status in ("completed", "failed", "cancelled"):
                yield f"event: done\ndata: {{}}\n\n"
                return

            await asyncio.sleep(0.5)
            idle_ticks += 1
            if idle_ticks % 20 == 0:              # 每 10 秒发一次心跳
                # 冒号开头是 SSE 注释行，客户端会忽略，作用只是让中间代理看到有流量
                yield ": keepalive\n\n"

    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

### 三个关键点

**一、`id:` 字段让客户端能续传。** 浏览器的 `EventSource` 断线重连时会自动带上 `Last-Event-ID` 头。

**二、心跳（`: keepalive`）防止连接被中间的代理掐断。** 冒号开头是 SSE 的注释行，客户端会忽略。

**三、任务结束时要显式发一个结束事件并关闭**，否则客户端会一直等。

### 可能卡在哪

**轮询数据库太频繁**

0.5 秒一次，几十个并发连接就是每秒上百次查询。优化：

1. 用 Postgres 的 `LISTEN/NOTIFY`：worker 写事件后 NOTIFY，订阅端 LISTEN，有事件才查
2. 或者上 Redis 的 pub/sub

**先用轮询跑通，有性能问题再优化。**

**Nginx 或云平台把 SSE 连接掐了**

需要配置：关闭响应缓冲、加长超时。具体配置看你用的网关。

**心跳能解决大部分「静默超时」问题。**

**客户端收不到事件**

检查：

1. `Content-Type` 是不是 `text/event-stream`
2. 有没有中间层做了缓冲（加 `X-Accel-Buffering: no` 响应头）
3. 事件格式对不对（**每个事件必须以两个换行结束**）

## 步骤 4 · 超时与重试

### 这一步在做什么

给每一层设合理的超时。

### 三层超时

| 层 | 建议值 | 超时后 |
|---|---|---|
| 单次模型调用 | 60 到 300 秒 | 重试（可重试错误） |
| 单个工具 | 30 秒 | 返回超时说明给模型，让它换个方式 |
| 整个任务 | 30 分钟 | 标记失败，保留已完成的步骤 |

**三层都要有。** 只有最外层的话，一个卡住的工具会拖到 30 分钟才被发现。

### 重试策略

U0.5 学的区分依然适用：

```python
# 分界线是「重试有没有可能换来不同结果」：限流和 5xx 是对方的临时状态，
# 4xx 和校验失败是请求本身有问题，重试一万次也一样
RETRYABLE = {429, 500, 502, 503, 504, TimeoutError, ConnectionError}
NON_RETRYABLE = {400, 401, 403, 404, ValidationError, ContentPolicyError}
```

**在任务层面还要加一条**：

```python
# 单次调用的重试之外还要有任务级上限：任务本身有 bug 时，锁一过期就被
# 重新领走，会形成「永远失败、永远重试」的死循环
if task.retry_count >= 3:
    await mark_failed(task.id, "重试次数超限")
    return
```

### 「部分完成」的处理

任务跑到第 6 步失败了，前 5 步的结果怎么办？

**保留。** U4.2 的 checkpoint 已经存了。用户重试时从第 6 步继续，不用重做前 5 步。

**但要告诉用户**：

```json
{
  "status": "failed",
  "error": "第 6 步调用外部 API 超时",
  "completed_steps": 5,
  "partial_result": {...},
  "resumable": true
}
```

`resumable` 是给前端看的：有它前端才知道该显示「重试」还是「只能重新开始」。

### 可能卡在哪

**超时了但操作实际成功了**

**这就是 U4.2 的幂等问题。** 超时不代表没执行。恢复时必须查证。

**用户不停重试同一个失败的任务**

加频率限制：同一个任务的重试间隔至少 N 秒，且总次数有上限。

## 步骤 5 · 优雅关闭

### 这一步在做什么

部署时不要把正在跑的任务弄丢。

### 怎么做

```python
import signal

# 用一个模块级标志而不是直接退出：信号处理函数里能做的事很有限，
# 它只负责「翻牌子」，真正的收尾留给主循环在安全的位置做
should_stop = False

def handle_signal(signum, frame):
    global should_stop
    logger.info("收到信号 %s，准备优雅退出", signum)
    should_stop = True

signal.signal(signal.SIGTERM, handle_signal)   # 容器编排系统关闭时发的就是这个
signal.signal(signal.SIGINT, handle_signal)    # 本地 Ctrl+C 走同一条路径，方便调试


async def worker():
    while not should_stop:
        task = await claim_pending_task()
        ...

    logger.info("worker 退出，等待当前任务完成")
    # 超时兜底：等不到就只能放弃，否则容器的宽限期一到会被 SIGKILL 直接砍掉
    await wait_for_current_task(timeout=30)
```

**关键行为**：

1. 收到 SIGTERM 后**不再领新任务**
2. 当前任务**跑完当前这一步**就保存 checkpoint 退出
3. 释放锁，让别的 worker 能接手

```python
async def run_task(task_id):
    while step < max_steps:
        # 检查点放在每一步的开头，也就是两步之间的安全边界：
        # 此时上一步已经完成并落库，中断不会留下做了一半的状态
        if should_stop:
            # 释放锁是关键动作，不释放的话要等 TTL 到期才有别的 worker 接手
            await save_checkpoint_and_release_lock(task_id)
            logger.info("任务 %s 在第 %d 步暂停，等待重新调度", task_id, step)
            return
        ...
```

### 可能卡在哪

**容器给的关闭时间不够**

Docker 默认 SIGTERM 后 10 秒就 SIGKILL。改长一点：

```yaml
services:
  worker:
    # 宽限期要大于「当前一步最长耗时 + 保存 checkpoint 的时间」，否则 SIGKILL 会打断收尾
    stop_grace_period: 60s
```

**用了 asyncio，信号处理不生效**

在 asyncio 里用 `loop.add_signal_handler` 而不是 `signal.signal`。
