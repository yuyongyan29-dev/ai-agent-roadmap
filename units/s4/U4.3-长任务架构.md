# U4.3 · 长任务架构（12 小时）

**这个单元解决什么问题**

你的 Agent 一个任务可能跑十分钟。现在的做法是：用户发一个 HTTP 请求，然后一直等着。

这有四个问题：**HTTP 连接会超时；用户看不到进度；刷新页面就断了；服务器重启所有正在跑的任务全废。**

**学完你能做到**：任务异步执行，客户端断线重连后能看到断开期间的全部进度。

---

## 步骤 1 · 改成异步接口

### 这一步在做什么

把「一个请求跑完全程」拆成「提交、查询、订阅、取消」四个接口。

### 接口设计

```python
@app.post("/tasks", status_code=202)
async def 提交(输入: 任务输入, 用户: 当前用户) -> 任务响应:
    """立刻返回 task_id，任务进队列"""
    task_id = 生成id()
    await 建任务(task_id, 用户.id, 输入)
    await 入队(task_id)
    return 任务响应(task_id=task_id, 状态="pending")


@app.get("/tasks/{task_id}")
async def 查状态(task_id: str, 用户: 当前用户) -> 任务详情:
    """当前状态、已完成的步骤、结果"""
    任务 = await 取任务(task_id)
    校验归属(任务, 用户)
    步骤 = await 取步骤(task_id)
    return 任务详情(状态=任务.状态, 当前步骤=任务.当前步骤, 步骤=步骤, 结果=任务.结果)


@app.get("/tasks/{task_id}/events")
async def 订阅(task_id: str, 用户: 当前用户, last_event_id: int = 0):
    """SSE 流式推送事件，从 last_event_id 之后开始"""
    ...


@app.post("/tasks/{task_id}/cancel")
async def 取消(task_id: str, 用户: 当前用户):
    ...


@app.post("/tasks/{task_id}/resume")
async def 恢复(task_id: str, 用户: 当前用户, 决定: 人工决定 | None = None):
    """从 paused 状态恢复，可带上人工确认的结果"""
    ...
```

**`202 Accepted` 这个状态码的语义就是「已接受，还在处理」。** 用它而不是 200。

### 可能卡在哪

**用户希望「就等着拿结果」**

前端可以在提交后自动订阅事件流，体验上和同步一样，但底层是异步的。**S5 会做这个。**

**要不要提供同步接口作为兼容**

可以提供一个「提交并等待，最多 N 秒」的接口，超时就返回 task_id 让客户端去轮询。**但不要让它成为主路径。**

## 步骤 2 · 任务队列

### 这一步在做什么

让任务在后台被 worker 消费。

### 不要一上来就上 Celery

**小项目用 Postgres 当队列就够了**，而且和你的事务天然一致。

```sql
-- 取一个待处理的任务，同时加锁
SELECT * FROM tasks
WHERE 状态 = 'pending'
  AND (锁过期时间 IS NULL OR 锁过期时间 < now())
ORDER BY 创建时间
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

**`SKIP LOCKED` 是关键**：多个 worker 同时查，各自拿到不同的任务，不会互相阻塞。

Worker 循环：

```python
async def worker(worker_id: str):
    while not 要停止:
        任务 = await 取一个待处理任务(worker_id)
        if 任务 is None:
            await asyncio.sleep(1)
            continue
        try:
            await 跑任务(任务.id)          # U4.2 写的
        except Exception:
            logger.exception("任务 %s 失败", 任务.id)
            await 标记失败(任务.id)
```

### 什么时候需要专门的队列

| 场景 | 需要 |
|---|---|
| 每秒几个任务 | Postgres 够 |
| 每秒几百个任务 | 需要 Redis 或专门的队列 |
| 需要优先级、延迟执行、重试策略 | 用 [ARQ](https://arq-docs.helpmanual.io/)（基于 Redis，轻量）或 Celery |
| 需要跨语言 | 消息队列（RabbitMQ / Kafka） |

**你的项目大概率永远不需要超出 Postgres。**

### 可能卡在哪

**worker 怎么部署**

三种：

1. 和 API 同一个进程，用 `asyncio.create_task` 起一个后台循环。**最简单，适合个人项目**
2. 同一个镜像，不同的启动命令（`uvicorn` vs `python worker.py`）
3. 完全独立的服务

**建议从第 1 种开始**，需要扩展时再拆。

**任务卡死了怎么办**

锁有 TTL（U4.2），过期后别的 worker 会接手。但要小心：**如果任务本身有 bug 导致每次都卡死，会被反复重试。**

加一个重试次数上限：

```sql
ALTER TABLE tasks ADD COLUMN 重试次数 INTEGER DEFAULT 0;
```

超过 3 次就标记为 failed，不再自动重试。

## 步骤 3 · 事件流与 SSE

### 这一步在做什么

**让用户看到 Agent 在做什么，而不是盯着一个转圈。**

### 事件表

```sql
CREATE TABLE task_events (
    id          BIGSERIAL PRIMARY KEY,
    task_id     TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    类型        TEXT NOT NULL,
    数据        JSONB NOT NULL,
    创建时间     TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX ON task_events (task_id, id);
```

**事件必须持久化，不能只存内存。** 否则客户端断线重连就拿不到断开期间的事件了。

### 事件类型

```python
事件类型 = [
    "任务开始",
    "轮次开始",       # {"轮": 3}
    "思考",           # {"文本": "我需要先搜索..."} 流式片段
    "工具开始",       # {"名字": "搜索笔记", "参数": {...}}
    "工具完成",       # {"名字": "搜索笔记", "摘要": "找到 23 条", "耗时": 0.42}
    "工具失败",       # {"名字": "...", "错误": "..."}
    "需要确认",       # {"操作": "删除 12 条草稿", "确认id": "c_123"}
    "任务完成",       # {"结果": {...}}
    "任务失败",       # {"错误": "..."}
]
```

**「工具完成」事件里放摘要而不是完整返回值**，否则事件表会很大。

### SSE 接口

```python
from fastapi.responses import StreamingResponse

@app.get("/tasks/{task_id}/events")
async def 订阅(task_id: str, 用户: 当前用户, last_event_id: int = 0):
    校验归属(await 取任务(task_id), 用户)

    async def 生成():
        游标 = last_event_id
        空闲次数 = 0
        while True:
            事件们 = await 取事件(task_id, 大于id=游标, 限制=100)
            for e in 事件们:
                游标 = e.id
                yield f"id: {e.id}\nevent: {e.类型}\ndata: {json.dumps(e.数据, ensure_ascii=False)}\n\n"
                空闲次数 = 0

            任务 = await 取任务(task_id)
            if 任务.状态 in ("completed", "failed", "cancelled"):
                yield f"event: 结束\ndata: {{}}\n\n"
                return

            await asyncio.sleep(0.5)
            空闲次数 += 1
            if 空闲次数 % 20 == 0:                # 每 10 秒发一次心跳
                yield ": keepalive\n\n"

    return StreamingResponse(生成(), media_type="text/event-stream")
```

### 三个关键点

**一、`id:` 字段让客户端能续传。** 浏览器的 `EventSource` 断线重连时会自动带上 `Last-Event-ID` 头。

**二、心跳（`: keepalive`）防止连接被中间的代理掐断。** 冒号开头是 SSE 的注释行，客户端会忽略。

**三、任务结束时要显式发一个结束事件并关闭**，否则客户端会一直等。

### 可能卡在哪

**轮询数据库太频繁**

0.5 秒一次，几十个并发连接就是每秒上百次查询。优化：

1. 用 Postgres 的 `LISTEN/NOTIFY`：worker 写事件后 NOTIFY，订阅端 LISTEN，有事件才查
2. 或者上 Redis 的 pub/sub

**先用轮询跑通，有性能问题再优化。**

**Nginx 或云平台把 SSE 连接掐了**

需要配置：关闭响应缓冲、加长超时。具体配置看你用的网关。

**心跳能解决大部分「静默超时」问题。**

**客户端收不到事件**

检查：

1. `Content-Type` 是不是 `text/event-stream`
2. 有没有中间层做了缓冲（加 `X-Accel-Buffering: no` 响应头）
3. 事件格式对不对（**每个事件必须以两个换行结束**）

## 步骤 4 · 超时与重试

### 这一步在做什么

给每一层设合理的超时。

### 三层超时

| 层 | 建议值 | 超时后 |
|---|---|---|
| 单次模型调用 | 60 到 300 秒 | 重试（可重试错误） |
| 单个工具 | 30 秒 | 返回超时说明给模型，让它换个方式 |
| 整个任务 | 30 分钟 | 标记失败，保留已完成的步骤 |

**三层都要有。** 只有最外层的话，一个卡住的工具会拖到 30 分钟才被发现。

### 重试策略

U0.5 学的区分依然适用：

```python
可重试 = {429, 500, 502, 503, 504, TimeoutError, ConnectionError}
不可重试 = {400, 401, 403, 404, ValidationError, 内容审核拒绝}
```

**在任务层面还要加一条**：

```python
if 任务.重试次数 >= 3:
    await 标记失败(任务.id, "重试次数超限")
    return
```

### 「部分完成」的处理

任务跑到第 6 步失败了，前 5 步的结果怎么办？

**保留。** U4.2 的 checkpoint 已经存了。用户重试时从第 6 步继续，不用重做前 5 步。

**但要告诉用户**：

```json
{
  "状态": "failed",
  "错误": "第 6 步调用外部 API 超时",
  "已完成步骤": 5,
  "部分结果": {...},
  "可恢复": true
}
```

### 可能卡在哪

**超时了但操作实际成功了**

**这就是 U4.2 的幂等问题。** 超时不代表没执行。恢复时必须查证。

**用户不停重试同一个失败的任务**

加频率限制：同一个任务的重试间隔至少 N 秒，且总次数有上限。

## 步骤 5 · 优雅关闭

### 这一步在做什么

部署时不要把正在跑的任务弄丢。

### 怎么做

```python
import signal

要停止 = False

def 处理信号(signum, frame):
    global 要停止
    logger.info("收到信号 %s，准备优雅退出", signum)
    要停止 = True

signal.signal(signal.SIGTERM, 处理信号)
signal.signal(signal.SIGINT, 处理信号)


async def worker():
    while not 要停止:
        任务 = await 取一个待处理任务()
        ...

    logger.info("worker 退出，等待当前任务完成")
    await 等待当前任务(超时=30)
```

**关键行为**：

1. 收到 SIGTERM 后**不再领新任务**
2. 当前任务**跑完当前这一步**就保存 checkpoint 退出
3. 释放锁，让别的 worker 能接手

```python
async def 跑任务(task_id):
    while 步骤 < 上限:
        if 要停止:
            await 保存checkpoint并释放锁(task_id)
            logger.info("任务 %s 在第 %d 步暂停，等待重新调度", task_id, 步骤)
            return
        ...
```

### 可能卡在哪

**容器给的关闭时间不够**

Docker 默认 SIGTERM 后 10 秒就 SIGKILL。改长一点：

```yaml
services:
  worker:
    stop_grace_period: 60s
```

**用了 asyncio，信号处理不生效**

在 asyncio 里用 `loop.add_signal_handler` 而不是 `signal.signal`。

```bash

# Ctrl+C 断开，记下最后一个 id
```
