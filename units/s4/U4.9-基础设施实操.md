# U4.9 · 基础设施实操：镜像仓库、HTTPS、托管数据库与备份、对象存储（8 小时）

**这个单元解决什么问题**

U4.0 你有了一台会用的服务器，U4.7 要把 Agent 部署上去。这两个单元之间缺了一段谁都以为对方讲了的东西：

- 镜像在你笔记本上 build 出来，**怎么到服务器上**？
- 域名解析过去了，**HTTPS 证书从哪来**？
- U4.7 说「数据库用云托管」，**怎么开、怎么连、怎么备份、坏了怎么恢复**？
- Agent 生成的文件、用户上传的附件、trace 里放不下的大段工具返回值，**存哪**？
- Redis 上了生产，**哪三件事不做就是事故**？

这些东西单独看都不难，难的是没人把它们串成一条能照着走的路。这个单元就是那条路。**做完它，U4.7 的部署流水线才有东西可接。**

**学完你能做到**：一条 `git push` 之后，镜像自动构建、推到仓库、服务器拉取重启；HTTPS 自动续期；数据库每天备份到对象存储，并且你亲手从备份恢复过一次。

**读之前**：U4.0 的服务器还在（或者重新买一台，几块钱）；U0.9 的 compose 能跑；U4.0 的 nginx 和 systemd 做过。

## 步骤 1 · 镜像仓库：让镜像能到服务器上（1.5 小时）

### 这一步在做什么

Docker 镜像是一坨文件层，服务器要拿到它有两条路：在服务器上 build，或者从一个「镜像仓库」拉。**生产一律走后者**——服务器上 build 意味着服务器要装完整工具链、要拉源码、CPU 被构建吃掉，而且你无法保证两台机器 build 出来的东西一样。

### 选哪个仓库

| 仓库 | 适合 | 注意 |
|---|---|---|
| **GitHub Container Registry（ghcr.io）** | 代码在 GitHub、服务器在境外 | 和 GitHub Actions 天然打通，免费；**国内服务器拉取慢甚至超时** |
| **阿里云 ACR 个人版 / 腾讯云 TCR 个人版** | 服务器在国内 | 免费额度够个人用；同地域内网拉取快 |
| Docker Hub | 公开镜像 | 国内直连不稳定，别把它当你的私有仓库 |

**规则**：仓库和服务器放在同一侧。国内服务器用国内仓库，境外服务器用 ghcr。两边都要的话 Actions 里推两次。

### 让 agent 做

```
给 s4-production 加一个 GitHub Actions workflow：.github/workflows/build-image.yml。
要求：
1. 触发条件：push 到 main
2. 用 docker/login-action 登录 ghcr.io，凭据用 GITHUB_TOKEN，job 要声明 permissions: packages: write
3. 用 docker/build-push-action 构建并推送，tag 两个：git sha 全量哈希 和 latest
4. 镜像名 ghcr.io/<仓库所有者>/agent-api，所有者从 github.repository_owner 取，转成小写（ghcr 要求小写）
5. 开启 GitHub Actions 缓存（cache-from/cache-to type=gha），不然每次都全量构建
6. 如果仓库有 secrets.ACR_REGISTRY / ACR_USERNAME / ACR_PASSWORD 三个变量，再登录并推到阿里云 ACR 同名镜像；没有就跳过这一步，不要报错
不要在 workflow 里出现任何明文密钥。写完把 workflow 每一步在做什么用中文注释写在 yml 里。
```

### 你自己做

1. 推到 GitHub，看 Actions 跑完
2. 仓库页面右侧 Packages 里能看到 `agent-api`，点进去把可见性设为 Private（默认可能是 Private，确认一下）
3. 在服务器上拉取：

```bash
# 在 GitHub Settings → Developer settings → Personal access tokens 建一个只有 read:packages 权限的 token
echo "$GHCR_TOKEN" | docker login ghcr.io -u 你的GitHub用户名 --password-stdin
docker pull ghcr.io/你的用户名/agent-api:latest
```

国内服务器：先在阿里云容器镜像服务开一个个人版实例，建命名空间和仓库，把三个值放进 GitHub 仓库的 Secrets，再推一次；服务器上 `docker login registry.cn-hangzhou.aliyuncs.com`（地域按你开的来）。

### 你验收

- `docker images` 里能看到刚拉下来的镜像，tag 是 latest 和一个 40 位的 sha
- 改一行代码再推，Actions 第二次跑的构建时间明显短于第一次（缓存生效）
- 用 sha tag 而不是 latest 跑一次容器：`docker run --rm ghcr.io/.../agent-api:<sha> python -c "print('ok')"`

### 你读懂

1. 为什么每个镜像要打 git sha 的 tag，只用 latest 会怎样？（提示：U4.6 回滚时你要回到「上一个」，latest 没有「上一个」）
2. `GITHUB_TOKEN` 是谁发的、有效期多久、为什么不用你自己的 token？
3. 服务器上的那个 token 只给了 `read:packages`，如果它泄露了，攻击者能做什么、不能做什么？

### 可能卡在哪

**`denied: permission_denied` 推送失败**

workflow 没声明 `permissions: packages: write`。GitHub 默认给 `GITHUB_TOKEN` 的权限是只读的。

**镜像名里有大写字母被拒**

ghcr 要求全小写。GitHub 用户名有大写的话要在 workflow 里转：`${{ github.repository_owner }}` 后接 `| tr '[:upper:]' '[:lower:]'`，或者用 `docker/metadata-action` 自动处理。

**国内服务器 `docker pull ghcr.io/...` 卡住**

不是你配错了，是网络。要么换国内仓库，要么在服务器上配镜像加速（各云厂商都有，以控制台当前文档为准）。**别在这上面耗时间，直接推一份到 ACR。**

**agent 把 `docker build` 写成了在服务器上 build**

这是它最常见的「省事」写法：在 deploy 脚本里 `git pull && docker compose up --build`。能跑，但违背这一步的全部理由。让它改成 pull 镜像。

### 背后的逻辑

镜像仓库让「构建」和「运行」分离：构建在 CI 里做一次，产物有唯一标识（sha），任何机器拉到的都是同一个东西。**这是 U4.6 灰度和回滚能成立的前提**——回滚 = 拉上一个 sha，而不是「重新 build 一遍希望和上次一样」。

## 步骤 2 · HTTPS：用 Caddy 自动签证书（1 小时）

### 这一步在做什么

浏览器、小程序、App 商店都要求 HTTPS。证书可以从 Let's Encrypt 免费拿，但手动 certbot 要配 nginx、要记得续期、SSE 还要单独关缓冲。**Caddy 把这三件事全自动化了**：写一行域名，它自己申请、自己续期、默认就是 HTTP/2。

U4.0 你已经会 nginx 了，这里换 Caddy 不是否定 nginx——大厂里 nginx 更常见，但**一个人维护一台机器，Caddy 省下的时间是实打实的**。两个都会，面试时能讲清楚各自适合什么。

### 让 agent 做

```
在 s4-production/compose.yaml 里加一个 caddy 服务，替换掉现在的 nginx：
1. 镜像 caddy:2，映射 80 和 443，两个命名卷：caddy_data 和 caddy_config（证书存这里，删容器不能丢）
2. Caddyfile 挂载进去，内容：
   api.example.com {
     reverse_proxy api:8000 {
       flush_interval -1
     }
   }
   域名从环境变量 DOMAIN 读（Caddyfile 支持 {$DOMAIN}），不要写死
3. flush_interval -1 是给 SSE 用的，加中文注释说明为什么（对照 U4.0 nginx 的 proxy_buffering off）
4. api 服务不再对外映射 8000 端口，只在 compose 内网
5. compose 里所有服务加 restart: unless-stopped
把改动说明写成 s4-production/docs/caddy.md
```

### 你自己做

1. 域名 A 记录指到服务器 IP，等生效（`dig +short api.example.com` 能看到 IP）
2. 云控制台安全组放行 80 和 443（**80 必须开**，Let's Encrypt 的 HTTP 验证走 80）
3. 服务器上 `docker compose up -d`，然后 `docker compose logs -f caddy`，看到 `certificate obtained successfully` 就成了

### 你验收

- 浏览器打开 `https://api.example.com/health`，锁是绿的，点开证书看签发者是 Let's Encrypt
- `curl -I http://api.example.com/health` 返回 308 跳到 https（Caddy 默认把 HTTP 重定向）
- 用 U4.3 的流式端点 `curl -N https://api.example.com/...`，事件是一条一条到的，不是攒一坨
- `docker compose down && docker compose up -d`，证书没有重新申请（看日志），说明卷挂对了

### 你读懂

1. Caddy 是怎么向 Let's Encrypt 证明「这个域名是你的」？为什么 80 端口必须开？
2. `flush_interval -1` 和 nginx 的 `proxy_buffering off` 是同一件事吗？不加会出现 U4.0 里的哪个现象？
3. 证书有效期是多久？续期谁来做？你怎么知道它续期失败了？（提示：U4.7 的告警要加一条证书剩余天数）

### 可能卡在哪

**日志里 `challenge failed` / `connection refused`**

三个原因按顺序查：DNS 还没生效（`dig`）；安全组没开 80；服务器本机防火墙（U4.0 的 ufw）没放行 80。

**Let's Encrypt 限流**

同一域名一周内签发次数有限。**反复 `down -v` 删卷重来会撞上。** 调试阶段在 Caddyfile 全局块加 `acme_ca https://acme-staging-v02.api.letsencrypt.org/directory` 用测试环境，通了再去掉。

**国内服务器、域名没备案**

80/443 会被云厂商拦截，浏览器显示备案提示页。这不是 Caddy 的问题。要么先备案，要么用境外服务器练。

### 背后的逻辑

HTTPS 的核心是「一个第三方（CA）证明这个域名归你」。ACME 协议把这个证明过程自动化：CA 给你一个随机串，你把它放在 `http://域名/.well-known/acme-challenge/` 下，CA 来取，取到就说明你控制这个域名。Caddy 做的就是这套握手加定时续期。**理解了这一点，你就知道为什么证书出问题永远先查 DNS 和 80 端口。**

## 步骤 3 · 托管数据库，还是自己跑（0.5 小时）

### 这一步在做什么

U4.7 的判据写着「数据库用云托管」。这一步把「为什么」和「什么时候不必」说清楚，你自己选。

### 两条路

| | 云托管（RDS） | 自己在 compose 里跑 |
|---|---|---|
| **谁负责备份、补丁、故障切换** | 云厂商 | 你 |
| **月费** | 最小规格几十到一百多元，以官网为准 | 服务器本身的钱 |
| **连接方式** | 内网地址 + 账号密码，走同地域内网 | compose 服务名 |
| **适合** | 有真实用户的数据、你不想半夜爬起来修数据库 | 练习、预览环境、数据丢了能重建的场景 |
| **国内选项** | 阿里云 RDS PostgreSQL、腾讯云 PostgreSQL | — |
| **海外选项** | Supabase、Neon（都有免费档，以官网为准） | — |

**建议**：预览环境自己跑，正式环境用托管。**但无论哪条路，步骤 4 的备份和恢复演练都要做**——托管数据库的自动备份是兜底，不是免你动手的理由，你得知道恢复要点哪里、要多久。

### 你自己做

开一个最小规格的托管 Postgres（或者决定先自己跑，把理由写进 `DEPLOY.md`），拿到连接串，放进服务器上的 `.env`，**不要放进代码、不要放进 compose 文件**。

### 你验收

从服务器上 `psql "$DATABASE_URL" -c "select version();"` 能连上。从你笔记本上连**应该连不上**（托管库默认只开内网），如果能连上，去控制台把公网访问关了。

## 步骤 4 · 备份与恢复演练（2 小时）

### 这一步在做什么

**没有恢复过的备份不算备份。** 这一步你要做一个每天自动备份到对象存储的任务，然后亲手把库删了、从备份恢复回来。

### 让 agent 做

```
写 s4-production/scripts/backup-db.sh 和对应的 systemd timer：
1. 用 pg_dump -Fc（自定义压缩格式）导出 DATABASE_URL 指向的库，文件名带日期时间：agent-YYYYmmdd-HHMM.dump
2. 导出后用 rclone 上传到对象存储的 backups/ 前缀下（rclone 的 remote 名叫 oss，配置我自己做），上传成功后删本地文件
3. 保留策略：对象存储里只留最近 14 天的，多的删掉
4. 任何一步失败都要非零退出，并把失败信息 POST 到 ALERT_WEBHOOK（U4.7 的告警通道）
5. 写 backup-db.service 和 backup-db.timer，每天凌晨 3 点跑，timer 要 Persistent=true（关机错过了开机补跑）
6. 再写一个 restore-db.sh：参数是备份文件名，从对象存储下载，用 pg_restore --clean --if-exists 恢复到 DATABASE_URL；恢复前先做一次当前库的 pg_dump 存到 /tmp，以防恢复错了还能退回
所有脚本 set -euo pipefail，中文注释。
```

### 你自己做

1. 对象存储的桶和 rclone 配置在步骤 5 做。**先做步骤 5 再回来跑这一步**，或者先用 rclone 的本地目录 remote 把流程跑通
2. `sudo systemctl enable --now backup-db.timer`，`systemctl list-timers` 里能看到下次触发时间
3. 手动触发一次：`sudo systemctl start backup-db.service`，然后 `rclone ls oss:你的桶/backups/`

**恢复演练**（这是本步骤的重点）：

```bash
# 1. 造一条你认得出来的数据
psql "$DATABASE_URL" -c "insert into tasks (id, status) values ('drill-001', 'done');"
# 2. 备份
sudo systemctl start backup-db.service
# 3. 删掉它，模拟事故
psql "$DATABASE_URL" -c "delete from tasks where id = 'drill-001';"
# 4. 从备份恢复
./scripts/restore-db.sh agent-<刚才那个时间>.dump
# 5. 它回来了吗
psql "$DATABASE_URL" -c "select * from tasks where id = 'drill-001';"
```

**计时。** 从「发现数据没了」到「数据回来了」用了多久，写进 `RUNBOOK.md`（U4.8 会用到）。

### 你验收

- `systemctl list-timers` 显示 backup-db 的下次触发
- 对象存储里有 dump 文件，大小合理（不是 0 字节）
- **恢复演练成功，`drill-001` 回来了，耗时记录在案**
- 故意把 `DATABASE_URL` 改错跑一次备份，手机收到告警

### 你读懂

1. `pg_dump -Fc` 和导成 `.sql` 文本有什么区别？为什么恢复时用 `pg_restore` 而不是 `psql < file`？
2. 备份文件里有没有密码？它放在对象存储里，桶的权限该是什么？（提示：步骤 5 的「私有桶」）
3. 如果数据库有 50GB，每天全量 dump 还合适吗？托管数据库的「时间点恢复（PITR）」解决的是什么问题？

### 可能卡在哪

**`pg_dump: server version mismatch`**

服务器上装的 pg_dump 版本低于数据库版本。用和数据库同版本的镜像跑：`docker run --rm postgres:17 pg_dump ...`，或者在 compose 里用 db 容器自带的：`docker compose exec -T db pg_dump -U app -Fc csvstats`。

**timer 没触发**

`systemctl status backup-db.timer` 看是不是 active；`journalctl -u backup-db.service` 看上次运行的错误。最常见是脚本在 timer 环境下没有你 shell 里的环境变量——**systemd 不读你的 `~/.zshrc`**，`DATABASE_URL` 要写进 service 文件的 `EnvironmentFile=`。

**pg_restore 报一堆 `already exists`**

没加 `--clean --if-exists`，或者恢复到了一个非空库。agent 有时会漏这两个参数。

**agent 写的保留策略删错了东西**

验收时先在一个测试前缀下跑，看它删的是不是 14 天前的。**`rclone delete` 加 `--dry-run` 先看一遍。**

### 背后的逻辑

备份要回答三个问题：**多久一次**（RPO，能接受丢多少数据）、**恢复要多久**（RTO）、**恢复真的能成功吗**。前两个是数字，第三个只有演练能回答。大厂的做法是定期做「恢复演练」并记录 RTO，你现在做的就是这个的个人版。**U4.8 的 Runbook 里，「数据库恢复」这一条的每一步都来自你今天的记录。**

## 步骤 5 · 对象存储：文件、附件、大内容放哪（2 小时）

### 这一步在做什么

Agent 项目里有一类数据放数据库不合适：用户上传的文件、Agent 生成的报告和图片、U3.5 说的「工具返回值太长只存前 2000 字符，完整内容存到别处」、步骤 4 的备份。**这些放对象存储。**

对象存储是「一个无限大的、按 key 存文件的桶」。所有主流厂商的对象存储都兼容 S3 API，**所以你学一套 API，换厂商只改一个 endpoint**：

| 厂商 | 产品 | 适合 |
|---|---|---|
| 腾讯云 | COS | 服务器在腾讯云、用了 CloudBase |
| 阿里云 | OSS | 服务器在阿里云 |
| Cloudflare | R2 | 海外用户；**出站流量免费**是它区别于所有人的点 |
| 自建 | MinIO | 本地开发、预览环境、不想为练习花钱 |

### 让 agent 做

```
给 s4-production 加对象存储支持：
1. compose 里加一个 minio 服务用于本地开发（镜像 minio/minio，命令 server /data --console-address :9001，命名卷），
   环境变量 MINIO_ROOT_USER / MINIO_ROOT_PASSWORD 从 .env 读
2. 写 src/agent/storage.py：用 boto3 封装三个函数
   - upload_bytes(key, data, content_type) -> str（返回 key）
   - presigned_put_url(key, expires=600) -> str（给前端直传用）
   - presigned_get_url(key, expires=600) -> str
   endpoint、bucket、access key、secret 全部从环境变量读：S3_ENDPOINT / S3_BUCKET / S3_ACCESS_KEY / S3_SECRET_KEY
   本地指向 minio，生产指向 COS 或 OSS，代码不变
3. 在 U4.3 的任务流程里：工具返回值超过 2000 字符时，完整内容 upload_bytes 到 tool-outputs/<task_id>/<step>.txt，
   数据库和 trace 里只存 key 和前 2000 字符
4. 给 FastAPI 加一个端点 POST /uploads/presign，返回 presigned_put_url，前端拿到后直接 PUT 文件到对象存储，不经过你的服务器
5. 写一份 docs/storage.md：本地怎么起 minio、生产怎么换成 COS/OSS、桶为什么必须私有、什么时候需要 CDN
中文注释，密钥不进代码。
```

### 你自己做

1. 本地：`docker compose up -d minio`，打开 `http://localhost:9001` 用 root 账号登录，建一个桶 `agent`，**Access Policy 保持 private**
2. 生产：在腾讯云 COS 或阿里云 OSS 开一个桶，**私有读写**；建一个只对这个桶有读写权限的子账号（腾讯云 CAM / 阿里云 RAM），拿它的密钥，不要用主账号的
3. 把生产的四个 `S3_*` 变量写进服务器的 `.env`
4. 顺手把步骤 4 的 rclone 配上：`rclone config` 选 s3 类型，provider 选对应厂商，填 endpoint 和密钥，remote 名叫 `oss`

### 你验收

- 本地：跑一个长输出的工具，数据库里那条记录只有前 2000 字符和一个 key；用 key 换 presigned_get_url 能在浏览器打开完整内容
- `curl -X PUT --upload-file 某个文件 "<presigned_put_url>"` 成功，文件出现在桶里；等 10 分钟后同一个 URL 再传，返回 403（过期了）
- **直接用 `https://<桶的公网地址>/<key>` 访问，必须是 403。** 能打开说明桶是公开的，立刻改。
- 生产：同样的代码，只换 `.env`，四条全过

### 你读懂

1. 预签名 URL 是怎么做到「不经过你的服务器、又不把密钥给前端」的？它里面签的是什么？
2. 为什么要建子账号而不是用主账号密钥？子账号的权限应该精确到什么粒度？
3. 什么时候需要在对象存储前面加 CDN？（提示：小程序的图片、落地页的静态资源；U5.6 提过主包 2MB 上限）R2 的「出站免费」为什么对个人项目是大事？

### 可能卡在哪

**boto3 连 MinIO 报 `SignatureDoesNotMatch` 或 `InvalidEndpoint`**

MinIO 和部分厂商需要 path-style 寻址：`Config(s3={"addressing_style": "path"})`。COS 用 virtual-host 风格，endpoint 形如 `https://cos.<region>.myqcloud.com`。**agent 经常把两种风格搞混**，报错时先看这个。

**预签名 URL 前端 PUT 报 CORS**

浏览器直传要在桶上配 CORS 规则（允许你的前端域名、PUT 方法、Content-Type 头）。这是桶的配置，不是代码。各厂商控制台都有 CORS 设置页。

**上传的文件 Content-Type 全是 `binary/octet-stream`**

预签名时没带 `ContentType`，或者前端 PUT 时没带同样的头。两边要一致，否则签名不匹配。

**agent 把桶设成了公共读「方便调试」**

验收第三条就是抓这个的。公共读的桶加上可枚举的 key，等于把用户文件放在公网上。

### 背后的逻辑

对象存储、数据库、缓存是三种不同形状的数据的家：**按 key 存大块不可变文件 → 对象存储；结构化、要查询、要事务 → 数据库；可丢、要快 → Redis。** 分对了，每一种都简单；混着放（文件塞数据库、状态放 Redis）是 U4.2 讲过的一致性问题和成本问题的共同来源。

预签名 URL 是这一步最值得记住的模式：**服务器只负责「授权」，数据流不经过它。** 上传 100MB 文件不占你服务器一点带宽。U5.4 的流式界面、U5.8 的 App 附件上传，用的都是这个端点。

## 步骤 6 · 生产 Redis 三条规矩（0.5 小时）

### 这一步在做什么

U0.11 的 Redis 是本地随便跑的。上生产前有三条不做就出事的规矩，五分钟配完，剩下的时间用来理解为什么。

### 让 agent 做

```
把 s4-production/compose.yaml 里的 redis 服务改成生产配置：
1. 不映射 6379 到宿主机，只在 compose 内网
2. 启动命令加 --requirepass 从环境变量 REDIS_PASSWORD 读，应用的 REDIS_URL 带上密码
3. 加 --maxmemory 256mb --maxmemory-policy allkeys-lru，命名卷挂 /data，加 --appendonly yes
4. 在 docs/redis.md 里写清楚：哪些数据在 Redis 里（引用 U4.2 的分类表），全部丢了会怎样，为什么可以接受
```

### 你验收

- 从你笔记本 `redis-cli -h 服务器IP` 连不上（端口没暴露）
- 服务器上 `docker compose exec redis redis-cli ping` 返回 `NOAUTH`，带 `-a` 密码后返回 `PONG`
- `docker compose restart redis` 后，U0.11 那个限流计数器的值还在（appendonly 生效）
- `docs/redis.md` 里每一类数据都能回答「丢了会怎样」，**如果有一类的答案是「会不一致」，它就不该在 Redis 里**，回 U4.2

### 你读懂

1. 2026 年的今天，公网上暴露的无密码 Redis 几分钟内就会被扫到并植入挖矿程序。攻击者是怎么通过 Redis 拿到 shell 的？（查 `CONFIG SET dir` 那个经典手法，理解就行）
2. `allkeys-lru` 在内存满时会做什么？这对「用 Redis 存任务状态」意味着什么？
3. 用了托管 Redis（阿里云 / 腾讯云）之后，这三条里哪些是厂商替你做了的、哪条仍然是你的责任？

### 背后的逻辑

三条规矩对应三类事故：**没密码 + 暴露公网 = 被入侵**；**没有 maxmemory = 内存打满把整台机器拖死**；**没持久化 = 重启后限流、锁、会话全清零**。U4.2 说过 Redis 只放可丢的数据，但「可丢」不等于「随便丢」——重启后所有用户同时失去限流保护，也是事故。

## 步骤 7 · 把它们串起来：一次完整的 push 到上线（0.5 小时）

### 这一步在做什么

前六步的产物拼成 U4.7 步骤 5 那条流水线里原来写着 `...` 的「部署」一步。

### 让 agent 做

```
在 build-image.yml 后面加一个 deploy job（needs: build）：
1. 用仓库 Secrets 里的 DEPLOY_SSH_KEY 和 DEPLOY_HOST，ssh 到服务器，用户名 deploy（下面「你自己做」里会建）
2. 远程执行：cd /opt/agent && docker compose pull api && docker compose up -d api，然后等 /health 返回 200，最多 60 秒
3. 迁移那一步按 U4.7 的顺序放在 up 之前：docker compose run --rm api uv run alembic upgrade head
4. 任何一步失败 job 失败，并 POST 到 ALERT_WEBHOOK
ssh 用 StrictHostKeyChecking=accept-new，私钥写到临时文件权限 600，job 结束删除。
```

### 你自己做

1. 建一个能登录、能用 docker、不是 root 的用户（U4.0 的 `appuser` 是给服务跑的，没有登录 shell，不能拿来 ssh）：

```bash
sudo adduser --disabled-password --gecos "" deploy
sudo usermod -aG docker deploy          # 能跑 docker 就够，不要 sudo
sudo -u deploy ssh-keygen -t ed25519 -N "" -f /home/deploy/.ssh/deploy_key
sudo -u deploy sh -c 'cat /home/deploy/.ssh/deploy_key.pub >> /home/deploy/.ssh/authorized_keys'
sudo cat /home/deploy/.ssh/deploy_key   # 这一段放进 GitHub Secrets 的 DEPLOY_SSH_KEY，然后把服务器上的私钥删掉
```
2. `/opt/agent` 下放好 `compose.yaml`、`.env`（权限 600，属主 deploy）、`Caddyfile`
3. 推一个改动，看着它一路绿到服务器上的新版本

### 你验收

- `git push` 之后不碰服务器，两三分钟后 `https://api.example.com/health` 返回的版本号（或 git sha）变了
- 把 `.env` 里的 `DATABASE_URL` 改错再推一次，deploy job 红了、手机收到告警、**线上跑的还是上一个版本**（up 失败不会把旧容器杀掉——验证一下这一点，它取决于健康检查怎么配）
- `docker compose ps` 里没有任何服务的端口直接暴露在 `0.0.0.0` 上，除了 caddy 的 80/443

### 你读懂

1. 这条流水线里哪一步是不可逆的？（迁移）它失败了怎么办？（步骤 4 的备份）
2. 为什么 deploy 用户不能是 root，它需要哪些最小权限？（能跑 docker、能读 /opt/agent，其他都不要）
3. 如果要加第二台服务器，这条流水线哪里要改？哪里不用改？
