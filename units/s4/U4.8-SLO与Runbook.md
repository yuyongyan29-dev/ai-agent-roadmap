# U4.8 · SLO 与 Runbook（10 小时）

**这个单元解决什么问题**

出事的时候，你需要的不是聪明，是流程。

**SLO 定义「什么算好」，Runbook 定义「坏了怎么办」。**

**学完你能做到**：基于测量制定 SLO，按 Runbook 排障；完成从轻端点到数据库再到 Agent 的分层压测，用一次改动前后的证据判断瓶颈。

**时间安排**：原有 SLO、降级和故障演练 6 小时；新增分层压测与优化对照 4 小时。

---

## 步骤 1 · 定 SLO

### 这一步在做什么

给「服务质量」一个可测量的定义。

### 三类 SLO

以下数字用于展示写法，**不是实测结论，也不是所有项目的默认目标**。交付时用你的实际业务与测量值替换。

**可用性**

```
成功率 ≥ 97%（按周统计）
定义：任务状态为 completed 的比例（不含用户主动取消）
```

**延迟**

```
P95 总耗时 ≤ 45 秒
P95 首 token 延迟 ≤ 3 秒
```

**质量**

```
在线评分 ≥ 0.80（U3.6 的采样评估）
用户点踩率 ≤ 5%
```

### 数字怎么定

**从你 U3.8 的实际数据往上定一点，不要拍脑袋。**

```
现状 P95 延迟是 42 秒
→ SLO 定 45 秒（留一点余量，且是你现在能达到的）

现状成功率 94%
→ SLO 先定 95%，达到后再往上提
```

**不要定一个自己都达不到的目标。** 一个天天违反的 SLO 等于没有 SLO——你会习惯性忽略它。

### 错误预算

SLO 97% 意味着允许 3% 的失败。这 3% 就是你的「错误预算」。

**它的用法是**：

- 预算充足时 → 可以大胆发新版本、做实验
- **预算快用完时 → 停止发新功能，专注稳定性**

**这个机制的价值是把「要不要冒险」变成一个有数据依据的决定**，而不是靠感觉。

### 可能卡在哪

**样本量太小，统计没意义**

个人项目一周可能只有几十个任务。**那就按月统计**，或者放宽 SLO 的精度（用「大致 95%」而不是「95.3%」）。

**用户主动取消算失败吗**

不算。**SLO 衡量的是「系统的表现」，不是「用户的行为」。**

但要单独统计取消率——**取消率高本身就是一个信号**（可能是太慢了，或者结果不对）。

## 步骤 2 · 写 Runbook

### 这一步在做什么

把「出这种事该怎么办」写下来，而不是每次现场想。

### 格式

每种故障一节，固定五段：

```markdown
## 故障：模型 API 不可用

### 现象
- 错误率飙升，日志里大量 `429` 或 `503`
- 告警：「错误率 > 20%」
- 用户反馈任务一直失败

### 快速判断（1 分钟）
1. 看告警内容里的错误分布，确认是不是集中在某一家提供方
2. 打开该提供方的状态页（在这里放链接）
3. 手工调一次 API：`curl ...`（在这里放完整命令）

### 立即处理（5 分钟）
- **如果是限流（429）**：
  1. 降低并发数：改配置 `max_concurrency` 从 5 到 2
  2. 如果还不行，切到 fallback 模型：改配置 `model.default` 为备用模型
- **如果是服务故障（5xx）**：
  1. 直接切 fallback 模型
  2. 如果所有云端都不可用，切本地模型（降级模式，告知用户能力受限）

### 恢复后
1. 确认错误率回落
2. 逐步恢复并发和模型配置
3. 在事故记录里写：什么时候开始、什么时候恢复、影响了多少任务

### 预防
- 检查是否需要提升配额
- 检查 fallback 链是否覆盖了这种情况
```

### 必须覆盖的三种故障

**一、模型 API 不可用**（上面那个）

**二、某个工具持续失败**

```markdown
### 现象
特定工具的失败率飙升，但整体服务正常

### 快速判断
1. 打开工具健康度看板（U3.8），确认是哪个工具
2. 看失败类型：参数校验失败 / 外部 API 错 / 超时
3. 打开一条失败的 trace 看具体错误

### 立即处理
- **外部 API 问题**：暂时把这个工具从工具集里摘掉（改配置），
  Agent 会用其他方式完成任务，能力降级但不至于全挂
- **参数校验失败**：说明模型传错参数，可能是 prompt 或工具描述的问题，
  回滚到上一个配置版本
```

**三、质量突然下降**

```markdown
### 现象
在线评分下降，用户点踩增多，但错误率正常

### 快速判断（这类最难查）
1. 看是从什么时候开始的（U3.8 的趋势图）
2. 对照那个时间点，检查：
   - 有没有发布？（查配置版本和代码版本的变更记录）
   - 模型提供方有没有更新版本？（查提供方公告）
   - 上游数据有没有变化？（检索的语料、外部 API 的返回格式）
3. 跑一次离线评估集，看是不是也下降了
   - **离线也降 → 优先查共同的系统/数据变更**
   - **离线正常 → 检查线上输入分布与环境差异**；离线集也可能没覆盖故障，不能直接断言是用户行为变了

### 立即处理
- 如果对应到某次发布 → 回滚（U4.6）
- 如果是模型版本更新 → 固定模型版本号，或者回到旧版本
- 如果是输入分布变化 → 不用回滚，去看那些新的输入，补进评估集
```

质量下降时，“离线评估也降吗”提供一条线索。继续用 U3.5 的五层归因表定位，不要一律归为 prompt 问题。

| 层 | 先看什么证据 | 确认后的处理入口 | 恢复判据 |
|---|---|---|---|
| 模型决策 | 实际输入、工具定义、选中工具、模型/采样版本 | 固定或回退相关模型配置，重跑该类评估 | 正常对照和失败类用例均验证，模型随机性有记录 |
| Prompt | 渲染后的约束、版本/hash 与正常 trace 差异 | 回退缺约束的模板/渲染变更 | 必要约束确实传入模型，回归通过 |
| 工具处理 | 原文引用、原始/传入长度、截断标记、转换错误 | 修复截断或解析，保留原始响应 | 关键字段传入模型，输出不再遗漏 |
| 外部 API | HTTP 与业务状态、fallback、来源、更新时间 | 停用坏来源或明确降级，恢复后查证 | 数据新鲜度和完整性恢复，降级提示一致 |
| 语料 | 文档 ID、版本、更新时间、错误片段和召回排名 | 隔离错误文档，修正并更新索引 | 正确版本被检索，相关案例回归通过 |

把每行展开成前面的五段 Runbook，并填你项目里的真实命令、日志查询、配置文件、回滚方法和负责人。泛泛写“检查 prompt”不算步骤；例如要写清根据哪个 trace ID 取哪次渲染结果，与哪个版本比较。记录证据不足的情况，避免在根因未知时同时改多层。

### 可能卡在哪

**写不出来**

**从你已经遇到过的问题开始写。** 你在 S2 到 S4 一定卡过很多次，那些就是素材。

**Runbook 写完就没人看**

**所以要演练。** 下一步就是。

## 步骤 3 · 降级模式

### 这一步在做什么

核心依赖挂了时，优雅地提供有限服务，而不是全挂。

### 设计降级层次

```python
from enum import Enum


class ServiceMode(str, Enum):
    """服务当前能提供到什么程度。

    继承 str 是为了让枚举值能直接写进日志、配置文件和 HTTP 响应，
    不用每次手动 .value 转换。
    """

    NORMAL = "normal"
    DEGRADED = "degraded"        # 部分能力不可用
    READONLY = "readonly"        # 不接新任务，已有任务继续
    MAINTENANCE = "maintenance"  # 完全不可用


async def current_mode() -> ServiceMode:
    # 判断顺序必须从最严重往下：先命中的先返回。
    # 反过来写的话，数据库都挂了却先撞上「主模型不可用」，会得出偏乐观的降级结论
    if db_unavailable:
        return ServiceMode.MAINTENANCE

    # 模型全挂就没法处理新任务了；但已经跑到一半的任务还有缓存、还有落库的中间结果，
    # 所以是只读而不是维护——维护会连已有任务一起暂停
    if all_models_unavailable:
        return ServiceMode.READONLY

    # 主模型或某个关键工具挂了仍然能干活，只是结果可能不完整。
    # 这一档最容易被忽略，也最需要告知用户，否则用户拿到残缺结果却以为是正常输出
    if primary_model_unavailable or key_tool_unavailable:
        return ServiceMode.DEGRADED

    return ServiceMode.NORMAL
```

### 各模式的行为

| 模式 | 新任务 | 已有任务 | 告知用户 |
|---|---|---|---|
| 正常 | 接受 | 继续 | 无 |
| **降级** | 接受，但**明确告知能力受限** | 继续 | 「当前部分功能不可用，结果可能不完整」 |
| **只读** | **拒绝** | 继续 | 「暂时无法处理新请求，请稍后再试」 |
| 维护 | 拒绝 | 暂停 | 「服务维护中」 |

**关键是要告知用户。** 最差的体验不是「用不了」，而是「用了但结果是错的，而且没人告诉我」。

### 可能卡在哪

**降级模式下 Agent 的行为怎么调整**

在系统提示里加一句：

```
当前 X 工具不可用。如果任务需要它，明确告诉用户「这部分信息暂时无法获取」，
不要用其他方式猜测或编造。
```

**「不要编造」这一句很重要**，否则模型会用它的训练知识填补空缺。

## 步骤 4 · 演练

### 这一步在做什么

**Runbook 只有走过才算数。**

### 怎么做

**每种故障演练一次**：

1. 制造故障（改配置让某个工具指向一个不存在的地址、把模型 key 改错、停掉数据库）
2. **不看代码，只照着 Runbook 走**
3. 记录：
   - 从「发现」到「恢复」花了多久
   - Runbook 里哪一步说得不清楚
   - 有没有需要临场想办法的地方

### 记录

```markdown
## 演练记录 2026-12-15

### 演练 1：模型 API 不可用
制造方式：把 API key 改成无效值
发现时间：14:02（告警到达）
恢复时间：14:07
耗时：5 分钟

**Runbook 的问题**：
- 「切到 fallback 模型」这一步没写清楚具体改哪个配置文件的哪一行 → 已补充
- 状态页的链接失效了 → 已更新

### 演练 2：某个工具持续失败
...

### 演练 3：质量突然下降
制造方式：把 prompt 改成明显有问题的版本
**发现问题**：我没有「质量下降」的告警，是我自己主动去看才发现的。
→ 改进：给在线评分加一条告警（评分低于 SLO 时告警）
```

**「发现问题」这一段是演练的全部价值。**

## 步骤 5 · 分层压测与一次优化（新增 4 小时）

### 这一步在做什么

先量 HTTP 基础开销，再增加数据库，最后加模型等待和并发上限。这样能区分是连接处理、查询、队列，还是模型限额限制了服务，而不是只得到一个“QPS 不够”的结论。

### 怎么做

**先在本地学习靶场练操作。** 仓库 `examples/production-labs/load_service.py` 只监听回环地址，使用临时 SQLite 与 mock 模型，没有模型 key，也不会调用真实模型。SQLite 和 Python HTTP 服务器只是实验用，不代表正式的 Postgres/FastAPI 架构。

```bash
cd ~/ai-agent-roadmap
python3 -m venv .venv
.venv/bin/python -m pip install 'locust==2.46.5'
.venv/bin/python examples/production-labs/load_service.py
```

本次实测启动输出：

```text
local-mock port=8765 indexed=False plan=SCAN items
```

服务会一直运行。在另一个终端执行以下单轮命令；`8` 个虚拟用户、每秒启动 `8` 个、持续 `20s` 是**实验参数**，不是容量结论。先用更低并发熟悉，再逐级调整。

```bash
cd ~/ai-agent-roadmap
mkdir -p s4-production/load
LAB_PATH=/health .venv/bin/locust -f examples/production-labs/locustfile.py --headless --host http://127.0.0.1:8765 -u 8 -r 8 -t 20s --csv s4-production/load/health --only-summary
```

把 `LAB_PATH` 和 `--csv` 文件前缀依次改为 `/db`、`/agent`，**分开运行**。Locust 的 [headless 参数](https://docs.locust.io/en/stable/running-without-web-ui.html)与 [HttpUser 脚本](https://docs.locust.io/en/stable/writing-a-locustfile.html)见官方文档。

本次做了每组 5 秒的脚本 smoke（短于上面的学习测量），macOS arm64 / Python 3.14.6 / Locust 2.46.5，8 用户，每用户请求后等 20ms。以下为实际 CSV 快照；完整条件和局限见 `examples/production-labs/VERIFICATION.md`。

| 无索引基线端点 | CSV 请求数 | 失败数 | CSV requests/s | P95（ms） |
|---|---:|---:|---:|---:|
| `/health` | 592 | 0 | 295.20 | 6 |
| `/db` | 1096 | 0 | 274.56 | 7 |
| `/agent` | 360 | 176 | 90.27 | 94 |

这里 `/agent` 的失败是 mock 并发限额返回的 429：实验人为设置了两个模型槽、40ms 模型延迟、50ms 排队超时。它用于练习“限制在哪里”，不是实测模型性能。Locust 把这些 429 算失败并返回非零退出码；不要改成成功来美化结果。**requests/s 包含失败请求，不能把 90.27 当成成功任务吞吐。**

**做一次改动。** 停掉靶场，只加查询索引后重新启动，其他参数不变：

```bash
.venv/bin/python examples/production-labs/load_service.py --indexed
```

本次实际启动输出：

```text
local-mock port=8765 indexed=True plan=SEARCH items USING INDEX item_key_idx (item_key=?)
```

重跑 `/db` 和 `/agent`，输出文件前缀加 `indexed-`。本次短跑里 `/db` 的 P95 仍为 7ms，`/agent` 的 P95 从 94ms 到 95ms，不能据此宣称优化成功。查询计划确认索引生效，但 HTTP 开销和 mock 模型并发仍在；这正是分层测量要识别的情况。测不到收益就如实保留结果，先量 `db_ms`、`model_wait_ms`、`model_ms` 和服务端资源，再决定下一步。

**迁移到自己的实验服务。** 剩余时间给 coding agent 以下任务：

> 在项目的隔离测试配置中加 Locust 脚本，依次测轻端点、真实数据库查询和 Agent 任务。使用专用测试库和 mock 模型，在代码入口明确标记实验模式，保持正式配置不变。逐级提高并发，每轮记录实际运行时长、虚拟用户、requests/s、成功任务/s、P50/P95、错误分布、CPU/内存、DB 查询/连接等待、任务排队时间。异步 Agent 要跟踪提交到终态：202 只算提交成功，不能当任务完成。用 trace 找一处瓶颈，只改一项，按同样数据和负载重测；提交 CSV、trace、修改和前后结论。如果瓶颈不在改动处，不要声称提升。

保存一张对照表，填自己的测量值：

| 实验轮次 | 数据/代码/模型模式 | 并发与运行时长 | requests/s 与成功任务/s | P50/P95 | 错误率/类型 | 最慢层/证据 | 改动与结论 |
|---|---|---|---|---|---|---|---|
| 基线 / 单项修改后 | 固定并记录 | 自己设置和实测 | 分开统计 | 实测 | 包含 429、超时 | span 与资源指标 | 可以是“无改善” |

把结果写回步骤 1 的 SLO 草案和步骤 2 的 Runbook，例如“API 202 正常、完成吞吐下降、最老等待任务年龄上升”应进入队列/worker 检查，而不是先切模型。只有真实模型和实际部署环境的测量才能支持对应环境的容量结论；mock 实验只验证测量方法和受控链路。

### 可能卡在哪

**用户数就是 QPS 吗**：不是。这个 Locust 脚本是闭环用户模型，每次请求完成后等 20ms 再发下一次；响应慢时实际 QPS 会下降。到达率要求、负载发生器本身的资源与目标容量需要分别记录。

**只看平均延迟，图很漂亮**：同时看 P95、错误分布和成功任务吞吐。大量快速 429 可能让平均值看起来更好，服务却更差。

**压完不知道哪里慢**：先看哪一个层次增加后延迟/错误开始明显变化，再用 trace 和资源指标确认。CPU 不高也可能在等数据库连接、队列或模型并发槽。

**加了索引却没有提升**：确认查询计划实际命中；固定数据、负载、暖机和测试时长，多次复测排除抖动。不要同时改缓存、并发数和模型，否则不知道哪个改动起了作用。

### 背后的逻辑

压测产出应是一条可验证的因果判断：在什么负载和数据下，哪一层先饱和，哪次改动改变了什么。一个孤立的 QPS 数字不能回答线上能接多少用户。
