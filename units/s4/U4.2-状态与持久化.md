# U4.2 · 状态与持久化（10 小时）

**这个单元解决什么问题**

进程可以随时死：机器重启、部署、OOM、你手滑 Ctrl+C。**但任务不能丢，而且不能重复执行已经做过的副作用。**

**学完你能做到**：任务跑到一半 `kill -9`，重启后从断点继续，且已完成的副作用不重复执行。

---

## 步骤 1 · 把状态分类并决定存哪

### 这一步在做什么

U2.4 分过三种记忆，这里从「持久化」的角度再分一次。

### 三类状态

| 类型 | 内容 | 存哪 | 丢了会怎样 |
|---|---|---|---|
| **会话状态** | 消息历史 | Postgres | 用户的对话上下文没了 |
| **任务状态** | 跑到第几步、每步结果、已执行的副作用 | **Postgres，必须持久** | **任务无法恢复，可能重复扣款** |
| **临时状态** | 单次函数调用内的变量 | 内存 | 无所谓 |

**关键判断：一个状态丢了会不会导致「不一致」？** 会的话必须持久化。

### 12-factor 第 5 条说的「统一」是什么意思

反面例子：

```
执行状态存在 Redis：{"task_id": "t1", "step": 3}
业务数据存在 Postgres：草稿表里有 3 条记录
```

**这两套可能不一致**：Redis 说跑到第 3 步，但 Postgres 里只有 2 条记录（第 3 步写到一半崩了）。

**正解**：把执行状态和业务数据放在同一个数据库，用**同一个事务**更新。

```sql
BEGIN;
INSERT INTO drafts (...) VALUES (...);           -- 业务数据
UPDATE tasks SET step = 3, updated_at = now() WHERE id = 't1';   -- 执行状态
COMMIT;
```

**这样它们要么一起成功，要么一起失败，永远一致。**

### 可能卡在哪

**用了 LangGraph 的 checkpointer，它存在哪**

看你配的后端。如果配的是 Postgres 且和业务库是同一个，可以做到同事务；如果是内存或者另一个库，就有不一致风险。

**查清楚你的框架实际怎么存的**——这正是 12-factor 第 5 条要你做的。

**Redis 不能用吗**

能用，但只用于**可以丢失的数据**（缓存、限流计数、会话的热数据）。**任何丢了会导致不一致的东西，放数据库。**

## 步骤 2 · Checkpoint 设计

### 这一步在做什么

在每一步之后保存状态，让任务能从任意一步恢复。

### 表结构

```sql
-- 任务主表：一行 = 一个可恢复的任务，恢复所需的一切都在这里
CREATE TABLE tasks (
    id               TEXT PRIMARY KEY,
    user_id          TEXT NOT NULL,
    task_type        TEXT NOT NULL,
    input            JSONB NOT NULL,
    status           TEXT NOT NULL DEFAULT 'pending',
      -- pending / running / paused / completed / failed / cancelled
    current_step     INTEGER NOT NULL DEFAULT 0,   -- 恢复时从这一步之后继续
    context_snapshot JSONB,                        -- 消息历史等，重启后靠它重建上下文
    result           JSONB,
    error            TEXT,
    created_at       TIMESTAMPTZ DEFAULT now(),
    updated_at       TIMESTAMPTZ DEFAULT now(),
    lock_holder      TEXT,                         -- 哪个进程在跑，防止两个进程抢同一个任务
    lock_expires_at  TIMESTAMPTZ                   -- 持锁进程崩了也能靠过期时间释放
);

-- 步骤表：每步一行，是「这一步做过没有」的唯一事实来源
CREATE TABLE task_steps (
    id               SERIAL PRIMARY KEY,
    task_id          TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    step_index       INTEGER NOT NULL,
    step_type        TEXT NOT NULL,   -- model_call（模型调用）/ tool_call（工具调用）/ human_confirm（人工确认）
    input            JSONB,
    output           JSONB,
    status           TEXT NOT NULL,   -- in_progress（记了意图还没确认）/ completed / failed
    idempotency_key  TEXT,            -- 只有带副作用的步骤才填
    duration_ms      INTEGER,
    cost             NUMERIC(10, 6),
    created_at       TIMESTAMPTZ DEFAULT now(),
    -- 同一个任务的同一步只能有一行，重放时插入会直接冲突失败
    UNIQUE (task_id, step_index)
);

-- 部分唯一索引：只约束填了幂等键的行，让数据库兜住重复执行
CREATE UNIQUE INDEX ON task_steps (idempotency_key) WHERE idempotency_key IS NOT NULL;
```

**注意最后那个唯一索引**：它从数据库层面保证同一个幂等键只能有一条记录。**这是幂等的最后一道防线。**

### 状态机

```
pending ──→ running ──→ completed
              │  │
              │  └────→ failed
              │
              └──────→ paused ──→ running
                          │
                          └─────→ cancelled
```

**状态转换要合法。** 写一个函数检查：

```python
合法转换 = {
    "pending": {"running", "cancelled"},
    "running": {"completed", "failed", "paused", "cancelled"},
    "paused": {"running", "cancelled"},
    "completed": set(),
    "failed": {"running"},        # 允许重试
    "cancelled": set(),
}

def 转换状态(任务, 新状态: str):
    if 新状态 not in 合法转换[任务.状态]:
        raise ValueError(f"不能从 {任务.状态} 转到 {新状态}")
    任务.状态 = 新状态
```

**加这个检查能挡掉一整类 bug**（比如已完成的任务又被启动）。

### 主循环改造

```python
async def 跑任务(task_id: str):
    async with 事务() as tx:
        任务 = await 加锁取任务(tx, task_id)      # SELECT ... FOR UPDATE
        if 任务.状态 not in ("pending", "paused", "failed"):
            return
        转换状态(任务, "running")

    历史 = 任务.上下文快照 or 初始历史(任务.输入)
    步骤 = 任务.当前步骤

    while 步骤 < 上限:
        步骤 += 1

        # 已执行过就跳过（恢复时的关键）
        已有 = await 查步骤(task_id, 步骤)
        if 已有 and 已有.状态 == "已完成":
            历史 = 应用步骤结果(历史, 已有)
            continue

        结果 = await 执行一步(历史, 步骤)

        # 业务数据和执行状态同事务写入
        async with 事务() as tx:
            await 写步骤(tx, task_id, 步骤, 结果)
            await 更新任务(tx, task_id, 当前步骤=步骤, 上下文快照=历史)
```

### 可能卡在哪

**上下文快照太大**

消息历史可能几万 token。三个优化：

1. 压缩后再存（用 U1.5 的策略）
2. 只存增量，恢复时重建
3. 大内容存对象存储，快照里放引用

**每步都写数据库，性能受不了**

Agent 的一步通常是几百毫秒到几秒（模型调用），**多一次数据库写入（几毫秒）可以忽略**。

如果真的成了瓶颈，可以隔 N 步存一次，代价是恢复时最多重做 N 步。

## 步骤 3 · 幂等：最难的部分

### 这一步在做什么

**保证恢复时不重复执行有副作用的操作。**

### 问题的本质

```
执行外部操作（发消息、扣款）
        ↓
    ← 这里崩溃
        ↓
记录「已执行」
```

**恢复时你不知道那次操作到底成功了没有。**

### 三种解法

**解法一：外部服务支持幂等键（最好）**

很多支付、消息服务的 API 支持传一个幂等键，同一个键重复请求只执行一次。

```python
await 外部服务.发送(内容, idempotency_key=f"{task_id}:{步骤}")
```

**能用这个就用这个，最可靠。**

**解法二：先记意图，再执行，最后确认**

```python
# 1. 先记「打算做」
async with 事务() as tx:
    await 写步骤(tx, task_id, 步骤, 状态="进行中", 幂等键=键)

# 2. 执行
try:
    结果 = await 外部操作()
    状态 = "已完成"
except Exception as e:
    结果, 状态 = str(e), "失败"

# 3. 记结果
async with 事务() as tx:
    await 更新步骤(tx, task_id, 步骤, 状态=状态, 输出=结果)
```

**恢复时**：看到「进行中」的步骤，说明崩溃发生在执行期间，**必须去外部服务查证**这次操作到底做了没有。

```python
if 已有.状态 == "进行中":
    实际 = await 外部服务.查询(幂等键=已有.幂等键)
    if 实际.存在:
        await 标记完成(已有, 实际)
    else:
        await 重新执行()
```

**「去查证」这一步是必须的，没有捷径。**

**解法三：设计成可重放**

把操作设计成「设置为某个值」而不是「增加某个值」：

```
不幂等：余额 = 余额 - 100
幂等：  余额 = 900        （如果已经是 900，重放无影响）
```

**能改成这样的就改**，能省掉大量麻烦。

### 可能卡在哪

**外部服务不支持查询**

那就只能用「宁可少做不可多做」或「宁可多做不可少做」的策略，取决于哪种后果更严重：

- **发消息**：多发比不发烦人，但不致命 → 可以选择重试
- **扣款**：多扣是事故 → 必须选择不重试，人工介入

**在设计时就要明确每个操作属于哪一类。**

**幂等键怎么生成**

`{task_id}:{步骤序号}` 是最简单可靠的。**不要让模型生成**——它不保证唯一，也不保证重放时一致。

如果同一步可能调多次同一个工具，加上调用序号：`{task_id}:{步骤}:{调用序号}`。

## 步骤 4 · 并发控制

### 这一步在做什么

防止同一个任务被两个进程同时跑。

### 为什么会发生

- 你手动重启了任务，但旧进程还没死透
- 部署时新旧两个版本同时在跑
- 定时任务和用户触发撞在一起

**后果**：副作用重复执行、状态互相覆盖。

### 用数据库行锁

```python
async def 加锁取任务(tx, task_id: str, 持有者: str, 超时秒: int = 600):
    行 = await tx.execute(text("""
        SELECT * FROM tasks
        WHERE id = :id
        FOR UPDATE NOWAIT
    """), {"id": task_id})

    任务 = 行.first()
    if 任务.锁持有者 and 任务.锁过期时间 > now():
        raise 任务已被占用(f"{task_id} 正被 {任务.锁持有者} 执行")

    await tx.execute(text("""
        UPDATE tasks SET 锁持有者 = :who, 锁过期时间 = now() + make_interval(secs => :ttl)
        WHERE id = :id
    """), {"who": 持有者, "ttl": 超时秒, "id": task_id})
    return 任务
```

**`FOR UPDATE NOWAIT` 的意思**：尝试加锁，加不上立刻报错而不是等待。

### 锁要有过期时间

如果持有锁的进程崩了，锁不能永远留着。**设一个 TTL**（比如 10 分钟），过期后别的进程可以抢。

**长任务要定期续期**：

```python
async def 续锁(task_id, 持有者):
    while 任务还在跑:
        await asyncio.sleep(60)
        await 延长锁(task_id, 持有者, 秒=600)
```

### 可能卡在哪

**锁过期了但进程还活着**

会导致两个进程同时跑。**续期的间隔要远小于 TTL**（比如 TTL 600 秒，每 60 秒续一次）。

**用 Redis 分布式锁行吗**

行，而且更轻。但要注意 Redis 锁的经典问题（进程 GC 停顿导致锁过期但进程以为自己还持有）。

**对个人项目，数据库行锁足够，而且和事务天然一致。**
