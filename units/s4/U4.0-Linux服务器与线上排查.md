# U4.0 · Linux 服务器与线上排查（4 小时）

**这个单元解决什么问题**

**又一处计划的自相矛盾，补上它不是加内容，是让 S4 的验收真正可达。**

U4.7 的验收要求「一个真实可访问的地址」「故意搞挂它，手机两分钟内收到告警」。U4.8 要求写三种故障的 Runbook。**但这两个单元之前，全库没有出现过 `ssh`、`systemctl`、`journalctl`。**

U0.1 教的是 macOS 本机的 `cd`、`ls`、`grep`、管道、重定向——**那是「用命令行管文件」，和「登上一台没有图形界面的服务器把问题查出来」是两回事。**

**为什么 JD 也要它**：本次核验的 2026 年在招 JD 里，后端通用角度 5/10 条写了「Linux 环境下的开发与线上排查」。**重点在后半句。**

**学完你能做到**：ssh 上一台服务器，把服务跑成 systemd 服务，配上反向代理，并在服务挂掉时用五件套定位到根因。

## 步骤 1 · 弄一台练习用的服务器

### 这一步在做什么

你需要一台真的 Linux 机器，本机的 Docker 容器不能完全替代——容器里没有 systemd，没有真实的网络边界。

### 三个选择

| 方式 | 成本 | 说明 |
|---|---|---|
| **云服务器按量付费** | 几块钱/天 | **推荐**。阿里云、腾讯云的轻量应用服务器，2核2G 够用，学完就释放 |
| 本地虚拟机 | 免费 | UTM（Mac）或 multipass，装 Ubuntu Server |
| 完整的 Ubuntu 容器 | 免费 | `docker run -d --privileged ubuntu:24.04 /sbin/init`，能跑 systemd 但网络部分打折 |

**建议花那几块钱买真的。** 你要练的东西里有一半和「这是一台在公网上的机器」有关。

### 拿到之后

```bash
ssh root@你的服务器IP
```

第一次会问你是否信任指纹，输 yes。

**看看你在哪**：

```bash
cat /etc/os-release       # 什么发行版什么版本
uname -a                  # 内核版本和架构
whoami                    # 当前用户
df -h                     # 磁盘还剩多少
free -h                   # 内存多大、用了多少
nproc                     # 几核
```

### 可能卡在哪

**连不上**

按顺序排查：IP 对不对；安全组/防火墙放开 22 端口了吗（云厂商默认可能没开）；密码对不对。

**Permission denied (publickey)**

服务器禁了密码登录，只允许密钥。用云控制台的 VNC 登进去，或者重置时选择密码登录。

## 步骤 2 · 密钥登录与用户权限

### 这一步在做什么

两件事：让登录更安全，以及理解「为什么服务不该用 root 跑」。

### 配密钥登录

在你的 Mac 上：

```bash
# 如果还没有密钥（U0.2 配 GitHub 时可能已经生成过）
ssh-keygen -t ed25519 -C "你的邮箱"

# 把公钥传上去
ssh-copy-id root@你的服务器IP
```

之后 `ssh root@IP` 不用输密码了。

**然后禁掉密码登录**：

```bash
sudo vim /etc/ssh/sshd_config
# 改这两行：
#   PasswordAuthentication no
#   PermitRootLogin prohibit-password
sudo systemctl restart sshd
```

**改之前先另开一个终端保持连接。** 万一配错了，你还有一条活路能改回来。

### 建一个专用用户跑服务

```bash
# 建用户，不给登录 shell —— 服务用户不需要登录
sudo useradd -r -s /usr/sbin/nologin appuser

# 建应用目录并交给它
sudo mkdir -p /opt/myapp
sudo chown -R appuser:appuser /opt/myapp
```

**为什么不用 root 跑服务**

这不是洁癖。如果你的服务有漏洞被攻破（回想 S4 的 U4.4，提示注入是真实威胁），攻击者拿到的权限就是服务进程的权限。

- root 跑 → 攻击者拿到整台机器
- appuser 跑 → 攻击者只能碰 `/opt/myapp`

**这就是最小权限原则在操作系统层的体现**，和 U4.4 讲的是同一件事。

### 理解权限位

```bash
ls -l /opt/myapp
# drwxr-xr-x 2 appuser appuser 4096 Sep 10 12:00 .
#  ↑↑↑↑↑↑↑↑↑   ↑        ↑
#  权限位       属主      属组
```

三组三位：属主、属组、其他人，各自的读写执行。

```bash
chmod 600 .env       # 只有属主能读写 —— 密钥文件必须这样
chmod 755 script.sh  # 属主可读写执行，其他人只能读和执行
chown appuser:appuser file
```

**`.env` 一定要 600。** 644 意味着服务器上任何用户都能读你的 API key。

## 步骤 3 · 用 systemd 把服务跑起来

### 这一步在做什么

`python main.py &` 挂在后台不算部署——你一断开 ssh 它就没了，崩了也不会自动重启。

### 怎么做

把 U0.9 的镜像拉上来，或者直接跑 Python。这里用 Docker 的方式（和你 S4 的部署一致）：

建 `/etc/systemd/system/myapp.service`：

```ini
[Unit]
Description=My Agent API
# 声明依赖：docker 起来了才启动本服务
After=docker.service
Requires=docker.service

[Service]
Type=simple
User=appuser
WorkingDirectory=/opt/myapp
# --rm 保证容器退出即清理，避免残留容器占用名字
ExecStart=/usr/bin/docker run --rm --name myapp -p 8000:8000 --env-file /opt/myapp/.env myimage:latest
ExecStop=/usr/bin/docker stop myapp
# 崩了自动重启，间隔 5 秒 —— 避免崩溃循环把 CPU 打满
Restart=always
RestartSec=5

[Install]
# 开机自启挂在这个 target 下
WantedBy=multi-user.target
```

四个命令你要熟到不用想：

```bash
sudo systemctl daemon-reload      # 改了 .service 文件后必须先重载
sudo systemctl start myapp        # 启动
sudo systemctl status myapp       # 看状态 —— 出问题第一个跑这个
sudo systemctl enable myapp       # 设置开机自启
```

### 看日志

```bash
journalctl -u myapp              # 这个服务的全部日志
journalctl -u myapp -f           # 实时跟踪，相当于 tail -f
journalctl -u myapp -n 100       # 最近 100 行
journalctl -u myapp --since "10 min ago"
journalctl -u myapp -p err       # 只看 error 级别以上
```

**`journalctl -u 服务名 -f` 是你在服务器上敲得最多的命令。** 现在就把它记住。

### 可能卡在哪

**`systemctl status` 显示 failed**

看 `journalctl -u myapp -n 50`，错误原因基本都在最后几行。常见的是：路径不对、权限不足、端口被占、环境变量缺失。

**改了 .service 没生效**

忘了 `daemon-reload`。systemd 缓存了配置。

**Restart=always 导致疯狂重启**

如果服务启动就崩，systemd 会每 5 秒重启一次，日志刷屏。加上 `StartLimitBurst=5` 和 `StartLimitIntervalSec=60`，连续失败 5 次就停下来等你处理。

### 背后的逻辑

systemd 是现代 Linux 的**服务管理器**：它负责启动顺序、依赖关系、崩溃重启、日志收集、资源限制。

理解它的价值在于：**你在 U4.7 用的云平台，底层做的也是这些事。** 平台把它包装成了图形界面，但概念是一样的——健康检查、自动重启、日志聚合。

**知道底下是什么，出问题时你才知道往哪查。**

## 步骤 4 · 排查五件套

### 这一步在做什么

**这是本单元的核心。** 服务挂了、变慢了、连不上了——五组命令覆盖 90% 的情况。

### 一、进程与 CPU

```bash
top                    # 交互式，按 P 按 CPU 排序，按 M 按内存排序
htop                   # 更好用，需要 apt install htop
ps aux | grep myapp    # 找特定进程
ps -eo pid,ppid,cmd,%cpu,%mem --sort=-%cpu | head -10   # CPU 前十
```

**要看的**：哪个进程在吃 CPU；进程还在不在；有没有意外的多个副本。

### 二、内存与 OOM

```bash
free -h                          # total/used/available，看 available 而不是 free
dmesg -T | grep -i "killed process"   # ← 关键：进程是不是被 OOM killer 杀了
```

**`dmesg | grep -i oom` 这条要记住。** 服务莫名其妙消失、`systemctl status` 显示被 signal 9 杀掉——十有八九是内存不够被内核干掉了，而且**应用日志里什么都不会留下**，因为进程是被瞬间杀死的。

### 三、磁盘

```bash
df -h                            # 各分区用了多少 —— 先看这个
du -sh /var/log/* | sort -rh | head   # 哪个目录最大
du -sh /* 2>/dev/null | sort -rh | head
```

**磁盘写满会让服务以极其诡异的方式失败**：数据库写不进去、日志写不了、临时文件建不了。而报错信息往往完全不指向磁盘。

**养成习惯：任何诡异问题，先 `df -h`。**

### 四、端口与网络

```bash
ss -tlnp                         # 谁在监听哪些端口（netstat 的现代替代）
ss -tn state established         # 当前建立的连接
lsof -i :8000                    # 8000 端口被谁占了
curl -v http://localhost:8000/health    # 从机器内部测
curl -v http://服务器IP:8000/health      # 从外部测
```

**「服务起来了但连不上」的排查顺序**：

1. `ss -tlnp` 确认真的在监听
2. **看监听地址**：`127.0.0.1:8000` 只接受本机连接，`0.0.0.0:8000` 才接受外部——**这和 U0.9 讲的容器里必须 `--host 0.0.0.0` 是同一个坑**
3. 本机 `curl localhost` 能通吗
4. 防火墙：`sudo ufw status`
5. **云厂商的安全组**——这一条最容易忘，它在服务器之外

### 五、日志

```bash
journalctl -u myapp -f | grep -i error
tail -f /var/log/nginx/error.log
grep -c "ERROR" /var/log/myapp.log              # 数一下有多少
grep "ERROR" /var/log/myapp.log | tail -20      # 看最近的
```

**U0.1 学的管道和 grep 在这里全用上了。**

## 步骤 5 · nginx 反向代理与 SSE 的那个坑

### 这一步在做什么

**这一步能把 U5.4 里那个「记住加 `X-Accel-Buffering: no`」变成「知道为什么」。**

### 配一个反向代理

```bash
sudo apt install nginx
```

`/etc/nginx/sites-available/myapp`：

```nginx
server {
    listen 80;
    server_name 你的域名;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        # 让后端知道真实客户端 IP，否则日志里全是 127.0.0.1
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # SSE 端点必须单独配 —— 这就是那个坑的根源
    location /tasks/ {
        proxy_pass http://127.0.0.1:8000;
        # nginx 默认会缓冲后端响应，攒够一块再发给客户端。
        # 对普通请求这是优化，对流式响应是致命的：
        # 用户会等到全部生成完才一次性看到，流式完全失效
        proxy_buffering off;
        proxy_cache off;
        # SSE 是长连接，默认 60 秒超时会把它掐断
        proxy_read_timeout 3600s;
        # SSE 走 HTTP/1.1，且不能用 keepalive 复用
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/
sudo nginx -t                    # 先测配置语法，别直接 reload
sudo systemctl reload nginx
```

**亲手验证那个坑**：

1. 先不加 `proxy_buffering off`，用 `curl -N` 请求你的 SSE 端点——你会看到它一次性全出来
2. 加上之后再试——现在是逐条出来的

**做完这个实验，U5.4 里那个 `X-Accel-Buffering: no` 响应头你就懂了**：那是应用层告诉 nginx「这个响应别缓冲」，和这里在 nginx 侧配 `proxy_buffering off` 是同一件事的两种做法。

### 配 HTTPS

```bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d 你的域名
```

certbot 会自动改 nginx 配置并设置自动续期。**前提是域名已经解析到这台机器，且 80 端口能从公网访问。**

## 步骤 6 · 防火墙与日志轮转

### 这一步在做什么

两件容易忘但会出事的小事。

### 防火墙

```bash
sudo ufw allow 22        # 先放开 SSH ！！！
sudo ufw allow 80
sudo ufw allow 443
sudo ufw enable
sudo ufw status
```

**先放 22 再 enable。** 顺序反了你会把自己关在门外，只能去云控制台用 VNC 救。

**注意**：8000 端口不要放开——外部只该通过 nginx 的 80/443 访问，应用端口只对本机开放。

### 日志轮转

**日志撑爆磁盘是最常见的生产事故之一，而且它发生得很慢，等你发现时已经出事了。**

建 `/etc/logrotate.d/myapp`：

```
/var/log/myapp/*.log {
    daily              # 每天轮转一次
    rotate 14          # 保留 14 份
    compress           # 旧的压缩
    delaycompress      # 最近一份先不压，方便查看
    missingok          # 文件不存在不报错
    notifempty         # 空文件不轮转
    create 0640 appuser appuser
}
```

```bash
sudo logrotate -d /etc/logrotate.d/myapp    # -d 是 dry-run，先看看会做什么
```

## 步骤 7 · 制造三种故障各排查一遍

### 这一步在做什么

**只有亲手制造并排查过，Runbook 才写得出来。**

### 故障一：磁盘写满

```bash
# 造一个大文件把磁盘填满
fallocate -l 10G /tmp/bigfile
df -h                            # 确认满了
```

现在去访问你的服务，观察它怎么失败。**记录：报的什么错？这个错指向磁盘问题吗？**

排查路径：`df -h` → `du -sh /* | sort -rh` → 找到 `/tmp/bigfile` → 删掉。

```bash
rm /tmp/bigfile
```

### 故障二：端口被占

```bash
# 先停掉服务，然后用别的东西占住端口
sudo systemctl stop myapp
python3 -m http.server 8000 &
sudo systemctl start myapp       # 会失败
```

排查路径：`systemctl status myapp` 看到失败 → `journalctl -u myapp -n 30` 看到 "address already in use" → `ss -tlnp | grep 8000` 或 `lsof -i :8000` 找到占用进程 → 处理。

### 故障三：进程 OOM

```bash
# 在容器上加一个很小的内存限制，然后让它处理一个大任务
docker run --rm --memory=64m myimage:latest
```

或者直接在服务器上跑一个吃内存的 Python：

```python
x = bytearray(10 ** 10)
```

排查路径：服务突然消失 → `systemctl status` 显示被 signal 9 杀 → **应用日志里什么都没有** → `dmesg -T | grep -i "killed process"` 确认是 OOM killer。

**「应用日志里什么都没有」是 OOM 的典型特征**，因为进程是被内核瞬间杀死的，没机会写日志。

### 写进 Runbook

三种故障各写一节，格式和 U4.8 一致：现象、快速判断、立即处理、恢复后、预防。

**每条命令都要贴你自己机器上跑出的真实输出。**
