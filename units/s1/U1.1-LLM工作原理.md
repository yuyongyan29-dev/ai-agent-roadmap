# U1.1 · LLM 工作原理（工程视角）（6 小时）

**这个单元解决什么问题**

你要开始跟大模型打交道了。但在写第一行调用代码之前，你需要一个准确的心智模型：**它到底在做什么，为什么会犯那些错，什么因素会改变它的输出。**

**这个单元不推公式，不讲 Transformer 架构。** 你不需要知道注意力机制怎么算，你需要知道的是：为什么长对话越来越贵、为什么它会一本正经地编造、为什么同一个问题问两次答案不一样。

**学完你能做到**：预判模型在什么情况下会出错；知道调哪个参数能改变什么。

## 步骤 1 · Token：模型眼里的文字

### 这一步在做什么

理解模型不是按「字」来处理文本的，而是按 token。**这直接决定你的成本。**

### 怎么做

打开 [OpenAI Tokenizer](https://platform.openai.com/tokenizer)，或者用代码：

```bash
cd s1-llm && uv init . && uv add tiktoken
```

```python
import tiktoken

# o200k_base 是 GPT-4o 系列用的分词器；换模型就要换编码，同一段文字算出来的 token 数会不同
enc = tiktoken.get_encoding("o200k_base")

# 故意放四类差别很大的文本，是为了对比「字符数 → token 数」的比例
samples = {
    "英文": "Hello, how are you doing today?",
    "中文": "你好，今天过得怎么样？",
    "代码": 'def add(a: int, b: int) -> int:\n    return a + b',
    "JSON": '{"name": "test", "count": 42}',
}

for label, text in samples.items():
    ids = enc.encode(text)
    print(f"{label}: {len(text)} 字符 → {len(ids)} tokens")
    # 逐个 decode 单个 id，才能看到切分边界；只看前 12 个，重点是观察词是怎么被拆开的
    print("  切分：", [enc.decode([i]) for i in ids[:12]])
```

### 你会看到什么

大致规律（不同模型的分词器有差异）：

| 内容 | 大致比例 |
|---|---|
| 英文 | 1 token ≈ 4 个字符 |
| **中文** | **1 个汉字 ≈ 0.6 到 1.5 token** |
| 代码 | 缩进、符号会占掉很多 token |
| JSON | 引号、冒号、括号每个都是 token |

**看切分结果会让你惊讶**：英文单词常常被拆成词根加后缀，中文有时一个字一个 token，有时两三个字合成一个。

### 这对你意味着什么

1. **中文比英文贵**。同样的意思，中文的 token 数通常更多
2. **JSON 格式的返回值成本不低**。你在 S2 设计工具返回值时要考虑这个
3. **缩进和空格都要花钱**。往上下文里塞格式化的 JSON 时要意识到这一点

### 可能卡在哪

**不同模型的 token 数不一样**

对。每家模型有自己的分词器，同一段文字算出来的 token 数不同。`tiktoken` 是 OpenAI 的，Anthropic 有自己的。

**估算方法**：中文按「字数 × 1.5」，英文按「字符数 ÷ 4」，够用了。精确计费以 API 返回的 usage 为准。

**为什么要关心这个**

到 S4 你要把成本降 40%，那时你会回来感谢自己现在建立的直觉。

### 背后的逻辑

**为什么不按字符处理？** 因为词表会太小，模型要处理的序列太长。

**为什么不按词处理？** 因为词表会太大（中文几十万词），而且遇到没见过的词就傻了。

Token 是折中：用一套「子词」单元，常见词一个 token，罕见词拆成几个部分。这样几万个 token 就能表示任何文本，包括没见过的新词。

**这也解释了一个经典现象**：问模型「strawberry 里有几个 r」它容易答错。因为它看到的不是 s-t-r-a-w-b-e-r-r-y 这 10 个字母，而是可能只有 2 到 3 个 token。**它根本看不到字母。**

## 步骤 2 · 自回归生成：它一次只想一个词

### 这一步在做什么

理解模型生成文本的过程，这是理解它所有行为的钥匙。

### 过程是这样的

给定输入「今天天气」，模型做的事是：

1. 计算「下一个 token 最可能是什么」，得到一个概率分布：`真` 30%、`不` 15%、`很` 12%、……
2. 按某种规则从中挑一个，比如挑中 `真`
3. **把 `真` 接到输入后面**，变成「今天天气真」
4. 回到第 1 步，重新算下一个

一直重复，直到生成了结束标记或者达到长度上限。

### 三个重要推论

**推论一：它没有「先想好再说」。**

模型不是先在心里构思完整答案再输出。**每一个 token 都是当场决定的。** 这就是为什么让它「一步步思考」（思维链）能提升准确率——把推理过程写出来，后面的 token 才能「看到」前面的推理。

**推论二：输出越长，越可能跑偏。**

每一步都有出错的概率，错误会累积并被后续步骤当成既定事实。

**推论三：错的开头会一路错下去。**

如果第一句话的方向就错了，后面所有内容都会围绕这个错误展开——因为对模型来说，前面输出的内容和你的输入一样都是「上下文」。

**这条推论在 Agent 里被放大**：如果第一轮工具调用返回了错误信息，后续所有决策都基于这个错误。S1.5 学的上下文管理和 S2 的错误处理，根子都在这。

### 亲手验证

```python
# 题干保持完全一致，只改末尾的输出要求，这样差异才只来自「是否写出中间步骤」
question = "一个班有 23 个学生，每人 4 支笔，其中 5 人各丢了 2 支。现在共有多少支笔？"

# 直接要数字：模型只有一次生成机会，多步运算被压进了一个 token 的计算量里
direct_prompt = question + "\n直接给出数字答案。"
# 要求写步骤：每一步的中间结果都进入上下文，后面的 token 能「看到」它们
cot_prompt = question + "\n一步步计算，先写出每一步，最后给答案。"
```

各跑 10 次，统计正确率。**分步的准确率通常明显更高。**

### 背后的逻辑

**为什么「一步步思考」有用？**

因为模型每生成一个 token 时，能用到的「计算量」是固定的。复杂问题需要多步推理，但如果直接输出答案，它只有一次机会。

让它写出中间步骤，等于给了它更多次计算机会，而且每一步的结果都进入上下文供后续使用。**思维链本质上是在用输出长度换计算深度。**

这也是「推理模型」（reasoning model）的原理——它们被训练成在给出答案前先生成大量思考内容。

## 步骤 3 · 采样参数：控制随机性

### 这一步在做什么

搞清楚 `temperature`、`top_p` 这些参数到底在调什么，什么任务该用什么值。

### 它们在调什么

上一步说到，模型算出的是一个概率分布。**采样参数决定「怎么从这个分布里挑」。**

**temperature（温度）** 改变分布的形状：

| 值 | 效果 |
|---|---|
| `0` | 永远选概率最高的那个。**最稳定，接近确定性** |
| `0.3` | 稍有变化，主要还是选高概率的 |
| `1.0` | 按原始概率分布采样 |
| `1.5+` | 放大低概率选项，输出发散甚至语无伦次 |

**top_p（核采样）** 改变候选范围：只从「累计概率达到 p」的那部分候选里选。`top_p=0.1` 意味着只考虑最可能的那一小撮。

**通常只调一个，不要两个一起调。**

### 怎么选

| 任务 | 建议 | 理由 |
|---|---|---|
| 结构化抽取、分类 | `0` 到 `0.2` | 要的是准确和可复现 |
| **Agent 的工具调用决策** | `0` 到 `0.3` | 要稳定，不要创意 |
| 一般问答、总结 | `0.3` 到 `0.7` | 平衡 |
| 创意写作、头脑风暴 | `0.8` 到 `1.2` | 要多样性 |

**注意**：`temperature=0` 也**不保证完全一样**。浮点运算的顺序、服务端的批处理、模型版本更新都会带来差异。**不要设计依赖「完全可复现」的系统。**

### 做这个实验

```python
import asyncio
from collections import Counter

question = "用一句话描述什么是 AI Agent。"

async def run_sampling_experiment():
    """同一个问题在不同 temperature 下各跑 10 次，观察输出的发散程度。

    只改 temperature 一个变量，prompt 和模型都固定，否则分不清差异来自哪里。
    """
    for t in [0.0, 0.3, 0.7, 1.0, 1.5]:
        outputs = []
        for _ in range(10):
            # call_model 是你自己封装的调用函数（U1.2 会写），这里只关心它接收 temperature
            r = await call_model(question, temperature=t)
            outputs.append(r)
        # 用 set 去重来量化随机性：越接近 10/10 不重复，说明采样越发散
        unique_count = len(set(outputs))
        avg_length = sum(len(o) for o in outputs) / 10
        print(f"temperature={t}: {unique_count}/10 不重复，平均 {avg_length:.0f} 字")
        # 顺带打一条样例，因为「不重复」只是措辞不同还是意思也变了，得肉眼看
        print(f"  样例：{outputs[0][:60]}")
```

**把结果做成表格存进笔记。** 这是本单元的核心产出。

### 可能卡在哪

**temperature=0 还是不一样**

正常，见上面的说明。如果差异很大（不只是措辞不同而是意思不同），检查是不是 prompt 里有歧义。

**有些模型不支持某些参数**

推理模型（reasoning model）通常不接受 temperature 参数，或者忽略它。读各家文档。

**调高 temperature 后输出变得莫名其妙**

这就是它的作用。超过 1.2 通常不实用。

### 背后的逻辑

temperature 这个名字来自统计物理学。它在 softmax 函数里作为分母：

```
概率 = exp(分数 / temperature) / 求和
```

- `temperature` 趋近 0 时，最高分的那个概率趋近 1，其余趋近 0 → 确定性
- `temperature` 很大时，所有分数被压平，概率趋于均匀 → 随机

**理解这个公式没有必要，理解「它在调整分布的尖锐程度」就够了。**

## 步骤 4 · 上下文窗口

### 这一步在做什么

理解模型的「记忆容量」，以及一个关键事实：**窗口大不等于能用满**。

### 基本概念

上下文窗口是**输入加输出的总预算**。

```
系统提示 + 工具定义 + 对话历史 + 你这次的输入 + 模型的输出 ≤ 窗口大小
```

新手常见误解是以为窗口只限制输入。如果你的输入已经占了 99%，模型就没空间输出了。

### 关键事实：长上下文会让质量下降

**这不是容量问题，是性能问题。** 所有前沿模型在上下文变长时表现都会可测量地下降，而且**远在窗口填满之前就开始**。

常见的表现：

- **中间遗忘**：放在上下文中段的信息最容易被忽略，开头和结尾的最受关注
- **注意力稀释**：无关信息越多，模型越容易抓错重点
- **指令衰减**：系统提示里的要求，在长对话后期越来越不被遵守

### 亲手验证

设计一个实验：

1. 准备一段关键信息，比如「用户的预算上限是 3000 元」
2. 分别把它放在上下文的开头、中间、结尾
3. 每种位置各跑 10 次，问一个需要用到这条信息的问题
4. 统计正确率

**你会发现中间位置的正确率明显低。** 把这个结果记进笔记，它会影响你 S2 设计上下文结构的方式。

### 这对你意味着什么

**不要把「塞得多」当成优化。** 精心挑选的 2000 token 上下文，效果通常好过随意堆砌的 50000 token，而且便宜 25 倍。

这就是 U1.5「上下文工程」的核心命题，那一节会给你三种具体的压缩策略。

### 可能卡在哪

**报错 `context_length_exceeded`**

超窗口了。要么压缩输入，要么换窗口更大的模型，要么减少 `max_tokens`。

**输出被截断**

`max_tokens` 设小了，或者窗口不够。检查返回的 `finish_reason`：

- `stop` = 正常结束
- `length` = **被截断了**
- `tool_use` = 要调工具
- `content_filter` = 被安全策略拦了

**每次都要检查 `finish_reason`。** 不检查的话，被截断的 JSON 会在下一步解析时莫名其妙地崩掉。

### 背后的逻辑

为什么长上下文会变慢变贵？因为注意力机制的计算量随序列长度**平方增长**：长度翻倍，计算量变四倍。

各家都有优化手段让实际增长没这么夸张，但根本的趋势不变——**上下文长度是要付出代价的**。

而质量下降的原因更微妙：训练数据里的长文本本来就少，模型在超长上下文上的训练不充分。这是个正在改善但短期内不会消失的问题。

## 步骤 5 · 幻觉：它为什么一本正经地编

### 这一步在做什么

理解幻觉的机制，从而知道什么场景绝不能相信模型。

### 机制

回到步骤 2：模型在做的事是「预测最像答案的下一个 token」。

**它没有「查证」这个动作，也没有「我不知道」这个默认选项。** 当它对某个事实没有可靠记忆时，它依然会生成一个「看起来最像正确答案」的东西。

所以幻觉的典型特征是：**格式完美、细节丰富、语气自信、内容错误**。

### 亲手感受

问这几类问题，看它怎么编：

```
1. 一个不存在的东西：「请介绍一下 2026 年发布的 XYZ-9000 芯片的参数」
2. 一个具体但冷门的事实：「某某论文的第 3 作者是谁」
3. 一个精确数字：「某公司 2025 年第三季度的具体营收数字」
4. 一个 API 的具体用法：「某个库的某个函数有哪些参数」
```

第 4 类对你尤其重要——**模型经常编造不存在的函数和参数**，因为它见过大量相似的 API。

### 什么时候该警惕

| 场景 | 风险 |
|---|---|
| 具体数字、日期、人名 | **高** |
| 引用来源、链接、文献 | **极高**，经常完全编造 |
| 冷门领域的细节 | 高 |
| API 的精确签名 | 高 |
| 通用概念解释 | 低 |
| 文本改写、总结（有原文） | 低 |

### 三种降低幻觉的手段

**一、给它资料（RAG）。** 让它基于你提供的文档回答，而不是靠记忆。这是 S2 的 U2.5。

**二、给它工具。** 让它去查而不是去猜。这是 Agent 的核心价值。

**三、让它能说不知道。** 在 prompt 里明确授权：「如果提供的资料里没有相关信息，直接回答『资料中未提及』，不要推测」。

**第三条经常被忽略，但效果显著。** 因为模型的默认行为是「必须给出一个答案」，你要显式地解除这个压力。

### 可能卡在哪

**给了资料它还是编**

检查两件事：资料是不是真的进了上下文（打印出来看）；有没有明确说「只基于资料回答」。

**它说不知道的次数太多了**

反向问题。约束太强会让它过于保守。需要调整措辞找平衡点，这属于 U1.4 的 prompt 工程。

### 背后的逻辑

有一个说法：**模型没有在「撒谎」，它在「做它被训练要做的事」——生成流畅、合理、符合上下文的文本。**

准确性从来不是它的目标函数，流畅和合理才是。准确性是训练数据质量带来的副产品。

**理解这一点，你就知道为什么 Agent 需要工具**：不是让模型变聪明，是让它别猜。查数据库、调 API、读文档——把「回忆」换成「查证」。

## 步骤 6 · 试试推理模型

### 这一步在做什么

理解「推理模型」和普通模型的区别，知道什么时候值得用。

### 区别是什么

推理模型在给出答案前，会先生成一大段内部思考过程。这段思考通常不返回给你（或者以摘要形式返回），但**你要为它付费**。

代价是：更慢、更贵。收益是：复杂推理任务的准确率明显更高。

### 亲手对比

准备三类任务，各跑 5 次，记录准确率、耗时、成本：

1. **简单任务**：把一段话改写得更简洁
2. **中等任务**：从一段文字里抽取结构化信息
3. **复杂任务**：一道需要多步推理的逻辑题或数学题

**你会发现**：简单任务上推理模型没优势甚至更差（想太多），复杂任务上优势明显。

### 这对你意味着什么

**这是 S4 成本优化的基础**。你的 Agent 里不是所有环节都需要最强的模型：

- 意图分类、格式转换 → 小模型
- 一般对话、工具调用 → 中等模型
- 复杂规划、疑难问题 → 推理模型

把这个「分级」的概念记下来，S4 的 U4.5 会让你真的实现它。

### 背后的逻辑

推理模型的训练方式和普通模型不同，它被专门训练成「在回答前先充分思考」。

从工程角度看，它把「让模型一步步思考」这件事从 prompt 层面移到了模型内部。你不用再写「请一步步推理」，它自己就会。

**代价是你失去了对思考过程的控制**。有些场景你反而希望自己控制推理步骤（比如 S2 的 Plan-and-Execute），那时普通模型加显式的思维链更合适。
