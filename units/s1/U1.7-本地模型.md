# U1.7 · 本地模型（6 小时）

**这个单元解决什么问题**

不是每个任务都值得调云端大模型。有些活（分类、抽取、改写）本地跑一个小模型就够了，而且**免费、无限调用、数据不出本机**。

这个单元让你亲手划出这条界线，而不是听别人说。

**学完你能做到**：本地跑开源模型；用数据说明你的项目里哪些环节可以换成本地模型。

---

## 步骤 1 · 装 Ollama 跑起来

### 这一步在做什么

三条命令跑起一个本地模型。

### 怎么做

```bash
brew install ollama
ollama serve          # 启动服务（或者装 Ollama.app 图形版，它会自动跑）
```

新开一个终端：

```bash
ollama pull qwen3:8b        # 下载模型，几个 GB
ollama run qwen3:8b         # 交互式对话，试几句
```

（模型名以 [ollama.com/library](https://ollama.com/library) 上的为准，中文任务建议选 Qwen 系列。）

看看你有什么：

```bash
ollama list
```

### 可能卡在哪

**下载特别慢**

模型几个 GB，国内下载慢是常态。可以配镜像，或者晚上挂着下。

**内存不够**

一个 8B 模型的 Q4 量化版大约需要 6 到 8 GB 内存。Mac 是统一内存，16GB 的机器跑 8B 没问题，跑 32B 就吃力了。

内存不够时的表现：极慢（在用交换分区）或者直接失败。**换更小的模型或更激进的量化。**

**生成特别慢**

正常。Mac 上 8B 模型大约每秒几十个 token，比云端 API 慢。这是本地模型的固有代价。

### 背后的逻辑

**为什么本地能跑动？** 因为**量化**。

原始模型的参数是 16 位浮点数，一个 8B 模型要 16GB。量化把参数压缩成 4 位或 8 位整数：

| 量化 | 一个 8B 模型 | 质量损失 |
|---|---|---|
| FP16（原始） | ~16 GB | 无 |
| Q8 | ~8.5 GB | 极小 |
| **Q4** | **~4.7 GB** | **可接受，最常用** |
| Q2 | ~3 GB | 明显下降 |

**Q4 是通常的甜点**：体积小四倍，质量损失在大多数任务上感觉不出来。

Ollama 默认拉的就是 Q4 版本。

## 步骤 2 · 接进你的客户端

### 这一步在做什么

让本地模型成为你 `llm_kit` 的第五个提供方，接口完全一致。

### 怎么做

Ollama 提供 OpenAI 兼容接口：

```python
from openai import AsyncOpenAI

client = AsyncOpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama",              # 随便填，本地不校验
)
```

或者直接用 LiteLLM：

```python
await acompletion(model="ollama/qwen3:8b", messages=消息)
```

**在 `models.yaml` 里加一条**：

```yaml
ollama/qwen3:8b:
  提供方: ollama
  上下文窗口: 32768
  输入价格: 0
  输出价格: 0
  支持工具调用: true      # 需要实测确认
  实测生成速度:           # 自己填
```

### 可能卡在哪

**连不上**

确认 `ollama serve` 在跑。`curl http://localhost:11434/api/tags` 能返回模型列表就是通的。

**工具调用不工作**

**不是所有开源模型都支持工具调用**，支持的质量也参差不齐。**这一点必须实测**，不能假设。

**上下文窗口比标称的小**

Ollama 默认可能只开了一部分上下文（为了省内存）。需要在 Modelfile 里调 `num_ctx`，或者创建自定义模型。

### 背后的逻辑

Ollama 本质上是把 llama.cpp 包了一层易用的接口：模型管理、REST API、OpenAI 兼容层。

**它做对的最重要一件事就是那个兼容层**——因为兼容 OpenAI 格式，所有现成的工具链都能直接用，不用为本地模型单独写代码。

**这就是 U1.2 讲的适配器模式的价值**：你的业务代码不知道也不关心底下是云端还是本地。

## 步骤 3 · 做能力边界实验

### 这一步在做什么

**本单元的核心。** 用你自己的任务和数据，测出本地模型的真实能力边界。

### 怎么做

把你在 S1 已经做过的任务，全部在本地模型上重跑一遍：

| 任务 | 来自 | 云端模型 | 本地 8B |
|---|---|---|---|
| 结构化抽取 | U1.3 的 20 篇文本 | /20 | /20 |
| 分类任务 | U1.4 的 20 组测试集 | /20 | /20 |
| 长文本总结 | U1.5 的摘要压缩 | 质量评分 | 质量评分 |
| 工具调用 | 构造 10 个需要调工具的输入 | /10 | /10 |
| 多步推理 | U1.1 的逻辑题 | /10 | /10 |

同时记录速度：

| 模型 | 首 token 延迟 | 生成速度 (token/s) |
|---|---|---|
| 云端 | | |
| 本地 8B | | |
| 本地 3B | | |

### 你大概率会发现的规律

| 任务类型 | 本地小模型 |
|---|---|
| **分类**（选项有限） | **通常够用** |
| **结构化抽取**（字段明确） | **通常够用，但要更详细的 prompt** |
| **改写、翻译、格式转换** | **够用** |
| 多步推理 | 明显不如 |
| 长上下文 | 明显不如 |
| 工具调用 | 参差不齐，要实测 |
| 复杂指令跟随 | 明显不如 |

**规律是：任务越「收敛」（答案空间越小、判断越机械），小模型越够用。**

### 可能卡在哪

**本地模型输出格式很乱**

小模型的指令跟随能力弱。三个应对：

1. **prompt 写得更详细**，给更多例子（U1.4 学的 few-shot 在这里特别有效）
2. 用更强的输出约束（工具调用而非 prompt 描述）
3. 加更多重试（反正免费）

**跑一遍要很久**

本地生成慢，20 个用例可能要几分钟。**不要开并发**——本地模型是计算密集的，并发只会互相抢资源，总时间不变甚至更慢。

（对比一下：云端 API 是 IO 密集，并发有效。**这个区别值得记住。**）

### 背后的逻辑

参数量决定了模型能「记住」多少知识、能做多复杂的推理。8B 和几百 B 的差距是本质的，不是靠 prompt 能弥补的。

**但是**：很多实际任务并不需要那么强的能力。

判断一个任务需不需要大模型，问自己：**这个任务需要世界知识吗？需要多步推理吗？答案空间有多大？**

- 「把这段话分类到这 5 个类别之一」→ 不需要世界知识，答案空间是 5 → 小模型够
- 「分析这份财报并给出投资建议」→ 都需要 → 小模型不够

## 步骤 4 · 得出你的结论

### 这一步在做什么

把实验数据变成一个能落地的决策。

### 输出这张表

针对你的主线项目（U1.8 会定），列出每个环节：

| 环节 | 任务性质 | 本地模型够吗 | 决定 | 预估节省 |
|---|---|---|---|---|
| 意图识别 | 5 分类 | 够（18/20） | **换本地** | 每次省 ¥0.002 |
| 关键词抽取 | 结构化抽取 | 够（19/20） | **换本地** | |
| 检索结果重排 | 相关性判断 | 待测 | 待定 | |
| 最终回答生成 | 开放生成 | 不够（12/20） | 保持云端 | |
| 工具调用决策 | 需要准确 | 不够（13/20） | 保持云端 | |

**「预估节省」这一列**：用 U1.6 的成本数据算，每次任务调用这个环节几次，每次多少钱。

### 隐私维度

除了成本，本地模型还有一个价值：**数据不出本机**。

如果你的项目要处理敏感数据（用户隐私、企业内部文档），某些环节必须本地跑。**在表里加一列「是否涉敏」。**

### 背后的逻辑

这张表就是 S4 的 U4.5「模型路由」的设计文档。

**路由的本质是「按任务难度分配算力」**，就像公司里简单的事交给新人、难的事交给专家。你现在做的是「摸清每个人能干什么」，S4 做的是「建立分配机制」。
