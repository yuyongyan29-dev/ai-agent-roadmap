# U1.9 · 需求发现与规格化（8 小时）

**这个单元解决什么问题**

U1.8 已经选了题、试过数据源。现在要把「帮我自动做周报」这类模糊要求，变成编码 agent 能实现、使用者能验收的规格。你最终交出 `s2-agent/SPEC.md`、五条验收用例和一次演示反馈，S2 按它实现，S3 把这些用例变成评估集。

**工作方式**：agent 整理材料、生成原型，你负责核对事实、决定边界、亲自验收。下面的「门店周报」是教学案例；数据是虚构的，不是用户访谈或业务效果。

| 步骤 | 时间 | 交付物 |
|---|---|---|
| 1. 看一次真实流程 | 2h | 原始记录和当前做法 |
| 2. 拆输入、输出、决策 | 1h | 流程表 |
| 3. 写一页规格与验收 | 2h | `SPEC.md` 和五条用例 |
| 4. 先演一遍，再交给 agent | 2h | 样例输入、原型、验收记录 |
| 5. 给使用者演示并修订 | 1h | 反馈、修改、里程碑说明 |

这里的时间和用例数量是练习预算。访谈约不到人时先做教学案例，真实验证单独保留为未完成，不用模型模拟的赞同代替用户反馈。

## 步骤 1 · 看一次真实流程（2 小时）

### 这一步在做什么

确认使用者到底在哪一步花时间、出错会有什么后果。不要从「要几个 Agent」开始问。

### 怎么做

找一个会实际使用这个功能的人，请他用最近一次任务演示现有做法。自己就是使用者时，拿最近一次真实输入重新走一遍，也记录卡点。

按顺序问这六个问题，把答案记进 `s2-agent/discovery/notes.md`：

1. 上一次什么时候做的？请拿出那次输入和最终交付物。
2. 从打开哪个页面开始？信息从哪几个地方来？
3. 哪一步需要判断？判断错了谁会发现？
4. 哪类信息不能缺？缺了时你现在怎么办？
5. 什么情况下需要找另一个人确认？
6. 怎么知道这次做完了？谁能决定可以交付？

教学案例的原话可以写成：「我每周从工单表、订单导出、巡店记录里整理未解决问题。重复工单会算两次；有人把缺失的订单金额写成 0；我需要看到原始记录才能相信汇总。」把每条标为 `示例`，真实访谈才标为 `已观察`，你的推断标为 `待确认`。

把材料交给 agent：

```text
读取 s2-agent/PROJECT.md 和 discovery/notes.md。
整理“原话/观察 → 当前步骤 → 痛点 → 待确认问题”四列表。
每行保留来源位置，不补写访谈回答，不把我的假设写成事实。
先只整理现状，不选框架，不开始编码。
```

**你验收**：随便挑三行，能回到原始记录；「很低效」「体验不好」都改为具体步骤和后果。记录一次人工完成时间，作为起点，不拿估计时间当实测值。

### 可能卡在哪

**对方只说「都自动化」**：请他演示一个例外，例如字段缺失、来源冲突、处理中撤单。例外往往会暴露真正的判断规则。

**拿不到公司数据**：让对方用脱敏样例演示，保留字段含义和异常形态即可。未经允许的原始资料不要提交进公开仓库。

### 背后的逻辑

用户需要的是完成工作。GOV.UK 的[用户需求方法](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs)强调观察实际做法、区分证据和假设。这里把它落成可追溯的记录，后续每个功能都能找到需求来源。

## 步骤 2 · 拆输入、输出、决策（1 小时）

### 这一步在做什么

明确每一步由确定性代码、模型还是人负责，以及失败时怎么停下来。

### 怎么做

在 `SPEC.md` 起草下面这张表。先照案例填一遍，再换成自己的项目。

| 步骤 | 输入 | 输出 | 执行者 | 失败时怎么办 |
|---|---|---|---|---|
| 获取本周记录 | 门店、时间范围、三个来源 | 带来源 ID 的记录 | 代码 | 某来源不可用就标记不完整 |
| 校验、去重、统计 | 记录和明确的业务规则 | 去重计数、缺失字段表 | 代码 | 缺失金额保持空值，不参与金额合计 |
| 整理问题摘要 | 有效记录及引用 | 按问题归类的草稿 | 模型 | 没有证据的结论删掉或标为待核实 |
| 决定是否交付 | 草稿、异常清单、引用 | 确认或修改意见 | 人 | 有争议的内容返回补查 |
| 交付 | 已确认的草稿 | 本次确认过的版本 | 人在本单元手动完成 | 首版不自动群发或改源数据 |

对每个判断追问：「规则写死是否足够？」精确加总和权限检查不需要模型判断。允许模型决定下一次查什么的地方，才需要进一步考虑 Agent。这个区分对应 Anthropic 的[工作流与 Agent](https://www.anthropic.com/engineering/building-effective-agents)说明；本表是本案例的实现选择，不是所有业务的固定架构。

```text
按现有事实补齐流程表。每步写输入、输出、执行者、结束条件、失败动作。
给两种方案：确定性流程加一次模型摘要；需要模型动态补查的 Agent。
只在材料证明确实需要补查时推荐第二种。列出缺少的证据。
```

**你验收**：从一次输入沿着表走到结束，任何空输入、超时或冲突都有落点；「模型自由处理」不能替代错误处理。

### 可能卡在哪

**一条流程写了十几个功能**：首版只保留完成这次任务必需的输入和一个交付物。U1.8 的三个数据源仍然可以保留，不意味着要同时做三个界面。

### 背后的逻辑

接口名称可以改，输入、输出和失败处理必须先约定。这样工具失败、检索失败、总结失败不会混成一句「AI 不行」。

## 步骤 3 · 写一页规格与验收（2 小时）

### 这一步在做什么

把需求写成别人拿到就能判断对错的协议。

### 怎么做

复制[需求规格模板](../../templates/需求规格模板.md)到 `s2-agent/SPEC.md`。填完后让 agent 审查：

```text
检查 SPEC.md，找出“快速、准确、智能、稳定”这类无法直接判定的词。
逐条改成“给定什么输入，执行什么动作，看到什么结果”。
需要我定阈值的地方列出问题，不替我编业务基线。
为正常、缺失、重复、越权、来源故障各写一条验收用例。
每条关联需求原话的位置和需要保存的证据。
```

教学案例可采用以下五条：

| ID | 给定与操作 | 应观察到的行为 | 保留的证据 |
|---|---|---|---|
| A1 正常 | 三个来源完整，生成门店 A 的草稿 | 只包含该门店；统计与人工核对一致；结论有来源 ID | 输入副本、草稿、人工对照表 |
| A2 缺失 | 一条记录金额为空 | 缺失数增加，金额不被补成 0；草稿说明不完整 | 输入和统计结果 |
| A3 重复 | 同一来源相同 ID 的记录重复一次 | 统计只计一次；重复数量可查 | 去重前后计数 |
| A4 越权 | 门店 A 用户请求门店 B | 在读取 B 的数据之前拒绝，模型上下文无 B 的内容 | 工具调用日志和拒绝结果 |
| A5 来源故障 | 工单来源超时 | 展示失败来源；不会标成“资料完整”；不自动交付 | 故障注入记录和输出 |

业务目标和工程验收分开记。比如「让整理更省时」需要观察人工校对时间；「重复 ID 不重复计数」可以用确定性测试验证。延迟、费用目标写在规格里，值由你和使用者定，不能从教程抄一个数字冒充业务要求。

**你验收**：让另一个人只看 A1–A5，能说出每条何时通过、何时失败。验收用例的写法可参考 GOV.UK 的[用户故事与验收条件](https://www.gov.uk/service-manual/agile-delivery/writing-user-stories)。

### 可能卡在哪

**所有验收都写成「输出看起来合理」**：先验事实、来源、完整性和隔离，再请人判断摘要是否易懂。事实错误不能用文风好来抵消。

### 背后的逻辑

规格与测试在实现之前写，才能挡住「代码已经这样写了，所以就这样验收」的循环。S3 可以直接拿这些输入扩成评估集。

## 步骤 4 · 先演一遍，再交给 agent（2 小时）

### 这一步在做什么

先做出一个不用真实账号和模型也能检验的最小结果，再接真实依赖。这里跑通的是统计约定，不代表整个 Agent 已完成。

### 怎么做

将下面完整代码保存为 `s2-agent/discovery/check_baseline.py`。它是 A2/A3 的教学夹具，只有标准库依赖：

```python
from decimal import Decimal

rows = [
    {"source": "orders", "id": "a1", "store": "A", "amount": "100.00"},
    {"source": "orders", "id": "a1", "store": "A", "amount": "100.00"},
    {"source": "orders", "id": "a2", "store": "A", "amount": None},
    {"source": "orders", "id": "b1", "store": "B", "amount": "900.00"},
]
seen = set()
total = Decimal("0.00")
missing = duplicates = 0
for row in rows:
    if row["store"] != "A":
        continue
    key = (row["source"], row["id"])
    if key in seen:
        duplicates += 1
        continue
    seen.add(key)
    if row["amount"] is None:
        missing += 1
    else:
        total += Decimal(row["amount"])
assert (len(seen), duplicates, missing, total) == (2, 1, 1, Decimal("100.00"))
print(f"unique={len(seen)} duplicates={duplicates} missing={missing} total={total}")
```

从仓库根目录运行：

```bash
python3 s2-agent/discovery/check_baseline.py
```

你应该看到（此固定夹具已本地运行核对）：

```text
unique=2 duplicates=1 missing=1 total=100.00
```

这段过滤代码不是服务端认证。真实 A4 必须由可信的用户身份确定门店权限，并在数据读取前执行。金额冲突、退款、重复记录版本的规则也需要另行确认，不能由这个夹具推断。

接着把需求交给 coding agent：

```text
以 SPEC.md 的 A1–A5 为验收基准，在 s2-agent/discovery/prototype/ 做离线原型。
用脱敏样例和 fake 三个来源，模型先用固定回复，只生成本地草稿文件。
先说明哪些规则已有确定答案、哪些仍需我决定。
把正常/缺失/重复/越权/超时各做成独立运行案例，给运行命令和输出路径。
不能依靠 prompt 执行访问控制；不能修改验收预期来迎合实现。
完成后给我 diff、命令、未实现项；真实模型和 SaaS 接入留给后续单元。
```

**你验收**：亲自运行五种输入，记录通过/失败及文件路径。然后自己改一条金额、增加一条重复记录，确认结果跟着变化。让使用者看草稿格式，而不是看终端滚动日志。

### 可能卡在哪

**代码通过了，人却说结果没用**：回到原话找遗漏的交付规则，比如他要的是待办清单，你给了流水账。先改规格和预期，再改代码。

### 背后的逻辑

fake 能验证确定性边界和展示形式，不能证明真实模型会正确归纳、外部 API 会稳定响应。分别记录这两类验证，后续接入时才知道还要补什么。

## 步骤 5 · 给使用者演示并修订（1 小时）

### 这一步在做什么

检查你理解的任务和使用者理解的任务是不是同一个。

### 怎么做

安排一次 15 分钟演示：前 5 分钟请对方输入一条正常案例和一条异常案例，接着请他复述结果能用来做什么，最后确认不符合预期的地方。是否录音先征得同意，不录音也可以逐项记笔记。

将反馈分三列写进 `discovery/feedback.md`：他说的原话、规格哪里要改、改后用哪条用例验收。agent 帮你修文案和原型，你重新跑受影响的案例。

复制[里程碑对外说明模板](../../templates/里程碑对外说明模板.md)。用一页普通话说明能做什么、还不能做什么、怎么试、希望对方判断什么。从 M2 起沿用，不向业务读者堆框架名和指标缩写。

**你验收**：对方可以复述「什么时候能相信结果、什么时候要补查」；至少一条实际反馈已体现在规格或明确不做的范围里。无人参与时记录待验证项，不填假反馈。

### 可能卡在哪

**演示变成了技术讲座**：只保留一次输入、一个结果、一个失败例子。需要解释数据库和模型协议才能使用，说明演示对象或产品表达需要调整。

### 背后的逻辑

能让非技术使用者判断结果，是交付能力的一部分。`PROJECT.md` 解释为什么选题，`SPEC.md` 约定首版做到哪里，`TECH.md` 说明用什么实现，三份文件各有用途。

## 完成判据

- [ ] 有带来源的现状记录；已观察、教学示例、待确认假设明确区分
- [ ] `SPEC.md` 写明价值、输入输出、成功指标、失败动作、明确不做的范围
- [ ] 流程中的代码、模型、人工职责明确，没有靠模型自由决定的权限边界
- [ ] 五条验收用例都有固定输入、判定标准、证据路径，离线原型亲自跑过
- [ ] 实际演示反馈已记录并处理；没有真实参与者就保留此项未勾选
- [ ] 更新 `PROJECT.md` / `TECH.md` 中受影响的决定，链接到规格
- [ ] 有一页使用者看得懂的交付说明，之后可复用到 M2–M6

**你必须能回答**：一句「自动做周报」里最容易误解的规则是什么？哪个判断无需模型？来源缺失与确实没有记录怎么区分？你亲自改过的验收输入是什么，结果如何变化？
