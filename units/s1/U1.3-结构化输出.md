# U1.3 · 结构化输出（8 小时）

**这个单元解决什么问题**

**这是从「聊天机器人」到「Agent」的第一道分水岭。**

聊天机器人返回文字给人看。Agent 需要返回**程序能直接用的数据**——因为下一步要拿这个数据去调工具、去查数据库、去做判断。

模型天生输出的是自由文本。这个单元教你怎么让它稳定地输出符合你定义的结构。

**学完你能做到**：让模型 100% 返回合法的结构化数据，失败时能自动修复。

## 步骤 1 · 先看看不做约束会怎样

### 这一步在做什么

亲手体验一下问题，这样你才知道后面每个手段在解决什么。

### 怎么做

```python
prompt = """
从下面的文字里抽取信息，返回 JSON，包含 title、likes、tags 三个字段。

文字：这篇《冬季家电选购指南》发布三天就有 1.2k 赞，标签是 家电、选购、冬季。
"""

# 同一个 prompt 跑 20 次：模型输出有随机性，单次成功说明不了任何问题，
# 只有重复采样才能看出真实失败率和失败的花样
success_count = 0
for _ in range(20):
    text = await llm.chat(prompt)
    try:
        # 不做任何清洗，直接解析——这里就是要暴露原始输出有多不可靠
        json.loads(text)
        success_count += 1
    except json.JSONDecodeError:
        # 只截前 200 字符：失败原因基本都在开头（markdown 包裹、寒暄前缀）
        print("失败样例：", repr(text[:200]))
print(f"{success_count}/20 成功")
```

### 你会看到的失败模式

把每一种都记进笔记：

| 失败模式 | 长什么样 |
|---|---|
| **markdown 包裹** | ` ```json\n{...}\n``` ` |
| **前后加话** | `好的，这是提取的结果：{...}希望对你有帮助！` |
| **数字变字符串** | `"likes": "1.2k"` 而不是 `1200` |
| **字段名不对** | 用了 `title_name` 而不是 `title` |
| **多余字段** | 自己加了 `summary` |
| **嵌套结构乱了** | tags 变成了字符串而不是数组 |
| **中文引号** | 用了「」或者全角引号 |

**这些不是模型笨，是你没给约束。** 接下来三步就是逐个解决。

## 步骤 2 · 三种约束方式对比

### 这一步在做什么

理解三种做法的可靠性差异，知道该用哪个。

### 方式一：prompt 里描述格式（最弱）

```python
# 全部约束都写在自然语言里：给一个「样例结构」比抽象描述有效，
# 但模型是否遵守完全靠自觉，没有任何机制保证
prompt = """
返回 JSON，格式如下，不要任何其他内容，不要 markdown 代码块：
{"title": "字符串", "likes": 整数, "tags": ["字符串"]}
"""
```

**可靠性：低。** 靠模型自觉，各家表现差异大。但胜在任何模型都支持。

### 方式二：JSON mode（中等）

```python
# 服务端接管「输出必须是合法 JSON」这件事，模型不再可能吐出 markdown 包裹或寒暄前缀；
# 但它只保证能被 parse，字段名、字段类型仍然可能是错的
response = await llm.chat(
    messages,
    response_format={"type": "json_object"},
)
```

服务端保证返回的是**合法 JSON**，但**不保证符合你的 schema**。字段名、类型还是可能错。

**注意**：用 JSON mode 时，prompt 里通常必须包含 "JSON" 这个词，否则某些模型会报错。

### 方式三：工具调用 / 结构化输出（最强）

把你要的结构定义成一个「工具」的参数，让模型「调用」它：

```python
# 这里其实没有真的要「保存」任何东西：工具只是承载 schema 的壳子，
# 目的是让模型走参数生成这条路径，而不是自由写文本
save_note_info_tool = {
    "type": "function",
    "function": {
        "name": "save_note_info",
        "description": "把抽取到的笔记信息保存下来",
        "parameters": {
            "type": "object",
            "properties": {
                # description 会随 schema 一起发给模型，等于贴在字段旁边的指令
                "title": {"type": "string", "description": "笔记标题"},
                "likes": {"type": "integer", "description": "点赞数，转成整数"},
                "tags": {"type": "array", "items": {"type": "string"}},
            },
            # required 缺一不可，additionalProperties 禁止模型自己加字段
            "required": ["title", "likes", "tags"],
            "additionalProperties": False,
        },
    },
}

response = await client.chat.completions.create(
    model=model_name,
    messages=messages,
    tools=[save_note_info_tool],
    # 不给模型「要不要调用」的选择权：指名这个函数，它只能生成参数
    tool_choice={"type": "function", "function": {"name": "save_note_info"}},
)
# 结果不在 message.content 里，而在 tool_calls 的 arguments 中，且是 JSON 字符串
arguments = json.loads(response.choices[0].message.tool_calls[0].function.arguments)
```

**可靠性：高。** 很多模型服务端会用受约束的解码（constrained decoding）保证输出严格符合 schema。

**这也是你 S2 定义 Agent 工具的同一套机制。** 现在学的东西直接复用。

### 做对比实验

三种方式各跑 30 次，记录：

| 方式 | 合法 JSON | 符合 schema | 字段类型正确 |
|---|---|---|---|
| prompt 描述 | /30 | /30 | /30 |
| JSON mode | /30 | /30 | /30 |
| 工具调用 | /30 | /30 | /30 |

### 可能卡在哪

**某些模型不支持 JSON mode 或工具调用**

查你的 `models.yaml`（U1.2 建的那张表）。不支持的就只能用方式一，然后加强解析和重试。

**`additionalProperties: False` 报错**

不是所有模型都支持这个约束。去掉它，改成在解析时用 Pydantic 过滤多余字段。

**强制调用工具后模型不说话了**

对，`tool_choice` 强制之后它只会输出工具调用，不会有文本。这正是你要的。

### 背后的逻辑

**为什么工具调用比 prompt 描述可靠得多？**

因为它不只是「告诉模型要什么」，很多实现里服务端会在**生成过程中**限制候选 token——生成到 `"likes":` 之后，只允许数字相关的 token 出现。

这叫**受约束解码**。它从机制上排除了不合法的输出，而不是靠模型「记得」你的要求。

## 步骤 3 · 用 Pydantic 定义并校验

### 这一步在做什么

把 U0.4 学的 Pydantic 用起来，让 schema 定义和校验用同一份代码。

### 怎么做

```python
from pydantic import BaseModel, Field, field_validator

class NoteInfo(BaseModel):
    """一篇笔记抽取出的结构化信息。这个类同时充当发给模型的 schema 和解析后的校验器。"""

    title: str = Field(description="笔记标题")
    # ge=0 是 JSON schema 表达得了的约束，会一起发给模型
    likes: int = Field(ge=0, description="点赞数，转成整数。1.2k 应转为 1200")
    # 用 default_factory 而不是 default=[]，避免所有实例共享同一个列表对象
    tags: list[str] = Field(default_factory=list, description="标签列表")

    @field_validator("title")
    @classmethod
    def strip_title(cls, v: str) -> str:
        # 模型常把标题连着书名号和空格一起带出来；空白标题在 schema 层面是合法的 str，
        # 只能在这里拦下来
        v = v.strip()
        if not v:
            raise ValueError("标题不能为空")
        return v
```

**从 Pydantic 模型自动生成 JSON schema**：

```python
schema = NoteInfo.model_json_schema()
```

**解析和校验一步到位**：

```python
result = NoteInfo.model_validate_json(raw_text)
```

**关键点：`Field(description=...)` 里的描述会进入 schema，模型能看到。** 所以把「1.2k 应转为 1200」这种指令写在这里，比写在 prompt 里更有效——它离字段更近。

### 可能卡在哪

**Pydantic 报 `ValidationError` 但我看不出哪错了**

错误信息的格式是「字段路径 + 什么问题 + 你传的是什么」。从第二行开始读。

**模型返回的 JSON 外面包了 markdown**

先剥壳再解析：

```python
import re

def strip_code_fence(text: str) -> str:
    """把模型输出里的 markdown 包裹和前后废话剥掉，只留 JSON 本体。"""
    text = text.strip()
    # 第一优先：匹配 markdown 代码块，DOTALL 让 . 能跨行吃下整段 JSON
    m = re.search(r"```(?:json)?\s*\n(.*?)\n```", text, re.DOTALL)
    if m:
        return m.group(1).strip()
    # 兜底：没有代码块但前后有寒暄时，取第一个 { 到最后一个 }。
    # 用 rfind 而不是 find，是为了保住嵌套对象最外层的右括号
    i, j = text.find("{"), text.rfind("}")
    if i != -1 and j != -1:
        return text[i:j+1]
    # 实在找不到就原样返回，让后面的 json.loads 去报错，不要在这里吞掉问题
    return text
```

**用了工具调用还需要 Pydantic 吗**

需要。理由有两个：一是不是所有模型的约束都严格；二是**Pydantic 还能做业务校验**（点赞数不能为负、标签不能超过 10 个），这些 JSON schema 表达不了。

### 背后的逻辑

**一份定义，三处使用**：

1. 给模型看的 JSON schema（`model_json_schema()`）
2. 解析和校验（`model_validate_json()`）
3. 你代码里的类型提示

这就是 U0.6 学 FastAPI 时那个「声明式」思想的同一个体现。**定义写一次，永远不会不同步。**

## 步骤 4 · 解析失败时自动修复

### 这一步在做什么

**这一步是本单元的核心。** 前面三步降低了失败率，但降不到零。这一步处理剩下的。

### 核心思路

失败了不要直接放弃，**把错误信息告诉模型让它重试**。模型看到「你少了 likes 字段」通常能一次改对。

### 怎么做

```python
from pydantic import BaseModel, ValidationError

async def structured_call[T: BaseModel](
    llm,
    messages: list,
    model_class: type[T],
    max_retries: int = 3,
) -> T:
    """调用模型并返回一个已通过校验的 model_class 实例；失败时带着错误信息重试。

    泛型写成 [T: BaseModel] 是为了让调用方拿到的返回值有准确类型，
    而不是一个笼统的 BaseModel。
    """
    # 复制一份，不要污染调用方传进来的 messages——重试会往里追加内容
    history = list(messages)

    for attempt in range(max_retries):
        response = await llm.chat(history, tools=[build_tool_from_model(model_class)])
        raw = extract_tool_arguments(response)

        try:
            return model_class.model_validate_json(raw)
        except ValidationError as e:
            # 最后一次仍然失败就把异常抛出去，不要静默返回 None 让上游猜
            if attempt == max_retries - 1:
                raise

            # 重试次数是诊断信号：重试率高说明 schema 有问题，所以要留痕
            logger.warning("第 %d 次解析失败：%s", attempt + 1, e)

            # 关键：把「它输出了什么」和「错在哪」一起放回对话。
            # 模型看不到自己上一轮的错误，不喂回去它只会原样再错一遍
            history.append({"role": "assistant", "content": raw})
            history.append({
                "role": "user",
                "content": (
                    f"你的输出不符合要求，校验错误如下：\n{e}\n"
                    f"请重新输出，严格符合 schema。只输出修正后的结果。"
                ),
            })
```

### 关键设计点

**一、把具体错误告诉它，不要只说「格式错了」。** Pydantic 的错误信息已经很精确（哪个字段、什么问题），直接贴过去。

**二、把失败的输出也放进历史。** 模型要看到自己输出了什么才知道怎么改。

**三、必须有最大次数。** 否则遇到根本满足不了的要求会无限循环烧钱。

**四、记录重试次数。** 如果某个 schema 经常需要重试，说明它的设计有问题（描述不清、要求太复杂），该改的是 schema 不是重试逻辑。

### 可能卡在哪

**重试之后还是错**

大概率是 schema 设计问题。检查：

- 字段描述是不是清楚
- 有没有互相矛盾的约束
- 是不是嵌套太深（超过 3 层就该考虑拆开）
- 必填字段是不是真的都能从输入里得到

**重试把成本翻倍了**

统计一下重试率。如果超过 10%，说明前置约束不够，回去改 schema 或换更强的模型。

**有个字段模型总是填错**

在 `Field(description=...)` 里给一个例子。「点赞数，转成整数。例如输入 1.2k 应返回 1200」比「点赞数」有效得多。

### 背后的逻辑

这个模式叫「**校验驱动的自我修复**」，是 Agent 设计里的一个基础模式。

它的一般形式是：**执行 → 校验 → 失败时把校验错误回喂 → 重试**。

你在 S2 会反复见到它的变体：

- 工具调用参数错了 → 把错误返回给模型 → 它重新调用
- 生成的代码跑不通 → 把报错贴回去 → 它修
- 输出不符合要求 → 让另一个模型评价 → 带着评价重做

**核心洞察是：模型看不到自己的错误，所以你要把错误明确地喂回去。** 这比在 prompt 里预防所有可能的错误有效得多，也简单得多。

## 步骤 5 · 试试 instructor

### 这一步在做什么

看看别人怎么封装上面这套，学习它的设计。

### 怎么做

```bash
uv add instructor
```

```python
import instructor
from openai import AsyncOpenAI

# from_openai 是在原客户端外面套一层，接口保持不变，只是多认 response_model
client = instructor.from_openai(AsyncOpenAI())

result = await client.chat.completions.create(
    model="gpt-5",
    messages=[{"role": "user", "content": text}],
    response_model=NoteInfo,          # 直接给 Pydantic 模型，schema 由它自动生成并注入
    max_retries=3,                    # 内部就是上一步那套「校验失败 → 回喂错误 → 重试」
)
# result 已经是 NoteInfo 的实例，不用再自己 json.loads 加 model_validate
```

**读它的源码**，看它是怎么做的：生成 schema、注入 prompt、解析、校验、重试。

### 为什么要自己实现一遍再看它

因为你现在能看懂它每一步在干什么，而且知道它做了哪些你没想到的处理。**这比直接用一个黑盒有价值得多。**

### 用不用它

小项目直接用它省事。但**如果你要做成本统计、trace 埋点、自定义重试策略**，自己那套更灵活。

**建议**：自己的 `llm_kit` 里保留自己的实现，因为 S3 要往里加 trace。
