# U1.4 · Prompt 工程（8 小时）

**这个单元解决什么问题**

你会写很多版 prompt。问题是：**你怎么知道新版比旧版好？**

大多数人靠感觉：「嗯，这版读起来顺一点」。然后上线，然后出问题，然后再改，再靠感觉。

这个单元教你用数据说话。**顺带，你会在这里第一次做「评估」**——S3 整个阶段就是把这件事做到工程级。

**学完你能做到**：用一张表证明 A 版比 B 版好；prompt 进 git 走版本管理。

---

## 步骤 1 · 先建测试集（在写 prompt 之前）

### 这一步在做什么

**顺序很重要：先定义什么是「好」，再去优化。**

反过来做的话，你会不自觉地把 prompt 调成「在我随手试的那几个例子上表现好」，而那几个例子根本不能代表真实情况。

### 怎么做

挑一个你项目里真实的任务。准备 20 组数据，每组包含：

```yaml
- id: T001
  输入: |
    （真实的输入文本）
  期望:
    描述: 应该识别出这是投诉类，情绪负面，涉及物流
    必须包含: [投诉, 物流]
    不能包含: [推荐, 购买]
  标签: [核心路径]

- id: T002
  输入: |
    （一个边界情况：信息不全）
  期望:
    描述: 信息不足时应该说明缺什么，而不是猜
    必须包含: [信息不足]
  标签: [边界]
```

**20 组的构成建议**：

| 类型 | 数量 | 说明 |
|---|---|---|
| 典型情况 | 10 | 最常见的输入 |
| 边界情况 | 5 | 信息不全、格式异常、超长超短 |
| **不该做的** | 5 | **测试它会不会做不该做的事** |

**最后那 5 条最容易被忽略也最重要。** 只测正例的话，你会把 prompt 优化成「什么都敢答」。

### 可能卡在哪

**期望输出怎么写**

不要求逐字匹配。写「判断标准」——包含什么、不包含什么、结构是什么、语气是什么。

**判断标准的检验方法**：**隔一天你自己再判一遍，结论应该一样。** 如果你自己都拿不准，说明标准写得不清楚。

**20 组太少了吧**

对早期够用。改动大的时候，20 组就能看出明显差异。等你能稳定通过 20 组了，再扩到 50 组。**S3 会告诉你为什么这个数量级是合理的。**

### 背后的逻辑

这一步的本质是**把「好」从主观感觉变成可检验的标准**。

在没有测试集的情况下，「这版更好」是一句无法反驳也无法证实的话。有了测试集，它变成「这版通过 17 条，那版通过 13 条」。

**这个转变是整个工程化的起点。** S3 会把它扩展成完整的评估体系，但核心思想在这里就已经完整了。

## 步骤 2 · 基本手法

### 这一步在做什么

学会五个基本手法，每个都在你的测试集上实测效果。

### 手法一：明确角色和任务

```
弱：分析下面的文字。

强：你是一个电商客服质检员。阅读下面的客服对话，判断客服的回复是否
符合规范。规范包括：三分钟内首次响应、不承诺无法兑现的时效、
涉及退款必须引导到售后流程。
```

**关键不是「你是一个专家」这种套话，而是把任务的具体标准写清楚。**

### 手法二：给例子（few-shot）

```
输入：这个快递也太慢了吧，等了一周
输出：{"类型": "投诉", "情绪": "负面", "涉及": ["物流"]}

输入：请问什么时候有货
输出：{"类型": "咨询", "情绪": "中性", "涉及": ["库存"]}

现在处理：
输入：{实际输入}
```

**例子比描述有效得多。** 尤其是对格式和风格的要求，说十句不如给一个例子。

**建议 2 到 5 个例子。** 太多会占上下文，而且边际收益递减。**要覆盖不同的情况**，不要给 5 个一模一样的。

### 手法三：要求分步

```
请按以下步骤处理：
1. 先列出文字里提到的所有事实
2. 判断每个事实属于哪个类别
3. 综合给出最终分类
最后用 JSON 输出结论。
```

复杂任务上效果明显（回想 U1.1 的自回归原理）。简单任务上反而是浪费 token。

### 手法四：明确输出格式

见 U1.3，用工具调用或 schema 最可靠。纯 prompt 的话，给一个完整的例子比描述格式好。

### 手法五：明确边界

```
如果提供的信息不足以做出判断，返回 {"类型": "信息不足", "缺少": ["具体缺什么"]}，
不要推测。
```

**这条经常被忽略。** 模型的默认行为是「必须给出答案」，你要显式地授权它说「不知道」。

### 一个反直觉的点：负面指令经常失效

```
弱：不要输出 markdown 代码块。
强：输出的第一个字符必须是 {，最后一个字符必须是 }。
```

```
弱：不要太长。
强：不超过 3 句话。
```

**规律是：把「不要做 X」改写成「要做 Y」。** 因为「不要想大象」这句话本身就让你想到了大象。

**自己验证一下这条**：同一个要求写成正反两种形式，各跑 20 次，统计违反率。**把数据记进笔记**，这是你自己得出的结论，比记住一条规则有价值。

### 可能卡在哪

**加了一堆要求，模型只遵守了一部分**

要求太多会互相稀释。三个解法：

1. **减少要求**，只留最重要的三五条
2. **把要求分层**：最关键的放最前面和最后面（回想 U1.1 的位置效应）
3. **拆成两次调用**，第一次生成，第二次检查修正

**prompt 越写越长，效果反而下降**

这是常见现象。**定期做减法**：删掉一条要求，跑测试集，如果分数不掉就永久删掉。

### 背后的逻辑

**prompt 工程的本质是「减少歧义」。**

模型的每一次生成都是在无数种可能里选一条路。你的 prompt 每增加一个明确的约束，就砍掉一批错误的路径。

所以有效的 prompt 不是「写得好听」，而是「把判断标准写清楚，把边界划明白」。

**一个实用的检验方法**：把你的 prompt 给一个不了解这个任务的人看，问他能不能照着做。**人做不到的事，模型也做不到。**

## 步骤 3 · 写 5 个版本并对比

### 这一步在做什么

这是本单元的核心动作。

### 怎么做

对同一个任务，写 5 个版本：

| 版本 | 特点 |
|---|---|
| v1 | 最朴素的一句话描述 |
| v2 | v1 + 明确角色和判断标准 |
| v3 | v2 + 3 个例子 |
| v4 | v3 + 要求分步 |
| v5 | 你觉得最好的组合（可能是 v3 去掉某些东西） |

**每次只改一个变量。** 如果你一次改三处，分数变了你不知道是哪处起的作用。

**写一个跑分脚本**：

```python
async def 跑一版(prompt模板: str, 测试集: list) -> dict:
    结果 = []
    for 用例 in 测试集:
        回复 = await llm.对话(prompt模板.format(输入=用例["输入"]))
        通过 = 判断(回复, 用例["期望"])
        结果.append({
            "id": 用例["id"],
            "通过": 通过,
            "输出": 回复.文本,
            "token": 回复.用量.输出token,
        })
    return {
        "通过率": sum(r["通过"] for r in 结果) / len(结果),
        "平均token": sum(r["token"] for r in 结果) / len(结果),
        "失败项": [r["id"] for r in 结果 if not r["通过"]],
    }
```

**判断函数怎么写**：先用规则（包含某词、符合 schema、长度范围）。规则判不了的，你先人工判 —— U3.4 才会学 LLM 打分。

### 输出这张表

| 版本 | 通过 | 平均输出 token | 平均耗时 | 失败的是哪几条 |
|---|---|---|---|---|
| v1 | 11/20 | 180 | 2.1s | T003 T007 T011 ... |
| v2 | 14/20 | 165 | 2.0s | T007 T011 ... |
| v3 | 17/20 | 150 | 2.3s | T011 T019 |
| v4 | 17/20 | 320 | 4.1s | T011 T019 |
| v5 | 18/20 | 155 | 2.2s | T011 |

**「失败的是哪几条」这一列是最有价值的。** 它告诉你哪些用例是硬骨头——如果某条题在所有版本上都失败，可能是题目本身有问题，或者需要换个思路而不是改 prompt。

上面这张表还能读出：v4 加了分步之后通过率没提升，但 token 翻倍、耗时翻倍。**这就是一个明确的「不值得」的结论。**

### 可能卡在哪

**每次跑分结果都不一样**

设 `temperature=0`（虽然不保证完全一致，但方差小很多），并且每个用例跑 3 次取多数。

**跑一次要好几分钟**

用 U1.2 学的并发。20 个用例并发 5 个，几十秒就完了。

**分数没有明显差异**

可能是测试集太简单（都通过了）或太难（都失败了）。**调整测试集的难度**，让它落在有区分度的区间。

### 背后的逻辑

**这就是 A/B 测试的思路**，只是被试对象是 prompt。

关键的方法论原则有三条，S3 会全部展开：

1. **控制变量**：一次只改一处
2. **样本量要够**：3 条数据的差异说明不了任何问题
3. **看失败细节，不只看总分**：总分一样的两个版本，失败的可能是完全不同的用例

## 步骤 4 · prompt 版本管理

### 这一步在做什么

把 prompt 从代码里抽出来，当成正式的资产管理。

### 为什么必须做

| 问题 | 后果 |
|---|---|
| prompt 写死在代码里 | 改一句话要发一次版 |
| 没有版本号 | 线上出问题不知道用的是哪版 |
| 不走 review | 改坏了没人发现 |
| 没有 diff | 不知道这次改了什么 |

**「prompt 是第一等公民」是 12-Factor Agents 里的一条原则**，S4 会完整学。现在先建立习惯。

### 怎么做

```
s1-llm/prompts/
├── 分类/
│   ├── v1.md
│   ├── v2.md
│   ├── v3.md
│   └── current -> v3.md      # 软链接指向当前使用的版本
└── README.md                 # 记录每版的变更和分数
```

每个 prompt 文件带元信息：

```markdown
---
版本: v3
创建: 2026-10-05
基于: v2
变更: 增加 3 个 few-shot 例子
测试集: eval/classify_v1.yaml
通过率: 17/20
平均token: 150
---

你是一个电商客服质检员。
...
```

代码里这样加载：

```python
from pathlib import Path

def 载入prompt(名字: str, 版本: str = "current") -> str:
    路径 = Path(__file__).parent / "prompts" / 名字 / f"{版本}.md"
    内容 = 路径.read_text(encoding="utf-8")
    # 去掉 frontmatter
    if 内容.startswith("---"):
        内容 = 内容.split("---", 2)[2].strip()
    return 内容
```

**并且把版本号记进日志**，S3 接 trace 时会用到：

```python
logger.info("使用 prompt %s@%s", 名字, 实际版本)
```

### 可能卡在哪

**软链接在 Windows 上有问题**

用一个 `config.yaml` 记录当前版本，而不是软链接：

```yaml
prompts:
  分类: v3
  抽取: v2
```

**prompt 里要插变量怎么办**

用 Python 的 `str.format()` 或者简单的模板引擎。**注意 prompt 里的花括号要转义**（JSON 例子里全是花括号）：

```python
模板.format(输入=x)          # prompt 里的 {} 会被当成占位符！
```

安全的做法是用不容易冲突的占位符，比如 `{{输入}}`，自己写一个简单替换。

### 背后的逻辑

把 prompt 当代码管理，带来的是**可追溯性**：

- 线上出了问题 → 查 trace → 看到用的是 v3 → 找到 v3 的文件 → 看 git 记录知道是谁什么时候为什么改的
- 想回退 → 改一个配置就行，不用发版
- 想 A/B → 同时跑 v3 和 v4，看数据

**这条链路在 S3 和 S4 会完整打通。** 现在打好基础。

## 步骤 5 · 跨模型验证

### 这一步在做什么

验证一个重要事实：**prompt 不是通用的。**

### 怎么做

把你的 v5 在三个不同的模型上跑同一个测试集：

| 模型 | 通过率 | 平均 token | 成本 |
|---|---|---|---|
| 强模型 | | | |
| 中等模型 | | | |
| 小模型 | | | |

**你会发现**：为强模型优化的 prompt，在小模型上可能表现很差；反过来，给小模型写的详细指令，在强模型上可能显得啰嗦、反而干扰。

### 这对你意味着什么

**换模型时必须重新跑评估。** 不能假设「这个 prompt 在 A 模型上好，换到 B 模型也好」。

这一点在 S4 做成本优化时会变得很现实——你想把某个环节换成便宜模型，就必须验证 prompt 在新模型上还能不能用，可能要为它单独写一版。

### 背后的逻辑

不同模型的训练数据、对齐方式、指令跟随能力都不同。它们对同一段文字的「理解」不完全一样。

**实践建议**：在你的 prompt 目录结构里预留模型维度：

```
prompts/分类/
├── v3.md              # 默认
├── v3-small.md        # 给小模型的版本，指令更详细
└── README.md
```

**动手部分**

- [ ] 5 个版本的 prompt，每版只改一个变量
- [ ] **完整的对比表**：通过率、平均 token、平均耗时、失败的具体条目
- [ ] 正反指令的对比实验数据（「不要 X」vs「要 Y」）
- [ ] prompt 全部放进 `prompts/` 目录，带版本号和元信息
- [ ] 代码里通过版本号加载 prompt，日志里记录用了哪版
- [ ] 跨三个模型的验证数据

**关键产出**：一段结论，说明你最终选哪版、**好在哪（用数字）、代价是什么**。

「v5 通过 18/20，比 v1 的 11/20 提升明显。主要来自 few-shot 例子。加分步推理（v4）没有提升通过率，但 token 翻倍，所以放弃。剩下的失败项 T011 是因为……」

**这段话就是你面试时讲 prompt 工程的素材。** 不能只说「效果更好」。
