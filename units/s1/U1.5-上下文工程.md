# U1.5 · 上下文工程（10 小时）

**这个单元解决什么问题**

**这是 2025 年之后 Agent 工程最核心的技能。**

Prompt 工程关注「怎么把这一句话说清楚」。上下文工程关注一个更大的问题：**在模型有限的注意力预算里，哪些信息值得占位置？**

一个 Agent 跑到第 15 轮时，它的上下文里有：系统提示、20 个工具的定义、前 14 轮的对话、5 篇检索到的文档、3 次失败的工具返回。**这些全塞进去，模型会被淹没。** 你要决定留什么、扔什么、压缩什么。

**必读**：Anthropic《[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)》（2025-09-29）。**精读两遍，做笔记。** 本单元的方法建立在它之上。

**学完你能做到**：用数据说明三种压缩策略各自的代价和收益；知道什么信息该在什么时候进上下文。

## 步骤 1 · 看清你的上下文里到底有什么

### 这一步在做什么

大多数人从没量化过自己的上下文构成。**这一步会给你一个意外的发现。**

### 怎么做

写一个分析函数，把一次真实调用的上下文拆开统计：

```python
import json
import tiktoken

# 固定用同一个分词器做相对比较：换个模型算出来的绝对值会变，
# 但「哪一块占大头」这个结论不会变
enc = tiktoken.get_encoding("o200k_base")


def count_tokens(text: str) -> int:
    return len(enc.encode(text))


def analyze_context(system_prompt, tool_defs, history, retrieval, current_input):
    """把一次真实调用的上下文按来源拆开，统计每部分吃掉多少 token。"""
    parts = {
        "system_prompt": count_tokens(system_prompt),
        # 工具定义要把整个 tools 参数序列化后再数：
        # 工具名、描述、每个参数的类型和描述都真实占位，这样才接近实际开销
        "tool_defs": count_tokens(json.dumps(tool_defs, ensure_ascii=False)),
        "history": sum(count_tokens(m["content"]) for m in history),
        "retrieval": count_tokens(retrieval),
        "current_input": count_tokens(current_input),
    }
    total = sum(parts.values())
    # 按占比从大到小排，最该动刀的那一块自然排在第一行
    for name, n in sorted(parts.items(), key=lambda x: -x[1]):
        print(f"{name:14s} {n:6d} tokens  {n / total * 100:5.1f}%")
    print(f"{'total':14s} {total:6d} tokens")
```

在你的 U1.3 抽取任务上跑一遍。如果你还没有多轮场景，构造一个：10 轮对话 + 10 个工具定义 + 3 篇文档。

### 你大概率会发现

| 项目 | 典型占比 | 说明 |
|---|---|---|
| **工具定义** | **可能 20% 到 40%** | **这是最容易被低估的一块** |
| 历史消息 | 随轮数增长 | 第 20 轮时通常是最大的一块 |
| 检索结果 | 20% 到 50% | 取决于你召回多少 |
| 系统提示 | 5% 到 15% | |
| 当前输入 | 通常很小 | |

**工具定义的占比是本步骤最大的收获。** 每个工具的名字、描述、每个参数的类型和描述，都要占 token。20 个工具轻松占掉几千 token，而且**每一轮都要重发**。

**这直接推出 S2 的一个设计原则**：工具不是越多越好，超过 15 到 20 个就要考虑分组或动态加载。

### 可能卡在哪

**不同模型算出来的数不一样**

正常，分词器不同。用一个固定的分词器做相对比较就行，不用追求绝对精确。

**工具定义怎么统计**

把你要传给 API 的 `tools` 参数整个序列化成 JSON 再数。这接近实际占用。

### 背后的逻辑

**为什么每轮都要重发全部上下文？**

回到 U0.5 学的：HTTP 是无状态的。服务器不记得你上次发了什么。

所以第 20 轮对话时，你实际上在重发前 19 轮的全部内容。**成本随轮数呈平方级增长**（每轮的上下文线性增长，累计就是平方）。

理解这一点，你就理解了为什么上下文管理是成本控制的核心。

## 步骤 2 · 亲手验证长上下文的衰减

### 这一步在做什么

用数据确认「上下文越长质量越差」这件事，并找到你的实际拐点。

### 设计实验

**实验一：位置效应**

把一条关键信息（比如「用户预算上限 3000 元」）分别放在长上下文的开头、25%、50%、75%、结尾，各跑 10 次，问一个必须用到它的问题。

| 位置 | 正确次数 |
|---|---|
| 开头 | /10 |
| 25% | /10 |
| 中间 | /10 |
| 75% | /10 |
| 结尾 | /10 |

**实验二：长度效应**

同一个任务，上下文里塞入不同数量的无关内容：

| 上下文长度 | 通过率 | 平均耗时 | 成本 |
|---|---|---|---|
| 2k tokens | | | |
| 8k | | | |
| 32k | | | |
| 100k | | | |

**用 U1.4 的测试集来测通过率。**

### 你会看到什么

典型结果是：**中间位置最容易被忽略；长度超过某个点后通过率开始下降。**

这个拐点因模型而异，但**通常远小于窗口上限**。一个 200k 窗口的模型，可能在 30k 就开始明显衰减。

**把你测出来的拐点记住。** 它是你后面设计上下文预算的依据。

### 可能卡在哪

**实验成本有点高**

100k 上下文跑 10 次不便宜。可以只跑 5 次，或者用便宜的模型做这个实验（结论的定性部分是通用的）。

**结果不明显**

可能是任务太简单（塞多少无关内容都不影响）。**换一个需要精确定位信息的任务**，比如「在这堆内容里找出唯一提到某个具体数字的地方」。

### 背后的逻辑

这个现象常被称为「lost in the middle」。原因是多方面的：

- 训练数据里超长文本本来就少，长上下文的训练不充分
- 注意力在长序列上会被稀释
- 位置编码在长距离上的表现不如短距离

**从工程角度你不需要知道原因，只需要知道结论并据此设计。**

## 步骤 3 · 三种压缩策略

### 这一步在做什么

实现三种策略，用数据对比它们的代价和收益。

### 策略一：摘要压缩

**做法**：历史超过 N 轮时，让模型把前面的内容总结成一段，用摘要替换原始历史。

```python
async def summarize_history(history: list[dict], keep_recent: int = 4) -> list[dict]:
    """把早期对话压成一段摘要，只保留最近 keep_recent 条原文。"""
    # 太短就不压：摘要本身要多花一次调用，省下的 token 还不够本
    if len(history) <= keep_recent + 2:
        return history

    to_compress = history[:-keep_recent]
    kept = history[-keep_recent:]

    # 关键在这段 prompt：不写清楚保留什么、省略什么，
    # 模型会按自己的判断丢掉你后面要用的信息
    summary = await llm.chat([
        Message.system(
            "把下面的对话总结成一段简洁的背景说明。"
            "必须保留：用户明确表达的偏好和约束、已确定的事实、"
            "已完成的操作及其结果。省略寒暄和推理过程。"
        ),
        Message.user(format_messages(to_compress)),
    ])

    # 摘要放进 system 位并显式标注来源，避免模型把它当成用户刚说的话
    return [Message.system(f"[早期对话摘要]\n{summary.text}")] + kept
```

| 优点 | 缺点 |
|---|---|
| 压缩率高（可到 10:1） | **摘要本身要花一次调用** |
| 保留语义连贯性 | **有信息损失，且损失什么不可控** |
| | 摘要错了会一直错下去 |

**关键设计点是摘要的 prompt**。「保留什么、省略什么」必须写清楚，否则模型会按自己的判断丢弃你需要的东西。

### 策略二：选择性保留

**做法**：不压缩，直接丢。但按规则决定丢哪些。

```python
def select_messages(history: list[dict], token_budget: int) -> list[dict]:
    """按规则决定丢哪些消息：不调模型，纯本地计算，保留的内容 100% 准确。"""
    kept = []
    used = 0

    # 1. 标记为重要的永远保留（比如用户明确的约束），先占预算再谈其他
    important = [m for m in history if m.get("important")]
    for m in important:
        kept.append(m); used += count_tokens(m["content"])

    # 2. 从最近往前加，直到预算用完
    #    倒着遍历是因为越近的消息对当前这一轮越有用，该优先占位
    for m in reversed(history):
        if m in kept:
            continue
        c = count_tokens(m["content"])
        if used + c > token_budget:
            break
        kept.insert(0, m); used += c

    # 重要消息是先插进来的，最后按原始时间顺序还原，否则对话的因果链会乱
    return restore_original_order(kept)
```

| 优点 | 缺点 |
|---|---|
| **零额外成本**，纯本地计算 | 压缩率低 |
| **保留的内容 100% 准确** | 被丢的内容彻底没了 |
| 快 | 需要你定义「重要」的规则 |

**「重要」怎么标记**：可以是规则（含「必须」「不要」「预算」等关键词的消息）、可以是模型判断、可以是用户显式标记。

### 策略三：外部化

**做法**：把长内容存到外部（文件、数据库），上下文里只留一个引用和摘要，需要时再让模型主动去读。

```python
# 不好：把 5000 行日志全塞进上下文，一次吃掉几万 token，而且每轮都要重发
context += full_log

# 好：原文存到外部，上下文里只留路径和索引信息
path = save_to_file(full_log)
# 索引里要给出足够的线索，模型才判断得出「这次要不要去读」
context += f"""
[日志文件] {path}
共 5000 行，时间范围 10:00-11:00，含 23 条 ERROR。
需要查看具体内容时，用 read_file(path, start_line, line_count) 或 search_file(path, keyword)。
"""
```

| 优点 | 缺点 |
|---|---|
| **压缩率极高** | 需要额外的工具支持 |
| **无信息损失**（原文还在） | 模型可能不去读，或者读错地方 |
| 模型按需取用 | 多一轮工具调用的延迟 |

**这是三种里最强的一种，也是最接近人类工作方式的**——你不会把整本书背下来，你会记住「这事在第三章」然后需要时翻过去。

### 对比实验

构造一个上下文超长的场景（50 轮对话 + 10 篇长文档），三种策略各跑你的测试集：

| 策略 | 通过率 | 平均上下文 token | 额外调用成本 | 总成本 | 平均耗时 |
|---|---|---|---|---|---|
| 不压缩（基线） | | | 0 | | |
| 摘要压缩 | | | | | |
| 选择性保留 | | | 0 | | |
| 外部化 | | | | | |

### 可能卡在哪

**摘要压缩之后模型「忘了」重要的事**

改摘要 prompt，明确列出必须保留的信息类型。或者改用「摘要 + 保留关键原文」的混合策略。

**外部化之后模型不去读文件**

在工具描述里说清楚什么时候该读，并在上下文的引用里给出足够的线索（「含 23 条 ERROR」比「日志文件」有用得多）。

**三种能不能一起用**

**能，而且实际项目里通常是组合的**：

- 大文档 → 外部化
- 早期对话 → 摘要压缩
- 最近几轮 → 原样保留
- 用户的硬约束 → 永远保留

### 背后的逻辑

三种策略对应三种不同的取舍：

| 策略 | 用什么换什么 |
|---|---|
| 摘要 | 用**一次调用的成本**和**信息损失**，换上下文空间 |
| 选择 | 用**信息完整性**（丢掉的彻底没了），换零成本 |
| 外部化 | 用**多一轮延迟**和**工具复杂度**，换零损失的压缩 |

**没有哪个绝对更好。** 你的选择取决于：任务对历史信息的依赖程度、延迟要求、成本约束。

**这就是「工程判断」**——面试里问你「上下文太长怎么办」，你能说清楚这三种取舍，比背出一个答案强得多。

## 步骤 4 · 上下文中毒与恢复

### 这一步在做什么

处理一个 Agent 特有的严重问题：**一条错误信息进了上下文，会污染后面所有轮次。**

### 问题长什么样

```
第 3 轮：调用「查库存」工具 → 返回错误的数据（比如接口临时故障返回了空）
第 4 轮：模型基于「库存为 0」做判断 → 建议用户换商品
第 5 轮：用户说「不对啊我看到有货」
第 6 轮：模型仍然坚持库存为 0，因为它的上下文里明明白白写着
```

**模型不会自己怀疑上下文里的内容。** 对它来说，上下文里的东西就是事实。

### 三种应对

**一、标注不确定性**

工具返回时带上可信度信息：

```python
# 不好：孤零零一个数字，模型只能当成永远成立的事实
return "库存：0"

# 好：带上数据时间和「可疑时该做什么」，给模型留出怀疑和重查的余地
return "库存查询结果：0（数据更新时间 10:23，如与实际不符请重新查询）"
```

**二、允许撤销**

设计一个机制，能把某条消息从历史里移除或标记为失效：

```python
def mark_invalid(history: list, message_id: str, reason: str):
    """把一条被证实有误的消息标记为失效，而不是从历史里删掉。"""
    for m in history:
        if m.get("id") == message_id:
            # 用失效声明替换原内容：位置还在，后面的消息才有东西可回应
            m["content"] = f"[此条信息已确认有误，原因：{reason}，请忽略]"
```

**注意是替换成明确的失效声明，而不是直接删除。** 因为直接删除会让上下文的因果链断掉（后面的消息在回应一个不存在的内容）。

**三、检测矛盾**

当用户明确反驳时（「不对」「我看到的不是这样」），触发重新验证而不是继续坚持。

### 亲手验证

构造一个中毒场景：

1. 手动往历史里插入一条错误的工具返回
2. 观察后续几轮模型的行为
3. 实现上面三种机制之一
4. 再跑一遍，确认能恢复

### 背后的逻辑

这个问题的根源是：**模型对上下文的信任是无条件的。** 它没有「这条信息可能是错的」这个概念，除非你显式地告诉它。

**这也是为什么工具的返回值设计很重要**（S2 的 U2.2 会展开）。返回值不只是数据，它还携带了「这个数据有多可信」的元信息。

在 S4 你会遇到这个问题的安全版本：**间接提示注入**——恶意指令藏在 Agent 读取的文档里，进入上下文后被当成指令执行。防御思路是一样的：**明确标注哪些内容是数据（不可信）、哪些是指令（可信）。**

## 步骤 5 · 设计你的上下文预算

### 这一步在做什么

把前面的所有发现变成一个明确的配置。

### 怎么做

给你的项目定一张预算表：

```yaml
context_budget:
  total_limit: 24000              # 基于步骤 2 测出的衰减拐点，不是模型窗口上限
  allocation:                     # 各部分的上限，加起来不超过 total_limit
    system_prompt: 800
    tool_defs: 3000               # 超了就要减少工具或动态加载
    long_term_memory: 1000
    retrieval: 6000               # top-5 每篇约 1200
    history: 12000                # 超了触发压缩
    output_reserve: 4000          # 给模型输出留的空间，必须先扣掉再分配输入
  strategies:                     # 每一项超限时执行哪种压缩，对应上面三种策略
    on_history_overflow: 摘要压缩，保留最近 4 轮
    on_retrieval_overflow: 减少 top_k，或先 rerank 再截断
    on_tool_defs_overflow: 按当前任务类型只加载相关工具组
```

**并且在代码里真的执行这个预算**：每次组装上下文前检查，超了就触发对应策略。

### 为什么用「衰减拐点」而不是「窗口上限」

因为窗口上限是「能塞进去的最大值」，衰减拐点是「塞进去还有效的最大值」。**后者才是你真正的预算。**

### 可能卡在哪

**预算怎么定初始值**

从步骤 2 测出的拐点往下打个七折开始，然后跑测试集验证，逐步调整。

**某个部分总是超预算**

说明这部分的设计有问题：

- 工具定义超 → 工具太多或描述太啰嗦
- 检索超 → top_k 太大或 chunk 太长
- 历史超 → 压缩策略没生效或触发阈值太高

### 背后的逻辑

「预算」这个概念的价值在于**把隐式的取舍变成显式的决策**。

没有预算时，上下文是「有什么塞什么」，最后爆了才发现。有预算时，你被迫回答「工具定义和检索结果哪个更重要」这类问题。

**这个思路会贯穿你后面所有的工程决策**：成本预算、延迟预算、token 预算、轮次预算。**先定预算，再在预算内做优化。**
