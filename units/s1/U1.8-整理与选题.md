## 第二部分 · 定主线项目（4 小时）

### 这一步在做什么

**这是整个 26 周里最重要的一个决定。**

S2 你会用它来学 Agent，S3 给它建评估，S4 让它上线，S5 给它做界面，S6 把它的运行时重写。**六个里程碑是同一个东西的六次升级。**

### 三条硬标准

**必须全部满足**，缺一条就换题。

**标准一：你自己每周真的会用它**

这条最重要。因为：

- S3 需要真实的失败案例来建评估集。你不用它，就没有真实失败
- S4 需要真实的成本和延迟数据
- S5 需要真实的用户反馈（哪怕用户就是你自己）
- **没有真实使用，整个学习会退化成写玩具**

检验方法：问自己「如果这个东西今天就做好了，我这周会用几次？」**答案少于 2 次的题目直接淘汰。**

**标准二：有明确的对错**

必须能判断「这次做对了没有」。

- 「帮我找出这周互动率最高的 5 篇同类笔记」→ 有对错，能验证
- 「帮我写一篇有趣的文案」→ 没有对错，无法评估

**没有对错就没法做评估，S3 整个阶段会落空。**

**标准三：需要至少三个外部工具或数据源**

单次模型调用能解决的问题不需要 Agent。你需要一个真的要「多步、调工具、看结果再决定下一步」的场景。

### 合格的例子

| 项目 | 为什么合格 |
|---|---|
| **小红书选题助手** | 每周真用；「选题是否真的有热度」可验证；需要搜索、拉互动数据、分析竞品三类工具 |
| **飞书周报自动汇总** | 每周必用；「是否遗漏了重要事项」可验证；需要读多维表格、拉会议纪要、读文档 |
| **合同条款审查** | 有真实需求时高频；「是否漏掉风险条款」可对照条款库验证；需要解析 PDF、检索条款库、比对 |
| **技术资料研究助手** | 学习本身就要用；「引用是否真实存在」可验证；需要搜索、抓网页、读 PDF |

### 不合格的例子

| 项目 | 为什么不合格 |
|---|---|
| 通用聊天机器人 | 没有对错，无法评估 |
| 写作助手 | 好坏主观，评估集建不起来 |
| 翻译工具 | 单次调用能解决，用不上 Agent |
| 「帮我管理日程」（但你日程很空） | 你不会真的用 |

### 可能卡在哪

**想不出题目**

从这三个角度找：

1. **你每周重复做的事**：有没有哪件事你每周都要花一小时手工做？
2. **你查资料的场景**：你经常要在多个地方来回翻信息吗？
3. **你的工作场景**：你的日常工作里有没有「收集信息 → 判断 → 产出」的固定流程？

**题目太大**

先砍到「一个人一周能做出第一版」的规模。你可以在 S4、S5 再扩展。

判断方法：如果你没法在一句话里说清楚它做什么，就是太大了。

**题目太小**

如果一次模型调用就能解决，那是 S1 的练习不是 S2 的项目。**看它需不需要多步和工具。**

## 写 PROJECT.md

### 这一步在做什么

把选题固化成文档。**这份文档 S3 到 S6 都会回来看。**

### 模板

```markdown
# 项目：（名字）

## 一句话
（这个 Agent 帮谁解决什么问题）

## 我为什么会用它
（具体到：我现在怎么做这件事，花多久，痛点是什么。
 如果写不具体，说明这个题目不满足标准一。）

## 使用场景
1. 我在什么情况下会打开它
2. 我会输入什么
3. 我期望它输出什么
4. 我怎么判断它做对了

## 需要的工具
| 工具 | 数据源 | 有 API 吗 | 需要认证吗 |
|---|---|---|---|
| | | | |

（至少三个。没有 API 的要想清楚怎么拿数据。）

## 成功标准
- 核心指标：（比如「我给的 10 个选题里，至少 6 个我真的会用」）
- 时间要求：（一次任务不超过 N 分钟）
- 成本要求：（一次任务不超过 N 元）

## 明确不做的
（划清边界，防止越做越大）

## 已知的难点
（现在就能预见的困难，比如某个数据源没有 API）

## 第一版的最小范围
（S2 结束时要做出什么，尽量小）
```

### 关键：写「我为什么会用它」这一段

**如果你写不出具体的使用场景，这个题目就不合格。**

不合格的写法：「这个工具能帮助内容创作者提高效率。」
合格的写法：「我每周一花 90 分钟翻小红书，看同类账号这周哪些内容火了，手工记在飞书表格里，然后决定这周做什么选题。翻的时候经常漏掉一些账号，而且判断'火'全靠感觉，没有数据。」

**第二种写法里，每一句话都能变成一个功能需求。**

## 做一次可行性验证

### 这一步在做什么

在正式开始 S2 之前，花一小时确认这个题目做得下去。

### 验证三件事

**一、数据源能不能拿到**

对每个工具，实际调一次 API 或者手工试一次。

**如果某个关键数据源拿不到，现在换题还来得及。** 到 S2 第三周才发现就晚了。

**二、模型能不能做核心判断**

把你的核心任务写成一个 prompt，手工准备 5 个真实输入，用 U1.4 的方法测一下。

如果模型在核心判断上表现很差（比如 5 个里对 1 个），要么换个思路，要么换题。

**三、成本能不能接受**

粗估一次完整任务要调几次模型、每次多大上下文。用 U1.6 的账本算一下。

如果一次任务要 5 块钱而你每天用 10 次，那不可持续。

### 可能卡在哪

**某个数据源需要爬虫**

先看有没有官方 API。没有的话，评估爬取的难度和合规性。**如果这是唯一的关键数据源，风险很高**，考虑换题或换数据源。

**验证发现模型做不了**

不一定要换题。先试试：拆解成更小的步骤、给更多上下文、给例子。**很多时候是任务描述不清楚，不是模型能力不够。**
