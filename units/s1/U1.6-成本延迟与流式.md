# U1.6 · 成本、延迟与流式（8 小时）

**这个单元解决什么问题**

到现在你的调用是「发出去，等着，拿回来」。这个单元让三件事变得可控：**钱花在哪、慢在哪、用户等待时看到什么。**

**学完你能做到**：跑完一批任务能说出花了多少钱、哪一步最慢；实现流式输出让用户不用干等。

---

## 步骤 1 · 精确统计成本

### 这一步在做什么

给 U1.2 的客户端加上真正的账本。

### 怎么做

**每次调用记录这些**：

```python
@dataclass
class 调用记录:
    时间: datetime
    模型: str
    输入token: int
    输出token: int
    缓存命中token: int      # 有缓存的话
    费用: float
    耗时秒: float
    首token延迟: float | None
    结束原因: str
    标签: dict[str, str]     # 任务类型、prompt 版本、用户 id 等
```

**累加器**：

```python
class 账本:
    def __init__(self):
        self.记录: list[调用记录] = []

    def 记(self, r: 调用记录):
        self.记录.append(r)

    def 汇总(self) -> dict:
        return {
            "次数": len(self.记录),
            "总输入": sum(r.输入token for r in self.记录),
            "总输出": sum(r.输出token for r in self.记录),
            "总费用": sum(r.费用 for r in self.记录),
            "总耗时": sum(r.耗时秒 for r in self.记录),
            "按模型": self.按维度("模型"),
            "按任务": self.按标签("任务类型"),
        }
```

**跑完一批任务打印**：

```
本次共 43 次调用
输入 128,450 tokens / 输出 12,330 tokens
费用 ¥2.41
耗时 87.3 秒
按模型：deepseek-v4-pro ¥0.31 (38次) / claude-sonnet-5 ¥2.10 (5次)
按任务：抽取 ¥0.28 (30次) / 分析 ¥2.13 (13次)
```

### 为什么要打标签

**「按任务类型拆分」是最有价值的一个维度。** 它会告诉你钱花在哪个环节，而这通常和你的直觉不一样。

S3 的成本看板就是这个的放大版，S4 的成本优化直接依赖这些数据。

### 可能卡在哪

**价格表怎么维护**

在 `models.yaml`（U1.2 建的）里记，代码从那里读。**价格随时在变，用之前去官网确认。**

**API 返回的 usage 和我算的对不上**

以 API 返回的为准。有些模型的计费规则复杂（缓存部分按不同价格、推理模型的思考 token 单独计），要读各家文档。

**推理模型的 token 怎么算**

它的「思考」内容通常算作输出 token，即使不返回给你。所以推理模型的实际成本可能远高于你看到的回复长度。**这一点要单独测。**

### 背后的逻辑

**成本可见是成本可控的前提。**

在没有账本之前，「这个 Agent 贵吗」是无法回答的。有了账本，它变成「每次任务平均 0.34 元，其中 78% 花在检索后的总结环节」。

第二种表述直接指向了优化方向。**这就是可观测性的价值**——它不产生任何功能，但它让所有优化成为可能。

## 步骤 2 · 流式输出

### 这一步在做什么

让用户边生成边看到内容，而不是盯着转圈等 20 秒。

### 两个不同的指标

| 指标 | 含义 | 用户感知 |
|---|---|---|
| **首 token 延迟（TTFT）** | 从发请求到收到第一个字 | **「反应快不快」** |
| 总耗时 | 到全部生成完 | 「等了多久」 |

**用户感知的「快」主要取决于前者。** 一个 TTFT 0.5 秒、总共 20 秒的流式输出，体验远好于 TTFT 8 秒、总共 10 秒的非流式。

### 怎么做

```python
async def 流式对话(self, 消息, 模型=None, **kw):
    开始 = time.perf_counter()
    首token时间 = None
    片段 = []
    用量 = None

    stream = await acompletion(model=模型, messages=消息, stream=True, **kw)
    async for chunk in stream:
        delta = chunk.choices[0].delta
        if delta.content:
            if 首token时间 is None:
                首token时间 = time.perf_counter() - 开始
            片段.append(delta.content)
            yield ("文本", delta.content)
        if getattr(chunk, "usage", None):
            用量 = chunk.usage

    yield ("完成", {
        "文本": "".join(片段),
        "首token延迟": 首token时间,
        "总耗时": time.perf_counter() - 开始,
        "用量": 用量,
    })
```

用起来：

```python
async for 类型, 内容 in llm.流式对话(消息):
    if 类型 == "文本":
        print(内容, end="", flush=True)
    else:
        print(f"\n[TTFT {内容['首token延迟']:.2f}s 总计 {内容['总耗时']:.2f}s]")
```

### 可能卡在哪

**`print` 不实时显示**

Python 的输出有缓冲。加 `flush=True`。

**流式模式下拿不到 usage**

有些提供方在流式时不返回 usage，或者需要额外参数（比如 OpenAI 的 `stream_options={"include_usage": True}`）。拿不到的话只能用分词器自己估算。

**流式 + 结构化输出怎么办**

**这是个真实的矛盾。** 结构化输出要等完整的 JSON 才能解析，没法边收边用。

三种处理：

1. 结构化的部分不用流式（大多数情况这样就行）
2. 用增量 JSON 解析器（partial-json 之类的库），边收边解析出已完整的字段
3. **把「给人看的文本」和「给程序用的结构」分开**：文本流式输出，结构在最后用工具调用返回

**第 3 种是 Agent 场景的标准做法**，S5 做前端时你会用到。

**流式中途出错**

已经吐出去的内容收不回来了。要设计好错误提示的展示方式（比如在已输出内容后面追加一行错误说明）。

### 背后的逻辑

**流式底层是 SSE（Server-Sent Events）**：一个长连接，服务端不断往里推数据块，客户端逐块处理。

它和 WebSocket 的区别是：SSE 是单向的（只有服务端推），基于普通 HTTP，实现简单。**模型输出的场景正好只需要单向。**

**这个技术你会在 S4 和 S5 再次遇到**：S4 用 SSE 推送 Agent 的执行进度，S5 用它在前端渲染工具调用过程。**现在理解的机制，到时候直接复用。**

## 步骤 3 · Prompt Caching

### 这一步在做什么

让重复的前缀不用重复付全价。

### 原理

如果你的每次调用都以同样的一大段内容开头（系统提示 + 工具定义 + 少量示例），服务端可以缓存这部分的计算结果。

命中缓存时，这部分按**大幅折扣**计费，而且更快。

### 关键约束

**缓存要求前缀完全一致。** 哪怕差一个字符，缓存就失效。

所以你的上下文必须这样组织：

```
[固定不变的部分]  ← 可缓存
  系统提示
  工具定义
  few-shot 示例
[变化的部分]      ← 不缓存
  对话历史
  当前输入
```

**如果你把当前时间戳放在系统提示里，缓存永远命中不了。** 这是个很常见的低级错误。

### 怎么做

各家的机制不同：

**Anthropic** 需要显式标记缓存点：

```python
system=[{
    "type": "text",
    "text": 长系统提示,
    "cache_control": {"type": "ephemeral"},
}]
```

**OpenAI** 通常是自动的，超过一定长度的前缀自动缓存。

**国内厂商**各有各的机制，读文档。

### 测一下效果

同一个带长前缀的请求连续跑 5 次，记录：

| 第几次 | 输入 token | 缓存命中 token | 费用 | 首 token 延迟 |
|---|---|---|---|---|
| 1 | | 0 | | |
| 2 | | | | |
| 3 | | | | |

**第一次是「写入缓存」，可能比不用缓存还贵一点点；从第二次开始省。**

### 可能卡在哪

**缓存一直不命中**

按顺序检查：

1. 前缀是不是真的完全一致（打印出来 diff 一下）
2. 前缀长度是不是达到了最低要求（各家有门槛，通常 1024 或 2048 token 以上）
3. 两次调用间隔是不是超过了缓存有效期（通常几分钟）
4. 模型是不是支持

**缓存有效期多久**

各家不同，通常 5 分钟左右，有些提供更长的选项（价格更高）。**低频调用的场景缓存价值不大。**

**缓存了但省得不多**

看你的固定前缀占总输入的比例。如果对话历史很长，固定前缀只占 10%，那省下的自然有限。

### 背后的逻辑

缓存的是模型对前缀的**中间计算结果**（KV cache）。因为 Transformer 是自回归的，前面 token 的计算结果不依赖后面的，所以可以复用。

**这也解释了为什么必须是前缀**：改了中间任何一个 token，它之后的所有计算都会变。

**工程上的启示**：把上下文按「变化频率」排序，最稳定的放最前面。这个原则在你设计上下文结构时要一直记着。

## 步骤 4 · 做一次成本拆解分析

### 这一步在做什么

用真实数据回答「我的钱花在哪」。

### 怎么做

跑 100 次你的典型任务（用 U1.4 的测试集扩展一下），然后分析：

**维度一：输入 vs 输出**

```
输入 token 占 92%，费用占 68%
输出 token 占 8%，费用占 32%
```

（输出通常单价是输入的 3 到 5 倍，所以占比不一样。）

**维度二：按环节**

```
检索后的总结：¥1.82 (75%)
意图分类：    ¥0.31 (13%)
最终生成：    ¥0.29 (12%)
```

**维度三：找出异常值**

```
最贵的 5 次调用平均 ¥0.21，是中位数的 6 倍
原因：这 5 次的检索返回了超长文档
```

### 你大概率会发现的三件事

**一、输入 token 是大头。** 不是你想的「模型生成得多所以贵」，而是上下文太长。

**二、成本集中在少数环节。** 通常 80% 的钱花在 20% 的调用上。

**三、异常值很显眼。** 少数几次超长的调用可能占了很大比例。

**这三个发现直接指向 S4 的优化方向**，那时你要在质量不掉的前提下把成本降 40%。

### 可能卡在哪

**数据量不够，看不出规律**

至少跑 50 次。不够的话用测试集重复跑。

**发现某个环节贵得离谱**

去看那个环节的上下文构成（用 U1.5 的分析工具）。**十有八九是某个工具返回值或检索结果太长。**

### 背后的逻辑

**优化的第一步永远是测量。**

没有数据时，你的优化是猜测：「我觉得换个便宜模型能省钱」。有数据时，它变成：「总结环节占 75% 成本，把它的输入从 8k 压到 3k，能省一半」。

**而且数据会推翻你的直觉。** 大多数人以为贵在模型，实际上贵在上下文。

## 步骤 5 · 批处理

### 这一步在做什么

对不要求实时的任务，用更便宜的方式跑。

### 什么是批处理

很多厂商提供 Batch API：你把一批请求打包提交，服务端在低峰期处理，**通常 24 小时内返回，价格约五折**。

### 什么场景适合

| 适合 | 不适合 |
|---|---|
| 离线数据处理 | 用户实时交互 |
| **跑评估集**（S3 会大量用） | Agent 的工具调用 |
| 批量生成内容 | 任何需要等结果的场景 |
| 定期报告 | |

**「跑评估集」是你最实际的应用场景。** S3 你会有 50 条评估用例，每次改动都要跑一遍，用批处理能省一半钱。

### 怎么做

各家的 API 不同，大致流程都是：

1. 把请求写成一个 JSONL 文件，每行一个请求
2. 上传文件
3. 创建 batch 任务
4. 轮询状态
5. 下载结果文件

**先跑通一次**，把代码留着，S3 会用。

### 可能卡在哪

**结果顺序和提交顺序不一致**

每个请求带一个 `custom_id`，结果里会带回来，靠它对应。

**部分失败怎么办**

结果文件里每行有独立的状态。失败的挑出来单独重试。

### 背后的逻辑

批处理便宜的原因是：**它让服务商能在算力空闲时处理，提高了 GPU 利用率。** 你用「延迟」换「价格」。

这是一个通用的工程权衡：**只要你的需求能容忍延迟，几乎总能换到更低的成本。** 同样的思路在 S4 会用在别的地方（异步任务、离线预计算）。
