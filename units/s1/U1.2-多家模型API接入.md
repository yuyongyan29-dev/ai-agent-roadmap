# U1.2 · 多家模型 API 接入（8 小时）

**这个单元解决什么问题**

你会同时用到好几家模型：海外的能力强，国内的快且便宜、不用翻墙。但每家的 SDK 都不一样。

这个单元让你写一套代码，换个字符串就能切换任意一家。**这是 S4 做成本路由的前提**——到那时你要让简单任务走便宜模型，复杂任务走贵模型，如果每家都要写一遍代码，这件事根本做不了。

**学完你能做到**：一个函数调用任意一家模型；正确处理限流、超时、审核拒绝。

## 步骤 1 · 用官方 SDK 各调一次

### 这一步在做什么

**先感受各家的差异，再抽象。** 直接上统一层会让你不理解它在屏蔽什么。

### OpenAI 格式

```bash
uv add openai
```

```python
from openai import AsyncOpenAI

# 用 Async 客户端：步骤 4 要靠 asyncio 并发发请求，同步客户端到时候得整个重写
client = AsyncOpenAI(api_key=os.getenv("OPENAI_API_KEY"))

r = await client.chat.completions.create(
    model="gpt-5",
    # OpenAI 系把 system prompt 当成 messages 里的第一条，靠 role 字段区分身份
    messages=[
        {"role": "system", "content": "你是一个简洁的助手。"},
        {"role": "user", "content": "什么是 AI Agent？"},
    ],
    max_tokens=200,
    temperature=0.3,        # 调低随机性，同一个问题跨厂商对比才有可比性
)
print(r.choices[0].message.content)
print(r.usage.prompt_tokens, r.usage.completion_tokens)   # token 数先记下来，步骤 3 算钱要用
```

### Anthropic 格式

```bash
uv add anthropic
```

```python
from anthropic import AsyncAnthropic

client = AsyncAnthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))

r = await client.messages.create(
    model="claude-sonnet-5",
    system="你是一个简洁的助手。",          # 注意：独立参数，不在 messages 里
    messages=[{"role": "user", "content": "什么是 AI Agent？"}],
    max_tokens=200,                         # 注意：这里是必填，漏了直接报错
    temperature=0.3,
)
print(r.content[0].text)                    # 注意：content 是一个列表
print(r.usage.input_tokens, r.usage.output_tokens)   # 注意：token 字段名也和 OpenAI 不同
```

### 国内的（以 DeepSeek 为例）

```python
# 国内厂商大多提供 OpenAI 兼容接口，所以客户端类不用换，只把请求指向它们的域名
client = AsyncOpenAI(
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com",    # 只改这一行
)
r = await client.chat.completions.create(model="deepseek-v4-pro", messages=[...])
```

**大部分国内厂商都提供 OpenAI 兼容接口**，改 `base_url` 就能用。

### 差异清单

把你观察到的差异记下来：

| 方面 | OpenAI 系 | Anthropic |
|---|---|---|
| system prompt | messages 里的一条 | 独立的 `system` 参数 |
| 返回文本 | `choices[0].message.content` | `content[0].text` |
| token 字段名 | `prompt_tokens` / `completion_tokens` | `input_tokens` / `output_tokens` |
| `max_tokens` | 可选 | **必填** |
| 多模态图片格式 | 不同 | 不同 |

### 可能卡在哪

**`AuthenticationError`**

密钥没读到，或者读错了。打印检查（**只打印前 8 位**）：

```python
print(os.getenv("OPENAI_API_KEY", "")[:8])
```

**`model_not_found`**

模型名写错了，或者你的账号没开通这个模型。去控制台看可用模型列表。**模型名会变，以官方文档为准。**

**连不上（海外的）**

需要代理。httpx 支持环境变量：

```bash
export HTTPS_PROXY=http://127.0.0.1:7890
```

**国内的报「内容审核」错误**

国内模型有内容安全策略，某些话题会被拒绝。这是正常的，你的代码要能处理这种错误。

### 背后的逻辑

**为什么大家都兼容 OpenAI 格式？**

因为先发优势。OpenAI 的接口设计成了事实标准，后来者兼容它可以让用户零成本迁移。

**这对你的实际意义**：绝大多数模型服务都能用 `openai` 这个库访问，只要改 `base_url`。真正需要单独处理的只有 Anthropic 这种自己定义了格式的。

## 步骤 2 · 用 LiteLLM 统一

### 你在搭的是这一层

```
   你的业务代码
   ┌──────────────────────────────┐
   │ llm.对话(消息, 模型="任意")     │  ← 只依赖你自己定义的接口
   └──────────────┬───────────────┘
                  │
   ┌──────────────▼───────────────┐
   │  你的 llm_kit（步骤 3 写）      │  ← 成本统计、重试、并发、
   │                              │     日志、S3 的 trace 埋点
   └──────────────┬───────────────┘
                  │
   ┌──────────────▼───────────────┐
   │        LiteLLM               │  ← 屏蔽各家的格式差异
   └──┬────────┬────────┬─────┬───┘
      │        │        │     │
   ┌──▼──┐ ┌──▼───┐ ┌──▼──┐ ┌▼────┐
   │Claude│ │OpenAI│ │国内 │ │本地 │
   └──────┘ └──────┘ └─────┘ └─────┘

关键：业务代码只依赖你自己的接口。
      LiteLLM 变了、某家模型下线了，你只改中间那一层。
```



### 这一步在做什么

装一层适配器，把所有差异藏起来。

### 怎么做

```bash
uv add litellm
```

```python
from litellm import acompletion

async def call(model: str, messages: list[dict], **kw):
    """统一入口：模型名带上提供方前缀，LiteLLM 自己挑 SDK、转格式、找对应的环境变量密钥。"""
    # **kw 原样透传，是为了不把 temperature、tools 这类参数写死在这层
    r = await acompletion(model=model, messages=messages, **kw)
    # 返回结构被 LiteLLM 统一成 OpenAI 的形状，所以调 Claude 也走 choices[0]
    return r.choices[0].message.content

# 同一个函数，换模型名就行
await call("gpt-5", messages)
await call("claude-sonnet-5", messages)
await call("deepseek/deepseek-v4-pro", messages)
await call("dashscope/qwen-max", messages)
```

**LiteLLM 统一成了 OpenAI 格式**，包括 system prompt 的位置、返回结构、usage 字段名。

### 可能卡在哪

**模型名前缀怎么写**

LiteLLM 用 `提供方/模型名` 的格式，OpenAI 的可以省略前缀。查 [LiteLLM 支持的提供方列表](https://docs.litellm.ai/docs/providers) 确认写法。

**某个参数不支持**

不是所有模型都支持所有参数。LiteLLM 有时会静默忽略，有时会报错。**关键参数要测一下是不是真的生效了。**

**要不要用 LiteLLM**

也可以自己写适配层（就是一堆 if-else）。用 LiteLLM 的好处是省事、支持的提供方多、自带成本计算。坏处是多一层依赖，出问题要多排查一层。

**建议**：用 LiteLLM，但**你自己的代码要包一层**（下一步），这样将来想换掉它只改一个文件。

### 背后的逻辑

这个模式叫「**适配器模式**」：在你的代码和多个不同的外部接口之间加一层，把差异消化掉。

关键设计原则是：**你的业务代码只依赖你自己定义的接口，不直接依赖任何第三方**。这样第三方变了（LiteLLM 升级改了 API、某家模型下线），你只改适配层。

**这个原则在 S2 选 Agent 框架时同样适用**——不要让整个项目和某个框架深度绑定。

## 步骤 3 · 封装你自己的客户端

### 这一步在做什么

**这一步的产出会跟着你走完剩下 20 周。** 认真写。

### 目标接口

```python
from s1_llm.client import LLM, Message

# 默认模型放在构造函数里：大部分调用点不用关心背后是哪家，只有需要时才覆盖
llm = LLM(default_model="deepseek/deepseek-v4-pro")

reply = await llm.chat(
    # Message.system / Message.user 是小工厂函数，省得到处手写 {"role": ..., "content": ...}
    messages=[Message.system("你是助手"), Message.user("你好")],
    model="claude-sonnet-5",       # 可选，覆盖默认
    temperature=0.3,
)

print(reply.text)
# 用量每次都要拿到：S4 的成本路由靠的就是这几个数字，事后补不回来
print(reply.usage.input_tokens, reply.usage.output_tokens, reply.usage.cost)
print(reply.finish_reason)         # 不是 "stop" 就说明没写完，别当完整结果用
print(reply.latency_s)
```

### 实现要点

```python
from dataclasses import dataclass
from pydantic import BaseModel

class Usage(BaseModel):
    """一次调用的计量结果。费用在客户端里算好再填进来，调用方不用自己查价格表。"""
    input_tokens: int
    output_tokens: int
    cost: float

class Response(BaseModel):
    """所有厂商的返回都收敛成这一个结构，业务代码因此不必知道背后是哪家。"""
    text: str
    model: str
    usage: Usage
    # 单独留出来是因为「有输出」不等于「答完了」，被截断的结果长得和正常结果一样
    finish_reason: str     # stop / length / tool_use / content_filter
    latency_s: float
    raw: dict              # 保留原始响应，方便排查
```

**必须包含的东西**：

- [ ] 记录每次调用的 token 数和费用
- [ ] 记录耗时
- [ ] **返回 `finish_reason`**，调用方必须能知道输出有没有被截断
- [ ] 保留原始响应，出问题时能查
- [ ] 用 logging 记录（不打印完整 prompt，太长；记 token 数和模型名）

### 可能卡在哪

**费用怎么算**

LiteLLM 有 `completion_cost()` 可以算，但价格表可能滞后。**建议自己维护一份价格配置文件**：

```yaml
# models.yaml
deepseek/deepseek-v4-pro:
  # 单价按「每 token」存：算费用时直接乘 token 数，省掉除以 1K 还是 1M 这种单位错误
  input_price: 0.0000005      # 每 token 的价格，单位元
  output_price: 0.000002
  context_window: 128000
  supports_tools: true
```

**价格随时在变。用的时候去官网确认，不要信任何二手资料包括这份文档。**

**要不要现在就做重试**

要。把 U0.5 学的 tenacity 用上，区分可重试和不可重试的错误：

| 错误 | 重试 |
|---|---|
| 429 限流 | 是，指数退避 |
| 500/502/503 | 是 |
| 超时 | 是 |
| 401 认证 | 否 |
| 400 参数错 | 否 |
| 内容审核拒绝 | 否 |
| 余额不足 | 否 |

**每次重试都是一次计费。** 一定要设最大次数，并在日志里记录重试了几次。

### 背后的逻辑

为什么要自己封一层而不是直接用 LiteLLM？

因为你需要的东西 LiteLLM 不提供：统一的成本统计、你自己的日志格式、你自己的重试策略、以及**将来接可观测性的埋点位置**。

S3 你会在这一层加 trace，S4 会在这一层加缓存和路由。**现在把接口设计好，后面就是往里填东西。**

## 步骤 4 · 并发控制

### 这一步在做什么

同时发多个请求提速，但不要把自己撞到限流。

### 怎么做

```python
import asyncio

async def batch_call(tasks: list, concurrency: int = 5):
    """并发跑一批请求，用信号量把在途请求数压在限流线以下。"""
    # 用信号量而不是手动分批：分批要等最慢的一个走完才开下一批，信号量是空一个补一个
    semaphore = asyncio.Semaphore(concurrency)

    async def run_one(task):
        async with semaphore:           # 同时最多 concurrency 个在跑
            return await llm.chat(task)

    # gather 的返回顺序和传入顺序一致，结果不用再想办法和输入对齐
    return await asyncio.gather(*[run_one(t) for t in tasks])
```

`Semaphore(5)` 的意思是「同时最多 5 个能进」。第 6 个会等着，直到有一个完成。

### 并发数设多少

看各家的限流策略，通常在控制台能看到 RPM（每分钟请求数）和 TPM（每分钟 token 数）。

**保守起见从 3 到 5 开始**，观察有没有 429，再往上调。

### 可能卡在哪

**`asyncio.gather` 里一个失败全部失败**

默认行为是有异常就抛出。想让其他的继续：

```python
# return_exceptions=True：异常不再往外抛，而是当成返回值放进结果列表
results = await asyncio.gather(*tasks, return_exceptions=True)
# 结果里失败的项是异常对象，要自己判断
for r in results:
    if isinstance(r, Exception):
        log_failure(r)      # 别静默吞掉：这些请求已经计费了，得知道亏在哪
```

**并发之后成本失控**

并发只是让请求更快发出去，不会减少总量。**加个总预算检查**：跑之前估算，超过阈值就拒绝。

**大量请求时限流了**

除了降低并发数，还要在 429 时按 `Retry-After` 头等待。

### 背后的逻辑

回到 U0.6 学的异步模型：所有请求在同一个线程里，靠事件循环调度。`gather` 把 100 个协程一起丢进去，它们会同时在「等网络」。

**这就是异步的价值**：100 个请求的总耗时接近最慢的那一个，而不是 100 个的总和。

但也正因为它们真的同时在飞，你需要 Semaphore 限制——**否则一瞬间 100 个请求打过去，服务端直接限流。**

## 步骤 5 · 建模型清单

### 这一步在做什么

把你手上所有模型的关键信息记在一个地方，以后选型有据可依。

### 怎么做

建 `s1-llm/models.yaml`，每个模型记录：

```yaml
claude-sonnet-5:
  provider: anthropic
  # 窗口和最大输出是两件事：能读 200K 不代表一次能写出 200K
  context_window: 200000
  max_output: 64000
  input_price: 
  output_price: 
  supports_tools: true
  supports_streaming: true
  supports_caching: true
  supports_vision: true
  # 下面两项官网都不给，只能自己压测填，是选型时唯一可信的速度依据
  measured_ttft_s: 
  measured_tokens_per_s: 
  good_at: [复杂推理, 长文档, 工具调用]
```

**最后三项要你自己测。** 写个小脚本，对每个模型跑 10 次同样的请求，记录首 token 延迟和每秒生成多少 token。

### 为什么值得花这个时间

到 S4 做成本优化时，你要回答「哪个环节能换成便宜模型」。**没有这张表，你只能凭感觉。**

### 背后的逻辑

**能力、速度、价格三者通常互相制约。** 你的工程判断就是在具体场景里找到平衡点。

一个实用的分级思路：

| 层级 | 特征 | 用在哪 |
|---|---|---|
| 小/快/便宜 | 几分之一的价格，够用的能力 | 分类、抽取、格式转换、意图识别 |
| 中等 | 平衡 | 大部分对话和工具调用 |
| 强/慢/贵 | 复杂推理 | 规划、疑难问题、最终质检 |

**S4 的 U4.5 会让你真的实现这个路由。** 现在先把数据准备好。
