# Stage 3 · 评估与可观测性（W11–W14，80h）

**这是整个计划里最值钱的四周。** 会做 Agent demo 的人很多，能证明自己的 Agent 好在哪、坏在哪、这次改动是变好了还是变坏了的人很少。面试里这也是最能拉开差距的部分。

**必读，在 U3.1 之前读完**：Anthropic《[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)》（2026-01-09）。本阶段的方法论直接建立在它之上，下面每个单元都会引用它的具体建议。

这篇文章最关键的几条：

- **从 20 到 50 个来自真实失败的任务开始就够了**，早期改动的效果差异很大，小样本足以给出信号
- **好任务的标准是「两个领域专家独立判断会得出相同的通过/失败结论」**
- 三类评分器互补：代码型（确定、快、便宜）、模型型（灵活、能处理细微差别）、人工（校准的黄金标准）
- **评分要评结果，不要评具体的工具调用序列**，否则会惩罚模型找到的更好解法
- **定期读原始 transcript**，验证评分器真的在评你以为它在评的东西
- 分数接近 100% 时评估集就饱和了，不再有信号，该换新题
- 原文的态度值得抄下来贴在墙上：**「在有人真正深入细节之前，我们不会把评估分数当真。」**

## U3.1 评估的思维框架（4h）

**目标**：想清楚什么该测、怎么测、测出来的数字意味着什么。

**具体做什么**

1. 理解为什么传统单元测试不够：LLM 输出不确定，同样输入两次结果不同，`assert output == expected` 直接失效。但**这不代表不能测，只代表断言要换一种写法**。
2. 划清边界，列出你项目里的两类逻辑：
   - **确定性逻辑**（工具函数、数据解析、权限判断、格式转换）→ 用 S0 学的 pytest，这部分必须 100% 确定
   - **非确定性逻辑**（模型的判断、规划、生成）→ 用评估
   很多人把整个 Agent 都当成黑盒去评估，其实一大半代码是可以用普通测试覆盖的。
3. 理解评估的三个层次：
   - **组件级**：单个环节，比如「检索是否召回了正确文档」「意图分类是否正确」
   - **轨迹级**：过程是否合理，比如「是否调用了危险工具」「步数是否失控」
   - **端到端**：最终结果对不对
4. 明确一个原则：**评结果优先于评过程**。除非过程本身有硬约束（比如「不能在没确认前发邮件」），否则不要断言具体的工具调用顺序。

**产出**：`s3-eval/SCOPE.md`——一张表，列出你项目每个模块归入哪一类、用什么方式验证。

**完成判据**：这张表覆盖你项目的全部模块，且能说明为什么某个模块归到这一类。

## U3.2 构建评估集（12h）

**目标**：一份 50 条左右、来自真实场景的黄金数据集。**这是整个 S3 的地基，质量决定后面一切。**

**具体做什么**

1. **从真实失败开始，不要凭空编题**。三个来源：
   - 你自己用 M2 的 Agent 这几周里，它做错的每一次
   - 你开发过程中手动检查过的那些 case
   - 你能想到但还没试过的边界情况
2. 目标 50 条，其中正例负例都要有：**既要测「该做的做了」，也要测「不该做的没做」**。只有正例会导致模型被优化成什么都敢做。
3. 每条记录这些字段：
   ```yaml
   id: EVAL-001
   input: 用户的原始输入
   context: 需要的前置状态（如已有的记忆、数据库状态）
   expected: 参考答案（证明这题是可解的）
   grader: 用哪个评分器
   criteria: 通过的具体标准
   tags: [核心路径 / 边界 / 安全 / 回归]
   source: 来自哪次真实失败
   ```
4. **写标注规范**：什么算通过、什么算部分通过、模糊情况怎么判。检验标准就是那句话——两个领域专家独立判断能得出同样结论。如果你自己隔一天判断结果都不一样，说明这条题目定义不清，要么改要么删。
5. **每条都要有参考答案**。写不出参考答案的题目说明它可能无解，删掉。
6. 版本化：评估集进 git，以后每次新增都是一次 commit。

**产出**：`s3-eval/dataset/golden.yaml`（50 条）、`s3-eval/RUBRIC.md`（标注规范）

**完成判据**：找一个朋友（或者隔三天后的你自己）按你的规范独立判 10 条，和你的判断一致率超过 90%。**不一致的那几条就是你规范写得不清楚的地方。**

## U3.3 代码型评分器（8h）

**目标**：能用规则判的绝不用模型判。代码型评分器又快又便宜又确定。

**具体做什么**

实现至少五种，按你项目的实际需要选：

1. **精确匹配 / 包含匹配**：适合分类、抽取类任务
2. **JSON schema 校验**：结构化输出必测
3. **数值容差**：`abs(actual - expected) < tolerance`
4. **集合比较**：召回的文档 id 集合与标准答案的交集，算 precision / recall
5. **工具调用断言**：只断言硬约束（「危险工具必须先经过确认」），不断言顺序
6. **副作用验证**：任务说要建一条记录，就去数据库查那条记录在不在。**这类「验证真实结果」的评分器最可靠**
7. **正则 / 静态分析**：输出格式、是否含敏感词、生成的代码能否解析

再实现一个评估运行器：读数据集 → 并发跑 Agent → 逐条评分 → 输出报告（总分、分标签分数、失败清单）。**并发要控制，且每条题目要在隔离环境里跑，不能共享状态**，否则前一条的副作用会污染后一条。

**产出**：`s3-eval/graders/code_graders.py`、`s3-eval/runner.py`

**完成判据**：一条命令跑完全部 50 条，输出一份含总分、分标签得分、失败 case 列表的 Markdown 报告。

## U3.4 模型型评分器（LLM-as-judge）（10h）

**目标**：处理规则判不了的东西，同时知道它有多不可靠。

**具体做什么**

1. 写评分 prompt，三个要素缺一不可：**明确的评分维度**、**每档分数的具体描述**（不要只写 1-5 分，要写清楚 3 分和 4 分的区别）、**要求先给理由再给分**。
2. 对比两种模式：
   - **绝对打分**：给一个输出打 1-5 分。简单，但分数漂移严重
   - **成对比较**：给 A 和 B 判哪个更好。**明显更稳定**，适合比较两个版本
3. **测 judge 自己的偏见**，这一步大多数人跳过，然后被坑：
   - **位置偏见**：把 A 和 B 交换位置再判一次，看结论会不会翻
   - **长度偏见**：长答案是不是天然得分高
   - **自我偏好**：用 A 模型判 A 模型自己的输出，会不会偏高
4. **用人工校准**：你自己人工打 30 条，和 judge 的结果比一致率。**低于 85% 就改评分 prompt 重来**，不要拿一个没校准的 judge 去跑几百条。
5. 加护栏：judge 也可能返回格式错误、也要重试、也要算成本。judge 的费用在大规模评估时不小。

**产出**：`s3-eval/graders/llm_judge.py`、`s3-eval/judge_calibration.md`

**完成判据**：一份校准报告，含 30 条人工打分与 judge 打分的对照表、一致率数字、以及三种偏见的测试结果。一致率必须超过 85%。

## U3.5 Trace 与可观测性（12h）

**目标**：任何一次运行，30 秒内定位到是哪一步出的问题。

**工具**：[Langfuse](https://langfuse.com)，开源可自托管，trace、评估、成本分析在一个地方。

**具体做什么**

1. Docker 起一个自托管的 Langfuse，接进你的 `compose.yaml`。
2. 接入你的 Agent，让 trace 层级结构正确：
   ```
   trace: 一次完整任务
   └── span: agent 的第 1 轮
       ├── generation: 模型调用（记录 prompt、输出、token、模型名、耗时）
       └── span: 工具调用（记录入参、返回、耗时、是否报错）
   └── span: agent 的第 2 轮
       └── ...
   ```
3. **遵循 OpenTelemetry 的 GenAI 语义约定**给属性命名（`gen_ai.system`、`gen_ai.request.model`、`gen_ai.usage.input_tokens` 等）。用标准命名的好处是以后换任何一家可观测性平台都不用重写埋点。
4. 每条 trace 打上业务标签：用户 id、会话 id、任务类型、prompt 版本、代码版本。**没有版本标签，你就无法回答「这个问题是哪个版本引入的」。**
5. 把 U3.3 和 U3.4 的评分结果作为 score 附到对应的 trace 上，这样评估结果和执行细节在一个地方能看到。
6. 练习一次真实排查：故意制造一个 bug，只用 Langfuse 界面找出它在哪。

**产出**：`s3-eval/tracing/`、`compose.yaml` 里的 langfuse 服务

**完成判据**：打开任意一条 trace，能看到完整的调用树，每个节点有输入、输出、token 数、耗时、成本，且带 prompt 版本标签。

## U3.6 在线评估与数据回流（10h）

**目标**：让线上的失败自动变成评估集的新题目。**这是评估集唯一正确的增长方式。**

**具体做什么**

1. **采集用户信号**，这些比任何自动指标都真实：
   - 显式：点赞、点踩、评分
   - 隐式：重试了、中途放弃了、手动改了结果、复制走了结果
2. 对线上流量采样（比如 5%），异步跑 LLM judge 打分，结果写回 trace。**异步跑，不要阻塞用户请求。**
3. 建一个失败 case 的收件箱：负反馈、judge 低分、异常报错的 trace 自动进队列。
4. **走通完整闭环**，这是本单元的核心：
   ```
   线上失败 → 进收件箱 → 你人工看 trace 确认 → 写成评估条目
   → 加进 golden.yaml → 修复 → 跑回归确认修好了 → 永久防止复发
   ```
5. **至少真实走通 3 个 case**，不是模拟，是你 Agent 这几周真实出的错。
6. 加一条纪律：修任何 bug 之前，先给它写一条评估题。没有评估题的修复等于没修。

**产出**：`s3-eval/online/`、`s3-eval/dataset/golden.yaml`（新增至少 3 条来自线上）

**完成判据**：能演示一个完整闭环——指出某条评估题来自哪次真实失败、当时的 trace 长什么样、修复的 commit 是哪个、现在跑回归是通过的。

## U3.7 评估进 CI（12h）

**目标**：把「改坏了」拦在合并之前。**这一步做完，你的项目就从个人作品变成了工程产物。**

**具体做什么**

1. 写 GitHub Actions workflow，在 PR 上触发评估。
2. **分层跑，控制成本和时间**：
   - 每次 PR：跑标了 `核心路径` 的快速子集（约 15 条），几分钟出结果
   - 合并到 main：跑全量 50 条
   - 每晚定时：跑全量 + LLM judge + 成本报告
3. **设门禁**：核心路径通过率不得低于基线，低于就红灯拦住合并。基线存在仓库里，每次 main 更新时刷新。
4. 结果自动贴回 PR 评论：本次得分、与 base 的差值、变差的条目具体是哪几条。
5. **密钥管理**：API key 放 GitHub Secrets。为了控制 CI 成本，可以给评估用的 key 设独立预算。
6. **做一次验证**：故意提一个把 prompt 改差的 PR，确认 CI 红灯并在评论里指出是哪几条题目挂了。

**产出**：`.github/workflows/eval.yml`、`s3-eval/baseline.json`

**完成判据**：那个「故意改差」的 PR 被 CI 拦下来了，且评论里能看到具体退化的条目。截图存进 README，这是很有说服力的作品集素材。

## U3.8 成本与延迟看板（12h）

**目标**：能回答「上周钱花在哪」「哪一步最慢」这两个问题。

**具体做什么**

1. 从 trace 数据聚合出这些指标，按天、按任务类型、按模型、按工具四个维度切：
   - 每次任务的平均成本、P50 / P95 / P99
   - 每次任务的平均轮次、平均工具调用次数
   - 首 token 延迟和总耗时的 P50 / P95 / P99
   - 各工具的调用次数、失败率、平均耗时
2. 用 Langfuse 自带的看板，或者自己用 Postgres 查询加一个简单页面。
3. **找出你的成本大头**。跑一遍分析，回答：钱是花在输入还是输出、是花在主 Agent 还是子 Agent、是哪个工具的返回值太长。**答案通常会让你意外**——很多项目的成本大头是工具返回值污染上下文，而不是模型本身贵。
4. **找出你的延迟大头**。是模型慢、还是某个工具慢、还是轮次太多。
5. 设三条告警线：单次任务成本超过 X、P95 延迟超过 Y、失败率超过 Z。
6. 基于这些数据，列出 S4 要做的优化清单。

**产出**：`s3-eval/dashboard/`、`s3-eval/cost_analysis.md`

**完成判据**：一份成本与延迟分析报告，明确指出前三大成本项和前三大耗时项，并给出 S4 的优化优先级。

## M3 里程碑

**交付物**：M2 的 Agent 现在有了完整的评估体系、全链路 trace、CI 门禁和成本看板。

**验收清单**

- [ ] 50 条以上的评估集，含正负例，有标注规范，一致率验证过
- [ ] 至少 5 种代码型评分器 + 1 个校准过的 LLM judge（一致率 > 85%）
- [ ] Langfuse 里能看到完整调用树，属性遵循 OTel GenAI 约定
- [ ] 线上失败到评估集的闭环走通过至少 3 次
- [ ] CI 门禁生效，有「拦住劣化 PR」的证据截图
- [ ] 成本与延迟分析报告，指出前三大问题
- [ ] `s3-eval/README.md` 讲清楚整套体系怎么用

**面试价值**：这一份东西比十个 demo 都管用。当面试官问「你怎么保证 Agent 的质量」，你可以直接打开 CI 的那条评论截图。
