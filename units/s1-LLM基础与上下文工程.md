# Stage 1 · LLM 基础与上下文工程（W4–W6，60h）

**这一阶段的核心不是学模型原理，是建立对模型行为的工程直觉**：它什么时候会错、错在哪、成本花在哪、上下文该放什么。

## U1.1 LLM 工作原理（工程视角）（6h）

**目标**：建立直觉，不推公式。你需要知道的只是「什么因素会让输出变化」。

**具体做什么**

1. 玩一遍 [OpenAI Tokenizer](https://platform.openai.com/tokenizer) 或 `tiktoken` 库。输入中文、英文、代码、JSON，看各自的 token 密度差多少。**中文通常一个字约 0.6 到 1.5 个 token，这直接决定你的成本。**
2. 理解自回归生成：模型一次只预测下一个 token，然后把它接到输入后面再预测下一个。所有的「思考」都发生在这个循环里。
3. 理解上下文窗口：它是输入加输出的总预算，不是只算输入。
4. **做参数实验**：固定一个 prompt，在 temperature 取 0 / 0.3 / 0.7 / 1.0 / 1.5 五档下各跑 10 次，记录输出的差异程度。再单独试 `top_p`。
5. 理解幻觉的机制：模型在预测「最像答案的文本」，不是在查证事实。所以它编造的东西往往格式完美、细节丰富、完全错误。
6. 试试推理模型（reasoning model）和普通模型的差别，看同一道逻辑题两者的表现和耗时。

**产出**：`s1-llm/experiments/sampling_report.md`

**完成判据**：一份实验报告，含 5 组参数各 10 次输出的记录表，以及你自己总结的「什么任务该用什么 temperature」。

## U1.2 多家模型 API 接入（8h）

**目标**：一套代码切换任意模型，为后面的成本路由打底。

**具体做什么**

1. 分别用各家官方 SDK 调通一次：`anthropic`、`openai`、以及国内一家。感受它们在参数命名、system prompt 位置、返回结构上的差异。
2. `uv add litellm`，用 [LiteLLM](https://docs.litellm.ai/) 做统一层。它把上百家提供方统一成 OpenAI 格式，是这一层最常见的选择。
3. 封装你自己的 `llm_kit.chat()`：入参是模型名、消息列表、参数，出参统一。换模型只改一个字符串。
4. 处理各家的差异点：有的 system prompt 是独立字段，有的是消息列表第一条；有的支持多模态，有的不支持；国内几家的限流策略更严。
5. 加上错误处理：限流（429）退避重试、超时、内容审核拒绝、余额不足。
6. 建一个模型清单文件，记录你手上每个模型的：上下文长度、输入输出单价、是否支持工具调用、是否支持流式。**价格随时在变，用的时候去官网确认，不要信任何二手资料包括这份文档。**

**产出**：`s1-llm/llm_kit/client.py`、`s1-llm/models.yaml`

**完成判据**：同一段测试代码，把模型名换成任意四家中的一家都能跑通，输出结构完全一致。

## U1.3 结构化输出（8h）

**目标**：让模型返回程序能直接用的数据，而不是需要人读的文字。**这是从「聊天机器人」到「Agent」的第一道分水岭。**

**具体做什么**

1. 用 Pydantic 定义一个数据结构，比如「从简历里抽出姓名、年限、技能列表、最近一段经历」。
2. 三种做法各试一遍，对比可靠性：
   - 在 prompt 里描述 JSON 格式，让模型自由输出，自己解析
   - 用 JSON mode / `response_format`
   - 用工具调用（function calling）把 schema 当成工具参数
3. **必须处理失败**：模型返回的 JSON 可能缺字段、类型错、带 markdown 代码块包裹、甚至直接是一段道歉。写一个 `parse_or_retry`，解析失败时把错误信息回喂给模型让它重试，最多三次。
4. 试试 [instructor](https://python.useinstructor.com/) 库，它把上面这套封装好了，看它是怎么实现的。
5. 测边界：字段特别多时会不会漏、嵌套结构深了会不会乱、枚举值会不会自己发明新的。

**产出**：`s1-llm/extract.py`、`s1-llm/data/samples/`（20 篇测试文本）

**完成判据**：20 篇非结构化文本输入，100% 返回符合 schema 的对象，日志里能看到重试发生了几次。

## U1.4 Prompt 工程（8h）

**目标**：能用数据说明 A 版比 B 版好，而不是「我觉得这版更好」。

**具体做什么**

1. 学这几个基本手法，每个都实测效果：明确角色与任务、给正例（few-shot）、要求分步思考、明确输出格式、给约束边界。
2. 学一个反直觉的点：**负面指令经常无效**。「不要输出 markdown」不如「只输出纯文本，第一个字符必须是字母」。自己做实验验证。
3. **建一个 20 条的测试集**：同一个任务的 20 组输入 + 你期望的输出。这是你第一次做评估，S3 会把它放大一百倍。
4. 写 5 个版本的 prompt，在这 20 条上各跑一遍，用表格记录通过数、平均 token、平均耗时。
5. 把 prompt 从代码里抽出来放进 `prompts/` 目录，文件名带版本号。**从今天起 prompt 进 git，改动走 diff。**
6. 试试同一个 prompt 在不同模型上的表现，理解 prompt 不是通用的。

**产出**：`s1-llm/prompts/v1..v5.md`、`s1-llm/eval/prompt_compare.md`

**完成判据**：一张对比表，说明你最终选哪版、好在哪、代价是什么。**不能只写「效果更好」，必须有数字。**

## U1.5 上下文工程（10h）

**目标**：这是 2025 年之后 Agent 工程最核心的技能。理解上下文是有限且会衰减的资源。

**必读**：Anthropic《[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)》（2025-09-29）。**精读，做笔记，两遍。**

**具体做什么**

1. 理解核心命题：上下文不是「能塞多少塞多少」。所有前沿模型在上下文变长时性能都会下降，而且远在窗口填满之前就开始。
2. 拆解一次真实调用的上下文构成：系统提示、工具定义、检索结果、历史消息、当前输入。**用代码统计每一部分各占多少 token**，你会发现工具定义往往比你想的大得多。
3. 实现三种压缩策略并对比：
   - **摘要压缩**：历史超过 N 轮就让模型总结成一段
   - **选择性保留**：只留最近 K 轮 + 被标记为重要的几轮
   - **外部化**：把长内容写进文件，上下文里只留文件路径和摘要，需要时再读
4. 构造一个「上下文超长」的场景（比如 50 轮对话 + 10 篇长文档），三种策略各跑一遍，测质量和成本。
5. 理解「上下文中毒」：一旦错误信息进了上下文，后续所有轮次都会被它污染。设计一个能剔除错误信息的机制。

**产出**：`s1-llm/context/`（三种策略的实现）、`s1-llm/context/report.md`

**完成判据**：一张三种策略的对比表，含质量分、token 数、耗时，以及你对「什么场景用哪种」的结论。

## U1.6 成本、延迟与流式（8h）

**目标**：成本和延迟从此可测、可控。

**具体做什么**

1. 给 `llm_kit` 加上统计：每次调用记录输入 token、输出 token、模型、耗时、按当前单价算出的费用。
2. **实现流式输出**：用 SDK 的 stream 模式，边收边打印。理解首 token 延迟（TTFT）和总耗时是两个完全不同的指标——用户感知的「快」主要取决于前者。
3. 试 **prompt caching**：把一段长的固定前缀（比如系统提示 + 少量示例）标记为可缓存，测缓存命中前后的成本和延迟差。各家的缓存机制和计费方式不同，读各自文档。
4. 做一次成本拆解：跑 100 次典型调用，统计钱花在哪——是输入还是输出、是哪个环节。
5. 理解批处理：不要求实时的任务用 batch API，通常能便宜一半。
6. 加上并发控制：用 `asyncio.Semaphore` 限制同时在飞的请求数，避免撞限流。

**产出**：`s1-llm/llm_kit/metrics.py`

**完成判据**：跑完一批任务后能打印出「本次共 N 次调用、X 输入 token、Y 输出 token、耗时 Z 秒、花费 W 元」，并能给出开缓存前后的对比数据。

## U1.7 本地模型（6h）

**目标**：知道开源模型的能力边界，理解什么任务不需要花钱调云端。

**具体做什么**

1. 装 [Ollama](https://ollama.com/)，跑一个 7B 到 14B 的模型。
2. 理解量化：Q4 / Q8 分别是什么意思，对显存占用和质量各有什么影响。
3. Ollama 提供 OpenAI 兼容接口，把它接进你的 `llm_kit` 当第五个提供方。
4. **做能力边界实验**：拿 U1.3 的结构化抽取任务和 U1.4 的测试集，在本地模型上跑一遍，和云端模型对比通过率。
5. 得出你自己的结论：哪类任务本地模型够用（通常是分类、抽取、改写），哪类不够用（通常是复杂推理、长上下文、多步工具调用）。

**产出**：`s1-llm/eval/local_vs_cloud.md`

**完成判据**：一张对比表和一句结论——你的项目里哪个环节可以换成本地模型。

## U1.8 整理与复盘（6h）

**具体做什么**

1. 把 S1 的所有代码整理成一个可安装的 `llm_kit` 包，写 README 和使用示例。
2. 补测试：mock 掉真实 API 调用，让 `pytest` 断网可跑。
3. 写 S1 复盘：这三周最反直觉的三个发现是什么。
4. **确定 S2 的主线项目选题**（下一阶段第一天就要用）。

**选题标准**，三条全部满足才算合格：

- 你自己每周真的会用它，不是为了做而做
- 有明确的对错，能判断「这次做对了没有」
- 需要调用至少三个外部工具或数据源

**合格例子**：小红书选题助手（搜同类笔记、分析互动数据、生成选题）、飞书周报汇总（读多维表格、拉会议纪要、生成周报）、合同条款审查（解析 PDF、比对条款库、标风险）。

**不合格例子**：通用聊天机器人（没有对错）、写作助手（无法判断好坏）、翻译工具（用不上多步工具调用）。

**产出**：`s2-agent/PROJECT.md`，写清楚：解决什么问题、用户是谁（大概率是你自己）、成功的标准是什么、需要哪些工具。
