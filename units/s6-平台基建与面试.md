# Stage 6 · 平台与基建 + 面试准备（W23–W26，80h）

**目标**：从「会用框架做 Agent」升级到「知道框架是怎么造的」，并把 26 周的成果变成能讲的作品集。

---

## U6.1 拆解主流 Agent 平台（10h）

**目标**：知道一个 Agent 平台由哪些部件组成，以及各家的取舍。

**具体做什么**

1. **动手用**，不要只看介绍文章。各挑一个真实场景搭一遍：
   - [Dify](https://github.com/langgenius/dify)：开源，**可以本地部署然后读源码**，这是最有价值的一个
   - 字节 Coze：看它的工作流编排和多渠道发布
   - 腾讯、阿里的企业级 Agent 平台：看它们怎么对接企业内部系统和权限
2. 每个平台回答同样一组问题：
   - 编排是怎么表达的（拖拽 DAG？状态机？代码？）
   - 工具怎么接入（插件市场？MCP？自定义 HTTP？）
   - 知识库怎么做（切分策略、检索配置暴露了多少）
   - 状态和记忆存在哪
   - 怎么发布和分发
   - 可观测性和评估提供了什么
3. **重点读 Dify 的源码**，它是开源的完整平台，能让你看清一个平台的真实结构。
4. 总结出一个「Agent 平台的部件清单」，对照你自己的项目缺哪些。

**产出**：`s6-platform/platform_teardown.md`

**完成判据**：一份对比文档，含部件清单和各家取舍，最后回答「如果我的项目要平台化，最先要补的三个能力是什么」。

## U6.2 编排引擎设计（14h）

**目标**：亲手写一个编排引擎，理解 LangGraph 之类的框架到底在做什么。

**具体做什么**

1. 理解三种编排模型的适用场景：
   - **DAG**：步骤固定、可并行、无环。适合数据处理型流程
   - **状态机**：有条件跳转、可循环、状态显式。**适合大多数 Agent 场景**，LangGraph 走的就是这条路
   - **自由循环**：模型自己决定下一步。最灵活，最难控制和调试
2. **实现你自己的 mini 引擎**，支持：
   - 节点注册（每个节点是一个函数，输入输出都是状态）
   - 边定义，含条件边（根据状态决定走哪条）
   - 并行分支与汇合
   - 循环与最大迭代次数
   - 状态的合并策略（并行分支各自改了状态，怎么合）
3. 加上生产必需的三件事，**这三件才是框架的真正价值**：
   - **Checkpoint**：每个节点执行后落盘，可从任意节点恢复
   - **中断与恢复**：在指定节点前暂停，等外部输入（比如人工确认）后继续
   - **流式**：节点执行过程中往外推事件
4. 用你的引擎重写 M2 的 Agent，验证它真的能用。
5. **和 LangGraph 对比**：读它的源码，看你的实现和它差在哪。差距本身就是最好的学习材料。

**产出**：`s6-platform/mini_engine/`

**完成判据**：你的引擎能跑通一个含并行分支、条件跳转、中途暂停等待人工确认的完整流程，且杀掉进程后能恢复。

## U6.3 沙箱与执行环境（12h）

**目标**：让 Agent 能安全地执行不可信代码。

**背景**：U4.4 提到的两个 CVE 说明这件事有多难。**CVE-2026-22708** 里白名单被 shell 内建命令绕过；**CVE-2025-59532** 里沙箱的可写根目录被模型生成的路径重定义。两个案例的共同教训是：**沙箱边界必须由外部强制，绝不能由被沙箱的东西自己决定。**

**具体做什么**

1. **先写威胁模型**，再写代码。列清楚：攻击者能控制什么（模型的输出、用户的输入、被读取的文档）、你要保护什么（宿主文件系统、密钥、网络、其他用户的数据）、你接受什么风险。
2. 实现一个容器沙箱：
   - 用 Docker 跑一次性容器，执行完即销毁
   - 只读挂载代码，可写目录单独挂且限制大小
   - `--network none` 默认断网，需要网络的显式开且走白名单代理
   - 限制 CPU、内存、进程数、执行时间
   - 非 root 用户运行，丢弃所有不必要的 capability
3. **理解容器不是安全边界的完整答案**。需要更强隔离时了解 gVisor 和 Firecracker 微虚拟机的思路，知道它们解决什么问题就够，不用实现。
4. 实现能力白名单：允许哪些命令、哪些路径、哪些域名。**参考 CVE-2026-22708 的教训，白名单要在真正的执行点检查，而不是在命令字符串上做匹配。**
5. **自己攻击自己**：写 5 个逃逸尝试（读宿主文件、访问网络、耗尽资源、写超出配额、通过子进程绕过限制），确认全部失败。

**产出**：`s6-platform/sandbox/`、`s6-platform/sandbox/THREAT_MODEL.md`

**完成判据**：5 个逃逸尝试全部失败，且威胁模型里明确写出「我不防护什么」——**知道自己防不住什么，比假装什么都防得住重要得多。**

## U6.4 A2A 与多 Agent 互操作（10h）

**目标**：理解 Agent 之间怎么标准化协作。

**背景**：[A2A 协议](https://a2a-protocol.org)最初由 Google 开发，后捐给 Linux 基金会，现由技术指导委员会维护，成员来自 AWS、Cisco、Google、IBM Research、Microsoft、Salesforce、SAP、ServiceNow。协议已发布 v1.0。

**MCP 和 A2A 的分工**：MCP 解决 Agent 怎么用工具（纵向），A2A 解决 Agent 怎么互相委派任务（横向）。**企业架构里两者通常一起用**，不是二选一。

**具体做什么**

1. 读 A2A 规范，理解核心概念：
   - **Agent Card**：Agent 的自我描述，说明它能做什么、怎么调用、需要什么认证
   - **Task**：一次委派的任务，有生命周期和状态
   - **Message / Artifact**：交互的内容和产出物
2. 用官方 SDK 跑通示例。
3. **实战**：把你的项目拆成两个独立进程的 Agent（比如「检索 Agent」和「分析 Agent」），通过 A2A 完成一次跨 Agent 委派。
4. 想清楚几个工程问题：跨 Agent 的错误怎么传播、超时怎么处理、trace 怎么串起来（**trace id 必须跨 Agent 传递**）、权限怎么传递而不放大。
5. **诚实判断**：你的项目现在需要 A2A 吗。**大概率不需要**，但知道它存在、知道什么时候会需要，这本身就是价值。

**产出**：`s6-platform/a2a/`

**完成判据**：两个独立进程的 Agent 能通过 A2A 完成一次任务委派，且 Langfuse 里能看到跨 Agent 的完整 trace。

## U6.5 Mini Agent Runtime（20h）

**目标**：整合前面所有能力，做出一个别人能用的 Agent 运行时。**这是你的毕业设计。**

**具体做什么**

把这些部件组装成一个整体：

1. **编排引擎**（U6.2）：状态机 + checkpoint + 中断恢复 + 流式
2. **工具系统**：本地工具注册表 + MCP 客户端（U2.7）+ 权限声明（U4.4）
3. **记忆系统**（U2.4）：短期、工作、长期三层
4. **检索**（U2.5）：hybrid + rerank
5. **沙箱**（U6.3）：代码执行工具跑在容器里
6. **可观测性**（U3.5）：自动埋点，符合 OTel GenAI 约定
7. **评估**（U3.3、U3.4）：内置评估运行器
8. **配置化**：**用一个 YAML 就能定义一个新 Agent**，不改代码

配置文件长这样：

```yaml
name: 选题助手
model: 
  primary: claude-opus-5
  fallback: deepseek-v4-pro
prompt: prompts/topic_helper_v3.md
tools:
  - local: [search_notes, analyze_engagement]
  - mcp: [{server: feishu, tools: [read_base]}]
memory: {short: 20, long: true}
retrieval: {collection: notes, top_k: 5, rerank: true}
guardrails:
  max_turns: 15
  max_cost: 2.0
  confirm_before: [publish, delete]
eval: eval/topic_helper.yaml
```

**关键验收方式**：找一个朋友（或者用另一个你没做过的场景），**在不改你任何代码的前提下，只写一个 YAML 配置出一个新 Agent**。

**产出**：`s6-platform/runtime/`、完整的 README 和一个 quickstart

**完成判据**：一个陌生人照着你的 README，20 分钟内配出一个能跑的新 Agent。**这是对文档质量和抽象质量的双重考验，也是真实开源项目的标准。**

## U6.6 作品集与面试准备（14h）

**目标**：把 26 周的成果变成能讲清楚、有说服力的东西。

**具体做什么**

**一、整理作品集**（6h）

给六个里程碑各写一页，每页固定四段：

1. **问题**：解决什么，为什么值得做
2. **方案**：架构图 + 关键技术决策
3. **数据**：**这一段最重要**。评估分、成本、延迟、召回率，有前后对比更好
4. **取舍**：你放弃了什么、为什么、如果重做会怎么改

**取舍这一段是区分度最高的部分。** 只讲做了什么的人很多，能讲清楚为什么不做另一种方案的人很少。

**二、准备系统设计题**（4h）

练这三道，每道画出架构图并写出关键取舍：

1. 设计一个企业客服 Agent 平台，支持多租户、知识库隔离、人工接管
2. 设计一个能跑数小时的深度研究 Agent，要求可中断、可恢复、成本可控
3. 设计一套 Agent 的评估与发布流水线

**三、准备高频问题**（4h）

按这几组整理，每题写出你自己的答案，**尽量引用你项目里的真实数据**：

- **检索**：怎么提升召回、混合检索为什么有效、rerank 的代价、chunk 策略怎么选、多跳问题怎么办
- **幻觉**：怎么检测、怎么降低、怎么让模型承认不知道
- **评估**：评估集怎么建、LLM judge 怎么校准、怎么防止评估集饱和、离线分高线上差怎么办
- **上下文**：长上下文为什么衰减、压缩策略怎么选、上下文中毒怎么处理
- **多 Agent**：什么时候该拆、成本代价、上下文隔离的价值、错误怎么传播
- **成本**：怎么降本、缓存怎么用、路由怎么做、降本后怎么保证质量不掉
- **安全**：提示注入怎么防、间接注入为什么更危险、沙箱怎么设计、最小代理权是什么
- **工程**：断点续跑怎么实现、幂等怎么保证、灰度怎么做、trace 怎么设计

**产出**：`PORTFOLIO.md`、`s6-platform/interview_prep.md`

**完成判据**：对着作品集能连续讲 40 分钟不卡壳；30 个高频问题每题都有你自己的答案，且至少 10 题能引用你项目的真实数据。

## 26 周之后

学习不会在这里结束，但**方式要变**。往后靠三件事保持：

1. **持续维护你的主线项目**。真实用户的真实反馈，比任何课程都有价值。
2. **每月读三篇一手工程博客**。Anthropic Engineering 是密度最高的来源，看它的更新频率就知道这个领域一个月能变多少。
3. **参与一个开源项目**。从给文档提 PR 开始，慢慢到提 issue、修 bug、加功能。这是从「会用」到「会造」最有效的路径。
