## 0. 这份计划怎么用

三条规则，比计划本身更重要。

**每个单元都必须留下一个能跑的东西。** 不是笔记，是代码、是能打开的页面、是能贴出来的截图。看完视频没有产出，这个单元就不算完成。

**按单元推进，不按章节推进。** 每个单元标了预计耗时和「完成判据」。判据没达到就不勾选，宁可拖一周也不要虚勾。

**每周留 4 小时写复盘。** 在 `logs/` 目录下按 `2026-W37.md` 命名，写三件事：这周做出了什么、卡在哪、下周第一件事做什么。这份日志后面直接变成你的面试素材。

推荐目录结构：

```

├── README.md          # 本文件
├── logs/              # 每周复盘
├── s0-foundation/     # 各阶段代码
├── s1-llm/
```

第一天就 `git init` 并推到 GitHub，从此每个单元至少一个 commit。这个仓库本身就是作品集。

## 2. 每周节奏

20 小时的建议切法：

| 项 | 时长 | 说明 |
|---|---|---|
| 输入 | 5h | 看文档、读源码、看课程。输入永远是最小的一块 |

| 复盘与整理 | 4h | 周复盘、整理笔记、补测试、写 README |

工作日每天 2 小时，周末各 5 小时，是最容易坚持的分布。

一个反直觉但很关键的建议：**遇到卡点先自己撞 30 分钟，撞不动立刻问 AI，但要求它解释而不是给答案。** 零基础阶段最大的风险不是学得慢，是全程让 AI 代写、最后什么都不会。给自己定个规矩：S0 和 S1 阶段的代码，每一行你都要能口头解释。

## 3. 技术栈决策

一次定好，中途不换。选型理由都写在这里，以后有人问你「为什么用这个」你直接答得出来。

**主语言：Python。** Agent 生态的默认语言，主流 SDK 都是 Python 优先。包管理用 `uv`，比 pip/poetry 快一个数量级，2026 年已是新项目默认。

**第二语言：TypeScript。** 前端和小程序必须用，同时 Agent SDK 基本都有 TS 版本。TypeScript 在 2025 年 8 月已成为 GitHub 使用量第一的语言。S5 之前不用碰。

**后端框架：FastAPI。** 异步原生、自动生成 OpenAPI 文档、类型提示和 Pydantic 打通。

**Agent 框架：先手写，再 LangGraph，再看另外两个。**
- 手写：S2 前两周不用任何框架，自己写 ReAct 循环。不这样做，你会永远不知道框架在替你做什么。
- LangGraph：生产验证最充分的一个，Klarna 用它支撑 8500 万用户，显式状态机的设计让 token 成本比 CrewAI 低约 47%，配套的 checkpointing 和流式能力齐全。
- OpenAI Agents SDK / Claude Agent SDK：轻量、抽象少，Claude Agent SDK 的 MCP 集成最深。S2 末尾各花一天做对比实验即可。

2026 年框架之争基本结束了，几个主流选项都足够上生产。**不要在选框架上花超过一天。**

**协议：MCP 必学，A2A 了解。** MCP 已经赢下了「Agent 连工具」这一层，下载量 9700 万，Anthropic、OpenAI、Google、微软全部采纳。A2A 在 2026 年 4 月发布 1.0，超过 150 家组织在生产使用，负责「Agent 之间协作」。企业架构的标准组合就是：工具走 MCP，Agent 间委派走 A2A。

**检索：Postgres + pgvector 起步，不要一上来就上专用向量库。** 2026 年的明显趋势是专用向量数据库在企业 RAG 中份额下降，向量检索变成现有数据平台的一个能力。检索策略统一用 hybrid：BM25 + 向量，RRF 融合，再 rerank。混合检索的 MRR 是 66.4%，纯语义只有 56.7%。标准管线是「hybrid 召回 top-50 → rerank 到 top-5 → 喂给模型」，在 RAGAS 指标上能带来 15%–30% 的提升。

**可观测性：Langfuse 自托管。** 开源、可自部署、trace 和 eval 和成本分析在一个地方，对个人学习者是最优解。生产团队常见的另外三个是 LangSmith、Braintrust、Arize Phoenix。

**前端：Next.js App Router + TypeScript + Tailwind + Vercel AI SDK。** 2026 年的事实标准组合是 React 19 + Next.js 15 + TypeScript 5 + Tailwind v4。Next.js 之所以是 AI 应用首选，是因为 Server Components 让模型调用留在服务端、Server Actions 简化了写操作、以及原生流式支持省掉了自己搭 SSE 的工作。

**小程序：Taro。** 它用 React 语法，S5 学的 React 能直接复用。如果只做微信一个平台且要求性能极致，再考虑原生。

**模型：至少同时接三家。**
- 海外：Claude（Opus 5 / Sonnet 5）、GPT 系列
- 国内：豆包、通义千问、DeepSeek、Kimi
学会用统一抽象层（LiteLLM 或 Vercel AI SDK）屏蔽差异，这是大厂的标准做法，也是你后面做成本路由的前提。

## 4. 大厂真实业务流里的「基本操作」

这一节是你特别问的部分。下面每一条都是 2026 年在真实生产环境里默认要做、不做就会被 review 拦下来的事。学完整个计划，你应该对每一条都有亲手实践过。

**评估驱动，不靠体感。** 这是 demo 和生产之间最大的一道坎。改一版 prompt 就跑一次离线评估集，分数掉了就不发。没有评估集的 Agent 项目在大厂里根本进不了发布流程。招聘时 RAG、Agent、评估是最被看重的三项能力。

**全链路 trace。** 每一轮对话、每一次工具调用、每一次模型推理都要有 span，遵循 OpenTelemetry 的 GenAI 语义约定。出问题时你要能在 30 秒内定位到是哪一步的哪个 token 出的错。

**Prompt 和配置版本化。** Prompt 进 git，走 code review，有 diff 有回滚。线上跑的是哪个版本的 prompt，必须能在 trace 里查到。

**灰度发布与回滚。** 新版本先 5% 流量，看在线指标，再逐步放量。任何时候能一键回滚到上个版本。

**高危动作强制人工确认。** delete、send、pay、publish 这四类操作在 2026 年被普遍当作特权动作，必须有硬性确认和便捷回滚。这背后是「最小代理权」原则：不只限制凭证能访问什么，还要限制 Agent 被允许决定什么。

**成本可见。** per-session 的 token 用量和费用要有看板。上下文越长成本越高、质量还越差，所以省 token 和提质量往往是同一件事。

**上下文工程而非堆 prompt。** 2025 年之后的核心技能已经从 prompt engineering 转移到 context engineering。原因很实在：所有前沿模型在上下文变长时性能都会可测量地下降，而且远在窗口填满之前就开始下降。所以每一步都要决定哪些 token 值得占位置。

**工具接入走 MCP，Agent 协作走 A2A。** 不要给每个工具手写胶水代码。

**小模型分流 + 缓存降本。** 简单意图用小模型，复杂推理才上大模型，重复前缀开 prompt caching。

**线上 case 回流成评估集。** 生产里出现的失败 case，人工标注后进 golden set，永久防止回归。这是评估集唯一正确的增长方式。

**长任务用异步架构。** 阿里云的 AgentRun 基于函数计算的异步调用，单个函数最长可跑 24 小时，中间结果 SSE 流式推送，会话状态持久化。这就是长任务 Agent 的典型形态：不要在一个 HTTP 请求里跑完。

**安全按分层防御做。** 2026 年的策略栈有六层：权限阶梯、pre-tool 钩子、操作系统级沙箱、人工中断、受众绑定的 MCP token、以及 OWASP Agentic Top 10 作为威胁地图。提示注入至今仍是生产事故的头号来源，OWASP 已把「Agent 技能供应链攻击」列入十大风险。

顺带一个行业现实：Gartner 警告，到 2027 年超过 40% 的 agentic AI 项目可能被取消，原因是价值不清、成本上升、治理薄弱。**这恰恰说明为什么 S3 和 S4 这两个阶段的内容比 S2 更值钱** —— 会做 demo 的人很多，能把 Agent 做到可评估、可运维、成本可控的人很少。

## 5. 阶段与单元明细

### Stage 0 · 工程地基（W1–W3，60h）

零代码基础的人最容易犯的错，是直接跳到 LLM 调用，结果第一次遇到虚拟环境冲突就卡三天。这三周是投资，不是绕路。

- [ ] **U0.1 命令行与文件系统**（4h）
  学 `cd ls mkdir cp mv rm cat grep find` 和管道，理解绝对路径与相对路径，会看和改 `~/.zshrc`。
  *判据*：不用 Finder，纯命令行完成「新建项目目录、下载一个文件、搜索其中包含某关键词的行、把结果写进新文件」。

- [ ] **U0.2 Git 与 GitHub**（6h）
  `init add commit push pull branch merge`，理解 staging area，会解决一次简单冲突，会写 `.gitignore`。
  *判据*：本仓库推上 GitHub，有至少 5 个语义清晰的 commit，成功制造并解决一次 merge 冲突。

- [ ] **U0.3 Python 语法基础**（10h）
  变量、类型、条件、循环、函数、list/dict/set/tuple、字符串处理、文件读写、异常。
  *判据*：不看资料写出「读 CSV、按某列分组统计、输出 JSON」的脚本。

- [ ] **U0.4 Python 工程化**（8h）
  类与对象、模块与包、`uv` 管理虚拟环境和依赖、类型注解、Pydantic 数据模型、`logging`。
  *判据*：把 U0.3 的脚本重构成有 `pyproject.toml`、有包结构、全量类型注解、用 Pydantic 定义数据模型的项目。

- [ ] **U0.5 HTTP 与 API**（6h）
  HTTP 方法与状态码、Header、JSON、认证方式（API Key / Bearer / OAuth）、用 `httpx` 发请求、读 OpenAPI 文档。
  *判据*：不看教程，只读官方文档，调通一个你没用过的第三方 API。

- [ ] **U0.6 FastAPI 写服务**（8h）
  路由、请求体校验、响应模型、依赖注入、异步、自动文档、错误处理。
  *判据*：一个有 4 个以上端点、带完整参数校验的 API，能在 `/docs` 里点着跑通。

- [ ] **U0.7 测试**（6h）
  pytest 基础、fixture、参数化、mock 外部依赖、覆盖率。
  *判据*：给 U0.6 的服务写测试，覆盖率 70% 以上，包含至少一个 mock 掉外部 HTTP 的用例。

- [ ] **U0.8 数据库基础**（6h）
  SQL 增删改查、JOIN、索引、事务，SQLAlchemy 或 SQLModel，Postgres 本地跑起来。
  *判据*：U0.6 的服务接上 Postgres，数据能持久化。

- [ ] **U0.9 Docker**（6h）
  镜像与容器、Dockerfile、docker compose、端口与卷挂载、环境变量。
  *判据*：`docker compose up` 一条命令同时起服务和数据库。

**M0 里程碑**：一个带测试、带数据库、能一键 Docker 启动的 REST API，README 写清楚怎么跑。这就是你的第一个作品。

### Stage 1 · LLM 基础与上下文工程（W4–W6，60h）

- [ ] **U1.1 LLM 工作原理（工程视角）**（6h）
  Token 与分词、上下文窗口、自回归生成、temperature / top_p / max_tokens 的实际影响、为什么会幻觉。不推公式，用实验建立直觉。
  *判据*：写一份实验报告，用同一个 prompt 在 5 组不同采样参数下各跑 10 次，说明差异和你的结论。

- [ ] **U1.2 多家模型 API 接入**（8h）
  接通 Claude、OpenAI、以及国内至少一家（豆包 / 通义 / DeepSeek / Kimi）。理解各家在 system prompt、多模态、流式上的差异。用 LiteLLM 做统一抽象。
  *判据*：一个函数，换个参数就能切换四家模型，输出格式统一。

- [ ] **U1.3 结构化输出**（8h）
  JSON mode、tool/function 定义、Pydantic schema 约束、解析失败时的重试策略。
  *判据*：一个信息抽取脚本，输入 20 篇非结构化文本，100% 返回符合 schema 的对象，含失败重试。

- [ ] **U1.4 Prompt 工程**（8h）
  角色设定、few-shot、思维链、输出格式约束、负面指令的陷阱、prompt 版本管理。
  *判据*：对同一任务做 5 版 prompt，用固定的 20 条测试样本对比，用表格说明哪版好、好在哪。这是你第一次做「评估」。

- [ ] **U1.5 上下文工程**（10h）
  精读 Anthropic 的《Effective Context Engineering for AI Agents》。理解上下文是有限资源、长上下文导致的性能衰减、系统提示 / 工具定义 / 检索结果 / 历史消息之间如何取舍。实践压缩、摘要、选择性保留三种策略。
  *判据*：构造一个上下文超长的场景，实现三种压缩策略，用数据说明每种策略对质量和成本的影响。

- [ ] **U1.6 成本、延迟与流式**（8h）
  计费模型、prompt caching、流式输出（SSE）、首 token 延迟 vs 总延迟、批处理。
  *判据*：给你的调用封装加上 token 计数和费用统计，实现流式输出，并测出开启 caching 前后的成本差。

- [ ] **U1.7 本地模型跑一次**（6h）
  用 Ollama 跑一个开源模型，理解量化、显存占用、本地推理的能力边界。
  *判据*：本地模型接进你的统一抽象层，作为第五个可选 provider。

- [ ] **U1.8 复盘与整理**（6h）
  整理 S1 的所有代码成一个可复用的 `llm_kit` 包。

**M1 里程碑**：一个命令行 LLM 工具，支持多家模型切换、结构化输出、流式显示、成本统计、prompt 版本管理。

### Stage 2 · Agent 核心（W7–W10，80h）

**本阶段第一件事：确定你的主线项目选题。** 后面四个阶段都围绕它展开。

- [ ] **U2.1 手写 Agent 循环**（10h）
  不用任何框架。自己实现：系统提示 → 模型返回 tool call → 执行工具 → 结果回填 → 再次调用 → 直到给出最终答案。加上最大轮次限制和错误处理。
  *判据*：200 行以内的纯 Python，能用 3 个工具完成一个需要多步的任务。这段代码你要能逐行讲明白。

- [ ] **U2.2 工具设计**（8h）
  工具描述怎么写模型才用得对、参数 schema 设计、工具返回值该给多少信息、工具太多时怎么办（分组、动态加载）、幂等与副作用。
  *判据*：设计 8 个工具，做一组对照实验，说明工具描述的写法如何影响调用准确率。

- [ ] **U2.3 规划与反思**（8h）
  ReAct、Plan-and-Execute、Reflexion 三种模式的实现与对比。什么时候该先规划、什么时候直接循环。
  *判据*：同一个任务用三种模式各实现一遍，对比步数、成本、成功率。

- [ ] **U2.4 记忆系统**（10h）
  短期（对话历史）、长期（跨会话事实）、工作记忆（当前任务状态）的区别与实现。事实的时效性问题：检索到的信息是否已经过期。
  *判据*：你的 Agent 能记住上周会话里用户说过的偏好，并在事实被更新后使用新值。

- [ ] **U2.5 RAG 与混合检索**（12h）
  文档切分策略、embedding 模型选型、pgvector 建库、BM25 全文检索、RRF 融合、cross-encoder rerank。搭出标准管线：hybrid 召回 top-50 → rerank top-5 → 生成。
  *判据*：在你自己的 50 篇以上文档上跑通，并用 20 条问答对量化对比「纯向量」和「hybrid + rerank」的召回率差异。

- [ ] **U2.6 多 Agent 编排**（10h）
  Orchestrator-Worker、Handoff、Subagent 三种模式。子 Agent 的上下文隔离为什么重要。什么时候多 Agent 是过度设计（大多数时候是）。
  *判据*：把主线项目里一个复杂子任务拆成子 Agent，用数据说明拆了比不拆好在哪；如果没有更好，写清楚为什么。

- [ ] **U2.7 MCP 实战**（10h）
  MCP 的架构（server / client / transport）、写一个自己的 MCP server 暴露 3 个工具、在 Claude Code 或你的 Agent 里接入、理解 tool / resource / prompt 三种原语。
  *判据*：你写的 MCP server 能被至少两个不同的客户端使用。

- [ ] **U2.8 框架横评**（12h）
  用 LangGraph、OpenAI Agents SDK、Claude Agent SDK 各实现一遍同一个 Agent。对比：状态管理、流式、错误恢复、可观测性接入、代码量。
  *判据*：一份带代码和数据的对比文档，最后给出你主线项目选哪个框架、为什么。

**M2 里程碑**：你的主线 Agent 第一个能用的版本。能真的帮你干一件事。

### Stage 3 · 评估与可观测性（W11–W14，80h）

**这是整个计划里最重要的一个阶段。** 会做 Agent 的人很多，能证明自己的 Agent 有多好的人很少。面试里这也是最能拉开差距的部分。

- [ ] **U3.1 为什么传统测试失效**（4h）
  LLM 的非确定性如何击穿单元测试假设、什么该断言什么不该、评估的三个层次（组件级 / 轨迹级 / 端到端）。
  *判据*：列出你的 Agent 里哪些部分可以用传统测试、哪些必须用评估，说明理由。

- [ ] **U3.2 构建评估集**（12h）
  从零手写 30 条种子样本，标注期望输出。设计标注规范。理解为什么评估集质量决定一切。
  *判据*：一份 50 条以上的 golden set，含输入、期望输出、评分标准，存成版本化的文件。

- [ ] **U3.3 规则型评分器**（8h）
  精确匹配、包含关系、正则、JSON schema 校验、工具调用序列比对、数值容差。能用规则的绝不用模型。
  *判据*：为你的评估集实现至少 5 种规则评分器。

- [ ] **U3.4 LLM-as-judge**（10h）
  评分 prompt 设计、评分标准的量化、成对比较 vs 绝对打分、judge 自身的偏见（位置偏见、长度偏见）、用人工标注校准 judge。
  *判据*：你的 judge 和你自己的人工打分在 30 条样本上的一致率超过 85%，并给出一致率数据。

- [ ] **U3.5 Trace 与 OpenTelemetry**（12h）
  自托管 Langfuse，接入你的 Agent，遵循 OTel GenAI 语义约定打点。理解 span 的嵌套结构：agent → llm call → tool call → retriever。
  *判据*：在 Langfuse 里能看到一次完整任务的全链路 trace，每个 span 有输入输出、token 数、耗时、成本。

- [ ] **U3.6 在线评估**（10h）
  采样线上流量做自动评分、用户反馈信号（点赞、重试、放弃）的采集、失败 case 自动回流到评估集。
  *判据*：跑通「线上失败 case → 人工确认 → 进 golden set → 下次回归自动覆盖」这个闭环，至少走通 3 个真实 case。

- [ ] **U3.7 评估进 CI**（12h）
  GitHub Actions 里跑评估、设置分数门禁、prompt 改动触发评估、结果生成报告贴到 PR。
  *判据*：提一个故意让 prompt 变差的 PR，CI 自动拦下来并给出分数对比。

- [ ] **U3.8 成本与延迟看板**（12h）
  per-session token 统计、按模型/工具/用户维度拆分成本、P50/P95/P99 延迟。
  *判据*：一个能回答「上周哪个工具最烧钱」「哪一步最慢」的看板。

**M3 里程碑**：M2 的 Agent 现在有了完整的评估体系、全链路 trace、CI 门禁和成本看板。**这一份东西拿去面试，比十个 demo 都管用。**

### Stage 4 · 生产化（W15–W18，80h）

- [ ] **U4.1 12-Factor Agents**（6h）
  精读 humanlayer/12-factor-agents（约 2.35 万 star）。逐条对照你的 Agent，列出不合规的地方。
  *判据*：一份 12 条的自查表，每条写明现状和改进项。

- [ ] **U4.2 状态与持久化**（10h）
  会话状态存储、checkpoint 与断点续跑、幂等设计、并发控制。
  *判据*：任务跑到一半杀掉进程，重启后能从断点继续，不重复执行已完成的副作用操作。

- [ ] **U4.3 长任务架构**（12h）
  异步任务队列、SSE 流式推送中间结果、超时与重试、任务状态查询接口。参考阿里云 AgentRun 的形态：长任务不占 HTTP 连接，状态持久化，中间结果流式推。
  *判据*：一个跑 10 分钟以上的任务，客户端断开重连后仍能看到进度。

- [ ] **U4.4 安全与权限**（14h）
  提示注入的攻防实验、OWASP Agentic Top 10 逐条对照、权限阶梯设计、工具白名单、pre-tool 钩子、操作系统级沙箱、高危动作的人工确认（delete / send / pay / publish）、MCP token 的受众绑定。
  *判据*：写 10 个提示注入攻击样本打自己的 Agent，记录哪些成功了，逐个修复，再跑一遍全部失败。

- [ ] **U4.5 成本治理**（10h）
  模型路由（简单意图走小模型）、prompt caching、上下文压缩、结果缓存、限流。
  *判据*：在评估分数下降不超过 2% 的前提下，把单次任务成本降低 40% 以上，给出前后数据。

- [ ] **U4.6 灰度与回滚**（10h）
  版本化发布、按比例放量、在线指标监控、一键回滚、A/B 实验设计。
  *判据*：同时跑两个 prompt 版本，按 90/10 分流，看板上能分别看到两版的评分和成本。

- [ ] **U4.7 部署上线**（12h）
  容器化、云端部署（国内选阿里云/腾讯云函数计算，海外选 Fly.io / Railway / Vercel）、环境变量与密钥管理、健康检查、日志收集、告警。
  *判据*：一个真实可访问的线上地址，有健康检查，出错时你的手机能收到告警。

- [ ] **U4.8 SLO 与值班**（6h）
  定义可用性、延迟、质量三类 SLO，设置告警阈值，写一份 runbook。
  *判据*：一份 runbook，写清楚三种典型故障的排查步骤。

**M4 里程碑**：M2 的 Agent 真的上线了，有灰度、有告警、有 SLO、有成本控制。

### Stage 5 · 产品外壳：网站 / App / 小程序（W19–W22，80h）

- [ ] **U5.1 TypeScript 基础**（10h）
  类型系统、接口、泛型、联合类型、类型推断、`tsconfig`。有 Python 基础后这块会快很多。
  *判据*：把 S1 的 `llm_kit` 用 TypeScript 重写一个精简版。

- [ ] **U5.2 前端基础与 React**（14h）
  HTML/CSS 够用即可、Tailwind v4、React 组件、hooks、状态管理、受控组件。
  *判据*：一个纯前端的多轮对话界面，消息能增删改，状态管理清晰。

- [ ] **U5.3 Next.js App Router**（12h）
  路由、Server Components、Server Actions、数据获取、布局、加载与错误状态。理解为什么 AI 应用适合它：模型逻辑留在服务端、写操作变成普通函数调用、流式原生支持。
  *判据*：U5.2 的界面迁到 Next.js，模型密钥不出现在浏览器端。

- [ ] **U5.4 Vercel AI SDK**（12h）
  统一的模型接口、流式 UI、工具调用的过程可视化、生成式 UI。
  *判据*：前端能实时看到 Agent 的思考过程和每一次工具调用，而不是等一个最终结果。

- [ ] **U5.5 认证与数据**（10h）
  用户登录（Clerk 或 Auth.js）、数据库接入、按用户隔离数据、订阅与实时更新。
  *判据*：多个用户各自登录，会话历史互不可见。

- [ ] **U5.6 小程序**（14h）
  Taro 基础、复用 React 技能、小程序的能力边界与审核规则、微信登录、与你后端的联调。
  *判据*：一个能在微信开发者工具里跑起来的小程序，调通你的 Agent 后端。

- [ ] **U5.7 上线与打磨**（8h）
  Vercel 部署、域名、SEO 基础、移动端适配、加载性能。
  *判据*：手机浏览器打开流畅可用。

**M5 里程碑**：你的 Agent 现在有了网页版和小程序版，可以直接发给别人用。

### Stage 6 · 平台与基建 + 面试准备（W23–W26，80h）

- [ ] **U6.1 拆解主流 Agent 平台**（10h）
  对比 Coze、Dify、腾讯 WorkBuddy、阿里悟空、AgentRun。看它们的产品形态、编排模型、扩展方式。理解大厂为什么走「平台化 + 开源化」双轮驱动。
  *判据*：一份平台对比文档，说明各家的编排抽象差异，以及你的项目如果要平台化该长什么样。

- [ ] **U6.2 编排引擎设计**（14h）
  DAG、状态机、自由循环三种编排模型的取舍。LangGraph 为什么用显式状态机，以及这个选择如何带来更低的 token 成本。
  *判据*：手写一个能跑 DAG 和状态机两种模式的 mini 编排引擎，支持并行节点和条件分支。

- [ ] **U6.3 沙箱与执行环境**（12h）
  为什么 Agent 执行代码必须隔离、容器沙箱、微虚拟机、能力白名单。研究几个真实 CVE：CVE-2026-22708 通过允许列表内的命令污染 Cursor 的执行环境、CVE-2025-59532 中 Codex CLI 的输出可以重定义自己的沙箱边界。
  *判据*：实现一个能安全执行不可信 Python 代码的沙箱，并写出你的威胁模型。

- [ ] **U6.4 A2A 与多 Agent 互操作**（10h）
  A2A 1.0 的协议结构、Agent Card、任务委派、与 MCP 的分工（MCP 给 Agent 手，A2A 给 Agent 同事）。
  *判据*：两个独立进程的 Agent 通过 A2A 完成一次跨 Agent 的任务委派。

- [ ] **U6.5 Mini Agent Runtime**（20h）
  把前面所有东西整合：自己的编排引擎 + 工具注册表 + MCP 接入 + 记忆 + trace + 评估 + 沙箱。这是你的毕业设计。
  *判据*：别人能用你的 runtime，在不改你代码的前提下，配置出一个新的 Agent。

- [ ] **U6.6 作品集与面试**（14h）
  整理六个里程碑成作品集、每个项目写清楚「问题—方案—数据—取舍」、准备系统设计题（设计一个客服 Agent 平台）、准备八股（RAG 优化、幻觉治理、评估方法、多 Agent 通信、成本优化）。
  *判据*：一份能讲 40 分钟的作品集，和一份写满 30 个高频问题的答案文档。

**M6 里程碑**：一个可复用的 Agent runtime，一份完整作品集。

## 8. 常见坑

**跳过 S0 直接学 Agent。** 最常见也最致命。没有工程基础，你后面每一个环境问题都会卡住半天，而且写出来的代码没人敢用。

**框架学了三个，循环没写过一次。** U2.1 手写循环是整个 S2 的地基。跳过它，你永远只会调 API，不会 debug。

**评估集永远只有五条。** 五条样本的评估等于没有评估。50 条是最低线，而且必须来自真实场景。

**上下文能塞就塞。** 所有前沿模型在上下文变长时性能都会下降，而且远在窗口填满前就开始。塞得多不等于效果好。

**多 Agent 上瘾。** 大多数场景单 Agent 加好工具就够了。拆多 Agent 之前先用数据证明单 Agent 不行。

**用 AI 写完所有代码然后什么都不会。** S0 和 S1 的代码必须每行能讲。S2 之后可以放开用 AI 加速，但架构决策必须是你自己做的。

**只做不写。** 每周 4 小时的复盘不是浪费，它是把「做过」变成「会讲」的唯一途径，而面试考的正好是后者。

**同时开三个项目。** 主线只有一个。S2 定的那个题，做到 S6 结束。深度远比数量值钱。
